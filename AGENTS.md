# Reference branch agent guide

This orphan branch is a self-contained technical reference corpus. It preserves
expensive-to-recover technical knowledge so future agents can reuse precise
results without repeating broad source crawls, experiments, or synthesis. The
corpus is general-purpose and is not limited to Anneal or zerocopy.

## Authority

The current tip of `refs/heads/reference` is the canonical corpus state. Git
history preserves provenance; historical trees are not competing current
documentation.

This branch is authoritative about its own organization, interpretation, and
maintenance. It is not authoritative about the systems it documents. Upstream
source code, specifications, release artifacts, and other primary sources retain
their own authority.

All documentation needed to interpret or maintain the corpus must live on this
branch. Files elsewhere may point here, but must not be required to determine
what the corpus means or how it is maintained.

`AGENTS.md` governs branch-wide behavior. `FORMAT.md` governs report semantics and
format. `tools/reference.py` mechanically enforces only a subset of those written
contracts. If the tool disagrees with the written contract, treat that as a
tooling defect rather than inferring a new corpus rule from the implementation.

The published `reference` history is linear. The orphan root has no parents and
every later published commit has exactly one parent, its predecessor on
`reference`. Do not introduce merge commits or otherwise graft another history
into this branch.

This repository is public. Do not commit credentials, private data, proprietary
material, or unnecessary large source mirrors.

## Self-validating candidates

A candidate is validated by the `tools/reference.py` contained in that same
candidate. The validator locates the candidate lexically from its own path; it has
no option for validating a different root. This keeps the validation rules and
the tree they validate in one versioned state.

Structurally meaningful filesystem names are exact and case-sensitive, matching
the names that will appear in Git. The validator obtains those names and their
file/directory types from directory entries without following symlinks. It does
not infer structural identity from case-insensitive or symlink-resolving path
lookup.

A Git worktree is a valid candidate only when the bytes and entries relevant to
the corpus are exactly the ones that will be published. Untracked files, unstaged
edits, ignored files, submodule working trees, or other worktree state can make a
filesystem differ from the Git tree eventually published. The validator does not
inspect Git state.

Publication must preserve the validated candidate. When using Git object APIs,
construct blobs and the candidate tree from the validated bytes and verify their
identities before advancing the branch. When using Git, validate a materialization
of the commit/tree that will actually be pushed, or otherwise establish that the
commit contains the same validated content.

Before publication, run:

```console
python3 tools/reference.py check
```

After changing a report package name or `REPORT.json`, regenerate the catalog and
validate:

```console
python3 tools/reference.py catalog
python3 tools/reference.py check
```

A `REPORT.md`-only or support-artifact-only change does not alter the catalog.

When changing `tools/reference.py` or its tests, also run:

```console
python3 -m unittest discover -s tests -v
```

The validator and tests require Python 3.10 or newer and otherwise use only the
Python standard library. Passing validation establishes machine-representable
corpus invariants only; it does not establish that report prose or technical
claims satisfy `FORMAT.md`.

## Reports

Each immediate child directory of `reports/` is one report package. A package
contains `REPORT.json`, `REPORT.md`, and any additional report-owned material.
Only the package directory and those two root files have structural meaning to the
validator. Other package contents are opaque to it.

Before writing or revising a report, read `FORMAT.md`. Reports must identify the
subjects actually examined, bind claims to supporting evidence, and preserve
important investigation limits. Package paths are navigation handles and do not
carry technical applicability semantics.

When upstream software changes, an older report remains a report about the subject
it identifies. Add another report when preserving newer behavior is useful. When
the corpus's account of its identified subject is wrong, correct the current
report; Git history preserves the earlier text as provenance.

Prefer reports that avoid future research cost: results that required substantial
synthesis, are easy to misunderstand, control later engineering decisions, depend
on fragmented sources, are expensive to reproduce, or admit a cheap probe that
can replace future rediscovery.

## Generated state

`CATALOG.json` is canonical generated bytes derived from report package names and
validated `REPORT.json` metadata. It is navigation only, not source state. Do not
edit it manually or treat it as independent technical evidence.

Regeneration discards the existing catalog entry and writes canonical bytes from
source. It need not preserve the old catalog's inode, links, permissions, or
contents. If regeneration is interrupted, the catalog may be missing or partial;
run `catalog` again and then `check`.

## Publication

Direct publication to `reference` is the normal workflow; a pull request is not
required unless the user explicitly requests one.

Treat publication as an atomic transition between coherent corpus trees:

1. Read the current remote `reference` tip before writing.
2. Construct the complete candidate from that tip.
3. Regenerate derived state and validate the candidate with its own validator.
4. Construct a commit whose sole parent is the observed `reference` tip and whose
   tree preserves that candidate.
5. Advance `refs/heads/reference` only by fast-forward to the validated candidate.
6. If another writer advanced the branch, fetch the new tip, reconcile, validate
   again, and retry.
7. Read back the resulting remote tree and verify the intended change.

For a multi-file change, do not publish files one at a time to the canonical ref.
Create the complete candidate tree or commit first, then move the branch ref once.
A sequential per-file API is unsuitable when it exposes intermediate trees.

The repository should enforce three matching branch rules for
`refs/heads/reference`: prohibit deletion, prohibit non-fast-forward updates, and
require linear history. These rules protect the history/ref invariant; they do not
replace candidate validation.

Do not force-push, rewrite published history, or delete the branch during normal
operation. Keep commits coherent, but readers should not need to replay history
to understand the current tree.

Do not add GitHub Actions or make routine corpus publication depend on repository
CI without explicit user direction. The intended maintenance path is lightweight,
deterministic validation followed by direct fast-forward publication.
