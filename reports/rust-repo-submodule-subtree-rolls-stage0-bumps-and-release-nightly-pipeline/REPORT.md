# Rust Repository Submodule and Josh Subtree Rolls, Stage-0 Bootstrap Bumps, PGO/BOLT Optimization, and Release Promotion Pipeline

## Summary

The `rust-lang/rust` repository is not a self-contained monorepo: at commit `412be32a6a189d9a28922beee178bc0abee9d492` (`1.102.0-nightly`, `2026-11-18`), it integrates **13 Git submodules** (`160000` gitlinks configured with `shallow = true` in `.gitmodules:1-53`), **11 bidirectional `josh` Git subtrees** governed by per-directory `josh-sync.toml` manifests (`rust-lang/josh-sync` at `8ce49808a529d3df3283fcdc7eceff1d034578b3`), **45 non-test `Cargo.lock` dependency graphs** (`13` workspace lockfiles audited by `src/tools/tidy/src/deps.rs:131-240`), and **576 SHA-256-pinned `stage0` bootstrap artifacts** (`src/stage0:1-600`) before compiling, PGO/BOLT-optimizing (`src/tools/opt-dist`), packaging (`src/bootstrap/src/core/build_steps/dist.rs` + `src/tools/rust-installer` + `src/tools/build-manifest`), signing, recompressing, and atomically promoting releases (`rust-lang/promote-release` at `9407dc9fe0a529c6d55b66ad54f75531eb34e51a`).

Six structural invariants govern how external trees, bootstrap compilers, and release artifacts move through `rust-lang/rust`:

1. **Multi-version C++ backend decoupling and CI cache invalidation (`13` submodules):** `src/llvm-project` (`08ec928a5bd1866f4008c8ad216166ca685fd380`, tracking branch `rustc/23.1-2026-07-22`) advances via upstream `release/23.x` merges and Rust-specific cherry-picks between major LLVM branch cuts (`src/doc/rustc-dev-guide/src/backend/updating-llvm.md:15-90`), while `compiler/rustc_llvm/llvm-wrapper/` (`8` files, `4,339` lines) maintains **29** `#if LLVM_VERSION_{GE,LT}` preprocessor guards (`12` at `23.0`, `17` at `24.0`) so `rustc` simultaneously builds against `system-llvm` `>= 22` (`src/bootstrap/src/core/build_steps/llvm.rs:818`), in-tree LLVM `23.1`, and upcoming LLVM `24` `main`. Prebuilt `download-ci-llvm` tarballs (`rust-dev-{version}-{triple}.tar.xz` across `30` host triples, `3` with LLVM assertions) invalidate by resolving the latest `bors@rust-lang.org` merge commit touching `LLVM_INVALIDATION_PATHS = ["src/llvm-project", "src/bootstrap/download-ci-llvm-stamp", "src/version"]` using `--author-date-order` before `--first-parent` so second-parent Josh subtree merges cannot mask `rustc` commits (`llvm.rs:315-320`, `src/build_helper/src/git.rs:174-258`). Meanwhile, `src/gcc` (`e1c6e07b095d091177376a163da44039475e05e3`) is lockstep-checked against `compiler/rustc_codegen_gcc/libgccjit.version` by `src/tools/tidy/src/gcc_submodule.rs:9-57`, `src/tpde` (`050927ee81dc11a9e599fa2524ff0eef16daf51a`, added after `1.99.1`) requires an in-tree dynamically linked LLVM (`llvm.rs:2413-2420`), and `rust-toolstate` (`src/bootstrap/src/core/build_steps/toolstate.rs:70-84`) has narrowed exclusively to the **6 documentation book submodules** (`5` release-blocking `STABLE_TOOLS` after day `35` of the `42`-day cycle, plus `1` `NIGHTLY_TOOLS` `embedded-book`).
2. **Bidirectional `josh-proxy` history filtering (`11` subtrees):** Components requiring atomic co-evolution with unstable `rustc_private` or `core` internals (`clippy`, `miri`, `rust-analyzer`, `rustfmt`, `rustc_codegen_cranelift`, `rustc_codegen_gcc`, `portable-simd`, `stdarch`, `compiler-builtins`, `hashbrown`, and `rustc-dev-guide`) synchronize via `rustc-josh-sync` over local `josh-proxy` (`127.0.0.1:42042`). Five subtrees use `pull-mode = "Nightly"` (updating `rust-toolchain.toml`) and six use `pull-mode = "Latest"` (tracking a `rust-version` commit SHA). Every outbound `push` from a standalone repository to `rust-lang/rust` executes a mandatory `roundtrip_check` (`rust-lang/josh-sync` `src/sync.rs:407-442`) verifying that re-filtering the pushed `rust-lang/rust` branch through `josh-proxy` reproduces `HEAD` bit-for-bit.
3. **One-train-step `stage0` bootstrap coupling (`src/stage0` + `src/tools/bump-stage0`):** On `main` (`src/ci/channel = nightly`, `src/version = 1.102.0`), `bump-stage0` (`src/tools/bump-stage0/src/main.rs:126-223`) pins `stage0` `rustc`/`cargo`/`rust-std`/`clippy` to the current `beta` (`1.101.0-beta.1` at `bbcdfd90a3f81ca2a5f6d69b943a6ff0d8582102`) and pins stage0 `rustfmt` (plus a matching `rustc-nightly-*` tarball supplying `librustc_driver` shared libraries) to `nightly` (`ac8310ba643a3796cbe77d2e06944d7c8513999f`). On `beta` and `stable` (`1.N.Y`), `bump-stage0` drops `rustfmt_*` and pins `stage0` to the prior minor stable channel `1.{N-1}` (as verified on `1.99.1` at `58cf8f9c35b355199727627d07ae34a4e2846d67`, whose `stage0` pins `1.98.0` at `88d9e12ae178fab0fb5cc050a94da85685d449ea`). Stage skew is bridged by passing `--cfg=bootstrap` strictly when `build_compiler.stage == 0` while passing `--check-cfg=cfg(bootstrap)` across all stages (`src/bootstrap/src/core/builder/cargo.rs:90-98,863-956`).
4. **Asymmetric host optimization in `src/tools/opt-dist`:** Official release builds do not apply identical optimizations across Tier-1 hosts. Only `x86_64-unknown-linux-gnu` runs the full five-phase `opt-dist` pipeline: Stage 1 PGO across `rustc`, `cargo`, `rustdoc`, `clippy`, and `rustc_codegen_cranelift` (`9` `RUSTC_PGO_CRATES` / `7` `BACKEND_PGO_CRATES`), Stage 2 LLVM PGO (`7` `BACKEND_PGO_CRATES`), and Stage 3 post-link `llvm-bolt` binary rewriting (`-reorder-blocks=ext-tsp -reorder-functions=cdsort -split-functions -split-strategy=cdsplit -split-all-cold -jump-tables=move -icf=all`) on both `libLLVM.so*` and `librustc_driver-*.so`. `aarch64-unknown-linux-gnu` runs Rust + dynamic-LLVM PGO with ThinLTO (`use_bolt = false`), `x86_64-pc-windows-msvc` runs Rust + static-LLVM PGO (`shared_llvm = false`, `use_bolt = false`, requiring extra `rustc` relinks), and `aarch64-pc-windows-msvc` plus both macOS hosts (`x86_64-apple-darwin`, `aarch64-apple-darwin`) bypass `opt-dist` completely (relying on ThinLTO + `codegen-units = 1` on macOS).
5. **Deterministic installer synthesis and two-stage atomic promotion:** `dist.rs` (`30` `Step`/`CommandLineStep` structs) emits `rust-installer` v3 tarballs (`override_file_mtime = 1153704088`, reversed-byte-suffix file ordering for LZMA locality) and `build-manifest` v2 TOML descriptors (`23` `PkgType` variants, `12` `-preview` renames, `7` nightly-only gates). In production, `promote-release` strips CI staging signatures, prunes unshipped CI tarballs (`rust-dev`, `gcc-dev`, `bootstrap`, `build-manifest`), recompresses every shipped tarball at maximum `gzip -9` and custom-dictionary `xz` preset-9 settings across 72 vCPUs, OpenPGP-signs `.asc` detached signatures, smoke-tests via `rustup` against a local Hyper server, uploads `/dist/YYYY-MM-DD/` **first**, and overwrites top-level `/dist/channel-rust-*.toml` **second** before purging CloudFront/Fastly caches and updating `manifests.txt` under S3 `--if-match` ETag optimistic concurrency (`promote-release` `src/lib.rs:117-260,661-750`).
6. **Mechanically audited backport provenance:** `src/tools/cherry-pick.sh` stamps `(backport-of: <sha>)` trailers onto cherry-picked commits, and `src/ci/scripts/verify-backported-commits.sh` runs `git cherry` on `beta` and `stable` to reject any non-patch-identical commit lacking either a valid `backport-of: <default-branch-sha>` reference or an explicit `backport-of: nothing` release-bump declaration.

#### 1.2 `src/llvm-project` Fork Lifecycle and Multi-LLVM C++ API Bridging (`compiler/rustc_llvm`)

`rust-lang/llvm-project` follows a two-cadence branch discipline documented in `src/doc/rustc-dev-guide/src/backend/updating-llvm.md:15-90`:

- **Point updates and Rust-specific cherry-picks (`rustc/23.1-2026-07-22`):** For production stability, `main` tracks a `rustc/<major>.<minor>-YYYY-MM-DD` branch forked from upstream `llvm/llvm-project`'s `release/<major>.x` branch (`updating-llvm.md:18-48`). Maintainers merge upstream LLVM point tags (for example, `1b9c0d5ff9bbe7634aead059efe6b11a7eeba145` merged `llvmorg-23.1.1` into `rustc/23.1-2026-07-22` prior to `1.99.1`) and cherry-pick miscompilation fixes or Rust codegen enhancements ahead of upstream point releases (`08ec928a5bd1866f4008c8ad216166ca685fd380` on `1.102.0-nightly`).
- **Major LLVM branch cuts (`rustc/<N+1>.0-YYYY-MM-DD`):** Roughly twice per year (and periodically on experimental `rustc/<N+1>.0-*` staging branches against upstream LLVM `main`), maintainers create a fresh `rustc/` branch carrying forward any still-unmerged Rust patches (`updating-llvm.md:50-90`).

Because Linux distributions and BSD ports build `rustc` dynamically against system-packaged LLVM (`target.<triple>.llvm-config` in `bootstrap.toml`) rather than `src/llvm-project`, `rustc` simultaneously supports **three major LLVM versions**: `N - 1` (minimum supported `system-llvm`), `N` (in-tree `src/llvm-project`), and `N + 1` (pre-staged upstream LLVM `main`). At `412be32a6a18`:

- `check_llvm_version` (`src/bootstrap/src/core/build_steps/llvm.rs:812-825`) parses `llvm-config --version` and panics if `major < 22` (`llvm.rs:818`), establishing **LLVM 22** as the floor while in-tree LLVM is **23.1**.
- `src/ci/github-actions/jobs.yml:131-147,435-460` continuously exercises `system-llvm` 22 in five PR/bors jobs (`test-x86_64-gnu-llvm-22-1`, `test-x86_64-gnu-llvm-22-2`, `test-x86_64-gnu-llvm-22-3`, `test-aarch64-gnu-llvm-22-1`, `test-aarch64-gnu-llvm-22-2`) with `--set target.<triple>.llvm-config=/usr/lib/llvm-22/bin/llvm-config`.
- `compiler/rustc_llvm/build.rs:1-340` bridges host/target `llvm-config` execution:
  - **Stage-0 `libLLVM.so` isolation (`build.rs:46-65`):** Bootstrap prepends stage0's `lib/` to `LD_LIBRARY_PATH` / `DYLD_LIBRARY_PATH` and saves the caller's original environment in `REAL_LIBRARY_PATH`. Before invoking freshly built `llvm-config`, `build.rs` restores `REAL_LIBRARY_PATH` so `llvm-config` does not dynamically load an older stage0 `libLLVM.so` with an incompatible symbol version.
  - **Quoted-path probing (`build.rs:189-205`):** Probes `llvm-config --quote-paths` (introduced in LLVM 22) and parses output via `shlex::Shlex` when supported, falling back to `split_whitespace`.
  - **Component gating (`build.rs:21-44,227-240`):** Requires **8** core LLVM components (`ipo`, `bitreader`, `bitwriter`, `linker`, `asmparser`, `lto`, `coverage`, `instrumentation`) and probes **19** optional architecture components (`x86`, `arm`, `aarch64`, `amdgpu`, `avr`, `loongarch`, `m68k`, `csky`, `mips`, `powerpc`, `systemz`, `webassembly`, `msp430`, `sparc`, `nvptx`, `hexagon`, `riscv`, `xtensa`, `bpf`), emitting both `cargo:rustc-cfg=llvm_component="<name>"` for Rust FFI and `-DLLVM_COMPONENT_<NAME>` for C++.
  - **Cross-compilation flag scrubbing (`build.rs:255-289`):** When `TARGET != HOST`, strips host `-m*` flags, `-flto*`, and `_GLIBCXX_USE_CXX11_ABI` macros from `llvm-config --cxxflags`, and rewrites `-I` include paths containing `HOST` to `TARGET`.

C++ API incompatibilities across LLVM 22, 23, and 24 are absorbed inside `compiler/rustc_llvm/llvm-wrapper/`, where `LLVMWrapper.h:11-15` defines `LLVM_VERSION_GE(major, minor)` and `LLVM_VERSION_LT(major, minor)`. Across all `8` files (`4,339` lines total), deterministic extraction (`support/dist_and_stage0_manifest.json`) finds **29** version-conditional guards concentrated entirely in `PassWrapper.cpp` (`26` guards across `1,710` lines) and `RustWrapper.cpp` (`3` guards across `1,941` lines), with `0` guards in `CoverageMappingWrapper.cpp`, `Linker.cpp`, `SymbolWrapper.cpp`, `offload/OffloadWrapper.cpp`, `LLVMWrapper.h`, and `SuppressLLVMWarnings.h`:

- **`LLVM_VERSION_GE(23, 0)` (`12` sites — bridging LLVM 22 vs in-tree LLVM 23.1):** `RustWrapper.cpp:544,2102` and `PassWrapper.cpp:58,76,472,718,864,956,1152,1180,1414,1677` guard pass-builder pipeline callbacks, PGO instrumentation constructors, target machine options, and debuginfo/DIBuilder signature shifts introduced in LLVM 23.
- **`LLVM_VERSION_GE(24, 0)` (`13` sites) and `LLVM_VERSION_LT(24, 0)` (`4` sites — pre-staging LLVM 24 `main`):** `RustWrapper.cpp:1505` (`GE(24, 0)`) and `PassWrapper.cpp:74,475,478,616,625,738,747,876,972,1150,1157,1182,1190,1300,1360,1372` adapt upcoming LLVM 24 pass-manager, sanitizer, and vectorization API changes ahead of the next major `src/llvm-project` roll.

#### 1.3 `download-ci-llvm` Invalidation, Stamp Files, and Option Compatibility

Building `src/llvm-project` from source consumes most of a cold compiler build, so `llvm.download-ci-llvm` (defaulting to `"if-unchanged"` on supported hosts) downloads prebuilt CI `rust-dev` tarballs when local inputs match upstream CI (`src/bootstrap/src/core/build_steps/llvm.rs:257-419`, `src/bootstrap/src/core/download.rs:273-401`):

1. **Invalidation path set (`llvm.rs:315-320`):** Rather than hashing evaluated CMake flags directly, `detect_llvm_freshness` (`download.rs:236-271`) queries Git history over exact path list `LLVM_INVALIDATION_PATHS`:
   - `"src/llvm-project"` (the submodule gitlink),
   - `"src/bootstrap/download-ci-llvm-stamp"` (a manual cache-buster file bumped whenever `src/bootstrap` changes LLVM CMake flags, patches, or build options without touching `src/llvm-project`; at `412be32a6a18`, last bumped for PR `#164134`), and
   - `"src/version"` (ensuring version bumps invalidate cached `rust-dev-{version}-*` URLs).
2. **Josh-aware bors merge lookup (`src/build_helper/src/git.rs:174-258`):** `updated_master_sha` searches for the latest commit authored/committed by `git_merge_commit_email` (`bors@rust-lang.org` in `src/stage0:4`) modifying `LLVM_INVALIDATION_PATHS`. Critically, `git.rs:200-228` passes `--author-date-order` **before** `--first-parent`: when a subtree repository pulls `rust-lang/rust` via `josh-proxy`, `rustc` history becomes the **second parent** of the subtree merge commit (`git.rs:176-198`), so running `--first-parent` inside a subtree checkout or unmerged subtree PR would skip `bors` commits entirely.
3. **Unchanged check and server selection (`llvm.rs:261-385`, `download.rs:273-360`):** When `llvm.download-ci-llvm = "if-unchanged"`, any local modification to `LLVM_INVALIDATION_PATHS` relative to the resolved `llvm_sha` causes `try_download_ci_llvm` to return `None` and build LLVM locally. Otherwise, `is_ci_llvm_available_for_target` (`llvm.rs:340-385`) checks **30** supported host triples (`9` Tier-1 + `21` Tier-2-with-host-tools). When `llvm.assertions = false`, bootstrap fetches `{artifacts_server}/{llvm_sha}/rust-dev-{version}-{triple}.tar.xz` (or falls back to `{artifacts_with_llvm_assertions_server}` for triples whose non-assertions archive is a subset); when `llvm.assertions = true`, only **3** triples have prebuilt assertions archives (`x86_64-unknown-linux-gnu`, `x86_64-apple-darwin`, `x86_64-pc-windows-msvc`, `llvm.rs:352-356`).
4. **Extraction, `cargo#10791` mtime touch, and `builder-config` verification (`download.rs:315-357`):** After unpacking `ci-llvm/` and writing stamp `.llvm-stamp = "{llvm_sha}{llvm_assertions}"`, `maybe_download_ci_llvm` updates `ci-llvm/bin/llvm-config`'s modification timestamp to `SystemTime::now()` (`download.rs:321-325`) so Cargo's mtime-based `build.rs` fingerprint notices newly downloaded LLVM binaries even though `rust-installer` tarballs clamp archived mtimes to 2006. Finally, `check_incompatible_options_for_ci_llvm` (`download.rs:343-357`) parses the `builder-config` file embedded inside `rust-dev` and rejects mismatches against local `llvm.plugins`, `llvm.offload`, `llvm.enzyme`, or `llvm.libzstd` settings.

#### 1.4 `src/gcc`, `src/tpde`, `src/tools/enzyme`, and `rust-toolstate` Book Windows

The remaining non-LLVM submodules follow distinct coupling models:

- **`src/gcc` and `gcc_submodule.rs` lockstep check:** `compiler/rustc_codegen_gcc` is synchronized via Josh (`§2`), whereas `src/gcc` (`rust-lang/gcc` fork providing `libgccjit`) is a Git submodule because cloning GCC's history through `josh-proxy` is prohibitive. To prevent skew between the two, `src/tools/tidy/src/gcc_submodule.rs:9-57` reads `compiler/rustc_codegen_gcc/libgccjit.version` (`e1c6e07b095d091177376a163da44039475e05e3`) and fails `tidy` unless `git submodule status --cached src/gcc` matches that exact 40-hex commit SHA (`gcc_submodule.rs:33-53`). Unlike LLVM (which compiles all target backends into one `libLLVM.so`), `libgccjit.so` is single-target: `src/bootstrap/src/core/build_steps/gcc.rs:28-65` keys builds on `GccTargetPair { host, target }`, and `download_ci_gcc` (`download.rs:403-426`) only downloads prebuilt `gcc-dev` on `x86_64-unknown-linux-gnu -> x86_64-unknown-linux-gnu` when neither `src/gcc` nor `src/bootstrap/download-ci-gcc-stamp` is locally modified.
- **`src/tpde` (`llvm::Tpde`, `llvm.rs:2309-2491`):** Compiles `tpde-plugin.so` (`-DTPDE_ENABLE_LLVM=ON -DTPDE_ENABLE_ENCODEGEN=ON`) on Linux hosts (`x86_64` and `aarch64` machine-code emitters). #### 2.2 `rustc-josh-sync` Proxy Mechanics, Filter Versions, and Roundtrip Verification

Synchronization across all 11 subtrees is standardized by `rust-lang/josh-sync` (`8ce49808a529d3df3283fcdc7eceff1d034578b3`), which installs the `rustc-josh-sync` CLI:

- **Local `josh-proxy` daemon (`src/josh.rs:14-95`):** `rustc-josh-sync` spawns a local `josh-proxy` process (`r26.08.28` minimum) bound to `http://127.0.0.1:42042` with `--remote=https://github.com --local=<cache_dir> --no-background`.
- **Filter construction and historical rename splicing (`src/config.rs:45-145`):**
  - When `josh-sync.toml` specifies `path = "library/stdarch"` without a custom `filter`, `FilterVersion::Version1` emits `:~(history="keep-trivial-merges",gpgsig="norm-lf")[:/library/stdarch]`, whereas `FilterVersion::Version2` (`library/hashbrown`) emits `:~(history="keep-trivial-merges,no-splice",gpgsig="norm-lf")[:/library/hashbrown]` to drop empty non-spliced merge commits.
  - Subtrees that moved directories inside `rust-lang/rust` over time (`clippy`, `miri`, `rust-analyzer`, `rustfmt`, `rustc_codegen_cranelift`, `rustc_codegen_gcc`, `portable-simd`) specify an explicit `:rev(<=<cutoff_sha>:prefix=<current_path>,...):/<old_path>` filter in `josh-sync.toml` so `josh-proxy` stitches pre-move and post-move history into a single continuous subdirectory DAG.
- **`rustc-josh-sync pull` (`rust-lang/rust` -> external subtree repo, `src/sync.rs:91-304`):**
  1. Resolves target `upstream_sha` on `rust-lang/rust` (`HEAD` of `main` in `Latest` mode, or the `commit-hash` corresponding to the target `nightly-YYYY-MM-DD` toolchain in `Nightly` mode).
  2. Updates either `rust-version` (`PullMode::Latest`) or `rust-toolchain.toml` (`PullMode::Nightly`) in a preparatory commit if needed (`sync.rs:140-210`).
  3. Fetches `http://127.0.0.1:42042/rust-lang/rust.git@{upstream_sha}{urlencoded_filter}.git` and checks whether `FETCH_HEAD` is already an ancestor of `HEAD` (exiting with status code `2`, `NothingToPull`, so scheduled GitHub Actions workflows such as `src/doc/rustc-dev-guide/.github/workflows/rustc-pull.yml` exit cleanly when no upstream commits touched the subtree).
  4. Runs `git merge FETCH_HEAD --no-verify --no-ff -m "Sync from rustc ..."` (`sync.rs:248-272`), counts `git rev-list --max-parents=0 HEAD` before and after the merge to guarantee `josh-proxy` did not create a disconnected orphan root (`sync.rs:274-286`), and executes `[[post-pull]]` commands (`cargo fmt` in `stdarch`/`rust-analyzer`; `clippy_utils/README.md` version rewrite in `clippy`).
- **`rustc-josh-sync push <branch> <github-user>` (external subtree repo -> `rust-lang/rust`, `src/sync.rs:306-384,407-442`):**
  1. Determines `base_upstream_sha` (either from `rust-version` or by finding the latest `rust-lang/rust` commit whose filtered tree is an ancestor of `HEAD`) and pushes `base_upstream_sha:refs/heads/<branch>` directly to `git@github.com:<user>/rust.git` so `josh-proxy` has an exact base commit on the user's `rust` fork.
  2. Pushes `HEAD:refs/heads/<branch>` through `http://127.0.0.1:42042/<user>/rust.git{urlencoded_filter}.git`, causing `josh-proxy` to invert the subdirectory projection and synthesize commits on `<user>/rust:<branch>` touching only `<subtree_dir>/`.
  3. Runs **`roundtrip_check` (`sync.rs:407-442`)**: fetches `<user>/rust:<branch>` *back* through `josh-proxy` with the forward filter and asserts `FETCH_HEAD == HEAD` (or `FILTERED_HEAD`), aborting before PR creation if any out-of-subtree file, `.gitattributes` normalization, or filter asymmetry altered the tree.

On the `rust-lang/rust` side, `triagebot.toml` enforces two critical subtree merge protections: `[no-merges]` (`triagebot.toml:2049-2051`) rejects ordinary merge commits in PRs *except* PRs whose titles match `"subtree update"` or `"subtree sync"` (preserving the diamond merge topology `josh-proxy` needs to recognize shared ancestry on the next `pull`), and `[issue-links]` (`triagebot.toml:2075`) rewrites bare `#1234` references in synced commits during review/bors processing so subtree commit messages do not accidentally spam or close unrelated `rust-lang/rust` issues.

#### 2.3 `rustc_private` Breakage Windows During `pull` vs `push`

Seven of the 11 subtrees (`clippy`, `miri`, `rust-analyzer`, `rustfmt`, `rustc_codegen_cranelift`, `rustc_codegen_gcc`, and indirectly `portable-simd` via `core` intrinsics) depend on unstable compiler or `core` internals (`#![feature(rustc_private)]`). Their sync mode creates two asymmetric breakage windows:

- **In-tree atomic refactoring (zero breakage in `rust-lang/rust`):** Because `src/bootstrap` compiles in-tree `clippy`, `miri`, `rustfmt`, `rust-analyzer`, `rustc_codegen_cranelift`, and `rustc_codegen_gcc` directly from their subdirectories in `rust-lang/rust`, any compiler PR changing `rustc_middle`, `rustc_hir`, or `rustc_span` updates those subdirectories in the **same bors commit**.
- **Standalone repository lag and `push` contention (`PullMode::Latest` vs `PullMode::Nightly`):**
  - In `PullMode::Latest` (`miri`, `rust-analyzer`), the standalone repository pins an exact `rust-lang/rust` commit SHA in `rust-version` (`src/tools/miri/CONTRIBUTING.md:390-445` uses `rustup-toolchain-install-master` to fetch CI `rustc-dev` artifacts for that exact bors commit). Between `pull` syncs, compiler devs land `rustc_private` fixes in `rust-lang/rust`'s `src/tools/miri/`. Consequently, **a `push` from `rust-lang/miri` to `rust-lang/rust` will conflict or fail `rustc` CI whenever `rust-lang/rust` has modified `src/tools/miri/` since `rust-version`**, forcing maintainers to run `rustc-josh-sync pull` *first* before `rustc-josh-sync push` (`src/tools/clippy/book/src/development/infrastructure/sync.md:15-95`).
  - In `PullMode::Nightly` (`clippy`, `rustfmt`, `rustc_codegen_cranelift`, `rustc_codegen_gcc`, `portable-simd`), the standalone repository builds against a dated `nightly-YYYY-MM-DD` toolchain (`rust-toolchain.toml`). If `rust-lang/rust` lands a breaking `rustc_private` API change after `12:00 UTC` on day $D$, the standalone repository cannot `pull` those commits until the `nightly-(D+1)` release finishes promoting (`§5.4`), creating an up-to-24-hour window during which `push` syncs are blocked awaiting a published nightly containing the new `rustc-dev` `.rmeta` interfaces.

#### 3.2 `src/tools/bump-stage0` and the 6-Week Release-Train Invariant

`./x run src/tools/bump-stage0` (`src/tools/bump-stage0/src/main.rs:1-311`) enforces a strict **one-minor-version bootstrap step** across all three release trains by reading `src/ci/channel` (`nightly`, `beta`, or `stable`) and `src/version` (`major.minor.patch`, `main.rs:126-198`):

- **On `main` (`Channel::Nightly`, `src/version = 1.(N+2).0`):** `detect_compiler` fetches `https://static.rust-lang.org/dist/channel-rust-beta.toml` (`1.(N+1).0-beta.*`)—or `channel-rust-1.(N+1).toml` during the narrow window after `main` bumps `src/version` (`3416a824041cc6d3fcb6834950458d1f2e32437e` bumped `main` to `1.102.0` on `2026-11-06`) if `channel-rust-beta.toml`'s minor version has not yet reached `N+1` (`main.rs:138-165`). Once `1.101.0-beta.1` (`bbcdfd90a3f81ca2a5f6d69b943a6ff0d8582102`, `2026-11-10`) promoted to `beta`, commit `325b278b7790437fe2b09c70da93559801e8ec91` (`2026-11-10`) ran `bump-stage0` on `main` to advance `stage0` from `1.100.0-beta` to `1.101.0-beta.1`. Simultaneously, `detect_rustfmt` (`main.rs:180-198`) fetches `channel-rust-nightly.toml`.
- **On `beta` and `stable` (`Channel::Beta | Channel::Stable`, `src/version = 1.(N+1).Y`):** `detect_compiler` computes `prior_minor = current.minor - 1` and fetches `https://static.rust-lang.org/dist/channel-rust-1.{N}.toml` (`main.rs:166-176`), which always resolves to the **latest published point release** `1.N.Z` of the immediately preceding stable compiler, while `detect_rustfmt` returns `None` (`main.rs:182-184`).

This coupling guarantees two crucial bootstrap properties:

1. **Continuous forward chain (`1.N -> 1.(N+1) -> 1.(N+2)`):** Linux distributions packaging Rust `1.(N+1).0` from source tarballs never need a pre-release `beta` binary—when `main` branches to `beta` and `1.N.0` promotes to `stable`, `bump-stage0` on `beta` switches `src/stage0` from `1.N.0-beta.*` to the newly released `1.N.0` stable compiler (`src/tools/bump-stage0/src/main.rs:166-176`).
2. **Bounded dialect skew (`<= 6` weeks):** `compiler/` and `library/` on `main` (`1.N+2`) are always compiled at stage 1 by `1.(N+1)-beta`, so in-tree code may unconditionally use any language or library feature stabilized or implemented on `main` prior to the most recent beta branch cut (`<= 6` weeks ago).

#### 3.3 `--cfg=bootstrap`, `--check-cfg=cfg(bootstrap)`, and `RUSTC_BOOTSTRAP`

Whenever `compiler/` or `library/` adopts a brand-new language feature, intrinsic, or lint introduced in the *current* `1.(N+2)` cycle that `stage0` (`1.(N+1)-beta`) does not yet understand—or removes an unstable feature that `stage0` still expects—bootstrap resolves the stage-0 vs stage-1+ dialect split via two mechanisms in `src/bootstrap/src/core/builder/cargo.rs`:

1. **Stage-gated `--cfg=bootstrap` with universal `--check-cfg=cfg(bootstrap)` (`cargo.rs:90-98,863-882`, `src/bootstrap/src/bin/rustdoc.rs:58-62`):**
   - `cargo.rs:94-97` unconditionally passes `--check-cfg=cfg(bootstrap)` at **every** stage (`0`, `1`, `2`) so `#![warn(unexpected_cfgs)]` never fires when `bootstrap` is unset at stage 1+.
   - `cargo.rs:864-882` injects `--cfg=bootstrap` into `rustflags` **and** into `hostflags` (working around `cargo#4423` so proc-macro crates compiled for the host during cross-target stage-0 builds also see `cfg(bootstrap)`) **strictly when `build_compiler.stage == 0`**. Likewise, the `rustdoc` shim (`src/bootstrap/src/bin/rustdoc.rs:58-62`) appends `--cfg=bootstrap` when `RUSTDOC_STAGE == "0"`.
   - At `412be32a6a189d9a28922beee178bc0abee9d492`, `compiler/` has **only 3 active `#![cfg_attr(bootstrap, ...)]` attributes** (`support/dist_and_stage0_manifest.json`), reflecting strict post-bump cleanup discipline:
     - `compiler/rustc_data_structures/src/lib.rs:13`: `#![cfg_attr(bootstrap, feature(pattern_type_macro))]`
     - `compiler/rustc_data_structures/src/lib.rs:14`: `#![cfg_attr(bootstrap, feature(ptr_alignment_type))]`
     - `compiler/rustc_middle/src/lib.rs:30`: `#![cfg_attr(bootstrap, feature(ptr_alignment_type))]`
     (plus `compiler/rustc_index_macros/src/lib.rs:44` retaining `pattern_type_macro` marked for removal on the next `stage0` bump).
2. **`RUSTC_BOOTSTRAP` mode control (`cargo.rs:905-956`, `bootstrap.py:1129-1148`):**
   - To allow `beta`/`stable` `stage0` compilers to compile `#![feature(...)]` gates in `std` and `rustc`, `bootstrap` sets `RUSTC_BOOTSTRAP=1` for `Mode::Std`, `Mode::Rustc`, `Mode::Codegen`, and `Mode::ToolRustcPrivate`.
   - Conversely, for standalone tools that must compile on stable Rust without nightly features (`Mode::ToolBootstrap`, `Mode::ToolTarget`) when no `-Zallow-features` list is configured, `cargo.rs:936-942` explicitly sets `RUSTC_BOOTSTRAP=-1` (forcing `rustc` to behave as a stable channel compiler even on nightly!) or restricts unstable features to an explicit `-Zallow-features=...` allowlist (`cargo.rs:922-935`).
3. **Four-step cyclic dependency dance (`src/doc/rustc-dev-guide/src/building/bootstrapping/bootstrap-in-dependencies.md:1-56`):** When an external dependency used by `std` or `rustc` (such as `compiler-builtins` or `proc_macro`, `library/proc_macro/Cargo.toml:19`) must change alongside an internal intrinsic: (1) add `#[cfg(not(bootstrap))]` around the new intrinsic and `#[cfg(bootstrap)]` around the old fallback in the external crate, (2) roll the crate and change the intrinsic in `rust-lang/rust` in one PR, (3) wait up to 6 weeks for the next `bump-stage0`, and (4) strip `#[cfg(bootstrap)]`.

### 4. Multi-Phase PGO and BOLT Release Optimization Pipeline (`src/tools/opt-dist`)

#### 4.1 Five-Phase Execution Choreography (`src/tools/opt-dist/src/`)

On optimized CI builders, `x.py run src/tools/opt-dist {linux-ci|windows-ci|local}` (`src/tools/opt-dist/src/main.rs:1-663`) wraps `x.py dist` inside a five-phase profile-guided and post-link binary layout optimization pipeline (`execute_pipeline`, `main.rs:252-552`):

1. **Pre-step — Build `rustc-perf` `collector` at Stage 0 (`main.rs:259-266,650-663`):** Runs stage-0 `cargo build -p collector` inside `src/tools/rustc-perf/` with `RUSTC` pointed at `stage0/bin/rustc` and `RUSTC_BOOTSTRAP=1`. All subsequent PGO and BOLT training passes invoke `collector profile_local eprintln` with `--frontend-threads 1` and `--jobs 4` (`src/tools/opt-dist/src/training.rs:51-114`).
2. **Stage 1 — Multi-component Rust PGO (`rustc`, `cargo`, `rustdoc`, `clippy`, `rustc_codegen_cranelift`; `main.rs:273-382`, `training.rs:120-238`):**
   - **Fast vanilla LLVM shortcut (`main.rs:278-286`):** When building LLVM dynamically (`shared_llvm = true`), Stage 1 overrides `--set llvm.thin-lto=false --set llvm.link-shared=true` so the throwaway LLVM used only to compile instrumented Rust components skips ThinLTO (saving ~9 minutes on Linux CI).
   - **Instrumented build (`main.rs:288-334`):** Builds stage-2 `rustc`, `cargo`, `rustdoc`, `clippy`, and (when present in `codegen_backends`) `rustc_codegen_cranelift` with `-Cprofile-generate=<dir>`. Notably, `rustc` and `cargo` share the **same** profile output directory (`rustc-pgo`, `main.rs:290-296`) because `collector` invokes `cargo` to drive `rustc` across every benchmark crate without symbol-hash collisions.
   - **Training workloads (`src/build_helper/src/lib.rs:15-36`, `training.rs:120-238`):**
     - `rustc` + `cargo`: `collector` runs `Check,Debug,Opt` across `All` scenarios (`Full`, `IncrFull`, `IncrUnchanged`, `IncrPatched`) on the **9** `RUSTC_PGO_CRATES`: `externs`, `ctfe-stress-5`, `cargo-0.87.1`, `token-stream-stress`, `enum-stress`, `tuple-stress`, `diesel-2.2.10`, `bitmaps-3.2.1`, and `serde-1.0.219-new-solver`.
     - `rustdoc`: runs `Doc` / `Full` on the same **9** `RUSTC_PGO_CRATES`.
     - `clippy`: runs `Clippy` / `All` (`--cargo-config build.rustflags=["-Dwarnings"]` disabled to avoid failing on benchmark lints) on the **9** `RUSTC_PGO_CRATES`.
     - `rustc_codegen_cranelift`: runs `Debug` / `Full` with `--backends Cranelift` on the **7** `BACKEND_PGO_CRATES` (`syn-2.0.101`, `cargo-0.87.1`, `serde-1.0.219`, `ripgrep-14.1.1`, `regex-automata-0.4.8`, `clap_derive-4.5.32`, `hyper-1.6.0`).
   - **Profile merge and optimized stage-2 Rust build (`main.rs:336-382`):** Merges `default_%m_%p.profraw` shards using in-tree `llvm-profdata merge` (`LlvmProfdata::Target`), deletes instrumented artifacts, and builds PGO-optimized stage-2 `rustc` + tools (`--rust-profile-use`, `--cargo-profile-use`, `--rustdoc-profile-use`, `--clippy-profile-use`, `--cranelift-profile-use`). When `use_bolt = true`, passes `--enable-bolt-settings`, which sets `RUSTC_BOLT_LINK_FLAGS=1` (`src/bootstrap/src/core/build_steps/compile.rs:1140-1143`) so `librustc_driver-*.so` retains ELF relocations (`-Wl,-q`).
3. **Stage 2 — LLVM C++ PGO (`main.rs:384-416`, `training.rs:116-162`):**
   - Deletes Stage 1's vanilla LLVM (`clear_llvm_files`) and builds PGO-instrumented LLVM (`--llvm-profile-generate`, `LLVM_PROFILE_FILE=<dir>/prof-%p`).
   - **Dynamic vs static LLVM relink bifurcation (`main.rs:390-405`):** On Linux (`shared_llvm = true`), `opt-dist` passes `--keep-stage 0 --keep-stage 1` and builds *only* `src/llvm-project`, swapping the instrumented `libLLVM.so*` straight underneath the already-built PGO-optimized stage-2 `rustc`! On Windows MSVC (`shared_llvm = false`, static `.lib` linking), `opt-dist` passes `--keep-stage 0` and must re-compile/re-link `rustc` against the instrumented LLVM static libraries.
   - Runs `Debug,Opt` / `Full` across the **7** `BACKEND_PGO_CRATES`, merges profiles with **host** `llvm-profdata` (`LlvmProfdata::Host`, avoiding invoking an instrumented `llvm-profdata` binary), and deletes the instrumented LLVM build tree.
4. **Stage 3 — Post-Link `llvm-bolt` Binary Layout Optimization (`main.rs:418-509`, `src/tools/opt-dist/src/bolt.rs:1-120`; `x86_64-unknown-linux-gnu` only):**
   - Builds PGO-optimized LLVM (`--llvm-profile-use`) with `--enable-bolt-settings` (`llvm.ldflags = "-Wl,-q"` preserving ELF relocations).
   - **Sequential BOLT instrumentation with hardlink isolation (`main.rs:432-462`, `bolt.rs:12-47,103-120`):** Because `stage2/lib/libLLVM.so*` and `build/<triple>/llvm/lib/libLLVM.so*` are hardlinked, `with_bolt_instrumented` wraps target files in RAII `BackedUpFile` (copying to a tempfile to break hardlinks during instrumentation and restoring the uninstrumented ELF on `Drop`). First, `/rustroot/bin/llvm-bolt -instrument --instrumentation-file=.../prof.fdata --instrumentation-file-append-pid` instruments `libLLVM.so*`, runs `llvm_benchmarks`, and merges profiles via `merge-fdata`; after `BackedUpFile::drop` restores clean `libLLVM.so*`, `opt-dist` repeats the exact cycle on `stage2/lib/librustc_driver-*.so` using `rustc_benchmarks` (`9` `RUSTC_PGO_CRATES`).
   - **Parallel BOLT rewriting (`main.rs:464-509`, `bolt.rs:50-100`):** `std::thread::scope` optimizes `libLLVM.so*` and `librustc_driver-*.so` concurrently via `bolt_optimize`, passing exact flags:
     `-reorder-blocks=ext-tsp -reorder-functions=cdsort -split-functions -split-strategy=cdsplit -split-all-cold -jump-tables=move -icf=all -update-debug-sections -dyno-stats`
     (`bolt.rs:60-96`; `bolt.rs:60-61` falls back from `cdsplit` to `profile2` if invoked on `aarch64`, and `bolt.rs:82-89` intentionally keeps `--use-old-text` commented out because non-deterministic segment reuse previously caused ~50 MiB tarball size swings). Finally, `main.rs:495-507` copies the BOLT-optimized `libLLVM.so` back across every `libLLVM*.so*` file in `llvm/build/lib/` so `dist::Rustc` and `dist::RustDev` package the BOLT-optimized binary regardless of hardlink breaks.
5. **Stage 5 — Final `x.py dist` Packaging and Unpacked Stage-0 Smoke Testing (`main.rs:513-550`, `src/tools/opt-dist/src/tests.rs:1-155`):**
   - Invokes `x.py dist` with `--keep-stage 0 --keep-stage 1 --keep-stage 2` (on Linux dynamic LLVM) or `--keep-stage 0 --keep-stage 1` (relinking `rustc` once more against PGO-optimized static LLVM on Windows MSVC, `main.rs:515-524`), passing `--reproducible-artifact <profdata>` for every generated PGO and BOLT profile (`6` `.profdata`/`.fdata` archives on `x86_64-linux`) so downstream rebuilders can reproduce the exact PGO/BOLT binary from `reproducible-artifacts-*.tar.xz`.
   - `run_tests` (`tests.rs:11-155`) unpacks `rustc`, `rust-std`, `cargo`, `rust-src` (plus `rustc-codegen-cranelift` if present) from `build/dist/*.tar.xz` into `build/unpacked-dist/`, writes a temporary `bootstrap.toml` (`local-rebuild = true`, `compiletest-allow-stage0 = true`, `lld = false`), and executes **11** smoke test suites against the unpacked distribution at `--stage 0` with `COMPILETEST_ENABLE_DIST_TESTS=1`: `tests/assembly-llvm`, `tests/codegen-llvm`, `tests/codegen-units`, `tests/incremental`, `tests/mir-opt`, `tests/pretty`, `tests/run-make/glibc-symbols-x86_64-unknown-linux-gnu` (verifying CentOS 7 `glibc <= 2.17` symbol ceilings), `tests/run-make/rust-lld-x86_64-unknown-linux-gnu-dist` (verifying default `rust-lld` linker wiring), `tests/ui`, `tests/crashes`, and `tests/rustdoc-html`.

#### 5.2 `rust-installer` Format v3 (`src/tools/rust-installer`)

Every `GeneratedTarball` in `dist.rs` delegates archive creation to `src/tools/rust-installer` (`rust-installer-version = 3`), whose four modules enforce deterministic, `rustup`-compatible layouts:

- **Metadata and `install.sh` generation (`src/generator.rs`, `src/combiner.rs`, `src/scripter.rs`):** Writes `rust-installer-version` (`3`), `components` (listing component name(s), e.g., `rustc` or merged `rustc\ncargo\nrust-std-...` in `Combiner`), `git-commit-hash`, `version`, and per-component `manifest.in` where ordinary files are recorded as `file:<relpath>` (individually tracked for clean uninstallation) while massive trees such as `share/doc/rust/html` are recorded as `dir:<relpath>` (`bulk_dirs`, extracted in bulk without per-file manifest lines). `Scripter` renders `install-template.sh` into POSIX `install.sh` for non-`rustup` standalone users.
- **Deterministic mtime, reversed-suffix LZMA sorting, and dual-stream compression (`src/tarballer.rs:1-210`, `src/compression.rs:1-140`):**
  - `Tarballer` sets `HeaderMode::Deterministic` (zeroing UID/GID/username) and clamps every file's tar header `mtime` to `override_file_mtime = 1153704088` (`2006-07-24T01:21:28Z`, commemorating Graydon Hoare's initial Rust repository commit, `tarballer.rs:34,158`).
  - Before writing tar entries, `tarballer.rs:111-125` places all directories first and then sorts all file paths by **reversed byte order** (`a.bytes().rev().cmp(b.bytes().rev())`)! Grouping all `.rlib`, `.rmeta`, `.so`, and `.html` files contiguously in the uncompressed tar stream dramatically increases LZMA sliding-window dictionary hit rates across sibling files.
  - `CombinedEncoder` (`compression.rs:85-138`) tees each tar write into simultaneous Rayon worker streams producing `<name>.tar.gz` and `<name>.tar.xz` in a single pass (using fast CI compression levels during PR/bors builds because `promote-release` recompresses production releases at level 9, `§5.4`).

#### 5.3 `build-manifest` V2 Schema and `replace-version-placeholder`

`src/tools/build-manifest` (`src/manifest.rs`, `src/versions.rs`, `src/main.rs`) scans a staging directory of tarballs and emits `channel-rust-{nightly,beta,stable}.toml` with `manifest-version = "2"` (`manifest.rs:8`):

#### 5.4 Release Promotion, Recompression, Signing, and Atomic Channel Flip (`rust-lang/promote-release`)

`rust-lang/promote-release` (`9407dc9fe0a529c6d55b66ad54f75531eb34e51a`) runs out-of-repo in AWS on a dedicated 72-vCPU promotion host (`prod/Dockerfile`) and exposes two top-level actions (`src/bin/promote-release.rs`, `src/lib.rs`, `src/branching.rs`):

1. **`Action::PromoteBranches` (6-week beta/stable branch advancement, `src/branching.rs:13-81`):**
   - Queries GitHub commits on `main` touching `src/version` to find the bors merge commit that bumped `main` from `1.(N+1).0` to `1.(N+2).0`, and extracts `prebump_sha = bump_commit.parents[0].sha` (the exact final `main` commit before the version bump!).
   - Verifies all three train version strings (`stable`, `beta`, `prebump`) are pairwise distinct.
   - Authenticates via a GitHub App JWT (`src/github.rs`) and updates three Git refs: (a) fast-forwards/updates `rust-lang/rust` `refs/heads/stable` to current `refs/heads/beta` (`beta_sha`), (b) updates `rust-lang/rust` `refs/heads/beta` to `prebump_sha`, and (c) creates branch `refs/heads/rust-{new_beta_version}` in `rust-lang/cargo` pointing at the exact `src/tools/cargo` submodule gitlink SHA recorded in `prebump_sha` (`branching.rs:62-79`). (Subsequent PRs on the new `beta` branch flip `src/ci/channel` from `nightly` to `beta` and run `bump-stage0` + `replace-version-placeholder`, while `stable` flips `src/ci/channel` to `stable`.)
2. **`Action::PromoteRelease` (`nightly` at `00:00 UTC`, `beta`, and `stable` two-phase `dev-static` -> `static.rust-lang.org` promotion, `src/lib.rs:117-260`):**
   - **Step 1 — Lock, idempotency check, and S3 staging pull (`lib.rs:120-185`):** Acquires filesystem `.lock`, resolves target branch/override commit SHA (`rev`), checks live `https://static.rust-lang.org/dist/channel-rust-{channel}.toml` to skip if `(date, rev, version)` was already published, downloads `s3://{download_bucket}/{download_dir}/{rev}/` via MinIO `silo`/`mc` (`rustc-builds` CI bucket for nightly/beta/dev-stable, or `dev-static` S3 bucket when promoting pre-staged stable builds to production!), and **deletes all pre-existing `.asc` and `.sha256` files** (`lib.rs:176-184`) so dev-key signatures from `dev-static` are never carried into production.
   - **Step 2 — Pruning pass via extracted `build-manifest` (`src/build_manifest.rs:1-95`):** Unpacks `build-manifest-*.tar.gz` produced by `dist::BuildManifest` (`§5.1 #27`) and executes it once against the downloaded directory solely to discover which tarballs appear in `[pkg]` or `[artifacts]`, deleting all CI-only archives (`rust-dev-*`, `gcc-dev-*`, `bootstrap-*`, `build-manifest-*`) before spending CPU on recompression and signing!
   - **Step 3 — 72-vCPU deterministic recompression (`src/recompress.rs:1-145`):** Recompresses every shipped `.tar.gz` (`flate2::Compression::best()`, level 9) and `.tar.xz` using single-threaded `xz2` LZMA2 preset 9 (`MatchFinder::BinaryTree4`, `nice_len = 273`, `depth = 1000`, and a custom `dict_size` rounded down to the largest `2^n` or `2^n + 2^(n-1)` `<= uncompressed_size` clamped to `[4 KiB, 128 MiB]` so small tarballs do not allocate 64 MiB decompression dictionaries on user machines!). Jobs are sorted **largest uncompressed file first** across Rayon threads to eliminate long-tail stragglers.
   - **Step 4 — Final manifest generation, SHA-256, and OpenPGP signing (`src/sign.rs:1-155`, `lib.rs:205-225`):** Re-runs `build-manifest` twice—once with production `https://static.rust-lang.org` URLs and once with a local loopback URL for smoke testing—then computes `.sha256` digests and signs every artifact and manifest with detached OpenPGP v4 binary signatures (`SignatureType::Binary`, `HashAlgorithm::SHA2_512`) via the pure-Rust `pgp` crate (`sign.rs:126-153`).
   - **Step 5 — Local `rustup` smoke test (`src/smoke_test.rs:1-115`):** Spins up an in-process Hyper HTTP server on `127.0.0.1:0` serving the signed directory, points `RUSTUP_DIST_SERVER` at it, runs `rustup toolchain install --profile minimal`, and executes `cargo init` + `cargo run` to prove end-to-end `rustup` manifest/hash/installer integrity before touching public S3.
   - **Step 6 — Two-step atomic S3 upload, CDN purge, and ETag-fenced `manifests.txt` (`lib.rs:228-260,560-750`, `src/fastly.rs`):**
     1. Uploads all tarballs, `.sha256`, `.asc`, and dated manifests to `s3://{bucket}/dist/{YYYY-MM-DD}/` **first** (`lib.rs:565-590`), and syncs `/doc/{channel}/` (plus `/doc/{version}/` on `stable`).
     2. Uploads top-level `s3://{bucket}/dist/channel-rust-{channel}*` **second** (`lib.rs:592-615`). Because `rustup` reads top-level `channel-rust-*.toml` to discover `/dist/{YYYY-MM-DD}/...` URLs, uploading dated blobs before overwriting top-level manifests prevents `404` races during promotion!
     3. Issues CloudFront invalidations (`/dist/*`, `/doc/*`) and optional Fastly surrogate-key purges (`src/fastly.rs`), then appends the new manifest URL to `s3://{bucket}/dist/manifests.txt` using `aws s3api put-object --if-match <etag>` (or `--if-none-match *`, retrying up to 20 times with random jitter on `PreconditionFailed`, `lib.rs:661-750`) so concurrent `nightly` and `beta`/`stable` promotions never clobber `manifests.txt`.
     4. On `stable` production runs (`tag = true`), creates GPG-signed Git tags (`1.X.Y` on `rust-lang/rust`, `0.(X+1).0` on `rust-lang/cargo`), merges the release blog PR, posts the Discourse announcement, and triggers `thanks.rust-lang.org` and `www.rust-lang.org` GitHub Actions workflows (`lib.rs:245-260`).

### 6. Beta Backports, Provenance Enforcement, and Point Releases

Between beta branching and stable release—and during emergency `1.X.1` point releases—changes enter `beta` and `stable` through an audited cherry-pick workflow:

- **Triagebot nomination and acceptance (`triagebot.toml:9-73`):** `[backport.t-compiler-beta-backport]` (`triagebot.toml:66-72`) automatically applies `beta-nominated` whenever an issue/PR carries `T-compiler` and `regression-from-stable-to-beta` (and adds `T-release` to notify release managers). Team approval transitions the PR label from `beta-nominated` to `beta-accepted` (`stable-nominated` -> `stable-accepted` for point releases).
- **Provenance trailer injection (`src/tools/cherry-pick.sh:1-34`):** Release managers backporting an upstream `main` commit `<sha>` run `./src/tools/cherry-pick.sh <sha>`, which executes `git cherry-pick -x` or amends the commit message to append `(backport-of: <40-hex-sha>)` (`cherry-pick.sh:22-33`).
- **CI provenance gate (`src/ci/scripts/verify-backported-commits.sh:1-143`):** Runs on every `beta` and `stable` CI build (`verify-channel.sh` simultaneously checks that `src/ci/channel` matches the target branch, `src/ci/scripts/verify-channel.sh:1-39`):
  - Uses `git cherry origin/HEAD HEAD <merge-base-limit>` (`verify-backported-commits.sh:45-95`) to list every commit on `beta` (or `stable`, checked against both `HEAD` and `beta`) whose diff patch-ID is not already identical to a commit on `main`.
  - Every non-patch-identical commit **must** contain either `backport-of: <40-hex-sha>` (which the script verifies is an actual ancestor of `origin/HEAD` via `git merge-base --is-ancestor`, `verify-backported-commits.sh:105-128`) or the literal exemption `backport-of: nothing` reserved strictly for release-engineering commits (`src/version`, `src/ci/channel`, `src/stage0`, `RELEASES.md`, or `replace-version-placeholder` commits that never existed on `main`).
- **Concrete point-release verification (`1.99.1` at `58cf8f9c35b355199727627d07ae34a4e2846d67`):** Inspecting `1.99.1` (`Auto merge of #164232 - cuviper:stable-next`) confirms this exact protocol: commit `d1e0df558f7375eecf223b2a01cdacb6898c64f1` (`1.99.1 release`) bumps `src/version` from `1.99.0` to `1.99.1` alongside targeted regression cherry-picks on `stable`, while `src/ci/scripts/verify-stable-version-number.sh:1-30` queries `https://static.rust-lang.org/dist/channel-rust-1.99.1.toml` before spending CI compute so `stable` cannot accidentally merge a PR without incrementing `src/version` once `1.99.0` is already live.

### 7. Architectural Consequences for a Verified or Drop-In Rust Compiler

Replacing or formally verifying `rustc` within the `rust-lang/rust` build and release ecosystem imposes four non-obvious engineering boundaries exposed by §§1–6:

1. **Post-link binary rewriting (`llvm-bolt`) sits *outside* compiler codegen verification:** On `x86_64-unknown-linux-gnu` (`§4.1`, `§4.2`), `opt-dist` Stage 3 runs `llvm-bolt` to disassemble, split, cold-partition (`cdsplit`), identical-code-fold (`-icf=all`), and re-emit both `libLLVM.so*` and `librustc_driver-*.so` *after* compilation and linking. Any machine-code equivalence or translation-validation proof that terminates at compiler object emission is invalidated if post-link BOLT rewriting mutates the shipped `librustc_driver-*.so` without its own binary-level equivalence proof (or explicit disablement via `use_bolt = false`, matching `aarch64-unknown-linux-gnu` and macOS).
2. **`stage0` dialect and `RUSTC_BOOTSTRAP` compatibility:** A drop-in `stage0` seed or verified compiler participating in the 6-week bootstrap chain (`§3.2`, `§3.3`) must honor `--cfg=bootstrap`, `--check-cfg=cfg(bootstrap)`, `RUSTC_BOOTSTRAP=1` vs `RUSTC_BOOTSTRAP=-1` (`-Zallow-features=...`), and stage-0 proc-macro `hostflags` (`cargo#4423`), while supporting the `N-1 -> N` one-train language window without requiring out-of-band nightly binaries on `beta`/`stable` (`bump-stage0`).
3. **`rustc_private` / `rustc-dev` surface coupling across 7 Josh subtrees:** While `stdarch`, `compiler-builtins`, `hashbrown`, and `rustc-dev-guide` interact through source/Cargo boundaries, `clippy`, `miri`, `rust-analyzer`, `rustfmt`, `rustc_codegen_cranelift`, and `rustc_codegen_gcc` (`§2.1`, `§2.3`) consume `rustc-dev` `.rmeta`/`.rlib` crates (`dist::RustcDev`, `§5.1 #8`) directly. A verified compiler that replaces `rustc`'s internal crate graph must either preserve a compatibility `rustc_private` facade or explicitly decouple tool synchronization from internal query/HIR data structures.
4. **Drop-in `rustup` and `promote-release` archive parity:** To install via `rustup` or flow through `promote-release` (`§5.2`–`§5.4`), a toolchain distribution must emit `rust-installer` v3 tarballs (`rust-installer-version = 3`, `components`, `manifest.in` `file:`/`dir:` directives, deterministic `mtime = 1153704088`) and `build-manifest` v2 TOML tables (`[pkg.<name>.target.<triple>]`, `[renames]`, `[profiles]`) with matching `.sha256` and OpenPGP v4 SHA-512 `.asc` detached signatures.
