# AArch64 PAC/MTE/TBI0 Pointer Tagging, SVE/PCS Partial-Register Clobbers, `STT_TLS` Mislinking, and Outlined Atomics at the MIR-to-ISA Seam

## Summary

Designing an ISA-parametric `MIR <-> ISA` verification seam (`MachineSeam`) that transfers cleanly from `x86-64` to `AArch64` without re-architecting core invariants requires replacing four implicit `x86-64` assumptions—untagged 48-bit canonical pointer equality, `XMM`/`YMM` dirty-upper clobber symmetry, single-instruction `LOCK` atomic RMWs, and TLS-safe object linking—with explicit hardware-parametric contracts. Direct source inspection of `rustc` (`1.99.1` and `1.101.0-nightly`), LLVM/LLD/`compiler-rt` (`23.1.1`), cross-compilation to `aarch64-unknown-linux-gnu`, live user-mode execution under `qemu-aarch64` (`11.1.2`, `-cpu max` / `neoverse-n2` / `neoverse-v1`), and a 13-theorem Lean `v4.34.1` mechanization ([`support/IsaParametricMachineSeam.lean`](support/IsaParametricMachineSeam.lean)) establish four load-bearing invariants:

1. **AArch64 `asm!` Target-Feature Bypass, Partial-Vector PCS Cliffs, and `FPSR`/`FPCR` Lowering Gaps (`Basis: normative + source + execution`):**
   - **Register-alias and `.arch_extension` bypasses:** In `compiler/rustc_target/src/asm/aarch64.rs:145-193`, `rustc` aliases `"z0".."z31"` directly to `AArch64InlineAsmReg::v0..v31` (`vreg`, which checks only `neon`, not `sve`) and treats `p0..p15` and `ffr` (`preg`) as clobber-only (`supported_types() == &[]`). Consequently, `out("z0") _`, `let y: u64; out("z0") y`, and `out("p0") _, out("ffr") _` all compile with exit code `0` in baseline `aarch64-unknown-linux-gnu` functions **without** `#[target_feature(enable = "sve")]`. While LLVM's AArch64 MC assembler rejects bare SVE/PAC mnemonics without target features, hint-space instructions (`paciasp`, `autiasp`) assemble unconditionally and inline `.arch_extension sve`/`sve2`/`sme`/`pauth`/`memtag` directives bypass MC feature gates completely inside unguarded Rust functions.
   - **Why `out("z0") _` (`=&{q0}`) preserves intra-function SVE spills yet AAPCS64 Base PCS destroys `[VL-1:64]`:** `rustc_codegen_llvm/src/asm.rs:721-736` lowers discarded `out("z0") _` to 128-bit `<2 x i64>` `=&{q0}`. Unlike x86 `out("ymm0") _` (`={xmm0}` omitting `vzeroupper`), LLVM's `AArch64RegisterInfo` models `Z0..Z31` as super-registers of `Q0..Q31`, so live `svuint64_t` values spilled across `out("z0") _..out("z31") _` use full-width `str zN, [x8, #-1, mul vl]` and preserve all lanes at both `VL = 256` and `VL = 512` bits (`qemu-aarch64`). By contrast, crossing **AAPCS64 Base PCS vs. SVE PCS** exposes an architectural zeroing cliff: an `#[target_feature(enable = "sve")]` `extern "C"` callee without SVE types in its signature uses Base PCS (`str d8` / `ldr d8`), saving only `[63:0]` and **architecturally zeroing `[127:64]` and `[VL-1:128]`** upon `ldr d8` (`base_pcs_callee_z8_lane1 = 0x0`).
   - **`options(preserves_flags)` lowers to `~{cc}` (`NZCV`) only, omitting `FPSR` and `FPCR`:** On AArch64, `rustc_codegen_llvm/src/asm.rs:260-262` emits `~{cc}` when `preserves_flags` is absent and omits `~{fpsr}` unconditionally. Live `qemu-aarch64` execution demonstrates three distinct failure modes: (a) mutating `NZCV` (`subs`) inside `options(preserves_flags)` causes `rustc -O` to miscompile `5 == 9` to `true` (`0xdeadbeef`); (b) NEON `uqadd` inside `options(preserves_flags)` compiles cleanly while setting sticky `FPSR.QC` (`0x08000000`), violating Rust's normative `r[asm.rules.preserved-registers]` contract; and (c) LLVM's instruction scheduler sinks pure Rust `f64` `fadd` (`let sum_before = a + b;`) *past* a subsequent `asm!("msr fpcr, x9")` setting `FPCR.FZ = 1`, flushing subnormal results created lexically *before* the `asm!` (`0x2 -> 0x0`).

2. **Upper-Bit Pointer Tagging (`TBI0`, `PAC`, `MTE`) Refutes Raw-Word Kripke Equality and Requires `FEAT_FPAC`-Aware Capability Stripping (`Basis: normative + execution + derived`):**
   - On `qemu-aarch64 -cpu max`, a `TBI0`-tagged pointer `p_tbi = raw_p | (0xA5 << 56)` satisfies `(p_tbi == raw_p) == false` as a 64-bit word yet loads and stores the identical memory cell as `raw_p`, refuting `reg == α(allocId) + offset`.
   - Conversely, stripping upper bits via `canonicalizeAddr(p)` alone is unsound under synchronous `MTE` (`PR_MTE_TCF_SYNC` + `PROT_MTE`): `p_tag5 = base | (5 << 56)` and `base` share the exact canonical address `base`, yet `p_tag5` loads `0x777788889999aaaa` while `base` (`tag 0 != 5`) and `p_tag5 + 16` (`tag 5 != 9`) fault synchronously with `SIGSEGV` (`rc = -11`).
   - Live testing across QEMU AArch64 CPU models exposes a critical three-regime `PAC` split: on **`-cpu max` and `-cpu neoverse-n2` (`FEAT_FPAC`, Armv8.6-A+)**, `autda` on a 1-bit-corrupted signature faults *synchronously at `autda`* with `SIGILL` (`rc = -4`), whereas on **`-cpu neoverse-v1` (`FEAT_EPAC` without `FEAT_FPAC`, Armv8.4-A)**, `autda` **succeeds without faulting**, XOR-canceling the MAC to leave `raw ^ (1 << 49)`—which faults with `SIGSEGV` if dereferenced directly, **but is stripped back to valid dereferenceable `raw` (`0x42`) by an unauthenticated `xpacd` instruction**! Sound pointer authentication in `MachineSeam` must therefore distinguish `autAuthenticate` from `xpacStrip` and track `FpacMode`.

3. **Silent `rust-lld` `STT_TLS` Mislinking on AArch64 and `+outline-atomics` (`__aarch64_*` / `ExclusiveMonitor`) Dual-Path Anatomy (`Basis: source + execution`):**
   - **AArch64 `STT_TLS` mislinking confirmed:** Linking a non-TLS Rust `extern "C" { static c_tls_var: u64; }` against an AArch64 ELF `.o` defining `STT_TLS` `c_tls_var` (`.tdata` offset `0x30`) via `rust-lld` (`23.1.1`) **exits with code `0` and zero diagnostics** across both `rustc 1.99.1` and `1.101.0-nightly`. In PIE mode (`-C relocation-model=pic`, `-pie`), `ld.lld` emits `R_AARCH64_RELATIVE 0x30` (or relaxes GOT loads to PC-relative `nop; adr x8, 0x30`), resolving `&raw const c_tls_var` to `pie_base + 0x30` so Rust silently reads **`0x0038004000000000`**—the binary's own AArch64 ELF64 header bytes (`e_ehsize = 0x40`, `e_phentsize = 0x38`)! In static non-PIE mode (`-C relocation-model=static`), `ld.lld` resolves `c_tls_var` to absolute zero-page address `0x0000000000000030`, crashing with `SIGSEGV` (`rc = -11`).
   - **`+outline-atomics` binary anatomy and `ExclusiveMonitor` hazards:** On `aarch64-unknown-linux-gnu`, `libcompiler_builtins` ships `100` C-shim `.o` helpers (`__aarch64_cas{1,2,4,8,16}_{relax,acq,rel,acq_rel}` and `__aarch64_{swp,ldadd,ldclr,ldeor,ldset}{1,2,4,8}_{relax,acq,rel,acq_rel}`; zero `_sync` symbols exist, as `SeqCst` lowers to `_acq_rel`; `fetch_max`/`min`/`nand` remain inline `ldaxr`/`stlxr` loops). Because `compiler-builtins-c` replaces the Rust `naked_asm!` shims via `#[maybe_use_optimized_c_shim]`, `HAVE_LSE_ATOMICS` is dead-store-eliminated (`__rust_enable_lse` compiles to bare `ret` `0xd65f03c0`!) and runtime dispatch consults `__aarch64_have_lse_atomics` populated by `.init_array.90` constructor `init_have_lse_atomics` (`getauxval(AT_HWCAP = 16)` bit 8 `HWCAP_ATOMICS`). While the helpers themselves clobber only `{x0, [x1], [x15], x16, x17, nzcv}` (`stlxr w15` / `stlxp w15` in `ldadd*` and `cas16*`), LLVM callers conservatively spill `x0..x18` and `q0..q31` around `bl __aarch64_*`. Moreover, `__aarch64_cas*` omits `clrex` on mismatch, and live `qemu-aarch64` probes confirm that `clrex`, interleaved reservations on another address, and nested failing `__aarch64_cas8_acq_rel` calls all clear an outer `ldxr` reservation (`stxr` status `= 1`).

4. **Zero-`sorry` Pass-1 Lean `v4.34.1` `IsaParametricSeam` Mechanization (`Basis: execution + derived`):**
   - [`support/IsaParametricMachineSeam.lean`](support/IsaParametricMachineSeam.lean) (`prelude` + `Init.*` only, `0.86 s` synchronous kernel check under `-DElab.async=false -Ddebug.skipKernelTC=false`, axioms `[propext, Quot.sound]`) mechanizes `TaggedAddrPolicy`, `RegSaveContract` (`SliceMask`), and fuel/schedule-indexed `ExclusiveState` (`runLlscRmw`, `runOutlinedRmw`, `runOutlinedCasFallback`) across 13 machine-checked theorems.

## Findings

### 1. AArch64 `asm!` Target-Feature Gates, SVE/Base-PCS Partial-Vector Clobbers, and `FPSR`/`FPCR` Hazards

`Basis: normative + source + execution` ([`support/probe_aarch64_seams.py`](support/probe_aarch64_seams.py), [`support/probe_aarch64_seams_results.json`](support/probe_aarch64_seams_results.json)).

#### 1.1 How `rustc` Lowers `z0..z31` and `p0..p15` Without `#[target_feature(enable = "sve")]`

Inspecting `compiler/rustc_target/src/asm/aarch64.rs:9-72, 145-203`, `compiler/rustc_hir_typeck/src/inline_asm.rs:435-518`, and `compiler/rustc_codegen_llvm/src/asm.rs:88-108, 721-748` (`58cf8f9c35`) and testing 12 `asm!` forms across `1.99.1` and `1.101.0-nightly` reveals an AArch64 structural counterpart to—and subtle divergence from—the x86 `out("ymm0") _` blind spot:

1. **`"z0".."z31"` are aliases of NEON `v0..v31` in `rustc`:** `def_regs!` (`aarch64.rs:145-176`) declares `v0: vreg, vreg_low16 = ["v0", "b0", "h0", "s0", "d0", "q0", "z0"]`. There is no separate `zreg` class, and `vreg.supported_types()` (`lines 63-68`) gates solely on `neon` (baseline-enabled on `aarch64-unknown-linux-gnu`). Consequently, **both** clobber `out("z0") _` (`=&{q0}` with `<2 x i64>`) **and** typed `let y: u64; out("z0") y` (`=&{d0}` with `i64`) compile cleanly (`rc = 0`) in baseline functions lacking `sve`! Meanwhile, `p0..p15` and `ffr` belong to `preg` (`supported_types() == &[]`), so `out("p0") _, out("ffr") _` bypasses `inline_asm.rs:463` (`!op.is_clobber()`) and `asm.rs:89` (`is_clobber_only`), compiling cleanly (`rc = 0`) to `"~{p0},~{ffr},~{cc},~{memory}"` without `sve`.
2. **LLVM MC subtarget check vs. `.arch_extension` and `HINT`-space bypass:** Unlike LLVM's x86 assembler (which encodes `vpaddq %ymm0` inside `"target-cpu"="x86-64"` functions lacking `+avx2`), LLVM's AArch64 MC assembler rejects bare `"incb x0"` (`error: instruction requires: sve or sme`) and bare `"pacia x0, x1"` (`error: instruction requires: pauth`) when the enclosing Rust function lacks the feature. However:
   - `HINT`-encoded instructions (`paciasp`, `autiasp`, `bti c`) assemble unconditionally (`rc = 0`); and
   - Embedding `.arch_extension sve`, `.arch_extension sve2`, `.arch_extension sme`, `.arch_extension pauth`, or `.arch_extension memtag` (or raw `.inst 0x...`) inside `asm!` **overrides LLVM MC's feature check (`rc = 0`)**, emitting `incb`/`ptrue`/`dup z0.d`, `smstart`/`smstop`, `pacia`/`autia`, or `stg` inside unguarded functions that safe callers can invoke or inline without `unsafe` `#[target_feature]` checks.

#### 1.2 Live SVE Upper-Lane Spilling vs. AAPCS64 Base-PCS `[VL-1:64]` Architectural Zeroing

Testing live SVE register preservation under `qemu-aarch64` at both `VL = 256` bits (`-cpu max,sve-default-vector-length=32`, `cntb = 0x20`) and `VL = 512` bits (`-cpu max`, `cntb = 0x40`) separates two cases that verifiers must not conflate:

- **Intra-function `out("z0") _` (`=&{q0}`) does *not* corrupt live SVE variables in LLVM:** When `test_sve_spill_across_all_z_clobbers` holds a live `svuint64_t` across `asm!("dup z0.d, #-1; dup z8.d, #-1", out("z0") _, ..., out("z31") _)`, every `out("zK") _` lowers to 128-bit `=&{qK}`. Because LLVM's `AArch64RegisterInfo` registers `Q0..Q31` as sub-registers of `Z0..Z31`, the register allocator detects interference on `Z0` and emits full-width scalable stack spills (`addvl sp, sp, #-1; str z0, [x8, #-1, mul vl]` ... `ldr z0, [x8, #-1, mul vl]`), preserving all 4 lanes at `VL = 256` (`0x1111111111111110..0x4444444444444443`) and all 8 lanes at `VL = 512` (`..0x8888888888888887`). Moreover, unlike x86 AVX (`X86InsertVZeroUpper`), AArch64 has no microarchitectural dirty-upper state transition penalty because any NEON `b/h/s/d/q` write **eagerly zeroes `[VL-1:128]`** in hardware.
- **AAPCS64 Base PCS vs. SVE PCS (`ARM-software/abi-aa@9f9e067e`, `aapcs64.rst` §6.1.3 & §7) creates a silent partial-width clobber cliff on `v8..v15` / `z8..z23`:**
  - `compiler_sve_pcs_callee(x: svuint64_t, ptr: *const u64) -> svuint64_t` (which carries an SVE vector in its signature, activating **SVE PCS**) emits `addvl sp, sp, #-3; str p4, [sp, #7, mul vl]; str z9, [sp, #1, mul vl]; str z8, [sp, #2, mul vl]` (plus DWARF `.cfi_escape` `VG`-scaled unwind rules), preserving all `[VL-1:0]` bits of `z8..z23` and `p4..p15`.
  - `compiler_base_pcs_callee(ptr: *const u64) -> u64`—**despite carrying `#[target_feature(enable = "sve")]` and executing SVE instructions**—has no SVE parameter or return type, so it uses **AAPCS64 Base PCS** and emits **`str d8, [sp, #-32]!` ... `ldr d8, [sp], #32`**! Because `ldr d8` writes the 64-bit `D` view of `z8`, hardware restores `[63:0]` (`lane0 = 0x1111111111111110`) and **architecturally zeroes `[127:64]` (`lane1 = 0x0`) and `[VL-1:128]` (`lane2..7 = 0x0`)**! Symmetrically, any handwritten `naked_asm!` or external `.S` routine called under SVE PCS that saves only `d8..d15` (`buggy_d8_only_sve_callee`) silently zeroes lanes `1..(VL/64 - 1)` of its caller's callee-saved `z8..z15`.

#### 1.3 `options(preserves_flags)` (`~{cc}` Only), `FPSR.QC` Saturation Leaks, and `FPCR` Code Motion

In `compiler/rustc_codegen_llvm/src/asm.rs:258-280`, omitting `options(preserves_flags)` appends `~{dirflag},~{fpsr},~{flags}` on `x86_64` and `~{fflags},~{vtype},~{vl},~{vxsat},~{vxrm}` on `riscv64`, **but appends only `~{cc}` (`NZCV`) on `AArch64`**, never emitting `~{fpsr}` or `~{fpcr}`. Live `qemu-aarch64 -cpu max` execution (`probe_aarch64_seams_results.json` -> `sve_pcs_and_flags_live`) establishes three concrete consequences:

1. **Live `NZCV` branch miscompilation (`nzcv_miscompile_witness`):** Comparing `let eq = a == b;` (`a = 5, b = 9`), overwriting `a, b` via `inout(reg)` inside `asm!("subs {x}, {x}, {x}; mov {y}, #0", ..., options(nomem, nostack, preserves_flags))`, and branching `if eq { 0xDEAD_BEEF } else { 0x1111_2222 }` causes LLVM to reuse `NZCV` across the `asm!` without re-comparing; `subs x, x, x` sets `Z = 1`, returning **`0x00000000deadbeef`** for `5 == 9`.
2. **Unchecked `FPSR.QC` & IEEE exception flag mutation (`fpsr_qc_sticky_probe`):** Normative Rust rule `r[asm.rules.preserved-registers]` (`rust-lang/reference@c9cc3282`, `src/inline-assembly.md:1381-1383`) requires `options(preserves_flags)` on AArch64 to preserve **both `NZCV` and `FPSR`**. Yet `uqadd v0.16b, v0.16b, v0.16b` (`0xff + 0xff`) and `fdiv s0, s0, s1` (`1.0 / 0.0`) inside `options(preserves_flags)` compile with zero warnings while mutating `FPSR` from `0x0` to **`0x08000000`** (`FPSR.QC` bit 27, which stays sticky at `0x08000000` across subsequent non-saturating `add v0.16b`) and **`0x00000002`** (`FPSR.DZC` bit 1). An Anneal `InlineAsm` verifier must reject any `options(preserves_flags)` block executing saturating SIMD (`SQADD`, `UQADD`, `SQRDMULH`, `SQXTN`, `UQXTN`, `SQRSHR`) or potentially trapping/flag-setting FP arithmetic, or resetting vector state via `smstart`/`smstop` (which sets `FPSR = 0x0800009f`).
3. **LLVM `fadd` code motion across `FPCR` writes (`fpcr_sink_demo`):** In Rust source:
   ```rust
   let sum_before = a + b; // a = b = f64::from_bits(1), true sum = f64::from_bits(2)
   asm!("mrs {orig}, fpcr; orr x9, {orig}, #(1 << 24); msr fpcr, x9", ...);
   ```
   Because LLVM's default FP environment (`fpexcept.ignore`) models `fadd d0, d0, d1` as pure with zero dependency on `FPCR` or memory, `rustc 1.99.1 -O` **sinks `fadd d0, d0, d1` after `msr FPCR, x9` (`FZ = 1`)**, flushing `sum_before` to **`0x0000000000000000` (`0.0`)**! Any `asm!` block that modifies `FPCR` (rounding mode `[23:22]` or `FZ` bit 24) must restore `FPCR` **inside the same `asm!` block** and pass affected FP values through explicit `asm!` register operands.

### 2. Upper-Bit Pointer Tagging (`TBI0`, `PAC`, `MTE`) vs. Kripke Address Map $\alpha$

`Basis: normative + source + execution + derived` (`torvalds/linux@65e4fd94`, `ARM-software/abi-aa@9f9e067e`, [`support/probe_aarch64_seams_results.json`](support/probe_aarch64_seams_results.json), [`support/IsaParametricMachineSeam.lean`](support/IsaParametricMachineSeam.lean)).

On `x86-64` without `LAM`, a valid user pointer in a 64-bit GPR has `[63:47] == 0`, so its raw 64-bit unsigned value equals its virtual address $\alpha(\text{allocId}) + \text{offset}$. On `AArch64` Linux (`VA_BITS = 48`, `TCR_EL1.TBI0 = 1`), bits `[63:48]` are partitioned into `[63:60]` software `TBI0` nibble, `[59:56]` `MTE` logical allocation tag, `[55]` `TTBR0`/`TTBR1` selector (`0` for EL0), and `[54:48]` `PAC` signature (`GENMASK_ULL(54, vabits_actual)`). ### 3. AArch64 `rust-lld` `STT_TLS` Mislinking and `+outline-atomics` (`__aarch64_*` / `ExclusiveMonitor`) Anatomy

`Basis: source + execution` (`rust-lang/rust@58cf8f9c35`, `rust-lang/llvm-project@1b9c0d5ff9`, [`support/probe_aarch64_seams_results.json`](support/probe_aarch64_seams_results.json)).

#### 3.1 Resolution of the AArch64 `rust-lld` `STT_TLS` Open Question

In `rust-cpp-ffi-abi-soundness-improper-ctypes-setjmp-errno-and-init-array`, declaring a C `__thread` (`STT_TLS`) variable as a non-TLS Rust `extern "C" { static c_tls_var: u64; }` was shown to link silently under `rust-lld` (`23.1.1`) on `x86_64-unknown-linux-gnu` while reading the ELF64 header at `pie_base + st_value`. Assembling an AArch64 ELF object (`llvm-mc --triple=aarch64-unknown-linux-gnu`) defining `STT_TLS GLOBAL DEFAULT c_tls_var` at `.tdata` offset `0x30` (`0x1122334455667788`) and linking it via `rust-lld` across `rustc 1.99.1` and `1.101.0-nightly` proves that **the exact same silent linker bug affects `aarch64-unknown-linux-gnu` in both PIC/PIE and static relocation models**:

1. **PIE / PIC mode (`-C relocation-model=pic`, `-pie`, default on Linux):** `rustc` emits `R_AARCH64_ADR_GOT_PAGE` + `R_AARCH64_LD64_GOT_LO12_NC` against `UND NOTYPE c_tls_var`. `ld.lld` **exits with code `0` and zero warnings**, binding the non-TLS GOT slot to the `STT_TLS` symbol's TLS-template offset (`st_value = 0x30`) via `.rela.dyn` `R_AARCH64_RELATIVE 0x30` (or, when `adrp` and `ldr` are adjacent and in `±1 MiB` range, relaxing them directly to PC-relative `nop; adr x8, 0x30`!). Under `qemu-aarch64 -cpu max`, `&raw const c_tls_var` resolves to `pie_base + 0x30`, silently reading **`0x0038004000000000`**—byte-for-byte identical to the AArch64 ELF64 header at `[0x30..0x38]` (`e_ehsize = 0x0040`, `e_phentsize = 0x0038`)!
2. **Static non-PIE mode (`-C relocation-model=static`):** `rustc` emits `R_AARCH64_ADR_PREL_PG_HI21` + `R_AARCH64_ADD_ABS_LO12_NC`. `ld.lld` again **exits with code `0`**, emitting `adrp x8, 0x0; add x8, x8, #0x30` (`0x0000000000000030` in the unmapped null page) and crashing immediately with **`SIGSEGV` (`rc = -11`)**!
3. **Single-CGU symbol-aliasing corollary:** If a single Rust codegen unit declares `#[link_name = "c_tls_var"]` both with `#[thread_local]` (emitting `mrs x22, TPIDR_EL0` + AArch64 Variant-I `16`-byte TCB offset) and without `#[thread_local]`, `rustc_codegen_llvm` merges both into a single LLVM `@c_tls_var` global inheriting whichever TLSness was declared first. Any object-level `.o` verifier must therefore enforce **symbol-type / relocation-class parity** (`sym.st_type == STT_TLS <-> reloc ∈ TlsRelocs`) independently of `rust-lld`.

#### 3.2 `+outline-atomics` Archive Shims, Dead `__rust_enable_lse`, and `ExclusiveMonitor` Semantics

Inspecting `library/compiler-builtins/compiler-builtins/src/aarch64_outline_atomics.rs:1-467`, `library/std/src/sys/configure_builtins.rs:1-62`, and disassembling `libcompiler_builtins-6d387bb3469b4925.rlib` (`aarch64-unknown-linux-gnu`) alongside `aarch64-apple-darwin` and `aarch64-pc-windows-msvc` (`1.99.1`) establishes the exact binary contract:

- **Exact 100-symbol inventory (no `_sync` suffix):** `libcompiler_builtins` defines 20 CAS helpers `__aarch64_cas{1,2,4,8,16}_{relax,acq,rel,acq_rel}` and 80 1–8 byte RMW helpers `__aarch64_{swp,ldadd,ldclr,ldeor,ldset}{1,2,4,8}_{relax,acq,rel,acq_rel}` (zero `_sync` symbols exist; `Ordering::SeqCst` calls `_acq_rel`, while `fetch_max`/`fetch_min`/`fetch_nand` and 128-bit `fetch_add` emit inline `ldaxr`/`stlxr` or `ldaxp`/`stlxp` loops even under `+outline-atomics`).
- **Two-mechanism LSE initialization split (`compiler-rt` `.o` vs. pure-Rust `compiler_builtins`):**
  - On `aarch64-unknown-linux-gnu` (and `aarch64-apple-darwin`), the shipped sysroot `libcompiler_builtins.rlib` is compiled with **`compiler-builtins-c`**, embedding `lse_*.o` and `aarch64.o` from LLVM `compiler-rt`. Every `__aarch64_*` helper loads `u8` **`__aarch64_have_lse_atomics`** (`R_AARCH64_ADR_PREL_PG_HI21` + `R_AARCH64_LDST8_ABS_LO12_NC`), which is initialized before `main` by local `.init_array.90` constructor `init_have_lse_atomics` (`mov w0, #0x10; bl getauxval; ubfx w8, w0, #8, #1; strb w8, [x9]`, testing `AT_HWCAP` bit 8 `HWCAP_ATOMICS`). Because `#[maybe_use_optimized_c_shim]` suppresses all 100 Rust `naked_asm!` definitions in `aarch64_outline_atomics.rs`, `HAVE_LSE_ATOMICS` has zero readers and **`__rust_enable_lse` in the shipped Linux `rlib` is dead-store-eliminated to a single `ret` (`0xd65f03c0`)**! (Conversely, in pure-Rust `compiler_builtins` builds without `compiler-builtins-c`, `std::sys::configure_builtins::RUST_LSE_INIT` places `init_lse` in `.init_array.90` to call `__rust_enable_lse()`, while `#![no_std]` targets without CRT `.init_array` keep the global `0` and execute the LL/SC loop unconditionally.)
- **Disassembled instruction & clobber anatomy (`libcompiler_builtins-6d387bb3469b4925.rlib`):**
  - **`__aarch64_cas8_acq_rel(x0=expected, x1=desired, x2=ptr) -> x0`:** Loads `__aarch64_have_lse_atomics` into `w16`; if non-zero executes `casal x0, x1, [x2]; ret`; else `mov x16, x0; 1: ldaxr x0, [x2]; cmp x0, x16; b.ne 2f; stlxr w17, x1, [x2]; cbnz w17, 1b; 2: ret`. Clobbers **`{x0, x16, x17, nzcv}`** and **omits `clrex` on `b.ne`**.
  - **`__aarch64_ldadd4_acq_rel(w0=val, x1=ptr) -> w0` & `__aarch64_cas16_acq_rel(x0:x1, x2:x3, x4=ptr) -> x0:x1`:** Fast path executes `ldaddal w0, w0, [x1]; ret` / `caspal x0, x1, x2, x3, [x4]; ret`; fallback loop executes `stlxr w15, w17, [x1]` / `stlxp w15, x2, x3, [x4]`, clobbering **`x15` (`w15`) in addition to `x16, x17, nzcv`** (matching `compiler-rt` `lse.S` and `aarch64_outline_atomics.rs:295, 354`). At the call site (`caller_register_pressure_across_outlined_atomics`), LLVM conservatively treats `bl __aarch64_*` as standard AAPCS64 (`x0..x18, v0..v31` volatile), spilling caller temporaries onto the stack, so `w15` clobbering is safe for compiler-generated callers—but handwritten assembly calling `bl __aarch64_ldadd*` or `cas16*` **must not** assume `x15` is preserved!
- **Live `ExclusiveMonitor` nondeterminism (`probe_aarch64_seams_results.json`):** Under `qemu-aarch64 -cpu max`, `ldxr` on `cell_x` followed by (a) `clrex` (`stxr_after_clrex = 1`), (b) an intervening `ldxr`/`stxr` on `cell_y` (`stxr_after_interleaved_y = 1`), or (c) a *failing* `bl __aarch64_cas8_acq_rel` on `cell_y` (`stxr_after_nested_failed_cas = 1`) unconditionally causes the outer `stxr` on `cell_x` to fail without mutating `cell_x`, while both `__aarch64_have_lse_atomics = 0` and `1` produce identical RMW results (`llsc_eq_lse = 1`).

## Boundaries

- **Multi-core weak-memory ordering of `LDXR`/`STXR` vs. LSE (`not examined` here):** Section 3 mechanizes single-location RMW linearizability, reservation clearing, and non-termination under adversarial `ExclusiveMonitor` schedules; relaxed/release-acquire weak-memory litmus interactions across concurrent hardware threads are covered in `assembly-atomic-fence-mappings-and-aarch64-x86-weak-memory-models` and `tier1-atomics-and-fences-instruction-lowering`.
- **Kernel-space `TTBR1_EL1` (`bit 55 == 1`), `VA_BITS = 52` (`FEAT_LVA`), and asymmetric/async `MTE` (`PR_MTE_TCF_ASYNC`) (`not examined` in Lean model):** `PtrWord64` and `isaLoadByte` specialize to EL0 user pointers (`VA48`, `bit55 = false`) and synchronous `PR_MTE_TCF_SYNC`. Under `PR_MTE_TCF_ASYNC`, tag mismatches do not fault synchronously at the offending load/store (`SEGV_MTEAERR` is delivered asynchronously at kernel entry/exit), so synchronous load fault-freedom (`isa_parametric_load_sound`) is **known not to apply** to asynchronous `MTE` fault detection without carrying a sticky fault bit in machine state.
- **Physical silicon timing and cache-line Exclusive Reservation Granule (`ERG`) sizes (`not examined`):** All `qemu-aarch64` (`11.1.2`) runs execute under functional user-mode TCG emulation (`ERG` modeled per reservation address). On physical Arm cores, `ERG` spans `16..2048` bytes (`CTR_EL0.ERG`), meaning false-sharing stores to *distinct* variables within the same cache line also trigger spurious `STXR` clears—already soundly over-approximated by `clearSched : Nat → Bool` in `IsaParametricMachineSeam.lean`.
- **Rust stable `preg` / scalable `zreg` typed `asm!` operands (`unsupported`):** Both `rustc 1.99.1` and `1.101.0-nightly` reject typed inputs/outputs on `preg` (`p0..p15`, `ffr`) and >128-bit types on `vreg` (`z0..z31`); passing SVE vectors into `asm!` currently requires loading/storing via pointer or nightly `stdarch_aarch64_sve` intrinsics.
