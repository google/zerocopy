#### 1.3 Exact `rfcbot-rs` State Machine vs. `@rustbot concern` Semantics

Direct source inspection of `rust-lang/rfcbot-rs` (`src/github/nag.rs:379-632, 953-1140`) and `rust-lang/triagebot` (`src/handlers/concern.rs:38-120`) reveals critical invariants that distinguish `@rfcbot` from `@rustbot`:

1. **Exact quorum arithmetic (`nag.rs:430-465`):** Let $N$ be the union of members of all `[rfcbot]` teams labeled on the issue/PR (excluding `exclude-members`), $C$ be `num_complete_reviews` (members whose `* [x] @login` checkbox is ticked in the bot's tracking comment or who posted `@rfcbot reviewed`; the FCP initiator's checkbox is pre-ticked at creation in `nag.rs:997`), and $U = N - C$ be `num_outstanding_reviews`. `evaluate_pendings()` transitions a proposal from `proposed-final-comment-period` (`fcp_start = None`) to `final-comment-period` (`fcp_start = Some(Utc::now())`) when:
   $$\text{active\_concerns} = 0 \;\land\; U < C \;\land\; U \le 2$$
   For a team of $N \ge 6$ (e.g., `compiler-fcp` with $N = 11$ or `libs-fcp` with $N = 7$), $U \le 2$ dominates (requiring $9/11$ or $5/7$ sign-offs). For small teams ($N \in \{1, 2, 3, 4\}$), strict majority $U < C$ prevents a 2-person or 3-person team from entering FCP with 0 or 1 reviews ($N=4 \implies C \ge 3$; $N=3 \implies C \ge 2$; $N=2 \implies C = 2$).
2. **Concern initiation, clock reset, and initiator-only resolution (`nag.rs:1056-1140`):** Any member of a tagged subteam may file `@rfcbot concern <name>`. If `fcp_start` was already set (`final-comment-period` in progress), `process_new_concern` sets `proposal.fcp_start = None`, removes `final-comment-period`, and re-adds `proposed-final-comment-period` (`nag.rs:1088-1102`). Crucially, `process_resolve_concern` queries `fcp_concern` with `.filter(fk_initiator.eq(author.id))` (`nag.rs:1124`): **only the exact GitHub user who registered an `@rfcbot` concern can resolve it** (otherwise the entire FCP must be cancelled via `@rfcbot fcp cancel` and re-proposed). Once resolved, `evaluate_pendings()` sets a fresh `fcp_start = Some(Utc::now())`, restarting the full 10-day window.
3. **Mutual exclusion with `@rustbot concern` (`concern.rs:47-68`):** `triagebot` provides `@rustbot concern <title>` / `@rustbot resolve <title>` for non-`rfcbot` workflows (such as MCPs or ordinary PRs, adding `S-waiting-on-concerns` on `rust-lang/rust` via `triagebot.toml:2079-2080`, which is in `rust-bors.toml`'s `labels_blocking_approval`). `concern.rs:48` calls `is_issue_under_rfcbot_fcp(...)` and rejects `@rustbot concern` if an `rfcbot` FCP is active; conversely, unlike `@rfcbot`, `@rustbot resolve` permits *any* member in `rust-lang/team` to resolve an open `@rustbot` concern (`concern.rs:54-68, 95-103`).

#### 3.2 `@bors` Command Grammar, Queue Ordering, and Two-Branch GitOps Protocol

Inspection of `src/bors/command/mod.rs:404-572`, `src/bors/merge_queue.rs:95-190`, and `src/utils/sort_queue.rs:1-54` establishes the exact command semantics and queue scheduling algorithm:

- **Approval, priority, rollup, squash, and delegation commands:**
  - `@bors r+` / `@bors r=<reviewer>`: Approves the exact current PR `HEAD` SHA (`approved_sha`); any subsequent push to the PR branch automatically invalidates approval (`InvalidationReason::CommitShaChanged`). By default, `bors` waits for PR CI (`11` `pr` jobs) to pass before transitioning from `TentativelyApproved` to `Approved` (`pr_ci_timeout = 7200`s default), unless `force` is specified.
  - `p=<u32>` (`Priority`): Sets queue priority (default `0`). Higher integers sort strictly earlier; `@bors treeclosed=<N>` closes the tree to all PRs with `priority < N` (`@bors treeopen` reopens it).
  - `rollup=always|maybe|iffy|never` (`RollupMode`): Controls rollup eligibility (default `None`, treated identically to `maybe` in queue sorting). Changing `rollup=` or `note=` alone without changing approver or priority requires only `PermissionType::Try` (`command/mod.rs:506-519`) so `@rust-timer` can mark benchmarked PRs `rollup=never` without holding `r+` permissions!
  - `@bors delegate+` / `@bors delegate=try` / `@bors delegate=<user>`: Grants the PR author (or named user) single-PR `review` or `try` authority (`DelegatedPermission`).
  - `@bors squash [commit-message] r+ ...`: Squashes all PR commits into one commit and immediately applies queue properties.
  - `@bors retry` / `@bors cancel` / `@bors r-`: Clears a failed `auto` status to re-test, cancels an in-flight `auto` build while keeping approval, or unapproves.
- **Total queue ordering (`sort_queue_prs`, `sort_queue.rs:4-53`):** At every merge-queue tick, `bors` sorts all non-closed PRs lexicographically by five keys:
  1. `QueueStatus`: `ReadyForMerge (0)` < `Pending (1)` < `Approved (2)` < `TentativelyApproved (3)` < `Failed (4)` < `NotApproved/NotOpen (5)`. If any PR is in `Pending`, the queue halts after checking `ReadyForMerge` (**strictly 1 concurrent `auto` build**, no speculative merge train).
  2. `MergeableState`: `Mergeable | Unknown (0)` < `HasConflicts (1)`.
  3. `Priority`: `priority.unwrap_or(0)` **descending** (highest `p=` first).
  4. `RollupMode`: **`Never (0)` < `Iffy (1)` < `Maybe / None (2)` < `Always (3)`**. Notice the inversion: `rollup=never` PRs get priority `0` within their `p=` tier because they *must* consume a dedicated ~1.5–2.5h `auto` slot alone, whereas `always`/`maybe` PRs wait to be swept into a single rollup PR!
  5. `PullRequestNumber`: **ascending** (oldest PR number first).
- **Two-branch atomic merge preparation (`automation/bors/*`):** Constructing a merge commit on GitHub requires resetting a staging branch to `main` and merging the PR head—two non-atomic API operations. To prevent GitHub Actions from triggering duplicate CI runs on the intermediate reset, `bors` performs the reset + merge on CI-silent **`automation/bors/{auto-merge,try-merge,try-perf-merge}`** and then atomically force-pushes the resulting merge commit to CI-active **`automation/bors/{auto,try,try-perf}`** (`unroll_queue.rs:17-21`, `merge_queue.rs:95`).

#### 3.3 Rollups, `rollup=never` Criteria, `@rust-timer`, and `@craterbot`

- **Rollup assembly (`src/github/rollup.rs:23-167`) and `[unroll]` (`src/bors/unroll_queue.rs:65-160`):** Because a full `90`-job `auto` build takes ~1.5–2.5 hours (`~10–16` serial `auto` slots/day) while `rust-lang/rust` merges `30–60+` PRs/day, reviewers with `Review` permission select up to **`50` approved PRs** (`ROLLUP_PR_LIMIT = 50`) on the `bors` web queue UI, which authenticates via GitHub OAuth, sequentially merges their heads into a branch on the reviewer's fork, opens a `"Rollup of K pull requests"` PR, and runs one combined `auto` build.
  - **Why PRs use `rollup=never`:** (a) **Submodule updates** (`src/llvm-project`, `src/tools/cargo`, `src/gcc`, etc.) and **`Cargo.lock` changes**, which frequently conflict or cause non-local build failures painful to bisect across 30 PRs; (b) **Risky/platform-fragile changes** (`rollup=iffy` is used for moderate risk, included only in small rollups); and (c) **Compiler performance-sensitive PRs**, although `[unroll]` (`rust-bors.toml:107`) mitigates rollup masking: once a rollup's `auto` build merges into `main`, `unroll_queue.rs` asynchronously builds each constituent PR individually on `automation/bors/try-perf` (`TRY_PERF_MERGE_BRANCH_NAME` -> `automation/bors/try-perf`) so `rustc-perf` obtains per-PR artifact series and posts a post-hoc attribution table on the rollup PR!
- **`@bors try` and `@rust-timer` (`src/ci/citool/src/jobs.rs:304-355`, `rustc-dev-guide/src/tests/perf.md`):**
  - Default `@bors try` runs only the `2` quick Linux dist jobs (`dist-x86_64-linux-quick` on 32-vCPU `c8a.8xlarge` and `dist-aarch64-linux-quick` on 16-vCPU `c9g.4xlarge`) with `DIST_TRY_BUILD=1` injected by `citool` (`jobs.rs:344-354`), instructing `opt-dist` to skip PGO/BOLT training and full test suites to produce downloadable sysroots rapidly.
  - Custom job subsets use `@bors try jobs=<glob1>,<glob2>` matching `auto` + `optional` job names via `glob_match` (capped at **`MAX_TRY_JOBS_COUNT = 20`** jobs unless `nolimit` is passed: `@bors try jobs=dist-* nolimit`, `jobs.rs:304, 323-330`), and run with `fail-fast: false` (`.github/workflows/ci.yml:101`).
  - `@bors try @rust-timer queue` triggers a try build followed by `rustc-perf` benchmarking on dedicated bare-metal `x86_64-unknown-linux-gnu` collector hardware (`@rust-timer build <40-hex-sha>` benchmarks an already-completed try merge SHA).
- **`@craterbot` ecosystem experiments (`rust-lang/crater:docs/bot-usage.md:1-140`):** Requires `crater = true` permission and a completed `@bors try` artifact (`start=<parent-auto-sha> end=<try-merge-sha>`). Supports **`6` modes** (`build-and-test`, `build-only`, `check-only` / shorthand `@craterbot check`, `clippy`, `rustdoc`, and `fix` for edition migration verification) across **`5` crate-selection scopes** (`full` covering all crates.io + GitHub repos known to Crater in ~3–6 days on x86_64 Linux, `top-{n}`, `random-{n}`, `list:{...}`, or an HTTP `retry-regressed-list.txt` URL). #### 4.3 Content-Addressed Docker Caching and `download-ci-llvm` Reuse

- **Docker image SHA-512 keying (`src/ci/docker/run.sh:342-448`):** `src/ci/docker/` contains **`62` Dockerfiles** (`57` under `host-x86_64/`, `5` under `host-aarch64/`) sharing **`49` build scripts** in `src/ci/docker/scripts/`. Before building `image`, `docker/run.sh` constructs `/tmp/.docker-hash-key.txt` by concatenating: (1) `image` name, (2) exact `Dockerfile` contents, (3) contents of all files referenced by non-multi-stage `COPY` directives sorted under `LC_ALL=C`, (4) normalized host architecture (`x86_64` or `aarch64`), and (5) manual cache-buster `"4"`, hashing the stream with **`sha512sum`**.
  - On **`auto`/`try` runs**, CI logs into `ghcr.io` and runs `docker pull ghcr.io/rust-lang/rust-ci:<sha512>`; on a cache hit, `docker build` is skipped completely, avoiding layer-cache thrashing (`docker/run.sh:441-448`). On a miss, it builds and pushes both `rust-ci:<sha512>` and BuildKit registry cache `rust-ci-cache:<sha512>`.
  - On **unprivileged `pr` runs** (`PR_CI_JOB == "1"`), CI spins up `ghcr.io/rust-lang/buildkit:buildx-stable-1` and builds read-only with `--cache-from type=registry,ref=ghcr.io/rust-lang/rust-ci-cache:<sha512>` (`docker/run.sh:421-434`).
  - Furthermore, C/C++ object compilation inside containers uses **`sccache`** backed by `s3://rust-lang-ci-sccache2` (`SCCACHE_C_CUSTOM_CACHE_BUSTER=2`, `src/ci/run.sh:235`).
- **`download-ci-llvm` artifact reuse (`src/ci/run.sh:182-205`, `src/bootstrap/src/core/download.rs:274-395`):**
  - Rebuilding `src/llvm-project` from C++ source on every test runner would dominate CI compute. In `src/ci/run.sh:191`, every non-`DEPLOY` test builder (unless `NO_DOWNLOAD_CI_LLVM=1` or external system LLVM `LLVM_VERSION="22"` is set) configures **`--set llvm.download-ci-llvm=if-unchanged`**.
  - `maybe_download_ci_llvm` (`download.rs:274-357`) calls `detect_llvm_freshness` to find the most recent upstream `bors` commit touching `src/llvm-project` or `src/bootstrap/download-ci-llvm-stamp`. If the PR has *no* local modifications to `src/llvm-project` (`if-unchanged`), bootstrap downloads pre-built `rust-dev-<version>-<triple>.tar.xz` (selecting `artifacts_with_llvm_assertions_server` when `llvm.assertions = true`, built by `dist-x86_64-linux-alt` / `dist-x86_64-msvc-alt`) into `build/<triple>/ci-llvm`, touches `llvm-config` mtime so Cargo's `rustc_llvm` build script re-runs, and verifies option compatibility against the archived `ci-llvm` `bootstrap.toml`! If a PR modifies `src/llvm-project`, `if-unchanged` transparently falls back to building LLVM from source on CI. (On local developer checkouts, `bootstrap.{compiler,library,tools}.toml` default to `download-ci-llvm = true`, while `bootstrap.dist.toml` sets `download-ci-llvm = false`.)

#### 6.2 Staged Library Stability and Recursive `const` Stability (`library/`)

Every standard-library facade crate (`core`, `alloc`, `std`, `proc_macro`, `test`, etc.; `13` occurrences in `library/`) declares `#![feature(staged_api)]`, activating item-level cross-crate stability checking across **`18,783` `#[stable(...)]`** and **`14,007` `#[unstable(...)]`** annotations in `library/` (`src/doc/rustc-dev-guide/src/stability.md:1-225`):

1. **Runtime vs. `const` stability asymmetry (`stability.md:60-170`):**
   - **Runtime `#[stable(feature = "...", since = "...")]`** is *non-recursive*: a `#[stable]` function's body may freely call `#[unstable]` functions or intrinsics internally. Macros, whose token trees expand at caller sites, opt in explicitly via **`#[allow_internal_unstable(feat1, ...)]`** (`81` occurrences in `library/`).
   - **Compile-time `#[rustc_const_stable(feature = "...", since = "...")]`** (`973` occurrences) vs. **`#[rustc_const_unstable(feature = "...", issue = "...")]`** (`4,546` occurrences) is **strictly recursive**: a `#[rustc_const_stable]` `const fn` is forbidden from calling any `#[rustc_const_unstable]` function or using unstable const features—even indirectly or through `#[allow_internal_unstable]` macros—so incomplete CTFE semantics cannot leak to stable `const` contexts.
   - Two escape hatches refine recursive `const` stability:
     - **`#[rustc_const_stable_indirect]`:** Marks a `#[rustc_const_unstable]` function whose *implementation* uses only const-stable operations (remaining const-unstable solely for API-design reasons) as safe to call from `#[rustc_const_stable]` callers and compiler-synthesized lang-item calls.
     - **`#[rustc_allow_const_fn_unstable(feat1, ...)]`** (`56` occurrences in `library/`): Explicitly permits specific unstable features inside a const-stable `const fn`; adding this attribute triggers an automatic `[mentions]` diff-content alert CC'ing `@rust-lang/wg-const-eval` (`triagebot.toml:1802-1808`), while `#[rustc_intrinsic_const_stable_indirect]` requires joint `T-lang` + `wg-const-eval` sign-off (`triagebot.toml:1809-1820`).
2. **Trait impls and default bodies:** `#[rustc_default_body_unstable(...)]` gates default trait method bodies while allowing stable explicit impls; `#[unstable_feature_bound(feat)]` gates `impl StableTrait for StableType` blocks across crate boundaries; and `#[rustc_allowed_through_unstable_modules]` grandfathers pre-September-2024 paths accidentally reachable through unstable parent modules.

#### 6.3 Editions (`2015`..`2024`, `future`) and the Stabilization PR Checklist

- **Span-hygienic edition gating (`compiler/rustc_span/src/edition.rs:1-135`, `src/doc/rustc-dev-guide/src/guides/editions.md`):** `Edition` is an ordered enum `[Edition2015, Edition2018, Edition2021, Edition2024, EditionFuture]`, where `DEFAULT_EDITION = Edition2015`, `LATEST_STABLE_EDITION = Edition2024`, and `EditionFuture` (`--edition=future -Zunstable-options`) is permanently unstable (`is_stable() == false`). Because macros defined in an Edition 2024 crate can expand inside an Edition 2015 crate (and vice versa), compiler passes check **`span.edition()`** (`span.at_least_rust_2024()`) rather than global `tcx.sess.edition()` to preserve macro edition hygiene, and stage edition-tied features through three phases: `tcx.features().foo()` -> `tcx.features().foo() && span.at_least_rust_20xx()` (in-development edition candidate) -> `tcx.features().foo() || span.at_least_rust_20xx()` (accepted edition feature).
- **End-to-end stabilization PR checklist (`stabilization-guide.md:1-185`, `features.rs`, `unstable_book.rs`):**
  1. **Normative docs & report:** Open and get `lang-docs` approval on a `rust-lang/reference` PR (tracked via `needs-reference-pr` in `rust-bors.toml:33`), author the stabilization report (`stabilization-report-template.md`), and complete `@rfcbot fcp merge` (`finished-final-comment-period`).
  2. **Promote feature entry using `CURRENT_RUSTC_VERSION`:** Move `(unstable, foo, ...)` from `compiler/rustc_feature/src/unstable.rs` to sorted `(accepted, foo, "CURRENT_RUSTC_VERSION", Some(issue))` in `accepted.rs` (or change `#[unstable(...)]` -> `#[stable(feature = "foo", since = "CURRENT_RUSTC_VERSION")]` in `library/`). Tidy (`src/tools/tidy/src/features/version.rs:8`) requires the literal placeholder `"CURRENT_RUSTC_VERSION"` so PRs never hardcode a guessed release number across the 6-week branch point; release promotion substitutes the real `1.XX.0` string on branch creation.
  3. **Bootstrap staging (`cfg_attr(bootstrap, ...)`):** Replace `#![feature(foo)]` inside `compiler/` and `library/` with `#![cfg_attr(bootstrap, feature(foo))]` (`stabilization-guide.md:90-95`) because `stage 0` (the previous beta compiler) still treats `foo` as unstable, whereas `stage 1+` emits `stable_features` warnings-as-errors if `#![feature(foo)]` is unconditional!
  4. **Unstable Book & status dump:** Delete `src/doc/unstable-book/src/{language,library}-features/foo.md` (enforced by `tidy`'s `unstable_book.rs`, whereas `src/tools/unstable-book-gen` auto-generates stubs for undocumented remaining unstable features and `rustc -Zhelp` flags) and remove feature-gate rejection checks (`gate_all!`), turning former gate tests into positive regression tests (`src/tools/features-status-dump` exports the resulting `{lang_features_status, lib_features_status}` JSON consumed by release dashboards).
