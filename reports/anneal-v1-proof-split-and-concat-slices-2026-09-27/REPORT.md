# Historical V1 proof-authoring experiments

## Summary

The V1 split gives separate progress and conditional correctness feedback, but duplicates execution reasoning and allows vacuous correctness feedback if progress remains open or admitted. The `concat_slices` case remains an unfinished challenge with trusted helper assumptions.

## Applicability

Historical V1 source, docs, fixtures, and Git history preserved in zerocopy at the identified revision. No current Anneal design claim is inferred from the prototype.

## Findings

### What the split tested

**Observed implementation.** V1 states a theorem from two premises: `∃ y, m = .ok y` and `∀ y, m = .ok y → P y`. Its proof of `WP.spec m P` uses the successful result from the first premise and applies the second to it ([`Anneal.lean`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/Anneal.lean#L62); introduction in `c12d64763`). The generator applies that theorem, emits a progress branch (a supplied `proof (h_progress)` or `eval_progress`), then introduces the returned value and `h_returns` equality for the correctness branch. It instantiates a `Post` structure, giving individual named fields explicit proof scripts or `autoParam` fallbacks ([`generate.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/generate.rs#L453), [`named_bounds.md`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/docs/design/named_bounds.md#L87)). `eval_progress` tries unfolding and splitting, then `⟨_, rfl⟩`/simplification, and finally fails or uses `sorry` according to the mode ([`Anneal.lean`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/Anneal.lean#L68)).

The motivating experiment was independent feedback when an execution step was stuck. The design note says a monolithic WP could block all postcondition diagnostics, while the split let named fields elaborate independently ([`named_bounds.md`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/docs/design/named_bounds.md#L127)). The `stuck_wps` fixture exercises transparent and opaque calls, zero/one/two postconditions, missing or named proofs, and `proof context: sorry`; its configuration explicitly runs `verify --allow-sorry`, and its golden output records `declaration uses sorry` warnings ([fixture source](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/tests/fixtures/stuck_wps/source/crates/app/src/lib.rs), [configuration](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/tests/fixtures/stuck_wps/anneal.toml), [golden](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/tests/fixtures/stuck_wps/expected.stderr)). That fixture demonstrates a diagnostic and fallback workflow under permissive mode, not completed verification of its impossible `False` postconditions.

**Observed cost: duplicated execution reasoning.** The progress proof must establish `.ok`, while each correctness proof may need to unfold and simplify the same function under `h_returns`. In [`abs.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/examples/abs.rs#L1), the long branch/arithmetic tactic sequence appears in `h_progress` and again in each of `h0`, `h1`, and `h2`. In [`anatomy.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/examples/anatomy.rs#L53), `proof context` shares setup among correctness fields, but progress separately reconstructs layout and `fast_add` success and converts a `WP.spec` theorem using `spec_imp_exists` ([`anatomy.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/examples/anatomy.rs#L148)). The split was useful for independent diagnostics, but did not itself share intermediate execution facts across the two branches. A named `Post` field can also repeat `unfold ... at h_returns`; the precondition structure only makes inputs accessible by name.

**Vacuity boundary.** The correctness premise alone is true when `m` never equals `.ok y`, even if `P` is false for every `y`. Thus a locally successful correctness field can be conditional and vacuous if progress remains open or is admitted. The full theorem avoids this *only when its progress premise is genuinely discharged*. V1's own agent guide calls correctness conditional on `h_returns` ([`04_specifications_and_syntax.md`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/docs/agent/04_specifications_and_syntax.md#L294)). Its `--allow-sorry` path places an `Anneal.allow_sorry` marker in generated configuration, lets tactics fall back to `sorry`, and forbids `sorry` only when that flag is absent ([`aeneas.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/aeneas.rs#L61), [`Anneal.lean`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/Anneal.lean#L49)). V1 documentation correctly says that permissive mode is a proof-skipping development aid and that invalid explicit tactic scripts still fail ([`05_proof_architecture.md`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/docs/agent/05_proof_architecture.md#L63)). Treat a solved postcondition under an unfinished or admitted progress goal as partial feedback, never as a verified Rust claim.

### Agent-facing proof-state observations

V1's intervention was mostly *structural*: named `Pre`/`Post` fields, local field failures, injected argument invariants, a generated `h_returns` equality, and Rust-span diagnostic mapping. The generator creates the source map; the Lean build then parses diagnostic JSON and maps spans back to Rust ([`generate.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/generate.rs#L473), [`aeneas.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/aeneas.rs#L462), [`aeneas.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/aeneas.rs#L591)). The failing named-bounds fixture shows both a local explicit `simp_all made no progress` error and an `unsolved goals` message with `h_returns` in context ([source](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/tests/fixtures/named_bounds_lean_failures/source/src/lib.rs), [golden](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/tests/fixtures/named_bounds_lean_failures/expected.stderr)). Such messages are more actionable than an undifferentiated failed theorem, but a mapped error is not a stable, structured goal-state API.

The historical workflow advises agents to author the specification first, inspect expansion, generate a Lean workspace, iterate in `.lean`, and copy working proofs back into Rust comments before final `verify` ([`07_workflow.md`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/docs/agent/07_workflow.md#L19), [`main.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/main.rs#L81)). It recommends small scratch Lean experiments and explicit inspection of the generated code. This is evidence of the ergonomics problem: the agent needs the precise elaborated goal, hypotheses, generated names, and relevant source/model definitions, not only the Rust annotation. `proof context` deliberately permits shared `have`/`let` bindings in term mode but not broad tactics that might change sibling field states ([`named_bounds.md`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/docs/design/named_bounds.md#L94), `79b93f211`).

There is a material contradiction in the V1 advice. [`06_tactics_and_tooling.md`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/docs/agent/06_tactics_and_tooling.md#L24) suggests using Aeneas `progress` in an explicit `h_progress` block, and the named-bounds note likewise proposes moving it there. Yet the generated goal after `wp_prove_orthogonal` is the existential equality, not `WP.spec`; [`anatomy.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/examples/anatomy.rs#L141) explicitly says ordinary Aeneas `progress` does not solve that goal and instead builds `.ok` equalities and applies `spec_imp_exists`. The latter matches the checked-in theorem shape. A prompt or tool should display the *actual goal* before proposing tactics; the contradictory prose cannot be treated as a reliable recipe.

### Preserve the `concat_slices` case

[`ptr_concat.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/examples/ptr_concat.rs#L1) labels itself a test of whether agents can write and prove Anneal specifications. It has three small `unsafe(axiom)` helpers for slice length, pointer cast, and slice construction. Their stated contracts describe metadata, address, size, and an `isize` bound, but their Rust bodies are trusted leaves in this fixture. The target `concat_slices` has a TODO list for same-allocation, contiguity, nonoverlap, concatenated contents, and result allocation. Its `spec` block is empty and its body is `todo!()` ([`ptr_concat.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/examples/ptr_concat.rs#L24)). No completed contract, implementation, or proof is present in this checkout. A successful proof-authoring claim for this case would therefore be unsupported.

This case exposes two distinct tasks an agent must not conflate. First, specify the Rust-level memory and pointer requirements precisely enough that callers know their obligations, including the boundary at which each trusted `unsafe(axiom)` helper is used. Second, establish that the implementation satisfies those requirements and returns concatenated bytes. Metadata and address equalities alone do not prove allocation identity, provenance, lifetime, contiguity, initialization, or the byte-level concatenation claim. The explicit TODOs are useful evaluation criteria, not accepted lemmas. `todo!()` also cannot supply the desired successful-result evidence. The fixture should remain a deliberately unfinished challenge when cited as historical evidence.

### Recommendations derived from the experiment

These are proposals for a future workflow, not observations of current Anneal behavior:

1. Report progress and each correctness obligation separately during authoring, but expose one explicit overall status. Show when a correctness field was checked only under `h_returns`, and label open/admitted progress and any `sorry` as incomplete. Preserve the connection to the Rust program and trust assumptions required by the current design contract ([`DESIGN.md`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/DESIGN.md)).
2. Give an agent a versioned query of the generated theorem, current goal and local context, source/model mapping, and diagnostics after each edit. Reject stale states and show the exact tactic target before suggesting `progress`, `simp_all`, or a manual `.ok` proof. For V1 specifically, include the generated `Pre`/`Post` names and `h_returns` equality.
3. Encourage small checked lemmas that both progress and correctness can consume where the proof system permits it, so cases such as `abs` and `anatomy` do not require repeated execution simplification. This is an authoring direction, not a claim that a particular shared-lemma API already exists.
4. Use `concat_slices` as a staged benchmark: first review the missing Rust contract and trusted leaf assumptions; then compile the implementation; then inspect translated semantics and prove progress; then prove content and allocation postconditions. Record each stage's evidence separately. Do not score an empty spec, axiomatized helper, admitted goal, or conditional postcondition as completed soundness proof.

### Limits of this review

This was a source, fixture, documentation, and local Git-history review. No Docker, Nix, integration suite, compiler run, Lean session, or agent trial was performed. The golden files are checked-in expected outputs, not results freshly reproduced here. I found no completed `concat_slices` run or measurements of agent success, proof time, or tactic-state quality in the reviewed checkout. Accordingly, the duplication and vacuity conclusions follow from visible proof shape and examples; the recommendations need a separately scoped implementation and evaluation.
