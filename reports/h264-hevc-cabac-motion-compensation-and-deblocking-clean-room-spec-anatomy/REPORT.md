# H.264/AVC and H.265/HEVC Spec Anatomy, FFmpeg Divergence, and Clean-Room Verified Rust Architecture

## Summary

ITU-T H.264 (AVC, ISO/IEC 14496-10) and ITU-T H.265 (HEVC, ISO/IEC 23008-2) share a hybrid block-based video coding pipeline—Network Abstraction Layer Unit (NALU) byte-stream framing, hierarchical parameter sets, Context-Adaptive Binary Arithmetic Coding (CABAC), Decoded Picture Buffer (DPB) reference management, spatial intra prediction, fractional-pel Finite Impulse Response (FIR) motion compensation, integer inverse transforms, and in-loop deblocking—yet diverge sharply in their state-machine invariants, intermediate arithmetic dynamic ranges, and data-parallelism boundaries. Direct inspection of upstream `FFmpeg/FFmpeg` (`7ddf7bc8a482cf28b4fab2e63b7093ba35cb6a80`) alongside normative specifications and arithmetic range probes establishes five load-bearing architectural findings for a clean-room, formally verified Rust media stack:

1. **Software Codec Asymmetry in Upstream FFmpeg:** Upstream `FFmpeg/FFmpeg` implements complete, multi-threaded, SIMD-accelerated first-party **decoders** for H.264 (`libavcodec/h264*.c`, ~16.5k lines of C) and HEVC (`libavcodec/hevc/*.c`, ~14.7k lines of C) backed by **56,124 lines** of H.264/HEVC-related assembly and init glue across x86 (`53` files, `34,149` lines), AArch64 (`32` files, `17,066` lines), and RISC-V RVV (`20` files, `4,909` lines). Conversely, `FFmpeg/FFmpeg` contains **no native software rate-distortion encoder** for either H.264 or HEVC: software encoding delegates via FFI wrappers to `libx264` (`libavcodec/libx264.c`, `1,742` lines), `libx265` (`libavcodec/libx265.c`, `1,111` lines), or `OpenH264` (`libavcodec/libopenh264enc.c`, `444` lines), while in-tree H.264/HEVC encoding code is restricted to Coded Bitstream (`cbs_h2645.c`) syntax serialization and hardware-API submission (`vaapi_encode_h264.c`, `vulkan_encode_h264.c`, `d3d12va_encode_hevc.c`, `nvenc_*.c`).
2. **Imperative MMCO vs. Declarative RPS Reference Lifecycles:** H.264 mutates DPB state imperatively after slice decoding via sliding-window eviction and six `memory_management_control_operation` (MMCO) opcodes (`libavcodec/h264_refs.c:680-805`), permitting malformed multi-slice frames or mid-stream SPS changes (`libavcodec/h264_slice.c:1084-1135`) to desynchronize `short_ref` and `long_ref` pointer tables across frame threads. HEVC eliminates MMCO in favor of declarative per-slice Reference Picture Sets (`ST_CURR_BEF`, `ST_CURR_AFT`, `ST_FOLL`, `LT_CURR`, `LT_FOLL` in `libavcodec/hevc/refs.c:357-428`), making reference-slot liveness a pure function of the slice header and active SPS prior to CTB decoding.
3. **Arithmetic Overflow & Intermediate Bit-Width Asymmetry:** H.264's 6-tap quarter-pel luma filter `[1, -5, 20, 20, -5, 1]` rounds and clips intermediate 1D samples on horizontal/vertical half-pel positions (`((sum + 16) >> 5)` clamped to `[0, (1 << bit_depth) - 1]`), except at the center half-pel position `'j'`, where unshifted 1D intermediates reach `[-2550, 10710]` at 8-bit (`[-213688, 475832]` in 2D) and `[-10230, 42966]` at 10-bit—overflowing signed `i16` even in 1D. By contrast, HEVC's 8-tap luma (`[-1, 4, -11, 40, 40, -11, 4, -1]` / `[-1, 4, -10, 58, 17, -5, 1, 0]`) and 4-tap chroma filters right-shift by `BitDepth - 8` before storing into a 16-bit intermediate buffer, bounding 1D outputs strictly within `[-6143, 22522]` across all 8-, 10-, and 12-bit profiles (`[-6143, 22522] \subset [-32768, 32767]`), enabling uniform `i16` SIMD lanes without overflow. Similarly, H.264's $4\times 4$ and $8\times 8$ integer IDCT (`libavcodec/h264idct_template.c:43-69`) must cast intermediate butterfly terms to unsigned `SUINT` (`uint32_t`) because malformed or `transform_bypass` residuals reach `401,440` before the `>> 6` shift and trigger C signed-overflow undefined behavior (UB).
4. **Bit-Serial CABAC Bottleneck and Inline-Assembly TCB Exposure:** Both codecs share the exact Marpe–Schwarz–Wiegand M-coder binary arithmetic decoding step (`libavcodec/cabac.c:32-120`, `libavcodec/cabac_functions.h:108-129`), unified around a `1,343`-byte lookup table (`ff_h264_cabac_tables`). Because every regular bin updates `range`, `low`, and `*state` sequentially before the next context index can even be selected in syntax-element trees, CABAC resists SIMD vectorization; FFmpeg instead relies on hand-scheduled `x86` (`libavcodec/x86/cabac.h`) and `aarch64` (`libavcodec/aarch64/cabac.h:30-100`) `volatile` inline assembly operating directly on `CABACContext` field offsets with unchecked 16-bit `bytestream` refills guarded only by `AV_INPUT_BUFFER_PADDING_SIZE` (`64` zero bytes).
5. **Parallelism & Verification Architecture:** H.264's macroblock-sequential $4\times 4$-edge deblocking order (`libavcodec/h264_loopfilter.c`) couples horizontal and vertical filtering within each $16\times 16$ macroblock, restricting intra-frame parallelism to diagonal macroblock wavefronts or independent slices, whereas HEVC restricts deblocking to an $8\times 8$ sample grid (`libavcodec/hevc/filter.c:501-660`) so all vertical edges in a picture can execute in parallel before all horizontal edges, followed by CTB-local Sample Adaptive Offset (SAO) filtering from preserved boundary line buffers (`copy_CTB_to_hv`, `sao_filter_CTB` at `hevc/filter.c:269-375`). A clean-room verified Rust architecture should separate bit-exact immutable parameter-set arenas, bounds-certified RBSP/CABAC readers, ghost-token-synchronized frame-progress planes, wrapping `i32` / range-typed `i16` scalar reference kernels, and machine-checked SIMD/ISA assembly refinements.

### 2. NALU Framing, Start-Code SWAR/SIMD Scanning, and `0x000003` RBSP Unescaping

`Basis: normative + source`

Under ITU-T H.264 Clause 7.3.1 / Annex B and ITU-T H.265 Clause 7.3.1 / Annex B, raw compressed slices are carried in Network Abstraction Layer Units (NALUs). Two wire framings coexist in containers and transport streams:
- **Annex B Byte-Stream Framing** (MPEG-TS, raw `.264`/`.265`, RTP depacketization): NALUs are delimited by 3-byte (`0x000001`) or 4-byte (`0x00000001`) start-code prefixes.
- **Length-Prefixed Framing** (`AVCC` / `HVCC` in ISO-BMFF MP4/MKV, ISO/IEC 14496-15): Each NALU is preceded by a 1-, 2-, or 4-byte big-endian byte length (`nal_length_size`), without start codes. Note that `libavcodec/h264dec.c:656-661` contains a heuristic fallback that switches `h->is_avc` between `0` and `1` on 4-byte length streams if `AV_RB32(buf) == 1` and `AV_RB32(buf + 5) > (unsigned)buf_size`—a legacy compatibility quirk that a clean-room parser must model explicitly if matching FFmpeg's acceptance of mis-signaled MP4 packets.

Inside every NALU payload (the Encapsulated Byte Sequence Payload, EBSP), encoders forbid accidental 3-byte sequences `0x00 0x00 0x00`, `0x00 0x00 0x01`, `0x00 0x00 0x02`, and `0x00 0x00 0x03` by inserting an **emulation prevention three-byte** (`0x03`) after two zero bytes (`0x00 0x00 0x03 0x0X` for `X in 0..=3`). During decoding, `ff_h2645_extract_rbsp` (`libavcodec/h2645_parse.c:37-150`) converts EBSP into a Raw Byte Sequence Payload (RBSP) via a two-stage pipeline:
1. **SWAR Zero-Pair Prefix Scan (`h2645_parse.c:60-88`):** On 64-bit unaligned-capable hosts (`HAVE_FAST_UNALIGNED && HAVE_FAST_64BIT`), FFmpeg steps `i += 9` bytes at a time using a Mycroft-style zero-byte word test `(~AV_RN64(src + i) & (AV_RN64(src + i) - 0x0100010001000101ULL)) & 0x8000800080008080ULL` targeting even/adjacent zero byte positions. Because random compressed CABAC bytes hit `0x000003` roughly once every $2^{22}$ bytes (`h2645_parse.c:104`), **most NALUs contain zero escape bytes**.
2. **Zero-Copy Fast Path vs. Padded Scratch Copy (`h2645_parse.c:90-148`):** If no `0x00 0x00 0x03` or embedded `0x00 0x00 0x01` appears (`i >= length - 1`) and `small_padding` is non-zero (meaning the caller's input `AVPacket` already carries `AV_INPUT_BUFFER_PADDING_SIZE = 64` zeroed tail bytes), `ff_h2645_extract_rbsp` aliases `nal->data = src` **zero-copy** (`lines 90-95`). Otherwise, it copies `src[0..i]` into `rbsp->rbsp_buffer`, strips `0x03` bytes in a scalar loop (`lines 103-139`), optionally records removed byte offsets in `nal->skipped_bytes_pos` (used by hardware accelerators that require raw EBSP offsets), and zeroes `AV_INPUT_BUFFER_PADDING_SIZE` (`64`) trailing bytes via `memset(dst + di, 0, AV_INPUT_BUFFER_PADDING_SIZE)` (`line 141`).

**Clean-Room Verification Obligation (`Basis: derived`):** Every downstream unchecked bitstream reader (`GetBitContext` when `UNCHECKED_BITSTREAM_READER == 1` and `CABACContext` refill) relies on those `64` zeroed padding bytes for spatial memory safety when reading past `nal->size`. In a verified Rust rewrite, replacing raw `const uint8_t *` + implicit 64-byte tail invariants with a refinement-typed `PaddedRbspSlice<'a>` (whose constructor proves `backing.len() >= payload_len + 64` and `backing[payload_len..payload_len + 64] == [0; 64]`) preserves FFmpeg's zero-copy fast path on unescaped `AVPacket` buffers while allowing 64-bit lookahead bit-readers and branchless CABAC refills to execute with **zero per-bit bounds branches** and **100% machine-checked spatial UB-freedom**.

### 3. Parameter Set Validation (`VPS`/`SPS`/`PPS`) and Dynamic Reconfiguration Hazards

`Basis: normative + source`

H.264 defines two parameter set tiers—Sequence Parameter Sets (`SPS`, `sps_id in 0..31`, `MAX_SPS_COUNT = 32` at `libavcodec/h264_ps.h:37`) and Picture Parameter Sets (`PPS`, `pps_id in 0..255`, `MAX_PPS_COUNT = 256` at `h264_ps.h:38`). HEVC adds a third root tier—Video Parameter Sets (`VPS`, `vps_id in 0..15`, `HEVC_MAX_VPS_COUNT = 16` at `libavcodec/hevc/hevc.h:113`) alongside tighter `SPS` (`HEVC_MAX_SPS_COUNT = 16`, `line 115`) and `PPS` (`HEVC_MAX_PPS_COUNT = 64`, `line 117`) tables.

Inspection of `libavcodec/h264_ps.c:336-470` and `libavcodec/hevc/ps.c:860-1010` highlights three critical validation and lifetime rules:
1. **Exp-Golomb Integer Overflow Guards:** Unsigned and signed Exp-Golomb syntax elements (`ue(v)`, `se(v)`) can decode up to `2^32 - 2` (`get_ue_golomb_long`) or `INT32_MIN` (`get_se_golomb_long`). In `h264_ps.c:406-415`, FFmpeg explicitly rejects `sps->offset_for_non_ref_pic == INT32_MIN || sps->offset_for_top_to_bottom_field == INT32_MIN` because negating or accumulating `INT32_MIN` during Picture Order Count (`POC` Type 1) derivation triggers signed 32-bit overflow UB. Similarly, `h264_ps.c:385-393` constrains `log2_max_frame_num_minus4` to `0..12` (`log2_max_frame_num in 4..16`), `chroma_format_idc` to `0..3` (`line 348`), `bit_depth_luma` and `bit_depth_chroma` to equal values in `8..14` (`lines 359-371`), and `poc_cycle_length < 256` (`lines 419-424`). In HEVC (`hevc/hevc.h:130-160`, `hevc/ps.c:868-872`), FFmpeg enforces `log2_ctb_size in 4..6` ($16\times 16$ to $64\times 64$ CTBs), `HEVC_MAX_WIDTH = HEVC_MAX_HEIGHT = 16888`, `HEVC_MAX_TILE_ROWS = 22`, `HEVC_MAX_TILE_COLUMNS = 20`, and checks `(vps_num_layer_sets - 1LL) * (vps_max_layer_id + 1LL) <= get_bits_left(gb)` in 64-bit arithmetic before skipping bits to prevent DoS loops or negative bit-cursor wraparound.
2. **In-Band Parameter Set Overwrite & `AVRefStruct` Immutability:** An adversarial bitstream can transmit a new `SPS` with the **same `sps_id`** as an `SPS` currently referenced by in-flight worker threads or a `PPS` in `pps_list`. Modern FFmpeg mitigates raw pointer use-after-free by allocating `SPS`, `PPS`, and `HEVCVPS` via reference-counted `AVRefStruct` (`av_refstruct_replace(&h->ps.pps, h->ps.pps_list[sl->pps_id])` at `h264_slice.c:1090`; `av_refstruct_unref(&vps)` at `hevc/ps.c:957`), and storing a strong `const SPS *sps` pointer inside each `PPS` when that `PPS` is parsed.
3. **Mid-Stream Resolution / Bit-Depth Reconfiguration (`h264_slice.c:1084-1123`):** Even with `Arc`-backed immutable `SPS`/`PPS` structs, if slice `k > 0` inside a multi-slice picture references a `pps_id` whose bound `SPS` changes `mb_width`, `mb_height`, `bit_depth_luma`, or `chroma_format_idc` relative to slice `0` (`must_reinit == 1` at `h264_slice.c:1108-1119`), continuing slice decode into an already-allocated `H264Picture` buffer of the old dimensions/pixel-size corrupts memory immediately. FFmpeg refuses mid-frame reinit on non-first slices. In Rust, binding an active `FrameDecodeSession` to a single `Arc<ValidatedSps>` at frame start—and checking `Ptr::eq(&slice_pps.sps, &frame_sps)` (or value equality of geometry/bit-depth invariants) on every subsequent slice header—renders mid-frame geometry/bit-depth mutation unrepresentable in the type state.

### 4. CABAC Binary Arithmetic Coding (M-Coder): Exact State Machine and Inline Assembly

`Basis: normative + source + execution`

Both H.264 (Clause 9.3; Main/High profiles) and HEVC (Clause 9.3; **all** profiles, since HEVC removed CAVLC entirely) use the exact same multiplication-free binary arithmetic coder ("M-coder", Marpe et al. 2003, `doi:10.1109/TCSVT.2003.815173`). Probability states are represented in 1 byte (`uint8_t s in 0..127`), packing a 6-bit probability state index `pStateIdx = s >> 1 in 0..63` (from $\sigma = 0$ near $p_{\text{LPS}} \approx 0.5$ down to $\sigma = 62$ near $p_{\text{LPS}} \approx 0.01875$, plus non-adapting $\sigma = 63$ for `end_of_slice_flag`) and the Most Probable Symbol `valMPS = s & 1`. H.264 uses up to `1,024` context models (`H264SliceContext::cabac_state[1024]`), whereas HEVC substantially reduced context-table RAM to `~154–200` contexts (`HEVCLocalContext`) and simplified coefficient group coding to increase bypass-bin throughput.

In `FFmpeg/FFmpeg`, `libavcodec/cabac.h:32-47` and `libavcodec/cabac.c:32-120` consolidate four lookup subtables into a single cache-resident `1,343`-byte array `ff_h264_cabac_tables`:
- `ff_h264_norm_shift` (offset `0`, `512` bytes): $\lfloor 8 - \log_2(x) \rfloor$ count-leading-zeros shift table for $x \in [1, 511]$ (`0` for $x \ge 256$).
- `ff_h264_lps_range` (offset `512`, `512` bytes): $4 \times 128$ table indexed by `2 * (c->range & 0xC0) + s` (ignoring the `valMPS` bit via duplicated adjacent pairs), quantizing the 9-bit interval `c->range` $\in [256, 510]$ into `qCodIRangeIdx = (range >> 6) & 3` $\in \{0, 1, 2, 3\}$.
- `ff_h264_mlps_state` (offset `1024`, `256` bytes, addressed around midpoint `+128` via signed `s ^ lps_mask`): combined MPS/LPS Markov state transition table, including the `valMPS` flip when `pStateIdx == 0` transitions on an LPS outcome.
- `ff_h264_last_coeff_flag_offset_8x8` (offset `1280`, `63` bytes).

An executable Python range sweep directly over the `1,343` bytes extracted from `libavcodec/cabac.c:32-120` (`Basis: execution`) confirms the exact finite-domain invariants of `get_cabac_inline` (`libavcodec/cabac_functions.h:108-129`):
- Across all `range` $\in [256, 510]$ and `s` $\in [0, 127]$, `RangeLPS` $\in [2, 240]$ (`RangeLPS == 2` occurs exclusively for the non-adapting terminate state `pStateIdx = 63`; adapting states `0..62` satisfy `RangeLPS` $\in [6, 240]$).
- On an **MPS** outcome (`lps_mask == 0`), `range' = range - RangeLPS` satisfies $\min(\text{range}') = 128$ (`256 - 128` at `q=0, pStateIdx=0` or `320 - 176 = 144` at `q=1`). Thus MPS renormalization shifts by **at most 1 bit** (`norm_shift[range']` $\in \{0, 1\}$), restoring `range''` $\in [256, 510]$.
- On an **LPS** outcome (`lps_mask == -1`), `range' = RangeLPS` $\in [2, 240]$, requiring `norm_shift[RangeLPS]` $\in [1, 7]$ left-shifts (`1..6` for regular states `0..62`, `7` for state `63`) so `range'' = RangeLPS << norm_shift` $\in [256, 480]$.
- FFmpeg's `c->low` packs a 16-bit bitstream shift register in its low 16 bits (`CABAC_BITS = 16`, `CABAC_MASK = 0xFFFF`), using a sentinel `1` bit so `!(c->low & 0xFFFF)` detects exact 16-bit exhaustion without maintaining a separate bit counter `bitsLeft` in a general-purpose register! When exhausted, `refill2` reads 2 big-endian bytes `(bytestream[0] << 9) + (bytestream[1] << 1) - 0xFFFF` and advances `bytestream += 2` (`cabac_functions.h:85-104`).

**Why FFmpeg Uses Inline Assembly Here (`Basis: source + derived`):** In `libavcodec/x86/cabac.h` (`301` lines) and `libavcodec/aarch64/cabac.h:30-100`, `get_cabac_inline` is written as `__asm__ volatile` using `csel`/`cinv` (AArch64) or `cmov` (x86) to avoid branch mispredictions on the unpredictable (~10–50% LPS) arithmetic split, keeping `low`, `range`, and `&ff_h264_cabac_tables` pinned in registers across inlined calls inside `h264_cabac.c` / `hevc/cabac.c`. Crucially, in `aarch64/cabac.h:62-66`, `ldrh %w[tmp], [%[r_c]]` executes **unconditionally before** comparing `r_c < r_a` (`bytestream < bytestream_end`), meaning even with `CONFIG_SAFE_BITSTREAM_READER`, the assembly **reads 2 bytes at `bytestream_end`** before clamping the pointer increment! In a verified Rust decoder, we can match this branchless machine code *purely in safe Rust* without inline assembly by:
1. Slicing `buf: &[u8]` up front with `buf.len() >= 2` and clamping a safe cursor index `pos = (pos + 2).min(buf.len() - 2)` before reading `u16::from_be_bytes([buf[pos], buf[pos + 1]])` (or pre-slicing the validated 64-byte zero-padded RBSP), and
2. Expressing the MPS/LPS split via explicit bitmasks (just as `cabac_functions.h:114-121` already does in C, or `core::hint::select_unpredictable`) while proving in Lean over the finite `512`-entry `lps_range` table that all shifts lie in `0..=7` and all table indices `[2*(range & 0xC0) + s]` lie strictly within `0..512`.

### 5. DPB Reference Lifecycle: H.264 Imperative MMCO vs. HEVC Declarative RPS and `ProgressFrame` Concurrency

`Basis: normative + source`

Reference-picture management is historically the single highest-density source of use-after-free, null-dereference, and multi-threaded data-race vulnerabilities in C video decoders:

1. **H.264 Sliding Window and MMCO (`libavcodec/h264_refs.c:490-805`, ITU-T H.264 Clause 8.2.5):**
   - H.264 maintains `H264Picture` pools of size `H264_MAX_PICTURE_COUNT = 36` (`h264dec.h:47`), partitioned dynamically into `short_ref[32]` (`short_ref_count`) and `long_ref[16]` (`long_ref_count`).
   - Reference marking occurs **after** a picture is decoded (`ff_h264_execute_ref_pic_marking`), driven either by implicit FIFO sliding-window eviction when `short_ref_count + long_ref_count == max(num_ref_frames, 1)` or by explicit `MMCO` opcodes (`MMCO_SHORT2UNUSED = 1`, `MMCO_LONG2UNUSED = 2`, `MMCO_SHORT2LONG = 3`, `MMCO_SET_MAX_LONG = 4`, `MMCO_RESET = 5`, `MMCO_LONG = 6`).
   - Look at the defensive repair paths FFmpeg was forced to accrete in `h264_refs.c:686-793`: malformed bitstreams attempt to assign the current picture to both `short_ref` and `long_ref` simultaneously (`lines 686-689`), assign one picture to two `long_ref` indices (`lines 692-700`), switch field parity between short-term and long-term in complementary field pairs (`lines 746-752`), or overflow `sps->ref_frame_count` (`lines 769-793`). Worse, `MMCO_RESET` (`opcode 5`, `lines 720-731`) wipes all references and resets `frame_num = 0` **at the end of decoding**, forcing `H264Picture::mmco_reset` flags to prevent display reordering from mixing pre-reset and post-reset POC spaces.
2. **HEVC Declarative Reference Picture Sets (`libavcodec/hevc/refs.c:220-430`, ITU-T H.265 Clause 8.3.2):**
   - HEVC eliminated MMCO and post-decode sliding windows completely. Every non-IDR slice header explicitly signals (or selects from the SPS table of up to `HEVC_MAX_SHORT_TERM_REF_PIC_SETS = 64` templates) the complete set of POCs that must remain in the DPB (`HEVC_MAX_DPB_SIZE = 16`, `hevc.h:120`), partitioned into five disjoint subsets: `ST_CURR_BEF`, `ST_CURR_AFT`, `ST_FOLL`, `LT_CURR`, and `LT_FOLL`.
   - Before decoding a single CTB of the current frame, `ff_hevc_frame_rps` sweeps the 16-slot DPB, marks any frame absent from the five subsets as unused for reference, synthesizes missing reference frames (`generate_missing_ref` allocating a neutral mid-gray frame if packet loss occurred so `RefPicList` pointers are never `NULL`!), and builds `RefPicList[0..1]` (`hevc/refs.c:357-428`).
3. **Cross-Frame Thread Synchronization (`ProgressFrame`):**
   - Both `h264dec` and `hevcdec` achieve high multi-core throughput via **frame-level threading** (`FF_THREAD_FRAME`), where thread $T_k$ decodes frame $k$ concurrently while thread $T_{k-1}$ is still reconstructing reference frame $k-1$.
   - Safety depends on vertical motion-vector progress barriers (`ff_progress_frame_report` and `ff_progress_frame_await`, `libavcodec/h264_mb.c:97`, `libavcodec/hevc/mvs.c:255,269`, `hevc/hevcdec.c:2069`). Before interpolating from reference picture `ref` at vertical coordinate `src_y` with filter tap overhang `halo` (3 rows below block bottom for H.264 6-tap; 4 rows + CTB deblock/SAO lag for HEVC 8-tap) or reading collocated temporal MVs (`TMVP`), the consumer thread awaits `ref->tf` reaching `required_row`.
   - **Clean-Room Rust Synchronization Contract (`Basis: derived`):** In C, forgetting a single `ff_progress_frame_await` call—or computing `required_row` without accounting for chroma subsampling shifts, interlaced field stride doubling, or HEVC SAO bottom-row delay—is an immediate silent C data race (and UB in Rust if `&[u8]` aliases an active `&mut [u8]` on the producer thread!). In a verified Rust decoder, a reference frame's pixel plane and MV grid must NOT expose `&[u8]` over the whole frame while under construction. Instead, wrap in-flight reference buffers in a row-monotone `PublishedRowsPlane<T>` backed by `UnsafeCell` + `AtomicU32` row watermarks, where:
     - Producer worker $T_{k-1}$ holds a linear `RowWriter<'frame>` advancing `published_y` monotonically with `Ordering::Release` **only after** its mutable borrow of rows `[0..new_y)` is dropped/consumed; and
     - Consumer worker $T_k$ calls `plane.await_rows(needed_y) -> &[T]` which executes an `Ordering::Acquire` spin/condvar wait until `published_y >= needed_y` and returns an immutable slice bounded **strictly** to `&backing[0 .. needed_y * stride]`. Any bug in computing `needed_y` from a motion vector then fails a deterministic slice bounds check (or fails verification in Lean) rather than causing a concurrent read/write UB race!

### 6. Spatial Intra Prediction, Fractional-Pel FIR Motion Compensation, and Edge Emulation

`Basis: normative + source + execution`

#### 6.1 Intra Prediction Modes and Boundary Substitution
- **H.264 (`libavcodec/h264pred_template.c`, `1,330` lines; Clause 8.3.1–8.3.4):** Supports nine $4\times 4$ luma modes (Vertical, Horizontal, DC, Diagonal Down-Left, Diagonal Down-Right, Vertical-Right, Horizontal-Down, Vertical-Left, Horizontal-Up), nine $8\times 8$ High-profile luma modes (which apply a 3-tap `[1, 2, 1] >> 2` low-pass filter to reference samples *before* directional projection), four $16\times 16$ luma modes (Vertical, Horizontal, DC, Plane), and four chroma modes. When `constrained_intra_pred_flag == 1`, neighboring inter-coded macroblocks are treated as unavailable to prevent error drift.
- **HEVC (`libavcodec/hevc/pred_template.c`, `591` lines; Clause 8.4.4.2):** Replaces size-fragmented mode tables with a **uniform 35-mode predictor** across all square Transform Units ($4\times 4$, $8\times 8$, $16\times 16$, $32\times 32$): Mode 0 (Planar bilinear interpolation), Mode 1 (DC average), and Modes 2–34 (33 Angular directions with $1/32$-pel displacement precision, Mode 10 pure horizontal, Mode 26 pure vertical). Reference array `top[-1..2*N]` and `left[-1..2*N]` (`129` samples max for $N=32$) fills unavailable segments deterministically by scanning from the bottom-left (`left[2*N-1]`) clockwise to top-right (`top[2*N-1]`) and propagating the first available sample, optionally applying `[1, 2, 1] >> 2` or strong bilinear reference smoothing (`intra_pred` at `hevc/pred_template.c:72-415`).

#### 6.2 Fractional-Pel FIR Motion Compensation and Rounding Asymmetry
A decisive numerical and SIMD distinction separates H.264 and HEVC motion compensation:

| Property | ITU-T H.264 (`h264qpel_template.c`) | ITU-T H.265 / HEVC (`hevc/dsp_template.c`) |
|---|---|---|
| Luma Sub-Pel Precision | $1/4$-pel via 6-tap half-pel + 2-tap bilinear quarter-pel | $1/4$-pel via direct 8-tap polyphase FIR for 1/4, 2/4, 3/4 phases |
| Luma FIR Coefficients | Half-pel: `[1, -5, 20, 20, -5, 1]` (sum `32`) | $1/4$: `[-1, 4, -10, 58, 17, -5, 1, 0]`; $2/4$: `[-1, 4, -11, 40, 40, -11, 4, -1]`; $3/4$: `[0, 1, -5, 17, 58, -10, 4, -1]` (sum `64`) |
| Chroma Sub-Pel Precision | $1/8$-pel (4:2:0) 2D bilinear `(8-dx)*(8-dy)*A + ...` | $1/8$-pel (4:2:0) direct 4-tap polyphase FIR (`ff_hevc_epel_filters`) |
| Intermediate Rounding & Clipping | **Two-stage non-associative:** half-pel clips `((sum + 16) >> 5)` to `[0, (1<<bd)-1]` *before* `(h + p + 1) >> 1`, **except** 2D center half-pel `'j'` which keeps unclipped 1D sums! | **Single-stage high-precision:** 1D pass shifts `>> (bd - 8)` with **no rounding and no clipping**; rounding/clipping happens once at final uni-pred or bi-pred output (`shift = 15 - bd` in bi-pred)! |
| 1D / 2D Mid-Buffer Range (Executed Probe) | 8-bit 1D `[-2550, 10710]`, 2D `'j'` `[-213688, 475832]`; 10-bit 1D `[-10230, 42966]` (**overflows signed `i16`!**) | 8-bit `[-6120, 22440]`; 10-bit `[-6138, 22506]`; 12-bit `[-6143, 22522]` (**fits signed `i16` `[-32768, 32767]` at all bit depths!**) |

Our executed arithmetic probe (`Basis: execution`) explains why HEVC's SIMD motion-compensation kernels (`x86/hevc_mc.asm`, `aarch64/hevcdsp_*`) are dramatically cleaner and more regular than H.264's (`x86/h264_qpel_8bit.asm`, `x86/h264_qpel_10bit.asm`):
- In HEVC, regardless of whether input pixels are 8-bit, 10-bit, or 12-bit, the 1D horizontal pass produces values strictly inside `[-6143, 22522]`, so a fixed `int16_t tmp[MAX_PB_SIZE * (MAX_PB_SIZE + 7)]` scratch buffer (`MAX_PB_SIZE = 64`) never overflows `i16`, and bi-prediction (`put_hevc_pel_bi_pixels` at `hevc/dsp_template.c:368-392`) averages two unrounded 14-bit-scale predictions `(pred0 + pred1 + offset) >> (15 - BIT_DEPTH)` with a single final `av_clip_pixel`.
- In H.264, 10-bit 1D intermediates reach `+42,966`, exceeding `INT16_MAX = 32,767`, forcing `h264_qpel_10bit.asm` to widen intermediate lanes to 32 bits (`int32_t`) or bias by `-pad` (`h264qpel_template.c:90,155`).

#### 6.3 Out-of-Frame Motion Vector Clamping (`emulated_edge_mc`)
Motion vectors legally point outside picture boundaries (up to thousands of pixels out-of-frame in adversarial bitstreams). Rather than allocating giant frame halos for arbitrary MVs, FFmpeg's `emulated_edge_mc` (`libavcodec/videodsp_template.c:24-95`) copies and edge-replicates a clamped tile of size `(block_w + filter_overhang) x (block_h + filter_overhang)` into a thread-local stack/context buffer `edge_emu_buffer` whenever `src_x < 0 || src_y < 0 || src_x + bw > w || src_y + bh > h`. Note `videodsp_template.c:38-54`: when `src_y >= h` or `src_x >= w`, FFmpeg rewinds the raw `src` pointer using `(1 + src_x - w) * sizeof(pixel)`—where `sizeof(pixel)` has unsigned `size_t` type, prompting the explicit comment at `line 48`: `// The subtracted expression has an unsigned type and must thus not be negative`! In safe Rust, `emulated_edge_mc` should compute clamped integer row/column index intervals `[clamped_x0..clamped_x1]` over `&[Pixel]` **without** forming temporary out-of-bounds raw pointers (`src + src_y * stride + src_x` before clamping is immediate pointer-offset UB in both C and Rust!).

### 7. Exact Integer Inverse Transforms (IDCT / DST-VII) and Signed-Overflow Hazards

`Basis: normative + source + execution`

Both codecs eliminate IEEE-754 floating-point IDCT drift (which plagued MPEG-2 / MPEG-4 Part 2 decoders) by specifying **bit-exact integer inverse transforms**:
1. **H.264 Multiplier-Free Transforms (`libavcodec/h264idct_template.c:35-345`, Clause 8.5.12):**
   - Uses $4\times 4$ integer butterflies involving only additions and `>> 1` shifts (`z0 = b0 + b2`, `z1 = b0 - b2`, `z2 = (b1 >> 1) - b3`, `z3 = b1 + (b3 >> 1)`), optional $4\times 4$ luma DC / $2\times 2$ (or $2\times 4$) chroma DC Hadamard transforms, and High-profile $8\times 8$ integer transforms.
   - **Critical UB Finding (`h264idct_template.c:43-58`):** Notice that FFmpeg explicitly casts operands to `unsigned` / `SUINT` (`uint32_t` for 8-bit, `uint64_t`/unsigned for high bit-depth): `const SUINT z0 = block[i + 4*0] + (unsigned)block[i + 4*2];`. Our executed probe (`Basis: execution`) shows why: although conforming encoder residuals keep intermediates within 16 bits for 8-bit video, a syntactically legal bitstream with extreme `qp`, custom scaling matrices, or `qpprime_y_zero_transform_bypass_flag` (`transform_bypass`) supplies arbitrary `int16_t` (`[-32768, 32767]`) or `int32_t` dequantized coefficients, driving 1D $4\times 4$ butterfly peaks to `114,688` and 2D pre-shift peaks to `401,440` (and exceeding `INT32_MAX` on 10–14-bit streams!). In Rust, all H.264/HEVC inverse transform butterflies on untrusted bitstreams MUST use `wrapping_add` / `wrapping_sub` / `wrapping_mul` (or widened `i64` intermediates) prior to final pixel saturation `clamp(0, (1 << bit_depth) - 1)`—never standard checked arithmetic (`+`/`-` in debug/checked profiles) or unchecked signed intrinsics!
2. **HEVC Core Integer DCT-II and Intra $4\times 4$ DST-VII (`libavcodec/hevc/dsp_template.c:85-298`, Clause 8.6.4):**
   - HEVC specifies 6-bit-scaled integer approximations of $4\times 4$, $8\times 8$, $16\times 16$, and $32\times 32$ DCT-II matrices (where smaller matrices are exact even-row subsets of larger ones, enabling shared butterfly sub-blocks `TR_4`, `TR_8`, `TR_16`, `TR_32` in `hevc/dsp_template.c:245-284`), plus an asymmetric $4\times 4$ **Discrete Sine Transform (DST-VII)** exclusively for $4\times 4$ intra luma residuals (where prediction errors grow away from the top/left boundary).
   - Between the 1D column pass (`shift = 7`, `add = 64` at `lines 266-267`) and the 1D row pass (`shift = 20 - BIT_DEPTH` at `line 278`), HEVC normatively **clamps every intermediate coefficient to `[-32768, 32767]`** (`av_clip_int16` in `SCALE` macro, `MAX_TX_DYNAMIC_RANGE = 15` for 8/10/12-bit Main/Main 10). Omitting this inter-pass `i16` saturation violates normative bitstream conformance on adversarial inputs and overflows `pmaddwd` SIMD lanes in the second pass.

### 8. In-Loop Deblocking and Sample Adaptive Offset (SAO) Parallelism Boundaries

`Basis: normative + source`

1. **H.264 Deblocking (`libavcodec/h264_loopfilter.c`, `847` lines; Clause 8.7):**
   - Operates on **every $4\times 4$ block edge** in raster macroblock order: for each macroblock $k$, all four vertical 16-sample edges (`x = 0, 4, 8, 12`) are filtered left-to-right, and *immediately afterward* all four horizontal 16-sample edges (`y = 0, 4, 8, 12`) of macroblock $k$ are filtered top-to-bottom using the *already vertically filtered* samples!
   - Boundary Strength `bS` $\in \{0, 1, 2, 3, 4\}$ (`bS = 4` strong intra macroblock boundary modifying up to 3 samples `p2, p1, p0, q0, q1, q2` on each side; `bS in 1..3` normal filter modifying `p1, p0, q0, q1` bounded by `tc0_table[index_a][bS]` at `h264_loopfilter.c:69-160`).
   - **Concurrency Consequence:** Because macroblock $(x, y)$'s left vertical edge modifies pixels in macroblock $(x-1, y)$ *after* $(x-1, y)$'s horizontal edges have run, and $(x, y)$'s top horizontal edge reads pixels modified by $(x, y-1)$'s vertical and horizontal passes, H.264 deblocking **cannot** run all vertical edges across a frame in parallel followed by all horizontal edges; intra-frame deblocking requires a 2D wavefront (`mb_x + 2 * mb_y = const`).
2. **HEVC $8\times 8$-Grid Deblocking + SAO (`libavcodec/hevc/filter.c`, `1,071` lines; Clauses 8.7.2–8.7.3):**
   - HEVC restricts `bS` $\in \{0, 1, 2\}$ to edges lying on an **$8\times 8$ sample grid** (`deblocking_filter_CTB` at `hevc/filter.c:501-660`). Because a 4-sample modification span (`p2..p0, q0..q2` in strong mode, modifying at most 3 luma samples per side) on $8\times 8$-spaced vertical edges never overlaps neighboring vertical edges (`3 + 3 = 6 <= 8`), **every vertical edge in the entire picture is data-independent of every other vertical edge**, and subsequently every horizontal edge is data-independent of every other horizontal edge!
   - Immediately following deblocking (lagged by 1 CTB row and 1 CTB column so all four neighbors of a CTB have finished deblocking, `hevc/filter.c:1040-1042`), `sao_filter_CTB` (`lines 269-375`) applies either **Band Offset (`SAO_BAND`)** (adding learned signed offsets to 4 contiguous intensity bands out of 32 `[sample >> (bit_depth - 5)]`) or **Edge Offset (`SAO_EDGE`)** (classifying each pixel against its two 1D neighbors along $0^\circ$, $90^\circ$, $135^\circ$, or $45^\circ$ via `sign(c - a) + sign(c - b)`).
   - **Buffer & Bypass Invariant (`hevc/filter.c:346-362`):** Because `SAO_EDGE` classifies original post-deblock samples (not cascade-updated SAO outputs!), in-place CTB filtering must preserve untouched right/bottom CTB border strips via `copy_CTB_to_hv` (`line 346`), and when `pps_transquant_bypass_enabled_flag` or `pcm_loop_filter_disabled_flag` is set, must save and restore lossless Coding Units via `restore_tqb_pixels` (`lines 348-357`).

### 9. Error Resilience vs. Verification Priority Stack and Clean-Room Rust Architecture

`Basis: source + derived`

Upstream `FFmpeg/FFmpeg` defaults to best-effort concealment on corrupt H.264 bitstreams (`libavcodec/error_resilience.c`, `1,368` lines, `ff_er_frame_end` at `line 910` and `guess_mv` at `line 410`), interpolating lost macroblocks from spatial neighbors or motion-compensated previous frames unless `AV_EF_EXPLODE` is set in `avctx->err_recognition`. Historically, mixing partial error recovery with mutable shared `H264Picture` pointers, mid-frame SPS changes, and unchecked inline assembly caused severe memory-corruption vulnerabilities when partially decoded frames remained in the DPB as references for subsequent slices.

Mapping these primary-source findings onto the four-level verification priority stack yields a clean-room Rust architecture that eliminates legacy C coupling without sacrificing SIMD throughput:

1. **Priority 1 — UB-Freedom (Tiny TCB):**
   - **Zero `unsafe` in NALU, `VPS`/`SPS`/`PPS`, `SEI`, DPB/RPS/MMCO, slice headers, MV derivation, and `CABAC`:** Using `PaddedRbspSlice` (`64`-byte zero tail proven at construction) and branchless safe Rust `get_cabac` eliminates `x86/cabac.h` and `aarch64/cabac.h` inline assembly entirely while keeping the arithmetic state machine register-resident.
   - **Sound Frame-Thread Row Barriers:** Replace raw `H264Picture*` / `HEVCFrame*` shared mutable plane pointers with `PublishedRowsPlane<Pixel>` enforcing Acquire/Release prefix slice visibility (`&plane[0 .. watermark * stride]`), and replace raw C edge-pointer rewinding in `emulated_edge_mc` with pure index-clamped copy kernels.
2. **Priority 2 — Panic-Freedom on Untrusted Bitstreams:**
   - Every slice index into `sps_list[32]`, `pps_list[256]`, `vps_list[16]`, `cabac_state[1024]`, `alpha_table[156]`, `ff_h264_cabac_tables[1343]`, and `RefPicList[16]` is statically discharged via bounded index wrappers (`Fin<N>` / `InRange<u16, 0, N>`) validated once when parsing syntax elements (`get_ue_golomb` -> `Result<Fin<32>, DecodeError>`), eliminating panicking slice checks from inner macroblock/CTB loops.
   - All IDCT, Hadamard, DST-VII, POC (`poc_type 0/1/2`), and MV scaling arithmetic uses explicit `i32::wrapping_*` (matching FFmpeg's `SUINT` semantics) or proven `i64` bounds—never debug-panicking `+`/`-`/`*` or `INT32_MIN` negation.
3. **Priority 3 — Behavioral & SIMD-vs-Scalar Equivalence:**
   - Author clean, monomorphized (`const BIT_DEPTH: u8`) pure-Rust scalar reference kernels for 6-tap/8-tap QPEL, 4-tap EPEL, H.264/HEVC intra modes, IDCT/DST-VII, deblocking, and SAO.
   - Verify SIMD kernels (`x86_64` AVX2/AVX-512, `aarch64` NEON, `riscv64` RVV—covering the `56,124` lines of H.264/HEVC assembly in FFmpeg) against those exact fixed-width scalar functions by bounded bit-vector / symbolic execution equivalence over arbitrary `Pixel` blocks (`4x4`..`64x64`), catching rounding-order bugs (such as H.264 `'j'` unclipped vs. half-pel clipped intermediates and HEVC inter-pass `av_clip_int16` saturation) mechanically. Differential FATE testing (`h264-conformance-*`, `hevc-conformance-*`) then validates bit-exact frame MD5 parity against `FFmpeg/FFmpeg@7ddf7bc8a482cf28b4fab2e63b7093ba35cb6a80`, including `AV_EF_EXPLODE` vs. concealment modes (`generate_missing_ref` neutral-frame substitution).
4. **Priority 4 — Full Normative Specification Conformance:**
   - Mechanize the pure declarative RPS transition relation (ITU-T H.265 Clause 8.3.2) and H.264 Clause 8.2.5 MMCO state machine as total pure functions `mark_dpb(dpb: DpbState, hdr: &SliceHeader) -> Result<DpbState, SpecViolation>`, isolating FFmpeg's non-normative error-concealment heuristics (`h264_refs.c:769-793`) behind an explicit `CompliancePolicy::{StrictItu, FfmpegConceal}` policy switch.

## Boundaries

- **Software H.264/HEVC Encoding Not Examined in FFmpeg Source:** Because `FFmpeg/FFmpeg` delegates software H.264/HEVC rate-distortion encoding (`RDO`, motion estimation search, lookahead rate control) to external repositories (`videolan/x264`, `multicoreware/x265_git`, `cisco/openh264`), internal RDO algorithms of `x264`/`x265` were **not examined** here; only FFmpeg's own `cbs_h2645`, hardware encode frontends, and FFI wrapper boundaries were inspected.
- **Interlaced MBAFF / PAFF Complexity in H.264:** H.264 Macroblock-Adaptive Frame-Field (`MBAFF`, `mb_adaptive_frame_field_flag`) and Picture-Adaptive Frame-Field (`PAFF`) double neighbor-derivation, CABAC context selection, MV scaling, and deblocking boundary-strength states across `h264_slice.c`, `h264_mb.c`, and `h264_loopfilter.c`. While DPB field-pair invariants in `h264_refs.c` were inspected, full MBAFF line-stride lens verification was **not examined** in detail; note that HEVC **known not to apply** macroblock-level MBAFF (interlaced content in HEVC is coded purely as field pictures or frame pictures signaled via SEI `pic_struct`).
- **Scalable and 3D Extensions (`SVC`, `MVC`, `SHVC`, `3D-HEVC`):** Upstream `FFmpeg/FFmpeg` rejects or ignores most multi-layer extensions beyond 2-layer HEVC alpha auxiliary streams (`hevc/ps.c:877-938`: `// we support at most 2 layers, so ignore the others`); multi-view/3D normative extensions are **unsupported** by FFmpeg's native decoders and **not examined** beyond parameter-set rejection bounds.
- **Live Wall-Clock Throughput of Inline-Asm-Free Rust CABAC:** Although arithmetic range bounds confirm that `get_cabac_inline` requires no SIMD instructions and can be expressed branchlessly in safe Rust over a 64-byte-padded slice, end-to-end throughput of a `rustc`-compiled CABAC loop vs. `FFmpeg`'s `x86/cabac.h` and `aarch64/cabac.h` register-pinned inline assembly remains **unknown** pending benchmark execution on matching LLVM backends (see companion package `av1-vp9-dav1d-rav1d-clean-room-rust-rewrite-and-performance-parity-anatomy` for measured LLVM register-spill effects in entropy loops).
