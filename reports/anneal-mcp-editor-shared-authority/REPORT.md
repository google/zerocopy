# Shared Document Authority, Multi-Client Reconciliation, and MCP Task Lifecycles for Interactive Lean Verification

## Summary

Interactive proof environments that combine an editor language-server client and an asynchronous Model Context Protocol (MCP) agent face two distinct state-synchronization problems: maintaining a single authoritative source document across unsaved editor buffers and disk mirrors, and managing long-running verification tasks across transport disconnects, retries, and cancellations. Across six bounded component experiments against Lean `v4.30.0-rc2` (`3dc1a088b6d2d8eafe25a7cd7ec7b58d731bd7cc`), the Language Server Protocol (LSP) `3.18` specification (`de9a671ae6ba374cc748a29c1c620cbc536302ff`), and the Model Context Protocol `2026-07-28` specification (`5f5440bb26a62e2cf3440b92da5a667efa03b267`):

1. **Open-document LSP authority vs. disk mirrors (`support/editor-mcp-shadow-authority-v4-30-0-rc2/`):** A direct `lean --server` process elaborates unsaved `textDocument/didOpen` and `textDocument/didChange` payloads while the underlying disk file (`Shadow.lean`) retains stale invalid bytes (`theorem demo : False := by exact ?_`). Closing and reopening the URI from disk reverts the goal to the stale disk state (`⊢ False`), whereas replaying the retained unsaved buffer after a forced server watchdog restart restores the valid goal (`no goals`) under a new server incarnation. Bare direct Lean servers also elaborate open `file:` URIs with no physical file on disk (`Missing.lean`) and `untitled:` URIs (`untitled:AnnealProof.lean`) for self-contained core proofs without Lake project imports.
2. **Per-origin diagnostic multiplexing and missed-notification reconciliation (`support/editor-mcp-shadow-authority-v4-30-0-rc2/`):** Two simultaneously open documents (`Shadow.lean` and `Other.lean`) maintain independent diagnostic streams and version counters. A deterministic replay model over the captured LSP notification stream demonstrates that dropping a version-3 empty diagnostic clearing notification leaves stale version-2 errors cached in a push-only client, whereas flattening notifications into a single "last diagnostic update" erases `Other.lean`'s active error when `Shadow.lean` clears. Because MCP `2026-07-28` `subscriptions/listen` streams do not retain or replay missed notifications across stdio reconnects, subscriptions can serve only as responsiveness hints backed by an explicit current-state read (`resources/read` or a typed state tool).
3. **Two-client shared authority and compare-and-swap guards (`support/multiclient-editor-contract/`, `support/lean-mcp-adapter-availability-probe/`):** In a local broker multiplexing logical `editor` and `agent` roles over one unsaved Rust-host projection (`Host.rs` $\rightarrow$ `Hidden.lean`), alternating version-checked edits transition the live Lean goal through `no goals -> ⊢ False -> no goals -> ⊢ False` while the disk file stays unchanged. Stale edits with mismatched source hashes or versions are rejected before emitting `didChange`, identical lost-response retries (`(client, request_id, payload_hash)`) return the cached mutation result idempotently without advancing the document version, reused request IDs with altered payloads fail with `id-reuse-conflict`, and closing/reopening the host increments `document_epoch` so pre-close preconditions cannot apply to a reopened buffer with identical text and version `1`. In a separate two-process stdio bridge (`support/lean-mcp-adapter-availability-probe/`), two independent clients using colliding JSON-RPC request ID `42` isolate per-session `notifications/cancelled` (`-32800` on Client A while Client B's request `42` completes) and enforce SHA-256 compare-and-swap preconditions across shared proof edits (`7f26c6ed...` $\rightarrow$ `b40ac46b...`).
4. **MCP `2026-07-28` task wire controls and live Lean goal composition (`support/mcp-2026-task-wire-controls/`, `support/mcp-shaped-async-task-lifecycle/`, `support/mcp-2026-lean-goal-wire-composition/`):** Standard-library stdio test bridges modeling the MCP `2026-07-28` core specification and the draft Tasks extension (`io.modelcontextprotocol/tasks`) verify per-request protocol version metadata (`-32022` on unsupported modern versions vs. legacy `initialize` fallback to `2025-11-25`), synchronous `resultType: "complete"` fallback when Tasks capability opt-in is omitted, immediate `tasks/get` visibility after `tools/call` returns `resultType: "task"`, distinction between tool-domain errors (`status: "completed"` with `result.isError: true`) and JSON-RPC failures (`status: "failed"`), and rejection of ordinary `notifications/cancelled` for task handles in favor of cooperative `tasks/cancel`. Composing this wire envelope with a real Lean `v4.30.0-rc2` server shows that pre-start `tasks/cancel` prevents launching an unneeded Lean query, while in-flight `tasks/cancel` during a slow `1.5 s` elaboration forwards `$/cancelRequest` to Lean (which returns JSON-RPC `-32800`) and suppresses task result publication.

## Applicability

All empirical runs used the pinned arm64 macOS Lean and Lake `v4.30.0-rc2` release from `leanprover/lean4` revision `3dc1a088b6d2d8eafe25a7cd7ec7b58d731bd7cc` (`lean` SHA-256 `b48bc5ab229bd8b320a224b87e20fc428dba6fa8a1c054bd4fa6def846e19997`, `lake` SHA-256 `9a89b2af1bddb7e6d5a8dbb2c715288bcb4f24b9129132640cee950734366bcb`) with `LEAN_NUM_THREADS=1`. Protocol comparisons are anchored to the Language Server Protocol `3.18` specification at `microsoft/language-server-protocol` revision `de9a671ae6ba374cc748a29c1c620cbc536302ff` and the Model Context Protocol `2026-07-28` specification at `modelcontextprotocol/modelcontextprotocol` revision `5f5440bb26a62e2cf3440b92da5a667efa03b267` (together with the official MCP Tasks extension draft as of `2026-09-29`).

A scoped availability check against the Anneal workspace in `google/zerocopy` at revision `bd0956be95c5f798f0c0484921b9b9d1fc6e9988` confirmed that `anneal/src` contains CLI, scanner, resolver, and project-setup modules (`Cargo.toml`, `scanner.rs`, `resolve.rs`, `setup.rs`, `parse.rs`) with no local LSP proxy or MCP server implementation, and that the local `PATH`, Python `3.14` environment, and global npm installation contained no pre-installed third-party Lean MCP adapter or `mcp`/`fastmcp` SDK packages. Consequently, the executed Lean observations are genuine `lean --server` and `lean --json` measurements, whereas the multi-client brokers and MCP stdio bridges are self-contained Python standard-library protocol models.

## Findings

### 1. Open-Document Authority, Shadow Mirrors, and Bare URI Schemes (`support/editor-mcp-shadow-authority-v4-30-0-rc2/`)

In three identical executions of [`support/editor-mcp-shadow-authority-v4-30-0-rc2/lsp_probe.py`](support/editor-mcp-shadow-authority-v4-30-0-rc2/lsp_probe.py), `Shadow.lean` on disk contained `theorem demo : False := by exact ?_`, which fails batch `lean --json` with exit code `1`. Opening that same `file://` URI in `lean --server` with unsaved memory text `theorem demo : True := by trivial` at document version `1` and waiting for diagnostics returned `no goals` while the on-disk SHA-256 remained the failing source hash:

| Sequence Step | Operation | LSP Document Version | On-Disk Content | Observed Lean Goal & Diagnostics |
| --- | --- | ---: | --- | --- |
| 1 | `didOpen` with unsaved valid proof | `1` | Invalid (`⊢ False`) | `no goals`; zero error diagnostics |
| 2 | `didChange` to invalid proof in memory | `2` | Invalid (`⊢ False`) | `⊢ False`; placeholder/unsolved-goal errors |
| 3 | `didChange` restoring valid proof in memory | `3` | Invalid (`⊢ False`) | `no goals`; empty diagnostic array clears version 2 |
| 4 | `didClose`, then `didOpen` reading disk bytes | `4` | Invalid (`⊢ False`) | `⊢ False`; reverts to stale on-disk bytes |
| 5 | `didClose`, then `didOpen` replaying retained buffer | `5` | Invalid (`⊢ False`) | `no goals` |
| 6 | Force-kill watchdog; new server `didOpen` replaying buffer | `1` (incarnation `2`) | Invalid (`⊢ False`) | `no goals`; version `1` in new server incarnation |
| 7 | Fresh server `didOpen` on nonexistent `file:` URI (`Missing.lean`) | `1` | Absent on disk | `no goals` |
| 8 | Fresh server `didOpen` on `untitled:AnnealProof.lean` | `1` | No disk backing | `no goals` |

**Basis: execution** in [`support/editor-mcp-shadow-authority-v4-30-0-rc2/transcript-run1.json`](support/editor-mcp-shadow-authority-v4-30-0-rc2/transcript-run1.json), [`support/editor-mcp-shadow-authority-v4-30-0-rc2/transcript-run2.json`](support/editor-mcp-shadow-authority-v4-30-0-rc2/transcript-run2.json), and [`support/editor-mcp-shadow-authority-v4-30-0-rc2/transcript-run3.json`](support/editor-mcp-shadow-authority-v4-30-0-rc2/transcript-run3.json). Consistent with LSP `3.18` `didOpen`/`didChange`/`didClose` ownership semantics, an open document's authoritative text lives in the synchronized buffer rather than on disk. If an integration materializes hidden shadow `.lean` files on disk for Lake or imports, a stale shadow file must be treated strictly as a derived mirror and never re-read as canonical truth behind an open editor buffer.

### 2. Per-Origin Diagnostic Multiplexing and Notification Loss (`support/editor-mcp-shadow-authority-v4-30-0-rc2/`)

While `Shadow.lean` cycled through versions `1`, `2`, and `3`, a second open document (`Other.lean`, containing `#check nonexistentName`) remained at version `1` with one unknown-identifier error. Lean emitted no clearing notification for `Other.lean` when `Shadow.lean` transitioned to version `3` with an empty diagnostic update; each `textDocument/publishDiagnostics` payload remained scoped to its own `(uri, version)`.

Replaying the captured event stream through [`support/editor-mcp-shadow-authority-v4-30-0-rc2/contract_probe.py`](support/editor-mcp-shadow-authority-v4-30-0-rc2/contract-observations.json) establishes two deterministic failure modes for naive notification caches:
- **Missed clearing notification:** Disconnecting a client at transcript sequence `36` (dropping the version-3 empty diagnostic notification at sequence `43`) leaves `Shadow.lean` version `2` showing two stale errors alongside `Other.lean` version `1`'s one error, whereas an authoritative state read at sequence `47` reports zero errors for `Shadow.lean` version `3` and one error for `Other.lean` version `1`.
- **Unscoped diagnostic replacement:** Flattening diagnostic updates into a single workspace-wide "last diagnostic notification" slot overwrites `Other.lean`'s active error with `Shadow.lean`'s empty version-3 array, falsely reporting zero workspace errors.

Because MCP `2026-07-28` `subscriptions/listen` filters resource-URI notifications without replaying dropped events across stdio disconnects, an integration multiplexing `rustc`, Charon, Aeneas, and Lean diagnostics must key every diagnostic set by `(producer_origin, document_or_obligation_id, generation_id, document_version)` and reconcile state via an explicit current-state read after any reconnect.

### 3. Multi-Client Shared Authority, Idempotent Retries, and Document Epochs (`support/multiclient-editor-contract/`, `support/lean-mcp-adapter-availability-probe/`)

Two complementary probes tested multi-client coordination over a shared proof target:

1. **Logical editor and agent broker over a single Lean server (`support/multiclient-editor-contract/probe.py`):** A Python broker maintained one authoritative unsaved Rust-host source buffer (`Host.rs` using a synthetic `//% ` line projection into `Hidden.lean`) over a single `lean --server` connection, tracking `(source_sha256, projection_sha256, app_version, document_epoch, lean_version, server_incarnation)`:
   - **Shared unsaved authority:** Opening `Hidden.lean` from the unsaved valid `Host.rs` buffer (version `1`) while disk files contained `theorem demo : False := by exact ?_` yielded `no goals` to both logical clients (LSP wire request IDs `80` and `81`). Alternating edits from `editor` (version `2`, invalid $\rightarrow$ `⊢ False`), `agent` (version `3`, valid $\rightarrow$ `no goals`), and `editor` (version `4`, invalid $\rightarrow$ `⊢ False`) updated the single Lean document without re-reading stale disk bytes.
   - **Compare-and-swap, idempotency, and epoch guards:** An `agent` edit against stale version `1` after `editor` advanced to version `2` was rejected with `conflict` before touching Lean. Retrying `editor`'s version-2 mutation with the identical `(client, request_id, payload)` returned the original version-2 success without re-applying the edit; reusing that `request_id` with a different payload returned `id-reuse-conflict`. After closing and reopening `Host.rs` with the same text (resetting `app_version` to `1`), an edit carrying the pre-close `document_epoch` was rejected despite matching both `app_version` and `source_sha256`.
   - **Server restart and host rename:** Killing the Lean watchdog at `app_version = 4` and spawning a replacement server reopened `Hidden.lean` at `lean_version = 1` under `server_incarnation = 2` while preserving `app_version = 4` (`⊢ False`). Saving and renaming `Host.rs` to `Renamed.rs` closed `Hidden.lean` and opened `RenamedHidden.lean` (with no physical `.lean` file on disk), preserving `⊢ False`.
2. **Two independent stdio client processes with colliding JSON-RPC request IDs (`support/lean-mcp-adapter-availability-probe/probe.py`):** Two stdio clients launched separate bridge processes backed by pinned `lean --server` workers against a shared `Proof.lean` file:
   - Both clients simultaneously issued delayed goal queries using JSON-RPC request ID `42`. Client A sent `notifications/cancelled` for its request `42` and received `-32800`, while Client B's request `42` completed normally (`n : Nat ⊢ n + 0 = n` with an `unsolved goals` diagnostic).
   - Client A applied a compare-and-swap edit replacing `skip` (`7f26c6edb74cf1cab89a66ddcc47530d92bdd989863ebe305c6f30c9d29bd0a3`) with `exact Nat.add_zero n` (`b40ac46bc6ade3aca44b3d9d863269d1530ef9079623379c1776fef0d38bacee`). Client B's next query carrying the old SHA-256 received an explicit stale-precondition rejection naming both digests; subsequent queries carrying the new SHA-256 refreshed both Lean workers to document version `2` and returned `no goals`.

## Boundaries

- **No production Anneal LSP/MCP server or third-party Lean MCP adapter:** The `google/zerocopy` checkout at `bd0956be95c5f798f0c0484921b9b9d1fc6e9988` contains no MCP or LSP server in `anneal/src`, and no external Lean MCP adapter or Python/npm MCP SDK was installed in the local environment. All broker and bridge scripts are standard-library protocol models and do not establish SDK conformance or third-party adapter behavior.
- **Bare core Lean vs. Lake project files:** Acceptance of nonexistent `file:` URIs and `untitled:` URIs in `lean --server` was demonstrated only on single-file core Lean proofs with no Lake workspace, `setup-file` invocation, generated Aeneas imports, or plugins.
- **Cooperative cancellation vs. elaboration preemption:** Forwarding `tasks/cancel` to Lean `$/cancelRequest` caused Lean to answer the cancelled request with `-32800` and caused the bridge to suppress the task result, but Lean finished elaborating the underlying `1.5 s` tactic snapshot before servicing a subsequent goal query.
- **Unexercised editor features:** Cross-language `rust-analyzer` + Lean LSP proxy routing, hover/definition/semantic-token projection, cross-file workspace renames, InfoView interactive RPC widgets under projected Rust coordinates, and format-on-save/autosave loop suppression were not executed in these fixtures.
