# Pinned one-shot Aeneas trait, external, shrink, reorder, and error matrix

## Summary

At the selected Charon/Aeneas CLI pins, a small Rust trait and external function produced four split Lean files. Reordering unchanged Rust declarations changed generated bytes and ranges while fresh Lean consumers still checked the selected trait caller. Removing the external call and an old function reduced the clean output set to three files and made their names unavailable to a fresh consumer; regenerating into a reused directory retained the old external template. A translation error exited nonzero but emitted Lean that compiled with `sorryAx`. These are one-shot CLI observations, not same-process Aeneas API or Anneal generation behavior.

## Applicability

The subjects are the exact executable and runtime hashes in `REPORT.json`, with `rustc 1.98.0-nightly (f8a08b688 2026-05-30)` (binary SHA-256 `2ab7af1ea2ec5c69195fd8dfb0e1f91afdb7cc1e53127bba416616ce43a18dbc`) on macOS arm64. Charon was invoked as `charon rustc --preset aeneas --dest-file ... -- <source> --crate-type lib --crate-name trait_probe --edition 2021`. Aeneas used `-backend lean -no-progress-bar -sequential -split-files -gen-lib-entry -print-unknown-externals -dest ... <llbc>`. Each variant used a new Charon and Aeneas process, the same source/LLBC path, and an emptied clean output directory. Fresh Lean processes compiled each generated module chain with the pinned prebuilt Aeneas runtime and dependencies in `LEAN_PATH`.

The fixture has `Step::step` for `u32`, a `use_step` caller, an `old` function, and an `extern "C" external_double` call. The reorder variant changes item order without changing these bodies. The shrink variant removes `old` and both external declarations. The error variant replaces those with raw-pointer dereference, unsupported by this Aeneas CLI. This extends the [identity/manifest run](../anneal-3730-aeneas-identity-manifest-2026-09-29/REPORT.md) with the trait declaration, reorder, external dependency, and fresh Lean controls it had left open. The concrete external model here is a *locally supplied Lean replacement* for the generated template, not a registered Aeneas external-model registry edit.

## Findings

### Translation, output ownership, and fresh consumers

| Variant | Charon / Aeneas exit | Clean generated files | Generated Lean declaration heads | Fresh Lean result |
| --- | --- | --- | ---: | --- |
| base | 0 / 0 | `Types`, `Funs`, `FunsExternal_Template`, entry | 7 | module chain and `use_step 1 = .ok 2` passed with an axiom template supplied for external call |
| reorder | 0 / 0 | same four names | 7 | same selected caller proof passed |
| shrink | 0 / 0 | `Types`, `Funs`, entry | 4 | selected caller proof passed; `#check old` and `#check external_call` each failed as unknown identifier |
| error | 0 / 1 | `Types`, partial `Funs`, entry | 5 | modules and `#check bad` compiled, but `#print axioms bad` reported `[sorryAx]` |

The clean base `Types.lean` contains `structure Step`; `Funs.lean` contains the `Step` implementation, `use_step`, `old`, and `external_call`; the template declares `axiom external_double`. A fresh consumer with that template could import the modules, but the external call is assumption-dependent. Replacing the template in a separate fresh compilation with a concrete Lean definition made `external_call 1 = .ok 2` pass by `rfl`; `#print axioms external_call` then said it depends on no axioms. This checks the *supplied model's* effect on Lean acceptance, not the correctness of the external C function or Rust-level claim.

The reorder case retained the same Lean names and the selected `use_step` type/proof in this fixture, yet `Funs.lean`, `Types.lean`, and the external template all changed hashes. For example, `use_step` moved from generated `Funs.lean` line 38, declaration-line byte range `[1826,1876)`, to line 50, range `[2571,2621)`. `Types.lean` changed because the trait source span moved. This supplies a byte-instability witness for I084/I148 without claiming semantic equivalence of entire generated modules. The fresh Lean check supports only the selected caller property.

The successful shrink's clean file set omitted `FunsExternal_Template.lean`. A subsequent one-shot shrink translation into a copy of the base destination still left that old file alongside the new three. A directory listing after success therefore cannot be used as a complete output manifest for the current request. The fresh shrink consumer compiled from its **clean** generated set and rejected both removed declaration names. This is a negative control for stale output availability, not an atomic publication implementation.

The error variant's Aeneas stdout identified unsupported raw-pointer dereference and a partial generated file. Its `Funs.lean` has `def bad ... := do sorry`. Fresh Lean accepted that file and reported `sorryAx` for `bad`, despite Aeneas exit 1. A pipeline must retain the translation status and trust/taint state; compiling emitted Lean alone is not a valid success oracle. **Basis: execution** of the preserved commands and fresh consumers.

### Experimental manifest and source correspondence

`support/raw-results.json` records, for each variant, source/LLBC SHA-256, exact generated filename/size/SHA-256 inventory, Charon declaration `def_id`, name and original `item_meta.span`, and generated declaration name, file, line, and exact UTF-8 byte interval for its declaration line. `support/inputs/` and `support/outputs/` preserve all matching bytes. The manifest's nearest `Source:` comment is a lexical hint. Its `authenticated_charon_link`, `proven_rust_to_lean_mapping`, and `editable_proof_ranges` fields are deliberately null: this CLI output does not authenticate a Rust item → Charon item → Lean declaration/one-to-many helper edge or an editable annotation range. That relation remains an Anneal-side requirement for I087/I149. **Basis: execution** for raw fields; **derived** for mapping limits.

## Evidence

`support/probe.py` is the standard-library-only replay harness, SHA-256 `a0dfa2475bd3645a8068ce4740b900b42ed957ef28b819269cdd101856d8997b`. `support/raw-results.json` (SHA-256 `d4891c9f4e990f817c4fceaeb2e7aaf316fdfd6d11cbb91e97266e804270d089`) preserves 36 chronological events/35 command records with argv, status, stdout/stderr, elapsed time, tool hashes, manifests, output inventories, and consumer responses. `support/check.py` (SHA-256 `34c689664d30556d8efe20b6a593c04cac401353983297ce754647362eb934ef`) checks all archived bytes and ranges, successful/failing controls, and null unproven links. It returned `OK: four Charon/Aeneas cases, fresh Lean consumers, exact file/range hashes, stale-output and sorry controls; 36 events`. Total sequential probe wall time was 51.65 seconds; the individual Charon calls were about 52–64 ms and Aeneas calls about 226–235 ms, with Lean compilation dominating. Those timings are one ordered run, not a benchmark.

Replay: from this package, run `python3 support/probe.py`; it replaces only its own `support/work`, `support/inputs`, `support/outputs`, and `support/raw-results.json`. The pinned local tools are referenced by absolute path. `python3 support/check.py` validates the retained run without launching toolchains. The previous [process-contract report](../anneal-3730-aeneas-process-contract-2026-09-29/REPORT.md) documents why the selected CLI executable is not evidence of same-process reuse safety.

## Revalidation

First run `python3 support/check.py`. For another Aeneas pin, record new binary/runtime hashes, rerun the four cases in private clean directories, compare file sets and declaration ranges, compile fresh Lean consumers, and deliberately check a reused destination plus a failed partial output. Any move to a same-process API requires a separate OCaml build, request-state reset protocol, and sequential/concurrent/cancelled-call tests; this one-shot matrix cannot substitute for them.
