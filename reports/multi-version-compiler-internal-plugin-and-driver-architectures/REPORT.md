# Multi-Version Compiler-Internal Plugin, IPC Helper, Worker-Router, and Verifier Driver Architectures

## Summary

Production compilers such as `rustc`, GHC, Clang, and OpenJDK `javac` provide no ABI or internal source-API stability across their middle-end and driver libraries (`rustc_driver` / `rustc_middle`, the GHC API and `.hi` interface format, Clang C++ `LibTooling` / `clangFrontend`, and `jdk.compiler`'s `com.sun.tools.javac.*`). Static analyzers, language servers, linters, and formal verifiers that inspect deep semantic representations therefore partition along five distinct version-isolation architectures, each carrying characteristic operational trade-offs and multi-toolchain failure modes:

1. **On-Demand Per-Toolchain Driver Synthesis and Baked `RPATH` Isolation (`trailofbits/dylint` `v6.4.0`):** `dylint` stamps compiled lint `cdylib` filenames with `@{channel}-{target}`, groups requested libraries by `<channel>-<target>`, and synthesizes a cached `rustc_private` driver binary on demand under `$HOME/.dylint_drivers/<toolchain>/dylint-driver` using advisory `flock` locking and `.into_temp_path()` pre-rename descriptor closure (`ETXTBSY` safety). It links `<toolchain>/lib` via `-Wl,-rpath` without setting `LD_LIBRARY_PATH` on Unix, spanning over four years of nightlies in one crate via `#[rustversion]` attributes—at the cost of requiring host-side compilation (`rustc-dev` + `llvm-tools-preview`) and, on nightlies since `2025-05-14`, performing a build-time network `git clone` of `rust-lang/rust-clippy` inside `driver/build/extra_symbols.rs` unless `DYLINT_CLIPPY_REPO` is pre-populated.
2. **Versioned Out-of-Process IPC Over Sysroot-Shipped Shims (`rust-analyzer` + `<sysroot>/libexec/rust-analyzer-proc-macro-srv`):** Gating `#![feature(rustc_private)]` behind `feature = "in-rust-tree"` keeps the host `rust-analyzer` binary completely free of `librustc_driver`, delegating procedural-macro dylib loading over `stdin`/`stdout` to the target sysroot's `rust-analyzer-proc-macro-srv` via negotiated `API_VERSION` (`0..=6`). Live execution across 17 `rustup` toolchains (`1.56.0`–`1.102.0-nightly`) establishes four concrete boundaries: (a) `<sysroot>/libexec/rust-analyzer-proc-macro-srv` is absent before `1.64` (`1.56.0`, `1.61.0`) and dynamically links `librustc_driver-<hash>.so` across `1.78.0`–`1.102.0-nightly`; (b) toolchains `1.78.0`–`1.84.0` reject `RUST_ANALYZER_INTERNALS_DO_NOT_USE=1` and `"this-is-unstable"` with exit code `122`, accepting only the space-separated literal `"this is unstable"`; (c) pre-`clap` binaries (`1.78.0`–`1.87.0-nightly`) silently ignore CLI flags (`--version`, `--format`); and (d) between `1.98.0-nightly` and `1.99.0`, reordering variants in `bidirectional::Response` silently changed COBS-framed `postcard` bytes for `ApiVersionCheck` from `[1, 2, 6]` to `[1, 1, 6]` without incrementing `CURRENT_API_VERSION = 6`, whereas self-describing NDJSON (`json-legacy`) remained compatible across all 15 shipping toolchains.
3. **Pre-Built Per-Compiler Worker Routers, Embedded Frontends, In-Process Compiler Plugins, and Compiler-Free CSTs (`HLS`/`hie-bios`, `IWYU`, `clangd`+`clang-tidy`, `ErrorProne`, `Semgrep`):** `haskell-language-server-wrapper` queries the project cradle's runtime GHC version and `execve`s `haskell-language-server-<X.Y.Z>` with `GHC_BIN` and `GHC_LIBDIR` because `ghcide` enforces exact patch-version equality (`compileTime == runTime`) to deserialize `.hi` interfaces and link object code in-process. `include-what-you-use` (`IWYU`) maintains a 1:1 `clang_<N>` branch lockstep plus runtime Clang `-resource-dir` probing because `libclang`'s stable C ABI (`CINDEX_VERSION_MINOR = 64`) intentionally omits full C++ template, overload, `TypeLoc`, and CFG internals. `clangd` (running `clang-tidy` checks in-process over `ParsedAST`) embeds one Clang `LibTooling` frontend while extracting external GCC/Clang system headers via `--query-driver` (`-E -v`). `ErrorProne` runs inside `javac` as a `TaskListener`, downcasting `JavacTask` to `BasicJavacTask` under explicit JPMS `--add-exports`/`--add-opens` flags on `jdk.compiler/com.sun.tools.javac.*`. At the opposite extreme, `Semgrep` bypasses target compilers entirely by lowering `tree-sitter` CSTs into `AST_generic`, achieving zero toolchain coupling while sacrificing macro expansion, trait/overload resolution, borrow checking, and layout semantics.
4. **Single-Toolchain Rust Formal Verifiers and Phase-1 vs. Phase-2 Cargo/`rustc` Split-Brain (`Kani`, `Verus`, `Creusot`, `Prusti`, `Flux`):** All five audited Rust verifiers link each driver binary against a single pinned `rustc`. Three of the five (`Verus`, `Creusot`, `Prusti`) run Phase-1 workspace inspection (`cargo metadata` or `cargo tree`) under the unpinned ambient/workspace Cargo before overriding Phase-2 `rustc`—creating a split-brain failure mode when a target repository declares a conflicting `rust-toolchain.toml`, `Cargo.lock` v4, or `edition = "2024"`. Most critically, `Prusti` (`prusti-utils/src/launch/mod.rs:428-462`) catches non-zero `cargo tree` exits by silently returning `false`, causing `cargo-prusti` to omit `--features prusti-contracts/prusti` in Phase 2 and compile specifications as erased no-ops. By contrast, `Kani` invokes its own bundled `cargo` binary in both phases while scrubbing `*/toolchains/*/lib` from `LD_LIBRARY_PATH`, and `Flux` resolves both phases through `rustup which --toolchain` and `cargo +<toolchain> --profile flux`.

### 2. Dynamic Per-Toolchain Driver Compilation, Caching, and RPATH Isolation (`trailofbits/dylint` `v6.4.0`)

`Basis: source (trailofbits/dylint@8cf8a6b17ea73364123226e7678aafbe0edc68c5)`

Dylint executes user-authored lint `cdylib` plugins that link directly against `rustc_private` crates (`rustc_driver`, `rustc_lint`, `rustc_middle`, `clippy_utils`), even when distinct lint libraries configured in the same target workspace require **different `rustc` nightlies** and different `clippy_utils` revisions.

#### 2.1 Toolchain-Stamped Plugin Filenames and Static-TLS Exhaustion Avoidance

Every Dylint lint library is compiled as a Cargo `cdylib` (`internal/template/Cargo.toml:10`) with `.cargo/config.toml` setting `rustflags = ["-C", "linker=dylint-link"]` (`internal/template/.cargo/config.toml:1-2`) and invoking `dylint_linting::dylint_library!()` (`utils/linting/src/lib.rs:248-265`):

1. **Shared `librustc_driver` TLS block:** `dylint_library!()` emits `#[allow(unused_extern_crates)] extern crate rustc_driver;` (`utils/linting/src/lib.rs:251-252`). As documented in `dylint/src/lib.rs:714-731`, if a lint `cdylib` links `rustc_private` crates without explicitly linking `librustc_driver.so`, Cargo statically links a private copy of `rand` and its thread-local storage block into each plugin; `dlopen`ing many lint dylibs into one driver process then exhausts Linux static TLS (`cannot allocate memory in static TLS block`). Explicitly linking `rustc_driver` forces every plugin to share the single `librustc_driver-<hash>.so` mapped into `dylint-driver`.
2. **Plugin ABI cookie:** `dylint_library!()` exports `#[no_mangle] pub extern "C" fn dylint_version() -> *mut std::os::raw::c_char` returning `"0.1.0"` (`CARGO_PKG_VERSION` of `dylint_linting`) alongside `register_lints(&rustc_session::Session, &mut rustc_lint::LintStore)` (`driver/src/lib.rs:34-44, 328-360`).
3. **Linker wrapper and `@<channel>-<target>` stamping:** `dylint-link` (`dylint-link/src/main.rs:18-52`) honors `$CARGO_HOME/config.toml` `target.<triple>.linker` (falling back to `cc` on Unix or MSVC `link.exe` / `rust-lld -flavor link` on Windows, `main.rs:54-120`), scans linker arguments and UTF-16 `@response` files for `-o <path>` or `/OUT:<path>` (`main.rs:122-193`), and—when `DYLINT_LINK_ENABLE_COPY_LIBRARY` is truthy (`main.rs:23-39`, `internal/src/env.rs:16`) or immediately after `cargo build` in `dylint`'s workspace builder (`dylint/src/library_packages/mod.rs:526-534`)—calls `dylint_internal::link::copy_library` (`internal/src/link.rs:54-83`). `library_filename_with_toolchain` (`internal/src/filename.rs:51-59`) embeds `RUSTUP_TOOLCHAIN` (`<channel>-<target>`) directly into the filename:
   ```text
   {DLL_PREFIX}{lib_name.replace('-', '_')}@{toolchain}{DLL_SUFFIX}
   // Example: libquestion_mark_in_expression@nightly-2026-05-14-x86_64-unknown-linux-gnu.so
   ```
   `parse_filename` (`internal/src/filename.rs:68-86`) recovers `(lib_name, toolchain)` via `stem.split_once('@')`.
4. **`mtime` preservation for `rustc` dep-info:** `copy_library` (`internal/src/link.rs:65-82, 123-169`) compares file contents byte-for-byte (`files_are_equal`) before overwriting so an unchanged `cdylib` retains its filesystem `mtime`. Preserving `mtime` prevents spurious downstream target rebuilds because `dylint_driver` registers every loaded plugin path in `sess.psess.file_depinfo` (`driver/src/lib.rs:324-326`).

#### 2.2 Grouping by Toolchain, `$HOME/.dylint_drivers/<tc>/` Caching, `#[rustversion]` Span, and the `build.rs` Network Hazard

At invocation time, Dylint discovers libraries from `DYLINT_LIBRARY_PATH` / `--lib-path` or workspace metadata (`[workspace.metadata.dylint].libraries` in `Cargo.toml` vs. `dylint.toml`, enforced mutually exclusive in `dylint/src/name_toolchain_map/mod.rs:57-61`). For unbuilt packages, `library_packages::toolchain` (`dylint/src/library_packages/mod.rs:401-410`) runs `rustup show active-toolchain` inside each lint directory under a sanitized environment (`internal/src/rustup.rs:35-45`), and `resolve()` (`dylint/src/lib.rs:232-270`) groups libraries into `ToolchainMap = BTreeMap<String, BTreeSet<PathBuf>>` keyed by `<channel>-<target>`.

For each `<toolchain>` key, `driver_builder::get(&opts, toolchain)` (`dylint/src/lib.rs:355`, `dylint/src/driver_builder/mod.rs:48-67`) resolves or synthesizes the matching driver:

- **Default cache path (`$HOME/.dylint_drivers`):** Drivers are cached at **`$HOME/.dylint_drivers/<toolchain>/dylint-driver`** (resolved via `dirs::home_dir()` in `driver_builder/mod.rs:69-91`, overridable via `DYLINT_DRIVER_PATH` in `cargo-dylint/src/main.rs:25-26` and `internal/src/env.rs:14`), rather than `$XDG_CACHE_HOME` or `~/.cache/dylint`.
- **SemVer freshness check (`is_outdated`, `mod.rs:93-115`):** Dylint runs `<driver> -V`, parses the trailing SemVer version, and rebuilds whenever `Version::parse(version_str) < Version::parse(env!("CARGO_PKG_VERSION"))`, invalidating older drivers on `cargo-dylint` upgrades without clobbering newer cached drivers.
- **Synthesized 3-file Cargo package (`initialize`, `mod.rs:29-42, 192-245`, `dylint/build.rs:13-52`):** On a cache miss, Dylint creates a temporary directory containing:
  1. `rust-toolchain.toml` setting `channel = "<toolchain>"` and `components = ["llvm-tools-preview", "rustc-dev"]` (triggering automatic `rustup` installation if absent);
  2. `Cargo.toml` declaring `dylint_driver-<toolchain>` (`edition = "2018"`) with `anyhow = "1.0"`, `env_logger = "0.11"`, and `dylint_driver = { version = "=6.4.0" }`; and
  3. `src/main.rs` enabling `#![feature(rustc_private)]` and calling `dylint_driver::dylint_driver(&args)`.
- **Four-year `#[rustversion]` compatibility span (`driver/src/lib.rs`):** Rather than maintaining per-compiler Git branches, one `dylint_driver` crate links `rustc_data_structures`, `rustc_driver`, `rustc_interface`, `rustc_lint`, `rustc_session`, `rustc_span`, and (`#[rustversion::since(2023-06-28)]`) `rustc_errors` (`driver/src/lib.rs:9-15, 158-159`), absorbing internal API breaks via `#[rustversion::before(...)]` / `#[rustversion::since(...)]` gates across `EarlyErrorHandler` -> `EarlyDiagCtxt` (`lib.rs:93-120, 495-533`), `parse_sess` -> `psess` -> `Session::env_depinfo` (`lib.rs:186-227, 305-327`), and `RunCompiler::new(...).run()` -> `run_compiler(...)` -> `compiler_entrypoint(...)` (`#[rustversion::since(2026-10-02)]`, `lib.rs:256-287`).
- **Build-time network `git clone` hazard (`driver/build/extra_symbols.rs:17-99`):** Starting on nightly `2025-05-06`, `clippy_utils` moved custom interned symbols into `clippy_utils/src/sym.rs`, requiring pre-initialization registration in `rustc_interface::Config::extra_symbols` (`driver/src/lib.rs:380-386`). #### 2.3 Dynamic Linker Isolation, Untracked-State Hashing, and `clippy_utils` Upgrade Automation

- **Absolute `-Wl,-rpath` without `LD_LIBRARY_PATH` on Unix (`driver_builder/mod.rs:120-136`):** On Unix, Dylint never sets `LD_LIBRARY_PATH` or `DYLD_FALLBACK_LIBRARY_PATH` when spawning Cargo or `dylint-driver`, avoiding host-library contamination of target `build.rs` scripts, proc-macro dylibs, and nested `rustup` subprocesses. On Windows, where PE binaries have no RPATH equivalent, Dylint prepends `<toolchain_path>/bin` to `PATH` under `#[cfg(windows)]` (`dylint/src/lib.rs:440-444`, `internal/src/command.rs:127-133`).
- **Per-toolchain target-dir and `RTLD_NODELETE` lifecycle (`dylint/src/lib.rs:379-472, 563-570`, `driver/src/lib.rs:122-128, 420-470`):** `check_or_fix` scrubs `CARGO`, `RUSTC`, and `RUSTUP_TOOLCHAIN` (`internal/src/rustup.rs:15-31`), isolates artifacts in `--target-dir <workspace_target>/dylint/target/<toolchain>`, and sets `RUSTUP_TOOLCHAIN=<toolchain>`, `RUSTC_WORKSPACE_WRAPPER=<driver>`, and `DYLINT_LIBS=<json-array>`. Inside `dylint-driver`, `sysroot()` (`driver/src/lib.rs:420-426, 465-470`) appends `--sysroot $RUSTUP_HOME/toolchains/$RUSTUP_TOOLCHAIN` when absent, opens each lint `cdylib` with `RTLD_LAZY | RTLD_LOCAL | libc::RTLD_NODELETE` so TLS destructors never execute against unmapped pages at exit, and hashes loaded plugin bytes plus `DYLINT_*` env vars into `-Cmetadata=dylint-untracked-state-<sha256>` (`driver/src/untracked_state.rs:46-125`) to invalidate Cargo's incremental cache cleanly.
- **Multi-nightly lint repositories (`package_options/mod.rs:37-44, 98-170`, `auto_correct/mod.rs:49-120`):** Each lint template carries an empty `[workspace]` table (`internal/template/Cargo.toml:19`) so dozens of lint crates—each pinning its own `rust-toolchain.toml` and `clippy_utils` Git revision—coexist in one repository, while `cargo dylint upgrade [--auto-correct]` updates both files in lockstep and mines intermediate `rust-clippy` diffs to rewrite migrated API calls.

#### 4.2 Clang `libclang` vs. `LibTooling`: `IWYU` Lockstep Branches vs. `clangd` + `clang-tidy` `--query-driver`

- **Why `libclang`'s stable C ABI cannot support deep verifiers (`llvm/llvm-project@2252e5dc…`):** `clang/include/clang-c/Index.h:36-70` (`CINDEX_VERSION_MAJOR = 0`, `CINDEX_VERSION_MINOR = 64`) maintains C ABI stability across LLVM releases, but `clang/docs/LibClang.md:3-5` and `clang/docs/Tooling.md:7-79` state that `libclang` *"will never provide all of the information representation stored in Clang's C++ AST, nor should it"*: `CXCursor`/`CXType` omit `Sema` lookup/overload state, uninstantiated vs. instantiated template specialization graphs, `TypeLoc` alias sugar chains, macro-argument expansion provenance, and CFG/dataflow internals (mirroring `rustc_public`'s omissions relative to `rustc_middle`).
- **`IWYU` 1:1 `clang_<N>` branch lockstep and `-resource-dir` coupling (`include-what-you-use@64476922…`):** Subclassing `clang::ASTConsumer`, `RecursiveASTVisitor`, `PPCallbacks`, and `CompilerInstance` (`iwyu.cc:101-120`, `iwyu_driver.cc:24-40, 260-427`) forces upstream `IWYU` to maintain one `clang_<N>` branch per LLVM major release (`clang_3.6` through `clang_23`, `README.md:49-77`) and probe `ComputeCustomResourceDir` (`iwyu_driver.cc:260-293, 323-331`) at runtime so `<stddef.h>`, `<stdarg.h>`, and target SIMD headers match the linked Clang frontend.
- **`clangd` + in-process `clang-tidy` with `--query-driver` (`llvm/llvm-project@2252e5dc…`):** Rather than shipping `M` worker binaries, `clangd` statically links one Clang `CompilerInvocation` and runs `clang-tidy` `ASTMatchFinder` checks directly inside `ParsedAST::build` (`clang-tools-extra/clangd/ParsedAST.cpp:40, 120, 293-294, 456, 501-526`; `clang-tools-extra/clang-tidy/ClangTidy.cpp:24-30`). When `compile_commands.json` names a different GCC, Clang, or cross-compiler binary matching the user's `--query-driver` allowlist, `SystemIncludeExtractor.cpp:8-31, 76-90` executes that external driver in verbose preprocessor mode (`-E -v`), parses `#include <...> search starts here:`, and injects `-isystem` paths and `-target` into `clangd`'s embedded Clang invocation while keeping `clangd`'s own bundled builtin `-resource-dir`.

#### 4.3 `ErrorProne` JPMS Internal-Compiler Coupling vs. `Semgrep` Compiler-Free CST Lowering

- **In-process JDK `javac` internal coupling (`google/error-prone@d37bcb8d…`):** `ErrorProneJavacPlugin` (`core/src/main/java/com/google/errorprone/ErrorProneJavacPlugin.java:25-37`) enters via the public `com.sun.source.util.Plugin` service interface, but `BaseErrorProneJavaCompiler.addTaskListener` (`check_api/src/main/java/com/google/errorprone/BaseErrorProneJavaCompiler.java:70-100`) immediately downcasts `(BasicJavacTask) javacTask` to grab `com.sun.tools.javac.util.Context` and enforce `compilePolicy=byfile` and `should-stop.ifError=FLOW`. - **Compiler-decoupled `tree-sitter` lowering (`semgrep/semgrep@c4dbe9ee…`):** `Parse_target.parse_and_resolve_name` (`src/parsing/Parse_target.mli:13-45`) and `languages/rust/generic/Parse_rust_tree_sitter.ml` parse source files directly with `tree-sitter` (`languages/rust/tree-sitter/semgrep-rust/lib/CST.ml`) into `AST_generic.program` (`src/ast_generic/AST_generic.ml:19-60`) without invoking any target compiler. #### 5.2 Concrete Toolchain-Conflict Failure Modes

When a target workspace declares its own `rust-toolchain.toml` (for example, an MSRV toolchain such as `1.78.0` or `1.82.0`), `Cargo.lock` v4 (stabilized in `1.83.0`), `edition = "2024"` (`1.85.0`), or an outer `RUSTC_WRAPPER`:

1. **Prusti fail-open silent contract erasure (`prusti-utils/src/launch/mod.rs:428-462`):** Before verification, `cargo-prusti` invokes bare `cargo tree` without `RUSTUP_TOOLCHAIN` to detect whether the target crate graph depends on `prusti-contracts`. If the workspace's `rust-toolchain.toml` causes `cargo tree` to fail (for example, `Cargo.lock` v4 or `edition = "2024"` under an older workspace toolchain, or an uninstalled toolchain channel), lines `458-461` catch `!output.status.success()` and **return `false` without emitting an error**. Phase 2 (`cargo-prusti.rs:60-61`) then omits `--features prusti-contracts/prusti`, compiling `#[requires]` / `#[ensures]` attributes as erased no-op macros while appearing to succeed.
2. **Creusot Phase-1 abort and `RUSTC_WRAPPER` collision (`cargo-creusot/src/main.rs:62-66, 156-163`):** Phase 1 (`MetadataCommand::new().exec()`) honors the target workspace's `rust-toolchain.toml` before Phase 2 sets `RUSTUP_TOOLCHAIN=nightly-2026-10-26`, aborting inside `cargo_metadata` whenever the workspace toolchain predates the lockfile or edition. In Phase 2, Creusot sets `RUSTC=creusot-rustc` without clearing `RUSTC_WRAPPER`, so an ambient `RUSTC_WRAPPER=sccache` wraps or rejects `creusot-rustc`.
3. **Verus Cargo-vs-`rustc` split-brain (`source/cargo-verus/src/subcommands.rs:593, 696-698`):** Because `cargo-verus` passes neither `+toolchain` nor `RUSTUP_TOOLCHAIN` (`subcommands.rs:696-698` notes `// TODO: use the "+ ... toolchain" argument?`), the target workspace's `rust-toolchain.toml` selects the **`cargo` executable**, whereas `RUSTC_WRAPPER=verus` discards Cargo's `argv[1]` compiler path and forces `1.100.0` `rust_verify` (`rust_verify/src/main.rs:46-89`). Passing `CARGO_UNSTABLE_CHECKSUM_FRESHNESS=true` (`subcommands.rs:593`) breaks if the workspace-selected Cargo predates `checksum-freshness` or emits compiler flags newer than `1.100.0`.
4. **Kani and Flux single-toolchain overrides:** Kani avoids Phase-1/Phase-2 split-brain by executing its bundled `~/.kani/kani-<VER>/toolchain/bin/cargo` in both phases, clearing `RUSTC_WRAPPER` and `RUSTC_WORKSPACE_WRAPPER`, isolating `--target-dir target/kani`, and stripping `*/toolchains/*/lib` from `LD_LIBRARY_PATH` / `DYLD_FALLBACK_LIBRARY_PATH` (`kani-verifier/src/lib.rs:197-245`), though overriding the compiler masks target MSRV regressions (`package.rust-version < kani_rustc`). Flux aligns Phase 1 (`rustup which --toolchain`) and Phase 2 (`cargo +nightly-2026-11-19 --profile flux`) cleanly under `rustup`, but hard-fails in Nix, Bazel, or distro environments where `cargo` on `PATH` is a direct binary rather than a `rustup` proxy.
