# Sandboxed Content-Addressed CI on GitHub Actions: Repository-Ruleset TCB Bootstrap, Static Cargo Closure, Right-Sized OCI vs. Nix Economics, and Batch Sigstore Claims

## Summary

- **Repository-ruleset Selection-TCB bootstrap without organization `workflows` rulesets:** Public organization repositories that cannot configure GitHub Enterprise Cloud organization-level `workflows` rulesets can close the `on: pull_request` workflow-tampering gap by combining (1) `.github/CODEOWNERS` with recursive `/.github/**` ownership dominance and zero-backslash validation, (2) static fixed-point consumer-TCB classification over all check-invoked and Dockerfile-copied repository paths (rejecting symlinks at or above TCB paths), (3) sibling-workflow `<gate_check_name>` anti-spoofing across both step jobs and `jobs.<id>.uses` reusable-workflow caller jobs, and (4) a compile-time-offline `FinalGate` that evaluates live default-branch policy jointly against the candidate tree (`joshlf/ci-core@39a79866b604b956467709d631ebbde97041a857`).
- **Zero-execution static Cargo workspace closure matches `cargo metadata` across multi-workspace trees:** Pure TOML and Git-tree analysis (without invoking `cargo`, `rustc`, proc-macros, or `build.rs`) reproduces `rust-lang/cargo@930a674da900a73c1dfbe16be62c42e75bdfdfc0` member discovery, target auto-discovery across Editions 2015–2024, local `path` dependencies, upward `.cargo/config(.toml)` `include` chains, and `rust-toolchain(.toml)` walks with zero discrepancies across all four Cargo workspaces in `google/zerocopy@db067a465fb2d7ab93f217a104a2b4fc9312c4da` and a 25-case edge suite. Hydrating `cargo_locked` caches safely requires running `cargo fetch --locked` from an empty scratch directory (`--manifest-path`) with an isolated `CARGO_HOME` while preserving `RUSTUP_HOME` so `rustup` proxy binaries resolve their toolchain.
- **Right-sized content-addressed OCI toolchain images (`1.92–6.73 GiB`) avoid standard-runner 14 GB SSD exhaustion and live Nix substitution latency:** Splitting 13 Rust toolchains, Kani `0.60.0`, and Anneal's Nix-built Lean 4 + Rust + Miri + Starnix dependencies into domain-partitioned OCI images (`zc-kani` `1.92 GiB`, `zc-nightly` `2.97 GiB`, `zc-stable-msrv` `3.92 GiB`, `zc-build-rs` legacy `4.97 GiB` / modern `6.72 GiB`, and single-user Nix `anneal-tc` `6.73 GiB` uncompressed) keeps every shard within standard GitHub-hosted `ubuntu-24.04` disk headroom while eliminating per-job network downloads. Inside read-only `/nix` container roots, offline `nix eval "path:.#..."` requires mounting an unprivileged user+mount-namespace `overlayfs` (`lowerdir=/nix`) so Nix retains `/nix/var/nix/db/db.sqlite` path validity while copying flake inputs into `/nix/store`.
- **Nested unprivileged `bubblewrap` (`NestedBwrap`) requires synthesized `/etc/passwd`, `openat2` work-tree confinement, and `--format docker` under Podman:** Running `bwrap --unshare-all --cap-drop ALL --clearenv` inside an outer `--network=none` container (`--cap-add SYS_ADMIN --security-opt seccomp=unconfined --security-opt apparmor=unconfined`) blocks inner capability escalation (`CapEff = 0`) while supporting inner `bwrap` invocations (such as `cargo-anneal` and Lean kernel replay), provided `/etc/passwd` and `/etc/group` entries are synthesized for the container UID/GID, work closures are materialized via `openat2(RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS)`, and declared outputs/caches are collected with `O_NOFOLLOW` and `st_nlink == 1` checks.
- **Tag-addressed GHCR claims + single-Fulcio-cert batch DSSE signing eliminate OCI Referrers races:** Addressing image (`img-v1-<recipe>`), cache (`cache-v1-<key>`), and check (`chk-v1-<action>`) claims by deterministic SHA-256 preimage tags—committed strictly bottom-up (`Image -> Cache -> Check`) in a single checkout-free `publish` job using one keyless Fulcio X.509 certificate (`OID 1.3.6.1.4.1.57264.1.8`–`.22`) across per-claim DSSE `Bundle0_3` envelopes—eliminates GHCR's `HTTP 404` Referrers API fallback race (`sha256-<hex>` read-modify-write clobbering across parallel shards).
- **Live GitHub Actions workflow compiler & GHCR release-archive behaviors:** GitHub's workflow parser rejects status functions (`cancelled()`, `always()`, `success()`, `failure()`) inside `env:` mappings at push time with a `0s` synthetic workflow-file failure (`Unrecognized function: 'cancelled'`); a trailing `if: cancelled()` step inside an `if: always()` `gate` job fails closed across both upstream and mid-gate cancellations. Setting `"org.opencontainers.image.source": "https://github.com/<owner>/<repo>"` on first push of an OCI release-archive manifest to GHCR from a public user repository automatically enables anonymous Bearer token pulls (`HTTP 200`).

## Findings

### 1. Repository-Ruleset Selection-TCB Bootstrap and Compile-Time-Offline `FinalGate`

Basis: source (`joshlf/ci-core@39a79866b604b956467709d631ebbde97041a857`: `crates/ci-core-model/src/{tcb.rs,gate.rs,config.rs}`, `crates/ci-core-model/tests/{compile_fail_firewall.rs,proptest_gate_and_tcb.rs}`) + derived

#### 1.1 Closing Caller-Edit and Gate-Spoofing Vectors Under Repository Rulesets

When an organization cannot attach an Enterprise-only organization `workflows` ruleset (`CallerKind::OrgRuleset`), caller workflows inside `.github/workflows/*.yml` live in the consumer repository (`CallerKind::RepoRuleset`) where `on: pull_request` evaluates workflow YAML from `refs/pull/<N>/merge`. `ci-core` enforces four joint invariants over the live default-branch policy `C_main` and candidate tree `T_cand`:

1. **Fixed-point consumer-TCB classification (`compute_effective_tcb`, `tcb.rs`):** A transition `T_base -> T_cand` is `NontrivialTcb` whenever any added, deleted, or mode/blob-changed path touches `.github/workflows/**` (except explicitly declared `non_tcb_workflows`), `.github/actions/**`, `.github/CODEOWNERS`, `/CODEOWNERS`, `/docs/CODEOWNERS`, `checks.toml`, any declared `pins.*.path` or `images.*.dockerfile`, any path matched by `images.*.context` or `extra_executable_paths`, or any repository script transitively invoked by `checks[].command` ( rejecting symlinks at or above every TCB path across both `T_base` and `T_cand`).
2. **`.github/CODEOWNERS` dominance (`validate_codeowners`, `tcb.rs`):** Rejects `\` escapes (`gitignore`-style backslash unescaping), `!` negations, `[...]` character classes, empty-owner clearing lines, shadow files at `/CODEOWNERS` or `/docs/CODEOWNERS`, and any pattern order where the last rule matching `/.github/**` (and every declared caller workflow) does not assign ownership exclusively to `tcb.owner_handles` / `tcb.owner_teams`. Remember that root `"/*"` in GitHub `CODEOWNERS` matches only direct root files and **never** matches `/.github/**`; recursive dominance requires `*`, `**`, `/**`, `/.github/`, or `/.github/**`.
3. **Sibling-workflow check-name anti-spoofing (`validate_workflows`, `tcb.rs`):** Parses every `.github/workflows/*.yml` in `T_cand` and rejects any non-caller step job **or** `jobs.<id>.uses` reusable-workflow caller job whose display name can collide with `gate_check_name` (default `"ci-core / gate"`), preventing a skipped `if: false` sibling job from satisfying `required_status_checks`.
4. **Live owner approval & `merge_group` stepwise attribution (`project_owner_approvals` & `verify_merge_group_slices`, `tcb.rs`):** On `pull_request` with a `NontrivialTcb` diff against `C_main`, `plan` short-circuits to `TcbPlan::Blocked` (`0` untrusted compute shards scheduled) unless a non-author owner in `C_main.tcb.owner_user_ids` (or self-author only when `C_main.tcb.allow_owner_self_approval == true`) holds a current GitHub `APPROVED` review bound to `pr.head.sha` (or `/ci-core approve <40-hex-pr-head-sha>` comment review not superseded by a later `/ci-core unapprove`). On `merge_group`, `BareGitSliceReplayer` (`git_bare.rs`) fetches `mergeQueue.entries` and replays `git merge-tree --write-tree` inside a bare repository (`core.hooksPath=/dev/null`, neutralizing `.gitattributes` merge-driver RCE) to attribute each queued PR slice stepwise before running or signing.

#### 1.2 Dependency-Typed Offline `FinalGate` (`ci-core-model`)

`crates/ci-core-model/Cargo.toml` contains zero network, filesystem-I/O, or async crates (enforced by `tests/compile_fail_firewall.rs` over `cargo metadata` plus `trybuild` compile-fail UI tests sealing `Verified<Claim>`, `NonEmptyVec<T>`, and `RepoSlug`). `evaluate_gate` (`gate.rs`) is a pure function over `(live_default_config, candidate_config, run_meta, plan_artifact, shard_records)` verifying seven conjunctive clauses: non-cancellation, run/attempt alignment (`plan_attempt == gate_attempt`), `plan_sha256` match, dual-config `EffectiveTcb` authorization, 100% check coverage across the union of checks required by `C_main` and `C_cand` (every check either `VerifyAtPlan` with an offline-verified `Bundle0_3` receipt or `Execute` with an exit-`0` shard record matching `action_digest`), job-conclusion consistency, and valid caller workflow paths.

### 2. Zero-Execution Static Cargo Closure vs. `cargo metadata` and Isolated `cargo_locked` Fetching

Basis: source (`joshlf/ci-core@39a79866`: `crates/ci-core-model/src/cargo_static.rs`, `crates/ci-core-cli/src/sandbox.rs`, `crates/ci-core-cli/tests/cargo_static_differential.rs`) + execution

1. **Differential equivalence without code execution (`cargo_static.rs`):** Running `cargo metadata` on an untrusted PR without `--no-deps` resolves registries and can execute arbitrary repository `.cargo/config.toml` settings (`rustc-wrapper`) or ambient `rust-toolchain.toml` channels. `discover_workspace` statically parses `Cargo.toml`, `[workspace]`, `workspace.members` / `exclude` globs, edition-aware default target discovery (`src/lib.rs`, `src/main.rs`, `src/bin/*`, `examples/*`, `tests/*`, `benches/*`, `build.rs`), local `path = "..."` dependencies across `[dependencies]`, `[dev-dependencies]`, `[build-dependencies]`, and `[target.<cfg>.*]`, upward `.cargo/config(.toml)` `include` chains (detecting `source.*.directory` and `local-registry` overrides), and upward `rust-toolchain(.toml)` files. Executed against `cargo metadata --no-deps --format-version 1` (`rustc/cargo 1.93.0`, matching `rust-lang/cargo@930a674da900a73c1dfbe16be62c42e75bdfdfc0` semantics), `cargo_static_differential.rs` observed **0 diffs** across all four workspaces in `google/zerocopy@db067a465fb2d7ab93f217a104a2b4fc9312c4da` and 25 synthetic edge cases (`0.73 s` wall time).
2. **Dual static `cargo_locked` audit (`audit_cargo_locked`):** Before populating a `cargo_locked` cache slot, `ci-core` audits both `Cargo.lock` (v3/v4) and every workspace `Cargo.toml` / `.cargo/config(.toml)` statically: rejecting `git+` sources, non-allowlisted registry URLs, missing package checksums, `[patch.*]` / `[replace]` overrides to non-local registries, and `rustc-wrapper` / `linker` / `runner` executables inside `.cargo/config(.toml)`.
3. **Isolated-`cwd` `cargo fetch --locked` invariant (`run_cargo_locked_fetch_native`, `sandbox.rs`):** `cargo fetch --locked --manifest-path /abs/work/Cargo.toml` must execute with `current_dir` set to an **empty temporary directory outside the repository** and `CARGO_HOME` set to a fresh staging directory, **while preserving `RUSTUP_HOME`**. Running from inside the repository allows Cargo's upward config walk from `cwd` to load untrusted `.cargo/config.toml` files; conversely, clearing `RUSTUP_HOME` causes `rustup` proxy binaries (`/usr/local/cargo/bin/cargo`) to fail with `error: rustup could not choose a version of cargo to run` when no `RUSTUP_TOOLCHAIN` is set.

### 3. Right-Sized OCI Toolchain Images vs. Live Nix Substitution and `NestedBwrap` Sandboxing

Basis: source + execution (`joshlf/ci-core@39a79866`: `crates/ci-core-cli/src/{ghcr.rs,sandbox.rs}`, `crates/ci-core-cli/tests/linux_sandbox_and_git_integration.rs`, measured on Linux `x86_64` kernel `6.12` with `podman` and `bwrap v0.13.1`)

#### 3.1 Measured Uncompressed OCI Image Sizes and Standard-Runner Disk Economics

Standard public GitHub-hosted `ubuntu-24.04` runners provide ~14 GB of free SSD prior to workspace cleanup (~32–45 GB after removing `/usr/local/lib/android`, `/opt/ghc`, and `/usr/share/dotnet`). Baking all 13 Rust toolchains, Kani, Miri, and Lean/Nix dependencies into a single monolithic container exceeds 18 GiB uncompressed and forces unrelated jobs to pull gigabytes of unused compilers. Partitioning images by toolchain role keeps every image under `6.8 GiB` uncompressed while eliminating per-job `rustup`, `crates.io`, Kani, and Nix binary-cache downloads:

#### 3.2 Offline Nix Flake Evaluation Over a Read-Only `/nix` Store (`overlayfs` Pattern)

When Nix `2.26.3` (`--no-daemon`) is pre-installed inside a read-only container rootfs (`--read-only` or read-only `bwrap --ro-bind / /`), `nix eval --offline --json "path:.#packages"` attempts to copy the local flake tree into `/nix/store` and open `/nix/var/nix/db/db.sqlite`.
- Mounting a fresh `tmpfs` at `/nix` loses the pre-populated SQLite valid-path database, causing Nix to treat pre-baked `/nix/store/*` paths as invalid.
- Copying `/nix/store` (`~5 GiB`) into `/scratch` per check wastes disk and tens of seconds of I/O.
- **Zero-copy solution (verified in execution):** Inside `NestedBwrap`, enter an unprivileged user + mount namespace (`unshare -Ur -m`) and mount a kernel `overlay` filesystem at `/nix` with `lowerdir=/nix` (the read-only image store) and `upperdir=/scratch/nix-upper,workdir=/scratch/nix-work` on `tmpfs`. Nix reads pre-baked store paths and `db.sqlite` at `O(1)` cost while writing newly evaluated `path:.` flake store entries strictly to `tmpfs`.

#### 3.3 `NestedBwrap`, Pure OCI Layout Normalization, and Filesystem Confinement Mechanics

1. **`NestedBwrap` outer/inner contract (`sandbox.rs`):** Checks that themselves spawn `bubblewrap` sandboxes (such as `cargo-anneal`'s Tier 1/Tier 2 `ExecSeal` sandboxes and 46-guard Lean TCB mutation testing, measured at `35.33 s` for `46/46` kills inside `NestedBwrap`) cannot run under Docker's default seccomp/AppArmor profile (`EPERM` on `CLONE_NEWUSER` / `mount`). Launching the outer `--network=none` container with `--cap-add SYS_ADMIN --security-opt seccomp=unconfined --security-opt apparmor=unconfined` while immediately wrapping the check command in an inner `bwrap --unshare-all --die-with-parent --new-session --clearenv --cap-drop ALL` drops all effective capabilities inside the check (`CapEff: 0000000000000000` verified in `/proc/self/status`) while permitting nested unprivileged user namespaces.
2. **Synthesized `/etc/passwd` and `/etc/group`:** Running the outer container as an arbitrary host UID:GID (`--user uid:gid`) causes tools that call `getpwuid(getuid())` (such as `ssh`, `git`, `nix`, and Python `getpass.getuser()`) to fail inside `NestedBwrap` if `/etc/passwd` lacks that UID. Synthesizing a minimal read-only `/etc/passwd` and `/etc/group` mapping the sandbox UID/GID to `ci:x:<uid>:<gid>:ci:/scratch:/bin/sh` resolves `getpwuid` without exposing host `/etc/passwd`.
3. **Podman `SHELL` directive & pure OCI layout normalization (`ghcr.rs`):** `podman build` defaults to `--format oci`, which ignores Dockerfile `SHELL ["/bin/bash", "-euo", "pipefail", "-c"]` directives; passing `--format docker` to `podman build` preserves `SHELL` semantics, after which `normalize_docker_save_to_pure_oci` unwraps nested `index.json` manifests, strips legacy Docker `manifest.json`/`repositories` files, and verifies every blob's SHA-256 and exact byte length (`verify_oci_layout`).
4. **Symlink-free `openat2` work-tree materialization and `O_NOFOLLOW` output collection:** Materializing `/work` with `rustix::fs::openat2(..., ResolveFlags::BENEATH | ResolveFlags::NO_SYMLINKS)` prevents path-traversal escapes during tree staging; collecting declared outputs and cache archives via fd-relative `openat` with `O_NOFOLLOW` and rejecting `st_nlink > 1` or special file modes (`FIFO`, sockets, devices, setuid/setgid) prevents hardlink/symlink exfiltration from container roots. Extracting archives containing `0555` read-only Nix directories requires tracking directory `chmod` permissions and restoring `0555` bottom-up *after* unpacking children.

### 4. Tag-Addressed GHCR Claim CAS and Single-Cert Batch Sigstore Attestation

Basis: source (`joshlf/ci-core@39a79866`: `crates/ci-core-model/src/attest.rs`, `crates/ci-core-cli/src/{ghcr.rs,signer.rs}`) + normative (`sigstore/protobuf-specs` v0.3)

1. **Eliminating GHCR's OCI 1.1 Referrers tag race:** Because `ghcr.io` returns `HTTP 404` on `GET /v2/<repo>/referrers/<digest>`, attaching attestations via OCI 1.1 referrers falls back to client-side read-modify-write updates on `sha256-<hex>`, which races under parallel matrix execution. `ci-core` instead publishes each verified claim to a deterministic, preimage-addressed lookup tag (`img-v1-<recipe_sha256>`, `cache-v1-<cache_key_sha256>`, `chk-v1-<action_sha256>`), where the OCI manifest carries `artifactType = "application/vnd.ci-core.claim.v1+json"` and two layers: the canonical JSON claim descriptor and its Sigstore `application/vnd.dev.sigstore.bundle.v0.3+json` bundle.
2. **Single-Fulcio-certificate batch signing & bottom-up commit order (`signer.rs`):** In the checkout-free `publish` job (`id-token: write`, `packages: write`), `ci-core` requests one GitHub Actions OIDC token (`aud = "sigstore"`), generates one ephemeral P-256 keypair in memory, obtains **one** short-lived Fulcio X.509 code-signing certificate, signs each claim's DSSE `in-toto` v1 PAE payload (`application/vnd.in-toto+json`), submits each signature to Rekor (`hashedrekord` v0.0.1 with integrated timestamp and inclusion proof within Fulcio certificate `notBefore..notAfter`), and commits OCI manifests strictly **bottom-up (`Claim::Image` -> `Claim::Cache` -> `Claim::Check`)** so no `Check` receipt is ever observable on GHCR before the `Image` and `Cache` claims recorded in its provenance are durable and verifiable.
3. **Offline X.509 OID and transitive provenance verification (`attest.rs`):** Offline verification checks TUF-pinned Rekor/Fulcio/CTFE roots, single-signature DSSE structural rules, and Fulcio X.509 v3 OID extensions (`1.3.6.1.4.1.57264.1.8` issuer `https://token.actions.githubusercontent.com`, `.1.10` `job_workflow_sha` in `trusted_engine_shas`, `.1.12`/`.1.14` immutable `repository_id`, `.1.15` `repository_owner_id`, `.1.18` `build_signer_uri` matching `https://github.com/<trusted_engine_workflow>@<sha>`, `.1.21` `run_invocation_uri`, and `.1.22` `repository_visibility`), and recursively verifies that every `Image` and `Cache` claim referenced by a `Check` claim was itself signed by an unrevoked `trusted_engine_shas` revision.

### 5. Live GitHub Actions Workflow Compiler & Release Distribution Findings

Basis: execution (live GitHub Actions runs on `joshlf/ci-core`: failed run `45090418675` / `45090419858` on `45d5a139a3ef54ecf7a695906072bdf70e825333`, succeeded `release.yml` run `45092559019` on `a126d795dfa6d883c380e8131d695b2e8a6d1d96`, and push compile check on `39a79866b604b956467709d631ebbde97041a857`, observed `2026-11-23`)

1. **`cancelled()` rejected inside `env:` mappings at workflow-compile time:**
   - Placing `WORKFLOW_CANCELLED: ${{ cancelled() }}` inside `jobs.gate.steps[*].env` passes offline schema linters (`action-validator v0.8.0` and `zizmor v1.23.1 --persona=pedantic`), **but** GitHub's server-side workflow compiler rejects it immediately on `push` (even on a `workflow_call`-only workflow file!) by creating a `0s` failed `push` workflow run with annotation:
     `Invalid workflow file: .github/workflows/ci.yml#L1 — (Line: 613, Col: 31): Unrecognized function: 'cancelled'. Located at position 1 within expression: cancelled()`.
   - **Fail-closed cancellation pattern inside `jobs.gate` (`if: always()`):** In GitHub Actions, step-level default `if: success()` evaluates `!cancelled()` and checks only prior steps in the *same* job (not upstream `needs.*` failures). Passing `--cancelled false` to the main `gate` evaluation step and appending a final step with `if: cancelled()` (`exit 1`) handles both upstream cancellation (skipping `bootstrap`/`download`/`gate` in `0s` and executing the `if: cancelled()` failure step) and mid-`gate` cancellation without using status functions outside `if:`.
2. **Automatic public GHCR anonymous pull inheritance via `org.opencontainers.image.source`:**
   - Pushing a multi-layer OCI manifest (`ghcr.io/joshlf/ci-core/release-archive:v0.1.0`) for the first time via `secrets.GITHUB_TOKEN` (`packages: write`) with top-level manifest annotation `"org.opencontainers.image.source": "https://github.com/joshlf/ci-core"` automatically inherited the public repository's visibility: an unauthenticated `GET https://ghcr.io/token?service=ghcr.io&scope=repository:joshlf/ci-core/release-archive:pull` followed by `GET https://ghcr.io/v2/joshlf/ci-core/release-archive/manifests/v0.1.0` returned **`HTTP 200`** immediately without manual package-visibility reconfiguration.
3. **Node 24 action pins & metadata artifact retention:**
   - Pinning `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1` (`v7.0.1`), `actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9` (`v7.0.2`), and `actions/download-artifact@9000827ccba6bdab643e8b6fd33ac0654aef8333` (`v8.0.2`) produced **0** annotations across `ubuntu-24.04` and `ubuntu-24.04-arm` (`build-archive` completed in `4m24s` on `x86_64-unknown-linux-musl` and `4m01s` on `aarch64-unknown-linux-musl`), whereas `v4` SHAs emitted Node.js 20 forced-Node-24 deprecation warnings.
   - Omitting `retention-days` on small (`<150 KB`) plan/shard metadata artifacts avoids `CreateArtifact` `HTTP 400` rejections in organizations whose maximum artifact retention policy is shorter than an hardcoded `retention-days` value, while keeping `retention-days: 1` on transient multi-GB OCI image/cache staging blobs.

## Boundaries

- **Live keyless Fulcio + Rekor `publish` latency under 30+ concurrent claims on GitHub-hosted runners (`not examined` in this report's local probes):** Batch signing and bottom-up GHCR commit order were verified against `InMemoryRegistry` and offline Sigstore `Bundle0_3` fixtures (`attest_offline.rs` / `linux_sandbox_and_git_integration.rs`); end-to-end Fulcio/Rekor network round-trip latency scales with Rekor inclusion-proof issuance on `merge_group`/`push`.
- **GHEC Organization Ruleset `referenced_workflows` payload under cross-org `workflow_call` (`unknown`):** `CallerKind::OrgRuleset` verification logic is implemented in `ci-core-model`, but live GitHub Enterprise Cloud organization-level `workflows` ruleset execution was not exercised because `google` organization ruleset settings were outside operator scope.
- **Native macOS and Windows check sandboxing (`unsupported`):** `ci-core` `v0.1.0` rejects non-Linux runner architectures/kernels (`verify_host_platform` via `rustix::system::uname()` enforces `Linux` + `x86_64` or `aarch64`); Windows cross-targets in `zerocopy` are tested via cross-compilation or Wine/Miri inside Linux containers rather than native Windows runners.
- **Container `NestedBwrap` is a capability/filesystem/network isolation tier, not a hardware VM hypervisor boundary (`known not to apply`):** Checks inside `NestedBwrap` share the host runner's Linux kernel; defending against unpatched Linux kernel privilege-escalation exploits requires ephemeral per-job VM isolation (such as GitHub-hosted ephemeral VMs or Firecracker/KVM microVMs).
