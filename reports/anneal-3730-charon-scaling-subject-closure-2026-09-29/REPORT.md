# Charon root closure and Cargo workspace inputs in a bounded scaling matrix

## Summary

At pinned Charon 0.1.210, a two-member offline Cargo workspace exposed three distinct sets: the Cargo units built, the local declarations Charon selected from the primary crate, and foreign dependency signatures that remained opaque. Selecting one app root chased its local node, leaf, and generated constant, producing four local function records; selecting 32 roots produced 97; the whole 192-root library produced 579. Feature selection, a build-script environment value, and an `include_str!` payload each changed the selected LLBC while the app's main Rust source bytes stayed fixed. A workspace-wide multi-library request exited 101 after writing a valid LLBC for the `shared_closure` member, not for the intended app member.

These are observations for this generated fixture, not a large-workspace benchmark or evidence of Anneal verification. The partial-output case is an especially concrete reason to bind an LLBC result to one declared compilation unit and successful transaction before publishing it to a proof consumer.

## Applicability

The local subject was `app_closure` in a two-member workspace with a path dependency on `shared_closure`. `app_closure` had 24 or 192 each of `leaf_N`, `node_N`, and `root_N`; a root calls its matching node, the node calls its leaf and `shared_closure::dep`, and every root reads a constant generated by `build.rs`. The crate also had a feature-gated `selected`/`default_only` function and a function using `include_str!("payload.txt")`. There were no registry dependencies. The script generated the fixture and lockfile locally, ran eleven sequential fresh-process Charon/Cargo cases with separate `CARGO_TARGET_DIR` paths, then removed each target directory. Each case used `--offline --locked`, `CARGO_BUILD_JOBS=1`, `CARGO_INCREMENTAL=0`, and `RAYON_NUM_THREADS=1`.

The host was macOS 26.6.2 arm64 with 8 GiB RAM. Charon's binary SHA-256 was `51bb6d23beab3f97a684c25162d3e402fc820c891b57b21d2ca781c1da211a8b`; rustc and Cargo were nightly 2026-05-31, with hashes in `REPORT.json`. The matching Charon source checkout was `AeneasVerif/charon@0c91ca1a8e002d6bfa8d8f1f452804fce2f92cf1`; behavioral claims here come from the preserved executable outputs. The script used a 15 GiB free-disk guard and ran cases serially.

This package extends the earlier `charon-performance-and-revision-probes-2026-09-28` independent-function matrix with a local call graph, a workspace dependency, a build script, a feature, and an included file. It gives bounded evidence for [#3731](https://github.com/google/zerocopy/issues/3731) I009, I020, I076, I078, and I080, with smaller implications for I015/I079. It does not exhaust any of these items. It also informs #3730 D07 and D09, which were consolidated into #3731.

## Findings

### Local root chasing is narrower than Cargo's build closure

For both 24 and 192 generated roots, selecting only `crate::root_000` yielded four local function records: `root_000`, `node_000`, `leaf_000`, and generated `BUILD_VALUE`. The LLBC also carried two foreign functions, including `shared_closure::dep` as `Opaque`. Selecting eight roots from the 24-root crate yielded 25 local records; selecting 32 roots from the 192-root crate yielded 97. Whole-library extractions yielded 75 and 579 local function records respectively, including `payload_len` and the active default-feature function. The count differences agree with the fixture's call graph plus one shared generated constant; the preserved LLBC contains all item names, locality, body kind, spans, and ordered-declaration counts. **Basis: execution**.

The selected app library's Cargo unit graph had four units: app library, build-script compilation, build-script execution, and shared library compilation. The unit graph's one root was the app library, while Charon's selected LLBC kept the shared function body opaque. A separate extraction selecting `shared_closure --lib` succeeded and emitted an LLBC with `crate_name: shared_closure` and one local function. Thus Cargo compiling a path dependency is not the same as Charon translating its body into the primary crate's result. **Basis: execution** of unit-graph and LLBC commands; the coverage distinction is **derived**.

### A source path alone does not identify the selected result

The 192-root app source SHA-256 was `0f62c857c9ae3cfd14d12bb25616ecbb6a18230762cc27b0ec527efeae153d8a` across the one-root, 32-root, whole-library, feature, build-env, and payload cases. Nevertheless, root selection changed local function counts from 4 to 97 to 579. Enabling `selected` kept 579 local functions but replaced `default_only` with `selected`; Cargo's four-unit graph showed `selected` in app/build-script unit feature lists and absent from the shared unit. **Basis: execution**.

With the source and manifest still fixed, changing only `BUILD_VALUE` from 7 to 9 changed the generated file contents and the serialized `BUILD_VALUE` body (literal 7 versus 9). Changing only `app/src/payload.txt` from `payload-A` to `payload-BBBBB` changed that file's hash and the serialized `payload_len` body. These differences are visible in preserved raw LLBC and per-function body hashes; the input-hash manifest records that `app/src/lib.rs` stayed fixed. The build script's `rerun-if-env-changed=BUILD_VALUE` is preserved in its source. **Basis: execution**. This identifies three inputs omitted by a key of only `{main source path, main source bytes}`; it does not enumerate every Cargo/rustc input.

### A multi-unit Cargo request can leave a misleading single LLBC

The `--workspace --lib` Cargo unit graph had two roots: app and shared library. The corresponding `charon cargo --dest-file n192-workspace-libs.llbc -- --workspace --lib --offline --locked` invocation exited 101 after an `extern location for shared_closure does not exist` error while compiling the app. The destination file nevertheless existed, parsed as LLBC, and identified `crate_name: shared_closure` with one local function. It was the output from one selected unit during a failed multi-unit request, not evidence of a successful workspace extraction. **Basis: execution**; exact command, stderr, and artifact are preserved.

The result illustrates why process success, expected subject identity, and output freshness/completeness are separate publication checks. A consumer that merely sees a parseable destination could accept the wrong member's LLBC in this observed failure. The fixture did not test an old destination file, atomic rename, or Charon's behavior under every multi-target selection. **Basis: derived** from the partial-output control.

### Resource observations are small-fixture measurements

| Case | Local functions | Wall time | Maximum sampled process-tree RSS sum | LLBC size |
| --- | ---: | ---: | ---: | ---: |
| 24 roots, one selected | 4 | 0.547 s | 185 MiB | 25 KB |
| 24 roots, whole library | 75 | 0.505 s | 193 MiB | 318 KB |
| 192 roots, one selected | 4 | 0.535 s | 193 MiB | 61 KB |
| 192 roots, 32 selected | 97 | 0.538 s | 185 MiB | 448 KB |
| 192 roots, whole library | 579 | 0.580 s | 190 MiB | 2.47 MB |

Each successful app case left about 1.13 MB in its fresh Cargo target directory before cleanup; the feature case was 28 bytes larger in this measurement. The script sampled `/bin/ps` at roughly 20 ms intervals and summed reported resident sizes across the Charon process tree; these are observed sample maxima, not true peak unique memory or a steady-state capacity estimate. Timings are one run per case and include Cargo/Charon startup; the first size and later cases may benefit from OS caches. The matrix therefore supports only a narrow conclusion: this generated fixture completed within the recorded time, memory samples, and target size. **Basis: execution**.

## Boundaries

- **I009/I015:** The fixture records source, manifests, lockfile, selected features/roots, tool binaries, `BUILD_VALUE`, included text, Cargo metadata, unit graphs, and generated-file content hashes. It does not close all possible environment, target, build-script, macro, external-model, or tool-version inputs. It did not run an in-flight proof query or measure whether dependency-scoped freshness is sound.
- **I010–I014/I016:** No live file capture, open buffer, ABA history, multi-document atomic edit, multiple writer race, or orchestration restart was tested. Separate target directories provide controlled inputs but do not establish a coherent live workspace snapshot.
- **I019–I021:** There were no annotations, parser attachment, structural item moves, duplicate markers, or in-flight proof results in this fixture. The earlier `anneal-3730-charon-subject-identity-2026-09-29` package addresses a separate subset.
- **I073–I075:** No saved-versus-overlay comparison, shadow relocation, or warmed Cargo target was tested. All cases used saved files at one location and fresh targets; the observed workspace failure is not a Cargo cache-skip result.
- **I076/I078:** The workspace multi-unit failure produced an LLBC for one member, but other target arrangements, simultaneous producers, interruption stages, old-file retention, and atomic publication remain open. No broad claim that Charon cannot handle workspaces follows from one failing selection.
- **I077/I080:** Every case used a fresh Charon process and a private target directory. No same-process Charon API, parallel consumers, shared writable cache, cancellation, or sustained memory/disk drift was measured.
- **I079:** Raw LLBC paths and keyed map ordering can vary; this report does not define a safe normalization or a semantic cache key. Only directly serialized item/body/file facts are interpreted.
- No Aeneas, Lean, Anneal, proof theorem, or source-to-LLBC semantic preservation was checked here. `has_errors: false` is a Charon-stage outcome only.
