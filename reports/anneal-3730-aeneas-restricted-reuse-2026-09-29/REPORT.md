# Restricted generated-module reuse after Aeneas trait changes

## Summary

In a tiny pinned Rust→Charon→Aeneas→Lean fixture, changing a trait implementation body left generated `Types.lean` byte-identical while changing `Funs.lean`; changing the trait method signature changed both. An oracle-guided prototype reused the old compiled `Types.olean` only for the body edit, recompiled affected imports, and passed the same fresh Lean proof as full regeneration. Reusing stale `Funs.olean` after the body edit made the updated proof fail; reusing stale `Types.olean` after the signature edit made compilation fail with a type mismatch. This adds a concrete module-level invalidation and negative-control result beyond the earlier one-shot trait/reorder/shrink matrix.

The prototype still invokes the whole-crate Aeneas CLI for every variant to learn the fresh generated bytes. It is **not** an Aeneas incremental API or evidence that the translator can skip work. In this one run, its permitted OLean reuse reduced the number of Lean compilation commands from three to two for the body edit, but the measured hybrid compilation was slower (7.386 s versus 5.493 s); no latency benefit was established.

## Applicability

The subject is the cached local Charon 0.1.210 / Aeneas nightly-2026.06.03 / Lean 4.30.0-rc2 tuple on macOS arm64. `support/probe.py` uses only installed binaries and the prebuilt Aeneas Lean runtime, with one Charon, Aeneas, or Lean command active at a time. No dependency was downloaded or installed. All three Rust variants used the same scratch source/LLBC path to avoid making source-location changes masquerade as semantic changes. Each Aeneas call generated into an empty case directory using `-sequential -split-files -gen-lib-entry`; each full consumer used fresh Lean batch processes.

The Rust fixture has `core.Step::step`, its `u32` implementation, a trait caller, an independent `side.untouched` function in another Rust module, and a `combine` caller. The body edit changes `wrapping_add(1)` to `wrapping_add(2)` without shifting source locations. The signature edit changes `step(self)` to `step(self, delta: u32)`, adapts the implementation to add `delta`, and adapts the caller to pass `1`; selected outputs remain equal to baseline. The output split produced three Lean modules: `Fixture.Types`, `Fixture.Funs`, and `Fixture`.

## Findings

### Observed output graph and reuse fence

The script parsed generated `import` lines and found the same graph in all three outputs:

```text
Fixture.Types  →  Fixture.Funs  →  Fixture
       (imported by)      (imported by)
```

`Fixture.Types` imports the fixed external Aeneas runtime; `Fixture.Funs` imports `Fixture.Types`; `Fixture` imports `Fixture.Funs`. The source comments and declarations identify the trait structure in `Types` and the trait implementation, `core.use_step`, `side.untouched`, and `combine` in `Funs`. Those Rust-to-Lean item associations are inspected fixture facts, not authenticated producer-issued dependency metadata. At this split granularity, the unchanged `side.untouched` cannot be reused as a separate compiled module because it shares `Funs` with the changed trait implementation. **Basis: generated source inspection and execution.**

| Variant versus baseline | `Types.lean` bytes | `Funs.lean` bytes | Entry `Fixture.lean` bytes | Safe compiled OLean reuse under the prototype |
| --- | --- | --- | --- | --- |
| Implementation body `+1→+2` | Equal | Different | Equal | `Fixture.Types` only |
| Trait signature + adapted caller | Different | Different | Equal | None |

The entry source text was equal across all variants, but its imported `Funs` artifact changed. The prototype therefore **copied** the old entry source bytes but recompiled its OLean. Its rule was: a generated module's OLean may be reused only if its source bytes are exactly equal to baseline and every imported generated module's artifact is reusable under the same rule. This is a deliberately conservative recursive fence. It does not assert that byte inequality implies semantic inequality, or that matching source bytes alone authenticate the Rust snapshot or external Aeneas runtime. **Basis: derived rule applied to exact output hashes and parsed imports.**

### Fresh proof oracle and unsafe-reuse controls

Full regeneration compiled `Types`, `Funs` and entry modules and checked `core.use_step 1`, `combine 1`, and `side.untouched 1`. Baseline and signature variants proved results 2, 13, and 11; the body variant proved 3, 14, and 11. Every full and guarded-hybrid proof exited zero and printed only `[propext, Classical.choice, Quot.sound]` for its three theorems, with no `sorryAx`. These are selected Lean computations over Aeneas output, not an independent Rust–Lean equivalence proof. **Basis: execution.**

The hybrid body consumer copied the baseline `Types.olean` and compiled only `Funs` and entry. The hybrid signature consumer copied no OLean and compiled all three modules, though it could reuse the identical entry *source* bytes. Conversely, an intentionally unsafe body consumer loaded baseline `Funs.olean` with the new claim: entry compilation succeeded, but the updated `rfl` claims failed, and failed-theorem axiom output included `sorryAx`. An intentionally unsafe signature consumer loaded baseline `Types.olean`; compiling new `Funs.lean` failed because a two-argument implementation was expected to fill a one-argument field. These failures show why a stable module name or unchanged entry source cannot authorize stale compiled imports. **Basis: execution.**

| Comparison in retained run | Full fresh Lean compile | Guarded hybrid Lean compile | Interpretation |
| --- | ---: | ---: | --- |
| Body edit | 3 modules, 5.493 s | 2 modules, 7.386 s | One OLean safely reused; no measured speedup. |
| Signature edit | 3 modules, 5.329 s | 3 modules, 18.216 s | No OLean was reusable; times are load/order-sensitive. |

Charon calls took 0.052–0.381 s and whole-crate Aeneas calls 0.212–0.223 s in this ordered run. The baseline Charon and Lean calls were cold relative to later cells. These single-run timings cannot support a throughput estimate. The prototype's oracle requires the fresh whole-crate output before deciding reuse, so any benefit here is solely possible downstream Lean compilation reuse. **Basis: execution and derived scope.**

## Boundaries

The existing [trait/output-shrink matrix](../anneal-3730-aeneas-trait-output-shrink-matrix-2026-09-29/REPORT.md) already covers reorder, output-set shrink, stale files in reused destinations and translation error taint. This report adds a trait body/signature mutation, parsed generated-module dependency graph, guarded OLean reuse, fresh full versus hybrid proof checks, and two unsafe-reuse controls. It does not repeat that matrix's external-model or shrink cases.

E11 / #3731 I083 now has a narrow executed prototype, not a complete fine-grained invalidation result. There is no same-process OCaml Aeneas API, translator-side per-item invalidation, authenticated Rust-item dependency graph, cross-crate graph, source-map preservation test, plugin/macro mutation, parallel worker, or realistic larger project. The generated split has only three modules, so it cannot measure whether declaration-level reuse would be worthwhile. The fresh Lean oracle checks three selected claims and does not prove whole-program translation soundness. OLean reuse also assumes the pinned tool/runtime and options remain fixed; the prototype does not implement a durable multi-input cache key.

## Revalidation

Run `python3 support/check.py` first. To rerun with the same locally installed pins, run `python3 support/probe.py` from this package; it replaces only its own `support/work`, `support/inputs`, `support/outputs` and `support/results.json`. Compare generated bytes, parsed imports, compile command count, Lean proof results and unsafe-control failure stage before considering timing. A genuine Aeneas incremental experiment would need an exposed same-process or item-level API and a producer-issued dependency map; this one-shot oracle-guided wrapper cannot establish either.
