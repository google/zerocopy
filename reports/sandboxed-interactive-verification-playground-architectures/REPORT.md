# Sandboxed Interactive Formal Verification Playground Architectures

## Summary

Interactive formal verification (FV) playgrounds face a sharp three-way tension between `<5 s` interactive round-trip latency, strong multi-tenant isolation against arbitrary compile-time and solver execution, and infrastructure/cold-start cost. Primary-source inspection of 22 repositories across Rust, Lean 4, Dafny, Coq/Rocq, Alloy, TLA+, Z3, and Compiler Explorer, paired with direct execution probes, yields five design conclusions:

1. **Sub-5 s interactive latency requires keeping warm state *and* pre-compiled artifacts across edits.** Cold-container models (`rust-lang/rust-playground`, `verus-lang/verus-playground`, gVisor `dafny-api`) achieve `<5 s` only when pre-compiling dependencies (`534` cached crates in `rust-playground`) or holding a persistent container/LSP session. Measured directly on Lean `v4.34.1`, `bubblewrap 0.12.0` spawn overhead is negligible (`17.23 ms` median), cold `lean --stdin` with `import Init` takes `1,558.69 ms` median (`817.82–2,403.2 ms`), and persistent `lean --server` inside `bwrap` cuts first `didOpen` (`import Init`) to `397.72 ms` (`76.52 ms` initialize) with `~208–213 ms` incremental edits (`[real measurement]`).
2. **Existing FV playgrounds leave concrete RCE, DoS, and memory-cap gaps.** `leanprover-community/lean4web` uses `bwrap --unshare-*`, yet enforces zero WebSocket rate or connection limits, runs `ulimit -t 3600` (1 hour CPU), relies on `ulimit -m` (`RLIMIT_RSS`, which modern Linux kernels ignore—empirically bypassed by allocating `128 MiB` under `ulimit -m 65536`), and lacks seccomp filtering so Lean `#eval IO.Process.output` spawns child shells inside the sandbox (`[real measurement]`). `fm-playground`'s gVisor Dafny runner (`--runtime=runsc`) omits `--network=none`, while `flux-playground` and `Alloy4Fun` isolate neither processes nor tenants.
3. **Full browser-native `rustc` + LLVM editing is blocked today, whereas browser-native proof checking splits cleanly.** `rustc` + LLVM + procedural macros + `build.rs` scripts require host execution/dynamic linking and have no hosted Tier 1/2 `wasm32` compiler toolchain. Conversely, theorem provers already run in Web Workers: `jsCoq`/`waCoq` runs OCaml bytecode on WASI + `js_of_ocaml`, `Z3` ships Emscripten pthread WASM (`TOTAL_MEMORY=2GB`), and `lean4-wasm-in-browser` / `browser-lean` run Lean 4 (`96.17 MiB` raw / `15.4 MiB` br `lean.wasm`) at `0.28–0.37 s` warm incremental checks once booted (`~2.2–5.6 s`) or snapshot-restored (`--incr-header-save`, `0.21–0.37 s` `Init` first run).
4. **Pure-Rust external Lean 4 kernels compile directly to tiny `<300 KB` gzip WASM modules—if exports are cone-pruned.** Measured directly: `nanoda_bin` (`ammkrn/nanoda_lib`) compiles to `wasm32-wasip1` at **`914,651 B` raw (`271,683 B` gzip)** (`[real measurement]`, requiring only a single-thread bypass around `tc.rs:155`'s unconditional `std::thread::scope`), and `con-ron-core` (`leanprover/con-ron`, zero external dependencies) compiles cleanly to `wasm32-unknown-unknown` (`284,828 B` raw / `69,747 B` gzip minimal `parse_bytes` `cdylib`). However, exporting even minimal `import Init.Prelude` without pruning produced **`330 MiB` of NDJSON** (`SampleInitPrelude.ndjson`, `[real measurement]`), making transitive cone pruning or pre-interned `Init` snapshots mandatory for `<5 s` browser replay.
5. **Recommended two-tier architecture for interactive Rust+Lean verification ("Try" vs "Break a Proof / Catch a Cheat"):** Run untrusted Rust MIR capture (`rustc` + proc-macros + `build.rs`) and full Lean editing inside hardened server sandboxes (`bwrap` + `--unshare-user --disable-userns` + dual-arch seccomp-BPF + cgroup v2 `memory.max` / `pids.max` / CPU quotas + warm session pool, as exemplified by Compiler Explorer's `nsjail` profiles and `cargo-anneal`'s `sandbox.rs`), while running pre-captured or challenge-scoped **external kernel replay (`nanoda` / `con-ron`) in browser Web Workers via WASM** for zero-server `<5 s` cryptographic/logical challenge scenarios.

## Applicability

- **Zero-server client-side interactive challenges ("Break a Proof / Catch a Cheat", badge/receipt replay):** Applies directly when Rust targets (`MIR -> Captured.lean`) are pre-captured server-side or at CI time into cone-pruned NDJSON (`lean4export`) plus editable proof templates, allowing client-side WebAssembly `lean4-wasm` elaboration paired with pure-Rust `nanoda`/`con-ron` WASM kernel verification.
- **Full interactive untrusted Rust + Lean verification playgrounds (`play.anneal` / `play.rust-lang.org` / `live.lean-lang.org`):** Applies when users write arbitrary Rust, `unsafe` blocks, macros, or large `Std`/`Mathlib` proofs. Requires server-side OS/VM containment (`bwrap` + seccomp + cgroups, `nsjail`, gVisor, or microVM pools) because arbitrary `proc-macro`/`build.rs` compilation executes host code and Lean elaborators require `~0.8–1.6 s` `Init` startup and `~0.8+ GB` RAM (`Mathlib` / `Init` caches) exceeding uncached cold browser budgets.
- **Out of scope:** Multi-day CI runners, production batch builds, and trusted local workstation tooling (though `cargo-anneal`'s `sandbox.rs` design bridges local and multi-tenant threat models when verifying untrusted proof packages).

### 5. Client-Side WASM vs Sandboxed Server & Hybrid Pre-Captured MIR + Kernel Replay

Comparing full WASM execution vs hardened server sandboxes reveals a sharp capability boundary:

1. **Arbitrary Rust MIR capture (`rustc-capture` / `cargo-anneal`) stays server-side:** `rustc` + LLVM + Miri/proc-macros lack Tier 1/2 `wasm32` host-compiler builds, and Rust procedural macros / `build.rs` require host shared-library execution (`dlopen`/ABI). Putting arbitrary Rust compilation client-side is `unsupported` without building and shipping an entire LLVM/`rustc` Emscripten fork (multi-hundred-MB payload + slow browser codegen).
2. **"Break a Proof / Catch a Cheat" and Proof Replay Move Cleanly to Client-Side WASM (`[real measurement]`):**
   When challenges start from **pre-captured `MIR -> Captured.lean` artifacts** (verified or deliberately buggy/adversarial exports generated once by CI/server), client-side Web Workers can run **zero-TCB proof checking** at `<5 s` with zero per-user server CPU:
   - **`nanoda_bin` (`ammkrn/nanoda_lib@0da9f98f`, `v0.4.32`):** Pure-Rust dependencies (`indexmap`, `rustc-hash`, `num-bigint`, `num-integer`, `num-traits`, `semver`, `serde_json`, `serde`; zero C FFI). Verified directly: `cargo +nightly-2026-01-25 build --bin nanoda_bin --target wasm32-wasip1 --release` succeeded (`rc=0`), producing **`914,651 B` raw (`271,683 B` gzip)** (`[real measurement]`), and `wasm32-unknown-unknown` library `cargo check` passed (`rc=0`). On `con-ron`'s `ind_mutual_sort_defeq.ndjson` (`7,675 B`, `133` lines), 1-thread native `nanoda_bin` finished in **`3.95 ms` at `3,104 KiB` (`3.0 MiB`) max RSS**.
     - *Observed WASM runtime caveat (`src/tc.rs:142-177`):* `ExportFile::check_all_declars` unconditionally enters `std::thread::scope` and `std::thread::Builder::spawn_scoped` even when `num_threads == 1`, which panics on non-threaded `wasm32-unknown-unknown` / `wasm32-wasip1` unless `check_all_declars_serial()` (`pub(crate)`) is exposed or gated with `#[cfg(not(target_arch = "wasm32"))]`.
   - **`con-ron-core` (`leanprover/con-ron@6fd8fee4`):** Verified kernel core with **zero `[dependencies]`** (`Cargo.toml` — uses only `std::sync::Arc` and `std`). Verified directly: `con-ron-core` compiled to `libcon_ron_core.rlib` on both `wasm32-unknown-unknown` (`13.5 MB`) and `wasm32-wasip1` (`13.3 MB`), and a minimal `parse_bytes` `cdylib` linked on `wasm32-unknown-unknown` at **`284,828 B` raw (`69,747 B` gzip)** (`[real measurement]`). Native `con-ron --jobs=1` checked `ind_mutual_sort_defeq.ndjson` in **`73.83 ms` (`61,664 KiB` max RSS)** because startup interns the embedded `con-ron-pins/2` dataset; `con-ron`'s native driver also allocates `1 GiB` worker stacks (`driver.rs:105-220`) for non-arena recursion, requiring larger WASM `-z stack-size` or iterative decode paths if deep legacy `Expr` pin walks occur.
   - **Mandatory export-pruning invariant (`[real measurement]`):** Running `leanexport` (`v4.35.0`) on a 2-line file with `import Init.Prelude` produced **`330 MiB` of transitive NDJSON** (`SampleInitPrelude.ndjson`, causing `con-ron --jobs=1` to run `>52 s` before cancellation). Unpruned `Init` NDJSON exports break `<5 s` latency and bloat WASM linear memory. Therefore, client-side `<5 s` WASM kernel replay MUST ship either (a) cone-pruned standalone NDJSON artifacts containing only challenge-reachable declarations (or `prelude`-scoped proofs), or (b) a pre-interned immutable `Init` snapshot loaded once into the persistent tier with small delta exports (`<1 MB`).

### 6. Adversarial Threat Model & Concrete Mitigations

| Attack Vector | Vulnerable Surface | Observed Primary Evidence | Required Control |
| --- | --- | --- | --- |
| **Fork bombs / PID exhaustion** | Unbounded process spawning via Rust tests/macros or Lean `#eval IO.Process.output` | `bwrap --unshare-all` without seccomp still allowed `#eval IO.Process.output { cmd := "sh" ... }` (`rc=0`, `[real measurement]`); `lean4web` has no `pids.max`; `ce` sets `pids=72` (compile) / `14` (exec); `rust-playground` sets `--pids-limit 512`. | Cgroup v2 `pids.max` (`16–64`) + seccomp syscall allowlist blocking `clone`/`fork`/`execve` after child launch (or `PR_SET_NO_NEW_PRIVS` + PGID `kill(-pgid, SIGKILL)`, as in `cargo-anneal/src/sandbox.rs`). |
| **Memory exhaustion / OOM** | Lean elaboration (`Init`/`Mathlib` caches ~0.8+ GB), Z3 quantifier/SAT blowup (`alloy-api` >30 GB RSS), gigantic completion payloads | `ulimit -m 65536` (`RLIMIT_RSS`) permitted a `128 MiB` `bytearray` (`rc=0`, `[real measurement]`), while `prlimit --as=64 MiB` trapped `MemoryError`; `#check Nat.` returned `235,318 B` JSON. | Enforce cgroup v2 `memory.max` + `memory.swap.max=0` (avoid `RLIMIT_AS` conflicts with allocator/Lean virtual reservations); `--oom-score-adj 1000`; slice LSP completions (`<=300` items); isolate browser WASM workers with memory bounds and watchdog `worker.terminate()`. |
| **Lean elaborator meta/IO escapes** | `#eval`, custom `elab`/`macro`, `IO.FS.readFile`, `IO.Process`, `import Lean`/`Lake`, `.olean` `CompactedRegion` memory corruption | Unsandboxed `lean --stdin` read `/etc/passwd` (`5,862 B`, `rc=0`, `[real measurement]`); `bwrap` minimal bind mounts blocked `/etc/passwd` (`rc=1`). | Minimal `--ro-bind` root + `--clearenv` + seccomp-BPF + `--unshare-user --disable-userns`; parse headers with `TrustedBoundary.lean` `"headers"` to forbid `Lean.*`/`Lake.*`/arbitrary `.olean` loads; decouple proof *acceptance* from elaboration via `leanexport` NDJSON + `nanoda`/`con-ron` WASM replay. |
| **Rust `proc-macro` / `build.rs` RCE** | Compile-time arbitrary host execution via `rustc` plugin ABI (`proc-macro` dylibs, `build.rs` binaries) | `rust-playground` explicitly executes `build.rs` and `proc-macro` inside `--net none --cap-drop=ALL` containers (`coordinator.rs:344, 435`); `flux-playground` has zero sandbox. | Never run `cargo`/MIR capture on untrusted crates outside `--net none` Tier-1 `bwrap` + seccomp or Firecracker/gVisor microVMs; reject/strip `proc-macro` and `build.rs` in fast unprivileged public modes when unneeded. |
| **CPU / quota / WS abuse** | SAT/SMT timeouts (`z3`, `dafny`, `verus`), Lean kernel reduction DoS (`decide`), unthrottled WebSocket `lake serve` spawns | `lean4web` allows `ulimit -t 3600` + unlimited WS sessions; `rust-playground` enforces `5s` WS handshake, `10s` container soft timeout, `60s` idle, `25` coordinators, `640 KiB` output cap. | Strict per-tenant token bucket + IP/session concurrency cap (`<=1–2` active sessions per client, `<30 s` wall/CPU timeout, `<1 MiB` stdout/stderr cap); for WASM, run in disposable Web Worker with `<5 s` timeout calling `worker.terminate()`. |
| **Supply-chain & cache/snapshot poisoning** | Shared `top-crates` `target/`, prebuilt `.olean` volumes, browser `--incr-header-save` snapshots, `LD_PRELOAD` / symlink escapes | `fm-playground`'s `run_in_docker_exec` shares one `dafny-worker` container across users (`/tmp/dafny_<id>`); `cargo-anneal` rejects `LD_*`/`DYLD_*` env vars, `..`, and symlinks (`sandbox.rs:171-395`). | Immutable `--ro-bind` / read-only squashfs/overlay base images (per-session ephemeral `--tmpfs /tmp`), zero cross-tenant `/tmp` sharing, reject `LD_*`/`DYLD_*`, verify `.wasm`/snapshot Subresource Integrity (`SRI`) / SHA-256 hashes (`CompactedRegion` and `--incr-header-save` snapshots are opaque binary heaps, so prefer deterministic NDJSON cones when untrusted). |

  - Server-side sandbox code of `https://hax-playground.cryspen.com` (only client `docs/javascripts/hax_playground.js` is in `cryspen/hax@0d2f66ed`).
  - Operational Ansible/Kubernetes secrets or reverse-proxy rules on live production hosts for `play.rust-lang.org` and `live.lean-lang.org` beyond checked-in systemd/Docker/PM2/nginx/bwrap manifests.
  - Compiler/tool internals of external Z3 (`C++`) and Boogie (`C#`) solvers unrelated to playground containment.
- **`unknown`:**
  - Actual browser V8/SpiderMonkey JIT execution time of `nanoda_bin.wasm` (`wasm32-wasip1`) and `con-ron-core` `wasm32-unknown-unknown` WASM on large multi-megabyte cones (`node`, `wasmtime`, and headless browsers were not installed on the test host, so compilation, binary sizing, and 1-thread native runs were directly measured while browser VM execution latency remains unmeasured).
  - Concurrent P99 tail latency of `rust-playground` / `lean4web` under production DDoS traffic spikes.
- **`unsupported`:**
  - Pure client-side browser compilation and MIR capture of arbitrary Rust crates with `rustc` + LLVM + `proc-macro`/`build.rs` (no Tier 1/2 `wasm32` `rustc` compiler host toolchain exists in Rust; server-side sandboxed capture or pre-captured challenges are required).
  - Running `nanoda_lib`'s unmodified `ExportFile::check_all_declars` in single-threaded `wasm32` without a `wasm32` bypass or `pub check_all_declars_serial()` (`src/tc.rs:155-177` invokes `std::thread::Builder::spawn_scoped` even for `num_threads == 1`).
- **`known not to apply`:**
  - `ulimit -m` (`RLIMIT_RSS`) as a multi-tenant memory limit on modern Linux kernels (`bubblewrap.sh:4` comment verified directly by allocating `128 MiB` under `ulimit -m 65536`).
  - `nsjail`'s example `seccomp` policy on multilib Compiler Explorer toolchains without arch filtering (`user-execution.cfg:234-237` documents it commented out due to `kafel` 32-bit compat syscall mismatch).
  - Live `docker`, `nsjail`, `runsc` (gVisor), and `firecracker` execution measurements on this host (`shutil.which` returned `null` for all four binaries; conclusions on those runtimes come strictly from source config/code inspection).
