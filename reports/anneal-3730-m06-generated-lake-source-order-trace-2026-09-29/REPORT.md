# M06: Lake trace and artifact response to a generated-source provenance change

Observed 2026-09-29 using the pinned local Lean 4.30.0-rc2, Lake 5.0.0-src+3dc1a08, and cached Aeneas Lean backend. This is executed component evidence for #3730 M06 and #3731 I100/I142. It extends [R21](../anneal-3730-lake-plugin-combined-family-mix-2026-09-29/REPORT.md)'s artifact-family inventory and [R43](../anneal-3730-charon-shortname-aeneas-impact-2026-09-29/REPORT.md)'s byte-identical generated-source replay with a **byte-different, real Aeneas-generated** module pair from the [cross-layer comparator mutants](../anneal-3730-cross-layer-comparator-mutants-2026-09-29/REPORT.md).

## Question and controls

The hypothesis was that Lake can replay a generated multi-module graph when source bytes are unchanged, including an mtime-only touch, and will rebuild the affected module and its dependents when generated bytes change. A no-op or mtime-only local `Built` event, or an unchanged trace/olean after the byte change, would have falsified the respective part of that hypothesis. The observation informs a possible future workaround review; no Anneal workaround was selected for deletion.

The retained `base` and `reorder` outputs contain `Source.Types`, `Source.Funs`, and `Source`, generated from the comparator's Rust declaration-reorder control. `Source/Types.lean` and `Source.lean` are byte-identical across variants. `Source/Funs.lean` differs only in three `Source:` doc-comment lines; the executable `def` text and order are identical. **This is not an isolated declaration-order mutation:** those comments also change the Rust source pathname (`base/source.rs` versus `reorder/source.rs`) and line ranges. This probe establishes a response to those actual generated bytes, not which of their pathname or line-range components caused it.

Each private Lake project adds `Consumer.lean`, which imports `Source` and checks three selected equalities for `inc`, `twice`, and `choose` with `rfl`. The package uses the already cached Aeneas backend/Mathlib dependency closure through a path dependency and cached package symlink; `LAKE_NO_NET=1` was set. Nine `lake build -v` calls ran sequentially, with `LEAN_NUM_THREADS=1` and no install or network fetch. The same-path sequence was base, no write, mtime-only touch of `Source/Funs.lean`, reordered source copy, no write, restored base copy, no write. Two additional projects built base and reorder at fresh paths. The full Lake graph contained 1,686 jobs, of which four local modules are inventoried here.

## Observations

| Run | Wall time | Local module result |
| --- | ---: | --- |
| Fresh base | 73.60 s | All four `Built` |
| Fresh reorder | 25.21 s | All four `Built` |
| Same path base | 61.41 s | All four `Built` |
| Same path no write | 5.63 s | All four `Replayed` |
| Same path mtime-only | 4.30 s | All four `Replayed` |
| Same path reorder | 28.15 s | `Source.Types` `Replayed`; other three `Built` |
| Same path reorder no write | 4.14 s | All four `Replayed` |
| Same path restore base | 21.17 s | `Source.Types` `Replayed`; other three `Built` |
| Same path restore no write | 3.67 s | All four `Replayed` |

Each run's local `.lake/build` inventory has 32 regular files: 12 `.hash`, and four each of `.json` setup, `.c`, `.trace`, `.olean`, and `.ilean`. The no-write and mtime-only calls changed no local build-file SHA-256 or mtime; the mtime-only call changed only the source file's mtime. On the same-path reorder, `Source/Funs.olean`, its `.hash`, and the `Source.Funs`, `Source`, and `Consumer` traces changed bytes, along with `Source/Funs.lean` itself. The local `.ilean` and `.c` bytes remained equal, though some output mtimes advanced. The restored-base build returned all 32 local build-file hashes to their original base values; 27 file mtimes still differed. Both post-change no-write calls replayed without local file hash or mtime changes.

Fresh-base versus same-path-base, and fresh-reorder versus same-path-reorder, had equal `.olean`, `.ilean`, and `.c` bytes for this graph. Four `.trace` and three setup `.json` files differed across paths. This is an observed file-family distinction for this particular graph, not a general path-invariance guarantee; R43 found a path-bearing generated external-template `.olean` in another graph. All nine builds exited 0, so the selected `Consumer` equalities were accepted each time. That is an elaboration check for three values, not semantic equivalence of all generated functions.

The measured wall times describe sequential calls on this host with a warmed dependency cache. They do not establish a speedup, a production workload cost, or an adoption threshold. In particular, the first fresh and same-path builds were much slower than later builds, so a matched performance comparison would require replicated runs and controlled cache state.

## Retained evidence and replay

`support/fixture/` retains the exact real generated Lean variants. `support/results.json` records pinned tool and dependency hashes, nine run durations, local job lines, file-level SHA-256/size/mtime inventories, and log hashes. `support/logs/*.gz` contains the full stdout/stderr streams; `support/work.tar.gz` retains the three final private projects and all local artifacts, with their external cached-package symlinks removed. `support/probe.py` is the run recipe. `support/check.py` verifies fixture and log bytes, all nine build statuses, exact artifact-family counts, expected no-op/mtime and reorder/restore deltas, and the archived final bytes. Run `python3 support/check.py` from this report directory for an offline evidence check.

To rerun Lake, copy this report directory, remove the **copied** `support/logs` directory, then run `python3 support/probe.py` in the copy and `python3 support/check.py`. The runner requires the same local tool paths and at least 5 GiB free disk; its per-build timeout is 90 seconds. It overwrites the copied `results.json` and `work.tar.gz`, creates copied logs, and retains only an archive of the generated work after completion. No package manager operation is required.

## Scope and residuals

- **M06/I100:** This fixture supports treating identical generated source bytes and mtime-only touches as replayable under this pinned Lake graph. A real generated comment/provenance byte change rebuilt the affected module and downstream modules. Deleting or normalizing any particular workaround still requires identifying that workaround, its intended identity contract, relevant artifact families (including native/plugin artifacts where applicable), and a compatible-revision regression set. The present graph has `.c` but no native plugin product.
- **I142:** The probe supplies local build/replay timings and exact invalidation behavior. A choice among Anneal reuse, fine invalidation, projection, broker, or history approaches still needs implemented alternatives and matched representative workloads; these data do not measure their adoption benefit.
- **I158 and integration:** Only one pinned Lean/Lake/backend tuple and one local generated graph were exercised. There is no cross-version upgrade oracle, Anneal generator or scheduler, editor/server state, shared cache writer, or power-loss/concurrency claim. Source comment equality would not itself prove source-level claim equivalence.
