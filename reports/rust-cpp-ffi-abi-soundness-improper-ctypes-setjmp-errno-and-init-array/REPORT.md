# Rust and C/C++ FFI Soundness Beyond Scalar ABIs: `improper_ctypes` Blind Spots, C++ Object/Exception/Constructor ABIs, `setjmp`/`errno`/TLS/Variadics, and `.o`-Level TBAA Elimination

## Summary

Sound cross-language verification between Rust and C/C++ cannot stop at scalar and aggregate C calling conventions. Direct source audits of `rustc`, Clang, `cxx`, `rust-bindgen`, and `glibc`, paired with live `rustc` (`1.98.0-nightly`, `1.99.1`, `1.102.0-nightly`) and `gcc`/`g++ 15.2.0` reproducers (`support/`), establish five load-bearing FFI soundness surfaces:

1. **`rustc`'s `improper_ctypes` / `improper_ctypes_definitions` lints are heuristic and fail open across 11 distinct unsoundness classes (`support/improper_ctypes_results.json`):**
   - **Zero-sized and empty structs:** `#[repr(C)] struct Empty {}` triggers a lint, but `#[repr(C)] struct OnlyUnit(())`, `#[repr(C)] struct OnlyZeroArr([u8; 0])`, `#[repr(C)] struct WithZeroArr { a: u32, z: [u8; 0], b: u32 }`, and `#[repr(transparent)] struct TAlignZst([u32; 0])` are all accepted silently. Empty structs remain a GNU C extension (`gcc -std=c23 -Wpedantic` warns) with size `0`, whereas ISO C++ gives empty members size `1` (unless `[[no_unique_address]]` is applied), causing live silent field corruption (`0x55667788` read as `0xdb49bd40`) when Rust passes `WithEmpty` to `g++ 15.2.0`.
   - **Value-validity and discriminant traps:** `bool`, `#[repr(C)]` enums, `&T`, `&mut T`, `NonNull<T>`, and `NonZero<T>` pass with zero warnings. Returning `2u8` from C as Rust `bool` under `rustc 1.99.1 -C opt-level=3` yields `classify_bool(b) == 2` and `(!b) as u8 == 3` (violating LLVM `range(i8 0, 2)`), and returning `99` into a 2-variant `#[repr(C)] enum` silently misclassifies it as variant `1`.
   - **Uninhabited types, unguaranteed niches, and `Box` asymmetry:** `!` (in arg/field positions without feature gate on `1.102.0-nightly`) and `core::convert::Infallible` are accepted silently in arguments, returns, and structs. `repr_nullable_ptr` accepts *any* user-defined 2-variant `#[repr(Rust)]` enum wrapping a non-null type (unguaranteed by the Reference) and accepts `Option<Box<u32>>` in `extern "C"` declarations even while rejecting bare `Box<u32>`.
   - **Declaration/definition/generic/variadic/recursion-limit fail-open gaps:** `*const String`, `&String`, and `Box<String>` are accepted silently in `extern "C" fn` definitions and inside callback `extern "C" fn(...)` pointers; generic `pub extern "C" fn<T>(x: T)` is unchecked even when instantiated with `String`; C-variadic call sites reject only `{f32, i8, i16, u8, u16, bool, FnDef}` (`E0617`) while silently accepting `String`, `char`, tuples, and `#[repr(Rust)]` structs; and starting in `rustc 1.99.1`, exceeding `recursion_limit` in `ImproperCTypesVisitor::visit_type` fails open (`return FfiSafe`).
2. **C++ ABI semantics violate Rust's C-ABI and bitwise-move assumptions (`support/cpp_abi_results.json`):**
   - Under Itanium C++ ABI §3.1.1, any class with a non-trivial copy constructor, move constructor, or destructor (or all copy/move constructors deleted)—even an 8-byte struct (`sizeof == 8`)—is passed and returned by **invisible reference** (`%rsi` input pointer + `%rdi` hidden `sret`). Calling such a C++ function from Rust `extern "C"` passes the value `0xdeadbeefcafebabe` as the C++ parameter's *address* (`&t`), causing immediate `SIGSEGV`. Crucially, a class with a trivial move constructor and trivial destructor but a non-trivial copy constructor satisfies `cxx`'s default `rust::IsRelocatable<T>` yet is *still* passed indirectly under Itanium §3.1.1 (safe in `cxx` only because `needs_indirect_abi` passes extern C++ types by pointer across its generated glue). Furthermore, `g++ 15.2.0` ignores `[[clang::trivial_abi]]`, creating a direct Clang-vs-GCC ABI break.
   - Moving a GNU `libstdc++` SSO `std::string` (`sizeof == 32`, interior pointer at offset `+16`) via Rust bitwise `memcpy` leaves `_M_p` dangling into the old stack frame (`corrupted_bytes_read = "XXXXX"`).
   - Itanium member-function pointers are 16-byte `{ptr, adj}` pairs (virtual bit in `ptr & 1`, `adj` for multiple-inheritance `this`-shift), whereas MSVC member-function pointers vary in size (`8`/`12`/`16`/`24` B on x64) by class inheritance model; Itanium null data-member pointers are encoded as **`-1`**, not all-zero bytes.
   - C++ `.init_array` global constructors execute **before Rust `main()`** (mutating shared globals from `0` to `42` prior to Rust entry and exhibiting link-order Static Initialization Order Fiasco: `100` vs `0`), function-local statics invoke `__cxa_guard_acquire`/`release`, and `__cxa_atexit`/`__dso_handle` destructors run **after Rust `main()` returns**.
   - Live `g++ 15.2.0` + `rustc 1.99.1` tests confirm all six cross-language exception outcomes: C++ `throw` through Rust `extern "C-unwind"` runs Rust `Drop` and is caught by C++; Rust `catch_unwind` aborts (`SIGABRT`) on foreign C++ exceptions; C++ `catch (...) { throw; }` preserves Rust panics while swallowing aborts via `__rust_drop_panic`; C++ `noexcept` calls `std::terminate`; and C++ `throw` across `extern "C"` silently skips Rust `Drop` (`rust_drops == 0`, live UB).
3. **`rust-bindgen` and `cxx` leave distinct, non-eliminable soundness boundaries:** `bindgen` generates opaque blobs for complex C++ types, ignores Itanium/MSVC non-trivial-for-calls ABI rules, emits `#[repr(C)]` structs/enums/bitfield units without aliasing, lifetime, or discriminant-validity proofs, and cannot catch C++ exceptions. `cxx` statically checks shared layout, `IsRelocatable`, signature types, and `Pin<&mut T>` non-relocation, and catches `std::exception` via a `noexcept` wrapper (calling `std::terminate` on non-`std::exception` throws!), but cannot verify unsafe `ExternType` impls, C++ interior aliasing/lifetime escapes, `const_cast` on `&T`, or `.init_array` side effects.
4. **Non-local control flow, ambient TLS/`errno`, and silent `rust-lld` `STT_TLS` corruption (`support/runtime_and_tbaa_results.json`):**
   - `longjmp` across a Rust frame bypasses `Drop` (`rust_drops == 0`), violates MiniRust/Tree Borrows call-protector exit invariants, and restores `PTR_MANGLE`'d `%rsp`/`%rbp`/`%rip` from glibc's 200-byte `jmp_buf`. Rust removed `#[ffi_returns_twice]` in `1.78.0`, leaving no stable or unstable `returns_twice` attribute; verifying a compiled C `.o` invoking `longjmp` must track saved `jmp_buf` machine state or fail closed.
   - `errno` (`__errno_location` via IE TLS) and C `__thread` statics are ambient per-OS-thread channels: live reproducers show an unsaved POSIX `SIGUSR1` handler clobbering `errno` (`11 -> 2`) and an async `Future` migrating across two worker threads observing the new thread's `errno` (`22`) and `__thread` value (`0xbbbb2002`).
   - **Silent `rust-lld` `STT_TLS` link bug:** Declaring C's `__thread uint64_t c_tls_var` as a plain Rust `extern "C" { static c_tls_var: u64; }` is rejected by GNU `ld.bfd` (`TLS definition ... mismatches non-TLS reference`), but **`rust-lld` (LLD `23.1.1`, default linker for `rustc 1.99.1`) links silently with exit code `0`**, resolving the symbol to `pie_base + 0x30` so Rust silently reads the binary's own ELF64 header bytes (`0x0038004000000000`)!
   - `c_variadic` (`VaList<'a>`, `VaList::next_arg`) stabilized in Rust `1.99.0`, enforcing `VaArgSafe` (blocking unpromoted `f32`/`i8`/`u8`/`i16`/`u16`/`bool` and all structs), while mismatched variadic calls (passing `i32` where C reads `double`) read stale/uninitialized `%xmm0` register-save-area memory (`0x4045400000000000`).
5. **Verifying C at emitted `.o` machine-code level eliminates C TBAA and `restrict` from the TCB (`support/runtime_and_tbaa_results.json`):** On `c_tbaa_write_read(uint32_t *a, float *b)` and `c_restrict_write_read(uint32_t *restrict a, uint32_t *restrict b)` called with aliased pointers from Rust, `gcc 15.2.0 -O2` materializes the UB assumption directly into `.o` instructions (`mov $0x1, %eax` / `mov $0xa, %eax`, returning `1`/`10` while memory holds `0x40000000`/`20`; `-fno-strict-aliasing` disables TBAA but *not* `restrict`). Verifying the emitted `.o` directly proves properties of the actual executed instructions without formalizing C effective types, `restrict`, or trusting `gcc`/`clang`—whereas source-level C verification and cross-language LTO (`-Clinker-plugin-lto`) must still model C aliasing/TBAA rules and compiler soundness.

**Additional `improper_ctypes` nuances verified:**
- **`extern type` (RFC 1861, `#![feature(extern_types)]`) vs. Nomicon opaque struct:** Both `ty::Foreign` (`L941`, behind `*mut`/`&`) and `#[repr(C)] struct Opaque { _data: [u8; 0], _marker: PhantomData<(*mut u8, PhantomPinned)> }` pass `improper_ctypes` silently. However, `&Opaque` using `[u8; 0]` asserts `size_of_val == 0` (making provenance/dereferenceable spans 0 bytes in LLVM and permitting ZST pointer assumptions), whereas `extern type` has unknown size (`!Sized`, thin pointer, no `size_of_val`).
- **Flexible Array Members (FAMs):** C's `struct Fam { size_t len; uint8_t data[]; }` cannot be written as `*const FamSlice` (`data: [u8]`) across `extern "C"` (wide pointer; `improper_ctypes` rejects `[u8]` as *"slices have no C equivalent"*), whereas `data: [u8; 0]` passes silently as a thin pointer—requiring strict raw-pointer arithmetic (`addr_of!`) because constructing `&FamZero` restricts Rust/Tree Borrows provenance and LLVM `dereferenceable` extent to the 8-byte header alone, making indexing past `data[0]` UB.
- **`#[repr(simd)]` version delta:** With `#![feature(repr_simd, simd_ffi)]`, `#[repr(simd)] struct F32x4([f32; 4])` failed `improper_ctypes` in `1.98.0-nightly` (`!def.repr().c() && !def.repr().transparent()`) and passes silently in `1.102.0-nightly` (`!def.repr().simd()` added at `L681`).
- **`c_char` signedness and `c_long` width (`library/core/src/ffi/primitives.rs:40-151`):** `c_char` is `u8` on non-Windows/non-Apple `aarch64`, `arm`, `riscv*`, `powerpc*`, `s390x` (e.g., `aarch64-unknown-linux-gnu`), but `i8` on `x86_64`, Windows, and Apple targets (`aarch64-apple-darwin`). `c_long` is `i64` on 64-bit non-Windows (`LP64`) and `wasm32-linux`, but `i32` on 64-bit Windows (`LLP64`) and 32-bit targets. `improper_ctypes` accepts raw `i8`/`u8`/`i64` with zero portability diagnostics.

#### Live Reproducers: Empty Structs and Invalid `bool`/Enum Miscompilation

1. **Empty struct C vs. C++ vs. Rust (`support/improper_ctypes_results.json` → `live_empty_struct`):**
   - `gcc -std=c23 -Wpedantic` emits `warning: struct has no members [-Wpedantic]` on `struct Empty {}`, giving `sizeof(Empty) == 0`, `sizeof(WithEmpty) == 8`, `offsetof(b) == 4`; calling `c_read_ab(WithEmpty { a: 0x11223344, e: EmptyZst([]), b: 0x55667788 })` returns `0x1122334455667788`.
   - `g++ -std=c++23` gives `sizeof(Empty) == 1`, `sizeof(WithEmpty) == 12`, `offsetof(b) == 8` (reduced to `sizeof == 8, offsetof(b) == 4` only with C++20 `[[no_unique_address]]`). Calling `cpp_read_ab` from Rust with `-D improper-ctypes` compiles cleanly and returns **`0x11223344db49bd40`** (uninitialized garbage in place of `b`).
2. **Invalid `bool` and `#[repr(C)] enum` under `rustc 1.99.1 -C opt-level=3` (`live_invalid_bool_enum`):**
   - `rustc` emits `define noundef range(i8 0, 2) i8 @classify_bool(i1 noundef zeroext %b)` and `define noundef range(i32 10, 21) i32 @classify_color(i32 noundef range(i32 0, 2) %c)`.
   - When C returns `2u8` as `bool`, `match b { false => 0, true => 1 }` compiles to returning `%b` directly (`classified_bool == 2`, `b as u8 == 2`, `(!b) as u8 == 3`—both `b` and `!b` are non-zero!). When C returns `99u32` as `enum Color { Red = 0, Green = 1 }`, `classify_color` silently returns `20` (`Color::Green`).

### 2. C++ ABI Specifics (Itanium & MSVC) and `cxx` / `bindgen` Soundness Boundaries

`Basis: normative + source + execution + derived`

#### 2.1 Non-Trivial-for-Calls Passing, `[[clang::trivial_abi]]`, and Self-Referential Moves

Under Itanium C++ ABI §3.1.1 (`abi.html:298-315, 3044-3115`), a class is **non-trivial for the purposes of calls** if it has a non-trivial copy constructor, move constructor, or destructor, or if all copy and move constructors are deleted. Both parameters and return values of such classes are passed by **invisible reference** (caller allocates a temporary and passes its address; callee receives a hidden return-slot pointer in `%rdi`), regardless of size. Clang enforces the same `canPassInRegisters()` gate for both Itanium (`ItaniumCXXABI.cpp:76-78`) and Microsoft x64/ARM64 (`MicrosoftCXXABI.cpp:888-924`, where x86-32 uses `RAA_DirectInMemory` unless required alignment `> 4`).

Live `g++ 15.2.0 -O2` disassembly and Rust execution (`support/cpp_abi_results.json` → `nontrivial_calls`):

| 8-Byte C++ Type (`sizeof == 8`) | `is_trivially_move_constructible && is_trivially_destructible` | `g++ 15.2.0 -O2` Disassembly (`objdump -d`) | Machine Passing Convention |

- **Live ABI corruption / crash:** Calling `observe_nontriv_addr(FakeNonTriv { x: 0xDEAD_BEEF_CAFE_BABE })` from Rust (`-D improper-ctypes`, zero warnings) passes `0xdeadbeefcafebabe` in `%rdi`; C++ observes `&t == 0xdeadbeefcafebabe` as the parameter's address, and dereferencing `t.x` immediately crashes with **`SIGSEGV` (`returncode = -11`)**.
- **Clang vs. GCC `[[clang::trivial_abi]]` split:** Because Clang treats `[[clang::trivial_abi]]` as `canPassInRegisters() == true` (passing in `%rdi`/`%rax`) while `g++ 15.2.0` ignores the attribute and passes by invisible reference, mixing Clang- and GCC-compiled objects (or Rust wrappers assuming one convention) silently breaks binary compatibility.
- **Self-referential C++ objects vs. Rust bitwise moves (`sso_self_referential`):** GNU `libstdc++`'s `std::string` (`sizeof == 32`, `align == 8`) uses Small String Optimization with an interior pointer `_M_dataplus._M_p` pointing to `this + 16` (`_M_local_buf[16]`). Constructing `std::string("hello")` at stack slot `0x7ffd90707290` sets `data() == 0x7ffd907072a0` (`sso_interior_offset == 16`). Moving those 32 bytes bitwise to a heap `Box` at `0x56127c071230` (Rust's universal move semantics) leaves `data() == 0x7ffd907072a0` pointing into the dead stack slot; overwriting the old slot causes `moved.data()` to read **`"XXXXX"`**.

#### 2.2 Member Pointers, Multiple Inheritance, Vtables, and RTTI

Live `g++ 15.2.0` inspection (`support/cpp_abi_results.json` → `memptrs_vtables_mi`) corroborated against Itanium C++ ABI §2.3 (`abi.html:742-895`) and Clang `clang/lib/AST/MicrosoftCXXABI.cpp:221-327`:

- **Member-function pointers (MFPs):**
  - **Itanium x86-64:** Fixed `16` bytes (`struct { fnptr_t ptr; ptrdiff_t adj; }`). Non-virtual methods set `ptr = addr` (even, `ptr & 1 == 0`) and `adj = this_delta` (`0` for primary base `A`, `16` for secondary base `B` in `struct D : A, B`). Virtual methods set `ptr = 1 + vtable_byte_offset` (`0x11` → offset `16`, `0x19` → offset `24`, after the two destructor slots `[0, 8]`). (On 32-bit ARM, Thumb code uses `ptr & 1`, so the virtual flag moves to `adj & 1` with `adj` shifted left by 1.)
  - **Microsoft x64 (`clang/lib/AST/MicrosoftCXXABI.cpp:250-327`):** Variable size determined by `MSInheritanceModel` (`Single`: 1 ptr = **`8` B**; `Multiple`: 1 ptr + 1 int, aligned to 8 = **`16` B**; `Virtual`: 1 ptr + 2 ints = **`16` B**; `Unspecified` / forward-declared class: 1 ptr + 3 ints, aligned to 8 = **`24` B**; on x86-32: `4`/`8`/`12`/`16` B). Virtual MFPs point to a generated vcall thunk rather than encoding a vtable byte offset.
- **Data-member pointers (DMPs) — non-zero null representation:** Under Itanium §2.3.1 (`abi.html:757-764`), `sizeof(uint64_t D::*) == 8`, and a **null data-member pointer is `-1` (`0xffffffffffffffff`)**, not `0` (`field_a` at offset `8` has bits `8`; a field at offset `0` has bits `0`). Zero-filling (`MaybeUninit::zeroed()` / `memset(0)`) a C++ DMP in Rust silently creates a valid offset-0 member pointer instead of null!
- **Multiple/virtual inheritance and vtables:** Casting `&d` (`D : A, B`) to `B*` shifts the `this` pointer by `+16` bytes (`mi_D_to_B_this_shift == 16`). At runtime, `vptr` sits at offset `0` of each polymorphic subobject; `vptr[-2]` holds `offset-to-top` (`0` for primary `A`-in-`D`, **`-16`** for secondary `B`-in-`D`), `vptr[-1]` holds the shared `std::type_info*` RTTI pointer, and in virtual inheritance (`struct VDer : virtual VBase`), `vptr[-3]` holds `vbase_offset` (`16`).

#### 2.3 `.init_array` Pre-`main` Execution, Static-Local Guards, `__cxa_atexit`, and SIOF

Linking two C++ translation units (`tu_a.o`, `tu_b.o`) into a Rust executable (`support/cpp_abi_results.json` → `init_array_siof_guards`) proves four runtime hazards that bypass Rust's entry-point model:

1. **Pre-`main` arbitrary execution (`.init_array`):** `tu_a.o` emits `.rela.init_array` entries that `ld.so` / CRT startup executes **before Rust `main()` (and before `std::rt::lang_start`)**. In our probe, `GlobalA::GlobalA()` mutates Rust's `#[unsafe(no_mangle)] pub static RUST_SHARED_GLOBAL: AtomicU32` from `0` to `42` before Rust executes a single instruction. Any verification model that assumes Rust `main()` starts in its declared static initial state is unsound whenever C/C++ objects with `.init_array` / `__attribute__((constructor))` are linked.
2. **Static Initialization Order Fiasco (SIOF):** Swapping only link order (`tu_a.o tu_b.o` vs `tu_b.o tu_a.o`) flips `.init_array` execution order: `GlobalB` reads `g_a.val == 100` in order A→B, but reads **`0`** (zero-initialized unconstructed storage) in order B→A.
3. **Post-`main` destruction (`__cxa_atexit` / `__dso_handle`):** `GlobalA`'s destructor is registered via `__cxa_atexit(dtor, &g_a, &__dso_handle)` (Itanium §3.3.5, `abi.html:4253-4284`) and runs **after Rust `main()` returns**, creating use-after-teardown hazards if destructors touch torn-down Rust TLS, allocators, or background threads still running during `exit()`.
4. **Function-local static guard variables (`__cxa_guard_acquire` / `__cxa_guard_release`):** `get_local_static()` emits an 8-byte guard variable (`abi.html:3687-3761`) checked via acquire-load on byte 0 and initialized under a global/per-guard mutex (`__cxa_guard_acquire` / `release` / `abort`), introducing hidden locking, futex syscalls, and deadlock on recursive initialization across FFI callbacks.

#### 2.4 Live Cross-Language C++ Exceptions vs. Rust Panics (`extern "C"` vs `extern "C-unwind"`)

Extending `rust-no-std-panic-abort-eh-personality-and-cross-crate-unwinding-abi-contracts` (which established `RUST_EXCEPTION_CLASS = "MOZ\0RUST"`, `CANARY`, and `PostCleanup` MIR lowering), live `g++ 15.2.0` + `rustc 1.99.1 -C panic=unwind -C opt-level=2` execution (`support/cpp_abi_results.json` → `cpp_exceptions_c_unwind`) verifies all six runtime boundaries:

| Scenario | Observed Exit / Signal | Observed Outcome & Mechanism |
| :--- | :---: | :--- |
| 1. C++ `throw std::runtime_error` → Rust `extern "C-unwind"` (`Drop` guard) → C++ `try/catch` | `0` | `cpp_caught_msg=cpp_boom`, **`rust_drops=1`**. Itanium two-phase unwind cleanly runs Rust landing pad and delivers original C++ exception. |
| 2. C++ `throw` → Rust `std::panic::catch_unwind` | **`SIGABRT` (`-6`)** | `fatal runtime error: Rust cannot catch foreign exceptions, aborting` (`exception_class` `"GNUCC++\0"` $\ne$ `"MOZ\0RUST"` in `panic_unwind/src/gcc.rs`). |
| 3. Rust `panic!` → C++ `try { ... } catch (...) { throw; }` (`CppGuard`) → outer Rust `catch_unwind` | `0` | `rust_caught_err=true`, **`cpp_drops=1`**. Rethrowing preserves `_Unwind_Exception` intact for Rust. |
| 4. Rust `panic!` → C++ `catch (...) {}` (swallowed) | **`SIGABRT` (`-6`)** | `fatal runtime error: Rust panics must be rethrown, aborting` (C++ calls `_Unwind_DeleteException`, invoking Rust's `exception_cleanup` → `__rust_drop_panic`). |
| 5. Rust `panic!` → C++ `noexcept` function | **`SIGABRT` (`-6`)** | `terminate called without an active exception` (`std::terminate`; libstdc++ reports no active C++ exception because the foreign `_Unwind_Exception` is not a `__cxa_exception`). |
| 6. C++ `throw` → Rust `extern "C"` (wrong ABI, `-O2`) → outer C++ `try/catch` | `0` (**Silent UB**) | `cpp_caught_msg=cpp_boom`, **`rust_drops=0`**. LLVM marked the call `nounwind` and omitted the Rust cleanup landing pad, silently skipping `RustGuard::drop`! |

**Windows MSVC C++ EH vs. SEH (`library/panic_unwind/src/seh.rs:1-298`):** On `*-pc-windows-msvc`, Rust does *not* implement a custom personality routine; it throws panics via `_CxxThrowException` (Windows exception code `0xE06D7363`) using personality `__CxxFrameHandler3` with a custom unmangled `_TypeDescriptor` named `"rust_panic\0"` (`seh.rs:125`), an `exception_cleanup` destructor calling `__rust_drop_panic` if C++ swallows it (`seh.rs:169-176`), and a `canary: &TYPE_DESCRIPTOR` check in `cleanup` (`seh.rs:283-297`) that calls `__rust_foreign_exception` when `catch_unwind`'s `catch (...)` intercepts a non-Rust C++ exception (`payload == null`) or a Rust panic from another DSO. Structured Exception Handling (SEH, `__C_specific_handler` / hardware faults like `STATUS_ACCESS_VIOLATION`) is distinct from C++ EH; asynchronous SEH exceptions interrupting Rust code remain explicitly undefined (`rfc_2945-c-unwind-abi.md:264-265`).

### 3. Non-Local Control Flow, Thread-Local State, and Runtime Contracts (`setjmp`/`longjmp`, `errno`, TLS, Variadics)

`Basis: normative + source + execution + derived`

#### 3.1 `setjmp`/`longjmp` Across Rust Frames

- **Normative status (`rust-lang/reference@c9cc3282`, `src/behavior-considered-undefined.md:64-68`; RFC 2945 `text/2945-c-unwind-abi.md:146-187, 241-252`; `rust-lang/rfcs#2625` [open issue]):**
  - The Rust Reference (`r[undefined.runtime]`) states that deallocating a Rust stack frame without executing destructors—explicitly citing C `longjmp`—violates Rust runtime assumptions and is Undefined Behavior.
  - RFC 2945 distinguishes **Plain Old Frames (POFs)** (dynamic frames with no pending `Drop` values and no active `catch_unwind`) from **non-POFs**: `longjmp` or forced unwinding across a non-POF is unconditionally UB, and even across POFs remains unspecified / UB today (tracked as open RFC issue `#2625`, not a merged RFC).
  - **`#[ffi_returns_twice]` removed in Rust 1.78.0 (`compiler/rustc_feature/src/removed.rs:155-157`, verified live in `support/runtime_and_tbaa_results.json`):** Attempting `#![feature(ffi_returns_twice)]` fails with `error[E0557]: feature has been removed`. Rust therefore has *no* mechanism to attach LLVM's `returns_twice` attribute to a `setjmp` declaration, meaning even calling `setjmp` directly in Rust invites compiler mis-spilling of locals across the second return.
- **Machine-level mechanism and live probe (`bminor/glibc@04e750e7`, `sysdeps/x86_64/__longjmp.S:38-148`; `support/runtime_and_tbaa_results.json` → `setjmp_longjmp`):**
  - On x86-64 glibc `2.43`, `sizeof(jmp_buf) == 200` bytes (8 callee-saved register slots `rbx, rbp, r12–r15, rsp, rip` plus signal mask). `setjmp`/`__longjmp` apply `PTR_MANGLE`/`PTR_DEMANGLE` (XOR with `%fs:0x30` pointer guard + `rol`/`ror $17`) to `rbp`, `rsp`, and `rip` (verified live: `saved_rsp_mangled_differs_from_stack == true`), adjust Intel CET shadow stacks via `rdsspq`/`rstorssp`/`incsspq` when active (`__longjmp.S:59-123`), restore `rbx, r12–r15, rsp, rbp`, and execute `jmpq *%rdx`.
  - Live execution (`c_run_with_setjmp` → `rust_frame_bypassed_by_longjmp` holding `LockGuard(&mut local)` → `c_trigger_longjmp(77)`): `setjmp` returns `77`, while **`rust_drops_executed == 0`**.
  - **Tree Borrows / MiniRust protector hazard (`derived`):** In Tree Borrows, passing `&mut T` or `&T` (without `UnsafeCell`) into a Rust function installs a `CallId` protector released only when that call returns or unwinds cleanly. When `longjmp` teleports `%rsp`/`%rip` out of the frame, neither `Drop` nor the function epilogue runs—leaving the `CallId` protector orphaned in any operational model that tracks call stacks, and violating LLVM's `noalias` scope guarantees on the bypassed frame.
  - **Verification consequence (`derived`):** Any verifier linking a compiled C `.o` (such as `libpng`, `libjpeg`, `Lua`, or `OpenSSL`) that calls `longjmp` or stores a `jmp_buf` cannot assume normal call-return discipline; it must either forbid non-local jumps (failing closed on `setjmp`/`longjmp`/`siglongjmp` imports or indirect jumps restoring `%rsp`), or explicitly model `jmp_buf` continuations alongside a POF + empty-protector-set invariant on every bypassed frame.

#### 3.2 `errno`, Signal Handlers, Async Task Migration, and the Silent `rust-lld` `STT_TLS` Bug

Building on `rust-thread-local-storage-models-and-runtime-contracts` (which covers target TLS instruction sequences), live `gcc 15.2.0` + `rustc 1.99.1` probes (`support/runtime_and_tbaa_results.json` → `errno_and_tls`) establish four FFI-level runtime contracts:

1. **`errno` as an unmodeled TLS channel (`bminor/glibc@04e750e7`, `csu/errno-loc.c:23-28`):** `c_get_errno` compiles to `call __errno_location@PLT; mov (%rax), %eax`, where `__errno_location()` returns the address of glibc's Initial-Exec TLS `__libc_errno`. Because `errno` appears in no C or Rust signature, any FFI call—or allocator/logging hook between an FFI call and `std::io::Error::last_os_error()`—can silently overwrite it.
2. **POSIX signal handlers clobbering `errno` (live execution):** Setting `errno = 11` (`EAGAIN`) and delivering `SIGUSR1` to a handler that invokes `open()` without saving/restoring `errno` leaves `errno == 2` (`ENOENT`) on return (`signal_after_bad_handler_errno = 2`), whereas saving and restoring `errno` inside the handler preserves `11` (`signal_after_good_handler_errno = 11`).
3. **Async task migration corrupting `errno` and C `__thread` TLS (live execution):** Running a Rust `Future` that sets `errno = 13` (`EACCES`) and C `__thread c_tls_var = 0xAAAA1001` before `.await` on Worker Thread A, then resuming Poll 2 on Worker Thread B (whose ambient state is `errno = 22` (`EINVAL`) and `c_tls_var = 0xBBBB2002`), observes **`errno = 22` and `c_tls_var = 0xbbbb2002`**. Any C library storing context in `errno` or `__thread` (e.g. OpenSSL error queues, database handles, thread-local arena allocators) is unsound to hold across `.await` points on work-stealing executors.
4. **Silent `rust-lld` `STT_TLS` vs. `STT_OBJECT` ELF-header corruption (live execution):**
   - C defines `__thread uint64_t c_tls_var = 0x1122334455667788ULL;` (`readelf -s`: `TLS GLOBAL DEFAULT .tdata`, offset `0x30`).
   - Because `#[thread_local]` on `extern "C"` statics remains unstable (`#![feature(thread_local)]`), declaring `unsafe extern "C" { static c_tls_var: u64; }` in stable Rust `1.99.1` emits an `STT_NOTYPE UND` symbol referenced via non-TLS `R_X86_64_GOTPCREL`.
   - **GNU `ld.bfd`** (`-fuse-ld=bfd`) fails closed (`exit = 1`): `c_tls_var: TLS definition in ... section .tdata mismatches non-TLS reference in ...`.
   - **`rust-lld` (LLD `23.1.1`, default linker for `rustc 1.99.1` on `x86_64-unknown-linux-gnu`)** **links silently with exit code `0`**, resolving `&raw const c_tls_var` to `pie_base + 0x30`, so reading `c_tls_var` at runtime silently returns **`0x0038004000000000`**—verified byte-for-byte identical to the binary's own ELF64 header bytes at file offset `0x30..0x38` (`e_ehsize = 0x0040`, `e_phentsize = 0x0038`)! By contrast, nightly `#![feature(thread_local)]` with `#[thread_local] static mut c_tls_var: u64` emits proper TLS relocations and reads/writes `0x1122334455667788` / `0xcafebabe12345678` cleanly.

#### 3.3 C Variadics (`...` / `VaList`): Rust 1.99 Stabilization, Promotions, and Type-Safety Gaps

Extending `bit-level-sub-eightbyte-packing-hfa-and-c-variadic-fnabi-refinement`:

- **Rust `1.99.0` stabilization (`library/core/src/ffi/va_list.rs:219-542`, verified live on `rustc 1.99.1`):** Defining `unsafe extern "C" fn(fixed: c_int, mut args: ...)` and reading via `VaList<'a>::next_arg<T: VaArgSafe>(&mut self) -> T`, `Clone` (`va_copy`), and `Drop` (`va_end`) are **stable** in `1.99.0+` (note: method renamed from RFC 2137's `arg` to `next_arg`). In our live C-to-Rust probe, C passes `(uint8_t)5, (int16_t)-7, (float)3.5f` (auto-promoted under C23 §6.5.2.2p6 to `int`, `int`, `double`) to stable Rust `rust_sum_promoted`, which reads `(c_int, c_int, c_double)` and returns `1.5`.
- **Asymmetric safety enforcement:**
  - **Callee side (`VaList::next_arg`):** Sealed `VaArgSafe` (`core/src/ffi/va_list.rs:313-485`) enforces platform-aware default-promotion rules at compile time (rejecting `f32`, `i8`, `u8`, `i16`, `u16`, `bool` on `x86_64`, while allowing `i16`/`u16` on `avr`/`msp430` and `f32` on `avr`!). Crucially, `VaArgSafe` covers *only* scalars and raw pointers (`i128`/`u128`/`f128` remain unstable) and **forbids all aggregates/structs** (`va_list.rs:307-309`).
  - **Caller side (`extern "C" { fn v(..., ...); }`):** `rustc_hir_typeck` (`checks.rs:512-542`) rejects unpromoted `{f32, i8, i16, u8, u16, bool}` and `FnDef` with hard error `E0617`, but **fails open (`_ => {}`)** on arbitrary non-FFI types (`String`, `char`, tuples, `#[repr(Rust)]` structs; Finding 1 #11) and performs zero format-string or arity checking.
  - **Live register-bank UB (`support/runtime_and_tbaa_results.json` → `c_variadics`):** Calling `c_va_read_double(1, 42_i32)` from Rust passes `42` in `%esi` with `%al = 0` (0 XMM registers used); C's `va_arg(ap, double)` reads the uninitialized/stale `reg_save_area` slot for `%xmm0`, returning **`0x4045400000000000` (`42.5`)**—literally leaking the stale floating-point argument from the *preceding* call!

### 4. C TBAA and `restrict` Miscompilation vs. the `.o` Machine-Code Verification Advantage

`Basis: normative + execution + derived`

Under ISO C23 N3220 §6.5p6–7 (effective types / strict aliasing) and §6.7.3.1 (`restrict`), accessing an object through an incompatible pointer type (`uint32_t *` vs `float *`) or aliasing two `restrict`-qualified pointers during mutation is Undefined Behavior. Compiling two 3-line C functions with `gcc 15.2.0` under `-O0`, `-O2 -fno-strict-aliasing`, and default `-O2`, and calling both from Rust with identical aliased pointers (`&raw mut word`), produces the following emitted `.o` machine code and live runtime outputs (`support/runtime_and_tbaa_results.json` → `tbaa_and_restrict`):

| C Function (Called from Rust with `a == b`) | `gcc 15.2.0 -O0` | `gcc 15.2.0 -O2 -fno-strict-aliasing` | `gcc 15.2.0 -O2` (Default) |
| :--- | :--- | :--- | :--- |
| `uint32_t c_tbaa_write_read(uint32_t *a, float *b) { *a = 1; *b = 2.0f; return *a; }` | Reloads `(%rdi)` → returns **`0x40000000`** (`mem = 0x40000000`) | `movl $1, (%rdi); movl $0x40000000, (%rsi); mov (%rdi), %eax; ret` → returns **`0x40000000`** | `movl $1, (%rdi); mov $0x1, %eax; movl $0x40000000, (%rsi); ret` → returns **`0x00000001`** (`mem = 0x40000000`) |
| `uint32_t c_restrict_write_read(uint32_t *restrict a, uint32_t *restrict b) { *a = 10; *b = 20; return *a; }` | Reloads `(%rdi)` → returns **`20`** (`mem = 20`) | `movl $0xa, (%rdi); mov $0xa, %eax; movl $0x14, (%rsi); ret` → returns **`10`** (`mem = 20`) | `movl $0xa, (%rdi); mov $0xa, %eax; movl $0x14, (%rsi); ret` → returns **`10`** (`mem = 20`) |

**What `.o` machine-code verification eliminates from the TCB vs. what remains required (`derived`):**

1. **Eliminated by verifying C/C++ at the emitted `.o` machine-code level:**
   - **C/C++ language semantics and UB zoo:** Effective types, TBAA (N3220 §6.5p7), `restrict` (§6.7.3.1), C++ object lifetime / `std::launder` / implicit-lifetime creation, integer promotions, sequence-point/evaluation-order UB, and preprocessor/header-macro resolution disappear completely from the TCB.
   - **The C/C++ compiler (`gcc`/`clang`) optimization pipeline:** In `c_tbaa_write_read` at `-O2`, the TBAA assumption is already materialized as concrete machine code (`mov $0x1, %eax` with zero reload). A machine-code verifier checking the `.o` against a specification permitting `a == b` will **immediately reject** the `-O2` object file (or succeed *only* under the explicit separation precondition `a != b`), catching the miscompilation without ever modeling TBAA or trusting `gcc`. Notice also that `-fno-strict-aliasing` does *not* protect against `restrict` miscompilation (`c_restrict_write_read` still returns `10`!).
2. **Still required at the `.o` machine-code verification boundary:**
   - **Target calling-convention and stack contracts:** `FnAbi`/`PassMode`, hidden `sret`/indirect pointers (including Itanium §3.1.1 non-trivial C++ parameters), callee-saved registers, 16-byte stack alignment, red zone, and post-codegen linker relaxations.
   - **Cross-boundary runtime metadata and global lifecycle:** `.init_array`/`.fini_array` pre-`main` constructors and `__cxa_atexit` destructors, `.eh_frame`/LSDA unwind tables (and `nounwind` obligation on `extern "C"`), `setjmp`/`longjmp` non-local stack exits, `errno`/TLS isolation (including `STT_TLS` symbol-type consistency across linkers), and ELF `STT_GNU_IFUNC` resolvers.
   - **Rust-side abstract memory relation $R$:** Proving that the bytes written by the `.o` into Rust-visible memory preserve Rust allocation liveness, pointer provenance, Tree Borrows alias permissions and call protectors, and typed bit-validity (`bool` $\in \{0, 1\}$, valid `char`/enum discriminants, non-null aligned references).
3. **Still required for C source-level verification or cross-language LTO (`-Clinker-plugin-lto`):**
   - **Source-level C verification** must model full C effective-type/TBAA/`restrict`/lifetime UB *and* keep `gcc`/`clang` in the TCB (or use a verified C compiler like CompCert, which has its own C subset and optimization limits).
   - **Cross-language LTO (`rustc -C linker-plugin-lto` + `clang -flto`)** dissolves the `.o` boundary by merging Rust and Clang LLVM bitcode before optimization: Clang's `!tbaa` metadata, `noalias`, and `noundef` attributes interact directly with Rust's `noalias`/`dereferenceable`/`range` attributes across inlined calls, reintroducing cross-language UB optimizations *after* any pre-LTO per-TU verification!

## Boundaries

- **`not examined`:**
  - Live execution on Windows MSVC (`cl.exe`, `__CxxFrameHandler3`/`4`, SEH `longjmp` forced unwinding, MSVC variable-size member pointers) and macOS (`arm64-apple-darwin`, `libc++` SSO layout, `_tlv_atexit`); MSVC C++ ABI and SEH findings rely on Clang (`4b8678a9`) and `rustc` (`panic_unwind/src/seh.rs`) primary source rather than Windows execution.
  - Cross-language LTO bitcode execution (`rustc -C linker-plugin-lto` + `clang -flto`), because `clang` was absent on the test host (`gcc`/`g++ 15.2.0` only).
  - C++20 modules, C++20 coroutines across FFI, C++26 P2786R13 trivial relocatability implementations, and `rust-bindgen` CLI execution on live C++ headers (audited via pinned `rust-bindgen@0d213bc3` source and docs).
- **`unknown`:**
  - Future Rust language semantics for `longjmp` / forced unwinding across Plain Old Frames (open RFC issue `#2625` and RFC 2945 unresolved questions) and future stabilization of `#[thread_local]` on `extern` statics or `extern type` (RFC 1861).
  - Whether `rust-lld`'s silent acceptance of `R_X86_64_GOTPCREL` against an `STT_TLS` symbol (`LLD 23.1.1`) also occurs on `aarch64-unknown-linux-gnu` or `mold`/`wild` linkers (tested live only on `x86_64-unknown-linux-gnu` comparing `rust-lld` vs GNU `ld.bfd`).
- **`known not to apply`:**
  - Passing `rustc -D improper-ctypes -D improper-ctypes-definitions` does **not** establish FFI layout, ABI, or soundness safety (11 counterexamples verified in Finding 1).
  - `cxx`'s default `IsRelocatable<T>` (`is_trivially_move_constructible && is_trivially_destructible`) does **not** imply Itanium C++ ABI triviality-for-calls (`CopyNonTriv` in Finding 2.1).
  - Passing `-fno-strict-aliasing` to GCC does **not** disable `restrict`-based aliasing miscompilation (Finding 4).
  - `#[ffi_returns_twice]` does **not** exist in Rust `1.78.0` and later (`E0557: feature has been removed`).
  - Zero-initializing (`memset(0)`) an Itanium C++ data-member pointer does **not** produce a null member pointer (null is `-1`, Finding 2.2).
- **`unsupported`:**
  - Stable Rust `1.99.1` does not support `#[thread_local]` on `extern "C"` statics, `extern type`, `f16`/`f128`, or `VaList::next_arg` for non-scalar aggregates/structs.
  - `g++ 15.2.0` does not support `[[clang::trivial_abi]]` (ignored with `-Wattributes`).
  - `rust-bindgen` does not support C++ exceptions, templates with specialization, or Itanium/MSVC non-trivial-for-calls passing conventions.
