# Configured capture, semantic reading and independent obligation completeness

## Summary

An independently selected program and domain can remain fixed while an untrusted producer proposes obligations and proofs. The checked pilot proves an exact safety-obligation theorem for a finite one-cell instruction language, including storage transitions and permitted panic. It also proves why omitted instructions and reordered failure boundaries matter. Rust elaboration/import, physical pointer/resource interpretation and the completeness of a real crate closure remain explicit interfaces.

## Applicability

This combines direct normative/source inspection at the listed Rust Reference, stdlib, Charon and Aeneas pins with an original Lean 4.31.0 experiment. The Rust fragment is deliberately small: scalar load/store, logical storage-live/dead and assertion operations on one modeled cell. `subject.rs` is an illustrative unsafe Rust subject; no Rust parser, compiler or MIR importer is proved for that original pilot. The later inlining/attachment appendices execute separately identified owned Rust subjects. The model’s resource flags need an independent source interpretation.

The report answers mechanism and interface questions for P056–P065, P072, P096 and P122. It distinguishes that research from implementing a complete Rust frontend. It does not enumerate every rustc internal elaboration pass or claim complete current crate coverage.

Logical acceptance below is conditional evidence. The parent independently inspected the Lean 4.31 kernel’s missing nested-inductive parameter validation reported in the official 4.32.2 soundness fix (#14576/PR14577). No exploit was executed here. Zero-axiom or successful checking output alone therefore supplies no arbitrary-producer checker-soundness guarantee; the forthcoming parent kernel report owns that source audit.

## Findings

### F1. A configured subject has semantic owners before MIR

Basis: normative + derived.

The pinned Reference distinguishes `cfg` attributes, which can remove source forms, from `cfg!`, which evaluates a Boolean literal. A false crate-level cfg retains preceding crate attributes while removing subsequent contents. [Conditional compilation, lines 354–367 and 439–451](https://github.com/rust-lang/reference/blob/2dafab96d919d6ab2884488e970bf95610ff83eb/src/conditional-compilation.md#L354).

Derived capture record: exact source/generated bytes, selected crate/roots, edition, compiler/sysroot/dependencies, target/ABI/features, effective flags/cfg, macro/build-script/procedural-macro outputs, annotation attachment identities and per-body origin. A source path or post-expansion name does not determine that subject by itself. Generated unsafe code needs a semantic owner and the same body/contract coverage as handwritten code. Specification attachment should bind the resolved declaration and instantiation, with an explicit expansion/alias correspondence; matching a name is insufficient.

An implementation can consume compiler-produced elaboration as a named premise, or certify parsing/elaboration separately. Either choice must identify which language judgments are trusted and what subsequent certificate actually assumes. Later model proofs cannot establish that the selected expansion or implementation was the intended one.

Charon’s driver sets MIR optimization level zero and preserves UB-relevant MIR, but also exposes an option replacing the borrow-check query. Its expansion and later-analysis hooks inspect compiler errors at different phases. [driver.rs:33–87, 367–394](https://github.com/AeneasVerif/charon/blob/cf02e3f228f97ee7be3a415be56989053063326d/charon/src/bin/charon-driver/driver.rs#L33). Compiler acceptance, whether a judgment actually ran, and a semantic ownership theorem must therefore be recorded separately; a selected early body is not itself checked borrow evidence.

### F2. Implicit operations, CTFE and persistent state are observable interfaces

Basis: normative + source; interface decomposition is derived.

The coercion chapter identifies specific coercion sites and reference/pointer, Deref/DerefMut, unsizing, function-item and closure conversions. [Coercions](https://github.com/rust-lang/reference/blob/2dafab96d919d6ab2884488e970bf95610ff83eb/src/type-coercions.md). Method lookup builds receiver candidates by repeated dereferencing, unsizing and insertion of shared/mutable borrows; the selected method follows a specified search order. [Method lookup, lines 21–38](https://github.com/rust-lang/reference/blob/2dafab96d919d6ab2884488e970bf95610ff83eb/src/expressions/method-call-expr.md#L21).

Required const evaluation can turn bounds/overflow failures into compilation errors. Const functions execute in the target environment, including target usize width. [Const evaluation, lines 23–26 and 277](https://github.com/rust-lang/reference/blob/2dafab96d919d6ab2884488e970bf95610ff83eb/src/const_eval.md#L23). A static denotes a persistent allocation; references/pointers identify that allocation and its initializer is evaluated at compile time. [Statics, lines 13–25](https://github.com/rust-lang/reference/blob/2dafab96d919d6ab2884488e970bf95610ff83eb/src/items/static-items.md#L13).

`LocalKey` documents lazy initialization, recursive-initializer hazards, panic on access during destruction, and process abort if its destructor panics. Destructor execution is best effort, with platform/reinitialization caveats. [Pinned thread-local contract, lines 27–33, 83–107 and 408–415](https://github.com/rust-lang/rust/blob/d8ef4f3fe7031514cbd7d056b7b058814987ecec/library/std/src/thread/local.rs#L27).

[Desugaring interfaces](https://github.com/rust-lang/rust/blob/d8ef4f3fe7031514cbd7d056b7b058814987ecec/compiler/rustc_ast_lowering/src/expr.rs#L1769), [Adjustment definitions](https://github.com/rust-lang/rust/blob/d8ef4f3fe7031514cbd7d056b7b058814987ecec/compiler/rustc_middle/src/ty/adjustment.rs#L11), [THIR construction](https://github.com/rust-lang/rust/blob/d8ef4f3fe7031514cbd7d056b7b058814987ecec/compiler/rustc_mir_build/src/thir/cx/expr.rs#L117), [MIR arithmetic](https://github.com/rust-lang/rust/blob/d8ef4f3fe7031514cbd7d056b7b058814987ecec/compiler/rustc_mir_build/src/builder/expr/as_rvalue.rs#L444), [bounds](https://github.com/rust-lang/rust/blob/d8ef4f3fe7031514cbd7d056b7b058814987ecec/compiler/rustc_mir_build/src/builder/expr/as_place.rs#L727), [cleanup](https://github.com/rust-lang/rust/blob/d8ef4f3fe7031514cbd7d056b7b058814987ecec/compiler/rustc_mir_build/src/builder/scope.rs#L37).

This is a source census for the architectural question, not a proof of those transformations. Source lifetime/region constraints, erased regions, runtime storage duration and ownership/resource validity need separate interpretations. Named exclusions from the census are an exhaustive HIR desugaring implementation, coroutine/async state-machine transformation, later drop elaboration, trait solver/monomorphization implementation and backend code generation. An admission grammar can conservatively reject those until their meaning and closure are supplied.

CTFE source facts: `Allocation` retains bytes, pointer provenance, initialization mask, alignment and mutability. `eval_in_interpreter` distinguishes static mutable-global access, loads the selected body/promoted item and reports interpretation errors. `intern_and_validate` interns then validates; final dangling/mutable/non-global/partial-pointer errors are distinct. Recursive validation selects Const/Promoted/Static modes. [Allocation:95–116](https://github.com/rust-lang/rust/blob/d8ef4f3fe7031514cbd7d056b7b058814987ecec/compiler/rustc_middle/src/mir/interpret/allocation.rs#L95), [evaluation:148–194,409–500](https://github.com/rust-lang/rust/blob/d8ef4f3fe7031514cbd7d056b7b058814987ecec/compiler/rustc_const_eval/src/const_eval/eval_queries.rs#L148), [interning:181–220](https://github.com/rust-lang/rust/blob/d8ef4f3fe7031514cbd7d056b7b058814987ecec/compiler/rustc_const_eval/src/interpret/intern.rs#L181), [validity:1654–1668](https://github.com/rust-lang/rust/blob/d8ef4f3fe7031514cbd7d056b7b058814987ecec/compiler/rustc_const_eval/src/interpret/validity.rs#L1654).

Derived CTFE certificate interface: bind configuration/target, instantiated definition and promoted/static identity, input global graph and selected semantic evaluation; conclude either the same classified failure or a related typed value plus reachable allocation graph. The graph relation preserves byte values where initialized, initialization mask, pointer target/offset/provenance under an injective allocation-ID renaming, alignment, mutability and persistent identity. It validates type invariants and disallows omitted reachable allocations; static roots must retain sharing/identity across accesses. A graph-normalization step needs its own relation rather than assuming raw allocation IDs are portable. Failure certificates need a finite prefix establishing the classified error; a mere missing value proves neither compile rejection nor runtime UB. Initializer-order/TLS state extends this interface with lifecycle transitions. This specifies certifying values, allocations, failures and initialization; implementing and proving the selected compiler/import connection remains future engineering.

### F3. The actual reader checks representation compatibility, not semantic adequacy

Basis: source + derived.

Charon `get_mir.rs:68–109` selects requested local representations when available, falls back when a requested local body was stolen, and separately uses nonlocal optimized/CTFE origins. [Exact source](https://github.com/AeneasVerif/charon/blob/cf02e3f228f97ee7be3a415be56989053063326d/charon/src/bin/charon-driver/translate/get_mir.rs#L68). This upstream behavior is distinct from a stricter local requested-promoted admission policy.

`export.rs:15–24` carries version, translated crate and partial-error status; `CharonVersion` checks version equality. [Envelope](https://github.com/AeneasVerif/charon/blob/cf02e3f228f97ee7be3a415be56989053063326d/charon/src/export.rs#L15). The ML convenience reader accepts the ordered two-field envelope or those fields plus an arbitrary third association entry, checks version, then returns only the translated crate. It does not retain/check the third error-status field. [OfJson.ml:21–53](https://github.com/AeneasVerif/charon/blob/cf02e3f228f97ee7be3a415be56989053063326d/charon-ml/src/OfJson.ml#L21). Aeneas’s two-line reader includes those Charon modules. [LlbcOfJson.ml](https://github.com/AeneasVerif/aeneas/blob/ca282ec2312a96f6a985a4d23a663690816d3f3e/src/llbc/LlbcOfJson.ml).

A semantic reader contract should export: successful complete decoding implies a well-formed AST, resolved identity/reference graph, retained admission metadata, and the same denotation as the independently captured subject under the selected schema/configuration. Version equality is one compatibility guard. It proves neither that the reader preserves semantics nor that the writer captured the right program. Unknown fields/constructors, invalid references, truncation, width conversions and partial extraction need explicit rules. No inversion/adequacy theorem for the full delegated reader was inspected here.

### F4. The original obligation generator has an exact checked endpoint

Basis: original source + execution.

`ObligationPilot.lean` defines one-cell State with liveness, initialization, read/write authority, alignment and numerical payload. Load/store guards include a u32-like range check. StorageLive/Dead change modeled liveness/initialization. An assertion failure produces panic; an invalid primitive produces UB. `run` stops at either outcome.

The logical generator recursively requires each primitive guard and continues with its next state; a permitted panic stops continuation obligations. Induction proves:

```text
generated_exact: generate operations state ↔ Safe(run operations state)
aggregate:
  proposed = independentlySelectedOriginal
  ∧ (∀ state, independentlySelectedDomain(state) → generate proposed state)
  ⇒ ∀ state, Domain(state) → Safe(run original state).
```

Safe permits returned states and panic, and excludes UB. No complete source-safety premise appears. This is obligation-generation soundness/completeness for the exact finite modeled language, rather than checking only a producer-selected roster or successful results.

`init_then_read` proves modeled safety of store(7);load for every entry state with the declared live/read/write/alignment rights, including initially uninitialized cells. Three checked controls show: an empty obligation list can hide an omitted invalid load; inserting StorageDead makes a formerly valid load invalid; an assertion before the load permits panic while reversing the order exposes UB. Each endpoint reports propext only, with no native computation assumption or accepted admission.

Initial ordinary tactic/elaboration failures are preserved separately. The final Lean process exits zero. Failed recovery declarations are not evidence of accepted proofs. `subject.rs` has no proved parser/capture or source-memory interpretation, so this pilot does not establish native Rust safety.

### F5. Complete semantic coverage is independent of heuristic obligation discovery

Basis: derived from the exact generator theorem and selected source interfaces.

For a real program, the consumer must select or check the original executable AST and initial domain independently. A producer may propose invariants, hints, a dependency graph or proof terms. Acceptance needs a completeness theorem that relates those objects to the original operations and all reachable calls, including generated helpers, dictionary/vtable targets, globals/TLS/initializers, destructors, callbacks and registered primitive meanings.

The pilot’s `proposed=original` premise makes omitted instructions material. In a larger system, a semantic equivalence witness can replace syntactic equality, but that witness must itself preserve first bad prefixes and the required outcomes. Source-to-AST adequacy, permitted-caller coverage, per-function/environment relations and checked model property remain separate conjuncts. Cycles need simultaneous finite-prefix or guarded reasoning; merely listing mutually assumed contracts is insufficient.

An operational service must bind that theorem to consumed bytes, exact dependencies, checking/assumption policy and complete stage status. The mathematical implication can be researched before such a service exists. Implementing the importer, semantic reader and closure checker is future engineering; the actual fixed-fragment generator pilot is completed evidence.

### F6. Actual inlining preserves a callee failure even when its value is unused

Basis: owned source + execution + derived correspondence obligation (P133).

The new `support/inline-control` subject uses `inline(always)` on a safe Rust callee: zero panics, other u8 inputs wrap-add one. Its caller discards the returned value and returns seven. Rust 1.99.0 (b940084d7, LLVM23.1.1), AArch64 macOS, opt-levels 0 and 3 each execute all 256 inputs: one intentional caught panic and 255 successful sevens. Emitted LLVM at both levels contains the zero comparison and panic branch inside the caller with no remaining callee call. At opt-level3 the internal return value itself is eliminated; the failure guard remains. This is an actual observed inlining instance, not a theorem about rustc.

`Inline.lean`, independently checked with Lean4.34.1@5045d0056413266e57c625dcd7c365b10e377c52, proves for every Byte that outcome-preserving inlining matches call-then-return, and proves that a result-only replacement disagrees at zero. The correct/counterexample endpoints use propext; UB/value and divergence/UB distinctions have no axioms. Initial ordinary tactic failure was rejected, not accepted evidence. Panic is permitted here and is not Rust UB; this complements rather than replaces the earlier UB-erasure and divergence controls. A pass certificate for real Rust still needs an adequate source/outcome interpretation and exact pass/input binding.

### F7. A semantic modular call cannot reuse mismatched callee evidence

Basis: owned source + execution (P134/T108).

`support/modular-control/Modular.lean` defines an executable selected dictionary, a callee performing `(x+bias)%modulus`, and a caller invoking it then adding three. A dependent `CalleeCertificate dictionary contract` proves the selected implementation's contract. `compose` separately requires complete entry coverage and that the proposed postcondition implies the independently fixed expected result. Its all-input caller theorem therefore uses actual callee evidence, rather than checking matching subject labels.

The accepted dictionary has modulus256/bias1. Six fresh negative Lean invocations reject the original semantic obligations for: changed body bias2; a 16-bit target at x255; associated nibble representation at x15; foreign dynamic implementation at x0; a narrowed contract omitting x255; and a weakened True postcondition. The last two have valid local callee certificates but fail coverage/adequacy, demonstrating why local verification alone is insufficient. A new proof can legitimately relink bias2 to an explicitly changed independent expectation. Final positive/counterexample theorems check under Lean4.34.1 with propext only (the legitimate relink uses no axioms); expected failed elaborations are not accepted proof objects.

These are semantic implementation/contract/arithmetic/instance substitutions in the owned caller/callee language. Real Rust associated-type, monomorphization, closure/vtable identity extraction and physical ABI correspondence remain explicit import premises; no source-level dispatch theorem is claimed. The preceding native GAT/dictionary reports provide separate Rust selection observations.

### F8. Expansion, alias resolution and renamed declarations give discriminating attachment cases

Basis: owned Rust source + compiler/native execution (T066).

`support/attachment-control/probe.rs` expands one declarative macro in two modules. Both functions are named `validate`, but one carries `anneal:bool-valid-v1` and accepts exactly bytes0/1; the decoy carries a trit predicate and also accepts2. Actual expanded output retains each doc-attribute marker on its own function. The HIR observation distinguishes local owners intended::validate (DefId0:11) and decoy::validate (0:14); both the exported alias and its call resolve to the intended owner. Native all256 checks confirm counts2/3 and alias agreement. Local DefIds apply only within this compiled subject; they are not stable cross-build names.

Two additional subjects are actually compiled/executed: moving the intended declaration to a renamed module preserves the byte law but changes its selected identity, and changing its body to `<3` while copying its Boolean annotation preserves the marker but changes semantics at byte2. A consumer-fixed fixture selection rejects both against the old selection, plus the decoy and treating the alias as a fresh declaration. An explicitly reviewed new attachment can admit a rename; name agreement alone cannot do so. The fixture records its compiler-expanded/HIR identities, source hashes and native outputs under nightly1.101.0@1d81eb4ad9cd207e3e638bd32b17ec4fce8412a6, edition2024. The doc marker is an experimental specification locator, not an implemented Anneal annotation language. The Python fixture selector and compiler are trusted observations, not a proved general hygiene/annotation importer. This closes a discriminating attachment experiment while retaining that general implementation obligation.

## Boundaries

Known scope: finite straight-line modeled instructions, one cell and explicit resource flags. Unsupported by this pilot: loops, arbitrary heaps/aliases/provenance, allocation epochs, generic/dynamic/foreign calls, real TLS and unwind cleanup. The original one-cell pilot performs no rustc/Charon/Aeneas build or Rust execution; F6/F8 add bounded owned Rust/compiler observations. No full compiler-elaboration or delegated-reader theorem was found or inferred.

Research boundary: the named excluded compiler families and a mechanized full TLS model are outside this bounded source census; no complete compiler theorem is claimed. Future engineering: instantiate the researched capture/reader/coverage interfaces for a selected admitted fragment. The source error-envelope limitation is a source fact, not a claim that every current pipeline accepts partial output.
