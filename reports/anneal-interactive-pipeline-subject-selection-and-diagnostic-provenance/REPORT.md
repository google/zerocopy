# Interactive Pipeline Subject Selection, Invalidation Graph, and Diagnostic Provenance

## Summary

An interactive verification pipeline built across Cargo, `rustc`, Charon, Aeneas, Lake, and the Lean 4 language server cannot treat "a file changed" as a single invalidation event, nor can it treat process exit status or generic diagnostic severity as a universal user-error indicator. Across the pinned toolchain stack, each stage maintains its own freshness contract, compilation-subject identity, and failure semantics:

1. **Cross-tool diagnostic provenance and failure classification (`rustc`, Charon, Aeneas, Lean):** No single exit code or severity string answers whether a failure is a user source error, an unsupported translation construct, a configuration/invocation error, or an internal tool failure. In Charon (`AeneasVerif/charon@a535e914f74db4fd9e6be7048f4233270d8945c0`), `CharonFailure::RustcError` exits with status `2` (covering ordinary `rustc` source errors, `Fatal` configuration/file-operation errors, and `Bug`/`DelayedBug` internal compiler errors distinguishable only via `rustc` JSON level `"error: internal compiler error"`), `CharonError` and `Serialize` both exit with status `1`, and caught panics exit with status `101`. Furthermore, Charon treats registered extraction errors as recoverable by default, serializing partial LLBC with `has_errors: true` while exiting `0` unless strict flags (`--abort-on-error`, `--error-on-warnings`) are enforced. In Aeneas (`AeneasVerif/aeneas@ac9f1bc5262a5e4ff1e24ca78617121382202727`), CLI errors, missing LLBC inputs, unsupported constructs, and internal invariants (`"Internal error, please file an issue"`) all exit with status `1`, and extraction recovery (`ExtractErrors.ml`) can emit placeholder `sorry`/`admit` tokens into generated Lean before exiting `1`. In Lean (`leanprover/lean4@3dc1a088b6d2d8eafe25a7cd7ec7b58d731bd7cc`), batch `lean --json` emits 1-based positions while LSP emits 0-based UTF-16 ranges, and process exit `1` conflates proof elaboration failure with shell/argument/setup failure. A sound Anneal diagnostic model must record a three-part tuple: **originating stage** (`rustc`, `charon`, `aeneas`, `lean`, `anneal/infrastructure`), **failure class** (`source-error`, `unsupported-translation`, `tool-internal`, `configuration`, `infrastructure`, `warning-policy`, `unknown`), and **source responsibility** (`original Rust`, `macro/generated Rust`, `generated Lean from Aeneas`, `generated Anneal scaffolding`, `user-authored Lean`, `external dependency/toolchain`, `none/unknown`).
2. **External-crate source recovery and synthesized scaffolding provenance:** During a live `rustc` session (`rust-lang/rust@f8a08b688cbe60acc386ed1fbd1b7cbaaf5576b1`), imported `SourceFile` records carry `src: None` alongside `src_hash`, line/multibyte tables, and `ExternalSource`, allowing `SourceMap::ensure_source_file_source_present` and `SourceFile::add_external_src` to lazily load candidate paths (including heuristic reverse prefix mappings) only when the pre-normalization content hash matches `src_hash`. Charon (`translate_meta.rs`) copies only `source_file.src.as_deref().cloned()` into LLBC `File.contents` (which is always `None` for imported files), normalizes paths to `/rustc/...`, `/toolchain/...`, and `/cargo/...`, and omits `src_hash` from serialized `File` records. Consequently, LLBC and Aeneas preserve external location metadata without verified source bytes. On the generated-Lean side, historical Anneal V1 (`anneal/v1/src/generate.rs` and `aeneas.rs` at `google/zerocopy@41f5b37afe7060fd9fe08c00b200672cd76d77b9`) attached explicit provenance only to copied user proposition/proof lines (`MappingKind::Source`), generated theorem names (`MappingKind::Synthetic` mapped to `fn_span`), and proof `by` tokens (`MappingKind::Keyword`, leaving `AstTheorem.keyword_span` unpopulated as `None` for `FunctionBlockInner::Axiom`), plus a message-specific `declaration uses 'sorry'` redirect bounded by the next synthetic theorem anchor. Most generated theorem glue (`Pre`/`Post` headers, `apply Anneal.wp_prove_orthogonal`, `rintro`, `rcases`, `exact`, `verify_user_bound`) is unmapped and must be classified as generator-owned or construct/obligation-owned rather than misattributed by proximity.
3. **Interactive pipeline invalidation graph, immutable SDK server execution, and bounded concurrency/identity probes:** Because neither Charon `0.1.210` nor Aeneas `nightly-2026.06.03` exposes a cross-run incremental delta protocol (`translate_crate_to_pure` rebuilds crate-wide use graphs, declaration groups, and global naming/SCC tables), the conservative semantic invalidation unit after any compilation-subject change is a newly extracted whole-crate LLBC snapshot and a newly generated whole-crate Lean tree published as an atomic generation. Downstream, Lake owns `.olean`/`.ilean` freshness via saved dependency traces (`Lake/Build/Module.lean`), while Lean's LSP server treats open documents as client-owned in-memory text (`didOpen`/`didChange`) and requires worker refresh/restart when imported `.olean` modules change on disk. Bounded Python model and APFS probes confirm that path/URI/version keys collide across source, import, subject, and A-to-B-to-A worker-epoch mutations; that UTF-8/UTF-16 scalar boundaries round-trip across 2,092 positions while synthetic gaps and stale host/projection digests must be rejected; that advancing a generation token only at staging (`stageB`) rather than request arrival (`requestB`) admits stale publication in 2 of 10 valid schedules; and that multi-file consumers must resolve and pin an immutable generation directory before reading. Live macOS `aarch64` execution against an immutable SDK view (`LEAN_SYSROOT`, `LAKE_OVERRIDE_LEAN=true`, `LEAN_SRC_PATH`, and a root `Dynlib` plugin target for `libaeneas_AeneasMeta.dylib`) compiled the 6-module Anneal V1 fixture in `3.2 MiB` of consumer state (replaying warm in `0.629 s` without copying the `1.8 GiB` dependency tree), loaded the native `aeneas_saturate` plugin, and served live LSP goals and Go-to-Definition queries into Aeneas and Mathlib without mutating any of the 28,893 shared SDK entries.
4. **Anneal V2 current source surface, Cargo root selection, and LLBC slug collisions:** At `google/zerocopy@bd0956be95c5f798f0c0484921b9b9d1fc6e9988`, the live `cargo-anneal` binary exposes only `setup`; `resolve.rs`, `scanner.rs`, `setup.rs`, and `util.rs` are compiled under `allow(dead_code)` with no CLI verification path, Charon/Aeneas invocation, or LSP/MCP handler, and offline `cargo build --locked --offline` exits `101` when the uncached `charon` Git dependency is absent. Direct harness execution of the checked-in `resolve.rs` in a two-package virtual workspace (`alpha` and `beta`, with `default-members = ["alpha"]` and a `gated` binary with `required-features = ["gated"]`) showed that V2's virtual-root default fallback uses `workspace_members` rather than `workspace_default_members` (returning 6 roots across `alpha` and `beta` where Cargo's default `check` builds only `alpha`) and does not filter targets by `required_features` (returning `gated` even with the feature disabled). Furthermore, direct harness and Charon `0.1.210` execution of `AnnealArtifact::artifact_slug()` (`scanner.rs`, which hashes only manifest path, target name, and `AnnealTargetKind`) proved concrete `.llbc` filename collisions across distinct compilation subjects of the same source file: default vs. `--features selected` (producing identical slug `UnitKeyProbeUnitKeyProbe2ddd03393e67b637.llbc` for distinct `U32` body literals `7` and `11`), and debug vs. `--release` vs. `RUSTFLAGS=--cfg probe_alt` (producing identical slug `UnitKeyProbeUnitKeyProbe420dc0784be82942.llbc` for distinct `(profile_value, config_value)` literal pairs `(7, 23)`, `(11, 23)`, and `(7, 29)`).

## Findings

### 1. Cross-Tool Error Provenance and Monotonic Failure Classification

Across the `rustc` -> Charon -> Aeneas -> Lean pipeline, nonzero process exit status is a stage-local signal rather than a universal user-error classification:

- **Charon driver exit codes and partial-artifact hazard (`charon/src/bin/charon-driver/main.rs`, `driver.rs`, `errors.rs`, `options.rs`):** `CharonFailure` defines four variants: `RustcError` ("Code failed to compile", exit `2`), `CharonError(usize)` ("Charon failed to translate this code", exit `1`), `Serialize` ("Could not serialize output file", exit `1`), and `Panic` ("Compilation panicked", exit `101`). While exit `101` isolates a tool panic and exit `2` localizes failure to the `rustc` callback side, exit `1` conflates unsupported Rust constructs with output serialization failures. Furthermore, `rustc_errors::Level` (`compiler/rustc_errors/src/lib.rs` and `json.rs`) serializes `Bug` and `DelayedBug` as `"error: internal compiler error"`, whereas both `Fatal` (configuration errors, internal overflows, file I/O failures) and ordinary source `Error` serialize as `"error"`. Critically, Charon treats registered extraction errors as recoverable by default: unless `--abort-on-error` or `--error-on-warnings` is passed, Charon serializes a partial `CrateData` carrying `has_errors: true` and exits `0`.
- **Aeneas coarse exit code, internal-error markers, and placeholder `sorry` recovery (`src/Errors.ml`, `src/Main.ml`, `src/extract/ExtractErrors.ml`):** Aeneas stores recoverable translation errors in a global `error_list` via `craise`/`CFailure` and exits `1` at the end of `Main.ml` if `error_list` is non-empty. However, CLI validation errors, missing/malformed LLBC files, unsupported translation cases, and internal invariant failures (`sanity_check` / `internal_error` emitting `"Internal error, please file an issue"`, with optional `-print-error-emitters` recording the OCaml emitter file and line) all exit `1`. During extraction, `admit_raise` / `admit_string` registers an error in `error_list` and emits `sorry` (for Lean) or `admit` so code generation can continue; therefore, the existence of syntactically valid generated Lean on disk never proves translation succeeded. Additionally, semantic warnings do not trigger nonzero exit unless `-warnings-as-errors` is enabled.
- **Lean batch vs. LSP coordinate contracts and shell exit conflation (`src/Lean/Message.lean`, `src/Lean/Shell.lean`):** Batch `lean --json` serializes `SerialMessage` records with 1-based line/column coordinates and `MessageSeverity` (`information`, `warning`, `error`), whereas Lean LSP `publishDiagnostics` uses 0-based UTF-16 ranges. Neither exit `1` from `Shell.lean` (which covers both `Elab.runFrontend` returning no environment and CLI/header/option/output-file failures) nor `MessageSeverity.error` distinguishes a user proof error from ill-typed generated scaffolding or environment misconfiguration. In interactive workflows, JSON-RPC request cancellation (`-32800`) and worker crashes are transport/lifecycle events with no source span and must be recorded as incomplete attempts rather than proof failures (verified across executed specimen suites in `support/cross-tool-error-provenance-specimens/specimens/RESULTS.md`, `support/cross-tool-error-provenance-specimens/lean-comparisons.json`, and `support/cross-tool-error-provenance-specimens/lsp-two-events.json`).

| Observation | Safe Monotonic Conclusion | Unsafe Shortcut to Avoid |
| --- | --- | --- |
| `rustc` JSON level `"error: internal compiler error"` | `rustc` internal compiler error (`tool-internal`) | Treating as ordinary user source error |
| Charon exit `101` | Charon/driver panic (`tool-internal`) | Treating as unsupported Rust construct |
| Charon exit `2` | `rustc`-driver-side failure; inspect `rustc` JSON diagnostics | Assuming bad user Rust without checking for `Fatal`/ICE |
| Charon exit `1` | Charon-side failure; inspect variant text (`CharonError` vs. `Serialize`) | Assuming unsupported translation without checking I/O |
| Charon exit `0` with `has_errors: true` | Partial artifact under non-strict policy; reject fail-closed | Treating exit `0` as complete translation |
| Aeneas exit `1` + `"Internal error, please file an issue"` | Pinned Aeneas internal invariant failure (`tool-internal`) | Blaming user Rust source at the attached span |
| Aeneas generated `sorry` + nonzero exit | Error recovery placeholder after registered extraction failure | Treating generated Lean file existence as translation success |
| Lean JSON severity `error` | Lean elaboration/frontend error; combine with span provenance | Blaming user proof when span lies in unmapped scaffolding |
| Lean exit `1` with no JSON diagnostic | Shell/invocation/setup failure (`configuration`/`infrastructure`) | Reporting as an unproved verification obligation |

**Basis:** Pinned source analysis (`support/error-provenance-classification/source-map.json`, `support/error-provenance-classification/classification-matrix.json`) and end-to-end specimen execution (`support/cross-tool-error-provenance-specimens/specimens/coverage.json`, `support/cross-tool-error-provenance-specimens/specimens/canonical-order-check.json`).

### 2. External-Crate Source Recovery and Synthesized Scaffolding Provenance

- **Loss of verified external-source recovery across the LLBC boundary (`support/external-crate-diagnostic-source-recovery/external-source-recovery-matrix.json`):** In `rustc` (`compiler/rustc_span/src/source_map.rs` and `lib.rs`), `SourceMap::new_imported_source_file` constructs imported crate files with `src: None`, `src_hash`, line/multibyte-character tables, and `external_src = Foreign { AbsentOk, metadata_index }`. When `rustc`'s diagnostic emitter (`compiler/rustc_errors/src/emitter.rs`, `should_show_source_code`) renders an imported span, `ensure_source_file_source_present` attempts to read `RealFileName::local_path()` or `FilePathMapping::reverse_map_prefix_heuristically`, and `SourceFile::add_external_src` accepts the candidate file **only if its pre-normalization hash matches `src_hash`**. In contrast, Charon (`charon/src/bin/charon-driver/translate/translate_meta.rs` and `charon/src/ast/meta.rs`) populates LLBC `File.contents` solely from `source_file.src.as_deref().cloned()` (which is `None` for all imported files), normalizes paths by rewriting sysroot paths to `/rustc/...` or `/toolchain/...` and Cargo home paths to `/cargo/...` (or stripping `/rustc/<40-hex-hash>/`), and does not serialize `src_hash` or `ExternalSource`. Aeneas (`src/Errors.ml`) formats only the normalized filename and line/column coordinates, and historical Anneal V1 (`anneal/v1/src/diagnostics.rs`) deliberately gated source excerpt rendering to paths lexically inside `user_root`, falling back to `[External Error]`. Consequently, downstream consumers that want verified dependency excerpts must either capture hash-verified source bytes during the `rustc` session or carry `src_hash` and crate identity across the translation boundary.
- **Synthesized Lean scaffolding provenance (`support/synthesized-scaffolding-diagnostic-provenance/source-map.json`):** Historical Anneal V1 (`anneal/v1/src/generate.rs`, `aeneas.rs`, `parse/attr.rs`) distinguished three sidecar mapping kinds: `MappingKind::Source` (direct byte ranges copied from user-authored proposition/proof lines via `push_spanned`), `MappingKind::Synthetic` (the generated theorem name `ast.spec_name` mapped via `push_mapped` to the Rust function identifier `ast.fn_span`), and `MappingKind::Keyword` (the generated theorem `by` token mapped to the first proof-context line or proof-case keyword span when present, though `generate_function` passes `keyword_span: None` for `FunctionBlockInner::Axiom`, leaving the renderer's `axiom` keyword branch unpopulated). In `anneal/v1/src/aeneas.rs`, `resolve_mapping` implements one targeted heuristic: if a Lean diagnostic contains ``declaration uses `sorry` `` and overlaps a `Synthetic` theorem-name mapping, it redirects the diagnostic to a subsequent `Keyword` mapping within the same Rust source file before the next `Synthetic` theorem boundary. All other generator-owned Lean syntax—`Pre`/`Post` structure headers, instance binders, `h_req`, `apply Anneal.wp_prove_orthogonal`, `rintro`, `rcases`, `exact`, and auto-generated validity helpers like `verify_user_bound`—is emitted via plain `push_str` with no sidecar entry and falls back to the generated `.lean` file. A complete provenance design must partition generated bytes into four explicit classes: **Direct source**, **Construct owner**, **Obligation owner**, and **Generated/internal**.

**Basis:** Pinned source analysis (`support/external-crate-diagnostic-source-recovery/source-map.json`, `support/synthesized-scaffolding-diagnostic-provenance/source-map.json`).

### 3. Interactive Pipeline Invalidation Graph, Bounded Model Probes, and Immutable SDK Server Execution

- **Multi-stage invalidation graph (`support/interactive-pipeline-invalidation-graph/invalidation-graph.json`):**
  1. *Cargo/Rust -> Charon LLBC:* Because `charon cargo` delegates unit graph construction to Cargo and Charon `0.1.210` (`translate_crate.rs`, `export.rs`) has no cross-run LLBC delta protocol (`--start-from` prunes reachable items within one run but is not an edit-invalidation algorithm), any change to a compilation subject's source, features, `cfg` flags, profile, dependencies, or build-script outputs requires producing a fresh complete LLBC snapshot.
  2. *LLBC -> Aeneas generated Lean:* `Translate.translate_crate_to_pure` (`src/Translate.ml`, `src/interp/Interp.ml`, `src/pure/PureMicroPasses.ml`) reconstructs crate-wide use graphs, declaration groups, type/function analyses, and global target naming/SCC structures on every call. The safe semantic invalidation unit is whole-crate Aeneas recomputation published as an atomic generated directory (accounting for deleted declarations).
  3. *Generated Lean -> Lake artifacts vs. Lean LSP server:* Lake (`src/lake/Lake/Build/Module.lean` and `Common.lean`) governs `.olean`/`.ilean` freshness via saved dependency traces over normalized source text, Lean options, toolchain identity, and import traces. Separately, under LSP 3.18 (`didOpen`, `didChange`, `didClose`) and Lean's server architecture (`src/Lean/Server/Watchdog.lean` and `FileWorker.lean`), an open document's text is owned by the client in memory; overwriting a generated `.lean` file on disk does not update an open worker without `didChange`/reopen. Conversely, when an open proof document imports a generated module whose `.olean` changes, Lake must rebuild/restore the module artifact and the Lean watchdog must refresh/restart the dependent worker so compacted `.olean` memory regions are reloaded cleanly. Proof-only body edits take the fast path (`didChange` -> prefix snapshot reuse in `Lean/Language/Lean.lean` -> incremental re-elaboration) without rerunning Charon or Aeneas.
- **Bounded finite-state identity, Unicode coordinate, supersession-gap, and APFS publication probes (`support/interactive-model-probes/`):**
  - *Identity vs. causal generation (`support/interactive-model-probes/model_probes.py`, `support/interactive-model-probes/model-probes.json`):* Across 10 single-field mutations and an explicit A->B->A content-recurrence sequence, path-only, URI/version, and proof-hash keys collided across changed Rust bytes, proof bytes, imports, and compilation subjects. Content-addressed cache keys must be kept distinct from the causal generation tag (`workspace + compilation subject + tool hashes + LLBC digest + generated Lean digest + Lake environment + LSP document version + worker/RPC incarnation`) attached to an interactive response.
  - *Unicode scalar conversion and patch compare-and-swap:* Across 59 deterministic strings (`2,092` valid Unicode scalar boundaries including ASCII, BMP, supplementary astral characters, combining marks, tabs, and CRLF/LF), UTF-8 byte offsets and UTF-16 code-unit offsets round-tripped without loss, while the piecewise projection harness rejected edits inside synthetic scaffolding gaps and rejected patches whenever the host digest, projection digest, or document version changed.
  - *Request-to-stage supersession gap (`support/interactive-model-probes/supersession_gap_probe.py`, `support/interactive-model-probes/supersession-gap.json`):* Enumerating all 120 five-event schedules and the 10 valid schedules adding `requestB` before `stageB` showed that advancing a generation token only when staging finishes (`stageB`) admits stale generation `A` publication in 2 schedules where `publishA` occurs between `requestB` and `stageB`; advancing the desired-generation token immediately at `requestB` eliminates both stale publications.
  - *APFS generation-pointer pinning (`support/interactive-model-probes/publication_probe.py`, `support/interactive-model-probes/publication-fixture/publication-probe.json`):* Replacing a `current` symlink via `os.replace` between unpinned reads of `Types.lean` and `Funs.lean` produced a mixed `gen-A`/`gen-B` view, and pointing `current` at an incomplete `gen-C` directory raised `FileNotFoundError`. Resolving and pinning the immutable `gen-A` directory handle once before reading multiple files guaranteed a coherent generation snapshot.
- **Immutable SDK imports, native plugins, and live Lean server execution (`support/immutable-sdk-native-server/`):**
  - On macOS `aarch64` with Lean `v4.30.0-rc2` (`3dc1a088b6d2d8eafe25a7cd7ec7b58d731bd7cc`) and the published omnibus archive (`1,464,207,302` compressed bytes; `1,825,191,796` extracted Aeneas logical bytes), exposing prebuilt `.olean` providers from RC2 `lib/lean`, Aeneas `backends/lean/.lake/build/lib/lean`, and the 9 path packages through an extended `LEAN_SYSROOT` (`support/immutable-sdk-native-server/evidence/harness/real_sdk_lake.py`) allowed a root Lakefile (`support/immutable-sdk-native-server/evidence/fixture/V1-lakefile.lean`) with no `require aeneas` dependency graph and one explicit `Dynlib` plugin target (`libaeneas_AeneasMeta.dylib`, `plugin := true`) to build all 6 local modules (`SdkIdentity`, `Config`, `Types`, `Funs`, `Anneal`, `Generated`) in `3.2 MiB` of consumer workspace state and replay warm in `0.629 s` (`support/immutable-sdk-native-server/evidence/selected-outcomes.json`).
  - Copying both `lean` (`49,968` bytes) and `lake` (`51,840` bytes) binaries into the SDK's `bin/` directory (rather than symlinking `lean`, which resolved the original installation prefix) made `lake env lean --print-prefix` select the coherent SDK view. With `LEAN_SRC_PATH` populated with the Aeneas backend and 9 package source roots, the live `--server` session (`support/immutable-sdk-native-server/evidence/lsp-selected.json`) loaded `libaeneas_AeneasMeta.dylib` (`aeneas_saturate`), verified positive/false/`sorry` controls (`support/immutable-sdk-native-server/evidence/logs/native-lake-v1-audit.stdout`, `support/immutable-sdk-native-server/evidence/logs/native-lake-v1-false.stdout`, `support/immutable-sdk-native-server/evidence/logs/native-lake-v1-sorry.stdout`), resolved Go-to-Definition for `aeneas_saturate` (`AeneasMeta/Saturate/Tactic.lean:741-745`) and `Nat.succ_injective` (`Mathlib/Data/Nat/Basic.lean:56`), and left all `28,893` shared Aeneas tree entries byte-identical before and after execution. Running final Lean `v4.30.0` (`d024af099ca4bf2c86f649261ebf59565dc8c622`) against the RC2 `AeneasMeta` artifact failed closed with `incompatible header`.

**Basis:** Source analysis (`support/interactive-pipeline-invalidation-graph/source-map.json`) and offline/runtime execution (`support/interactive-model-probes/check.py`, `support/immutable-sdk-native-server/check.py`, `support/immutable-sdk-native-server/evidence/INDEX.json`).

### 4. Anneal V2 Source Surface, Cargo Root Selection, and LLBC Locator Collisions

- **Current V2 source surface (`google/zerocopy@bd0956be95c5f798f0c0484921b9b9d1fc6e9988`):** `anneal/src/main.rs` exposes only the `Setup` subcommand and a feature-gated (`exocrate_tests`) Lake archive test. `resolve.rs`, `scanner.rs`, `setup.rs`, and `util.rs` are compiled under `allow(dead_code)` and are unreachable from `main`. `resolve.rs` defines `LockedRoots` and an OS directory lock (`util.rs`, `DirLock`) alongside a shared global Cargo target directory outside that lock, and `Cargo.toml` pins `charon` as a Git dependency (`https://github.com/AeneasVerif/charon.git?tag=nightly-2026.06.03#0c91ca1a`), causing offline `cargo build --locked --offline` to exit `101` when the checkout is absent from the local Cargo cache.
- **Two-package workspace root selection differences (`support/cargo-root-selection-multipackage/`):** Executing the unmodified `anneal/src/resolve.rs` (`SHA-256 6b36c1c5647d4bff5955799c02c6c764ee1b7e29455fd55a8c5d01f0462d23b4` in `support/cargo-root-selection-multipackage/harness/src/resolve.rs`) against a two-package virtual workspace (`alpha` and `beta`, where `default-members = ["alpha"]` and `alpha` defines `rlib` + `cdylib` library kinds, an `always` binary, a `gated` binary with `required-features = ["gated"]`, and an integration test) demonstrated two concrete selection divergences from Cargo (`support/cargo-root-selection-multipackage/commands.json`, `support/cargo-root-selection-multipackage/raw/root_default.stdout`, `support/cargo-root-selection-multipackage/raw/alpha_bins.stdout`):
  1. *Virtual-root `default-members` ignored:* With no package flags at the virtual workspace root, `resolve_packages` falls back to `workspace_members` rather than `workspace_default_members`, returning all 6 roots across `alpha` and `beta` (matching `--workspace`), whereas `cargo check` builds only `alpha`.
  2. *Target `required-features` uninspected:* For `-p alpha --bins` without `--features gated`, `resolve_targets` returned both `always` and `gated` because it filters only by target kind and name without checking `required_features`, whereas `cargo check -p alpha --bins` omitted `gated` until `--features gated` was supplied.

## Boundaries

- **Unconnected V2 CLI surface:** At `google/zerocopy@bd0956be95c5f798f0c0484921b9b9d1fc6e9988`, `cargo-anneal` does not yet wire `resolve.rs` or `scanner.rs` into a live verification, Charon extraction, Aeneas translation, or LSP/MCP command. Any future per-function reuse requires explicit dependency/SCC/deletion equivalence proofs.
- **Historical V1 scope:** Findings from `anneal/v1/src/{generate,aeneas,diagnostics}.rs` and the V1 immutable-SDK fixture characterize historical V1 mechanisms and design constraints; they do not define current Anneal V2's final annotation syntax or sidecar format.
- **Platform and filesystem scope:** The live SDK/LSP server runs, APFS symlink-swap probes, and Cargo/Charon harness runs were executed on macOS `aarch64` (`darwin_aarch64`). Linux dynamic loader and filesystem rename behaviors are evaluated separately in the toolchain packaging and sandbox reports.
