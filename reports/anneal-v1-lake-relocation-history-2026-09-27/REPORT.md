# V1 Lake integration, generated workspaces, and interactive tooling

## Summary

V1's Lake history moves from worker clones through artifact caching and local-Git indirection to read-only prebuilt archives. The final fixture checks generation beside an archive, not moving an already generated workspace. Interactive proof authoring remained manual Lean-file editing; LSP support was future work.

## Applicability

Historical V1 implementation and tests at the identified zerocopy revision, together with source/history evidence for the V1 integration chronology. Related corpus reports: [anneal-v1-clean-workspace-prebuilt-archive-41f5b37](../anneal-v1-clean-workspace-prebuilt-archive-41f5b37/REPORT.md), [anneal-v1-end-to-end-pipeline-41f5b37](../anneal-v1-end-to-end-pipeline-41f5b37/REPORT.md).

### Generated-workspace relocation: actual boundary

V1 computes a workspace under the Cargo target tree, scoped by a hash of the Cargo workspace root ([resolver](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/resolve.rs#L275)). It writes generated Lean into a temporary sibling, then replaces the final `lean` directory. On rerun it carries forward the old `.lake` directory for local build/config caches, but writes a new manifest because package paths depend on the final directory ([atomic replacement](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/aeneas.rs#L314)). The final directory is briefly absent during replacement; the source itself calls out that this is not strictly atomic. A long-lived editor or server must therefore be restarted or invalidated across regeneration rather than assuming stable open files.

The manifest function canonicalizes the **final workspace's parent** and appends its future leaf, because that leaf may not exist yet. It canonicalizes installed Aeneas and each path package, then computes relative `dir` entries from that future final location ([manifest code](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/aeneas.rs#L342)). The [unit test](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/aeneas.rs#L989) constructs a not-yet-created final workspace, creates it after generating the manifest, and asserts that all relative entries resolve to Aeneas, Mathlib, and Qq. This establishes the temporary-directory-to-final-directory case for those entries. It does **not** establish that copying or moving the resulting workspace independently of the toolchain leaves its manifest valid. The generated `lakefile.lean` also contains the installed Aeneas path, so a move of the toolchain or a copy to another machine would need regeneration/rebinding, even when manifest entries are syntactically relative.

The [read-only archive integration fixture](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/tests/integration.rs#L297) creates its workspace once next to the installed archive, writes a relative manifest, and runs build and JSON diagnostics. It checks archive write bits. It has no second location, no post-generation move, no server `setup-file`, and no explicit network-denying harness. Current V1 source plus this fixture support **fresh generation at the intended location using a prebuilt archive**, not a general relocation guarantee. A `--old` cache hit alone is also insufficient: cache validity, source/model correspondence, and accepted proof meaning need separate evidence under the current [design contract](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/DESIGN.md).

The path dependency has a configuration sensitivity: [V1's Lake command setup](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/aeneas.rs#L712) removes ambient `CI` because Aeneas's `precompileModules` setting differs when it is set. The source says a mismatch invalidated read-only prebuilt traces and attempted rebuild/removal under the installed archive. This is a concrete limit on treating “archive exists” as enough; archive build settings and consumer settings must agree. The fixture mirrors the `CI` removal ([test command](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/tests/integration.rs#L461)).

### Interactive proof tooling: experiment and limit

The checked-in V1 workflow is file-based. The `generate` subcommand emits the Lean workspace and prints a manual `lake build` command ([CLI](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/main.rs#L79)); `expand` prints generated Aeneas/Anneal code; `verify` builds and runs `lake env lean --json` for each generated `Specs.lean`, then maps diagnostics back to Rust ([verification path](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/aeneas.rs#L590)). The [agent workflow](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/docs/agent/07_workflow.md) advises generating files, iterating with normal Lean tools, and copying finished proof text back to Rust comments. This was an interactive *manual Lean file* experiment, with generated Lean as disposable working material and Rust as the source of truth.

The V1 [design document](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/docs/design/design.md#L499) explicitly places Rust-editor Lean server/goal-state integration under “Future Work.” I found no V1 server launch, LSP request handling, cursor mapping, or live goal-query implementation in `anneal/v1/src`. The generated `.lean.map` files map diagnostics to Rust spans; they are useful metadata but do not themselves define reverse cursor mapping for unsaved Rust edits, versioned requests, or tactic-state queries. The test fixture for `generate` checks printed paths/command, while `lean_generation` checks emitted assets; neither is a live editor test.

Related Nix-independent synthetic work in this research series observed that a **small** read-only relocated Lake producer was consumable by a fresh workspace when a correct relative manifest was seeded before first load, and that omitting it could attempt a lock write in the producer's `.lake/config` ([Lake probes](../lake-generated-workspace-readonly-probe-v4-30-0-rc2/REPORT.md)). A separate bare Lean 4.30.0-rc2 server probe exercised `didOpen`, versioned `waitForDiagnostics`, unsaved `didChange`, and `$/lean/plainGoal`, showing one unsolved then one solved local tactic state ([query lifecycle](../lean-tactic-state-protocol-transcript-v4-30-0-rc2/REPORT.md)). Those are useful interface experiments, not V1 Aeneas/Mathlib relocation tests or evidence that V1 shipped an editor bridge. An empty goal list at a cursor position cannot establish Anneal verification success.

### Setup and prompt recommendations

1. Ask any future V1-history prompt to name the exact Git commit and source path for each claim, and distinguish commit-message intent, checked-in implementation, test coverage, and fresh observation.
2. For generated workspaces, record the final workspace path, toolchain/archive identity, generated Lakefile and manifest, resolved dependency directories, Lean/Lake version, build settings including `CI`, and whether outputs were prebuilt. Regenerate the manifest and Lakefile after a path change; do not assume moving the already generated directory works.
3. To test relocation specifically, use one tiny producer/consumer fixture first: build at A, move to B, seed or regenerate the manifest before Lake loads B, compare `--no-build`/`--old build`, `setup-file`, and `lean --json`, and check read-only producer hashes/mtimes and attempted writes. Test a real installed archive separately without copying its large build tree. Only claim disconnected operation under an explicit network-denying harness.
4. For interactive work, keep `generate`/`expand`/manual Lean editing labeled as the historical V1 path. A future server adapter should identify generated bytes, Rust source mapping, URI, document version, cursor position, toolchain, imports, and final diagnostics; invalidate old goal/diagnostic responses on edits or regeneration. Report cancellation, setup failure, missing artifacts, and server crash as incomplete states. Present goals as proof-authoring assistance, with verification success reserved for checked Rust-level obligations and explicit TCB/scope evidence.
