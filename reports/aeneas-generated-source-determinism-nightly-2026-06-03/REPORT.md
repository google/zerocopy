# Aeneas generated-source determinism at nightly-2026.06.03

## Summary

At `AeneasVerif/aeneas@ac9f1bc5262a5e4ff1e24ca78617121382202727`
(`nightly-2026.06.03`), the generated Lean source path is deliberately structured
to avoid several obvious sources of nondeterminism. Generated-file headers contain
no wall-clock timestamp. The importer clears Charon `short_names` specifically to
make printing more deterministic. Builtin memoized tables are forced before
parallel work. Parallel function translation returns results in task-list order
rather than completion order. Two previously identified shared-state races were
fixed before this revision: fresh-variable generators became task-local, and SCC
construction stopped using an ocamlgraph vertex type backed by a global mutable
counter. Final extraction then emits declaration groups in the serialized LLBC
`crate.declarations` order.

Those facts support a narrower conclusion than “Aeneas is byte-for-byte
deterministic under all supported executions.” The upstream test runner at this
revision explicitly adds `-sequential` to every Aeneas test invocation, even
though normal Aeneas execution defaults to parallel translation. The checked-in
generated test corpus therefore does not exercise the default parallel path as a
golden determinism test. No fresh repeated-run experiment was executed for this
report.

For Anneal, generated-source identity should therefore be defined relative to an
exact Aeneas revision, identical LLBC bytes and declaration order, identical
backend/configuration inputs, and the same relevant source-path metadata.
Sequential generation is the strongest source-backed reproducibility mode at
this pin. Default-parallel generation has substantial determinism safeguards, but
should receive a repeated byte-level probe before Anneal treats equality across
parallel runs as a hard invariant.

## Applicability

This report concerns the Aeneas source generator selected by Anneal's
`nightly-2026.06.03` Aeneas release:

- repository: `AeneasVerif/aeneas`;
- revision: `ac9f1bc5262a5e4ff1e24ca78617121382202727`;
- backend of primary interest: Lean;
- input boundary: an already serialized Charon LLBC crate;
- output boundary: generated source files and their filenames.

“Deterministic” in this report means that repeated Aeneas executions with the
same declared inputs produce the same generated-source file set and the same
bytes in those files. It does not mean that Charon necessarily produces
identical LLBC from two independently compiled Rust workspaces, that filesystem
metadata is identical, or that later Lean compilation artifacts are identical.

The distinction matters for Anneal. A stable Aeneas translation stage can only
be compared meaningfully after the upstream LLBC identity and all source-affecting
Aeneas options are fixed.

## Findings

### Generated-file headers do not inject time

`Translate.extract_file` writes a fixed Lean header:

- `-- THIS FILE WAS AUTOMATICALLY GENERATED BY AENEAS`;
- the Rust module name plus a caller-supplied custom message;
- fixed imports and fixed option lines derived from configuration.

The function does not read the clock while generating these headers. It sets the
OCaml formatter margin to a constant 80 before printing definitions. Time
measurements in `Main.ml` and the translation diagnostics are used for logging
and profiling, not inserted into generated source.

This removes two common sources of incidental byte differences: generation
timestamps and terminal-dependent formatter width.

Basis: **source** in `src/Translate.ml` and `src/Main.ml`.

### Aeneas deliberately discards Charon short names before translation

Immediately after importing the LLBC crate, `Main.ml` replaces its `short_names`
field with an empty list. The adjacent source comment says the purpose is to
“make printing more deterministic.”

This is direct evidence that the selected revision treats printable-name state as
a reproducibility concern rather than accepting the serialized short-name cache
as an output-affecting input.

The operation is not a general proof of name determinism. Aeneas still derives
names from declaration identities, Rust names, configuration, collision handling,
and extraction order. It does show an explicit normalization step at the
LLBC-to-Aeneas boundary.

Basis: **source** in `src/Main.ml`.

### Builtin memoization is forced before parallel work

Before reading and translating the LLBC module, `Main.ml` forces all of the
memoized builtin maps used by extraction. The accompanying comment says that
parallel execution could otherwise race on those memoized elements.

This converts lazy initialization that could occur from worker domains into a
single pre-translation initialization phase. It is another explicit
parallel-determinism safeguard.

Basis: **source** in `src/Main.ml`.

### The default translation mode is parallel at this revision

`Config.ml` sets `parallel = ref true`; the CLI option is `-sequential`, which
clears that flag.

The same source comment records that an earlier SCC race had been fixed and that
the persistent worker pool was considered usable again. Consequently, Anneal
cannot assume that ordinary Aeneas execution is sequential merely because the
upstream test suite happens to use sequential mode.

Basis: **source** in `src/Config.ml` and `src/Main.ml`.

### Parallel completion order is not used as result order

For the default pool implementation, `Parallel.parallel_filter_map_pool_aux`:

1. creates asynchronous tasks with `List.map`, preserving the input task list;
2. retains the task handles in that list order; and
3. awaits them with `List.filter_map (T.await pool) tasks`.

A worker that finishes earlier does not append its translation to a shared
completion-order list. The returned list follows task-list order.

`Translate.translate_crate_to_pure` may reorder transparent functions before
dispatch by a deterministic size-based sort intended for scheduling efficiency.
After translation, extraction constructs declaration-ID maps. Final source
emission does not walk worker completion events; `extract_definitions` walks
`ctx.crate.declarations` and looks translated declarations up by ID.

This architecture removes the most obvious scheduler-dependent source ordering
failure mode: “whichever function finished first appears first in the file.”

Basis: **source** in `src/Parallel.ml` and `src/Translate.ml`.

### Final declaration emission follows the LLBC declaration sequence

`extract_definitions` iterates `ctx.crate.declarations`. Each declaration group
selects its translated definition by identifier and emits the corresponding
type, function group, global, trait declaration, or trait implementation.

For a fixed serialized crate, this makes the LLBC declaration-group sequence an
explicit source-order input. Aeneas does not reconstruct top-level file order
from parallel completion time.

The consequence for Anneal is important: a generated-source equality test should
either compare from identical LLBC bytes or separately account for any Charon
change that reorders otherwise equivalent declarations.

Basis: **source** in `src/Translate.ml`.

### Known shared-state races were fixed before the selected revision

Two February 2026 fixes are present in the selected Aeneas revision.

First, `PureMicroPasses.ml` creates a fresh-variable-ID generator separately for
each parallel task. The source comment states that the generator must be
domain-local to avoid races on a shared mutable counter.

Second, `SCC.ml` uses `Imperative.Digraph.Concrete` rather than
`Pack.Digraph`. Its source explains that `Pack.Digraph`'s abstract vertices used
a global mutable vertex counter that was not thread-safe. The old implementation
had an assertion that randomly failed under parallel execution; the selected
implementation uses value-comparable integer vertices and unconditionally checks
that the SCC result covers the same IDs.

The corresponding history records the fixes as:

- `a6ee3423bfc3370d37f88c32e310d802d3455174` — “Fix a race condition in
  PureMicroPasses.ml”;
- `62d5293278190ed9ffd2ef489d37a74f42338069` — “Fix the race condition in
  SCC.ml by using Imperative.Digraph.Concrete instead of Pack.Digraph”;
- `adf75de33b81430e453d251ed5f129c151d472ff` — merge that reactivated parallel
  compilation by default.

These fixes are evidence about known races, not a formal audit that no other
shared mutable state can affect translation.

Basis: **source and repository history** in `src/pure/PureMicroPasses.ml`,
`src/utils/SCC.ml`, and the commits above.

### The upstream generated-output tests intentionally do not exercise default parallelism

At the selected revision, `tests/test_runner/run_test.ml` unconditionally appends
`-sequential` to the arguments used for Aeneas test translation. It also disables
the progress bar and enables checks, but the determinism-relevant fact is that
the test runner bypasses the normal parallel default.

The repository stores many automatically generated backend outputs, and its
ordinary test machinery regenerates those files. That is useful evidence that
sequential output is maintained as stable checked-in source. It is not evidence
that repeated default-parallel translation produces the same bytes.

This is the largest verification gap for Anneal's intended use: the production
default and the upstream golden-generation mode differ on the concurrency axis
most likely to expose hidden nondeterminism.

Basis: **source** in `tests/test_runner/run_test.ml` and `Makefile`.

### Source-affecting inputs are broader than the Rust program

Even if Aeneas's internal computation is deterministic, byte identity is
conditional on inputs that are intentionally rendered into or otherwise shape the
generated source. These include:

- the exact LLBC declaration identities, ordering, names, spans, and other
  metadata supplied by Charon;
- backend selection;
- namespace, subdirectory, split-file, termination/decreases, recursion,
  computability, tuple-projector, and related source-generation options;
- custom imports/includes and custom messages assembled by extraction;
- source paths or module names carried through metadata and comments where the
  selected extraction path prints them; and
- the exact Aeneas revision, because printer and naming behavior are
  implementation details.

Output-directory location by itself should not be treated as part of semantic
identity unless a generated file actually embeds it. Conversely, an LLBC source
path that appears in a generated comment is an output input even if it has no
semantic effect in Lean.

For reproducibility, Anneal should compare a declared generator-input identity,
not merely “same Rust source tree.”

Basis: **source** in `src/Translate.ml`, `src/Main.ml`, and the exact pinned
generator configuration surface.

### Sequential mode is the conservative byte-reproducibility baseline

The selected revision contains specific engineering to make parallel translation
safe and stable. Nevertheless, source inspection cannot exclude every
schedule-sensitive interaction in a large OCaml program with mutable caches,
error accumulators, graph algorithms, and backend-specific extraction state.

Because upstream tests themselves force `-sequential`, Anneal can obtain the
strongest source-backed reproducibility posture by using that mode for any
artifact whose byte identity is intended to be a hard cache key, golden output,
or cross-run invariant.

If parallel generation is materially faster and Anneal wants to depend on it, a
small repeated-run probe can promote that choice from a source-level expectation
to an observed property of the exact toolchain revision.

This recommendation concerns reproducibility. It does not assert that parallel
translation is semantically incorrect.

## Boundaries

**No fresh repeated execution.** This report did not run the selected Aeneas
binary repeatedly. It therefore does not claim an empirically established
byte-for-byte guarantee.

**No proof of race freedom.** The report identifies known race fixes and
order-preserving structures. It is not a whole-program concurrency proof.

**Successful source generation is the primary scope.** Error diagnostics,
partial files produced after recoverable translation failures, profiling output,
and progress/log ordering may have different concurrency behavior. Anneal should
not treat those streams as deterministic source artifacts unless separately
tested.

**LLBC determinism is upstream.** This report holds the serialized LLBC input
fixed. Charon output determinism is a separate corpus subject.

**Lean artifacts are downstream.** `.olean`, `.ilean`, native artifacts, traces,
and Lake state are not generated-source bytes and require separate evidence.

**Path normalization is not assumed.** If the LLBC or extraction configuration
carries different printable source/module paths, generated comments or names can
differ even when the Rust program is otherwise equivalent.

**Sequential upstream tests do not validate the default.** The checked-in Aeneas
goldens are useful but specifically insufficient as evidence for default-parallel
byte determinism.

## Revalidation

After an Aeneas upgrade, revalidate generated-source determinism in two layers.

First, inspect the implementation:

1. Check whether normal translation is parallel by default and whether upstream
   tests still force a different concurrency mode.
2. Recheck all result-collection helpers used by function and micro-pass
   translation. Completion order must not become emission order.
3. Search for shared mutable counters, generators, memoized lazy values, hash
   table iteration, random seeds, timestamps, temporary paths, and
   environment-dependent strings that can reach extraction.
4. Recheck `Main.ml` LLBC normalization, especially `short_names` handling and
   eager builtin initialization.
5. Recheck name-registration order and `extract_definitions`; generated source
   should continue to have an explicit declaration-order basis.
6. Recheck the generated-file header and formatter configuration for clock,
   locale, terminal, or path dependencies.
7. Recheck historical race fixes rather than assuming adjacent revisions retain
   the same concurrency architecture.

Second, execute an exact-pin byte probe:

1. Preserve one representative `.llbc` input and a complete Aeneas command line.
2. Generate into fresh empty output directories repeatedly in `-sequential`
   mode. Hash the sorted relative file list and every file byte.
3. Repeat the same matrix under the default parallel mode, enough times to vary
   scheduling materially.
4. Compare sequential and parallel trees. Record differences in filenames and
   bytes, not only whether Lean accepts them.
5. Repeat on at least two machines or domain-count configurations if
   default-parallel output will be a cross-host cache identity.
6. Include fixtures with recursive functions/loops, traits/impls, name
   collisions, external definitions, split files, and generated decreases
   clauses because those paths exercise naming, SCCs, fresh IDs, and
   multi-file extraction.
7. Separately vary only the output directory. If bytes change, identify which
   generated field depends on destination location.
8. Separately vary LLBC source-path spelling while holding declaration semantics
   fixed. Treat resulting byte changes as input-identity differences rather
   than generator nondeterminism.

Until that probe passes for the exact production invocation, Anneal should phrase
the property as **source-structured determinism with a parallel-execution
validation gap**, not as an unconditional byte-for-byte guarantee.
