# I086: serialized files and byte-buffer handoff around one-shot Aeneas

Observed 2026-09-29 with pinned Charon, Aeneas and Lean 4.30.0-rc2 CLIs. A tiny Rust `inc` source produced a 6,851-byte LLBC file. The **file path** passed that LLBC directly to Aeneas; the **buffer path** read its exact bytes into Python, forced a copy, materialized a second `source.llbc`, then called the same one-shot Aeneas CLI. Both runs exited 0, generated three byte-identical Lean files, and fresh file-based Lean module builds plus proof consumers passed. The LLBC digest, output digests, Charon declaration span, and generated `Source:` comment are preserved in `support/results.json` and `support/work`.

The installed Aeneas CLI advertises a required `FILE` argument. The buffer route therefore **still writes a file** before invoking Aeneas; this is a wrapper/copy measurement, not an OCaml library or structured-stream handoff. Aeneas elapsed times in this one sequential run were about 209 ms (file) and 211 ms (buffer), with sampled peak Aeneas RSS around 45 and 44 MiB. These are sampled process RSS values, not precise resident peaks or a causal speed comparison. Warm 16-repeat transfer medians for this 6.7-KiB input were about 20 µs to read, 0.4 µs for a forced Python byte copy, and 67 µs to write plus `fsync`; the one actual buffer materialization took about 132 µs. `tracemalloc` recorded about 14 KiB during read+copy and 7 KiB during the later buffer copy. The raw per-command times, RSS sample counts, byte counts and inventories are retained; Python heap allocation, RSS and disk bytes are distinct metrics.

Lean `--stdin` accepted the captured generated `Types`, `Funs` and root texts in order, emitted three OLean files, and a fresh imported proof consumer passed. This avoided materializing those generated **source** files in that route, while still requiring imported `.olean` files. It did **not** reproduce identical artifacts or diagnostics: all three stdin OLean digests differed from file compilation, and an intentionally failing proof reported `<stdin>:2:52` instead of `CheckWrong.lean:2:52`. The proof outcome and some imported semantics agreed for this fixture; module/source provenance and general imported-context equivalence were not established.

Truncated and first-byte-corrupted LLBC buffers caused Aeneas nonzero exits and no generated files. Truncating generated `Funs.lean` failed Lean compilation. A syntactically valid `1#u32`→`2#u32` mutation compiled through all three modules, but the original proof consumer failed; output hashes and a claim oracle catch a change that syntax checks alone miss. In separate active Aeneas runs, a FIFO held `Funs.lean` after `Types.lean` appeared. SIGTERM left no observed process-group member; the file and buffer cases reached the barrier at about 257 and 218 ms and exited about 1 ms after the signal, then succeeded on retry. These two timings are individual observations under local cache state, not a performance estimate.

**I086 residuals.** This is a one-shot CLI and Python-buffer approximation. It does not call a same-process OCaml Aeneas API, test a structured Aeneas stream, compare library retention of LLBC objects, prove stdin Lean module identity, measure realistic large outputs or sustained concurrency, or implement Anneal cancellation/publication. The tiny fixture and warm APFS timings cannot justify an architecture choice about file elimination. Exact bytes remain useful as independent provenance evidence here; whether memory handoff can safely avoid mandatory files requires an actual library boundary and module/import contract.

**Replay.** From this directory run `python3 support/probe.py`, then `python3 support/check.py`. The standard-library probe uses cached installed pins, one heavy subprocess at a time, a 5-GiB free-disk preflight, and no installs. It replaces only this package's `support/work` and `support/results.json`; copy the package first if retaining the original observation matters.
