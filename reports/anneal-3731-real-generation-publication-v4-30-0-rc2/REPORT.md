# Complete-generation publication over a real Charon/Aeneas/Lean model family

## Summary

A disposable gated publisher used two retained, **real** Charon LLBC, Aeneas Lean source, and Lean `.olean` generations for the same Rust fixture. It staged all seven B files privately, checked their exact set and hashes, ran fresh Lean proof and axiom oracles, then replaced one selected-generation symlink. Fresh readers saw complete A at every preparation gate and complete B after publication. An A language server opened before publication still returned `no goals` afterward under its pinned A import path. `SIGKILL` immediately before the pointer replacement left A selected; `SIGKILL` immediately after left B selected.

The controlled in-place replacement exposed four mixed A/B inventories. A fresh Lean process accepted the **old** proof at each of those mixed gates because the old compiled function artifact remained in place, even though the LLBC and later the generated source had already changed. The **new** proof passed only once the exact B family was complete. These are results of this fixture protocol and do not establish Anneal's publisher or crash durability.

## Applicability

The experiment ran on macOS arm64 with Python 3.14.7 and installed Lean `v4.30.0-rc2`, `leanprover/lean4@3dc1a088b6d2d8eafe25a7cd7ec7b58d731bd7cc`; the Lean executable hash was `b48bc5ab229bd8b320a224b87e20fc428dba6fa8a1c054bd4fa6def846e19997`. It used the installed Aeneas Lean dependency paths and `LEAN_NUM_THREADS=1`. No tool was installed or downloaded.

Generation A was copied from the retained `golden_vertical` base Charon/Aeneas/Lean model at reference commit `b1787210c0143a705f6bbbf2da3b2fba30cc5718`. Generation B was copied from the changed-model artifacts in `anneal-3731-embedded-proof-generated-model-vertical-v4-30-0-rc2`, where the source changed `wrapping_add(1)` to `wrapping_add(2)` and Charon/Aeneas/Lean regenerated the model. This experiment reused those generated bytes; it did not rerun Charon or Aeneas. The paired A/B proof texts and both complete seven-file families are retained under `support/inputs/`.

The experiment's generation ID is SHA-256 of canonical JSON containing the seven relative file names and SHA-256 hashes. It is an experiment-local content identity: A is `bc62fce58f5d7edca726224f9174b1bc41ed706a4ced9bca8bafaededd6da2a9`; B is `620055318c21f7616fb671ce0c33f3f289b9a6f237d21aeddb48c0fa5c5d4e4b`. The IDs differ from the earlier report's host/model generation IDs because this experiment hashes a different, explicitly defined inventory. A mixed inventory has **no generation ID** in the result.

## Findings

### Exact artifact family and oracle

Each generation has `current.llbc`, `Current/Types.lean`, `Current/Types.olean`, `Current/Funs.lean`, `Current/Funs.olean`, `Current.lean`, and `Current.olean`. The retained manifest hashes match all seven bytes in each input family. The entry `Current.olean` is byte-identical across A and B (`34547467aa8017d1ff0efebc746e14a1b50ef6cb446e9aa1404d09cc0ffef149`), while `Current/Funs.olean` changes from `2320c0125c0e0748942a5fde0e6d204b4f77b9cd3f6ac7abf7f43f9c97c4546c` to `57bcadabf1795a8540685e174966444097701f49da4c704446a2bb5ae5d94871`. A reader that checks only the entry `.olean` would miss this model change.

The fresh oracle checks the actual old `.ok 1#u32` and new `.ok 2#u32` theorem texts with `lean --json`, appends a fixed proposition consumer, and runs `#print axioms obl_inc`. Under A, old passes and new fails. Under B, old fails and new passes. Successful checks reported `[propext, Classical.choice, Quot.sound]` and no `sorryAx`. This checks one proposition under these retained imports; it does not prove the generated translation or a Rust-level obligation. Basis: **execution**, `support/results.json` command records, source hashes, return codes and streams.

### Staged publication and pinned old server

The writer copied B privately in the fixed order LLBC, Types source/artifact, Funs source/artifact, and entry source/artifact. It paused after each copy; a separate reader resolved the selected symlink and hashed the full selected directory at every gate. All seven snapshots remained exact A. The writer then required the exact B inventory and old-fail/new-pass fresh Lean oracle, paused at `validated`, moved the B directory into `generations/B`, paused at `generation-moved`, and paused immediately before and after `os.replace(current.next, current)`. The selected pointer stayed exact A through `before-publish` and was exact B at `after-publish`. Fresh Lean checks at `validated` saw A old-pass/new-fail; at `after-publish` they saw B old-fail/new-pass.

Before B preparation, a Lean `--server` process opened the old proof with `LEAN_PATH` pinned to the resolved `generations/A` directory and returned `no goals`. The same server process returned `no goals` after B publication, then exited cleanly. Its result is explicitly A generation guidance, not a current-B answer. The exact JSON-RPC messages, process ID, and two responses are retained. Basis: **execution** for the filesystem, fresh Lean, and server observations; the publication guard is fixture-local Python.

### Coordinated in-place control

The control copied the same B files in the same order directly over `generations/A`, pausing after each write. The selected symlink still pointed to that path. After the first four writes, the seven-file inventory matched neither A nor B, and the reader classified it `mixed` with no generation ID. Fresh Lean still accepted the old proof and rejected the new proof at each mixed gate. The LLBC changed at `write-0`; by `write-3`, both LLBC and `Current/Funs.lean` were B while `Current/Funs.olean` was A. This is a concrete source/compiled-artifact inconsistency that can look successful to a proof-only reader if the answer is mislabeled current.

At `write-4`, replacing `Current/Funs.olean` made the inventory exact B and flipped the fresh Lean result to old-fail/new-pass. The last two writes copied files whose A and B bytes were identical, so the family stayed B. The experiment did **not** observe acceptance of the new proof under a mixed family. Its counterexample is the earlier mixed family with an accepted old proof; the reader must retain the `mixed` label and decline current-generation acceptance. Basis: **execution**, all seven per-gate inventories and both fresh Lean command outcomes in `support/results.json`.

### Kill boundaries and selected readback

In separate clean roots, the staged writer was killed with `SIGKILL` at `before-publish` and at `after-publish`. Both writers had validated the exact B inventory and fresh old-fail/new-pass Lean oracle before the kill. The first root read back exact A, generation `bc62fce5…`; the second read back exact B, generation `62005531…`. A complete unselected B directory remained in the first root; this experiment did not test orphan cleanup. These are process-kill observations, not power-loss or storage-durability claims. Basis: **execution**, child exit codes, gate order, selected readback hashes, and validation records in `support/results.json`.

## Boundaries

- **Not examined:** Anneal V2 publisher, its editor/MCP readers, Lake archive or cache format, production input-closure key, parallel publishers, garbage collection and reader leases, model regeneration during publication, or end-to-end source-to-proof acceptance.
- **Not established:** power-loss durability, `fsync` ordering, cross-filesystem behavior, or other host filesystem semantics. `SIGKILL` terminates the writer process while the OS and its caches remain available.
- **Not established:** a general theorem that every mixed generated family will be rejected by Lean. Here the old proof passed during four mixed states and the new proof first passed when the exact B inventory appeared.
- **Not established:** safe behavior for readers that repeatedly resolve `current` between component opens. The fixture's inventory reader resolves once per gate, and the old Lean server is pinned to A. The earlier `anneal-interactive-model-probes-2026-09-29` report records a controlled two-open symlink-swap mix.
