# Drop-In libav* Shared-Library Symbol Versioning, avpriv_* Cross-DSO Elimination, Hardware-Context ABI Layouts, and H.264 MBAFF/PAFF Interop

## Summary

Achieving binary-level drop-in dynamic-library (`DSO` / `.dylib` / `.dll`) replacement for FFmpeg's seven public shared libraries—`libavutil` (`v61`), `libswresample` (`v7`), `libswscale` (`v10`), `libavcodec` (`v63`), `libavformat` (`v63`), `libavfilter` (`v12`), and `libavdevice` (`v63`)—requires satisfying four loader, ABI, and codec invariants that are invisible to source-level C API wrappers:

1. **Seven-library symbol versioning and `avpriv_*` cross-DSO coupling:** Exhaustive source analysis of `FFmpeg/FFmpeg` (`7ddf7bc8a482cf28b4fab2e63b7093ba35cb6a80`) identifies exactly **60** distinct `avpriv_*` identifiers across the entire repository: **56** shared-library C function definitions (**28** in `libavutil`, **17** in `libavcodec`, **11** in `libavformat`, and **0** in `libswresample`, `libswscale`, `libavfilter`, or `libavdevice`), plus **4** non-DSO entries (1 conditional `compat/strtod.c` polyfill `avpriv_strtod`, 1 `static av_always_inline` header helper `avpriv_mirror`, 1 orphan Doxygen identifier `avpriv_smpte_436m_coded_anc_payload_size`, and 1 stale comment `avpriv_mpeg4audio_get_config`). None of the **148** installable public C headers (`HEADERS` + `ARCH_HEADERS` + `BUILT_HEADERS`) or `fftools` CLI programs link any `avpriv_*` symbol. Consequently, a **homogeneous 7-library Rust replacement** eliminates 100% of `avpriv_*` exports cleanly, whereas **heterogeneous single-DSO replacement** (e.g., swapping only `libavcodec.so.63` beneath upstream C `libavformat.so.63` and `libavfilter.so.12`) requires preserving 16 `avpriv_*@LIBAVCODEC_63` functions and their private C struct layouts.
2. **Naive `rustc --crate-type=cdylib` breaks ELF symbol versioning under `rust-lld`:** Empirical execution on `rustc 1.98.0-nightly` (`14210df0e27ccd7d9e6a05b8085cbd438e4bbc65`) proves that passing `-Clink-arg=-Wl,--version-script=libavcodec.ver` to a `cdylib` crate fails to attach `@@LIBAVCODEC_63` to `#[no_mangle]` exports and leaks internal `#[no_mangle]` symbols despite `local: *;`. Because `rustc` prepends its own anonymous `-Wl,--version-script=/tmp/.../list` (`{ global: ...; local: *; };`) and `-Wl,--no-undefined-version` ahead of user `-Clink-arg`s, `rust-lld` binds every `#[no_mangle]` symbol to unversioned `VER_NDX_GLOBAL` (`Index 1`), causing prebuilt Linux binaries with `VERNEED` `LIBAVCODEC_63` to fail at `ld.so` startup. Two verified architectures resolve this cleanly: (A) linking a `staticlib` with `cc -shared -Wl,--whole-archive` under a single `--version-script`, or (B) keeping Rust implementation functions unexported and binding them via `core::arch::global_asm!(".globl {s}\n.symver {s}, sym@@LIBAVCODEC_63, remove", s = sym impl_fn)`.
3. **Hardware-context struct offset traps (`AVHWDeviceContext` / `AVHWFramesContext`):** Across VA-API, Vulkan, CUDA, D3D11VA, and D3D12VA, callers allocate hardware contexts via `libavutil` (`FFHWFramesContext` embeds `AVHWFramesContext p` at offset `0` in `libavutil/hwcontext_internal.h:102-135`) and mutate `hwctx` fields directly by static byte offset. Critical layout hazards include `AVVulkanDeviceContext` (`1,360` bytes on LP64/LLP64) embedding a `240`-byte `VkPhysicalDeviceFeatures2` by value plus a `16`-byte conditional `#if FF_API_VULKAN_SYNC_QUEUES` block (`hwcontext_vulkan.h:119-138`), and `AVVkFrameFlags` (`hwcontext_vulkan.h:158-166`), whose `(1ULL << 0)` enumerator still compiles to a **4-byte** `unsigned int` under ISO C11 §6.7.2.2 (`offsetof(AVVulkanFramesContext, img_flags) == 84`, whereas a mistaken Rust `#[repr(u64)]` shifts `img_flags` to `88` and corrupts `lock_frame` at `128`).
4. **H.264 interlaced MBAFF and PAFF field-pair invariants:** Interlaced H.264 (`ITU-T Rec. H.264` clauses 6.4, 8.2.1, 8.4, 8.7, 9.3.3.1.1) delivers both PAFF complementary field pairs and MBAFF macroblock-adaptive frames inside a **single weaved `AVFrame`** (`AV_FRAME_FLAG_INTERLACED = 1 << 3`, `AV_FRAME_FLAG_TOP_FIELD_FIRST = 1 << 4`), using signed `ptrdiff_t` (`isize`) `linesize` doubling (`mb_linesize = linesize * 2`) and odd-MB pointer rewind (`dest_y -= linesize * 15`), doubled reference indices (`ref_count[list] << FRAME_MBAFF`), deferred CABAC `mb_skip_flag` lookahead before `mb_field_decoding_flag`, a 4-mode `left_block_options[4][32]` neighbor remapping table, and asymmetrical 2-pass horizontal (`bS = 3`) / 8-element vertical (`bS[8]`, dual-`QP`) deblocking across mixed frame/field macroblock-pair edges.

Three non-obvious build invariants emerge directly from `configure` and `libav*/*.v`:
1. **Unintended `av*;` wildcard over-export in `libavutil.v` and `libavformat.v`:** Because `libavutil.v:3` and `libavformat.v:3` write `av*;` (without a trailing underscore) to cover `av_`, `avutil_`, `avio_`, `avformat_`, and `avpriv_` in one token, any non-`static` internal function starting with `av` is exported in `.dynsym` even if omitted from `HEADERS` (for example, `libavutil/integer.h` is installed in `HEADERS`, whereas internal fixed-point AAC helpers or debug symbols matching `av*` leak automatically unless declared `static` or renamed `ff_*`).
2. **macOS `VERSION_SCRIPT_POSTPROCESS_CMD` wildcard expansion (`configure:6139-6140`):** On Darwin, FFmpeg transforms `.v` files for `ld64 -exported_symbols_list` via:
   ```sh
   tr " " "\n" | sed -n /global:/,/local:/p | grep ";" | tr ";" "\n" | sed -E "s/(.+)/_\1/g" | sed -E "s/(.+[^*])$$$$/\1*/"
   ```
   The final `sed` expression appends `*` even to exact symbol names lacking a wildcard (`avsubtitle_free` in `libavcodec.v:6` becomes `_avsubtitle_free*`). A clean-room Rust build targeting macOS should emit exact symbol lists (`_avsubtitle_free`) rather than copying that `sed` accident.
3. **`libavutil/version_major.h` is intentionally empty (`lines 22-23`):** Unlike the other six libraries (which define `LIB*_VERSION_MAJOR` in `version_major.h`), `libavutil` defines `LIBAVUTIL_VERSION_MAJOR 61` inside `libavutil/version.h:81` and keeps `libavutil/version_major.h` as an uninstalled empty stub solely to satisfy `ffbuild/libversion.sh` Makefile prerequisites.

`Basis: source + derived`

#### 2.5 Architectural Verdict on `avpriv_*` Elimination

- **Homogeneous Deployment (All 7 `cdylib`s Replaced as an Atomic Suite — Recommended):** **Zero `avpriv_*` symbols should be exported.** External applications (`vlc`, `mpv`, `chromium`, `gstreamer-libav`, `obs-studio`, `ffmpeg` CLI) link strictly against public `av_*` / `avcodec_*` / `avformat_*` / `avfilter_*` / `avdevice_*` / `sws_*` / `swr_*` symbols declared in the 148 installed headers. Internally, shared parsers (`ac3`, `adts`, `dca`, `mpeg4audio`, `xiph`, `tak`) live in pure safe Rust rlib crates statically linked (or shared via an internal Rust rlib/dylib) without C-ABI exposure, eliminating cross-DSO raw-pointer downcasts (`avctx->priv_data as *const H264Context`, `st as *mut FFStream`) and Windows cross-CRT `FILE*` UB (`avpriv_fopen_utf8`).
- **Heterogeneous / Incremental Strangler Deployment:** Because `libavdevice` downcasts `AVStream*` -> `FFStream*` via `avpriv_set_pts_info` and `libavformat` calls `avpriv_h264_has_num_reorder_frames(AVCodecContext*)` (which in upstream C casts `avctx->priv_data` to `H264Context*`, **unless** the Rust `libavcodec` implements `avpriv_h264_has_num_reorder_frames` itself by inspecting its own Rust H.264 decoder state via `avctx->codec` identity check before touching `priv_data`!), `libavformat` and `libavdevice` must always be replaced together as a single unit, while a standalone Rust `libavcodec.so.63` linked beneath C `libavformat.so.63` must export the 16 consumed `avpriv_*@LIBAVCODEC_63` shims and guard `avpriv_h264_has_num_reorder_frames` and `avpriv_codec_get_cap_skip_frame_fill_param` against foreign `AVCodec*` / `priv_data` pointers.

### 3. Cross-Platform Rust Shared-Library Emission: ELF `.symver`, macOS Two-Level Namespaces, and Win64 `.def` Exports

`Basis: execution + source + normative`

#### 3.1 Linux / BSD ELF64: The `rustc` `cdylib` Dual `--version-script` Failure and Two Verified Remedies

Prebuilt ELF binaries on Linux distributions record both `DT_NEEDED` (`libavcodec.so.63`) and `.gnu.version_r` (`VERNEED`) symbol version tags (`avcodec_version@LIBAVCODEC_63`). Testing `rustc 1.98.0-nightly` (`14210df0e27ccd7d9e6a05b8085cbd438e4bbc65`) with `--crate-type=cdylib -Clink-arg=-Wl,-soname,libavcodec.so.63 -Clink-arg=-Wl,--version-script=libavcodec.ver` revealed a critical linker failure (`Basis: execution`):

1. **Root cause in `rustc` + `rust-lld`:** When building a `cdylib`, `rustc` invokes `cc -fuse-ld=lld` and **automatically prepends** `-Wl,--version-script=/tmp/.../rustcXXXXXX/list` and `-Wl,--no-undefined-version` *before* any user `-Clink-arg`. That compiler-generated `list` file places every `#[no_mangle]` and `#[export_name]` symbol into an **anonymous** global version block (`{ global: avcodec_version; av_packet_alloc; avpriv_should_stay_hidden; local: *; };`). When `rust-lld` processes the user's second `--version-script=libavcodec.ver` (`LIBAVCODEC_63 { global: av_*; avcodec_*; avsubtitle_free; local: *; };`), symbols already matched by the first anonymous script retain version index **`1 (*global*)` (unversioned!)**, and any `#[no_mangle]` internal helper (`avpriv_should_stay_hidden`) remains **publicly exported** instead of hidden by `local: *;`. Even worse, applying GNU `as` 3-argument `.symver __impl, sym@@LIBAVCODEC_63, remove` to an `#[export_name = "__impl"]` function causes `rust-lld` to abort with `error: version script assignment of 'global' to symbol '__impl' failed: symbol not defined` because `.symver ..., remove` deletes `__impl` before `rust-lld` checks `rustcXXXXXX/list` under `--no-undefined-version`.

2. **Verified Remedy A (`--crate-type=staticlib` + Single C/LLD Shared Link — Recommended for Multi-OS Parity):**
   Compile the Rust implementation crate as `--crate-type=staticlib -C panic=abort` (`#[unsafe(no_mangle)] pub extern "C" fn avcodec_version() -> u32`), then invoke `cc`/`clang` `-shared -Wl,-soname,libavcodec.so.63 -Wl,--version-script=libavcodec.ver -Wl,--whole-archive liblavc.a -Wl,--no-whole-archive -Wl,--gc-sections`.
   - **Verified `readelf -W --dyn-syms` result:** Every matching public symbol (`av_packet_alloc@@LIBAVCODEC_63`, `avcodec_version@@LIBAVCODEC_63`, `avsubtitle_free@@LIBAVCODEC_63`) receives `.gnu.version` index `2` (`LIBAVCODEC_63` default `@@` definition), `avpriv_should_stay_hidden` is completely hidden, `--gc-sections` strips unused `libstd` dead code down to 7 total `.dynsym` entries, and an external C executable compiled with `gcc caller.c -L. -lavcodec` records `UND avcodec_version@LIBAVCODEC_63` and executes cleanly (`0x3f1c64`).

### 5. H.264 Interlaced MBAFF and PAFF Field-Pair Invariants Across the C/Rust Boundary

`Basis: normative + source`

Clean-room H.264 decoders frequently implement progressive frame coding (`frame_mbs_only_flag == 1`) first and underestimate the invasive structural impact of **PAFF** (Picture-Adaptive Frame-Field, `frame_mbs_only_flag == 0 && field_pic_flag == 1`) and **MBAFF** (Macroblock-Adaptive Frame-Field, `frame_mbs_only_flag == 0 && field_pic_flag == 0 && mb_adaptive_frame_field_flag == 1`) across `AVFrame` buffer lifetimes, stride arithmetic, POC/reference lists, CABAC parsing, and deblocking (`ITU-T Rec. H.264` clauses 6.4, 7.4.3, 8.2.1, 8.4, 8.7, 9.3.3.1.1; `FFmpeg/FFmpeg@7ddf7bc8a482cf28b4fab2e63b7093ba35cb6a80`).

#### 5.1 Single-`AVFrame` Weave Layout, PAFF Complementary Field Sharing, and Signed `linesize`

Across the C/Rust `avcodec_receive_frame()` boundary (`libavutil/frame.h:496-525, 702-706`), **FFmpeg never emits separate half-height `AVFrame`s to the caller for decoded H.264 PAFF complementary field pairs or MBAFF frames**:
- Both MBAFF frames and PAFF complementary field pairs (top field slice(s) followed by bottom field slice(s), or bottom-first) decode into a **single full-frame `AVFrame`** of dimensions `width x height` where even scanlines (`2y`) hold the top field and odd scanlines (`2y + 1`) hold the bottom field (**weave layout**), setting `frame->flags |= AV_FRAME_FLAG_INTERLACED` (`1 << 3`) and conditionally `AV_FRAME_FLAG_TOP_FIELD_FIRST` (`1 << 4`, when `field_poc[0] <= field_poc[1]` or SEI `pic_struct` signals top-field-first).
- **PAFF second-field buffer aliasing (`libavcodec/h264_slice.c:1658-1665`):** When the second field of a complementary PAFF field pair arrives in a subsequent NAL access unit, it **reuses the `cur_pic_ptr` `AVFrame` buffer allocated by the first field**, offsetting row 0 of `PICT_BOTTOM_FIELD` by `+linesize` bytes (`data[p] + linesize[p]`) and stepping rows by `2 * linesize[p]`. Crucially, in frame-threaded decoding (`await_references`, `libavcodec/h264_mb.c:66-75`), the second field of a PAFF picture **can reference the first field of the exact same `AVFrame`** (`(ref->reference & 3) != h->picture_structure`), so per-field thread progress (`tf.progress` tracked separately for top and bottom fields) is required to prevent self-deadlock while avoiding data races on the shared weave buffer!
- **Negative `linesize[]` UB trap in Rust (`libavutil/frame.h:496-523`):** Callers supplying custom `get_buffer2` allocators are explicitly permitted by `frame.h:521-522` to pass **negative** `linesize[p]` (`int`) with `data[p]` pointing to the last row of the image! Converting `linesize[p]` to `usize` wraps negative strides to `~2^64` and causes out-of-bounds pointer arithmetic; every Rust plane-indexing helper must represent stride as **`isize`** (`ptrdiff_t`) and validate the signed bounding interval `[min_offset, max_offset]` against the backing `AVBufferRef` allocation before constructing slices or invoking SIMD kernels.

#### 5.2 MBAFF Macroblock-Pair Addressing and `mb_linesize` Switching

In MBAFF (`FRAME_MBAFF(h) == 1`), macroblocks are coded in vertical **$16 \times 32$ luma macroblock pairs** at `(mb_x, mb_y & ~1)` (top MB `mb_y = 2k`, bottom MB `mb_y = 2k + 1`, `h264_slice.c:82-114`):
- **Frame-coded pair (`MB_FIELD == 0`):** Top MB covers luma rows `32k .. 32k + 15` (`dest_y = base + 32k * linesize`) with `mb_linesize = linesize`; bottom MB covers rows `32k + 16 .. 32k + 31` (`dest_y = base + (32k + 16) * linesize`) with `mb_linesize = linesize`.
- **Field-coded pair (`MB_FIELD == 1`):** Top MB covers the **16 even rows** `32k, 32k + 2, ..., 32k + 30` (`dest_y = base + 32k * linesize`) with **`mb_linesize = 2 * linesize`**; bottom MB covers the **16 odd rows** `32k + 1, 32k + 3, ..., 32k + 31` (`dest_y = base + (32k + 1) * linesize` — computed in `h264_slice.c:93-110` as `(32k + 16) * linesize - 15 * linesize`!) with **`mb_linesize = 2 * linesize`** (and `mb_uvlinesize = 2 * uvlinesize`, rewinding odd chroma by `(block_h - 1) * uvlinesize` where `block_h = 8` for 4:2:0 and `16` for 4:2:2/4:4:4).
- **Chroma 4:2:0 vertical phase shift (`h264_mb.c:289`):** Under ITU-T H.264 §8.4.2.2.2, when a field MB (`MB_FIELD == 1` or `FIELD_PICTURE == 1`) references a field of opposite parity in 4:2:0 (`chroma_format_idc == 1`), vertical chroma motion vectors carry an extra $\pm 2$ eighth-sample phase offset (`mv_y + 2` for top-referencing-bottom, `mv_y - 2` for bottom-referencing-top) because 4:2:0 top and bottom chroma fields are sited at $0.25$ and $0.75$ luma-pair spacing rather than $0.0$ and $0.5$!

#### 5.3 Picture Order Count (`field_poc[2]`) and Doubled MBAFF Reference Lists

In `libavcodec/h264_parse.c` (`ff_h264_init_poc`, `lines 280-360`, implementing ITU-T H.264 §8.2.1):
- Every decoded picture tracks **three** POC integers: `field_poc[0]` (TopFieldOrderCnt), `field_poc[1]` (BottomFieldOrderCnt — adjusted by `delta_poc_bottom` in POC type 0 or `offset_for_top_to_bottom_field + delta_poc[1]` in POC type 1 when `picture_structure == PICT_FRAME`), and `poc = min(field_poc[0], field_poc[1])` (`line 357`). Note lines `350-352` explicitly guard signed 32-bit overflow via `int64_t field_poc[2]` (`field_poc[i] != (int)field_poc[i] -> AVERROR_INVALIDDATA`), which a panic-free Rust decoder must replicate with `i64` -> `i32::try_from`.
- **Reference list doubling in MBAFF (`h264_direct.c:64-69, 268`):** While slice headers specify frame-level `RefPicList0`/`RefPicList1` (`ref_count[list]` entries, up to 16), field-coded macroblocks inside an MBAFF slice index **field** reference lists of length **`2 * ref_count[list]`** (up to **32** entries, `ref_idx` `2r` selecting same-parity field and `2r + 1` selecting opposite-parity field of frame `r`!), and temporal `B_Direct_16x16` motion-vector scaling (`DistScaleFactor`) switches dynamically per macroblock pair between frame `poc` (when `MB_FIELD == 0`) and `field_poc[mb_y & 1]` (when `MB_FIELD == 1`).

#### 5.4 CABAC Deferred `mb_field_decoding_flag` Lookahead and 4-Way Neighbor Table

MBAFF introduces three non-local CABAC state couplings (`ITU-T H.264` §7.3.4 & §9.3.3.1.1; `libavcodec/h264_cabac.c:1342-1376, 1660-1686, 1935-2030` and `h264_mvpred.h:487-555`):
1. **Deferred `mb_field_decoding_flag` on skipped top MB (`h264_cabac.c:1935-1964`):** In P/B MBAFF slices, `mb_field_decoding_flag` is signaled **once per macroblock pair**, *only if at least one of the two macroblocks in the pair is non-skipped*! If the top MB (`(mb_y & 1) == 0`) decodes `mb_skip_flag == 1`, the decoder **cannot** yet know whether the skipped top MB is a frame MB or a field MB (`decode_mb_skip` motion vector prediction depends on `MB_FIELD`!): it must immediately peek/decode `next_mb_skipped = decode_cabac_mb_skip(mb_x, mb_y + 1)` (`line 1943`), and:
   - if `next_mb_skipped == 0`, decode `mb_field_decoding_flag` **before** reconstructing the skipped top MB (`line 1945`) and cache `next_mb_skipped = 0` for the bottom MB;
   - if `next_mb_skipped == 1` (both MBs skipped), infer `mb_field_decoding_flag` without reading a bit from the bitstream via left-pair / top-pair neighbor inheritance (`predict_field_decoding_flag`, `h264_slice.c:138-144`, defaulting to `0` when neither neighbor pair belongs to the current slice)!
2. **4-Way Left-Neighbor Partition Remapping (`h264_mvpred.h:491-541`):** Because a `16x32` left neighbor pair (`left_mb_field_flag`) and current pair (`curr_mb_field_flag`) can disagree in field/frame mode, `fill_decode_neighbors` selects among four `left_block_options[4][32]` 4x4 subblock tables: `(0)` homogeneous (`frame<-frame` or `field<-field`), `(1)` bottom-frame reading field-pair (`[2, 2, 3, 3]`), `(2)` top-frame reading field-pair (`[0, 0, 1, 1]`), and `(3)` field-MB reading frame-pair (`[0, 2, 0, 2]`, mapping top/bottom 4x4 rows across both `left_xy[LTOP]` and `left_xy[LBOT] = left_xy[LTOP] + mb_stride`!).
3. **Field vs. Frame Scan and Significance Context Switching (`h264_cabac.c:1662-1686`):** Residual decoding switches per macroblock between frame zig-zag scan (`zigzag_scan` / `zigzag_scan8x8`) and alternate field scan (`field_scan` / `field_scan8x8`), and shifts CABAC context-index offsets by `significant_coeff_flag_offset[MB_FIELD(sl)][cat]` and `last_coeff_flag_offset[MB_FIELD(sl)][cat]`.

#### 5.5 Asymmetrical Mixed-Mode MBAFF Deblocking (`ITU-T H.264` §8.7)

Standard progressive deblocking (`ff_h264_filter_mb_fast`, `h264_loopfilter.c:421`, gated by `av_assert2(!FRAME_MBAFF(h))`!) cannot run on MBAFF frames because mixed frame/field boundaries break 4-edge symmetry (`h264_loopfilter.c:494-575, 730-805`):
1. **Double-pass top horizontal edge (`dir == 1`, `h264_loopfilter.c:494-540`):** When a top **frame** MB (`(mb_y & 1) == 0 && !MB_FIELD`) sits directly below a **field-coded** macroblock pair (`IS_INTERLACED(mbm_type & ~mb_type)`), its top horizontal boundary must be filtered **twice** at doubled stride `2 * linesize`—once against the upper pair's top field MB (`mb_xy - 2 * mb_stride` on `img_y[0]`) and once against the upper pair's bottom field MB (`mb_xy - mb_stride` on `img_y[linesize]`)—with intra strength **`bS = 3`** (not `4`!).
2. **8-element left vertical edge with dual `QP` (`dir == 0`, `h264_loopfilter.c:730-805`):** When `IS_INTERLACED(mb_type ^ sl->left_type[LTOP])`, the left macroblock edge has **8 distinct boundary strengths `bS[0..7]`** (instead of 4) and **two distinct averaged quantizers `qp[0]` and `qp[1]`** (`(mb_qp + mbn0_qp + 1) >> 1` and `(mb_qp + mbn1_qp + 1) >> 1` against `left_mb_xy[0]` and `left_mb_xy[1]`), filtered via dedicated `filter_mb_mbaff_edgev` / `filter_mb_mbaff_edgecv` kernels.
