# R428 Lake invalidation canary and guarded resource stop

## Result

The [pinned R428 source report](../lake-olean-invalidation-v4-30-0-rc2/REPORT.md) (SHA-256 `058707d092a64bdce2ee34b195ab31d8a889220791c6797797d9c72cb829d397`) proposes an empirical Lake `.olean` invalidation matrix. This package records a **preflight canary only**. It does **not** execute any source/configuration mutation or other invalidation matrix case, and it does not provide a 4.30-versus-4.34 invalidation behavior comparison.

The corrected, isolated 4.30.0-rc2 canary built one path dependency (`Dep`) and two consumer modules (`Core`, `Main`) successfully with `lake --no-cache -v build Core Main`. Lake reported seven jobs. The retained workspace has all three `.olean`, `.ilean`, and `.trace` files, with exact hashes, sizes, and original mtimes in [raw/old/record.json](raw/old/record.json). This establishes that the tiny fixture and exact older Lake toolchain can produce the artifacts needed for a later matrix. Its **sampled process-group RSS reached 1,046,032 KiB**, only 2,544 KiB below the 1 GiB stop cap.

The same corrected fixture under Lake 4.34.1 passed prelaunch admission but exceeded the mandatory process-group cap during its initial build. The runner sampled **1,096,880 KiB**, killed the process group, and recorded Lake exit `-9` after 3.838 seconds. Only package-configuration outputs had been written; no `Dep`, `Core`, or `Main` module `.olean`, `.ilean`, or `.trace` artifact had been produced. This is a **resource-bound termination**, not a compiler failure or an observed invalidation difference. No further Lake child was launched after it.

An earlier **excluded fixture-setup attempt** appears under [preliminary/old-unregistered-core](preliminary/old-unregistered-core/). It ran the old tool under the same guard but specified `Main` without registering local `Core` as a Lake library target. Lake exited 1 with `unknown module prefix 'Core'`. The fixture was corrected by adding `lean_lib Core` and building both `Core` and `Main`; the failed setup attempt is not counted as a canary result or Lake behavior difference.

## Remaining R428 matrix

Every requested invalidation dimension remains **untested**: semantic source change, LF/CRLF normalization, relocation, `leanOptions`, `moreLeanArgs`, `weakLeanArgs`, original package name versus version, imported artifact identity, extra dependency targets, platform/dynamic-library inputs, missing trace or output, ordinary versus `--old`, and disabled versus seeded artifact-cache hashes. There was no `--no-build` follow-up, trace before/after mutation, cache restoration, or Lean invocation-count comparison. The old canary's initial `.trace` files are preserved for future work, but they have not been subjected to a mutation. A future full matrix needs a higher RSS allowance or a smaller validated fixture under the same hard cap, then a fresh resource admission; this run did not relax the cap.

[Raw stdout/stderr and machine records](raw/), the excluded [preliminary attempt](preliminary/), and [analysis.json](analysis.json) retain the exact evidence. `python3 -B support/check.py` verifies fixture hashes, Lake identities, guarded admission arithmetic, captured streams, all retained workspace file hashes and sizes, presence of recorded mtime fields, old module outputs, the new cap termination, and exclusion of the setup failure without launching Lake. It is designed to work after package relocation; the recorded absolute argv and cwd are provenance, while file verification uses relative package paths. Relocation can change filesystem mtimes, so the checker does not compare current mtimes to those captured during the run.
