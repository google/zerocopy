# Pinned editor API and projection precedents for an interactive Anneal

## Summary

The selected upstream APIs support a conservative adapter: keep the complete authored input and imported Lean environment as explicit job inputs, treat live goals as versioned editor observations, enumerate every generated-to-authored edit mapping, and decline edits whose ownership is ambiguous or crosses generated text. This is a design inference, not an observation of an Anneal V2 implementation. The [earlier architecture-contracts report](../anneal-3730-architecture-contracts-2026-09-29/REPORT.md) compared broad topologies and upstream overviews; this report narrows its I002/I003/I008 gaps to pinned Lean and rust-analyzer API call sites and Volar edit transformation code.

A standard-library Python fixture based on the inspected source-map rules produced two authored destinations for one generated edit; reversing mapping order changed a first-result choice from source range `[27,33]` to `[64,70]`. With cross-mapping fallback, another virtual range produced a candidate authored range `[30,67]` that included an intervening Rust function boundary. A modeled completion transformation retained one mapped auxiliary edit and dropped one generated-only auxiliary edit. A proposed strict, atomic proof-edit policy rejected all three cases. These are **execution of an independent model**, not executions of Volar, Lean, rust-analyzer, Razor, or Anneal.

## Applicability

This report concerns the exact source revisions in `REPORT.json`: Lean 4 `3dc1a088b6d2d8eafe25a7cd7ec7b58d731bd7cc` (the selected v4.30.0-rc2 pin), rust-analyzer `03fcb77246f2568adb0e9b2fa60d19c6cc1686f4`, and Volar `44d58aee30d1d476c8ad3f6f5581b288d7185d1e`. The rust-analyzer guide stored at that commit says its narrative describes the 2024-01-01 release, so current API assertions below are taken from the pinned `crates/ide/src/lib.rs`; guide-only architectural explanation is marked as such. The Volar investigation uses its source-map and language-service implementation at the pinned commit, not a Vue extension or a running language server.

The toy host is ASCII Rust text with two `/// @lean by rfl` annotations; the toy virtual document contains two `by rfl` spans separated by a generated-only wrapper. Three explicit mappings intentionally include two authored spans targeting one virtual span. This is a *falsification fixture for a proposed projection contract*, not Anneal's annotation parser or a prediction that Volar normally emits this exact mapping. Python 3 standard library is the sole runtime; no upstream language server or dependency was installed. The analyzed source files' immutable URLs, SHA-256 values, and narrow review scopes are in `support/upstream-source-ledger.json`.

## Findings

### Editor queries and compiler acceptance have different observable contracts (I002)

The [pinned Lean server protocol overview](https://github.com/leanprover/lean4/blob/3dc1a088b6d2d8eafe25a7cd7ec7b58d731bd7cc/src/Lean/Server/ProtocolOverview.lean#L56-L85) says clients must first `didOpen` every queried file, closed-file notifications are discarded and requests error, `initialize.rootUri` is ignored in favor of server cwd, and most standard client capabilities are ignored. It advertises `.lean`/`.ilean` watchers and a Lean-specific `didOpen` build-mode extension. In the [pinned extension types](https://github.com/leanprover/lean4/blob/3dc1a088b6d2d8eafe25a7cd7ec7b58d731bd7cc/src/Lean/Data/Lsp/Extra.lean#L20-L55), `always`, `once`, and `never` control dependency builds; `waitForDiagnostics` completes after diagnostics for a document version **greater than or equal to** the requested version. The [plain-goal request](https://github.com/leanprover/lean4/blob/3dc1a088b6d2d8eafe25a7cd7ec7b58d731bd7cc/src/Lean/Data/Lsp/Extra.lean#L99-L111) extends position params without an exact document-version field; the [RPC call params](https://github.com/leanprover/lean4/blob/3dc1a088b6d2d8eafe25a7cd7ec7b58d731bd7cc/src/Lean/Data/Lsp/Extra.lean#L225-L234) carry a session ID and position, not an imported-artifact digest. **Basis: source.** These field facts mean that a response's bare goal text is insufficient as an Anneal verification witness; this last statement is **derived**, and does not assert that the Lean server always returns stale data. The existing `anneal-3730-lean-protocol-races-v4-30-0-rc2` and `anneal-3730-lean-protocol-import-deletion-v4-30-0-rc2` packages supply separate pinned **execution** examples of old-version waits and stale import observations.

The [rust-analyzer guide](https://github.com/rust-lang/rust-analyzer/blob/03fcb77246f2568adb0e9b2fa60d19c6cc1686f4/docs/book/src/contributing/guide.md#L16-L76) describes an IDE-first, I/O-free analysis host fed explicit file and crate-graph changes and answering current-state queries. Its dated narrative should not be treated as an exact current-commit implementation claim. At the inspected commit, [`AnalysisHost::analysis` and `apply_change`](https://github.com/rust-lang/rust-analyzer/blob/03fcb77246f2568adb0e9b2fa60d19c6cc1686f4/crates/ide/src/lib.rs#L169-L245) do expose snapshots, apply a `ChangeWithProcMacros`, and say outstanding snapshots are canceled when state changes. The same source explicitly treats `Analysis` as independent of LSP types. **Basis: documentation + source.** This is a precedent for explicit input ownership and cancellation, not evidence that rust-analyzer diagnostics equal `rustc` or that Anneal should embed rust-analyzer. A separate fresh compiler/proof oracle remains necessary whenever the accepted claim is stronger than an editor observation. This is a **derived** acceptance rule, reinforced by the earlier architecture report's TypeScript plugin, Roslyn, and clangd comparisons rather than a new runtime comparison of those tools.

| Precedent | Actual observed API boundary | Anneal rule supported | What it does not establish |
| --- | --- | --- | --- |
| Lean LSP | Open document, cwd-based launch, version-threshold diagnostic wait, position-based goal/RPC requests | Fence live replies with captured document version and worker/session identity; attest imports separately | Exact imported `.olean` identity or equivalence to fresh batch checking from a goal response |
| rust-analyzer | Current-state `AnalysisHost` supplied explicit changes, with cancellable snapshots | A client can own complete semantic input and invalidate queries on change | `rustc` parity, Lean semantics, or a historical proof snapshot |
| Volar | Virtual code plus source-map and service transforms | A projected document can expose language services through explicit maps | Sound Rust-hosted Lean edits, theorem acceptance, or import provenance |

### Virtual document mapping can lose proof-edit ownership (I003)

The [Volar source-map API](https://github.com/volarjs/volar.js/blob/44d58aee30d1d476c8ad3f6f5581b288d7185d1e/packages/source-map/README.md) documents returning *all* matching source ranges and an optional fallback that allows the start and end offsets to come from different mappings. Its [implementation](https://github.com/volarjs/volar.js/blob/44d58aee30d1d476c8ad3f6f5581b288d7185d1e/packages/source-map/lib/sourceMap.ts#L95-L130) first yields same-mapping ranges; when none exist and fallback is enabled, it combines a mapped start with the first acceptable mapped end. In contrast, [`getSourceRange`](https://github.com/volarjs/volar.js/blob/44d58aee30d1d476c8ad3f6f5581b288d7185d1e/packages/language-service/lib/utils/featureWorkers.ts#L193-L229) returns the first result from an all-ranges generator and enables cross-mapping fallback. Its source-map memo builds per-offset `Set`s in mapping input order, so first-result behavior can depend on mapping construction order for overlapping maps. **Basis: documentation + source interpretation.** No upstream runtime was executed to verify a particular plugin's map order.

The pinned [completion provider](https://github.com/volarjs/volar.js/blob/44d58aee30d1d476c8ad3f6f5581b288d7185d1e/packages/language-service/lib/features/provideCompletionItems.ts#L109-L129) records an embedded-document URI and transforms the virtual completion to the source via `getSourceRange`. [`transformCompletionItem`](https://github.com/volarjs/volar.js/blob/44d58aee30d1d476c8ad3f6f5581b288d7185d1e/packages/language-service/lib/utils/transform.ts#L84-L106) maps `additionalTextEdits` and filters unmappable ones; its primary `textEdit` becomes undefined if mapping fails. [`transformWorkspaceEdit`](https://github.com/volarjs/volar.js/blob/44d58aee30d1d476c8ad3f6f5581b288d7185d1e/packages/language-service/lib/utils/transform.ts#L350-L491) maps each virtual text edit and includes successfully mapped edits, while unmappable ones are omitted. The [code-action provider](https://github.com/volarjs/volar.js/blob/44d58aee30d1d476c8ad3f6f5581b288d7185d1e/packages/language-service/lib/features/provideCodeActions.ts#L118-L135) uses that transform. **Basis: source.** These are useful IDE adaptation choices; they do not by themselves promise atomicity or one-to-one source ownership for a proof edit.

`support/projection_probe.py` mirrors the relevant equal-length range-enumeration, cross-mapping fallback, first-result, and auxiliary-edit filtering rules in a small Python model. Its assertions and retained `support/projection-results.json` show:

| Modeled operation | Raw result | Strict Anneal-oriented edit rule |
| --- | --- | --- |
| Replace virtual `[0,6]` (`by rfl`) | Two authored `[27,33]` and `[64,70]`; first selection flips when map order reverses | Reject: destination is not unique |
| Replace virtual `[3,31]` across generated wrapper | Fallback includes authored `[30,67]`, spanning `fn second()` boundary | Reject: endpoints belong to distinct mappings |
| Completion on second virtual span with two auxiliary edits | One maps to authored `[66,68]`; wrapper edit `[10,12]` has no authored range and is dropped in a Volar-like transform | Reject candidate atomically: one requested change has no authored owner |

**Basis: model execution.** This report's fixture adds an upstream-call-site correspondence to the older [`anneal-3730-projection-properties-2026-09-29`](../anneal-3730-projection-properties-2026-09-29/REPORT.md) synthetic projection tests. Neither report executes a Volar plugin with a Rust/Lean document. An Anneal proof workspace should also give every projected document an identity derived from source bytes, projection algorithm/configuration, and generated import environment; the first two are needed for edit CAS, and the last for proof context. That is a **derived contract**, not an existing Volar feature claim.

### Adapter-first API gap inventory (I008)

| Pin and concern | Existing observable API | Bounded adapter without an upstream patch | Small upstream API that might be worth proposing | Decision condition / residual |
| --- | --- | --- | --- | --- |
| Lean exact live goal | `plainGoal` is position-based; diagnostic wait is version-threshold; RPC has session identity | Capture source/document version, request worker incarnation, and selected imported artifacts; discard any reply after a change; reconstruct a fresh worker or run batch acceptance for an exact claim | Version-bound goal query returning elaborated document version and a consumed-import manifest/digest | Compare adapter versus proposed API on the same source/import mutation and stale-response oracle; no patch or integrated Anneal call site tested |
| Lean dependency refresh | `didOpen.dependencyBuildMode` and `.lean`/`.ilean` watchers exist | Own generated Lake output generation and restart/reopen a worker when its imports are untrusted | Explicit reload/import-environment acknowledgement, if restart cost is material | First measure supported refresh combinations and restart cost; an imported-artifact identity is still absent from the reviewed request/response fields |
| rust-analyzer input overlay | `apply_change` supplies explicit semantic inputs and cancels outstanding snapshots | Keep a client-side captured input graph and feed all changes before querying; use a fresh compiler oracle for acceptance | No upstream change indicated by these source regions | Test only if Anneal actually adopts rust-analyzer; source review is not proof of compiler parity |
| Volar virtual edit ownership | `SourceMap` can enumerate all ranges, while edit transform paths take first or filter unmappable edits | Enumerate every candidate, reject ambiguous/cross-segment edits, require all completion/code-action edits to map to one captured authored version | Optional strict/atomic mapping result with ambiguity and generated-only reason codes | Real Volar plugin and Rust-hosted Lean editor tests remain; source-level possibility is not a product defect |
| Charon/Aeneas delta/reset/span hooks | Prior architecture and component reports identify full-output CLI handoffs and candidate reusable-library gaps | One process per captured request with private outputs, complete manifests, and full regeneration | Only after measured latency benefit: explicit reset/delta and source-span contracts | Not re-reviewed in this narrow package; see `anneal-3730-architecture-contracts-2026-09-29` and component reports for their exact pins and limits |

The first two rows define a correctness fallback using present APIs; upstream extensions would make attestation or latency better if the matched acceptance experiment shows a need. This is **derived**, not a declaration that the fallback is implemented in Anneal or that upstream maintainers would accept a patch. The current checkout has no integrated Anneal V2 editor adapter in which to measure that comparison.

## Boundaries

- **Not examined:** an actual Volar, Razor, rust-analyzer, or TypeScript language-server process; any editor UI; Anneal's real Rust annotation syntax or generated Lean projection; a cross-language completion applied by a real client; an upstream patch; or an end-to-end batch/live acceptance comparison. A Python model proves only its own assertions.
- **Unknown:** whether a particular Volar plugin emits overlapping mappings or whether its client applies a partial action when an auxiliary edit is absent. The pinned source demonstrates the transformation path and possible mapping semantics, not a real-world failure. The toy mapping is deliberately adversarial.
- **Lean API limit:** a reviewed request type without an import hash does not by itself prove the server cannot internally track imported artifacts or refresh a worker under some launch mode. Existing Lean execution reports give narrower counterexamples; the adapter should treat their results as reasons to attest exact imports, not as a universal server impossibility.
- **rust-analyzer guide date:** the guide is checked in at the pinned revision but describes 2024-01-01. Current-commit API claims use the pinned implementation. No `rustc` equivalence test was run here.
- **Scope status:** I002 receives source/API evidence but retains compiler-oracle parity tests; I003 receives a pinned source-map analysis and executable *model*, but real embedded-language runtime/editor behavior remains; I008 receives a concrete adapter-versus-patch decision table, but neither alternative was implemented in Anneal or measured on the real pipeline. None is claimed fully complete.

## Revalidation

Run `python3 support/projection_probe.py` and compare the regenerated `support/projection-results.json` with the committed result; its assertions must pass. When Volar is changed, diff `SourceMap.findMatchingStartEnd`, `featureWorkers.getSourceRange`, `transformCompletionItem`, and `transformWorkspaceEdit` at the new exact revision; a changed first-match or all-or-nothing policy requires a new report. For a real Anneal implementation, use one captured Rust annotation and imported-model generation, then test overlapping projection spans, a generated-only wrapper edit, an atomic completion with one unmappable edit, a stale document response, and an import mutation against a fresh batch checker. Record exact source/artifact/worker identities and both accepted and rejected edits. Only that integrated test can settle whether the proposed adapter works in the product or an upstream API change is needed.
