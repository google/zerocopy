# Formal Semantics, Ambiguities, Miscompilation Classes, and Formalization Cost of the LLVM 23.1.1 IR Subset Emitted by rustc 1.99.1

## Summary

Formalizing the LLVM 23.1.1 (`1b9c0d5ff9bbe7634aead059efe6b11a7eeba145`) IR subset actually emitted by `rustc` `1.99.1` (`58cf8f9c35b355199727627d07ae34a4e2846d67`) — whether for foundational proof generation (`rustc_codegen_llvm` verification) or for a translation-validated LLVM optimization tier — requires reconciling what `rustc` emits (`support/rustc_w4_emission_sites.json`), what LLVM 23.1.1's `llvm/docs/LangRef.md` (`support/langref_w4_sections.json`) specifies, and what existing formalizations (Vellvm, Alive2, Crellvm) cover:

1. **Five Significant LLVM 23.1.1 Specification Upgrades Utilized by `rustc` 1.99.1**:
   - **Decomposition of `getelementptr` into `inbounds`, `nusw`, and `nuw` (`LangRef.md:12198-12340`)**: Following the LLVM 19+ GEP flag redesign, `rustc` `1.99.1` emits fine-grained `GEPNoWrapFlags` (`compiler/rustc_codegen_llvm/src/builder.rs`, `llvm/ffi.rs`). Unlike `inbounds` (which requires both the base pointer and result to lie within or one-past-the-end of a live allocated object), `nusw` (no unsigned-signed wrap) and `nuw` (no unsigned wrap) specify pure address-arithmetic non-wrapping without asserting live allocation bounds.
   - **Replacement of Legacy `nocapture` with Structured `captures(...)` (`LangRef.md:1538-1595`, `3805-3955`)**: LLVM 23.1.1 decomposes pointer capture into orthogonal components: `captures(none)`, `captures(address)`, `captures(read_provenance)`, and `captures(address_is_null)`. In `rustc` `1.99.1`, `attributes.rs:83` (`AttributeKind::Captures`) emits `captures(none)` (`LLVMRustAddCapturesAttr`) on reference parameters.
   - **Write-Before-Read and Unwind-Safety Attributes (`writable`, `initializes((Lo, Hi))`, `dead_on_unwind`, `dead_on_return` at `LangRef.md:1815-1915`)**: `rustc` `1.99.1` (`attributes.rs:146-188`) emits `writable`, `dead_on_unwind`, and `dead_on_return` on `sret` and mutable reference arguments (when `-Z mutable-noalias` / ABI rules apply), enabling `MemCpyOptimizer::performCallSlotOptzn` and `DeadStoreElimination` without introducing the unwinding partial-write miscompilation (`llvm/llvm-project#50806`).
   - **Structured `memory(...)` Effects (`LangRef.md:2261-2330`)**: Replaces legacy `readnone`/`readonly`/`writeonly`/`argmemonly`/`inaccessiblememonly` with orthogonal location-wise bitmasks (`memory(none)`, `memory(readwrite, argmem: read, inaccessiblemem: write)`).
   - **Addition of `ptrtoaddr` (`LangRef.md:12882-12927`)**: LLVM 23.1.1 includes the `ptrtoaddr <ty> <val> to <int_ty>` instruction, which extracts only the integer address bits of a pointer **without** exposing or capturing its provenance (`captures(address)` rather than `captures(address, provenance)`). While `rustc` `1.99.1` still lowers `.addr()` and integer casts via `ptrtoint` (`builder.rs`), `ptrtoaddr` provides the first clean target-IR primitive for Rust Strict Provenance (`p.addr()`).

2. **Four Persistent Semantic Ambiguities in LLVM 23.1.1 `LangRef.md` That Cause Real Miscompilations**:
   - **Ambiguity A — `ptrtoint` + `inttoptr` Provenance Reconstruction vs Integer GVN (`llvm#34548`, `llvm#35229`)**: `LangRef.md:3750-3804` states that an `inttoptr` pointer is "based on" all pointers that contributed to the integer value, yet LLVM passes perform integer algebraic identities (`x - x -> 0`, `GVN` replacing `i2` with `i1` under `icmp eq i1, i2`) and also fold `inttoptr(ptrtoint(p)) -> p`. These three rules are mutually inconsistent in every formal model (Lee et al., OOPSLA 2018; Alive2 CAV 2021).
   - **Ambiguity B — `noalias` and `!alias.scope` / `!noalias` Operational Dependence (`LangRef.md:1512-1537`, `7511-7830`)**: Defined in terms of C99 `restrict` "based-on" dependence, which becomes circular when a function computes a pointer branch-dependently or compares two pointers for equality. Furthermore, cloning `!alias.scope` metadata without cloning its scope identifier or `@llvm.experimental.noalias.scope.decl` (`LangRef.md:28215`) across loop unrolling or jump threading causes unsound `NoAlias` deductions.
   - **Ambiguity C — `@llvm.lifetime.start` / `end` on Non-`alloca` or Partial Pointers (`LangRef.md:26303-26380`)**: In LLVM 23.1.1, `@llvm.lifetime.start.p0(ptr %p)` takes a single `ptr` operand (size argument removed in LLVM 22/23 in favor of `alloca` whole-object lifetime!), but its interaction with `SROA`, `Inliner`, and address-taken stack slots when invoked inside loops remains subtle if two dynamic lifetimes overlap.
   - **Ambiguity D — Infinite Loops without Side Effects vs `mustprogress` (`LangRef.md:2140-2175`)**: Rust permits side-effect-free infinite loops (`loop {}`), so `rustc` deliberately does **not** emit the C++ `mustprogress` function attribute. However, several LLVM loop/CFG passes (`ADCE`, `LoopDeletion`, `PostDominatorTree`-based `DSE`) historically assumed forward progress when computing post-dominance unless carefully gated on `mustprogress` / `willreturn`.

3. **Formalization Cost Estimate**:
   Formalizing the deterministic sequential + concurrency-primitive subset of LLVM 23.1.1 IR emitted by `rustc` `1.99.1` in Lean 4 requires **`~18,500–24,500` LOC** (`~3,500` LOC syntax & well-formedness, `~4,500` LOC byte-level memory model with `(alloc_id, offset)` provenance + byte-wise `Poison | Undef(mask) | Bits(b) | PtrFrag(prov, idx)` representation, `~4,500` LOC instruction/terminator step relation, `~3,500` LOC function/parameter attribute & `!alias.scope` semantics, and `~3,500` LOC intrinsic contracts).

### 2. Detailed Analysis of the Four Critical Semantic Pitfalls for a Verified `rustc`

**Basis: normative + source + derived**

#### 2.1 Pitfall 1: Why `rustc` Emits `assume` Operand Bundles Instead of `ptrtoint` Alignment Checks
If a compiler lowers an alignment assertion `assert!(ptr.is_aligned_to(16))` into:
```llvm
%addr = ptrtoint ptr %p to i64
%rem  = and i64 %addr, 15
%ok   = icmp eq i64 %rem, 0
call void @llvm.assume(i1 %ok)
```
then `ptrtoint` exposes/captures `%p`'s provenance (`LangRef.md:3821`), which disables `BasicAliasAnalysis` non-escaping local object optimizations! By instead emitting either `["align"(ptr %p, i64 16)]` operand bundles (`LangRef.md:3217`) or `ptrtoaddr` (`LangRef.md:12882`), provenance is **not** captured (`captures(address)` only).Note also that `rustc` explicitly sets `-preserve-alignment-assumptions-during-inlining=false` (`llvm_util.rs:136`) because excessive `@llvm.assume` instructions block `SimplifyCFG` speculation and `LoopVectorize` if-conversion.

#### 2.2 Pitfall 2: Byte-Level Memory Representation Required by `SROA`, `memcpy`, and Uninitialized Padding
In Rust, reading uninitialized padding bytes of a `struct` via `ptr::copy_nonoverlapping` (`@llvm.memcpy`) or `SROA` aggregate splitting is **not** immediate UB as long as those uninitialized bytes are not typed at a `noundef` type or branched upon.
- Therefore, an LLVM IR memory model cannot represent memory cells as typed whole values `Val` (which would turn a 4-byte `i32` load overlapping 1 byte of uninitialized padding into either an immediate type error or full 32-bit `undef`).
- Following **Alive2's CAV 2021 memory model** (Lee, Kim, Lopes, Regehr, *"An SMT Encoding of LLVM's Memory Model for Bounded Translation Validation"*), each byte in an allocation block $B$ must be a 2-tuple:
  $$\text{Byte} \triangleq \text{NonPtrByte}(\text{valueBits} : \text{BitVec}_8,\; \text{nonPoisonMask} : \text{BitVec}_8) \;\mid\; \text{PtrByte}(\text{prov} : \text{AllocId},\; \text{addr} : \text{BitVec}_{64},\; \text{byteIdx} : \text{Fin}_8,\; \text{nonPoison} : \text{Bool})$$
  where `@llvm.memcpy` copies `Byte`s verbatim without inspecting `nonPoisonMask` or `PtrByte` vs `NonPtrByte`, whereas `load i32` / `load ptr` reconstructs the typed value and yields `poison` only in the bits/lanes whose `nonPoisonMask` is 0!

#### 2.3 Pitfall 3: `noundef` on Function Arguments and Returns vs Aggregate Padding
In `rustc` `1.99.1`, `attributes.rs:90,342` attaches `noundef` to scalar and reference arguments/returns (`PassMode::Direct` and `PassMode::Pair` when the Rust type requires initialized bits, such as integers, floats, `bool`, `char`, references, and `Box`). It deliberately **omits** `noundef` on `MaybeUninit<T>` and on direct register-passed integer chunks (`PassMode::Cast`) that cover uninitialized struct padding! Any formalization of `rustc_codegen_llvm` must preserve this exact invariant: attaching `noundef` to a register chunk containing struct padding makes passing a validly initialized Rust struct immediate UB in LLVM IR (`LangRef.md:1699`).

#### 2.4 Pitfall 4: LLVM 23.1.1's New Parameterless Size for `@llvm.lifetime.start` / `@llvm.lifetime.end`
In `rustc` `1.99.1` with LLVM 23.1.1, inspect `LangRef.md:26311-26375` and `compiler/rustc_codegen_llvm/src/builder.rs:1417-1439`:
- In LLVM $\le 21$, `@llvm.lifetime.start.p0(i64 <size>, ptr <%ptr>)` took a byte size and an arbitrary pointer (often a GEP into an `alloca`).
- In LLVM 23.1.1 (`LangRef.md:26315`: `declare void @llvm.lifetime.start.p0(ptr captures(none) <ptr>)`), the `<size>` operand is **gone**: the intrinsic takes **only** `ptr captures(none) <ptr>`, which **must** be an `alloca` instruction Directly!
- Formally, this simplifies the operational semantics of `lifetime.start`/`end` enormously: every `alloca` block $b \in \text{AllocId}$ now has a boolean state $\text{alive}(b) \in \{\text{true}, \text{false}\}$ (instead of byte-range liveness masks), toggled by `lifetime.start(b)` ($\text{alive}(b) \gets \text{true}$, bytes filled with `poison`) and `lifetime.end(b)` ($\text{alive}(b) \gets \text{false}$).

## Boundaries

- **Inline assembly (`call asm ...`)**: `rustc` lowers `core::arch::asm!` to LLVM inline assembly strings with target register constraint codes (`compiler/rustc_codegen_llvm/src/asm.rs`). Inline assembly has no target-independent semantics in `LangRef.md` (`L4450`) and must be interpreted directly through the target ISA model (`x86_64` / `AArch64`).
- **GPU offload and target-specific intrinsics (`llvm.nvvm.*`, `llvm.amdgcn.*`, `llvm.x86.avx512.*`, `llvm.aarch64.sve.*`)**: The `~18.5k–24.5k` LOC estimate covers target-independent LLVM IR and standard SIMD intrinsics emitted by `rustc` MIR lowering; vendor-specific `core::arch` intrinsics (`16,423` records in `Intrinsics*.td`) require importing target ISA semantics (see `reports/llvm-tablegen-isa-extraction-and-verified-selector-reuse`).
