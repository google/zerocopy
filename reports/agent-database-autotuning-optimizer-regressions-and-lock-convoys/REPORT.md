# Agentic Database Autotuning, Optimizer Plan-Regression Guards, Hypothetical Indexes, and DDL Lock Convoys

## Summary

Primary-source synthesis across 11 peer-reviewed database and software-engineering studies (2014–2024), line-level inspection of 8 pinned upstream repositories (`postgres/postgres`, `HypoPG/hypopg`, `ankane/dexter`, `hyrise/index_selection_evaluation`, `cmu-db/ottertune`, `itrummer/dbbert`, `SolidLao/GPTuner`, `TsinghuaDatabaseGroup/DB-GPT`), and deterministic local verification on `SQLite 3.53.4` and Python 3.10+ (`scripts/verify_db_tuning_plans_locks.py`) establishes five invariants governing automated database configuration tuning, index selection, anomaly diagnosis, online DDL execution, and ORM query rewriting:

1. **Multi-Join Cardinality Cliffs Dominate Cost-Constant Calibration (`Leis et al., PVLDB 2015 / VLDBJ 2018`, `SQLite 3.53.4`, `Probe 1`):** Under correlated filter predicates across joins, System-R attribute-independence assumptions underestimate intermediate row counts exponentially with join depth ($10\times \to 100\times \to 1{,}000\times \to 10{,}000\times$ across $k = 1\text{–}4$ joins at $s = 0.10$; up to $10^8\times$ on the Join Order Benchmark). In `SQLite 3.53.4` (`Probe 1B`), single-index `ANALYZE` statistics (`sqlite_stat1 = '2000 200'` on zero-skew data) leave a **`17.15×` nested-loop `idx_ta_a1` slowdown persisting even after `ANALYZE`** (`413,937` VDBE opcodes vs. `24,137` opcodes when `+ta.aw1 = 1` forces an ephemeral covering B-tree + Bloom filter). Lowering planner `random_page_cost` from `4.0` to `1.5` for SSDs *without* fixing `20×` join-cardinality underestimation widens nested-loop selection (`2/6 -> 5/6` queries) and degrades true SSD execution cost by **`3.89×`** (`39,875.0 -> 155,250.0`, vs. `23,625.0` with true cardinalities at uncalibrated `4.0`).
2. **What-If Index Cost Illusions and Heap-Only Tuple (`HOT`) Write Amplification Require Two-Sided Gating (`HypoPG@a0d0213d`, `Dexter@da35df3a`, `Hyrise@61f08074`, `Ding et al., SIGMOD 2019`, `Probe 2`):** `HypoPG` estimates B-tree size using a fixed `bloat_factor = 130.0 / 90.0 = 1.4444` (`3,543` pages on $10^6$ `int8` rows vs. `2,454` pages at `100%` packing, `2,726` leaf pages at fresh `fillfactor = 90`, and `5,889` pages on a `2.4×`-bloated post-churn B-tree) and leaves `entry->tree_height = -1` (`hypopg_index.c:2229–2241`), zeroing `btcostestimate` descent CPU (`selfuncs.c:8201`) so `EXPLAIN` prices a hypothetical duplicate cheaper than a bloated live index (`9,753.26 < 9,845.76`, `delta = 92.50`) and passes unclustered scans through `Dexter`'s `50%` read-only `Total Cost` gate despite **`2.72×` runtime regression** (`779.19 < 1,875.0` vs. `10,189.44` true cost). On a `200`-page OLTP table with $K = 4$ immutable-key indexes (`read_cost` `325.0 -> 83.59`), indexing a mutated column invalidates PostgreSQL Heap-Only Tuple (`HOT`) updates (`0.95 -> 0.00`), raising per-`UPDATE` physical page-cost units from `5.80` to `48.00` (`8.28×` write amplification) and flipping net workload cost from speedup to regression above an exact crossover ratio of **$R_{\text{broken}}^* = 5.72$ `UPDATE`s per `SELECT`** (vs. **$R_{\text{safe}}^* = 603.5$** when `HOT` is preserved, yielding a **`3.60×` net regression** vs. **`1.68×` speedup** at $R = 40:1$).
3. **ACID Durability-Knob Admissibility Gaps Enable `tmpfs`-Masked Reward Hacking (`OtterTune@9758c657`, `DB-BERT@120a61c6`, `GPTuner@89401e61`, `Probe 3`):** Among audited autotuners, only human-curated `OtterTune` locks all **`6/6`** core PostgreSQL/MySQL durability knobs (`tunable: false`). `DB-BERT` lacks any safety denylist and exposes **`4/6` durability knobs in both NLP hint extraction and total repo union** (`2/6` in DDPG; `postgres.fsync` is blocked across every `DB-BERT` code path by `param_reg = r'[a-z_]+_[a-z]+'` on `collection.py:228`—including `use_implicit`—and by `is_numerical('on') == False` on `ddpg.py:130` / `run_ddpg.py:163`, while `mysql.innodb_doublewrite` fails `is_numerical('ON')`). `GPTuner` exposes `0/6` in its shipped `target_knobs.txt`, crashes/omits in unpatched CLI `space_optimizer/knob_selection.py:21–34` (`mysql/candidate_knobs.txt` missing; `postgres/candidate_knobs.txt` plain-text omitting all 3 PG knobs), and exposes **`5/6`** via Streamlit `demo/util/get_knobs.py:11–23` (`system_view.json`) or unconstrained GPT interdependent-knob expansion (`knob_selection.py:160–188`). Under `16`-stream closed-loop Little's Law on `1.2 ms` `fdatasync` storage (`5,242` tx/s default), unguarded UCB disables commit flushing by trial `2` (`46,254` tx/s = `8.82×` with zero crash durability vs. `8,502` tx/s = `1.62×` crash-safe), whereas `0.005 ms` container `tmpfs` compresses the unsafe/safe ratio to **`1.019×`** (`1.9%`), hiding durability reward-hacking in CI.
4. **PostgreSQL `waitMask` Lock Convoys and 4-Transaction `CONCURRENTLY` Zombie Residue (`postgres@9b5d4e33`, `Dexter@da35df3a`, `Probe 4`):** `LockAcquireExtended` (`lock.c:1140`) tests `conflictTab[lockmode] & lock->waitMask` *before* held locks, so an unguarded `ALTER TABLE` (`AccessExclusiveLock`) queued behind a `12 s` `SELECT` saturates a capped `100`-connection pool in **`0.38 s`** (`2,403` `SELECT`s and `601` `UPDATE`s disrupted; `1.86 s` and `600` `UPDATE`s for non-concurrent `CREATE INDEX` `ShareLock` behind a writer). `CREATE INDEX CONCURRENTLY` executes across **4 kernel transactions** (`indexcmds.c:1670, 1742, 1802, 1821–1832`): a read-only `12 s` `SELECT` (`AccessShareLock`) passes both `ShareLock` writer barriers (`WaitForLockers`, `L1710, 1757`) so `Tx1`–`Tx3` commit `indisready = true`, then blocks `Tx4`'s `WaitForOlderSnapshots` (`L1821` via `VirtualXactLock`). Aborting under per-wait `SET lock_timeout = '5s'` (`Dexter` `connection.rb:21`) leaves an **`indisvalid = false, indisready = true` zombie index** that incurs full DML/`HOT` write maintenance and blocks `autovacuum` during execution, while `Dexter`'s `WHERE indisvalid = 't'` filter (`indexer.rb:521`) accumulates **`N` duplicate zombie indexes** across `N` 60-second retries.
5. **ORM `N+1` vs. `IN`-Batching Depends on Column Width, Engine Architecture, and Network RTT (`Yang et al., ICSE 2018`, `Chen et al., 2014/2016`, `Probe 5`):** Controlling for equal column projections in `SQLite 3.53.4` (`120` parents, `7,200` children), indexed `IN`-batching (`2` queries) executes *fewer* VDBE opcodes than `N+1` (`121` queries) at both 2 columns (`44,658 < 44,886`, `1.0051×` near-parity) and 3 columns (`51,858 < 52,086`, `0.519 ms` vs. `0.521 ms` at `0 ms` in-process RTT, vs. **`61.02 ms` vs. `1.52 ms` = `40.2×` `N+1` penalty** at `0.5 ms` TCP RTT; comparing 2-col `N+1` `44,886` against 3-col `IN` `51,858` reflects `7,200` extra `OP_Column` extractions of `project_id`, while 1-child `LEFT JOIN` costs `65,408` ops). Unlike embedded row-store SQLite cursors, vectorized columnar engines (`DuckDB`) heavily penalize sequential `N+1` point queries even in-process. Merging $k = 2$ child collections (`60 × 40`) into one `LEFT JOIN` inflates rows **`23.8×`** (`48,000` vs. `2,020`) and VDBE ops **`33.0×`** (`344,556` vs. `10,456`), while `SELECT 1 ... LIMIT 1` (`14` ops) cuts `SELECT COUNT(*)` (`23,412` ops) by **`1,672.3×`**.

### 2. Correlated Multi-Join Cardinality Cliffs vs. Cost-Constant Calibration

`Basis: documentation + derived + execution (Probe 1)`

- **Exponential Independence Decay Across Join Depth (`Probe 1A`):** Under System-R attribute- and join-independence assumptions ($f_{\text{join}} = 1 / \max(\text{NDV}_A, \text{NDV}_B)$), when $(k + 1)$ joined relations over $N = 10{,}000$ entities each carry a predicate of marginal selectivity $s = 0.10$ satisfied by the *same* `1,000`-entity cohort, independent multiplication estimates $N \cdot s^{k+1}$ rows while true cardinality remains `1,000`, compounding underestimation q-error geometrically: **`10×`** at $k = 1$ (`est = 100.00`), **`100×`** at $k = 2$ (`est = 10.00`), **`1,000×`** at $k = 3$ (`est = 1.00`), and **`10,000×`** at $k = 4$ (`est = 0.10`).
- **Live `SQLite 3.53.4` Plan Cliff Persisting Even After `ANALYZE` (`Probe 1B`):** Across four tables (`titles`, `title_tags`, `title_awards`, `box_office`, `2,000` rows partitioned into `10` exact `200`-row uniform cohorts so single-column histograms have zero skew), running `ANALYZE` populates exact single-index prefix statistics `sqlite_stat1 = '2000 200'` on `idx_t_g1`, `idx_tt_t1`, and `idx_ta_a1`. Both before and after `ANALYZE`, SQLite's cost-based planner selects a nested-loop secondary-index probe `SEARCH ta USING INDEX idx_ta_a1 (aw1=?)` because multiplying independent predicate selectivities underestimates the intermediate rows entering `title_awards`. Executing `sql_default_nl` after `ANALYZE` requires **`413,937` VDBE bytecode instructions** (returning `[(40, 20660)]`), whereas suppressing `idx_ta_a1` via unary `+ta.aw1 = 1` forces SQLite to materialize an **ephemeral covering B-tree + Bloom filter** (`OP_OpenEphemeral`: `BLOOM FILTER ON ta (aw2=? AND aw3=? AND tid=?)` + `SEARCH ta USING AUTOMATIC PARTIAL COVERING INDEX`) that finishes in **`24,137` VDBE instructions**—a **`17.15×` instruction slowdown persisting even after `ANALYZE`**.
- **Why Calibrating `random_page_cost` Without Fixing Cardinalities Degrades Latency (`Probe 1C`):** On a 6-query multi-join workload (`true_outers = [5000, 15000, 25000, 35000, 50000, 80000]`, inner table `2,000` pages / `100,000` rows, `inner_cache_hit_ratio = 0.25`, true SSD hardware `random_page_cost = 1.5`) suffering a moderate **`20×` join-cardinality underestimation**, lowering the planner's `random_page_cost` from PostgreSQL's rotational default `4.0` to the true SSD value `1.5` (`GPTuner`'s `[1.0, 2.0]` recommendation range) lowers the perceived crossover threshold for Index Nested-Loop Join (`NLJ`). Planner `NLJ` selection expands from **`2/6` to `5/6` queries**, *worsening* true SSD workload execution cost by **`3.89×`** (`39,875.0 -> 155,250.0`), whereas supplying accurate cardinalities at the uncalibrated `random_page_cost = 4.0` achieves **`23,625.0`** (`NLJ = 0/6`, within `0.0%` of the `23,625.0` oracle at `rpc = 1.5`).

### 3. `HypoPG` What-If Cost Illusions, `Dexter`/`Hyrise` Read Gates, and `HOT` Write Amplification

`Basis: source + derived + execution (Probe 2)`

#### 3.1 `HypoPG` Synthetic Page Estimation and `btcostestimate` Tree-Height Bias

- **Exact `HypoPG` B-Tree Size Formula (`HypoPG/hypopg@a0d0213d`, `hypopg_index.c:1167–1215, 2093–2117, 2229–2241` — `source`):** `hypo_injectHypotheticalIndex` injects backend-local `IndexOptInfo` structs into `rel->indexlist`. In `hypo_estimate_index` (`L2229–2241`), `HypoPG` computes:
  - `line_size = ind_avg_width + MAXALIGN(sizeof(IndexTupleData)) + sizeof(ItemIdData)` (`8 + 8 + 4 = 20` bytes for a single non-null `int8` key on 64-bit PostgreSQL);
  - `usable_page_size = BLCKSZ - SizeOfPageHeaderData - sizeof(BTPageOpaqueData)` (`8192 - 24 - 16 = 8152` bytes);
  - `bloat_factor = (100.0 + additional_bloat) / fillfactor` with hardcoded `additional_bloat = 30` and default `fillfactor = 90` (`BTREE_DEFAULT_FILLFACTOR`), giving `130.0 / 90.0 = 1.4444...`;
  - `entry->pages = (BlockNumber)(entry->tuples * line_size * bloat_factor / usable_page_size)` and **`entry->tree_height = -1; /* TODO */`** (`L2241`).
- **Interaction with PostgreSQL `btcostestimate` & `genericcostestimate` (`postgres@9b5d4e33`, `src/backend/utils/adt/selfuncs.c:7622, 8201`; `src/backend/optimizer/path/costsize.c:615–715, 901–946` — `source + execution`):**
  1. In `btcostestimate` (`selfuncs.c:8201`, unlike `gistcostestimate` at `L8351`), B-tree root-to-leaf descent CPU is `(index->tree_height + 1) * 50.0 * cpu_operator_cost`. When `HypoPG` leaves `tree_height = -1`, `(-1 + 1) * 50.0 * 0.0025 = 0.0` (vs. `0.50` on a height-`3` physical B-tree).
  2. In `genericcostestimate` (`selfuncs.c:7622`), single-scan index leaf I/O charges `ceil(numIndexTuples * index->pages / index->tuples) * spc_random_page_cost` (`1.0 × 4.0` per leaf page), while `cost_index` (`costsize.c:615–715`) interpolates heap I/O via `correlation^2` between sequential range scans and Mackert-Lohmann (`costsize.c:928`, `min(T, ceil(2*T*n / (2*T + n)))` when $T \le b$).
  3. On $10^6$ `int8` rows (`Probe 2A`, `25,000` heap pages, `selectivity = 0.01`, `correlation = 0.85`), `100%`-packed leaf capacity is **`2,454` pages**, fresh `fillfactor = 90` leaf capacity is **`2,726` pages**, `HypoPG` estimates **`3,543` pages**, and a `2.40×`-fragmented production B-tree occupies **`5,889` pages**. Consequently, `EXPLAIN` prices a redundant hypothetical index **92.50 cost units cheaper** than the existing physical index (`9,753.26 < 9,845.76`). - **Unclustered Scan Regression Passing `Dexter`'s `50%` Read Gate (`ankane/dexter@da35df3a`, `lib/dexter/client.rb:88–89`, `indexer.rb:286–296`; `Probe 2B`):** `Dexter` promotes single-column candidates purely when initial read `Total Cost >= 100` (`--min-cost`) and hypothetical `new_cost < initial_cost * 0.50` (`--min-cost-savings-pct 50`). #### 3.2 Heap-Only Tuple (`HOT`) Invalidation and Closed-Form Write Crossover $R^*$

`Basis: source + derived + execution (Probe 2C)`

- **PostgreSQL `HOT` Eligibility Rule:** When an `UPDATE` modifies no column referenced by *any* index on the relation (not even an `indisready = true, indisvalid = false` index) and the new tuple fits on the same `8 KiB` heap page (`fillfactor < 100`), PostgreSQL appends a Heap-Only Tuple chained from the existing root line pointer without inserting entries into *any* of the table's $K$ secondary indexes. Creating an index on a frequently mutated column (such as `status_code` or `updated_at`) sets `rd_hotblockingattr` on that attribute, dropping `HOT` eligibility to `0%` for every `UPDATE` touching that column and forcing new index-tuple insertions across **all $K + 1$ indexes** on the table.
- **Commensurate Page-Cost Accounting and Exact Crossover Ratio $R^*$ (`Probe 2C`):** Expressing both `SELECT` and `UPDATE` work in standard PostgreSQL page-cost units (`seq_page_cost = 1.0`, `random_page_cost = 4.0`, zero arbitrary scaling multipliers) on an active `200`-page, `10,000`-row OLTP queue/orders table (`fillfactor = 80`, $K = 4$ existing immutable-key indexes, `hot_ratio = 0.95` before indexing `status_code`):
  - **Read savings $\Delta C_{\text{read}}$:** Indexing `status_code` (`selectivity = 0.002`, `correlation = 0.10`, `35` `HypoPG` pages) lowers `SELECT` cost from **`325.00` to `83.59`** (`74.3%` reduction, `Dexter_accept = True`), saving $\Delta C_{\text{read}} = 241.41$ cost units per `SELECT`.
  - **Per-`UPDATE` write amplification $\Delta C_{\text{upd}}$:** Modeling an in-page heap modification + WAL record at `4.0` (`1.0 × random_page_cost`), a non-HOT overflow heap-page modification at `4.0`, and each non-HOT secondary B-tree index insertion at `8.0` (`4.0` random leaf fetch + `4.0` dirty leaf writeback / `XLOG_BTREE_INSERT_LEAF` WAL write):
    $$C_{\text{upd}}(h, M) = 4.0 + (1 - h)\bigl(4.0 + 8.0 M\bigr)$$
    Before indexing (`h = 0.95, M = 4`), $C_{\text{upd,before}} = \mathbf{5.80}$. Indexing mutated `status_code` collapses `HOT` to $h = 0.00$ across $M = 5$ indexes, jumping to $C_{\text{upd,broken}} = \mathbf{48.00}$ (**`8.28×` per-`UPDATE` write amplification**, $\Delta C_{\text{upd}} = +42.20$). By contrast, indexing an *immutable* filter column preserves $h = 0.95$ at $M = 5$, yielding $C_{\text{upd,safe}} = \mathbf{6.20}$ ($\Delta C_{\text{upd}} = +0.40$).
  - **Closed-Form Break-Even Ratio $R^* = \Delta C_{\text{read}} / \Delta C_{\text{upd}}$:** Net workload cost regresses whenever $\lambda_{\text{upd}} / \lambda_{\text{sel}} > R^*$:
    - **HOT-destroying index (`status_code`):** $R_{\text{broken}}^* = 241.41 / 42.20 = \mathbf{5.72}$ `UPDATE`s per `SELECT` (`> 85.1%` updates).
    - **HOT-preserving index (immutable column):** $R_{\text{safe}}^* = 241.41 / 0.40 = \mathbf{603.5}$ `UPDATE`s per `SELECT` (**`105.5×` higher write tolerance**).
  - At a realistic state-machine / job-queue OLTP mix of `50 SELECT/s` and `2,000 UPDATE/s` ($R = 40:1$), adding the `HOT`-destroying index degrades total workload cost by **`3.60×`** (`27,850.0 -> 100,179.5`, falsely accepted by `Dexter`'s read-only gate and rejected by a two-sided `Ding 2019` per-query latency + workload write gate), whereas the `HOT`-preserving index achieves a **`1.68×` net workload speedup** (`27,850.0 -> 16,579.5`, accepted).

### 5. PostgreSQL `waitMask` Lock Convoys, 4-Transaction `CONCURRENTLY` Zombie Indexes, and Diagnostic Blind Spots

`Basis: normative + source + derived + execution (Probe 4)`

#### 5.1 `LockAcquireExtended` Wait-Mask Preemption (`postgres@9b5d4e33`, `lock.c:68–108, 1140–1160`, `proc.c:1200–1274`)

- In `src/backend/storage/lmgr/lock.c:1140–1145`, PostgreSQL tests incoming lock requests against **waiting** lock modes *before* checking currently held modes:
  ```c
  if (lockMethodTable->conflictTab[lockmode] & lock->waitMask)
      found_conflict = true;
  ```
  When `found_conflict` is true (and the backend holds no existing lock on the relation, `myHeldLocks == 0` in `JoinWaitQueue`, `proc.c:1200–1274`), the backend sleeps behind existing waiters in FIFO order:
  - **`ALTER TABLE` (`AccessExclusiveLock`, mode `8`, conflicts with modes `1..8`, `Probe 4A`):** Queued with `lock_timeout = 0` behind one `12 s` analytical `SELECT` (`AccessShareLock`, mode `1`), `waitMask |= (1 << 8)` blocks **100% of subsequent `SELECT` and `UPDATE` arrivals**. Under `200 SELECT/s + 50 UPDATE/s` (`20 ms` hold time), a hard-capped **`100`-connection pool saturates in `0.38 s`**, disrupting **`2,403` `SELECT`s** (`79` queued in `wait_queue` + `2,324` rejected by the exhausted pool) and **`601` `UPDATE`s** (`20` queued + `581` pool-rejected).
  - **Non-Concurrent `CREATE INDEX` (`ShareLock`, mode `5`, conflicts with modes `3..8` but *not* `AccessShareLock` mode `1`, `indexcmds.c:698`, `Probe 4B`):** Queued behind a `12 s` `RowExclusiveLock` (mode `3`) writer, `waitMask |= (1 << 5)` allows `SELECT`s to pass (`0` `SELECT`s disrupted) while queueing `UPDATE`s until the **`100`-connection pool saturates in `1.86 s`**, disrupting **`600` `UPDATE`s** (`95` queued + `505` pool-rejected).

#### 5.2 Four-Transaction `CREATE INDEX CONCURRENTLY` Mechanics and `indisready = true` Zombie Accumulation

- **4-Transaction Kernel Execution vs. 3-Step Documentation Summary (`postgres@9b5d4e33`, `doc/src/sgml/ref/create_index.sgml:598–699` vs. `src/backend/commands/indexcmds.c:449–513, 1667–1832`):** While `create_index.sgml:634–637` summarizes `CREATE INDEX CONCURRENTLY` (`CIC`) as three conceptual steps, `DefineIndex` in `indexcmds.c` commits **four** distinct transactions while holding a session-level `ShareUpdateExclusiveLock` (`L1667`, mode `4`, self-conflicting with `VACUUM`, `autovacuum`, `ANALYZE`, and concurrent DDL):
  1. **Transaction 1 (`L1667–1670`):** Inserts the `pg_index` catalog entry (`indisvalid = false, indisready = false`) and commits (`CommitTransactionCommand()` at `L1670`).
  2. **Transaction 2 (`L1710–1742`):** Waits at `WaitForLockers(heaplocktag, ShareLock, true)` (`L1710`, Phase `WAIT_1`—blocking *only* on `ShareLock`-conflicting writers, **never** on read-only `AccessShareLock` `SELECT`s), executes `index_build` (Scan 1), sets **`indisready = true`**, and commits (`L1742`). From this commit onward, every `INSERT`/`UPDATE`/`DELETE` maintains the index and `HOT` is blocked on its key columns.
  3. **Transaction 3 (`L1757–1802`):** Waits at `WaitForLockers(heaplocktag, ShareLock, true)` (`L1757`, Phase `WAIT_2`), runs `validate_index` (`L1795`, Scan 2 catch-up), and commits (`L1802`) specifically so the `CIC` backend's own `MyProc->xmin` resets before snapshot waiting.
  4. **Transaction 4 (`L1803–1832`):** Computes `limitXmin`, blocks at **`WaitForOlderSnapshots(limitXmin, true)` (`L1821`, Phase `WAIT_3`)**—which calls `VirtualXactLock(old_snapshots[i], true)` (`indexcmds.c:507`, `lock.c:4738`) across **every backend in the database holding an MVCC snapshot `xmin < limitXmin`**, *including read-only `SELECT`s on unrelated tables*—and finally sets `INDEX_CREATE_SET_VALID` (`indisvalid = true`, `L1832`).
- **`Dexter` Per-Wait `lock_timeout = '5s'` Abort and Multi-Run Zombie Accumulation (`ankane/dexter@da35df3a`, `connection.rb:21`, `indexer.rb:521`, `index_creator.rb:18–36, 46–61, 74`; `Probe 4C–4D`):**
  - PostgreSQL's `lock_timeout` bounds *each individual lock wait*, not cumulative scan runtime. Against a `12 s` read-only `SELECT`, `CIC` sails past `WAIT_1` and `WAIT_2` (`Tx1`–`Tx3` commit `indisready = true`), then aborts with `PG::LockNotAvailable` after `5 s` inside `Tx4` `WaitForOlderSnapshots` (`L1821`).
  - `Dexter` rescues `PG::LockNotAvailable` (`index_creator.rb:30–31`) **without dropping the failed index**, leaving an **`indisvalid = false, indisready = true` zombie index** (unusable by `SELECT` plans, yet imposing full B-tree write amplification and `HOT` invalidation). Furthermore, because `Dexter`'s catalog check (`indexer.rb:521`) filters `WHERE indisvalid = 't'`, subsequent 60-second daemon cycles (`index_creator.rb:20, 74`) ignore prior invalid residue and create **`3` duplicate write-amplifying zombie indexes across `3` retries** (`Probe 4C`), whereas preflighting `pg_stat_activity` (`backend_xmin` / `xact_start`) + mandatory post-abort `DROP INDEX CONCURRENTLY` leaves **`0` disrupted queries and `0` zombie indexes** (`Probe 4D`).

### 6. ORM `N+1` vs. `IN`-Batching Column Parity, Engine Architecture, and Cartesian `JOIN` Blowups

`Basis: documentation + source + derived + execution (Probe 5)`

- **Column-Controlled `N+1` vs. `IN`-Batching vs. 1-Child `LEFT JOIN` in `SQLite 3.53.4` (`Probe 5A`):** Across `120` parent `projects` and `7,200` child `issues` (`60` per project):

  2. *Controlled Equal-Column Parity vs. Extra Foreign-Key Extraction:* With `idx_issues_pid` present, controlling for identical projected columns proves `IN`-batching (`2` queries) executes **strictly fewer** VDBE instructions than `N+1` (`121` queries) by `228` opcodes at both widths: **`44,658 < 44,886`** (`1.0051×`) for `SELECT id, title` (2 columns) and **`51,858 < 52,086`** (`1.0044×`) for `SELECT project_id, id, title` (3 columns). Comparing 2-column `N+1` (`44,886`) against 3-column ORM `IN`-preloading (`51,858`)—which must fetch `project_id` to hash-group children in application memory—accounts for the exact `7,200`-opcode difference (`1` `OP_Column` per child row). A single-child `LEFT JOIN` (`SELECT p.id, p.name, i.id, i.title`) executes **`65,408` VDBE opcodes** (`1.26×` above 3-col `IN`) by repeatedly extracting parent columns across all `7,200` joined rows.
  3. *Network-RTT Crossover vs. Columnar OLAP Engines:* On equal 3-column projections, embedded in-process `SQLite` (`0 ms` RTT, prepared-statement caching) runs `N+1` and `IN` at near-parity (`0.521 ms` vs. `0.519 ms`), whereas a `0.5 ms` client-server TCP round-trip inflates `121`-query `N+1` to **`61.02 ms` vs. `1.52 ms` (`40.2×` slower)**. Crucially, embedded `SQLite` `N+1` parity relies on lightweight B-tree row cursors and **does not transfer to vectorized columnar engines (`DuckDB`)**, where issuing `121` separate point queries incurs per-query binder, optimizer, and morsel-pipeline scheduling overhead across `2,048`-tuple vectors compared to a single vectorized hash `JOIN` or `IN` scan.
- **Multi-Child `LEFT JOIN` Cartesian Product Trap (`Probe 5B`) and Early-Exit `LIMIT 1` (`Probe 5C`):**
  - Eagerly joining $k = 2$ independent `1:N` child collections (`60` `issues` and `40` `labels` per project across `20` projects) in a single `LEFT JOIN` materializes $20 \times 60 \times 40 = \mathbf{48{,}000}$ Cartesian rows (**`344,556` VDBE opcodes**) vs. **`2,020` rows (`10,456` VDBE opcodes)** across `3` separate `IN (...)` queries—a **`23.8×` row blowup** and **`33.0×` VDBE instruction blowup**.
  - Replacing unindexed `SELECT COUNT(*) FROM issues WHERE state = 0` (`23,412` VDBE opcodes, Rails `.any?` anti-pattern in `Yang ICSE 2018` `IC`) with early-terminating `SELECT 1 FROM issues WHERE state = 0 LIMIT 1` (`.exists?`) finishes in **`14` VDBE opcodes (`1,672.3×` reduction)**.

### 7. Synthesized Engineering Invariants for Database Agents

`Basis: derived (synthesized from Sections 1–6)`

1. **Hard Code-Level ACID Durability Denylist + Storage Flush Verification:** Lock `{fsync, synchronous_commit, full_page_writes, wal_level, ignore_checksum_failure}` on PostgreSQL and `{innodb_flush_log_at_trx_commit, innodb_doublewrite, sync_binlog, innodb_flush_sync}` on MySQL in an immutable code-level denylist (`OtterTune` `tunable: false` pattern) rather than relying on regexes or LLM prompts, and verify non-`tmpfs` `fdatasync` latency (`pg_test_fsync` / `fio`) before accepting OLTP tuning gains.
2. **Two-Sided Read-Regression and `HOT`/DML Write Gate for Index Selection:** Gate candidate indexes on (a) live `pgstattuple` B-tree density so idealized `1.44×` `HypoPG` page counts cannot undercut bloated indexes, (b) `pg_stat_user_tables` `n_tup_upd` / `n_tup_hot_upd` accounting to reject indexes on frequently mutated columns when `UPDATE:SELECT` exceeds $R^*$, and (c) canary execution or pairwise regression classification (`Ding et al., 2019`) rather than raw `EXPLAIN` `Total Cost`.
3. **Cardinality Diagnosis Preceding Cost-Constant Tuning:** Inspect `EXPLAIN (ANALYZE, BUFFERS)` estimated-vs.-actual row counts before adjusting `random_page_cost` or join enable flags; repair intra-table skew/correlation with `CREATE STATISTICS (dependencies, ndistinct, mcv)` and cross-table join correlation via selective cohort materialization or execution-guided plan stitching.
4. **Zero-Convoy DDL with Snapshot Preflight and Mandatory `NOT indisvalid` Cleanup:** Never run `ALTER TABLE` or non-concurrent `CREATE INDEX` with `lock_timeout = 0`; before `CREATE INDEX CONCURRENTLY`, check `pg_stat_activity` for both table writers (`WaitForLockers`) and database-wide old `backend_xmin` snapshots (`WaitForOlderSnapshots`), bound per-wait `lock_timeout`, and unconditionally drop `pg_index WHERE NOT indisvalid` residue via `DROP INDEX CONCURRENTLY` on any abort.
5. **Topology-, Engine-, and Multiplicity-Aware ORM Rewrites + Catalog Introspection:** Batch `N+1` loops into indexed `WHERE fk IN (...)` queries on client-server TCP databases and vectorized OLAP engines (`DuckDB`), emit one `IN (...)` query per `1:N` child collection rather than multi-collection `LEFT JOIN`s, use `SELECT 1 ... LIMIT 1` / `EXISTS` for non-emptiness checks, and query `pg_blocking_pids()`, `pg_locks`, and `pg_index (NOT indisvalid)` directly alongside `DB-GPT`-style slow-query and top-$K$ metric summaries.

- **Architectural and parameter limits of embedded `N+1`, `HypoPG`, cost tuning, and analytical surrogates — `known not to apply`:**
  - Embedded `SQLite` B-tree `N+1` vs. `IN` near-parity (`1.004×–1.005×` equal-column VDBE ops at `0 ms` RTT) **does not apply** to vectorized columnar engines such as `DuckDB` (which incur heavy per-query planning and morsel-scheduling overhead on sequential point lookups even in-process) or to networked client-server databases (`40.2×` slower at `0.5 ms` TCP RTT).
  - Read-only `HypoPG` `EXPLAIN` cost reductions **do not imply** net OLTP speedup when indexing a column updated more frequently than $R^* = \Delta C_{\text{read}} / \Delta C_{\text{upd}}$, and lowering `random_page_cost` **does not improve** multi-join plans under unmitigated cardinality underestimation (`3.89×` regression in `Probe 1C`).
  - Specific cost ratios (`3.60×` `HOT` regression, `8.82×` UCB gain, `0.38 s` / `1.86 s` pool-saturation times) are exact outputs of the stated analytical page-cost, `16`-stream Little's Law (omitting single-server WAL queueing and group-commit batching), and `10 ms`-tick arrival parameters, not hardware-universal constants.
- **Cross-table extended statistics, physical `HypoPG` bloat/height tracking, and transactional `CONCURRENTLY` — `unsupported`:** PostgreSQL `CREATE STATISTICS` supports only single-relation column sets and cannot track cross-table join correlations; `HypoPG` virtual indexes carry no physical storage (`entry->tree_height = -1` and fixed synthetic bloat); and PostgreSQL `CREATE INDEX CONCURRENTLY` explicitly forbids execution inside a transaction block and cannot skip global `WaitForOlderSnapshots` MVCC barriers.
