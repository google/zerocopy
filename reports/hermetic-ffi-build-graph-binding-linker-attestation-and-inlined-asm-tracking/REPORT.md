# Hermetic FFI Build-Graph Binding, Linker Symbol and Constructor Attestation, Cross-Language LTO Bitcode Detection, and Inlined `asm!` Tracking

## Summary

Binding verified Rust MIR, inline/naked/global assembly, and foreign `.S`/`.o`/`.a` artifacts to the machine code that actually executes requires closing four distinct provenance and link-time gaps across Cargo, Bazel/Fuchsia, system linkers (`rust-lld` and GNU `ld.bfd`), and LLVM code generation:

1. **Cargo `build.rs` Verify-vs-Build Divergence, `.rlib` Bundling, and Hermetic Linker Interception:**
   - Cargo executes `build.rs` with `RUSTC_WRAPPER`, `OPT_LEVEL`, `PROFILE`, and `OUT_DIR` exposed in the environment (`src/compiler/custom_build.rs:371-457`), sorts transitive `cargo::rustc-link-search` paths with `OUT_DIR` (`LibraryPath::CargoArtifact`) ahead of external directories (`src/compiler/mod.rs:578-585`), forwards `rustc-link-arg-cdylib` even from transitive dependencies (`cargo#9562`, `mod.rs:603-614`), and skips linking completely under `cargo check` (`--emit=dep-info,metadata`, `mod.rs:1321-1322`). Consequently, `cargo check` exits `0` even when `build.rs` requests a nonexistent native library, and an environment-sensitive `build.rs` compiles distinct C objects from identical Rust sources under a `RUSTC_WRAPPER` verification run (`VAL=42`) versus plain debug (`VAL=666`) and release (`VAL=999`) builds.
   - Inside `rustc`, `-l static=+bundle` (default) unpacks `.o` members into `.rlib` (`link.rs:677-680`), `+whole-archive` / `-Z packed-bundled-libs` packs the archive into a `.bundled_lib` object wrapper (`link.rs:284-301, 666-675`), whereas `-l static:-bundle` defers lookup to downstream linking—allowing an on-disk mutation of `libmyffi.a` after building an upstream `.rlib` to silently change the downstream binary (`K=11` $\to$ `K=77`) without recompiling the `.rlib`.
   - Unlike Cargo, Bazel (`bazelbuild/rules_rust`) and Fuchsia GN bypass `build.rs` for first-party native dependencies, passing `CcInfo.linking_context.linker_inputs` or GN `{{rustdeps}}` directly via `-Lnative=...`, `-lstatic=...`, and `-Clink-arg=...` (with `rules_rust` sandwiching `.rlib`s between `-lstatic=` and `-Clink-arg=-l` and creating `_ambiguous_libs/` symlinks for colliding basenames).
   - Hermetic link-time capture via `-C linker=<wrapper>` must expand `@response_file` arguments, inject `-Wl,--dependency-file=<dep>`, `-Wl,--trace`, and `-Wl,-Map=<map>`, pin pre/post SHA-256 digests and `(st_dev, st_ino)` for every resolved input, and **unconditionally pass `-Wl,--no-dependent-libraries` on `lld`**—because `rust-lld` enables ELF `SHT_LLVM_DEPENDENT_LIBRARIES` (`.deplibs`) autolinking by default (`lld/ELF/Driver.cpp:1421-1422`, `InputFiles.cpp:380-394, 623-641`), allowing a relocatable `.o` to silently pull in an arbitrary archive path absent from linker `argv` (`SMUG=777` verified live, blocked with exit `1` by `--no-dependent-libraries`).

2. **Linker Symbol Hijacking, Dynamic Interposition, `.init_array` Injection, and Pre-Link vs. Post-Link Verification Boundaries:**
   - Both `rust-lld` (`23.1.1` / `22.1.6`) and GNU `ld.bfd 2.47` exhibit identical silent hijacking hazards with zero diagnostics: (a) duplicate archive definitions resolve purely by command-line archive order (`105` vs. `-1`); (b) a strong `STB_GLOBAL` symbol overrides a verified `STB_WEAK` definition whenever it arrives via a direct `.o`, an earlier archive, `+whole-archive`, or a later archive member extracted to satisfy an unrelated sibling symbol (while an unreferenced later archive does *not* override an already-defined weak symbol); (c) `#[link_name = "..."]` completely severs the Rust MIR callee identifier from the ELF relocation target (even binding ambient `libc` symbols such as `getpid` with no `-l` flag); (d) under `LD_PRELOAD`, Rust `cdylib` intra-crate calls stay protected via `assume_dso_local` (`10`), whereas Rust `extern "C"` foreign calls (`20` $\to$ `888`) and default `-fPIC` C shared-library internal calls (`10` $\to$ `999`) are silently interposed unless bound with `-Wl,-Bsymbolic` or `STV_HIDDEN`; and (e) `+whole-archive` pulls unreferenced `.o` members containing `.init_array` constructors (`SUM=5` $\to$ `SUM=1005`, `2` $\to$ `3` `.init_array` entries), while a constructor in the *same* `.o` as a referenced symbol runs even *without* `+whole-archive` (`SUM=2005`).
   - ELF `.note.gnu.property` (`IBT`, `SHSTK`) uses bitwise-AND merging across all inputs: a single `-fcf-protection=none` C object strips `IBT`/`SHSTK` from a `#![no_std]` `-Z cf-protection=full` link, and on standard `std` builds without `-Z build-std`, prebuilt `libstd-*.rlib` `.rcgu.o` objects themselves lack `.note.gnu.property` and silently drop `IBT`/`SHSTK` even when every user Rust and C unit enables CET.

3. **Cross-Language LTO (`-C linker-plugin-lto`) and Fail-Closed Bitcode/IR Detection:**
   - Machine-code FFI verifiers must fail closed not only on raw LLVM bitcode (`BC\xc0\xde` / `42 43 c0 de`), but across **six distinct IR/bitcode carriers**: (1) raw LLVM bitcode `.o` or `.rlib`/`.a` members (`rustc -C linker-plugin-lto`, `clang -flto=thin|full`); (2) LLVM Bitcode Wrapper headers (`0x0B17C0DE` / `de c0 17 0b`, verified directly accepted and inlined by `rust-lld`); (3) thin archives (`!<thin>\n`) referencing external bitcode `.o` paths; (4) Clang `-ffat-lto-objects` ELF/COFF `.llvm.lto` (`SHT_LLVM_LTO = 0x6fff4c0c`) and Mach-O `__LLVM,__bitcode` sections—where linking the *identical* `c_clang_fat.o` preserves an FFI tail-jump (`jmpq *GOT`) under `--no-fat-lto-objects` yet discards pre-link `.text` and collapses across the Rust/C boundary into `leal 0x5(,%rdi,2), %eax; retq` under `--fat-lto-objects`; (5) GCC 15 GIMPLE LTO `.gnu.lto_*` sections (15 sections in both `-fno-fat-lto-objects` slim LTO carrying `__gnu_lto_slim` and `-ffat-lto-objects` fat LTO carrying *zero* `__gnu_lto_*` symbols); and (6) `.llvmbc` sections in default `rustc` `.rlib`s (ignored by `rust-lld`'s `ObjectFile::isSectionBitcode`, which checks `.llvm.lto`, but consumed by `rustc` internal LTO unless compiled with `-C embed-bitcode=no`).

4. **Tracking and Attesting Inlined, Cloned, and Loop-Unrolled `asm!` Sites in `.o` Binaries:**
   - Under `rustc -O`, a single MIR `TerminatorKind::InlineAsm` undergoes multi-caller inlining (producing distinct physical registers, REX prefixes `0x48` vs. `0x49`, x86-64 opcodes `0x35` vs. `0x81 /6`, byte lengths `10 B` vs. `11 B`, and caller stack spills), intra-function CFG tail duplication (`1 MIR` $\to$ `2` machine copies using `%rdx` vs. `%rcx`), loop unrolling (`1 MIR` $\to$ `4` machine copies even inside `#[inline(never)]`), and differing AVX2 `vzeroupper`/red-zone behavior (`clobber_abi("C")` with `options(nostack)` spills `%ymm0` into `-0x20(%rsp)` red zone without emitting a pre-`asm!` `vzeroupper`, whereas an out-of-line call emits `2` `vzeroupper`s and allocates a 32-byte frame).
   - `#[inline(never)]` does **not** guarantee 1:1 MIR-to-`.o` fidelity: it permits intra-function unrolling/cloning, permits LLVM IPSCCP/DeadArgumentElimination to drop parameters and hardcode constants (`movl $0x1337, %ecx`) on non-exported functions, does not prevent LLVM `MergeFunctions` (`unnamed_addr alias`, enabled by default at `-O`) or linker `--icf=all` from collapsing distinct `#[no_mangle] #[inline(never)]` symbols to identical VMAs even under `--icf=none`, and `#[no_mangle]` without `#[inline(never)]` is still inlined into intra-crate callers.
   - Comparing four attestation designs, a compiler-injected `SHF_EXCLUDE` metadata table (`.pushsection .anneal.asm_sites,"e",@progbits` with reserved numeric local labels `9998:` / `9999:`) emits exact relocatable `(section, start_off, end_off, site_id)` spans for `7/7` live inlined and 4×-unrolled instances (`10 B`, `11 B`, `10 B`, and `4×7 B`) and `0` records for dead `options(pure)` code, strips cleanly from final executables without inhibiting `--gc-sections` on both `rust-lld` and `ld.bfd`, and avoids the span-merging imprecision of DWARF `.debug_line`. Where register-allocator independence is required, out-of-line `#[unsafe(naked)]` `naked_asm!` / `global_asm!` provides fixed 1:1 bytes at the cost of a direct call boundary.

## Findings

### 1. Native Artifact Provenance Across Cargo (`build.rs`), Bazel (`rules_rust`), and Fuchsia GN

`Basis: source + execution` (`rust-lang/cargo@5f94df478`, `rust-lang/rust@58cf8f9c3`, `bazelbuild/rules_rust@7e60a45f9`, `fuchsia@4799c98e7`, `rust-lang/cc-rs@c548c664c`, `rust-lang/cmake-rs@c7e1801f7`, `kornelski/nasm-rs@78580a964`, `support/probe_build_graph_and_linker_wrapper.py`, `support/probe_1_results.json`)

#### 1.1 Cargo `build.rs` Directive Pipeline and Helper Crates (`cc`, `cmake`, `nasm-rs`)

In Cargo `1.99.1` (`rust-lang/cargo@5f94df4789f005f9a352888e8355ffc645b7ed0e`, note that Cargo moved `src/cargo/core/compiler/` to `src/compiler/`), native artifact discovery flows through three stages:

1. **Build-script execution environment (`src/compiler/custom_build.rs:332-458, 561-575`):**
   Cargo runs the host-compiled `build.rs` with `OUT_DIR`, `CARGO_MANIFEST_DIR`, `TARGET`, `HOST`, `OPT_LEVEL`, `DEBUG`, `PROFILE` (`"debug"` or `"release"`), `RUSTC`, `RUSTDOC`, optional `CARGO_MANIFEST_LINKS`, `DEP_<LINKS>_<KEY>` metadata from direct dependencies, and **`RUSTC_WRAPPER`** (propagated whenever configured, lines `455-457`). Helper crates compile foreign C/C++/assembly inside this opaque host process:
   - `cc-rs` (`src/lib.rs:2247-2267`, `c548c664cb6d`) invokes the discovered C/C++ compiler and archiver into `OUT_DIR/lib<name>.a` and prints `cargo:rustc-link-search=native=<OUT_DIR>` and `cargo:rustc-link-lib=static[:<modifiers>]=<name>` (using `static:-bundle=<stdlib>` for static C++ standard libraries, `lib.rs:1372`).
   - `cmake-rs` (`src/lib.rs:441-556`, `c7e1801f740e`) invokes external `cmake` into `OUT_DIR` and returns the install prefix `PathBuf`; the crate's own `build.rs` manually emits `cargo::rustc-link-search` and `cargo::rustc-link-lib`.
   - `nasm-rs` (`src/lib.rs:50-59, 217-275`, `78580a964d38`) invokes `nasm` into `OUT_DIR` and either archives into `lib<name>.a` (`compile_library`) or returns raw `.o` paths (`compile_objects`).
2. **Directive parsing (`src/compiler/custom_build.rs:797-1062`):**
   `BuildOutput::parse` captures `rustc-link-lib`, `rustc-link-search` (tagged as `LibraryPath::CargoArtifact` if under `script_out_dir` else `LibraryPath::External`), `rustc-flags` (`-l` / `-L` only), and scoped linker arguments (`rustc-link-arg`, `rustc-link-arg-bins`, `rustc-link-arg-bin=BIN=ARG`, `rustc-link-arg-cdylib` / legacy `rustc-cdylib-link-arg`, `rustc-link-arg-tests`, `rustc-link-arg-benches`, `rustc-link-arg-examples`).
3. **Forwarding to `rustc` (`src/compiler/mod.rs:310-313, 552-617, 1321-1322`):**
   - **Transitive `-L` path sorting (`mod.rs:563-585`):** Cargo collects `library_paths` from *all* transitive `build_scripts.to_link`, stably sorts `LibraryPath::CargoArtifact(_)` (`0`) strictly ahead of `LibraryPath::External(_)` (`1`), and emits `-L <path>`. Consequently, any transitive crate's `OUT_DIR` takes search precedence over external system or vendor `-L` directories.
   - **Direct `-l` forwarding (`mod.rs:312, 595-601`):** Cargo emits `-l <name>` only for `key.0 == current_id` and only when `pass_l_flag` holds (`unit.target.is_lib() || !unit.pkg.targets().iter().any(|t| t.is_lib())`—a binary in a package that also has a library inherits native libraries through the library's `.rlib` instead).
   - **Transitive `cdylib` `-C link-arg=` leak (`mod.rs:603-614`):** `linker_args` are gated by `lt.applies_to(target, mode) && (key.0 == current_id || *lt == LinkArgTarget::Cdylib)`. Because of the retained compatibility carve-out (`rust-lang/cargo#9562`), a transitive dependency's `cargo::rustc-link-arg-cdylib=` injects raw `-C link-arg=` flags into downstream `cdylib` links.
   - **`cargo check` bypass (`mod.rs:1321-1322`):** When `unit.mode.is_check()`, Cargo passes `--emit=dep-info,metadata`, so `rustc` skips `link_rlib` and `link_natively` completely.

#### 1.2 `rustc` Native Library Bundling (`+bundle` vs. `-bundle` vs. `+whole-archive`)

In `rust-lang/rust@58cf8f9c35b355199727627d07ae34a4e2846d67`:

- `rustc_metadata::native_libs::collect` (`compiler/rustc_metadata/src/native_libs.rs:148-198`) merges `#[link(...)]` attributes with CLI `-l [KIND[:MODIFIERS]=]NAME[:RENAME]` flags, moving any re-mentioned library to the end of the list so dependents precede dependencies.
- During `.rlib` creation (`compiler/rustc_codegen_ssa/src/back/link.rs:284-301, 662-682`), static libraries behave in three distinct ways—verified live in `Probe 1B` (`support/probe_1_results.json`):

| `-l` Modifier | `.rlib` Archive Members (`ar t libup.rlib`) | Link-Time Handling (`link.rs:3397-3450`) | Post-`.rlib` On-Disk Mutation of `libmyffi.a` (`11` $\to$ `77`) |
| :--- | :--- | :--- | :--- |
| `static=myffi` (default `+bundle`) | `lib.rmeta`, `lib.rmeta-link`, `*.rcgu.o`, **`myffi_impl.o`** (unpacked loose `.o` member!) | Linked directly as `.rlib` member (`ab.add_archive`) | Downstream binary stays **`K=11`** (snapshot frozen in `.rlib`) |
| `static:+bundle,+whole-archive=myffi` (or `-Z packed-bundled-libs`) | `lib.rmeta`, `lib.rmeta-link`, `*.rcgu.o`, **`libmyffi.a`** (wrapped in `.bundled_lib` object, listed in `lib.rmeta-link`) | Extracted to `tmpdir` via `extract_bundled_libs`, linked via `link_staticlib_by_path(..., whole_archive)` | Downstream binary stays **`K=11`** (snapshot frozen in `.rlib`) |
| `static:-bundle=myffi` | `lib.rmeta`, `lib.rmeta-link`, `*.rcgu.o` (**no native code embedded**) | Emits `-lmyffi` during downstream final link, resolved fresh against downstream `-L` search paths | Downstream binary silently mutates to **`K=77`** without recompiling `libup.rlib`! |

#### 1.3 Bazel (`rules_rust`) and Fuchsia GN: Native Provenance Without `build.rs`

Both Bazel and Fuchsia GN construct native `.o`/`.a`/`.so` artifacts in hermetic, action-tracked C/C++ build actions and wire them directly into `rustc` without executing `build.rs`:

- **Bazel `rules_rust` (`bazelbuild/rules_rust@7e60a45f9f95c0f04fbe1eb144ce4823aa76a766`, `rust/private/rustc.bzl`):**
  1. `collect_deps` (`rustc.bzl:240-306`) collects `CcInfo.linking_context.linker_inputs` from `cc_library` (and `dylib` Rust) dependencies into `dep_info.transitive_noncrates`.
  2. `_disambiguate_libs` (`rustc.bzl:651-728`) detects non-standard archive basenames or colliding stripped names across directories and creates per-crate symlinks under `_ambiguous_libs/<crate_basename>/` so `-lstatic=<name>` resolves deterministically.
  3. `_add_native_link_flags` (`rustc.bzl:3263-3355`) and `portable_link_flags` (`rustc.bzl:3081-3136`) emit `-Lnative=<dir>` plus a **"sandwich" ordering** (`n1 n2 ... r1 r2 ... n1 n2 ...`): each static library is passed *both* as `-lstatic=<name>` (before/among `.rlib`s) and `-Clink-arg=-l<name>` (appended at the end of `rustc`'s linker invocation via `add_user_defined_link_args`) to resolve bidirectional C $\leftrightarrow$ Rust symbol cycles. Because `rustc` inserts `-Bdynamic` prior to `-Clink-arg`, `rustc.bzl:3102-3118` explicitly special-cases sysroot `libstd-*`/`libtest-*` to avoid accidentally binding `.so` files instead of `.rlib`s. Libraries marked `alwayslink = True` bypass `-lstatic=` and emit explicit `-Clink-arg=-Wl,--whole-archive -Clink-arg=<path> -Clink-arg=-Wl,--no-whole-archive` (`rustc.bzl:3191-3197`, or `-force_load` on Darwin, `/WHOLEARCHIVE:` on MSVC).
  4. When `experimental_use_cc_common_link` is enabled (`rustc.bzl:1852-2154`), `rules_rust` bypasses `rustc`'s linker driver altogether and links the Rust objects with `cc_common.link`, giving Bazel's C++ toolchain direct control over all linker inputs.
- **Fuchsia GN (`fuchsia@4799c98e7566bf11f1bb3f07dfea86173f00e336`):**
  1. `build/toolchain/clang_toolchain.gni:526-554` invokes `rustc` with `-Zshell-argfiles @shell:<outfile>.rsp` containing GN-expanded `{{rustdeps}} {{externs}}`, unconditionally emits `-Clink-args=[ -Wl, ]--Map="<unstripped>.map"`, and runs `$depfile_verifier` against `--emit=dep-info=$depfile`.
  2. `build/rust/rustc_link_attribute.gni:8-103` explicitly discourages `#[link(name = "...")]` because `rustc` lowers it to a search-based `-lfoo` flag rather than a pinned file path; when required for third-party crates, the template emits *both* `lib_dirs` + `-lstatic=<name>` *and* `-Clink-arg=<rebased_file_path>` so remote build execution (RBE) uploads and binds the exact archive file.

#### 1.4 Verify-vs-Build Divergence, TOCTOU Hazards, and Hermetic `-C linker=` Interception

Live execution in `Probe 1A` (`support/probe_1_results.json`) proves two immediate verify-vs-build failure modes on both `rustc 1.99.1` and `nightly-2026-06-01`:
- **`cargo check` missing-native-library blind spot:** With `build.rs` emitting `cargo::rustc-link-lib=static=nonexistent_ghost_lib`, `cargo check` exits **`0`** while `cargo build` fails with exit **`101`**. Any verifier anchored to `cargo check` or `--emit=metadata` never observes whether native archives exist, match, or link.
- **Environment-sensitive `build.rs` divergence:** Compiling the *identical* Rust `src/main.rs` with a `build.rs` inspecting `RUSTC_WRAPPER` and `OPT_LEVEL` produces three distinct executables and runtime behaviors: `VAL=42` under a `RUSTC_WRAPPER` verification run, `VAL=666` under plain `cargo build`, and `VAL=999` under `cargo build --release`.

To hermetically bind the *exact* linked inputs to the verified artifact without trusting `build.rs` or re-running a second unverified build, a verifier must intercept the actual final link via `-C linker=<wrapper>` (and capture/digest every input *actually opened by the linker*). `Probe 1C` (`support/probe_build_graph_and_linker_wrapper.py`) validates this architecture across both default `rust-lld` (`gnu-lld-cc`) and GNU `ld.bfd 2.47` (`-C link-arg=-fuse-ld=bfd`):

| Attestation Mechanism / Linker Behavior | Bundled `rust-lld` (`23.1.1` / `22.1.6`) | System GNU `ld.bfd 2.47` | Implication for Hermetic Linker Wrapper |
| :--- | :--- | :--- | :--- |
| **`@response_file` expansion (`exec_linker`, `link.rs:2091-2235`)** | `rustc` falls back to `@<tmpdir>/linker-arguments` on `E2BIG` (POSIX escaping on Unix, UTF-16LE BOM + `"..."` on MSVC/Windows LLD) | Same `cc`/`ld` POSIX `@file` syntax | Wrapper MUST recursively expand `@file` arguments before auditing flags or hashing direct path inputs (`response_files_expanded: ["<TMPDIR>/extra.rsp"]` verified live). |

> **Closing the TOCTOU window during linking:** Because the `cc` driver resolves `-l<name>` across `-L` paths and system library directories only inside the linker invocation, pre-hashing `argv` files alone misses `-l` libraries and `.deplibs`/linker-script targets, and hashing post-link alone is vulnerable to an $A \to B \to A$ ABA swap on mutable directories (`compiler-concurrent-source-modification-and-hermetic-input-binding`). A truly hermetic attestation wrapper therefore operates in a **two-phase or isolated-staging protocol**: either (a) execute inside an immutable read-only mount/sandbox (as in Bazel `SkyframeActionExecutor` or Fuchsia RBE) and digest every file listed in `--dependency-file` plus the output ELF, or (b) run a dry discovery / copy-and-pin staging step into a private read-only directory where every `.o`/`.a`/`.rlib`/`.so` is opened once, hashed (`SHA-256`), and linked from immutable copies with `-Wl,--no-dependent-libraries`, verifying zero pre/post `(st_dev, st_ino, sha256)` drift.

### 3. Cross-Language LTO (`-C linker-plugin-lto`) Soundness Boundary and Fail-Closed Bitcode/IR Detection

`Basis: source + execution` (`rust-lang/llvm-project@1b9c0d5ff`: `llvm/lib/BinaryFormat/Magic.cpp:33-145`, `llvm/lib/Object/{IRObjectFile.cpp:72-107, ObjectFile.cpp:80-86, MachOObjectFile.cpp:2184-2189}`, `lld/ELF/{Driver.cpp:250-277, 1389-1390, 2129-2145}`, `support/probe_xlto_bitcode_fail_closed.py`, `support/probe_3_results.json`)

When Rust (`-C linker-plugin-lto`) and C/C++ (`clang -flto=thin|full` or `gcc -flto`) participate in link-time optimization, the pre-link machine-code FFI boundary **ceases to exist**: `lld` / `LLVMgold.so` / `liblto_plugin.so` ingests IR modules, inlines across the Rust/C call boundary, and propagates cross-language aliasing (`!tbaa`, `noalias`), signed-overflow `nsw` poison, and `undef` semantics (`cross-language-lto-linker-plugin-bitcode-and-llvm-ir-semantics`). A machine-code FFI verifier that checks pre-link `.o`/`.a` machine code without failing closed on IR/bitcode inputs is **unsound**—notably even on *ELF fat LTO objects* that appear to contain valid native `.text`!

#### 3.1 Live Fat-LTO Silent Pre-Link vs. Post-Link Divergence (`Probe 3`)

Compiling `c_double_add(int32_t x, int32_t y) { return x * 2 + y; }` with `clang-19 -O2 -fPIC -flto=thin -ffat-lto-objects` produces an ordinary `ET_REL` ELF64 object (`magic: 7f454c4602010100`) containing **both** native x86-64 `.text` **and** an `.llvm.lto` (`SHT_LLVM_LTO = 0x6fff4c0c`) bitcode section. - **With `--no-fat-lto-objects`:** `rust-lld` links the pre-link native `.text` of `c_clang_fat.o`, preserving the FFI boundary:

      12f0: be 05 00 00 00       movl $0x5, %esi

  ```asm
  00000000000012c0 <rust_entry>:
      12c0: 8d 04 7d 05 00 00 00 leal 0x5(,%rdi,2), %eax
      12c7: c3                   retq
  ```

#### 3.3 Fail-Closed Admission Rules for a Machine-Code FFI Verifier

To guarantee that no LTO pass optimizes across a verified machine-code FFI boundary unless explicitly modeled, the hermetic linker wrapper must enforce all four checks (implemented in `scan_artifact_fail_closed` in `support/probe_xlto_bitcode_fail_closed.py`):
1. **Reject LTO linker flags:** Reject `-plugin`, `--plugin`, `-plugin-opt*`, `--fat-lto-objects`, `-flto*` (and ensure `rustc` is invoked with `-C lto=off -C linker-plugin-lto=no -C embed-bitcode=no`).
2. **Recursively scan archives and thin archives:** Unpack every member of `!<arch>\n`, resolve external member paths of `!<thin>\n` relative to the archive directory (as well as Mach-O universal fat binaries `0xCAFEBABE` / `0xCAFEBABF` on Darwin and MSVC `ClGlObjMagic` bigobj LTO files `Magic.cpp:39-49` on Windows).
3. **Reject all IR/bitcode magic headers:** Fail closed on `42 43 c0 de` (`BC\xc0\xde`) and `de c0 17 0b` (`0x0B17C0DE`).
4. **Reject all embedded LTO/IR sections and marker symbols:** In ELF objects, fail closed on section type `SHT_LLVM_LTO` (`0x6fff4c0c`) or section names `.llvm.lto`, `.gnu.lto_*`, and (under strict `-C embed-bitcode=no` policy) `.llvmbc`, plus any `__gnu_lto_*` symbol; in Mach-O objects, fail closed on `__LLVM,__bitcode`; in COFF objects, fail closed on `.llvm.lto` / `.llvmbc` and `ClGlObjMagic` (`Magic.cpp:48-49`).

### 4. Tracking and Attesting Inlined, Cloned, and Loop-Unrolled `asm!` Sites in Emitted `.o` Binaries

`Basis: source + execution` (`rust-lang/rust@58cf8f9c3`: `compiler/rustc_codegen_llvm/src/asm.rs:27-390`, `support/probe_inlined_asm_tracking.py`, `support/probe_4_results.json`)

#### 4.1 Live `rustc -O` Transformations on `TerminatorKind::InlineAsm` (`Probes 4A–4D`)

Unlike `naked_asm!` or `global_asm!`, a `TerminatorKind::InlineAsm` lowers into an LLVM `call ... asm ...` instruction (`compiler/rustc_codegen_llvm/src/asm.rs:347`) inside the enclosing LLVM function, fully exposed to LLVM's inliner, CFG simplifier/tail-duplicator, loop unroller, instruction scheduler, register allocator, and target post-RA passes. Live probes on both `rustc 1.99.1` and `nightly-2026-06-01` establish four concrete divergences between MIR and emitted `.o` bytes:

1. **Multi-caller inlining (`Probe 4A` — distinct registers, REX prefixes, opcodes, byte lengths, and spills):**
   A single helper `asm_mix` (`"imul {0}, {1}\n xor {0}, 0x5a5a"`, `inout(reg) a, in(reg) b, options(pure, nomem, nostack)`) inlines into three distinct encodings across `caller_simple` and `caller_high_pressure`:
   - `caller_simple`: `48 0f af c6` (`imulq %rsi, %rax`, 4 B) + `48 35 5a 5a 00 00` (`xorq $0x5a5a, %rax`, **6 B** short `%rax` immediate opcode `0x35`) = **`10 B`**, zero spills.
   - `caller_high_pressure` (copy 1): `49 0f af c4` (`imulq %r12, %rax`, **REX.B=`0x49`**) + `48 35 5a 5a 00 00` (`xorq $0x5a5a, %rax`, 6 B) = **`10 B`**, surrounded by 7 callee-saved pushes (`pushq %rbp..%rax`).
   - `caller_high_pressure` (copy 2): `48 0f af d9` (`imulq %rcx, %rbx`) + `48 81 f3 5a 5a 00 00` (`xorq $0x5a5a, %rbx`, **7 B** ModR/M opcode `0x81 /6`) = **`11 B`**, followed by stack reload `movq 0x40(%rsp), %rcx`.
2. **Intra-function CFG tail duplication (`Probe 4B` — `1` MIR site $\to$ `2` machine copies):**
   `cfg_cloned_asm` contains **exactly `1` `asm!` terminator** in `-Z dump-mir=runtime-post-cleanup`, yet LLVM `-O` tail-duplicates it into both branches of `if cond` with **different source registers**:
   - Branch 1 (`0xc`): `48 c1 c8 0d` (`rorq $0xd, %rax`) + `48 31 d0` (`xorq %rdx, %rax`).
   - Branch 2 (`0x1c`): `48 c1 c8 0d` (`rorq $0xd, %rax`) + `48 31 c8` (`xorq %rcx, %rax`).
3. **Loop unrolling (`Probe 4C` — `1` MIR site $\to$ `4` machine copies even inside `#[inline(never)]`):**
   `unrolled_loop_asm` is annotated `#[no_mangle] #[inline(never)]` and contains **exactly `1` `asm!` terminator** in `Runtime(PostCleanup)` MIR, yet LLVM `-O` fully unrolls the 4-trip loop into **4 emitted copies** (`0xa`, `0x11`, `0x1c`, `0x27`) interleaved with memory loads (`movq (%rdi), %rcx`, `movq 0x8(%rdi), %rdx`, `movq 0x10(%rdi), %rcx`, `movq 0x18(%rdi), %rcx`) and alternating between `%rcx` and `%rdx`.
4. **AVX2 `vzeroupper` placement & red-zone spilling (`Probe 4D`, `-C target-feature=+avx2`):**
   Comparing three callers holding live `%ymm0` across the same `"add ..., 1"` operation reveals a critical interaction with LLVM's `X86VZeroUpper` pass:
   - `avx_inlined_plain_asm` (`options(pure, nomem, nostack)`): **`1` `vzeroupper`** (at epilogue `0x14`), zero `%ymm0` spills; LLVM schedules `vmovdqu %ymm0, (%rdi)` *before* `addq $0x1, %rax`.
   - `avx_inlined_clobber_abi_asm` (`clobber_abi("C"), options(nomem, nostack)`): **`1` `vzeroupper`** (only at epilogue `0x25`—**none emitted before the `asm!`!**) and LLVM spills `%ymm0` into the **128-byte x86-64 red zone** (`vmovdqu %ymm0, -0x20(%rsp)` before `addq $0x1, %rax`, reloaded via `vmovups -0x20(%rsp), %ymm0` after). Because LLVM inserts `vzeroupper` before `isCall()` MachineInstrs rather than `INLINEASM` with clobbers, an `asm!` with `clobber_abi("C")` does *not* automatically trigger a pre-`asm!` `vzeroupper` transition.
   - `avx_calling_outline_asm` (calling `#[inline(never)] #[no_mangle] pub extern "C" fn out_of_line_asm`): **`2` `vzeroupper` instructions** (`0x19` immediately before `callq` and `0x30` at epilogue) and an explicit 32-byte stack frame (`subq $0x20, %rsp`), keeping `%ymm0` out of the red zone.

#### 4.2 Four Empirical Limitations of `#[inline(never)]` (`Probe 4E`)

Relying on `#[inline(never)]` to establish a 1:1 mapping from a MIR function containing `asm!` to an `.o` function symbol fails in four ways verified live in `Probe 4E` (`support/probe_4_results.json`):

1. **Intra-function duplication persists:** As shown in `Probe 4C`, `#[inline(never)]` on `unrolled_loop_asm` still yields `4` unrolled machine copies from `1` MIR `asm!`.
2. **IPSCCP and DeadArgumentElimination mutate non-exported `#[inline(never)]` signatures:** When private `#[inline(never)] fn internal_never_inline(a: u64, b: u64) -> u64` is called from two sites with `b = 0x1337`, LLVM drops parameter `b` (`%rsi`) completely and emits `movq %rdi, %rax; movl $0x1337, %ecx; addq %rcx, %rax; retq`. The emitted `.o` symbol no longer obeys its MIR function signature.
3. **`#[no_mangle]` without `#[inline(never)]` is still inlined intra-crate:** `caller_of_exported` inlined `#[no_mangle] pub extern "C" fn exported_no_inline_never` directly into `xorq $0x2468, %rdi; leaq 0x1(%rdi), %rax; retq` (`exported_without_inline_never_was_inlined_into_caller: true`), duplicating the `asm!` into its caller while leaving an out-of-line copy for external callers.
4. **LLVM `MergeFunctions` (`unnamed_addr alias`) AND linker `--icf=all` collapse distinct `#[no_mangle] #[inline(never)]` functions:** In `Probe 4E`, `icf_target_alpha` and `icf_target_beta` both carry `#[no_mangle] #[inline(never)]`, yet even under **`-Wl,--icf=none`**, `rustc -O -C codegen-units=1` emitted `@icf_target_beta = unnamed_addr alias i64 (i64), ptr @icf_target_alpha` inside `limits.o`, placing both ELF `STT_FUNC` symbols at offset `0x0` of `.text.icf_target_alpha` and identical VMA `0x14ab0` in the final executable! Preserving 1:1 symbol separation requires both `-Z merge-functions=disabled` (or distinct non-identical bodies/addresses) and `--icf=none`.

## Boundaries

- **Mach-O (`ld64`/`ld64.lld`) and PE/COFF (`link.exe`/`lld-link`) live execution (`not examined`):** All live linker-wrapper, symbol-shadowing, `LD_PRELOAD`, `.init_array`, fat-LTO, and `.pushsection` execution probes ran on `x86_64-unknown-linux-gnu` (`ELF64`, `rust-lld` `23.1.1`/`22.1.6`, GNU `ld.bfd 2.47`). Mach-O `__LLVM,__bitcode`, `MH_TWOLEVEL`, `-force_load`, and PE/COFF `/WHOLEARCHIVE:`, `ClGlObjMagic`, and UTF-16LE `@response_file` handling are documented from primary upstream source (`rust-lang/rust`, `rust-lang/llvm-project`, `bazelbuild/rules_rust`), not live macOS/Windows execution.
- **Native AArch64 and RISC-V inline-assembly and linker probes (`not examined`):** Live `asm!` inlining/unrolling/cloning and `.pushsection` tests ran on `x86_64`. While the ELF `SHF_EXCLUDE` + numeric-label `.pushsection` mechanism is ISA-agnostic in `llvm-mc` and GNU `as`, AArch64 constant-pool literals / branch veneers and RISC-V length-shrinking relaxations (`R_RISCV_RELAX`) inside or adjacent to `asm!` blocks were not executed locally.
- **Live Bazel and Fuchsia GN build execution (`not examined`):** Bazel `rules_rust` and Fuchsia GN native-linking behaviors are established strictly from primary source inspection at their pinned upstream commits (`7e60a45f9f95` and `4799c98e7566`), not by executing `bazel build` or `fx build` locally.
- **Clang/LLVM `-fembed-bitcode` (`__LLVM,__bitcode`) on macOS (`known not to apply` to ELF `ObjectFile::isSectionBitcode`):** On ELF and COFF, `ObjectFile::isSectionBitcode` (`ObjectFile.cpp:80-86`) matches only `.llvm.lto` (not `.llvmbc`), whereas on Mach-O `MachOObjectFile::isSectionBitcode` (`MachOObjectFile.cpp:2184-2189`) matches `__LLVM,__bitcode`. A cross-platform fail-closed detector must therefore treat Mach-O `__LLVM,__bitcode` as active fat-LTO input rather than extrapolating the ELF `.llvmbc` distinction to Mach-O.
- **Linker wrapper protection against a hostile compiler or linker binary (`unsupported` / out of scope):** A `-C linker=` wrapper attests the exact resolved linker inputs, flags, and output binary given a trusted linker binary; it does not by itself verify that an untrusted `rustc`/LLVM backend translated MIR faithfully into the emitted `.rcgu.o` code outside the attested `asm!` sites (which requires either a verified compiler backend or translation validation).
- **Dynamic `dlopen` / runtime `LD_PRELOAD` after static link (`unknown` at build time):** No build-time or post-link static check on an `ET_DYN` or dynamically linked `ET_EXEC` binary can prevent an OS operator from injecting `LD_PRELOAD` over external `DT_NEEDED` imports at process launch (`Probe 2D`); defending against runtime dynamic interposition requires either fully static linking (`-C target-feature=+crt-static` / static PIE with zero `DT_NEEDED`) or OS-level loader/code-signing policy (`AT_SECURE`, sealed `ld.so` configuration, or integrity-measured rootfs).
