# Exocrate install state machine and concurrency

## Summary

Source inspection traces Exocrate's path resolution, source opening, exclusive interprocess lock, staging extraction, and rename commit. Its code explicitly states same-process concurrent calls are unsupported. Runtime races were not measured because no built caller was available.

## Applicability

Exocrate crate 0.1.0 and Anneal setup code at the identified zerocopy revision. The report is source-backed; it does not claim observed runtime concurrency outcomes. Related corpus reports: [exocrate-atomic-staging-rename-main-41f5b37](../exocrate-atomic-staging-rename-main-41f5b37/REPORT.md), [exocrate-cache-version-identity-main-41f5b37](../exocrate-cache-version-identity-main-41f5b37/REPORT.md).

### Current integration and version identity

Current `cargo-anneal setup` enters the `main.rs` CLI and calls `setup_installation_dir`, which selects `LocalDev` when `__ANNEAL_LOCAL_DEV` exists, otherwise `UserGlobal`; `--local-archive` selects a local archive, otherwise it selects platform-specific remote metadata ([main.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/src/main.rs#L30), [main.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/src/main.rs#L58)). The adjacent `setup.rs` has the same Exocrate configuration and a `run_setup` helper, while `Toolchain::resolve` only resolves a directory and asks the user to run setup if absent ([setup.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/src/setup.rs#L16), [setup.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/src/setup.rs#L65), [setup.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/src/setup.rs#L127)). `main.rs` declares the `setup` module, but its CLI `Setup` arm calls its own `setup` function ([main.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/src/main.rs#L12), [main.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/src/main.rs#L94)).

Anneal's configuration is `.anneal/toolchain/<slug>`, where the slug is a compile-time SHA-256 hex digest over the *paths and bytes* of Anneal's `Cargo.toml` and `Cargo.lock`, followed by OS and architecture bytes ([setup.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/src/setup.rs#L16), [lib.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/exocrate/src/lib.rs#L550)). `UserGlobal` starts at the user's cache directory; `LocalDev` starts at `CARGO_MANIFEST_DIR/target` or the current directory's `target` fallback; `Custom` allows a caller-supplied base ([lib.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/exocrate/src/lib.rs#L242)). The manifest currently contains placeholder remote URLs and hashes, so default remote installation cannot be treated as a usable release path ([Cargo.toml](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/Cargo.toml#L27)).

**Source finding:** An update to either versioned file yields a new slug when the binary is rebuilt, even if the archive itself did not change. An archive change with unchanged slug does not trigger an update: an existing directory wins before opening the source. A local archive's contents are not part of the slug; local archives also have no expected checksum in `open_source` ([lib.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/exocrate/src/lib.rs#L195), [lib.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/exocrate/src/lib.rs#L229)). Old version directories are retained; Exocrate documents no cleanup helper ([lib.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/exocrate/src/lib.rs#L131)).

**Inference from the commit sequence:** Cooperating separate processes can observe either no target directory or the renamed populated target; they do not need a read lock for the existence check. This relies on the same-filesystem sibling rename and on every writer respecting the persistent lock. It does not establish durability after power loss: the code has no file or directory `fsync`. It also does not protect against manual creation of an incomplete target, external deletion after resolution, or modifying the installed directory after commit. A killed process can leave `.staging`; the next lock holder removes it before retrying. The source uses an advisory file lock, so noncooperating writers are outside this guarantee ([sync.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/exocrate/src/sync.rs#L16), [sync.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/exocrate/src/sync.rs#L123)).

### Process concurrency and status semantics

The process coordination key is the full target path's sibling `.lock` file. Distinct version slugs have distinct locks and can install independently. For the same target, a losing process waits at `lock_exclusive`, then rechecks the target and skips extraction if the winner committed. A checked-in test verifies the lock filename, locked state during population, and persistent unlocked file after installation and deletion; it is a *test assertion in source*, not a test run in this report ([sync.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/exocrate/src/sync.rs#L90), [sync.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/exocrate/src/sync.rs#L351)).

There are two caller-visible race details. First, both processes can miss the initial existence check and open their source independently. The remote branch calls `ureq::get(...).call()` before the lock; the archive body is consumed only if population runs. Thus duplicate request setup is possible, and a loser can fail before waiting if its source cannot be opened even though the winner later succeeds. Second, `install` returns `()` whether this caller populated or the post-lock recheck found the winner's directory. `resolve_installation_dir_or_install` then unconditionally returns `NewlyInstalled` after that call. Under this race, `NewlyInstalled` means “the initial check missed and the operation finished successfully,” not “this caller performed the installation” ([lib.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/exocrate/src/lib.rs#L201), [lib.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/exocrate/src/lib.rs#L205), [lib.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/exocrate/src/lib.rs#L407), [sync.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/exocrate/src/sync.rs#L116)). These are source deductions; no two-process trace was run.

### Same-process concurrency limit

`ManagedDirName::check_exists_or_create` explicitly states that multiple concurrent calls **from the same process** are not concurrency-safe ([sync.rs](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/exocrate/src/sync.rs#L63)). The implementation has one shared staging pathname per target and no process-local mutex around the lock and cleanup path. **Inference:** callers must serialize same-target installation attempts within one process. The exact failure mode on this host was not measured, so this report does not claim that a particular pair of threads will corrupt, block, or succeed. The source's process lock cannot be promoted into a same-process guarantee against its own stated limitation.

### Implications for the remaining Anneal work

Keep Exocrate setup as a separate, serialized prerequisite for workers in one Anneal process. Workers may share a versioned directory only after setup has returned successfully and the required tool paths have been checked. Do not interpret a directory existing by itself as evidence that the expected toolchain contents, archive identity, or verification proof inputs are valid. In accordance with [the design contract](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/DESIGN.md#verification-success-has-a-precise-meaning), setup failure, absent tools, and uncertain version identity must remain tool failures or incomplete work, never verification success.

If a later report needs an empirical install race, its prompt should explicitly authorize building a tiny Exocrate caller from checked-in source, establish an offline dependency cache, and allocate two separate process invocations with a local archive and isolated `Location::Custom` root under `$CHECKOUT_LOCAL_TOOLS/scratch/exocrate`. Record each process's initial state, status, source-open outcome, elapsed time, target contents, and lock/staging inventory. Bound each invocation to 30 seconds, the scratch tree to 1 GiB, and recheck free disk before running. No setup change is needed for the other reports solely on this source finding; they should treat the Exocrate concurrency guarantees and status limitation above as unmeasured until that probe exists.
