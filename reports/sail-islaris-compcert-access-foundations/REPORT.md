# Sail, Islaris, and CompCert mechanisms for missing ISA and access obligations

## Summary

Three precise mechanisms address different Kraken integration gaps. Sail can supply larger architecture definitions and generated prover interfaces; Islaris turns constrained instruction traces into Iris proof obligations with a separate trace-to-ISA validation question; CompCert's memory primitives check every byte of a chunk with block permissions and alignment before its assembly step proceeds. None is a ready replacement theorem for Kraken or a Rust borrow bridge.

Two configuration boundaries matter immediately. The examined Sail Lean backend defaults to a Float-based `FakeReal` interface unless real-number support is selected. The examined Islaris Arm-to-Sail experiment is explicitly unfinished and contains admissions. These facts concern named source paths; they do not invalidate unrelated trace-logic theorems or establish that every generated scalar model uses approximate real operations.

## Applicability

The comparison directly inspects Sail `7e0e53d183cad75b8f36bfbbecc0ef75614a8418`, Islaris `c978e10f50db5c40f0fdf113f5f76a779782c6f9`, and CompCert 3.18 `74cbdbf0e86ecbfa39a5ca8f248f77fb2f974cb6`. The Islaris PLDI 2022 paper is identified by DOI `10.1145/3519939.3523434`; it is used for its published architecture/validation scope, not as evidence of later tool execution.

This is new source investigation of ISA/import/access interfaces, not a repeated whole-compiler survey. CompCert is the AS23 route selected because the pinned Kraken permission-request boundary lacks an enforced full-width permission predicate. Existing corpus material on assembly-versus-binary compiler endpoints supplies context only; it is not the evidence for the newly examined memory primitives.

No Sail/Isla/Islaris/CompCert prover or compiler was installed or run. The owned Python probe executes finite predicate fixtures only. AS18/AS19/AS23 comparison scopes are answered below; actual shared-instruction proofs and tool ports remain unexamined.

## Findings

### Sail generation changes the semantic input, not the need to identify it

Sail's pinned README distinguishes full architecture definitions from fragments: it describes Arm-A definitions translated from Arm's ASL and an adopted RISC-V model, while x86/CHERI-x86 and legacy Power are user-mode fragments. It describes executable emulators and Coq, Isabelle, and HOL4 generation; the separately inspected Lean plugin implements a Lean output route. The existence of a Lean plugin does not make every listed model available, buildable, and proof-ready under every backend. The architecture model revision, configuration, preprocessing, support library, and generated output are additional subjects. [Pinned inventory](https://github.com/rems-project/sail/blob/7e0e53d183cad75b8f36bfbbecc0ef75614a8418/README.md#sail-isa-models), [Lean plugin](https://github.com/rems-project/sail/blob/7e0e53d183cad75b8f36bfbbecc0ef75614a8418/src/sail_lean_backend/sail_plugin_lean.ml#L175).

The Lean plugin runs a rewrite pipeline, including undefined-value and loop/effect rewrites, before emitting definitions. It exposes support-library repository/revision/path options, emits a Lean toolchain and Lake project, and selects a specialization interface. `SpecializationArchSem.lean` preserves named interfaces for register access, undefined values, memory requests/results, system registers, barriers, cache/TLB operations, translation events, and exceptions. These are calls into the selected Sail support semantics, not a proof that one chosen execution interpreter handles every effect faithfully. [Generated project/support configuration](https://github.com/rems-project/sail/blob/7e0e53d183cad75b8f36bfbbecc0ef75614a8418/src/sail_lean_backend/sail_plugin_lean.ml#L310), [architecture interface](https://github.com/rems-project/sail/blob/7e0e53d183cad75b8f36bfbbecc0ef75614a8418/src/sail_lean_backend/Sail/SpecializationArchSem.lean#L13).

The plugin initializes `opt_lean_real_numbers` to false and selects `FakeReal.lean` unless enabled. That file defines `real` as `Float`, ordinary real operations through Float operations, `random_real` as a constant, and `undefined_real` by returning the default value. The real-number option selects `Real.lean` and a mathlib dependency. Therefore a proof that materially uses Sail real-number primitives needs this configuration accounted for; scalar integer code that never uses them is a separate scope. This source observation alone does not establish a soundness bug in a particular generated ISA theorem. The plugin also permits explicitly marked partial functions; totality and termination claims must examine the generated declarations actually used. [Default/options](https://github.com/rems-project/sail/blob/7e0e53d183cad75b8f36bfbbecc0ef75614a8418/src/sail_lean_backend/sail_plugin_lean.ml#L81), [real-library selection](https://github.com/rems-project/sail/blob/7e0e53d183cad75b8f36bfbbecc0ef75614a8418/src/sail_lean_backend/sail_plugin_lean.ml#L325), [FakeReal](https://github.com/rems-project/sail/blob/7e0e53d183cad75b8f36bfbbecc0ef75614a8418/src/sail_lean_backend/Sail/FakeReal.lean#L6).

For Kraken, there are two distinct candidate arrows: prove selected Kraken operations refine an independently identified Sail model under configuration constraints, or prove programs directly over generated Sail semantics. The first retains Kraken's compact proof interface but needs a relation for all relevant state/effects. The second avoids that handwritten relation but inherits generator/runtime/configuration correspondence and proof cost. Neither arrow was proved by inspecting generated source. Basis: **source**; alternative-arrow comparison **derived**.

### Islaris adequacy is over traces; validating their ISA origin is another theorem

The published Islaris approach symbolically simplifies constrained Sail instruction executions using Isla and proves properties of the resulting traces in an Iris-based logic. Its optional translation-validation result was for RISC-V, not Arm. The paper identifies Isla and the SMT solver as trusted in the basic route and restricts its demonstrated configuration to sequential settings; it does not claim a general relaxed-memory or address-translation integration. [Primary paper, §§1, 3–5](https://www.cl.cam.ac.uk/~pes20/2022-pldi-islaris.pdf).

The pinned `isla_adequacy` theorem makes its endpoint explicit. Given an instruction trace table, initial memory and register maps, a trace specification `Pκs`, and an Iris proof using `instr_table`, `backed_mem`, `spec_trace`, and points-to resources, any specified finite `nsteps` execution yields non-stuck final threads and `Pκs κs`. This is a safety/trace adequacy statement with premises; it is not a termination theorem or, by itself, a theorem relating the trace table to source Sail opcodes. [Exact adequacy statement](https://github.com/rems-project/islaris/blob/c978e10f50db5c40f0fdf113f5f76a779782c6f9/theories/adequacy.v#L91).

The operational semantics carries memory lengths explicitly. A trace `ReadMem` or `WriteMem` becomes a labeled operation with a length `N`; a positive-length memory operation either accesses all present map bytes or, for a wholly disjoint absent range, emits an external read/write event with a no-overflow condition. A partially backed range is not silently treated as one ordinary mapped access. The inspected branches explicitly ignore memory tags and access kinds. These choices matter to any comparison with permission checks, MMIO, atomics, or capability/provenance information; absent memory is not simply synonymous with a permission fault. [Operational memory branches](https://github.com/rems-project/islaris/blob/c978e10f50db5c40f0fdf113f5f76a779782c6f9/theories/opsem.v#L504).

The main README requires user-supplied constraints and manually selected disassembly in its example workflow. It records tested Isla and snapshot pins (`b8e614bda4a20e42c37d8b216853653133d04322`, `b58da9170470a422c9396983ac8f87f0a63ba6f8`). These pins identify documented prerequisites, not independently examined or executed source subjects of this report. If pruning omits a feasible path, a correct proof about the remaining trace does not repair that omission. A trace certificate must establish coverage under the exact constraints, not only correctness of each retained path. [Pinned frontend workflow](https://github.com/rems-project/islaris/blob/c978e10f50db5c40f0fdf113f5f76a779782c6f9/README.md#generating-coq-traces-from-a-partial-decompilation-of-pkvm).

The separate `sail/` Arm-linking directory is explicitly described as work in progress with untested installation directions. `sail_opsem.v` admits `sim_Write_reg`; `test.v` declares `_admit`, an interrupt-simulation axiom, and admitted undefined-value, translation, and fetch lemmas including `sim_fetchA64`. This is direct evidence that those particular experimental files do not provide the missing closed Arm trace-to-Sail bridge. It is not a repository-wide closure audit, and it must not contaminate a separate theorem merely by co-location. [WIP description](https://github.com/rems-project/islaris/blob/c978e10f50db5c40f0fdf113f5f76a779782c6f9/sail/README.md), [admitted register lemma](https://github.com/rems-project/islaris/blob/c978e10f50db5c40f0fdf113f5f76a779782c6f9/sail/sail_opsem.v#L232), [experimental fetch and interrupt bridge](https://github.com/rems-project/islaris/blob/c978e10f50db5c40f0fdf113f5f76a779782c6f9/sail/test.v#L441).

Basis: **source**, with the explicitly attributed published scope from the paper. No fresh Coq dependency-closure check or trace validation ran.

### CompCert provides an enforced full-width permission mechanism with another pointer model

CompCert's `Mem.valid_access m chunk b ofs p` requires current permission `p` at every offset in `[ofs, ofs + size_chunk chunk)` and chunk alignment. `Mem.load` asks for Readable and returns None if this predicate fails; `Mem.store` asks for Writable. `loadv` also requires a `Vptr b ofs` and prevents pointer-modulus overflow. The x86 abstract assembly `exec_load`/`exec_store` turns a failed memory primitive into `Stuck`. This directly addresses a missing Kraken obligation: permission checks must cover every byte actually accessed, not just map membership or a narrow request prefix. [Full-width predicate](https://github.com/AbsInt/CompCert/blob/74cbdbf0e86ecbfa39a5ca8f248f77fb2f974cb6/common/Memory.v#L220), [load/loadv](https://github.com/AbsInt/CompCert/blob/74cbdbf0e86ecbfa39a5ca8f248f77fb2f974cb6/common/Memory.v#L428), [store](https://github.com/AbsInt/CompCert/blob/74cbdbf0e86ecbfa39a5ca8f248f77fb2f974cb6/common/Memory.v#L534), [assembly primitives](https://github.com/AbsInt/CompCert/blob/74cbdbf0e86ecbfa39a5ca8f248f77fb2f974cb6/x86/Asm.v#L577).

CompCert pointers have block/offset structure. Kraken's inspected memory has flat BitVec keys. Transferring the mechanism therefore needs a state relation connecting blocks and permissions to concrete address ranges. CompCert's block permission is still not automatically a Rust allocation/provenance/borrow model or a real page-table permission. Its assembly syntax contains compiler-oriented pseudo-instructions and its semantics also has external-call rules; it is not a general arbitrary-x86 binary decoder. The useful reusable mechanism is the full-range permission gate and resulting stuckness, not an inference that CompCert already closes Kraken's entire ISA/ABI/Rust bridge.

### Executed finite fixtures separate the predicates without simulating an upstream tool

`access_models.py` creates a 64-byte defined/mapped region, grants write authority for its first eight bytes, and checks every byte of requested widths. The scalar eight-byte write predicate succeeds; the 32-byte vector write fails despite complete map membership and mapping; a crossing 64-byte access fails map membership; a separate expired logical-authority flag can be false with the same physical bytes and VM accessibility. All expected outcomes pass.

These are explicit finite logical fixtures. They are neither CompCert executions nor evidence that a chosen Rust alias model implements that logical flag. They help preserve the independence of byte existence, VM accessibility, full-width permissions, and logical lifetime authority. No amount of successful fixture execution establishes the cross-model relation. `access_models.json` records the exact results.

## Boundaries

- **Known not to apply:** basic trace adequacy does not validate the origin/completeness of its trace table. The inspected Arm bridge files contain admissions; the paper's RISC-V validation scope cannot be transferred to Arm by analogy.
- **Known not to apply:** Sail's generated Lean code alone does not prove the generator, selected support interpretation, or ISA-to-hardware relation correct. Float-based real support needs explicit configuration accounting where used.
- **Not examined:** compiling and importing an exact generated Lean ISA model, proving selected Kraken/reference instructions, an underspecified-result/fault case, RISC-V validation theorem closure, or a successful shared load/store proof and rejection mutant in Sail/Islaris/CompCert. These are genuine remaining research experiments, not already established theorems awaiting implementation.
- **Not examined:** ACL2 x86isa, K x86, HOL4/HolBA, CakeML machine interfaces, bedrock2, and other RISC-V systems. They are deferred because this bounded comparison selected CompCert's concrete range-permission mechanism; no comparative ranking of those families follows.
- **Not examined:** source Rust safety correspondence, borrowed-pointer authority, hardware page tables, weak memory, or arbitrary device behaviors.

## Revalidation

First decide which arrow needs closure. For generated Lean semantics, pin the architecture model, generator, support library, toolchain, real-number mode, and interpreter before proving a scalar operation. For Islaris, separately check `isla_adequacy`, opcode/constraint-to-trace validation, and the architecture-specific validation theorem's imported assumptions. Mutate one feasible branch and one memory operation to test completeness, not only path-local correctness. For the CompCert mechanism, rerun a real model proof with full-width loads/stores and then cross a permission boundary.

`python3 support/access_models.py` is the cheap fixture check; it cannot substitute for those upstream proof experiments. A new Arm validation result or Sail backend configuration deserves fresh source and closure inspection rather than carrying forward this report's boundaries.
