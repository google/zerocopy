# Prepared Lake operation, cache-integrity, and native-artifact contract probes

## Summary

In a tiny two-package Lean/Lake 4.30.0-rc2 fixture, clean Lean-configured and TOML-configured producers built the same `Dep.olean`, `.ilean`, and generated `.c` bytes and passed the same consumer theorem and axiom check. The Lean package configuration additionally compiled a configuration OLean; the producer trace bytes differed. A prepared tree still passed no-build setup and batch checking after relocation to a new path depth with its old path absent, a frozen producer, isolated home, and a macOS profile that denied a loopback network control. The frozen producer and consumer inventories did not change during those reads; a source-only non-writable consumer failed when Lake needed to create `.lake`.

Artifact acceptance was operation-specific. A separate `+Dep:dynlib` build created a 50,464-byte `.dylib`; ordinary batch checking worked without it, while explicit loading of invalid dylib bytes failed and a missing native facet made no-build Lake reject the target. Most consequentially, replacing a cache object named for `depValue = 7` with a **valid** OLean for `depValue = 9` left Lake `--no-build build Dep` and `--no-build setup-file` successful. Direct Lean then evaluated 9, and a proof expecting 8 failed. A truncated cache output mapping was rejected with invalid JSON and out-of-date status. Lake's cache lookup success was not an independent integrity or proof-equivalence verdict in this fixture.

## Applicability

The experiment used local `lean` and `lake` at `leanprover/lean4@3dc1a088b6d2d8eafe25a7cd7ec7b58d731bd7cc`, version `v4.30.0-rc2`, on macOS 26.6.2 arm64 with APFS and 8 GiB RAM. The two local packages were `probe_dep`, defining `depValue : Nat := 7` or 9, and `probe_consumer`, importing `Dep` and proving `depValue + 1 = 8` or 10 by `decide`. Every consumer had a complete relative path manifest before its first Lake command. There were no registry or remote dependencies. The fixture is generated by `support/probe.py`; it is not an Anneal archive, generated Rust model, Mathlib installation, or proof server.

Twenty-six commands ran sequentially with 25-second limits, `ELAN_TOOLCHAIN` pinned, `LEAN_NUM_THREADS=1`, `LAKE_CACHE_DIR` and `LAKE_ARTIFACT_CACHE` controlled, and an empty HOME under conversation-owned scratch. The offline cells were wrapped in `/usr/bin/sandbox-exec` with `(deny network*)`; a Python loopback-connect control under the same profile failed with `Operation not permitted`. That control shows network denial applied to the child process, but the local-only Lake fixture did not need network access. The script required at least 15 GiB free disk and used only disposable local work paths.

This extends the earlier `anneal-3730-lake-concurrency-preparation-v4-30-0-rc2`, `anneal-3730-lake-identity-matrix-v4-30-0-rc2`, and `anneal-3730-lake-writer-scale-v4-30-0-rc2` packages. The new deltas are a valid wrong-generation cache object, truncated mapping, actual native facet/load controls, Lean versus TOML configuration, and a network-denied relocated read. It informs [#3731](https://github.com/google/zerocopy/issues/3731) I092/I093/I097–I099/I101–I104/I125/I150 most directly, with narrower evidence for I089/I096/I120/I151. No issue item is exhausted by this fixture.

## Findings

### Clean configuration variants and prepared reads have the same tested logical outcome

Both clean package configurations built `Generated`, returned `setup-file` import information, and ran `lake env lean --json Generated.lean` with exit 0. The batch output evaluated 8 and printed that `generatedEq` depends on no axioms. The `Dep.olean` SHA-256 was `cebebbbc892381bd3920a0b12ab5e4d65f1804574357994ccb20f95f87f98f9b` in both trees; `.ilean` and generated `.c` hashes also matched. Their `Dep.trace` hashes differed. The Lean configuration produced `.lake/config/probe_dep/lakefile.olean` and its trace, while the equivalent TOML configuration did not. **Basis: execution**. This is one declared package shape; executable configuration can depend on arbitrary Lean/environment behavior not exercised here.

A copy of the clean Lean-configured tree was placed under `different/depth/prepared`, then the old `clean-lean` path was renamed away and the relocated producer was made read-only. Under the network-denying profile, no-build `build Dep`, no-build `setup-file Generated.lean`, and batch `lean --json` all exited 0. Setup named the relocated producer OLean; batch again evaluated 8 and reported no axioms. Hash/size/mode inventories of the frozen producer and the writable consumer were identical before and after these three operations. **Basis: execution**. This verifies one final-path layout and read-only operation set, not arbitrary archives, imported native files, Lean server workers, or all path-bearing traces.

In a separate copy, the consumer's `.lake` was removed and its source/control directory made non-writable. `lake build Generated` exited 1 with `permission denied` for `consumer/.lake`; this shows the tested build operation needed consumer-local mutable state even though the prepared producer reads did not write to the producer. **Basis: execution**. It does not prove every Lake read can run from a non-writable consumer directory.

### Native code adds another operation-specific artifact family

`lake build +Dep:dynlib` succeeded and produced `probe__dep_Dep.dylib` (50,464 bytes in the preserved run). Explicit `lake env lean --load-dynlib` with that file and the consumer source exited 0; replacing its input with a short invalid dylib made the same explicit load exit 1 with a `dlopen` error. Removing the dynlib from a copied prepared producer made `--no-build build +Dep:dynlib` exit 3 as out of date, but ordinary batch checking of `Generated.lean` still exited 0 and evaluated 8. **Basis: execution**. The distinction is between a requested native facet and a batch import that did not require it. A native plugin with initialization, ABI replacement, search-path collision, or server process lifetime was not tested.

### Cache filename and mapping are insufficient to prove object bytes

Two isolated artifact caches were populated with source-identical package names and versions but `depValue` definitions 7 and 9. The producer cache output mappings named different content-addressed OLean paths. Direct Lean loader controls using each intact object evaluated 7 and 9 respectively. A third cache copied the version-7 mapping and filenames but replaced the bytes of its referenced OLean with the valid version-9 OLean; its object name remained `4ab07c203eb6f06e.olean`, while its bytes had SHA-256 `fe893ce3c24d2c295ade06017eb859638f0e75aa29df7e9444f3026bfd7a7745`.

Against a source/control-only value-7 reconstruction, Lake `--no-build build Dep` exited 0 and logged `Fetched Dep`; `--no-build setup-file Generated.lean` also exited 0 and returned that object path. Direct Lean given that object's bytes under the conventional `Dep.olean` name evaluated 9. When direct Lean checked the value-7 consumer proof, the `decide` tactic reported that `depValue + 1 = 8` was false, `#eval` returned 10, and the command exited 1. The failing theorem's subsequent axiom print mentioned `sorryAx`; that is an error-path artifact, not a successful verified theorem. **Basis: execution**. This is local deliberate tampering, not a collision in a cryptographic hash function or evidence about remote cache transport validation.

In a separate cache copy, truncating the producer output-mapping JSON to `{"data":` made both no-build `build Dep` and no-build `setup-file` exit 3 with an invalid-JSON warning and out-of-date status. **Basis: execution**. Thus the tested Lake path rejected an incomplete mapping but accepted a present, parseable, wrong-generation OLean object behind a retained mapping. The object-byte mismatch must be checked before a verification consumer treats the returned artifact as belonging to the claimed source generation. **Basis: derived** from the paired negative controls.
