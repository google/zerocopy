# Generated Lean files under an interactive Lean server

## Summary

A generated Lean file has two different identities in an interactive workflow: the bytes written by the generator and the document state currently owned by the LSP client. Once a client sends `textDocument/didOpen`, LSP makes the client-managed text authoritative for that open document. Re-running Aeneas and replacing the file on disk therefore does not, by itself, replace the text that Lean is elaborating for an already-open document. The client must synchronize the regenerated text with `didChange`, or close the document and reopen the regenerated bytes.

Lean v4.30.0-rc2 makes that distinction concrete. The watchdog retains each open document's URI, version, and text and starts one worker process for it. Edits are forwarded as `didChange`; the worker incrementally reuses snapshots where valid, invalidates work after the changed region, and cancels pending requests tied to the previous document state. A worker restart is reconstructed from the watchdog's retained document text, not by rereading the path as an implicit source of truth.

Imported generated modules have a separate lifecycle. Lean 4 requires compiled `.olean` artifacts for imports. Editing or regenerating an imported source file does not make an already-open dependent silently elaborate against the new source. Lean's server documentation explicitly describes saved dependencies as stale and uses dependency refresh/restart to rebuild and reload them. Thus changing the generated module graph can require both document synchronization for directly opened generated files and dependency rebuilding/restart for files that import them.

Aeneas itself writes generated Lean to ordinary destination paths. At the selected revision, `extract_file` opens the target filename and emits the generated source; split mode writes `Types.lean`, `Funs.lean`, and optional companion modules under the selected destination. There is no LSP handshake in this generation path. The durable interactive rule is therefore: treat regeneration as a source-production event, then explicitly advance the Lean document/dependency state before asking semantic questions about the new generation.

No Aeneas, Lean, Lake, editor, LSP, or MCP process was executed for this report. The result combines the normative LSP 3.18 document-ownership rules with exact pinned Aeneas and Lean source.

It records the state transitions an interactive implementation must respect if it exposes generated Lean through Lean's language server.

“Generated file” means a Lean source file produced by Aeneas from LLBC, including single-file output and the split `Types.lean` / `Funs.lean` package form. User-maintained external-model files are not generator-owned merely because they sit next to generated files.

Three state layers are intentionally separated:

1. **generated source state** — bytes Aeneas writes to destination paths;
2. **open document state** — text and version managed by the LSP client for a URI; and
3. **imported dependency state** — compiled module artifacts and environment loaded by a file worker.

A change can advance one layer without advancing the others. The workflow is correct only when the layers required by the next semantic query have been synchronized.

The existing `aeneas-lean-project-package-anatomy-nightly-2026-06-03` report owns the generated package structure. `aeneas-generated-lean-stability-near-nightly-2026-06-03` owns cross-version output stability. `aeneas-generated-source-determinism-nightly-2026-06-03` owns same-input generation determinism. `lean-server-tactic-state-v4-30-0-rc2` owns goal-at-position semantics and the Lean RPC surface. This report concerns the lifecycle connecting regenerated source to an already-running interactive server.

## Findings

### Open LSP documents are not implicit views of the filesystem

LSP 3.18 defines `textDocument/didOpen` as transferring management of the document's content to the client. While the document is open, the server must not obtain its content by rereading the document URI. `didClose` reverses that state: after close, the document's master again exists where the URI points.

This creates the central generated-file boundary. If Aeneas overwrites `Foo.lean` while `Foo.lean` is already open through LSP, the filesystem has a new generated artifact but the open LSP document does not thereby acquire those bytes. The client must send the new content through the synchronization protocol or close and reopen the document.

Basis: **normative** LSP 3.18 `didOpen` / `didClose` semantics + **derived** generated-file consequence.

### A `didChange` is a document-state transition, not merely a notification that disk changed

LSP requires a document to be open before `didChange`. The change carries a document version naming the state after the supplied edits, and multiple changes in one notification are applied in the order received. The specification also requires the client to synchronize document state before requesting information when it needs reliable results.

A regeneration-aware client therefore needs to convert the generator's output into an LSP document transition. Two conservative choices are sufficient at the protocol layer:

- replace the client buffer with the regenerated bytes and send the corresponding versioned `didChange`; or
- send `didClose`, reload the regenerated file, and send a fresh `didOpen`.

The protocol does not define a special “file was regenerated” operation. File-watch notifications and filesystem replacement are not substitutes for document synchronization once the URI is open.

Basis: **normative** LSP 3.18 document synchronization + **derived** workflow.

### Lean retains open-document text explicitly so workers can be restarted from it

Lean's watchdog is not a thin pass-through to files on disk. For each open document it keeps document metadata including URI, version, and a `FileMap` containing the current text. On `didChange`, the watchdog computes the new document text, updates that retained state, and forwards the change to the worker.

When starting or restarting a file worker, the watchdog sends the worker an `initialize` request followed by one `didOpen` containing the retained URI, version, and full text. The source comment states that no further `didOpen` notifications are forwarded to that worker; subsequent edits use `didChange`. A crashed worker is restarted only when a later `didChange` arrives, and the restart begins from the watchdog's retained document state.

This strengthens the LSP-level conclusion for the pinned Lean implementation: an out-of-band generator write is not the recovery source for an open file worker. If the client never advanced its document text, a restarted worker can faithfully recover the old client-owned version.

Basis: **source** in `Lean.Server.Watchdog`.

### Editing an open generated file invalidates semantic work after the edit boundary

Lean's file worker incrementally processes an open file as a tree/chain of snapshots. Its source explains that `didChange` locates the processing task containing the change. Work that cannot safely be reused is terminated and elaboration restarts from the appropriate point. Pending requests are also cancelled by edit through a cancellation path distinct from explicit `$/cancelRequest`.

The language processor is more careful than “reuse everything before the byte offset.” Lean's incremental parser and elaborator preserve snapshots only when syntax/state reuse conditions hold. The parser explicitly accounts for edits whose grammar effect can reach before a naïve command boundary, and command elaboration reuses persistent state only when the corresponding syntax is unchanged.

A client should therefore identify semantic results with a document generation rather than with a file path and position alone. After regeneration, a tactic-state response from the previous generation is stale even if the target line number still exists.

Basis: **source** in `Lean.Server.FileWorker`, `Lean.Server.RequestCancellation`, and `Lean.Language.Lean` + **derived** generation-identity requirement.

### Aeneas writes generator output independently of the LSP lifecycle

At the selected Aeneas revision, `Translate.extract_file` opens `fi.filename` and writes the generated source, including the standard “THIS FILE WAS AUTOMATICALLY GENERATED BY AENEAS” header and backend-specific content. `-dest` chooses the output directory; `-subdir` affects generated paths/imports; and `-split-files` changes the output into multiple files such as `Types.lean` and `Funs.lean`. The generated entry module, when requested, is also written directly to its destination.

There is no Lean-server or LSP operation in this source path. Aeneas generation and interactive-document synchronization are separate transitions. An integration that runs Aeneas behind an agent or editor must bridge them explicitly.

This report does not treat direct target-file writing as an atomic replacement guarantee. It only needs the narrower fact that generation changes filesystem source independently of any existing LSP document state.

Basis: **source** in pinned Aeneas `Translate.ml`, `Main.ml`, and `Config.ml`.

### Split generation makes the module graph part of the interactive invalidation surface

Aeneas can emit one crate file or a split package. In split mode, Lean output commonly includes `Types.lean` and `Funs.lean`; `Funs` imports `Types`, with optional external-model and termination modules. `-subdir` affects import paths. Upstream setup documentation places those generated files inside a Lean/Lake project that imports the Aeneas support package.

Regeneration can therefore change more than the contents of one open buffer. It can change several source files, their declaration names, and their import graph. A client that synchronizes only the file under the cursor can still be querying an environment built from stale generated dependencies.

For a package-wide regeneration, the safe unit is the generated package generation: synchronize directly opened generated documents, rebuild or refresh changed imported modules, and only then treat dependent semantic queries as belonging to the new generation.

Basis: **source** + upstream **documentation** + **derived** lifecycle consequence.

### Imported-module changes are not propagated as unsaved live-document state

Lean's server documentation gives a separate lifecycle for dependencies. Lean 4 imports compiled `.olean` artifacts. If two files `A` and `B` are open and `B` imports `A`, editing open `A` does not make `B` immediately elaborate against the unsaved in-memory contents of `A`; `B` can continue to operate against the previously compiled dependency.

When the dependency is saved and changes become relevant, the server can mark dependent workers stale. Lean's documented “refresh file dependencies” path restarts the affected worker and uses `lake setup-file` to rebuild and locate dependencies. The watchdog source likewise sends a stale-dependency notification to workers for files that depend on a saved file.

This is especially important for generated Lean. If regeneration changes a generated module imported by a proof file, sending `didChange` to the proof file alone is not a dependency update protocol. The generated module must reach the compiled/project state the proof worker will load, followed by the appropriate dependency refresh/restart.

Basis: upstream **documentation** + **source** in the Lean server.

### Directly opened generated files and imported generated files require different synchronization

The two common cases can be summarized as follows:

| Generated artifact role | What changes first | What does **not** happen automatically | Conservative transition before semantic query |
| --- | --- | --- | --- |
| Generated `.lean` file is itself open | Aeneas changes disk bytes | Open LSP document does not adopt disk bytes | Replace client-owned document via versioned `didChange`, or close/reopen; wait for desired semantic readiness |
| Generated `.lean` file is closed | Aeneas changes disk bytes | No open-document state exists to update | Next open should send the regenerated text; dependent imports still need correct compiled state |
| Generated module is imported by another open file | Generated source/build artifact changes | Dependent worker does not silently switch to unsaved/new source | Build/refresh the dependency and restart/refresh dependent worker as required |
| Regeneration changes module/file graph | Several files/imports appear, disappear, or move | Incremental edit of one URI does not reconstruct project/module graph | Reconcile open documents, rebuild project state, and restart affected workers against one coherent generated package generation |

Basis: synthesis of the normative LSP and pinned implementation findings above.

### Interactive services need an explicit generated-package generation

LSP gives document versions for open text, but Aeneas regeneration can affect a package of files and Lean dependency artifacts. A robust agent-facing service therefore needs one identity above the per-document version. It can be an opaque generation ID, digest set, or another immutable handle, but it must distinguish “the proof query was answered against generated package G” from “the path currently contains whatever the latest generator wrote.”

A useful minimum state tuple is:

`(project identity, generated-package generation, document URI, document version, dependency generation, semantic readiness)`

Not every implementation must expose every component to users. The correctness requirement is that hidden caching and process reuse cannot make a result appear to belong to the new generated source when some server layer still belongs to an older generation.

This is an architectural consequence, not an LSP field prescribed by the standard.

Basis: **derived** from package-wide generation plus document/dependency state separation.

## Boundaries

- No Aeneas generation, Lean server, Lake build, editor, LSP client, or MCP bridge was executed. The report establishes source/specification behavior, not measured latency or race behavior.
- The report does not prove that every editor notices an out-of-band generated-file change or chooses the same buffer-conflict policy. Editor filesystem-watch behavior is client-specific.
- It does not claim that Aeneas's target-file writes are atomic or crash-safe. The inspected source establishes direct generation to paths, not filesystem transactionality.
- It does not establish a universal Lean “semantic-ready” barrier. The existing tactic-state report records `textDocument/waitForDiagnostics` for the pinned server; clients still need to define what readiness their operation requires.
- It does not establish that rebuilding a dependency is sufficient without worker restart in every server state. The pinned documentation explicitly uses refresh/restart for stale dependencies.
- It does not define the correct Anneal V2 package layout or generated-file ownership policy. Current Anneal deliberately leaves those design choices open.
- It does not establish same-revision Aeneas generation determinism or cross-release generated-source compatibility; dedicated reports cover those questions.
- It does not say user-authored external-model files may be overwritten. Aeneas split output distinguishes generated templates from user-provided model modules.
- It does not characterize multiple independent Lake workspaces inside one Lean server process; the dedicated multi-workspace report owns that boundary.
- It does not claim document version numbers alone identify a whole proof environment. Imported dependency state and process generation are separate.

## Revalidation

For a later Lean/Aeneas pin, the cheapest reliable revalidation is a small two-part probe backed by a source diff.

First, recheck the source-level contracts:

1. confirm the LSP version's `didOpen` / `didChange` / `didClose` ownership semantics;
2. diff Lean watchdog and file-worker document/restart logic, especially whether workers still start from retained client text and how edits invalidate requests/snapshots;
3. diff Lean dependency-staleness and refresh behavior; and
4. diff Aeneas's output-writing and split-package logic.

Second, run one discriminating integration probe with a tiny generated module and one dependent proof file:

1. open the generated module and query a known definition;
2. regenerate different valid bytes on disk without sending `didChange`; verify that the open document still reports the old client-owned state;
3. synchronize the new bytes with a new document version and wait for the chosen processing barrier; verify that semantic queries now reflect the new generation;
4. regenerate a module imported by the dependent proof, rebuild/refresh dependencies, and verify the dependent worker switches generations only after the documented refresh/restart transition; and
5. repeat with a split-package change that adds/removes a module to exercise project-graph invalidation.

Record exact generated bytes, document versions, process/restart events, build artifacts, and query results. Passing that probe establishes the lifecycle exercised by those cases; it does not by itself establish editor-specific file-watch behavior, whole-project concurrency safety, or all package-layout changes.
