# Aeneas process reuse API and output ownership at a pinned release

## Summary

The selected Aeneas source exposes translation functions through a public Dune library, but the local release installation has only the CLI executable. This host has no OCaml/Dune toolchain or compiled Aeneas library objects, so **same-process sequential and concurrent request reuse was not run**. Source-level mutable configuration and error accumulators make reset and isolation an explicit adapter design question; they are not a measured same-process failure.

The strongest executable comparator available here was separate CLI processes. At this pinned executable, 1, 2, and 4 concurrently launched jobs with private destinations produced the same file bytes as clean sequential A/B oracles. When a destination was shared across two distinct inputs or reused with different output flags, files from distinct requests coexisted. An unsupported request exited nonzero but overwrote some prior files with partial `sorry` output while retaining others. An external timeout killed a process; this establishes a host-side cancellation mechanism only.

## Applicability

The executable was the local macOS arm64 Aeneas nightly-2026.06.03 binary, SHA-256 `f476001e1a8e8c5cb1d8a621a25716d8e15f0809c8a023c5349357acc0911d03`; `aeneas -version` printed `aeneas unknown`. The inspected source checkout was `AeneasVerif/aeneas@ac9f1bc5262a5e4ff1e24ca78617121382202727`. Because the executable does not self-identify its commit, source observations are context for this selected release, not proof of its exact compiled source. Exact source excerpts and full-file digests are preserved in `support/source-api-evidence.txt`.

The execution input was three retained `.llbc` files generated by the earlier Charon/Aeneas boundary report: safe A (`0784839f4f1fd3ade660340301810d4a2109729b0ecbf47e6c2bf72bc9f96e7e`), changed safe B (`6774e33245dfeddc0a110c9ac2ea2244710a3d233140241589cb19ef370e4c55`), and unsupported raw-pointer case (`daab1c093c8af871b3d7751a9625f49137f3bedf03f19e9ab3a3c46b10fb078d`). Their source A/B text and exact LLBC bytes are retained in `support/fixture/`. The LLBC source spans still refer to the earlier report's fixture path; that does not affect this CLI translation observation. Baseline invocation was `aeneas -backend lean -no-progress-bar -sequential -split-files -gen-lib-entry -dest <directory> <file.llbc>`. All invocations used separate OS processes and the same binary.

This is an executable process/output-owner slice of [google/zerocopy#3731](https://github.com/google/zerocopy/issues/3731) I081/I082/I083/I087/I088, with partial relevance to I148/I158. The report extends the prior `anneal-3730-charon-aeneas-boundary-2026-09-29` and `aeneas-library-process-architecture-nightly-2026-06-03` reports; it does not re-test their Charon path or same-input determinism matrix.

## Findings

### Source API exposes translation stages but not a request-isolated host contract

`src/dune` declares a public `aeneas` library and a separate executable linked to it. `src/Translate.ml` defines `translate_crate_to_pure`, `extract_translated_crate`, and `translate_crate`. The CLI `src/Main.ml` parses one `.llbc` filename, loads it, clears `short_names`, applies pre-passes, calls `Aeneas.Translate.translate_crate`, then exits 1 if `Errors.error_list` is nonempty. This is source evidence that a custom OCaml host could call translation stages. It is not an exposed multi-request CLI protocol or proof that arbitrary calls are reusable without initialization/reset.

`Config.ml` stores backend, namespace, split-file, and parallel choices as process-global refs; `Errors.ml` stores `error_list` and `unique_errors` refs; `Parallel.ml` has a lazily created pool explicitly described as persistent and torn down at process exit. The inspected entry-point path does not reset these error refs between requests. A host embedding this library must establish request-specific configuration, error reset, output ownership, and serialization or synchronization by further source review and direct testing. The `Parallel` pool concerns parallel work *inside a translation* and does not establish safe concurrent translations in one process. The selected CLI exposes `-sequential` and ordinary OS process termination; inspection of these files found no request cancellation token or deadline API.

Basis: **source**, preserved line-numbered excerpts and file digests in `support/source-api-evidence.txt`. `command -v dune`, `ocamlc`, and `opam` found none, and the checkout had no `.cma`, `.cmxa`, or `.cmi` objects. Same-process calls were therefore unavailable to execute locally, rather than tested and found defective.

### Private destinations give the CLI comparator clean request outputs

The probe first built sequential clean A and B oracles. It then launched groups of 1 (A), 2 (A/B), and 4 (A/B/A/B) CLI processes with a private destination for each. Every process exited 0, and each complete inventory matched its corresponding oracle by filename, size, and SHA-256. The two-job group had one measured process-lifetime overlap pair and the four-job group had six; `-sequential` constrained internal Aeneas translation only. A produced `A.lean` `239c1030...`, `Types.lean` `a06e07ba...`, and `Funs.lean` `61d00aea...`; B produced the same Types hash, `B.lean` `ca425ba1...`, and `Funs.lean` `fffaaf29...`.

The request identity needed to interpret this observation includes the exact LLBC bytes, executable hash, backend, namespace, split-file/library-entry flags, destination ownership, and source/provenance association carried by the LLBC. `-namespace Alternate` on the same A input exited 0 but changed both `Types.lean` and `Funs.lean` hashes. Thus an LLBC digest alone is insufficient for byte-exact cache identity in this fixture. This does not determine a minimal complete cache key for all Aeneas options or dependencies.

Basis: **execution**, `support/probe.py`, `support/raw-results.json` (`oracles`, `isolated_groups`, `namespace_option`), and retained output trees under `support/artifacts/`.

### Shared destinations are not request ownership boundaries

Two concurrently launched, different-input CLI processes both exited 0 into one directory. Its final inventory contained `A.lean` and `B.lean` together, although neither clean oracle does. Its final `Funs.lean` matched A in the retained run; the earlier exploratory run had matched B. The latter was overwritten by rerunning the script, so only the retained A result is package evidence. The mixed entry-file inventory alone establishes that the directory cannot be treated as one request's complete output. This run did not deliberately interleave writes at sub-file granularity or prove a torn file.

Changing output mode in one directory gave a deterministic stale-output control: split-file A created `A.lean`, `Types.lean`, and `Funs.lean`; a subsequent successful unsplit A created a new `A.lean` matching a clean unsplit oracle but left `Types.lean` and `Funs.lean` from the previous request. A successful process exit therefore does not assert that all files in a reused destination belong to that request.

Finally, successful A followed by the unsupported raw-pointer input in the same directory exited 1 for the second request. The directory then contained old `A.lean`, new `Unsupported.lean`, and newly generated `Funs.lean` with `sorry`; Aeneas stdout explicitly called its generated files partial. The nonzero process status must gate publication even if generated paths exist. This also shows that checking the previous successful inventory after a failed run is insufficient without request-scoped ownership.

Basis: **execution**, `support/raw-results.json` (`different_input_shared`, `flag_change_shared`, `failed_shared`) and corresponding retained directories. The requirement for isolated staging plus status/completeness checks before publishing is **derived** from these cases.

### Cancellation was exercised at the host process boundary

The harness launched A into an empty private directory, applied a one-microsecond `communicate` timeout, then sent `kill` and reaped the child. The retained run timed out, exited `-9`, and left no files. This is an external-process cancellation control, not an Aeneas API cancellation test or a guarantee that kills at later phases leave no output. A result publisher must still reject killed jobs and clean or discard their private destination, because output may already have been written at an arbitrary kill point.

Basis: **execution**, `support/raw-results.json` `timeout_control`; the later-phase caution is **derived** from arbitrary termination timing and the observed partial-error output.

## Boundaries

- Same-process sequential A→B→A, same-process concurrent 1/2/4, internal default-parallel mode, error-state reuse, and pool cleanup after cancellation are **unknown**. The source exposes a possible library integration, but the installed environment did not provide an executable library build. No claim that Aeneas is unsafe or safe for those operations follows from this probe.
- The CLI group comparison covers two small LLBC inputs, fixed backend and mostly fixed flags, one host, and only the successful exit path. It establishes no general scaling or scheduling limit for I081/I082/I083.
- The shared-destination run establishes leftover/mixed file ownership and last-writer result for this fixture; it does not establish atomicity, torn-write behavior, filesystem crash recovery, or exact winner under another schedule.
- The source search for cancellation/deadline interfaces was limited to `Main.ml`, `Translate.ml`, `Config.ml`, `Errors.ml`, and `Parallel.ml`. It is not a whole-repository proof of absence.
- Generated Lean was compared as bytes, not checked with Lake/Lean or a theorem. The report does not validate Rust-to-Lean semantic correspondence, provenance completeness, or the finer source-to-proof mapping of I087/I148.

## Revalidation

For another executable, replay this bounded private-destination and shared-destination probe with a fresh binary hash and exact flags. For true same-process claims, compile an OCaml adapter against the pinned public library, explicitly reset request-global state, run A→B→A and 1/2/4 concurrent library requests into private destinations, include a failed request between successes, and compare every output and error list to fresh-process oracles. Add a cancellation mechanism at the adapter boundary and verify post-cancel state before accepting reuse. Until that test exists, process isolation remains the demonstrated execution boundary for this report.
