# GitHub Actions Cross-Repo Reusable Workflows: Rulesets, Token Scoping, Action Resolution, Binary Distribution, and Artifact/Checkout Boundaries

## Summary

- **Reusable workflow limits and least-privilege `permissions:` enforcement:** On github.com (`fpt`) and GitHub Enterprise Cloud (`ghec`), workflows support up to **10 levels** (1 top-level caller + 9 nested reusable workflows; 4 levels on GHES) and up to **50 unique called reusable workflows** per top-level workflow file (20 on GHES). Called workflows can only maintain or downgrade the caller's `GITHUB_TOKEN` permissions. For cross-org reusable workflows, `actions/runner` sets `isTrusted = false` and denies `id-token: write` unless explicitly declared at the caller workflow or calling job level. Crucially, `WorkflowTemplateConverter` validates each job's explicit `permissions:` against the **caller's ceiling** (`explicitMaxPermissions`), while jobs omitting `permissions:` inherit the **called workflow's top-level `permissions:`**—enabling a single caller job to grant a superset while the called workflow defaults all untrusted build/test shards to `contents: read` and selectively grants write scopes only to a final trusted publish/attest job.
- **GHEC Org Rulesets can call reusable workflows, with documented constraints:** `troubleshooting-rules.md` explicitly confirms that ruleset workflows (`workflows` rule) can invoke reusable workflows, and no documented rule prohibits calling an external public reusable workflow across org boundaries (subject to org/enterprise `allowed_actions` / `selected_actions.patterns_allowed`; `sha_pinning_required` still permits tag-referenced reusable workflows unless narrowed by patterns). Live GHEC execution for cross-org `uses:`, `allowed_actions` precedence, and ruleset `GITHUB_TOKEN`/GHCR repo binding remain `unknown`.
- **`./` actions in external reusable workflows are a TCB escape; `$/` resolves to the called workflow's repo without checkout:** In `actions/runner`, `steps[*].uses: ./actions/...` (`SelfAlias`) skips backend action download and resolves strictly against `$GITHUB_WORKSPACE` (whatever the caller checked out—executing untrusted PR code if run after PR checkout). By contrast, **`$/path/to/action`** (`SelfRepositoryAlias`, shipped July 2026 in `actions/runner >= v2.336.0`) rewrites to `job.workflow_repository` + `job.workflow_sha`, downloads outside `$GITHUB_WORKSPACE` via runner-authenticated `codeload`, requires no checkout, and eliminates self-referential SHA circularity, though it is **unsupported on GHES**.
- **Both GitHub Release direct web URLs and GHCR anonymous OCI v2 pulls consume zero `api.github.com` 60 req/hr unauthenticated quota:** Live probes confirmed `github.com/.../releases/download/<tag>/<asset>` (`302` → `release-assets.githubusercontent.com` Fastly + Azure Blob SAS, 214.7 ms / 2.56 MB) and GHCR anonymous Bearer OCI pulls (`ghcr.io/token` → manifest → `307` → `pkg-containers.githubusercontent.com`, ~410 ms / 6.6 MB) leave unauthenticated `api.github.com/rate_limit` untouched (`60/60`), whereas `api.github.com/repos/.../releases/assets/<id>` decrements `core.remaining`. Because `ubuntu-24.04` does **not** preinstall `oras`, `cosign`, `crane`, or `bubblewrap` (it preinstalls `curl`, `jq`, `sha256sum`, `tar`, `zstd`, `gh`, `docker`, `skopeo`), a ~20-line `curl`+`jq`+`sha256sum` puller (or direct Release URL + hardcoded SHA-256 in the SHA-pinned reusable workflow) provides zero-circularity, 100% offline integrity verification. `uses: docker://...` actions are unsuitable for host sandboxing because they translate `$GITHUB_WORKSPACE` to `/github/workspace` (breaking sibling `docker run -v` host mounts) and run under default Docker seccomp/AppArmor (blocking `bwrap`).
- **Checkout, host-Git `merge-tree`, and runner file-command hazards:** `actions/checkout@v4.4.0` persists `GITHUB_TOKEN` in `.git/config` until the `post` step unless `persist-credentials: false` is set (`v6.1.0` moves it to `$RUNNER_TEMP/git-credentials-<uuid>.config` via `includeIf`, still requiring `persist-credentials: false`), and `set-safe-directory: true` writes only to a temporary `.gitconfig` deleted in `finally`. Live `git 2.56.1` execution proved that `git merge-tree --write-tree` in a **non-bare** repo reads working-tree `.gitattributes` and **executes configured `merge.<name>.driver` commands**, whereas a **bare** repo or `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1` blocks all filters and merge drivers. `actions/runner` `$GITHUB_ENV` blocks only `NODE_OPTIONS` and `$GITHUB_PATH` has no validation.
- **Cross-job outputs, matrices, and artifacts across reusable workflows:** `jobs.<id>.outputs` is capped at 1 MB/job and 50 MB/run (UTF-16), silently drops secret-matching values, and collides non-deterministically across matrix jobs. Matrix jobs cap at 256 per matrix (`limits.md` documents no 1,000-job total run cap; `JobCountValidator` enforces a server-supplied `MaxJobLimit`). `actions/upload-artifact` and `download-artifact` share artifacts seamlessly between caller and called reusable workflows via shared `workflowRunBackendId` in `ACTIONS_RUNTIME_TOKEN`, but `overwrite: true` is a non-atomic delete-then-create race, `upload-artifact@v7` `archive: false` ignores `name` and uses file basename (colliding across matrix shards), and artifact names forbid `:` and `/`.

## Applicability

This report synthesizes GitHub Actions workflow-engine source (`actions/runner@7e211dc69c347b78fc398e630e74facb11a13235`), first-party action implementations (`actions/checkout` `v4.4.0` and `v6.1.0`; `actions/upload-artifact` `v4.6.2` and `v7.0.2`; `actions/download-artifact` `v4.3.0` and `v8.0.2`; `@actions/artifact@6.3.1`), `actions/runner-images@0e63d4f9d2c29043b4cf1d2f40d1812a7cde1369` (`ubuntu-24.04`), `github/docs@d7487f5debb5a5a2a6e65e6f9fa539266f5f8db6`, `github/rest-api-description@c9c95fe34ced05fe076001f5c55704742bc8e7f8`, `cli/cli@de06af2c2ea536d5722fda35dc2001565f9b9f64`, local `git 2.56.1` execution probes on Linux `x86_64`, and live HTTP probes against `github.com`, `api.github.com`, and `ghcr.io` observed on `2026-11-21`.

#### 1.2 Exact `permissions:` Inheritance, Cross-Org `id-token: write`, and Per-Job Downgrade

Basis: source (`actions/runner@7e211dc6`: `WorkflowTemplateConverter.cs:84-94, 114-196`, `PermissionsHelper.cs:21-78`, `ReferencedWorkflow.cs:128-135`, `Permissions.cs:38-76, 226-240`) + documentation (`github/docs@d7487f5d`: `workflow-syntax.md:364-378`, `reusing-workflow-configurations.md:88-111`, `oidc.md:584-588`) + derived

1. **Implicit-deny and base calculation (`workflow-syntax.md:364-366`, `github-token-available-permissions.md:25`):** Specifying any single scope in `permissions:` sets all unspecified scopes to `none`. Caller workflow top-level `permissions:` propagates to calling jobs that omit `jobs.<id>.permissions` (`WorkflowTemplateConverter.cs:84-94`).
2. **Ceiling construction when caller omits `permissions:` (`PermissionsHelper.cs:35, 58-76`):**
   ```csharp
   var effectiveMax = explicitMax ?? CreatePermissionsFromPolicy(
       context, permissionsPolicy, includeIdToken: isTrusted, ...);
   ```
   - Under default `LimitedRead` policy (default for newly created orgs/repos), `CreatePermissionsFromPolicy` grants **only `contents: read` and `packages: read`** (`PermissionsHelper.cs:67-72`, `includeIdToken: false`, `includeAttestations: false`). Requesting `packages: write`, `attestations: write`, `id-token: write`, `checks: write`, or `statuses: write` inside the called workflow fails parse-time validation (`"Error calling workflow '...'. The nested job '...' is requesting '...', but is only allowed '...'."`).
   - Under permissive `Write` policy (`PermissionsHelper.cs:73-74`), `includeIdToken` receives `isTrusted = ReferencedWorkflow.IsTrusted()` (`ReferencedWorkflow.cs:128-135`), which is `true` only within the same user, organization, or enterprise trust boundary.
   - **Cross-org `id-token: write` denial:** For any reusable workflow outside the caller's organization or enterprise, `isTrusted == false`, so `id-token: write` is **denied unless explicitly declared at the caller workflow or calling-job level** (confirmed verbatim in `oidc.md:586-587`).
3. **Monotonic downgrade + selective per-job elevation up to the caller ceiling (`WorkflowTemplateConverter.cs:156-195`):**
   - `explicitMaxPermissions` records the caller job's ceiling (`L123`).
   - If the called reusable workflow defines top-level `permissions:`, it is validated against `explicitMaxPermissions` and stored into `workflowJob.Permissions` (`L156-166`).
   - For each job inside the called workflow (`L176-195`):
     - If `embeddedJob.Permissions != null`, it is validated against **`explicitMaxPermissions`** (the **caller's** ceiling, `L186`—*not* the called workflow's top-level `permissions:`).
     - If `embeddedJob.Permissions == null`, it inherits `workflowJob.Permissions` (`L193`—the called workflow's top-level `permissions:` if set, else the caller's).
   - **Least-privilege pattern (derived):** The caller job declares the minimal union required by the workflow (e.g., `contents: read`, `packages: write`, `id-token: write`, plus `attestations: write` if using the Attestations API). The called reusable workflow declares top-level `permissions: { contents: read }`. Every untrusted build/test shard omits `permissions:` (inheriting `contents: read` only), while only the final trusted publish/attest job declares explicit write `permissions:` within the caller's ceiling.

#### 1.3 GHEC Org Ruleset Required Workflows Calling External Public Reusable Workflows

Basis: normative (`github/rest-api-description@c9c95fe3`: `descriptions/ghec/ghec.2026-03-10.json`) + documentation (`github/docs@d7487f5d`)

- **Ruleset schema (`repository-rule-workflows` & `repository-rule-params-workflow-file-reference`):** Org-level (`POST /orgs/{org}/rulesets`) and enterprise-level (`ghec`, `ghes >= 3.18`) rulesets take `parameters.do_not_enforce_on_create` and `parameters.workflows[]` items containing required `repository_id` (int) and `path` (string), plus optional `ref` (branch/tag) and `sha` (commit SHA pinning the ruleset workflow itself).
- **Ruleset workflows can invoke reusable workflows (`troubleshooting-rules.md:69`):** Verbatim: *"Ruleset workflows can't use the CodeQL actions, except `github/codeql-action/upload-sarif`. This also applies to CodeQL actions in a reusable workflow that the ruleset workflow calls."*
- **Cross-org public reusable workflows and `allowed_actions` policies:** Public reusable workflows are callable by public, internal, and private repositories (`reusing-workflow-configurations.md:31-49`), governed by org/enterprise `allowed_actions` (`"all"` | `"local_only"` | `"selected"`). Under `"selected"`, `selected_actions.patterns_allowed` supports up to **1,000 patterns** including reusable workflow syntax `OWNER/REPOSITORY/PATH/FILENAME@TAG-OR-SHA` (`allow-specific-actions-intro.md:12-25`). Under `sha_pinning_required: true`, actions must be SHA-pinned while reusable workflows may still reference tags unless restricted by patterns or a workflow dependency lockfile (`enforcing-policies-for-github-actions-in-your-enterprise.md:63`, `lockfile-allowed-actions-sha.md:4-7`). No documentation prohibits a GHEC ruleset workflow from calling an external public reusable workflow across org boundaries.
- **Ruleset workflow operational rules (`ruleset-workflow-event-triggers.md:1-9`, `available-rules-for-rulesets.md:48, 289-313`, `troubleshooting-rules.md:65, 91-120`):** Only `pull_request` (`opened`, `synchronize`, `reopened`), `pull_request_target` (`opened`, `synchronize`, `reopened`), and `merge_group` (`checks_requested`) are supported; all `branches`/`paths`/`types` filters are ignored; `concurrency.cancel-in-progress` is forbidden; events generated by `GITHUB_TOKEN` do not trigger ruleset workflows; `github.repository` resolves to the target consumer repository; and *"Require merge queue"* is repository-level only (unavailable in org-level rulesets).

### 2. Cross-Repo `workflow_call` `GITHUB_TOKEN` Scoping and GHCR Package Linking

Basis: documentation (`github/docs@d7487f5d`: `github_token.md:17-24`, `reusing-workflow-configurations.md:43, 120`, `compromised-runners.md:69`, `workflow-syntax.md:366`, `working-with-the-container-registry.md:91`, `configuring-a-packages-access-control-and-visibility.md:26-28, 111-145`, `public-forks-private-packages.md:1`) + derived

- **Repository scope:** When `consumer-org/consumer-repo` invokes an external reusable workflow in `core-org/core-repo`, `GITHUB_TOKEN` is a per-job GitHub App installation access token (expiring at job end or 24 hours max) scoped **exclusively to `consumer-org/consumer-repo`**—never `core-org/core-repo`. Actions inside the called workflow run as if defined in the caller repository.
- **Fork PR downgrade:** For `pull_request` events from forked repositories (when *"Send write tokens to workflows from pull requests"* is disabled), GitHub downgrades all write permissions on `GITHUB_TOKEN` to read-only and withholds repository secrets identically inside called reusable workflows (`workflow-syntax.md:366`, `pull_request_forked_repos_link.md:5`). `pull_request_target` runs from the base branch without downgrading `GITHUB_TOKEN`.
- **GHCR targeting and repository linking:**
  - `packages: write` inside the external called workflow authenticates as `consumer-org/consumer-repo` and targets `ghcr.io/<consumer-org>/*` (e.g., `ghcr.io/<consumer-org>/<consumer-repo>/ci-cache`).
  - First push via `GITHUB_TOKEN` automatically links the new GHCR package to `consumer-org/consumer-repo` with Actions `Admin` role (unless org *"Inherit access from source repository"* is disabled). Pre-existing packages pushed out-of-band without `LABEL org.opencontainers.image.source=https://github.com/<consumer-org>/<consumer-repo>` return HTTP `403` until `consumer-org/consumer-repo` is granted `Read`/`Write`/`Admin` under **Package Settings -> Manage Actions access**.
  - `core-org/core-repo` (external cross-org reusable workflow repository) never requires and cannot be granted Actions access to a private package in `consumer-org`.
- **Public repo + private GHCR package fork-leak warning (`public-forks-private-packages.md:1`):**
  > *"If you grant a public repository access to private packages, forks of the repository may be able to access the private packages."*
  Consequently, granting a public consumer repo access to a private GHCR cache package permits read-only cache pulls from public fork PRs (whose `packages: write` is downgraded to `read`), but **prohibits storing any confidential or secret material** in that package.

### 3. Action Resolution Inside External Reusable Workflows (`./` vs. `$/` vs. Remote Subpath vs. `docker://`)

Basis: source (`actions/runner@7e211dc6`: `PipelineConstants.cs:40-80`, `PipelineTemplateConverter.cs:601-656`, `ActionManager.cs:190-202, 319-351, 450-458, 585-594, 699-712, 855-868, 910-913, 1072-1417, 1553-1689`, `JobContext.cs:102-148`, `ContainerActionHandler.cs:193-258`, `DockerCommandManager.cs:194-262`) + documentation (`github/docs@d7487f5d`: `workflow-syntax.md:751-786`, `metadata-syntax.md:343-354`, `contexts.md:385-388, 442-466`, `allow-specific-actions-intro.md:6`, `reusable-workflow-calling-syntax.md:3, 7`) + derived

| Step `uses:` Inside `core-org/core-repo/.github/workflows/gate.yml@<sha>` | Resolution Target | Needs Checkout? | Safe After Untrusted PR Checkout? | Self-Ref SHA Cycle? | GHES Support? |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `uses: ./actions/helper` (`SelfAlias`) | `$GITHUB_WORKSPACE/actions/helper` (**caller's checkout**) | Yes | **NO — TCB ESCAPE** | No | Yes |
| `uses: $/actions/helper` (`SelfRepositoryAlias`, `runner >= v2.336.0`) | `core-org/core-repo/actions/helper@<job.workflow_sha>` (in `_actions/`) | **No** | **Yes** | **No** | **No (`unsupported`)** |
| `uses: core-org/core-repo/actions/helper@<sha>` | `core-org/core-repo/actions/helper@<sha>` (in `_actions/`) | **No** | **Yes** | **Yes** (lagged SHA or separate repo) | Yes |
| Inline `run:` step in `gate.yml` | Embedded directly in `gate.yml@<sha>` | **No** | **Yes** | **No** | **Yes** |
| `uses: docker://ghcr.io/...@sha256:...` | Docker container action via `ContainerActionHandler` | **No** | Breaks host sandbox isolation | **No** | Linux only |

1. **Why `./` is a TCB escape in steps (`ActionManager.cs:699-706, 910-913, 1413-1417, 1599-1602`):** Both `PrepareRepositoryActionAsync` and `GetDownloadInfoLookupKey` return `null` for `PipelineConstants.SelfAlias`, skipping backend action download. `LoadAction` resolves `./` directly against `executionContext.GetGitHubContext("workspace")`. Before checkout it throws `NotSupportedException` (`L912`); after checking out an untrusted consumer PR it executes **`$GITHUB_WORKSPACE/actions/helper/action.yml` from the untrusted PR**. *(Distinct from job-level `jobs.<id>.uses: ./.github/workflows/foo.yml`, which resolves to the same commit as the calling workflow file per `reusable-workflow-calling-syntax.md:3, 7`.)*
2. **New `$/` self-repository syntax (shipped July 2026, `actions/runner` PR `#4457` / `dde968bf57` / `v2.336.0+`, `github/docs` commit `6a8580f09b`):** When feature flag `actions_self_repository` (`Constants.cs:183`) is enabled, `ResolveSelfRepositoryReferences` (`ActionManager.cs:1553-1580`) rewrites `$/<path>` in-place to `RepositoryTypes.GitHub` with `Name = job.workflow_repository` and `Ref = job.workflow_sha` (or the enclosing action's repo/ref inside nested composite actions, `L319-351, 585-594, 855-868`), fails closed with `InvalidOperationException` if unset (`L707-712, 1604-1607`), extracts into `_actions/` outside `$GITHUB_WORKSPACE`, and is automatically allowed under `"selected"` action policies (`allow-specific-actions-intro.md:6`). Rejects `@ref` suffixes (`PipelineConstants.cs:61-80`). **Explicitly unsupported on GHES** (`workflow-syntax.md:757`, `contexts.md:385-388`).
3. **Remote action tarball mechanics (`ActionManager.cs:1072-1400, 1626-1689`):** `GetDownloadInfoAsync` resolves remote (and rewritten `$/`) actions through the runner launch/job backend using a runner-scoped installation token (`scoped-token-note.md:1`, 1-hour expiry) sent to `codeload` as `Bearer` or `Basic x-access-token`, bypassing the 60 req/hr unauthenticated `api.github.com` bucket even on public fork PRs. However, `DownloadRepositoryArchive` downloads the **entire repository tarball** for `NameWithOwner@Ref`, so large compiled binaries should not be committed into an action repository.
4. **Why `uses: docker://...` fails host-level sandboxing (`ContainerActionHandler.cs:193-258`, `DockerCommandManager.cs:194-262`):** `ContainerActionHandler` mounts `/var/run/docker.sock`, `_runner_file_commands`, and `$GITHUB_WORKSPACE` as `/github/workspace` and `$RUNNER_TEMP` as `/github/runner_temp`, passes `ACTIONS_RUNTIME_TOKEN` and `ACTIONS_ID_TOKEN_REQUEST_TOKEN`, and runs under default Docker seccomp/AppArmor without `--privileged` or unconfined profiles. This simultaneously (a) blocks outer `bwrap --unshare-all` inside the action container, (b) breaks host-path `-v` bind mounts when invoking sibling `docker run` via `/var/run/docker.sock`, and (c) runs as `uid=0` creating root-owned files in `$GITHUB_WORKSPACE`.

#### 4.2 Preinstalled `ubuntu-24.04` Tooling and Zero-Circularity Pinning

- **Preinstalled (`actions/runner-images@0e63d4f9`, `images/ubuntu/Ubuntu2404-Readme.md`):** `curl 8.5.0` (`L267`), `jq 1.7` (`L83, L284`), `tar 1.35` (`L318`), `zstd 1.5.7` (`L102`), `Git 2.56.1` (`L79`), `Git LFS 3.8.1` (`L80`), `GitHub CLI 2.104.0` (`L111`), `Docker 28.0.4` (`L76-77`), `Skopeo 1.13.3` (`L98`).
- **NOT preinstalled:** **`oras`**, **`cosign`**, **`crane`**, and **`bubblewrap` (`bwrap`)** (0 occurrences in `Ubuntu2404-Readme.md`). Consequently, bootstrapping a binary via `oras pull` introduces a circular tool-install dependency, whereas raw `curl`+`jq`+`sha256sum`+`tar` works with zero external installs on both `ubuntu-24.04` and minimal Docker-less `ubuntu-slim` runners.
- **Zero-circularity offline integrity verification:** GitHub Immutable Releases (`immutable-releases.md:14-43`, GA on `fpt`/`ghec`/`ghes >= 3.20`) prevent post-publish release asset mutation and expose `release.immutable` and `asset.digest` (`sha256:...`), **but** `gh release verify-asset` (`cli/cli@de06af2c`, `pkg/cmd/release/verify-asset/verify_asset.go:130-192`) always makes online `api.github.com` calls (`FetchRefSHA` + `AttClient.GetByDigest`) with no offline `--bundle` flag. Instead, a two-phase release pipeline—(1) build & publish static Linux binaries to GHCR (`@sha256:<manifest-digest>`) and/or Immutable Releases (`<asset-sha256>`), then (2) commit the immutable digest(s) into `gate.yml` at commit `<S>`—binds binary integrity cryptographically to the consumer-pinned workflow SHA `<S>` with zero circularity, zero mutable-tag trust, and zero `api.github.com` calls at runtime.
- **Cross-repo `GITHUB_TOKEN` REST note:** `GITHUB_TOKEN` receives `1,000 req/hr/repo` (`15,000` on GHEC; `primary-rate-limit-github-token-in-actions.md:1`), and first-party actions like `actions/setup-node@66f83c82` (`action.yml:18-20`, `official_builds.ts:229-234`) send `github.token` to read public repos on `api.github.com` to avoid the 60/hr unauthenticated IP cap; avoiding `api.github.com` altogether via Probe A or Probe C removes this dependency.

### 5. Checkout Hygiene, Host-Git Security (`git merge-tree`), and Runner File-Command Isolation

#### 5.1 `actions/checkout` (`v4.4.0` vs. `v6.1.0`) Source Audit

Basis: source (`actions/checkout@11d5960a` `v4.4.0` and `actions/checkout@d23441a4` `v6.1.0`)

1. **`persist-credentials` (default `true`, `action.yml:52-54`):** In `v4.4.0`, `git-source-provider.ts:140` writes base64 `x-access-token:<GITHUB_TOKEN>` into `<repo>/.git/config` (`http.<origin>/.extraheader`) and leaves it there until the `post` step (`main.ts:46`, `git-source-provider.ts:297-339`) unless `persist-credentials: false` is set (which removes auth immediately in `finally`, `L287-291`). In `v6.1.0`, `git-auth-helper.ts:326-425` moves persisted credentials out of `.git/config` into `$RUNNER_TEMP/git-credentials-<uuid>.config` via `includeIf.gitdir:`, which still leaves the token readable on the host/in container actions unless `persist-credentials: false` is set.
2. **`submodules: false` and `lfs: false` (defaults, `action.yml:83-94`):** Passes `--no-recurse-submodules` (`git-command-manager.ts:278`) and sets `GIT_LFS_SKIP_SMUDGE=1` (`L661-663`) **only for `actions/checkout`'s own child `git` processes**—subsequent `run:` steps do not inherit `GIT_LFS_SKIP_SMUDGE=1`.
3. **`clean: true` and `path` containment (`input-helper.ts:45-53`, `git-directory-helper.ts:91-124`):** `path` must resolve inside `$GITHUB_WORKSPACE`, and `clean: true` wipes existing files via `git clean -ffdx && git reset --hard HEAD`. Trusted engine binaries must live outside `$GITHUB_WORKSPACE` (e.g., `$RUNNER_TEMP/engine/<sha>/`, mode `0555`, invoked by absolute path).
4. **`set-safe-directory: true` doc-vs-source discrepancy (`git-source-provider.ts:46-63, 292`, `git-auth-helper.ts:196-202`):** Both `v4.4.0` and `v6.1.0` run `git config --global --add safe.directory` against a temporary copy of `~/.gitconfig` under `$RUNNER_TEMP/<uuid>/.gitconfig` and delete it in `finally`, so `safe.directory` is **not** persisted into `~/.gitconfig` for subsequent steps.
5. **`allow-unsafe-pr-checkout: false` (default in `v4.4.0`, `unsafe-pr-checkout-helper.ts:13-82`, `input-helper.ts:62-78, 189-200`):** Blocks checking out fork PR refs/SHAs on `pull_request_target` and `workflow_run` unless explicitly overridden, trimming only ASCII whitespace in `ref` to avoid Unicode whitespace bypasses.

#### 5.2 Host `git` Command Injection & `git merge-tree --write-tree` Execution Probes

Basis: execution (`git 2.56.1.750.gf70dc682cf-goog`, Linux `x86_64`, ephemeral `TemporaryDirectory`) + derived

| Probe | Command & Config Setup | Observed Result | Security Consequence |
| :--- | :--- | :--- | :--- |
| **1a / 1b** | `git checkout -f <pr_sha>` with `.gitattributes` + global `filter.evil.smudge`, without vs. with `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1` | `filter_fired=True` → `False` | Global/system filters (e.g., `git-lfs`) fire on untrusted `.gitattributes` unless config is cleared. |
| **2a / 2b** | `git diff <base> <pr>` vs. `git diff --raw --no-ext-diff --no-textconv <base> <pr>` with global `diff.evil.textconv` | `diff_fired=True` → `False` | Plumbing flags suppress external diff/textconv drivers. |
| **3a** | **`git merge-tree --write-tree <A> <B>` in NON-BARE repo** with worktree `.gitattributes` + global `merge.evil.driver` | `rc=0`, **`merge_driver=True`** | **Hazard:** `git merge-tree --write-tree` in a non-bare repo reads worktree `.gitattributes` and executes configured merge/filter drivers. |
| **3b** | **`git merge-tree --write-tree <A> <B>` in BARE repo** (even with `.gitattributes` committed on `HEAD` + global drivers) | `rc=1` (conflict), **`smudge=False, clean=False, merge_driver=False`** | Bare-repo object-store merge ignores worktree `.gitattributes` and executes zero drivers. |
| **3c** | `git merge-tree --write-tree <A> <B>` in non-bare repo with `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1` | `rc=1`, `smudge=False, clean=False, merge_driver=False` | Clearing global/system config blocks external drivers if local `.git/config` is unpoisoned. |
| **4a / 4b** | `git status` on repo with poisoned local `.git/config` (`core.fsmonitor`), with `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1` vs. adding `-c core.fsmonitor=false` | `fsmon_fired=True` → `False` | Global/system isolation does **not** neutralize a poisoned local `.git/config`; never run host `git` on a `.git` dir previously writable by untrusted code. |

**Hardened host-Git invocation invariant (derived):** Run trusted `git merge-tree`/`git diff`/`git ls-tree` in a clean bare object store (never exposed writable to untrusted sandboxes) with `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_LFS_SKIP_SMUDGE=1`, `GIT_TERMINAL_PROMPT=0`, and `-c core.hooksPath=/dev/null -c core.fsmonitor=false -c core.autocrlf=false -c diff.external= -c protocol.ext.allow=never`.

#### 5.3 Runner File-Command Isolation (`$GITHUB_ENV` & `$GITHUB_PATH`)

Basis: source (`actions/runner@7e211dc6`: `src/Runner.Worker/FileCommandManager.cs:127-219`)

- `SetEnvFileCommand._setEnvBlockList` (`L215-218`) blocks **only `"NODE_OPTIONS"`**—allowing writes to `$GITHUB_ENV` to inject `LD_PRELOAD`, `BASH_ENV`, `GIT_CONFIG_PARAMETERS`, `RUSTC_WRAPPER`, `HTTPS_PROXY`, etc. into subsequent steps.
- `AddPathFileCommand.ProcessCommand` (`L134-157`) prepends arbitrary directories to `PATH` with **zero validation**.
- Untrusted check sandboxes must never inherit `GITHUB_ENV`, `GITHUB_PATH`, `GITHUB_OUTPUT`, `GITHUB_STATE`, `GITHUB_STEP_SUMMARY`, `ACTIONS_RUNTIME_TOKEN`, `ACTIONS_ID_TOKEN_REQUEST_TOKEN`, or `GITHUB_TOKEN`, nor bind-mount `$RUNNER_TEMP` or `_runner_file_commands`.

### 6. Outputs, Matrix Caps, and Artifact Handoff Across Reusable Workflows

#### 6.1 `jobs.<id>.outputs`, `workflow_call.outputs`, and `strategy.matrix` Limits

Basis: documentation (`github/docs@d7487f5d`) + source (`actions/runner@7e211dc6`)

- **Output byte limits (`output-limitations.md:1`, `WorkflowTemplateConverter.cs:2075-2100`, `JobExtension.cs:803-838`):** `jobs.<id>.outputs` is limited to **1 MB per job** and **50 MB per workflow run** (approximated in UTF-16). `on.workflow_call.outputs` has no separate smaller documented cap (maps `jobs.<id>.outputs.<name>` using `github`, `inputs`, `vars`, `jobs` contexts). Any job output matching a registered secret is **silently dropped** (`JobExtension.cs:803-838`), and duplicate output keys across matrix jobs collide non-deterministically (`section-defining-outputs-for-jobs.md:44-81`, `reuse-workflows.md:245-246`).
- **Inputs & variables:** `on.workflow_call.inputs` accepts `string`, `boolean`, and `number` (`workflow-syntax.md:232`). For comparison: `GITHUB_STEP_SUMMARY` caps at 1 MiB/step (20 shown/job), `GITHUB_ARTIFACTS` at 1 MiB/step (500/job), and `vars` at 48 KB/var / 256 KB combined org+repo per run (`workflow-commands.md:935, 978-979`, `variables.md:125-136`).
- **Matrix & total job caps (`limits.md:31, 34, 49, 70-71`, `ParseOptions.cs:60-64`, `JobCountValidator.cs:26-34`):** A job matrix generates at most **256 jobs per workflow run** (enforced server-side, not in `MatrixBuilder.cs`). Contrary to common folklore, `limits.md` does **not** document a 1,000-job total cap per workflow run (`1,000` in `limits.md` is concurrent larger runners; check suites cap at 50,000 check runs); `JobCountValidator` enforces a server-supplied `MaxJobLimit` whose live github.com value is unpublished.

#### 6.2 `actions/upload-artifact` (`v4.6.2` vs. `v7.0.2`) & `actions/download-artifact` (`v4.3.0` vs. `v8.0.2`)

Basis: source (`actions/upload-artifact` `ea165f8d` / `cf430e03`; `actions/download-artifact` `d3f86a10` / `9000827c`; `@actions/artifact@6.3.1` `3e145bf7`) + documentation (`github/docs@d7487f5d`)

- **Seamless cross-job sharing between caller and called reusable workflows:** `@actions/artifact` (`util.ts:21-72`, `upload-artifact.ts:72-84`, `list-artifacts.ts:124-136`) extracts `workflowRunBackendId` from the JWT `scp` claim `Actions.Results:<workflowRunBackendId>:<workflowJobRunBackendId>` in `ACTIONS_RUNTIME_TOKEN`. Because caller and all called reusable-workflow jobs share one workflow run, artifacts uploaded inside a called workflow are directly downloadable by other called jobs or the caller workflow with default inputs (no `github-token` required).
- **Concurrency, naming, and version hazards:**
  - **Non-atomic `overwrite: true` race:** Both `v4` (`src/upload/upload-artifact.ts:11-23, 60-62`) and `v7.0.2` (`L68-70`) implement `overwrite: true` as a separate best-effort `deleteArtifactIfExists` before `CreateArtifact`. Matrix shards must use shard-unique artifact names.
  - **`v7.0.2` `archive: false` basename collision trap:** Passing `archive: false` (raw single-file upload without ZIP) causes `@actions/artifact` (`upload-artifact.ts:50-51`) to **ignore `name` and use the uploaded file's basename**, colliding across matrix shards unless the filenames themselves are shard-unique.
  - **`merge-multiple: true` (`download-artifact.ts:9, 185-205`):** Downloads up to 5 artifacts concurrently into one directory; relative file paths inside distinct artifacts must be unique to avoid non-deterministic overwrites.
  - **Illegal artifact name characters (`path-and-artifact-name-validation.ts:11-27`):** Rejects `"`, `:`, `<`, `>`, `|`, `*`, `?`, `\r`, `\n`, `\`, `/`; digests formatted as `sha256:<hex>` or `/`-delimited paths cannot be used as artifact names.
  - **Version deltas:** `v4` runs on `node20` (`@actions/artifact@2.3.2`); `v7.0.2`/`v8.0.2` require **`node24`** (`@actions/artifact@6.3.1`). `download-artifact@v8.0.2` adds `skip-decompress: true` and defaults to **`digest-mismatch: error`** (`download-artifact.ts:211-242`). Both `v4` and `v7` ship `actions/upload-artifact/merge`. Neither `v4+` nor `v7/v8` is supported on GHES (`unsupported`).
- **Count, retention, and billing (preserving upstream discrepancies):**
  - *Per-job count discrepancy:* `actions/upload-artifact` `README.md` (`v4` L66, 447; `v7.0.2` L458) and `github/docs` `workflow-commands.md:979` document **500 artifacts per job**, whereas `@actions/artifact@6.3.1` `README.md:52` retains stale text stating *"limit of 10 artifacts"*. Public REST listing (`github-token` supplied) caps pagination at `ACTIONS_ARTIFACT_MAX_ARTIFACT_COUNT = 1000` (`config.ts:103-105`).
  - *Retention (`about-artifact-log-retention.md:15-21`):* Min **1 day**, max **90 days** (public) or **400 days** (private/internal), bounded by repo/org/enterprise caps.
  - *Private-repo billing discrepancy (`github-actions.md:26-74`, `github-packages.md:47-61, 96-115`, `actions-included-quotas.md:3-7`):* Shared Packages+Artifacts private storage includes Free 500 MB, Team 2 GB, GHEC 50 GB, and **Pro 1 GB (`actions-included-quotas.md:4`) vs. 2 GB (`github-packages.md:54`)**, with `$0.25/GB-month` overage accrued hourly in GB-Hours (setting `retention-days: 1` for tiny manifests minimizes accrual).
