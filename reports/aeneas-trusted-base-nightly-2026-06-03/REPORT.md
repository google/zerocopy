# Aeneas trusted base at nightly-2026.06.03

## Summary

For a theorem proved over Lean generated by `AeneasVerif/aeneas@ac9f1bc5262a5e4ff1e24ca78617121382202727`, the trusted base depends on what conclusion is being claimed.

For a **Lean-level theorem**, the central logical trust boundary is Lean itself plus the theorem's admitted assumptions. Tactics, Aeneas's code generator, Charon, and most library implementation code need not be trusted merely because they produced the proof term: Lean checks the resulting declarations. At `leanprover/lean4@3dc1a088b6d2d8eafe25a7cd7ec7b58d731bd7cc`, however, axioms and `sorryAx` are explicit logical assumptions, `debug.skipKernelTC` can bypass ordinary kernel checking, and native-evaluation proof mechanisms intentionally extend trust to compiled execution. A theorem's transitive `#print axioms` result is therefore a necessary part of any claim that it is free of unexpected admissions.

For a **Rust-level theorem**, the trusted base is larger. Lean can check a theorem about the generated Lean program without checking that the program faithfully denotes the original Rust. Carrying that theorem back to Rust requires trusting or separately proving the source-to-target bridges: the selected Rust compiler semantics and compiler-internal state consumed by Charon; Charon's MIR-to-(U)LLBC translation and transformation passes; Aeneas's LLBC preprocessing, symbolic execution, pure translation, and Lean extraction; and the semantic adequacy of every builtin, standard-library, external, or opaque model on which the theorem relies. The Aeneas papers establish important language-level results, especially for LLBC and symbolic borrow checking, but they do not make the pinned Charon/Aeneas production implementation a proof-producing compiler.

The Lean environment adds a second kind of boundary. The pinned Aeneas library itself contains explicit assumptions and admissions. Examples at this exact revision include axiomatized models for `Pin`, atomics, `PanicInfo`, and `Formatter`, plus `sorry` in the `core::slice::Slice.get_unchecked` model and its `@[step]` specification. Aeneas can also emit `sorry` while recovering from extraction errors and emits axioms for unresolved opaque declarations. These facts do not make every theorem unsound; they mean trust is **dependency-sensitive**. An end result must establish which assumptions its theorem actually depends on, not merely that the Aeneas package imports files containing assumptions somewhere.

Accordingly, the practical trusted-base policy for Anneal should distinguish four layers:

1. **logical checker trust** — the Lean kernel/checking configuration and any proof mechanism that deliberately trusts native execution;
2. **theorem-specific assumptions** — the exact transitive axioms, `sorryAx`, unresolved opaque declarations, and model axioms used by the theorem;
3. **source-model correspondence** — Charon, Aeneas, their transformation semantics, and external/builtin model adequacy needed to interpret the Lean theorem as a theorem about Rust;
4. **tool and artifact identity** — exact compiler, Charon, Aeneas, Lean, model-library, generated-source, and proof-environment revisions needed to know which three boundaries above were actually exercised.

No fresh Charon, Aeneas, Lean, or Rust execution was performed. The report combines exact pinned source with existing exact-revision corpus results. It does not repeat the neighboring inventories of translation-correctness obligations, formal paper theorems, or semantic omissions.

The report concerns the ordinary functional Charon → Aeneas → Lean path selected by the current Anneal work. It uses “trusted base” in the operational sense: components or assumptions whose failure could make a claimed result false without the claimed verification boundary detecting that failure.

That definition is claim-relative. A buggy Aeneas tactic that emits an invalid proof term is normally caught by Lean and therefore need not be trusted for logical validity. The same Aeneas repository can nevertheless contain an axiom that a theorem depends on, in which case that axiom's proposition and intended meaning are trusted. Likewise, a bug in Charon cannot make Lean accept an invalid Lean theorem, but it can make a correct theorem about the wrong generated program and thus invalidate a Rust-level interpretation.

This report does not treat all imported source code as equally trusted. It distinguishes code that generates/checks proof artifacts from assumptions that enter the logic and from translators whose correctness is needed only for the source-level interpretation.

## Findings

### Lean checking and Rust-level correspondence are different trust claims

The generated Lean program is an ordinary Lean input. If Lean accepts a theorem without a kernel bypass, Lean has checked that theorem relative to the declarations and axioms in its environment. The kernel does not know that a translated definition came from Rust, Charon, or Aeneas, and it does not check that relationship.

This divides the end-to-end argument cleanly:

- **Lean theorem validity:** trust Lean's logical checker and every transitive logical assumption used by the theorem.
- **Rust theorem validity:** additionally justify that the Lean definitions and models denote the Rust behavior to which the theorem is being attributed.

A code generator does not automatically belong to the first category. If it prints malformed syntax, an ill-typed term, or an invalid proof term, ordinary Lean checking rejects the result. But it belongs to the second category unless there is an independent refinement proof that removes it from the source-to-target trusted base.

Basis: Lean **source** + pinned Aeneas **source** + **derived** composition.

### Charon and rustc are trusted for the Rust-to-LLBC bridge

At `AeneasVerif/charon@a535e914f74db4fd9e6be7048f4233270d8945c0`, `charon-driver` is a `rustc_driver` client. Its source says that it calls rustc with callbacks to compile a Rust crate to LLBC. The driver links compiler-internal `rustc_*` crates, changes MIR-related compiler options, and runs Charon translation from a rustc callback before later MIR analysis. The translation recursively converts rustc items and bodies into Charon's ULLBC representation; Charon then applies a substantial pass sequence, including normalization, resugaring, control-flow reconstruction from ULLBC to LLBC, simplification, partial monomorphization, and type checks before serialization.

Those implementation steps are not visible to Lean. If Charon translates a source construct incorrectly but still emits well-formed LLBC, downstream Aeneas and Lean can faithfully verify the wrong LLBC model. Therefore the exact rustc/compiler-internal semantics used by the driver, Charon's translation code, and the semantics of the transformations on which the claimed behavior depends are part of the Rust-level trusted base unless separately covered by a proof.

Charon's own type checks and fail-closed errors reduce implementation risk but do not turn the bridge into a proof-producing translation.

Basis: Charon **source** (`charon-driver`, translation, and transformation pipeline) + **derived** trust consequence.

### Aeneas is trusted for the LLBC-to-Lean correspondence

Aeneas does more than pretty-print LLBC. The pinned pipeline applies LLBC pre-passes, symbolically executes function bodies, translates symbolic states into a pure intermediate language, rewrites that pure program, and extracts Lean syntax. The generated proof-facing definitions are therefore the output of a semantic transformation pipeline.

The neighboring translation-correctness report establishes that Aeneas does not emit a per-program semantic-preservation certificate connecting each Rust/LLBC function to the generated Lean. It has useful validation machinery—Aeneas-preset checks, accumulated errors, optional interpreter invariants, and target checking—but those checks do not prove that every successful transformation preserves source semantics.

For a Rust-level theorem, the relevant Aeneas implementation and its internal semantic builtins therefore remain trusted unless a formal implementation-refinement result applies. For a theorem stated only about the generated Lean definitions, those translator components are provenance rather than logical trust.

Basis: pinned Aeneas **source** + existing exact-revision corpus evidence + **derived** trust classification.

### The formal Aeneas results strengthen the semantic foundation but do not erase implementation trust

The Aeneas literature gives more than an informal design argument. The 2022 work formalizes the ownership-centric LLBC semantics and functional translation; the 2024 work proves important relationships between a low-level heap/address model, LLBC concrete execution, symbolic execution, borrow checking, and the join operation used for loops.

The paper inventory preserved for this corpus also records the crucial implementation boundary. The 2022 work treats the generated Aeneas program as a trusted pure translation rather than emitting a refinement proof for each compiler run. The 2024 theorem chain concerns the formal languages and symbolic semantics; it does not mechanically certify the exact 2026 Charon and Aeneas implementations.

Thus the papers can justify parts of the semantic design while the production implementation remains a separate trusted bridge. “Formalized” should not be collapsed into “the executable translator is mechanically verified.”

Basis: Aeneas publication results preserved by the neighboring report + **derived** end-to-end composition.

### External models are theorem-relevant trust assumptions when a proof uses them

At the pinned revision, Aeneas maps external Rust definitions to Lean definitions through an explicit `rust_type`, `rust_fun`, `rust_const`, `rust_trait`, and `rust_trait_impl` registry. The registration metadata can change parameter projection, failure behavior, lifting into `Result`, mutable-region handling, variant/field naming, and opacity. A matched model can therefore determine the semantics seen by generated Lean even though the corresponding Rust body is not translated.

The registry verifies names and selected structural metadata; it does not prove that a model refines the Rust implementation. A theorem that uses such a model inherits whatever argument or assumption makes that model semantically adequate for the Rust-level claim.

This boundary is narrower than “trust all of Aeneas.Std.” A model that is not in the theorem's semantic dependency path cannot affect that theorem merely by existing in the imported package. Conversely, a small hand-written model can be critical even if all surrounding generated definitions are fully kernel-checked.

Basis: exact-revision external-model report grounded in pinned Aeneas **source** + **derived** dependency-sensitive trust classification.

### The pinned Aeneas Lean library contains explicit axioms

Several standard-library model files at `ac9f1bc5262a5e4ff1e24ca78617121382202727` contain Lean `axiom` declarations. Concrete examples include:

- `Aeneas/Std/Core/Pin.lean`: `core.pin.Pin` and `core.pin.helper.PinHelper`;
- `Aeneas/Std/Core/Panic.lean`: `core.panic.panic_info.PanicInfo`;
- `Aeneas/Std/Core/Atomic.lean`: `core.sync.atomic.AtomicBool` and `core.sync.atomic.AtomicU32`;
- `Aeneas/Std/Core/Fmt.lean`: `core.fmt.Formatter`.

These are logical assumptions at the Lean level. Lean checks that their types are well formed; it does not prove inhabitants or semantics for them.

The trust consequence is theorem-specific. Merely importing a file containing an axiom does not make every theorem depend on that axiom. Lean's transitive axiom collector follows declaration dependencies and reports an axiom when the theorem actually reaches it.

Basis: pinned Aeneas **source** + Lean **source**.

### The pinned Aeneas Lean library also contains `sorryAx` dependencies

The exact pinned `Aeneas.Std.Slice` source contains a model of `core::slice::Slice.get_unchecked` whose body is `sorry`. It also contains a `@[step]` theorem, `core.slice.Slice.get_unchecked_SliceIndexUsizeSlice_spec`, whose proof is `sorry`.

At Lean `v4.30.0-rc2`, ordinary `sorry` expands to the global axiom `sorryAx`. Any theorem whose transitive dependency closure reaches one of these declarations therefore depends on `sorryAx`, even though the source-level placeholder may be several modules away.

This gives a concrete reason not to use “Lean successfully compiled the Aeneas library” as a no-admissions test. Compilation accepts declarations containing `sorry` while normally warning. For a theorem intended to support a high-assurance result, the relevant check is its transitive axiom dependency set under an explicit allowlist policy.

Basis: pinned Aeneas **source** + Lean **source** + **derived** dependency consequence.

### Aeneas can emit `sorry` as error recovery, but a correct integration should fail closed

`src/extract/ExtractErrors.ml` chooses the text `sorry` for Lean when an extraction helper needs an admission after registering an error. Separately, `src/extract/ExtractBase.ml` has error-rendering paths that also produce Lean `sorry` text.

The same pinned executable records these translation errors in `Errors.error_list`; at top level, `Main.ml` treats a nonempty list as failure and exits with status 1 after translation. This is an important fail-closed property: partial diagnostic output can exist, but the process status records that the run was not a successful translation.

The trust boundary therefore includes the integration discipline. A consumer that ignores Aeneas's nonzero status and later proves a theorem over partially emitted Lean can convert translator error recovery into a logical `sorryAx` dependency. A consumer that requires successful translation and audits final theorem axioms has two independent ways to reject that path.

Basis: pinned Aeneas **source** + **derived** integration requirement.

### Unresolved opaque declarations can deliberately become axioms

The Aeneas extraction context records whether an opaque definition has been extracted; its source comment explains that extracting such a definition means generating an axiom. The pinned README recommends `-split-files` so missing external definitions can be separated into generated templates and user-maintained model files.

An opaque declaration is therefore not necessarily a translator bug. It can be an intentional assumption boundary. For a Rust-level theorem, that boundary must be closed by a justified model or exposed as an accepted assumption. Lean can prove consequences of the axiom without knowing whether it faithfully represents the external Rust behavior.

This is distinct from a translated opaque Lean definition. In Lean itself, an ordinary `.opaqueInfo` declaration has a checked body and is not automatically an axiom. The Aeneas term “opaque external definition” here describes a source/extraction case that may be rendered as a target axiom.

Basis: pinned Aeneas **source** + Lean trust report + **derived** terminology distinction.

### `#print axioms` is the right logical-admission audit, but it is not a source-correctness audit

Lean's transitive axiom collector recursively follows theorem/definition dependencies. It records declarations stored as axioms; a direct or indirect `sorry` appears as `sorryAx`. This makes `#print axioms` suitable for answering a precise question: “Which logical assumptions does this final theorem depend on?”

A clean or policy-approved axiom set does not answer four different questions:

- whether Charon represented the Rust source correctly;
- whether Aeneas implemented the intended LLBC-to-pure translation correctly;
- whether a concrete model matches the Rust operation it stands for;
- whether the theorem's specification is the property the user intended.

Those are semantic correspondence questions outside the kernel's declaration-dependency audit.

The two checks should therefore be composed, not substituted for each other: audit assumptions to establish target-level proof integrity, then separately justify the source-to-model bridge required by the claimed Rust interpretation.

Basis: Lean **source** + **derived** composition.

### Tactics and metaprograms are normally outside the logical TCB

Aeneas ships substantial Lean metaprogramming and tactics, including `step`, arithmetic automation, simplification support, and helper commands. A bug in such code can make a tactic fail, produce an inefficient proof, or attempt to produce an invalid proof term. Under ordinary Lean checking, an invalid proof term does not become a theorem merely because a tactic generated it.

Thus these metaprograms are not normally trusted for theorem validity in the same way as the kernel or axioms. Their output is checked.

There are explicit exceptions at the Lean platform level. A tactic or proof method that deliberately invokes a trust-expanding mechanism—such as native-evaluation proof infrastructure that adds an axiom after compiled execution—changes the trust story. The classification must follow the actual proof dependencies, not the fact that code happened to run during elaboration.

Basis: Lean **source** + existing WP/tactic report + **derived** trust classification.

### Lean's own trust boundary includes configuration and native-execution escape hatches

The selected Lean revision provides a strong checker boundary, but that boundary has explicit exceptions.

`debug.skipKernelTC` defaults to `false`. When enabled, declaration insertion can use a path that skips ordinary kernel checking; Lean's source warns that this compromises the normal soundness guarantee. A result that claims kernel checking must therefore bind the claim to a configuration where this option remains false.

Separately, native-evaluation proof infrastructure compiles and executes a Boolean computation and then adds a fresh axiom for the successful result. This means proofs using mechanisms such as `native_decide` or `bv_decide` extend trust beyond the kernel to the compiler/runtime path that produced that Boolean result. `#print axioms` can expose the resulting axiom dependency, but the kernel does not replay the native computation.

Basis: Lean `v4.30.0-rc2` **source**.

### Imported Lean dependencies are not automatically part of the logical TCB in the same way as axioms

The pinned Aeneas Lean package requires mathlib `v4.30.0-rc2`; its manifest fixes mathlib to commit `5450b53e5ddc75d46418fabb605edbf36bd0beb6` and fixes inherited packages to concrete revisions. The Aeneas root module imports its standard library and tactics.

For ordinary proof terms, Lean checks imported declarations according to its environment format and kernel rules. A large imported theorem library is therefore not semantically trusted merely because a tactic or proof uses one of its proved theorems: the relevant logical premises are the theorem definitions and any transitive axioms they use.

This does not make dependency identity irrelevant. Exact package revisions are needed for reproducibility and to know which declarations, axioms, tactics, and compiler hooks were present. Moreover, a theorem from an imported package can carry axioms, which the transitive axiom audit must surface.

Basis: pinned Aeneas package **source/manifest** + Lean **source** + **derived** distinction.

### Builtins implemented inside Aeneas are part of the source-model trust boundary

External Lean models are not the only modeled semantics. Aeneas also has internal LLBC/pure builtins that the interpreter and extractor handle specially. For example, the Lean extraction name map routes builtin array/slice operations, failure, result lifting, and related functions to Lean library operations rather than recovering all behavior from an ordinary translated Rust body.

For a Rust-level theorem, these internal builtin semantics need the same kind of justification as external models: the special case must denote the source operation strongly enough for the theorem. Their presence does not necessarily add a Lean axiom; they are trusted primarily as part of the source-to-model correspondence.

Basis: pinned Aeneas **source** + existing external-model report + **derived** trust classification.

### The minimum useful Anneal result record is a trust ledger, not one boolean

A single statement such as “Lean verified this” loses information needed to interpret the result. A durable Rust-level result should preserve enough information to recover at least:

- exact Rust/rustc, Charon, Aeneas, Aeneas-model-library, Lean, and relevant Lean dependency identities;
- hashes or identities of the LLBC and generated Lean artifacts actually proved;
- successful/fail-closed status for Charon and Aeneas;
- the source-item coverage mapping needed to know what Rust code the proof is about;
- the final theorem names and their transitive axiom dependency sets;
- the policy decision for each non-foundational axiom or `sorryAx`;
- whether any proof used a native-evaluation or kernel-bypass trust expansion;
- which external/internal models the source-level claim relies on and the justification for those models;
- the formal or engineering basis used to trust the Charon and Aeneas translation bridges.

This ledger does not itself prove the bridges. It prevents a later consumer from silently replacing a conditional target-level theorem with a stronger Rust-level claim.

Basis: **derived** from the trust boundaries above.

## Boundaries

- No fresh Charon, Aeneas, Lean, rustc, Lake, or proof-assistant execution was performed.
- This report does not claim that every explicit axiom or `sorry` in the Aeneas Lean package is reachable from every generated theorem. Trust is dependency-sensitive.
- The examples of Aeneas axioms and sorries are concrete witnesses, not an exhaustive count of all assumptions in the package.
- The report does not prescribe an Anneal axiom allowlist. Some assumptions may be intentional and acceptable for a particular result; the requirement here is to expose and classify them.
- `#print axioms` establishes the transitive global axiom dependency set as represented by Lean. It does not establish source-model fidelity, specification correctness, compiler correctness, or absence of every possible implementation bug in Lean itself.
- The report characterizes Lean's kernel/checking boundary from source; it does not prove the Lean kernel implementation correct.
- It does not repeat the exact Aeneas paper theorems, production translation-correctness obligations, or unsafe-Rust semantic-omissions inventory. Those are neighboring corpus subjects.
- The ordinary Aeneas functional path remains narrower than arbitrary unsafe/concurrent Rust; this report does not turn a trusted-base inventory into a statement that the model covers out-of-domain behavior.
- Charon's rustc-internal dependency means this report does not attempt to define a freestanding Rust operational semantics against which the exact compiler is proved correct.
- Aeneas can recover from some errors and emit partial/admitted material. This report establishes the fail-closed process-status and axiom-audit requirements; it does not enumerate every recovery site.
- Native-evaluation and kernel-bypass mechanisms are included because they change the claimed Lean trust boundary. The report does not inventory every compiler/debug option in Lean.
- Exact mathlib and inherited package revisions are provenance/reproducibility inputs. They become theorem-level trust inputs only through the declarations and assumptions the final theorem actually depends on.

## Revalidation

For another Anneal/Aeneas pin, revalidate in this order.

1. Resolve exact Rust/rustc, Charon, Aeneas, and Lean identities. Check that Aeneas still pins the Charon producer actually used and that its Lean toolchain still matches the checking environment.
2. Diff Charon's rustc callback/translation entry points and `transform/mod.rs`. Any new compiler phase, transformation, or serialization boundary can change the source-to-LLBC trusted bridge.
3. Diff Aeneas's LLBC preprocessing, symbolic-to-pure path, extractor, internal builtin mappings, error/admission machinery, and external-model registry.
