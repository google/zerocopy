# G15: pinned Rust-to-Lean navigation, and the producer-ID boundary

Observed 2026-09-29 on AArch64 macOS. This report adds executable **component navigation evidence** for #3730 G15 and #3731 I066/I149 using the already retained [R44 compatible-bundle full-pipeline fixture](../anneal-3730-compatible-bundle-upgrade-golden-2026-09-29/REPORT.md), the [R12 reorder fixture](../anneal-3730-cross-layer-comparator-mutants-2026-09-29/REPORT.md), and fresh same-leaf-name and loop-helper fixtures. The manifests pin bytes cryptographically, but their Charon→Aeneas→obligation links are **derived name/span matches and fixture-authored choices**, not a producer-authenticated cross-layer identity. The requested actual Anneal agent navigation and usability trial remains unrun.

## Hypothesis and exact subject

Hypothesis: a selected, immutable generation can support useful Rust→Lean and Lean→Rust navigation if every hop carries exact source/LLBC/generated/proof identities. Confirmation is correct forward and reverse lookup for a bounded fixture with stale artifacts rejected. Falsification is a wrong target under the selected hashes or a stale source/output accepted. An additional question is whether the pinned tools themselves emit the shared identity needed to treat the links as authoritative.

The subject is the June 3 R44 pair: Charon `0.1.210` executable SHA-256 `51bb6d23beab3f97a684c25162d3e402fc820c891b57b21d2ca781c1da211a8b`, Aeneas executable SHA-256 `f476001e1a8e8c5cb1d8a621a25716d8e15f0809c8a023c5349357acc0911d03`, and Lean 4.30.0-rc2 executable SHA-256 `b48bc5ab229bd8b320a224b87e20fc428dba6fa8a1c054bd4fa6def846e19997`. No tool was downloaded or installed. The R44 retained `june3-base` and `june3-changed` cases use the same crate and change `wrapping_add(1)` to `wrapping_add(2)`. [Manifest](support/manifest.json), SHA-256 `c897830c70cd75c9c1e036fd8ef4f12cb0732d8748eadde402e09f73bbed6c37`, records these pins, an SHA-256 of R44's result ledger, and SHA-256/size/path for every copied source, LLBC, generated Lean, compiled imported OLean, proof, and new goal-probe file. [Artifacts](support/artifacts) contain the exact copied bytes. This establishes integrity relative to the retained run, not an external signature or independent proof of translator correctness.

## What each producer actually exposed

Charon's LLBC `files[0].contents` contains the **entire exact Rust source** for `src/lib.rs`. Each local `fun_decl` has a `def_id`, fully qualified name, `file_id`, source span, and `source_text`; in these two cases the source text equals the byte slice of the pinned Rust file at that span. Aeneas's generated `Funs.lean` emits a doc comment beside each `def` with `bundle_golden::name`, `Source: 'src/lib.rs'`, and the same line/column span. These are actual producer-emitted fields, checked from the retained files.

However, the Aeneas Lean output does **not** carry the Charon `def_id`, a stable source-item key, a machine-readable declaration map, or a generated obligation ID in these files. The output comment's matching name/span is evidence of what this Aeneas run emitted, but joining it to the LLBC declaration is still a derived comparison. The `obl_*` proof names were manually written in R44; the Rust doc comments even say “Manually mapped obligation.” Neither Charon nor Aeneas emitted an authenticated Rust item→Lean obligation relation. No Anneal declaration/annotation ID was present.

## Executed navigation and goal observations

[The builder](support/probe.py) copied the two generations and ran a fresh `lean --json GoalProbe.lean` against their previously compiled, pinned imports. Each of three fixture-authored theorems calls `trace_state` before `rfl`. Lean exited 0 in both generations and emitted three actual goals; the prior R44 `Proof.lean` also exited 0 with the expected theorem/axiom output. [The navigation implementation](support/nav.py) selects a generation by case and verifies the current Rust and queried Lean file hashes before returning a link. It offers forward lookup from a Rust byte offset to the generated declaration and fixture obligation, and reverse lookup from generated definition lines, proof theorem lines, or trace positions to the Rust item.

| Rust item | Rust byte range `[start,end)` | Charon `def_id` | Aeneas `def` lines in `Funs.lean` | Fixture proof line | Fresh goal result at zero, base → changed |
| --- | --- | --- | --- | --- | --- |
| `bundle_golden::inc` | `[61,108)` | 0 | 21–23 | 2 | `.ok 1#u32` → `.ok 2#u32` |
| `bundle_golden::twice` | `[151,194)` | 1 | 27–30 | 4 | `.ok 2#u32` → `.ok 4#u32` |
| `bundle_golden::choose` | `[238,309)` | 2 | 34–37 | 6 | `.ok 3#u32` → `.ok 5#u32` |

All six item/generation combinations returned the expected forward target and three reverse target classes (generated declaration, fixture proof, fresh goal trace). The [result ledger](support/results.json) retains the full trace diagnostics, 24 navigation responses, three stale-control reasons, and both Lean command lines/outputs. The [offline checker](support/check.py) rechecks every file hash and producer field, exact Rust slice, Aeneas comment match, Lean proof/trace line, and navigation response.

The strongest negative control is an **equal-locator, changed-content** pair: base and changed source preserve the same item names, byte spans, Charon `def_id` values, Aeneas declaration lines, and proof line numbers, while Rust, LLBC, generated `Funs.lean`, and goal bytes change. A link based on name/span/line/ID alone would silently point across generations. The hash-gated navigator rejected (1) changed Rust under the base generation, (2) changed `Funs.lean` under the base generated-file identity, and (3) changed proof text under the base proof identity. These are integrity/freshness checks in the toy navigator, not source authority furnished by the producer tools.

A reorder demonstrates that Charon's local numeric ID is not a durable identity; the same-leaf case demonstrates why leaf-name joins are ambiguous. Neither creates the missing shared producer-issued key.

## Actual generated-helper fanout

A third [helper manifest](support/helper-manifest.json), SHA-256 `9c0655062bc22faf3d8670fe1e9d0b5fa13c70564f6544e202fc72f71e44394c`, records a newly executed `sum_to` loop fixture under the same cached Charon/Aeneas/Lean tuple. Charon's LLBC contains **one** local `loop_nav::sum_to` function declaration. Aeneas emits **three** top-level Lean definitions from it: `loop_nav.sum_to_loop.body`, `loop_nav.sum_to_loop`, and `loop_nav.sum_to`. All three Aeneas doc comments name `loop_nav::sum_to`; the first two cite the loop-body subspan and the wrapper cites the whole Rust function span. This is actual one-to-many output, with the relationship derived from Aeneas's producer-emitted name/span comments rather than a shared stable ID.

The fixture ran in base and changed forms, replacing `x.wrapping_add(i)` with `x.wrapping_add(1)` without moving the function or loop span. In both forms Charon/Aeneas succeeded and all three generated Lean modules compiled. Fresh Lean `#check` resolved all three declarations. Lean `#eval (loop_nav.sum_to 4#u32)` returned `.ok 6#u32` for base and `.ok 4#u32` for changed; separately compiled Rust oracles returned the same selected values. **A direct theorem attempt using `rfl` failed in both forms**, while `trace_state` showed the intended goal. Evaluation and a failed `rfl` attempt do not amount to proof acceptance or translation soundness. [The helper ledger](support/helper-results.json) preserves all 18 commands, including the two expected theorem failures, while [the artifacts](support/helper-artifacts) preserve Rust, LLBC, generated Lean, imported OLean, Lean checks, and the failed attempts.

The hash-gated navigator returned all three generated targets from the one Rust byte range and reverse-navigated each helper back to `sum_to`, for six helper links over two generations. It also returned from the selected Lean evaluation and goal trace to the same Rust item. Substituting changed Rust or changed `Funs.lean` under the base generation was rejected before navigation. The [helper checker](support/helper_check.py) verifies one local LLBC item, the three actual Lean declarations and source comments, the selected Rust/Lean evaluations, both failed proof attempts, all six helper links, and both stale rejections. The initial source/loop spans and declaration names remain the same after the edit; the source and generated bytes differ. This is a concrete reason to carry generation hashes even when a multi-target relation appears to have stable names and ranges.

## Design impact and residual

The executed fixture supports carrying a generation tuple of source, LLBC, generated file, imported-model, proof, and tool hashes into a navigation result. It also shows that a generated comment can serve as a useful *candidate* source hint only after both sides are pinned and checked. The one Rust item leads to several local navigation destinations—generated definition, manually written theorem, and fresh goal trace—but only the source/LLBC span and the Aeneas-emitted comment are producer observations; the cross-tool join and proof association remain manually derived.

For I149 to reach authenticated provenance, the selected Charon/Aeneas/Anneal pipeline must issue or preserve a stable typed item key and a producer-authored mapping from LLBC declaration identity to every generated Lean declaration/helper and every Anneal obligation. That map must be bound to the exact generation and carry edit authority separately from coarse origin hints. Source comments or line matches alone cannot supply those properties, even where a genuine one-to-three helper relation is visible. For I066/G15, run the typed navigation/query/edit/verify API on an actual Anneal workspace with subject selection, multiple agents or users, deletions, and measured agent task success. The local reorder, same-leaf, and loop-helper probes are narrow controls for that design. This report has no agent usability measurement and no actual Anneal service, so G15 remains unrun as requested; I066/I149 gain bounded partial component evidence.

From the repository root, with the retained R44 package and cached Lean/backend present:

```sh

python3 reports/anneal-3730-pinned-cross-layer-navigation-boundary-2026-09-29/support/extra_probe.py

```

The first probe replaces only this package's `support/artifacts`, `support/manifest.json`, and `support/results.json`. The extra probe replaces `support/extra-artifacts`, `support/extra-manifest.json`, and `support/extra-results.json`; the helper probe similarly owns its `support/helper-*` outputs. Run them in a copy to preserve this observation. The combined offline checker needs no tool execution and passed for 15 item links, six helper links, two helper evaluations, two expected failed `rfl` attempts, and seven stale controls. The helper run's observed manifest hash pins the retained bytes; replay may require repinning if raw LLBC metadata changes. These small cases do not infer correctness for macros, same-fully-qualified-name collisions, UTF-16 edit positions, or larger workspaces.
