# Rust-to-Lean Coordinate Projection, Provenance, and Edit Ownership Boundaries

## Summary

Across twelve controlled component probes and source audits, Rust-hosted Lean annotation projection requires separating four distinct relations that naive embedded-language adapters conflate:
1. **Tolerant lexical discovery versus compiler-backed subject attachment**: Line-based annotation scanners locate complete payload blocks even when surrounding Rust fails to parse (`rustc` exit `1`), while witholding projection for unclosed delimiters or malformed payload prefixes. Conversely, compiler-backed extraction through Charon (`0.1.210`) requires a compilable Rust target (`charon cargo` exits `101` on malformed syntax) and yields target-dependent declaration sets (`5` local functions in default `--lib`, `6` with `--features selected`, and `14` in `--tests`), shifting local `def_id` indices and spans across item movement and producing ambiguous candidates when markers are duplicated.
2. **Exact authored byte intervals versus compiler/translator provenance hints**: Charon assigns macro-generated items (`macro_rules!`) a span inside the macro definition with `source_text: null` and `generated_from_span: null`, which `rustfmt` shifts across lines (`35` to `47–49`). Aeneas (`nightly-2026.06.03`) emits Rust item names and source line/column comments above generated Lean definitions (including one-to-three loop helper fanout: `sum_to_loop.body`, `sum_to_loop`, and `sum_to`), but omits Charon `def_id` values or machine-authenticated declaration keys. Consequently, compiler spans and translator comments serve only as lexical navigation candidates or diagnostic blame anchors—never as writable Rust proof ranges.
3. **Explicit coordinate-unit conversion and inverse domains**: Direct `rustc --error-format=json`, Lean batch (`lean --json`), and Lean LSP (`lean --server`) disagree numerically after non-ASCII scalars, supplementary surrogate pairs, combining marks, tabs, and CRLF line endings. Across `2,982` enumerated scalar boundaries in `106` Unicode specimens (`support/projection-properties/`), `158` boundaries in doc-comment provenance (`support/projection-provenance/`), `28` boundaries in a compiler-backed CRLF bridge (`support/compiler-backed-coordinate-bridge/`), and a zero-length owned doc-comment insertion (`support/empty-owned-v2-bridge/`), round-trip inversion holds only on valid Unicode scalar boundaries inside authored segments; UTF-8 continuation bytes, UTF-16 surrogate interiors, CRLF interiors, stripped prefixes, and synthetic wrappers lie outside the inverse domain.
4. **Revision-fenced atomic edit ownership**: Multi-edit actions, Volar-style source-map transforms (`volarjs/volar.js`), one-to-many obligation projections, and many-to-one combined theorems require a compare-and-swap guard over host source digest, projected Lean digest, document version, and unique single-segment authored ownership. Edits touching synthetic headers, crossing segment gaps, targeting read-only generated models, diverging across duplicate projections of a single source block, or arriving after host-only shifts (`rustfmt`) or line deletions are rejected atomically without mutating host bytes.

## Findings

### Tolerant Annotation Discovery, Subject Attachment, and Multi-Compiler Stability

In `support/annotation-gap-probes/probe.py` (`support/annotation-gap-probes/raw-results.json`), an invented `//% begin <id>`, `//% ` payload, and `//% end` scanner separates text discovery from compiler attachment:
- **Discovery under Rust syntax failure**: Changing `pub fn f() -> u32 { 7 }` to `pub fn f( -> u32 { 7 }` caused `rustc 1.98.1` to exit `1`, while the line scanner still returned the complete annotation and both payload intervals. Conversely, an unclosed marker or replacing a `//% ` prefix with `// ` caused the scanner to retain the block as incomplete/malformed and withhold Lean projection.
- **Cross-version Rust compiler runtime (`support/rust-version-runtime/`)**: `support/rust-version-runtime/run_probe.py` replayed the exact `baseline` (`74e1732c32004df0e0c6c9af6626f571235480fa47128a7e0db94a4a979d0aa5`) and `rust_incomplete` (`41010e6f5c2229314abc201dc5f61eca18b4f66003ffcb11125a54b2b445ae02`) fixtures across `rustc 1.98.0-nightly` (`2026-05-31`), `rustc 1.98.1`, and `rustc 1.100.0-nightly` (`2026-09-17`). All three compilers exited `0` on baseline and exited `1` on the malformed input with identical diagnostic text (`this file contains an unclosed delimiter` pointing to line 1 `(` and line 5 `//% end`) and no stale `.rmeta` emission (`support/rust-version-runtime/evidence.json`).
- **Unsaved buffer regeneration**: Changing `exact helper` in an unsaved host buffer to `  exact helper -- retained spacing` and then modifying the Rust function return value from `7` to `9` preserved the exact authored spacing and comment during projection regeneration because regeneration consumed the authoritative host buffer rather than prior generated Lean.
- **Fragment order and namespace visibility**: Direct Lean `4.30.0-rc2` compilation accepted `helper` followed by `proof`, rejected reversed order with `Unknown identifier helper`, rejected duplicate `helper` declarations in the same namespace with `` `helper` has already been declared ``, and accepted one `helper` in each of namespaces `A` and `B`.

In `support/annotation-subject-boundary-matrix/probe.py` (`support/annotation-subject-boundary-matrix/raw-results.json`, `support/annotation-subject-boundary-matrix/summary.json`, `support/annotation-subject-boundary-matrix/attachment-manifest.json`), a crate with five `//%` blocks, a shared Lean helper, namespaced claims, a `build.rs` script, and `include_str!("lib.rs")` was tested through `rustc`/`cargo` (`nightly`), Charon `0.1.210`, and Lean `4.30.0-rc2`:

|---|---|---|---|
| Baseline | Five complete blocks: module helper; two namespaced claims; selected and test claims | `rustc` and projected Lean exit `0` | Charon default `--lib` has `claim-a` and `claim-b` (`5` local functions); `--lib --features selected` has `6`; `--tests` has `14`. |
| Malformed Rust signature | Same five complete text blocks | `rustc` exits `1` with unclosed delimiter | Charon Cargo extraction exits `101` with no LLBC. Text discovery grants no valid compiled attachment. |
| Unfinished trailing marker | Five complete blocks plus `orphan` marked incomplete; `orphan` excluded from projection | `rustc` exits `0` | No Charon run for this variant; it tests scanner recovery only. |
| Moved item | `claim-a` block and `alpha` moved from `left` to `relocated`, line `17` to `49`, with matching Lean namespace update | `rustc` and projected Lean exit `0` | Charon name changes from `left::alpha` to `relocated::alpha`, local ID `4` to `5`. |

This proves that comment-only proof edits are not universally invisible to Rust compilation when `include_str!` or `build.rs` (`rerun-if-changed=src/lib.rs`) inspects source bytes, and that Charon local numeric IDs are not stable across item movement.

### Macro Spans, One-to-Many/Many-to-One Provenance, and Atomic Patch Guards

In `support/projection-provenance/` and `support/projection-macro-doccomment-patch-matrix/`, Charon extraction of `macro_rules!`-generated functions (`subject_identity_probe::generated` at line `35`, cols `8–40`, shifted by `rustfmt 1.9.0` to lines `47:8–49:9`; `macro_generated` at line `20`, col `8`) always produced `source_text: null` and `generated_from_span: null`. Running `rustfmt` on `support/projection-macro-doccomment-patch-matrix/fixture.rs` changed host Rust bytes (`8000c44b...` → `e2c8ae14...`) while leaving projected Lean text byte-identical (`88f95120...`).

When one Rust doc-comment block feeds two obligations (`left` and `right`) and two blocks assemble into one `combined` theorem (`support/projection-macro-doccomment-patch-matrix/`), an 80-step duplicate-aware indexed update stream matched full regeneration on every step, with process-local median latency `9.625 µs` (total `0.81 ms`) for indexed updates versus `8.2705 µs` (total `0.70 ms`) for full regeneration—showing that on small fixtures full regeneration is both simpler and faster.

| Patch / Origin Control | Observed Outcome |
| --- | --- |
| Two-range authored replacement (`trivial` → `simp`) under matching host/projection/version hashes | Accepted atomically; regenerated Lean (`left`, `right`, `combined`) exits `0` in fresh batch check |
| Host-only prefix edit or `rustfmt` reflow with unchanged projected Lean; or `A→B→A` source bytes at newer revision | Rejected as `stale-generation` / `stale-source-or-projection` |
| Mixed-revision multi-edit action | Rejected as `mixed-generation` |
| Distinct replacements to two projected copies of one authored doc-comment block | Rejected as `conflicting-duplicate-origin` |
| Edit inside synthetic header/wrapper or spanning across a synthetic gap between segments | Rejected as `no-exact-single-origin` / `no-single-authored-origin` |
| Edit targeting read-only Aeneas `Funs.lean` URI, snippet placeholder, or file rename resource operation | Rejected as `read-only-or-external-uri`, `snippet-unsupported`, and `resource-operation-unsupported` |
| Owning Rust doc-comment line deleted `0.14 ms` after live version-1 request (`support/source-owned-projection-diagnostic-matrix/`) | Server settles at `2,754 ms` with version-1 diagnostics; applying version-1 patch to version-2 source (`4ee11307...` → `2e27c2c8...`) rejected as `stale-source-or-projection` |

### Upstream Editor and Projection Precedents (`Lean`, `rust-analyzer`, `Volar`)

Source inspection and modeling in `support/upstream-api-projection-precedents/` (`upstream-source-ledger.json`, `projection_probe.py`, `projection-results.json`) compared pinned Lean 4 (`src/Lean/Server/ProtocolOverview.lean`, `src/Lean/Data/Lsp/Extra.lean`), `rust-analyzer` (`crates/ide/src/lib.rs`), and Volar (`packages/source-map/lib/sourceMap.ts`, `packages/language-service/lib/utils/featureWorkers.ts`, `packages/language-service/lib/utils/transform.ts`):

## Boundaries

- **Not examined**: Production Anneal annotation syntax, Rust procedural-macro expansion provenance (`proc_macro` span hygiene), `cfg_attr` / `include!`-generated annotations, negotiated UTF-8/UTF-32 LSP position encodings, Lean InfoView widget RPC rewiring, or multi-file `WorkspaceEdit` transactions in a live editor client.
- **Unknown**: Whether a future Anneal projection engine will adopt per-annotation, per-item, or per-crate virtual documents, and whether upstream Aeneas `translation.json` facilities in post-`2026.06.03` releases emit stable cross-layer declaration IDs.
- **Known not to apply**: Charon item spans for `macro_rules!` definitions, Aeneas source-location comments in `Funs.lean`, and synthetic diagnostic blame anchors do not establish editable Rust proof ranges; the exact-copy linear offset bridge applies only within a single contiguous authored segment and never across stripped line prefixes, CRLF interiors, or synthetic headers.
