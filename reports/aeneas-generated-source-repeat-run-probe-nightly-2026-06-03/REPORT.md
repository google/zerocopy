# Aeneas generated-source determinism

## Summary

Ten Aeneas Lean-generation runs on identical serialized LLBC emitted byte-identical source. Logs and filesystem mtimes varied. The result is limited to one input, binary, backend, and flag set.

## Applicability

The executed artifact is the macOS arm64 Aeneas release archive pinned by SHA-256 and associated source revision. Input is the fixed three-function LLBC file, with the Lean backend and `-no-progress-bar`. Related corpus reports: [aeneas-generated-source-determinism-nightly-2026-06-03](../aeneas-generated-source-determinism-nightly-2026-06-03/REPORT.md).

## Findings


Scope: Nix-independent, local Aeneas translation of one fixed LLBC input to Lean. This is a byte-stability probe, not a proof of translation correctness or Rust/Lean correspondence. Under Anneal's [principles](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/PRINCIPLES.md) and [design contract](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/DESIGN.md), matching generated source cannot establish UB freedom, complete coverage, or a valid verification result. The `v1/` implementation is historical evidence rather than current design authority.

### Direct observations

The input was the existing `../charon-llbc-output-goldens-and-revision-diffs-2026-09-27/support/translation-goldens/probe.llbc`, without editing its Rust source or LLBC. It is 19,827 bytes, SHA-256 `b98023ca3d222796ed4f08e9331e8ffa750c8971daeb786fea37a888b8c8d098`, with `has_errors: false`, six `ordered_decls`, and three local functions: `checked_add`, `choose`, and `bump`. The fixture's `item_names` ordering has varied across earlier Charon runs; this probe held the *serialized LLBC bytes* fixed, so it isolates Aeneas from Charon's serialization variability.

All commands ran from the repository root on macOS `aarch64-apple-darwin`, with `$CHECKOUT_LOCAL_TOOLS/env.sh` sourced. The invoked `aeneas` symlink points to `the Aeneas release archive at the pinned hash/aeneas`. Its SHA-256 is `f476001e1a8e8c5cb1d8a621a25716d8e15f0809c8a023c5349357acc0911d03` (28,061,048 bytes), and `aeneas -version` prints `unknown`. The local downloaded `aeneas-macos-aarch64.tar.gz` is 61,499,346 bytes, SHA-256 `76f78b645e338ec7e89329f0ad22792997f42bd9b5eb14643ac32ade224eeb61`; its embedded `aeneas` member has the same size and SHA-256 as the invoked binary. The archive's SRI hash, `sha256-dveLZF4zjsfokynwrSJ5KZf0K9m16xRkOsMq3iJO62E=`, matches the `aarch64-darwin` Aeneas hash in `anneal/flake.nix`, where the release tag is `nightly-2026.06.03`. The local Aeneas source checkout is `ac9f1bc5262a5e4ff1e24ca78617121382202727`, tagged `nightly-2026.06.03`; the tag is supporting provenance, while the archive and binary hashes identify the executed artifact. No Nix command was run.

The reproducible invocation is:

```sh
# Set PATH to the pinned local binaries identified above.
python3 support/aeneas-determinism/probe.py
```

The script runs the following child command five times against the same destination, then once each against five new destinations. It saves each generated file and stdout/stderr under `runs/<label>/`, with hashes, file sizes, modification times, command arguments, exit codes, and clock readings in `manifest.json`. It uses a 20-second per-run timeout and runs one Aeneas process at a time. Because the script requires a new `runs/` directory, rerun it in a fresh copy of the scratch directory or remove only this probe's `runs/` and destination directories first.

```sh
aeneas -backend lean \
  -dest support/aeneas-determinism/same-dest \
  -no-progress-bar \
  ../charon-llbc-output-goldens-and-revision-diffs-2026-09-27/support/translation-goldens/probe.llbc
# For fresh-1 through fresh-5, replace same-dest with fresh-dest-N.
```

All ten processes exited 0 and emitted exactly one file named `Probe.lean`; stderr was empty. Every saved copy is byte-for-byte equal, 1,219 bytes, SHA-256 `767acaeb0288a57cfdabdb1c276cbf0f7d9a85a0558f367601f5082c60349bca`. The five same-destination writes and five fresh-destination writes therefore showed **no generated-source byte difference** for this input, binary, backend, and flag set. The three function declarations stayed in `checked_add`, `choose`, `bump` order. The generated file contains no destination path or date-like timestamp. It contains the source path from LLBC in three comments (`../charon-llbc-output-goldens-and-revision-diffs-2026-09-27/support/translation-goldens/probe.rs`), which stayed fixed because the LLBC was fixed.

| Surface | Same destination, five runs | Fresh destinations, five runs | Classification |
| --- | --- | --- | --- |
| Generated path and file inventory | `same-dest/Probe.lean` each time | `fresh-dest-N/Probe.lean` | Directory path differs as requested; one output file per run. Destination is absent from generated bytes. |
| Generated contents and declaration order | Identical bytes and hash | Identical to same-destination bytes and hash | No observed Aeneas source or declaration-order drift. One-file output does not exercise multi-file enumeration order. |
| File metadata | `mtime_ns` changed on each overwrite | Distinct modification times | Filesystem timestamps changed; no timestamp was embedded in Lean. |
| stdout/stderr | stdout hashes differed because the printed execution seconds changed; stderr empty | stdout additionally printed each destination path; stderr empty | Diagnostic/log variability, outside generated source. |

For example, the first same-destination stdout reports `Generated: .../same-dest/Probe.lean` and `Total execution time: 0.143051 seconds`; the second reports the same path and `0.143871 seconds`. The first fresh-destination log reports `.../fresh-dest-1/Probe.lean` and `0.152865 seconds`. Comparing full logs or filesystem metadata as a source golden would therefore create false differences. The stored `manifest.json` and copies in the scratch directory preserve the exact run evidence.

### Proposed bounded follow-up probe

Repeat the same ten-run comparison separately for `-sequential` and `-split-files` on the fixed LLBC, using unique destination roots per configuration and the same 20-second limit. `-sequential` addresses Aeneas's execution scheduling; `-split-files` tests multi-file names, contents, and inventory ordering. Compare runs **within** each flag configuration; flag-induced output changes across configurations are expected and require their own goldens. `-namespace probe` and `-subdir` can be added as separate two-run cases to test name and import-path handling. Record exact flags, binary/input hashes, exit codes, diagnostics, output inventory, and per-file hashes. If a flag rejects this fixture, record that as a tool result rather than a determinism pass. This plan has not been run here.

For input-order sensitivity, make scratch *copies* of the fixed LLBC and change only JSON object-key order and schema-confirmed map-as-list entry order (for example, `translated.item_names` keyed by ID). Assert a structural equality check after those permitted reorderings and keep the original bytes. Feed each copy through the same fixed Aeneas command and compare generated output. Do not reorder `ordered_decls`, branch arms, statements, or other arrays whose order may carry meaning. To test declaration-order changes, create a separate copy of the tiny Rust source with independent function declarations permuted, regenerate LLBC with the pinned Charon command, and review the resulting item identities and source spans before interpreting an Aeneas diff. None of these input-order variants was run in this report.

### Interpretation and limit

For this one small Lean backend case, generated source bytes were stable across ten runs and destination changes; log times and filesystem times were not. The finding does not cover other backends, flags, input ordering, larger crates, concurrency, source relocation, source/model correctness, or Lean typechecking. A source golden should pin the LLBC and binary identity, compare generated bytes and file inventories, and report dynamic logs separately. Any future normalization of source paths or declaration order needs schema-aware review; silently dropping differences could hide a coverage change.

**Setup/prompt tweak recommendation:** no local-tool setup change is needed. A follow-up prompt should authorize the bounded `-sequential`/`-split-files` and schema-checked LLBC ordering matrix above, with explicit per-run time and output-size limits, before treating generated-source determinism as a general property.

## Boundaries

No alternate flags, input-order changes, multi-file outputs, other backend, concurrency, Lean compilation, or larger crate was tested. The binary reports its version as `unknown`; archive and executable hashes provide identity.
