# Rust Aggregate, Dynamically Sized Type, and Target Layout Guarantees

*Authored by an AI agent acting on joshlf's behalf.*

## Summary

Rust's memory-layout contract separates **normative language representation guarantees** from **compiler-internal and target-specific layout computations**:

1. **Aggregate Representation Guarantees (`repr(Rust)`, `repr(C)`, Primitive Enums, `packed`, `align`, `transparent`):**
   - Default `repr(Rust)` guarantees only that every field offset is divisible by that field's alignment, the aggregate alignment is at least the maximum field alignment, and non-zero-sized struct fields do not overlap in some compilation-chosen order. Source declaration order is not guaranteed, and zero-sized fields may share addresses with other fields.
   - `#[repr(C)]` fixes declaration-order struct layout with deterministic inter-field alignment padding and tail padding rounded to the aggregate alignment. `#[repr(C)]` unions place every field at byte offset zero (whereas default `repr(Rust)` unions do not guarantee offset zero) with size equal to the maximum field size rounded up to the maximum field alignment. Fieldless `#[repr(C)]` enums match the target C enum size and alignment while retaining strict Rust discriminant validity. Fieldful `#[repr(C)]` enums lay out as a `repr(C)` struct of `(tag, payload_union)`, whereas primitive representations (`#[repr(u8)]`, `#[repr(i32)]`) lay out as a `repr(C)` union of `repr(C)` variant structs each starting with the primitive tag, and `#[repr(C, u8)]` keeps the top-level `(tag, payload_union)` shape with a fixed `u8` tag.
   - `#[repr(packed(N))]` lowers field placement alignment to $\min(N, \text{field\_align})$ without altering the field type's own alignment; forming an ordinary reference (`&T` or `&mut T`) to a misaligned packed field is immediate undefined behavior (`&raw const`/`&raw mut` with `read_unaligned`/`write_unaligned` must be used instead). `#[repr(align(N))]` raises aggregate alignment to $\max(N, \text{natural\_align})$ without fixing field order, cannot be combined with `packed` on the same type, and cannot be transitively contained inside a `packed` type.
   - `#[repr(transparent)]` requires at most one field that is not simultaneously zero-sized and alignment-one (plus any number of size-zero, alignment-one fields) and delegates both memory layout and calling-convention ABI to that single field (or `()` if none exists).
2. **Type-Level vs. Value-Level Geometry (`size_of`, `align_of`, `size_of_val`, `align_of_val`) and Dynamically Sized Types (DSTs):**
   - `size_of::<T>()` reports array element stride in bytes (including trailing alignment padding), and `align_of::<T>()` reports the ABI-required minimum alignment (always a power of two $\ge 1$, with `size_of::<T>() % align_of::<T>() == 0`). Zero-sized types have `size_of::<T>() == 0` while retaining their alignment (`align_of::<[u16; 0]>() == 2`).
   - Slice values `[T]` of runtime length $n$ have dynamic size $n \times \text{size\_of}::<T>()$, alignment $\text{align\_of}::<T>()$, and element $i$ at byte offset $i \times \text{size\_of}::<T>()$; `str` has the layout of `[u8]` plus the UTF-8 validity invariant. Trait objects `dyn Trait` have the size and alignment of their erased concrete value, exposed via `DynMetadata::size_of` and `align_of`.
   - A struct whose final field is a DST inherits the final field's pointer metadata (`Pointee::Metadata`), but `size_of_val` and `size_of_val_raw` measure the **entire outer value** (statically sized prefix + padding + dynamic tail), whereas `DynMetadata::size_of` reports only the trait-object tail's concrete size. Safe `size_of_val(&x)` / `align_of_val(&x)` require a valid reference `&T` at entry; raw queries (`size_of_val_raw`, `align_of_val_raw`) require initialized slice length or valid unsizing vtable metadata and a total value size fitting in `isize::MAX`.
3. **Compiler Layout Internals (`rustc_abi::LayoutData`) and Multi-Version / Multi-Target Observations:**
   - Inside `rustc`, `LayoutData` computes `FieldsShape` (with source-order offsets and memory-order permutations), `Variants` (`Single`, `Empty`, `Multiple` with `TagEncoding::Direct` or `TagEncoding::Niche`), `BackendRepr` (`Scalar`, `ScalarPair`, `SimdVector`, `ScalableVector`, `Memory { sized }`), `largest_niche`, `uninhabited`, ABI/preferred `Align`, and static `Size`. These are revision- and target-specific compiler facts, not portable language guarantees for `repr(Rust)` types, and `BackendRepr` alone does not determine full function-call `FnAbi` / `PassMode` classification.
   - Across `nightly` (`1.98.0-nightly`) and `nightly` (`1.101.0-nightly`) on `aarch64-apple-darwin`, all 12 runtime geometry queries (including a field-reordered `repr(Rust)` struct with offsets `a=10, b=0, c=8` vs. `repr(C)` `0, 8, 16`) and 97 of 98 `-Zprint-type-sizes` lines were byte-identical.
   - Across native little-endian `aarch64-unknown-linux-gnu` and emulated big-endian `s390x-unknown-linux-gnu` (`qemu-s390x` `7.2.22`) under Rust `1.89.0` (`29483883eed69d5fb4db01964cdf2af4d86e9cb2`), all 78 finite checks passed: native scalar byte sequences reversed with endianness while `repr(C)` record geometry, array-to-slice and DST-tail coercions, `Option` niche sizes, trait-object dynamic dispatch, checked/wrapping integer arithmetic, floating-point bit round-trips, readiness-mask checks, and valid wide-union copies agreed across both architectures.

## Findings

### 1. Normative Aggregate Representation Rules (`repr(Rust)`, `repr(C)`, Enums, Modifiers, `transparent`)

Basis: normative specification + derived unsafe-code consequences (`support/rust-aggregate-layout/layout-matrix.json`, `support/rust-aggregate-layout/source-map.json`)

1. **Minimal `repr(Rust)` Guarantees and ZST Address Sharing:**
   - Omitting a representation attribute or writing `#[repr(Rust)]` guarantees only: (a) every field offset is divisible by that field's alignment, (b) aggregate alignment is at least the maximum alignment of its fields, and (c) struct fields do not overlap when considered in some unspecified ordering.
   - Zero-sized fields (`size_of::<F>() == 0`) may share the exact same memory address as other zero-sized or non-zero-sized fields in the struct. Unsafe code cannot use field address distinctness to distinguish logical fields when zero-sized types are present, nor infer source-declaration order from a single compiler observation.
2. **Non-Recursive Nominal Scope of Representation Attributes:**
   - Representation attributes apply only to the outer nominal item, not recursively to nested field types. A `#[repr(C)]` struct containing a default `repr(Rust)` field places that field at its `repr(C)` offset according to the inner type's size and alignment, but the inner struct's internal layout remains unspecified `repr(Rust)`.
   - Representation kind is independent of generic type parameters (`Foo<Bar>` and `Foo<Baz>` share the same representation kind, though their instantiated field sizes and alignments differ).
3. **`#[repr(C)]` Structs and Unions vs. Default Unions:**
   - **`#[repr(C)]` Struct Algorithm:** Start at `offset = 0`; for each field in declaration order, advance `offset` to the next multiple of `align_of::<Field>()`, place the field at `[offset, offset + size_of::<Field>())`, and advance `offset` by `size_of::<Field>()`. Set struct alignment to $\max_i \text{align\_of}::<\text{Field}_i>($ (adjusted by any `align(N)`/`packed(N)` modifier) and round total struct size up to the next multiple of struct alignment (creating trailing padding when needed). In Rust, a fieldless `#[repr(C)]` struct has size 0 and alignment 1 (unlike standard C/C++).
   - **`#[repr(C)]` Unions vs. Default Unions:** Under `#[repr(C)]`, every union field is guaranteed to start at byte offset `0`, union alignment is $\max_i \text{align\_of}::<\text{Field}_i>()$, and union size is $\max_i \text{size\_of}::<\text{Field}_i>($ rounded up to union alignment. Under default `repr(Rust)`, union fields share storage but the Reference explicitly permits **non-zero field offsets** (`&raw const u.field` is not guaranteed to equal the union base address without `#[repr(C)]`).
   - **No Active-Field Tag:** Rust unions have no runtime or abstract-machine active-field tag. Writing a union field is safe (because union fields cannot have implicit drop glue unless wrapped in `ManuallyDrop<T>`), while reading a union field is `unsafe` and reinterprets the stored bytes as the read field's type (causing immediate UB if the bytes are not a valid value of that type).
4. **Enum Representations (`#[repr(C)]`, `#[repr(Int)]`, `#[repr(C, Int)]`):**
   - **Fieldless Enums:** Under `#[repr(C)]`, size and alignment match the target platform's default C `enum` ABI, whereas under `#[repr(u8)]` / `#[repr(i32)]` / etc., size and alignment match the named primitive integer type. Crucially, layout compatibility does **not** relax Rust value validity: even in a `#[repr(C)]` or `#[repr(u8)]` fieldless enum, holding any integer value not declared as a Rust discriminant of that enum is immediate UB.
   - **Fieldful Enums:**
     - `#[repr(C)]` on an enum with fields is layout-equivalent to a `#[repr(C)]` struct with two fields: a `#[repr(C)]` fieldless discriminant tag and a `#[repr(C)]` union of `#[repr(C)]` per-variant payload structs (unit variants correspond to zero-sized structs).
     - `#[repr(Int)]` (such as `#[repr(u8)]`) on an enum with fields is layout-equivalent to a `#[repr(C)]` union of `#[repr(C)]` variant structs where **each variant struct begins with the `Int` discriminant tag field** followed by that variant's payload fields.
     - `#[repr(C, Int)]` (such as `#[repr(C, u8)]`) retains the top-level `#[repr(C)]` two-field struct shape `(tag, payload_union)` while fixing the `tag` field to the primitive `Int` representation rather than the target's default C `enum` width.
5. **Alignment Modifiers (`#[repr(align(N))]`, `#[repr(packed(N))]`) and Reference Hazards:**
   - `N` must be a power of two in $1 ..= 2^{29}$; bare `#[repr(packed)]` means `#[repr(packed(1))]`.
   - `align(N)` raises aggregate alignment to $\max(N, \text{natural\_align})$. Applied to an enum, `#[repr(align(N))]` behaves as if the enum were wrapped in a single-field `#[repr(align(N))]` newtype struct.
   - `packed(N)` lowers field-placement alignment and aggregate alignment to $\min(N, \text{field\_align})$, eliminating inter-field and trailing padding completely when $N = 1$.
   - Neither `align(N)` nor `packed(N)` fixes struct field order unless paired with `#[repr(C)]`. Moreover, `align` and `packed` cannot appear on the same type, and a `packed` type cannot transitively contain a `#[repr(align(N))]` type.
   - Because `packed(N)` lowers placement alignment without changing the field type's own required alignment, forming `&packed_struct.field` or `&mut packed_struct.field` when the field is misaligned is immediate UB. Callers must copy the field by value or form a raw pointer via `&raw const packed_struct.field` / `&raw mut packed_struct.field` and use `ptr::read_unaligned` / `ptr::write_unaligned`.
6. **Transparent Representation (`#[repr(transparent)]`):**
   - Applicable to any struct or single-variant enum with at most one field that is not simultaneously zero-sized and alignment-one (`size == 0 && align == 1`), plus any number of zero-sized, alignment-one fields (an over-aligned ZST with `align > 1` counts as the single non-trivial field!).
   - Guarantees both **memory layout equivalence** and **function-call ABI equivalence** with that single field (or `()` if all fields have size 0 and alignment 1). By contrast, two unrelated aggregates that merely happen to have equal `size_of` and `align_of` do not necessarily share calling-convention pass modes (`FnAbi` / `PassMode`).

### 2. Type-Level and Value-Level Geometry Queries and Dynamically Sized Types (DSTs)

Basis: normative specification + documentation + source (`support/rust-size-align/semantics-matrix.json`, `support/rust-size-align/source-map.json`, `support/rust-dst-slice-layout/layout-matrix.json`, `support/rust-dst-slice-layout/source-map.json`)

| Query / Construct | Signature / Metadata Type | Layout Formula and Preconditions |
| :--- | :--- | :--- |
| `core::mem::size_of::<T>()` | `const fn size_of<T>() -> usize` (`T: Sized`) | Returns `SizedTypeProperties::SIZE` (`intrinsics::size_of::<T>()`): byte stride between consecutive elements in `[T; N]`, including alignment padding. Always a multiple of `align_of::<T>()`. |
| `core::mem::align_of::<T>()` | `const fn align_of<T>() -> usize` (`T: Sized`) | Returns `SizedTypeProperties::ALIGN` (`intrinsics::align_of::<T>()`): ABI-required minimum alignment in bytes ($2^k \ge 1$). Note: `size_of::<T>() == 0` does **not** imply `align_of::<T>() == 1`, and primitive alignment can be strictly smaller than primitive size (e.g., `u128` or `u64` on certain targets). |
| `core::mem::size_of_val(&x)` / `align_of_val(&x)` | `const fn size_of_val<T: ?Sized>(val: &T) -> usize` | Requires a **valid Rust reference `&T`** at call entry (aligned, non-null, dereferenceable, initialized valid pointee). Delegates to `intrinsics::size_of_val(val)` / `align_of_val(val)`. |
| `core::mem::size_of_val_raw(ptr)` / `align_of_val_raw(ptr)` | `const unsafe fn size_of_val_raw<T: ?Sized>(val: *const T) -> usize` (unstable `layout_for_ptr`) | Avoids forming `&T`, but requires: (a) for a slice tail, initialized `usize` length metadata; (b) for a `dyn Trait` tail, a valid compiler vtable from an unsizing coercion; and (c) total byte size of the **entire value** (prefix + tail) $\le \text{isize::MAX}$ (with length 0 documented as a valid special case). |
| Slice `[T]` and `str` | `<[T] as Pointee>::Metadata = usize` (element count); `<str as Pointee>::Metadata = usize` (byte length) | Dynamic size $= n \times \text{size\_of}::<T>()$, dynamic alignment $= \text{align\_of}::<T>()$, element $i$ offset $= i \times \text{size\_of}::<T>()$. For ZST elements (`size_of::<T>() == 0`), dynamic byte size is `0` for every $n$, while element count metadata remains $n$. |
| Trait object `dyn Trait` | `<dyn Trait as Pointee>::Metadata = DynMetadata<dyn Trait>` | Dynamic size and alignment equal those of the erased concrete type stored in the vtable (`DynMetadata::size_of`, `DynMetadata::align_of`). |
| Struct with DST tail `Struct<..., Tail: ?Sized>` | `<Struct as Pointee>::Metadata = <Tail as Pointee>::Metadata` | Pointer metadata is forwarded from the final field `Tail`, but the outer value's dynamic size includes the statically sized prefix, inter-field padding, and trailing rounding—**not** merely `DynMetadata::size_of()` or `n * size_of::<Elem>()`. Under `repr(C)`, prefix and tail offsets follow the deterministic alignment-rounding algorithm; under `repr(Rust)`, prefix field order is unspecified. |
| Wide pointer representation `&T` / `*const T` (`T: ?Sized`) | Sized pointer value containing data address/provenance + `Pointee::Metadata` | Normatively guaranteed to be `Sized` with size and alignment at least those of a thin pointer. While current 64-bit targets represent wide pointers as $2 \times \text{size\_of}::<\text{usize}>() = 16$ bytes with alignment 8, the Reference type-layout chapter explicitly warns that code must not rely on a fixed two-word field order `(data, metadata)` across compilations. |

### 3. Compiler-Internal Layout Model (`rustc_abi`, `rustc_middle`, `rustc_public`)

Basis: source (`rust-lang/rust@14210df0e27ccd7d9e6a05b8085cbd438e4bbc65`) + execution (`support/rust-layout-runtime-may-september/results.json`, `support/rust-layout-runtime-may-september/analysis.json`)

1. **`rustc_abi::LayoutData<FieldIdx, VariantIdx>` Structure (`compiler/rustc_abi/src/lib.rs`):**
   - `fields: FieldsShape`: classifies field placement into `Primitive`, `Union(NonZero<usize>)`, `Array { stride: Size, count: u64 }`, or `Arbitrary { offsets: IndexVec<FieldIdx, Size>, memory_index: IndexVec<FieldIdx, u32> }`. In `Arbitrary`, `offsets` is indexed by source declaration order (and need not be monotonic because `rustc` reorders `repr(Rust)` fields), while `memory_index` maps source fields to increasing memory address order. Byte gaps between fields in an outer layout are not necessarily uninitialized padding: enum layouts can store tags inside inner-field niche gaps.
   - `variants: Variants`: `Empty` (uninhabited), `Single { index: VariantIdx }`, or `Multiple { tag: Scalar, tag_encoding: TagEncoding<VariantIdx>, tag_field: FieldIdx, variants: IndexVec<VariantIdx, LayoutData> }`. `TagEncoding` is either `Direct` (tag scalar stores discriminant directly) or `Niche { untagged_variant: VariantIdx, niche_variants: RangeInclusive<VariantIdx>, niche_start: u128 }` (for example, `Option<(usize, &T)>` uses the null pointer niche of `&T` at the reference field's offset to encode `None` without increasing size).
   - `backend_repr: BackendRepr`: `Scalar(Scalar)`, `ScalarPair(Scalar, Scalar)`, `SimdVector { element: Scalar, count: u64 }`, `ScalableVector { element: Scalar, count: u64 }`, or `Memory { sized: bool }`. Each `Scalar` carries a primitive kind (`Int`, `F16`, `F32`, `F64`, `F128`, `Pointer(AddressSpace)`) and a ` valid_range: WrappingRange` defining bit-level scalar validity and niche availability (`largest_niche: Option<Niche>`).
   - `align: AbiAndPrefAlign`, `size: Size`, `max_repr_align: Option<Align>`, `unadjusted_abi_align: Align`, and `randomization_seed: Hash64`.
   - **Separation of `BackendRepr` from Calling Convention (`FnAbi` / `PassMode`) and `PointeeInfo`:** `BackendRepr` describes the codegen value shape, not the platform C/Rust calling-convention register assignment (`FnAbi`). Separately, `PointeeInfo` records advisory dereferenceable size, alignment, and pointer kind (`PointerKind::SharedRef`, `MutableRef`, `Box`, `Raw`) for LLVM optimization attributes (`dereferenceable`, `align`), which is distinct from wide-pointer `Pointee::Metadata` computed in `compiler/rustc_middle/src/ty/sty.rs` (`ptr_metadata_ty_or_tail`, `ptr_metadata_ty`).
   - **`TyAndLayout` (`compiler/rustc_abi/src/layout/ty.rs`) and `rustc_public::abi::LayoutShape` (`compiler/rustc_public/src/abi.rs`):** `TyAndLayout::field` and `for_variant` traverse sub-layouts, including synthetic compiler views (enum variants, discriminant fields, wide pointers) that do not correspond to standalone surface Rust types.
2. **May 2026 vs. September 2026 Nightly Host-Layout Probe (`aarch64-apple-darwin`):**
   - Compiling `support/rust-layout-runtime-may-september/fixture/layout.rs` under `rustc 1.98.0-nightly` (`f8a08b688cbe60acc386ed1fbd1b7cbaaf5576b1`) and `rustc 1.101.0-nightly` (`5c543b0b8c73c7b72bc8284ced4fb22ead15734d`) with `--edition 2024 -C opt-level=0 -Zprint-type-sizes` produced **byte-identical runtime stdout** (`support/rust-layout-runtime-may-september/raw/old/run.stdout` and `support/rust-layout-runtime-may-september/raw/new/run.stdout`):
     - `Reordered { a: u16, b: u64, c: u32 }` (`repr(Rust)`): `size=16 align=8`, field offsets `a=10, b=0, c=8` (reordered by decreasing alignment `b, c, a` with 2 bytes of trailing padding).
     - `CControl { a: u16, b: u64, c: u32 }` (`#[repr(C)]`): `size=24 align=8`, field offsets `a=0, b=8, c=16` (6 bytes of inter-field padding after `a` and 4 bytes of tail padding after `c`).
     - `CUnion { a: [u8; 6], b: u32 }` (`#[repr(C)]`): `size=8 align=4`, field offsets `0, 0`.
     - `Payload` data enum: `size=16 align=8`; `Option<&u8>` and `&u8`: `size=8 align=8`; `&[u16]`, `&str`, `&dyn Probe`: `size=16 align=8`.
     - Dynamic pointee queries: `size_of_val(&[1u16, 2, 3][..]) == 6` (`align=2`), `size_of_val("abc") == 3` (`align=1`), `size_of_val(dyn Probe for u32) == 4` (`align=4`), and `DynMetadata<dyn Probe>::size_of() == 4`.
   - Across the 98 lines of `-Zprint-type-sizes` compiler stdout (`support/rust-layout-runtime-may-september/raw/old/compile.stdout` vs. `support/rust-layout-runtime-may-september/raw/new/compile.stdout`), 97 lines were identical; the sole difference was an internal stdlib module path rename from `unwind::libunwind::_Unwind_Reason_Code` to `unwind::types::_Unwind_Reason_Code` (both 4 bytes, alignment 4).

## Boundaries

- **No cross-compilation stability for `repr(Rust)` field offsets or wide-pointer internal field order:** Observed `repr(Rust)` field offsets (`a=10, b=0, c=8` in `Reordered`) and two-word wide-pointer layouts are compiler- and target-specific observations, not language-level guarantees. Only `#[repr(C)]`, `#[repr(Int)]`, `#[repr(transparent)]`, and documented `Option` null/non-zero niche guarantees provide portable layout contracts.
- **Layout compatibility does not imply value validity, initialization, or call-ABI equivalence:**
  - Matching `size_of` and `align_of` (or using `#[repr(C)]` on a fieldless enum or union) never makes arbitrary integer discriminants, uninitialized padding bytes, or invalid bit patterns legal to read as a typed Rust value.
  - Even two types with identical memory layouts can have distinct function-call pass modes (`FnAbi` / `PassMode`); only `#[repr(transparent)]` (and guaranteed niche-optimized `Option` wrappers around FFI-safe pointers/primitives) normatively delegates call ABI.
- **Safe vs. raw dynamic size queries:** `size_of_val(&x)` and `align_of_val(&x)` cannot be called on uninitialized, misaligned, null, or dangling storage because forming the `&T` argument is already immediate UB. Even `size_of_val_raw` and `align_of_val_raw` impose preconditions on slice-length initialization, trait-object vtable validity, and total size $\le \text{isize::MAX}$.
- **Scope of execution evidence:** The Rust `1.89.0` `aarch64` and `s390x` runs (`78` checks each) and the May/September 2026 nightly `aarch64-apple-darwin` probes (`12` runtime lines, `98` `-Zprint-type-sizes` lines) establish exact behavior for those pinned binaries, flags (`-C opt-level=0`), and fixtures. They do not constitute an all-target mechanized proof of floating-point arithmetic, arbitrary vtable layouts, or 32-bit target ABIs.
