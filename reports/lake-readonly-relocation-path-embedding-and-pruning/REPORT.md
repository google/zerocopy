# Lake Read-Only Relocation, Path Embedding, Package Pruning, Native Artifacts, and Server Preparation

## Summary

Consuming a prebuilt Lean 4 and Lake dependency universe from a relocated, read-only, network-offline, or concurrently shared location across `v4.29.0`, `v4.30.0-rc2`, `v4.31.0`, and `v4.34.1` requires separating **validity-governing trace hashes** from **operational path fields**, **write-path ownership**, **package-tree pruning boundaries**, **native/cross-platform artifact classes**, and **language-server file preparation**:

1. **Path embedding across Lake metadata and build artifacts (`v4.30.0-rc2` and `v4.34.1`)**:
   - **Manifests (`lake-manifest.json`)**: `PackageEntrySrc.path` stores a `FilePath` resolved relative to the root workspace via `relPkgsDir / dir`. Moving a self-contained root workspace and its `.lake/packages` tree together preserves relative manifest paths, whereas moving a consumer workspace independently of a shared dependency tree requires adjusting relative path coordinates.
   - **Module setup (`<mod>.setup.json`) and linker response files (`<base>.rsp`)**: `ModuleSetup` (`importArts`, `dynlibs`, `plugins` written by `compileLeanModule`) and `<base>.rsp` (`mkArgs`) embed concrete filesystem paths consumed directly by `lean` or the host linker. Stale relocated paths in `setup.json` or `.rsp` fail when invoked directly without Lake regenerating them, and `-I`/`-L` search flags placed in `traceArgs` (rather than `weakArgs`) enter `depHash`.
   - **Build traces (`BuildMetadata` vs. `ConfigTrace`)**: In standard JSON `.trace` files (`BuildMetadata`), `depHash` is authoritative for `checkHashUpToDate` while `inputs` captions, `outputs`, and replayed `log` entries are informational or operational. By contrast, Lake configuration traces (`*.olean.trace` serialized as `ConfigTrace`) store `options : NameMap String` that `compileConfig` passes back to `lean` via `-D` if the trace goes stale and `-R` (`reconfigure`) is not set.
   - **Trace-prefix rewriting (`anneal/rewrite-lake-vendor.py`)**: Anneal's `rewrite-lake-vendor.py` performs whole-file UTF-8 regex replacement across `*.trace` files (while skipping `.trace.nobuild` via glob pattern), scrubbing build-root prefixes from captions, logs, outputs, and `ConfigTrace.options` without altering `depHash`.

2. **Read-only relocation, offline execution, and workspace-load lock ownership (`v4.30.0-rc2` vs. `v4.31.0` / `v4.34.1`)**:
   - Relocation, read-only execution, network-offline execution (`LAKE_NO_CACHE` vs. `--offline`), and concurrent worker execution are four independent properties; Lake's `Lake.Util.Lock` guards only individual configuration `.olean.lock` files rather than providing a workspace-wide build lock.
   - In an executed macOS arm64 probe on `v4.30.0-rc2` ([`support/lake-generated-workspace-readonly-probe/lake-probes/runs.json`](support/lake-generated-workspace-readonly-probe/lake-probes/runs.json)), consuming a relocated, `chmod -R a-w` prebuilt producer package from a fresh generated workspace without a pre-seeded `lake-manifest.json` failed with `permission denied` creating `producer/.lake/config/probe_dep/lakefile.olean.lock`. Pre-seeding a relative `lake-manifest.json` before the first Lake invocation bypassed dependency reconfiguration, allowing `lake --no-build --no-cache build`, `lake --no-cache --old build`, `lake --no-build --no-cache setup-file`, and `lake env lean --json` to exit `0` with zero producer mutations.
   - Starting in `v4.31.0` (`leanprover/lean4` commit `8a3fc2361ff5d3de7ca3a3c7ee75dd7dcab5f5ee`) and continuing in `v4.34.1`, Lake hoists all package configuration artifacts into the root consumer workspace's `.lake/config/<pkgIdx>/` directory (`LoadConfig.configDir` in `src/lake/Lake/Load/Config.lean:83` and `importConfigFile` in `src/lake/Lake/Load/Lean/Elab.lean:180–185`), eliminating writes to read-only path dependencies' `.lake/config` directories even when their `lakefile.lean` is loaded.

3. **Package-tree pruning, native artifacts, and cross-platform portability**:
   - Safe pruning is defined relative to an explicit consumer contract (`anneal/prune-lake-cache.py` at `google/zerocopy` commit `41f5b37afe7060fd9fe08c00b200672cd76d77b9`). Anneal prunes unreachable Mathlib modules in `.lake/build/lib/lean` and `.lake/build/ir`, removes a fixed list of repository metadata files/directories (including `README.md`, `LICENSE`, `test/`, and `tests/`), and deletes `*.ltar` archives after `leantar` unpacking. Because `remove_package_metadata` deletes `test/` and `tests/` unconditionally across all packages, "keep all non-Mathlib Lean modules" applies only outside those deleted directory names.
   - Native artifacts (`.c.o`, `.bc.o`, `o`, `static`, `shared`, executables, and mangled `Module.dynlibFile` per-module precompiled shared libraries such as `AeneasMeta` when `precompileModules := notCI`) carry `platformTrace` (`System.Platform.target`) and are strictly host-platform-specific, whereas Lean module elaboration outputs use tri-state `platformIndependent : Option Bool` (`none`, `some false`, `some true`). Anneal packages four distinct platform derivations (`x86_64-linux`, `aarch64-linux`, `x86_64-darwin`, `aarch64-darwin`).
   - In Mathlib's `lake exe cache` (`v4.30.0-rc2` vs. `v4.34.1`), `Cache/IO.lean` bumps `rootHashGeneration` from `4` to `5` (line 150), adds optional `.ir.sig` and `.ir.sig.hash` entries to `mkBuildPaths` (line 344), and adds a per-process suffix to temporary `<hash>.ltar.part` download paths (line 69).

4. **Language-server file preparation (`lake serve` and `lake setup-file`)**:
   - `lake serve` spawns `lean --server` with workspace environment variables; per-file preparation occurs when a file worker parses the open buffer's header and runs `lake setup-file <path> -` (passing `ModuleHeader` JSON on stdin and reading `ModuleSetup` JSON on stdout). Under `--no-build --no-cache`, stale imports cause `setup-file` to exit `3` (`importsOutOfDate`). In `v4.34.1`, `ModuleSetup.importArts` serializes each module's artifact paths as a nested array of string arrays rather than a flat string array.

## Findings

### 1. Path Embedding Across Lake Manifests, Module Setup, Traces, and Response Files

Lake embeds filesystem paths across five artifact families with distinct runtime roles:

| Artifact / Field | Source Location (`v4.30.0-rc2` & `v4.34.1`) | Path Form | Operational vs. Validity Role |
| --- | --- | --- | --- |
| `lake-manifest.json` (`packagesDir`, `PackageEntrySrc.path`) | `Lake/Load/Manifest.lean`, `Lake/Load/Workspace.lean`, `Lake/Load/Package.lean` | Relative `FilePath` (`relPkgsDir / dir`) | Operational package resolution during workspace load; breaks if root workspace moves relative to `.lake/packages` or external path dependencies. |
| `<mod>.setup.json` (`importArts`, `dynlibs`, `plugins`) | `src/Lean/Setup.lean`, `Lake/Build/Module.lean` (`compileLeanModule`), `Lake/CLI/Actions.lean` (`setupFile`) | Resolved host filesystem paths | Passed to `lean --setup` (`compileLeanModule`) or stdout (`lake setup-file`); stale paths fail if `lean --setup` is called directly without Lake regenerating `setup.json`. |
| `<base>.rsp` linker response file | `Lake/Build/Actions.lean` (`mkArgs`) | Raw compiler/linker file paths | Operational input when `compileStaticLib` or `compileSharedLib` invokes a tool with `usingResponseFile := true`. |
| `traceArgs` vs. `weakArgs` (`-I`, `-L`, `moreLeanArgs`, `moreLinkArgs`) | `Lake/Build/Module.lean`, `Lake/Build/Common.lean`, `Lake/Build/Targets.lean` | User/package CLI arguments | `traceArgs` are mixed into `depHash`; `weakArgs` (including Lake's built-in `-I` include and `-L` library search paths) are passed to tools without entering `depHash`. |
| `BuildMetadata` (`.trace`) vs. `ConfigTrace` (`*.olean.trace`) | `Lake/Build/Trace.lean`, `Lake/Load/Lean/Elab.lean` (`compileConfig`) | Captions, `outputs`, `log`, and `ConfigTrace.options` | In `BuildMetadata`, `depHash` governs validity (`checkHashUpToDate`); captions and logs are non-authoritative. In `ConfigTrace`, `options` are reused via `-D` on stale-config re-elaboration when `-R` is false. |

In `Lake/Build/Trace.lean`, `BuildTrace` carries `caption : String`, `inputs : Array BuildTrace`, `depHash : Hash`, and `mtime : MTime`. When `BuildTrace.mix` combines traces, it hashes only `depHash` values and ignores `caption`. Consequently, when `computeFileTrace` records `TextFilePath` or `FilePath`, its path string populates `caption` while `depHash` hashes the file contents. Likewise, `ArtifactDescr` (`{hash}.{ext}`) is path-neutral while `Artifact.path` holds the runtime filesystem location.

### 2. Trace-File Relocation and Prefix-Rewrite Boundaries (`anneal/rewrite-lake-vendor.py`)

As cataloged in [`support/lake-trace-relocation-rewrite-boundaries/rewrite-field-matrix.json`](support/lake-trace-relocation-rewrite-boundaries/rewrite-field-matrix.json), Lake writes two distinct `.trace` schemas:

1. **Ordinary target traces (`BuildMetadata` in `src/lake/Lake/Build/Trace.lean`)**:
   - `depHash : Hash`: governs `BuildMetadata.replay` (`checkHashUpToDate`). Rewriting `caption`, `log`, or `outputs` without changing `depHash` preserves up-to-date status.
   - `inputs : Array (String × String)`: serialized pairs of `(caption, depHash.toJson)`. Only the first element contains path text.
   - `outputs : Option Json`: deserialized via `ResolveOutputs` (`Lake/Build/Common.lean`) into content-addressed `ArtifactDescr` entries (`resolveOutput` checks the package build path first and then `Lake.Cache.getFile?` in the local artifact cache).
   - `log : Log`: replayed via `replayLr` on cache hits (`Lake/Build/Common.lean`); rewriting path strings in `log` changes only replayed diagnostic text.
2. **Configuration traces (`ConfigTrace` in `src/lake/Lake/Load/Lean/Elab.lean`)**:
   - Written alongside compiled configuration files (`lakefile.olean.trace`). Contains `platform : String`, `leanHash : String`, `configHash : Hash`, `options : NameMap String`, and `mtime : MTime`.
   - During `compileConfig`, if the configuration `.olean` is up to date (or `buildUnlessUpToDate` hits under `--old`), Lake imports the existing `.olean` without reading `options`. However, if the configuration trace is stale and `reconfigure` (`-R`) is not set, Lake re-elaborates `lakefile.lean` using `trace.options` converted into `-D<key>=<val>` flags. Any build-time path stored in `Lake.LoadConfig.leanOpts` and persisted in `ConfigTrace.options` becomes live input on that stale-config re-elaboration path.

At `google/zerocopy` commit `41f5b37afe7060fd9fe08c00b200672cd76d77b9`, `anneal/rewrite-lake-vendor.py` walks `<vendor-root>` for `*.trace` files and replaces build-root path prefixes (`--strip-prefix <prefix>=<replacement>`) across the raw UTF-8 file text before running `check_traces` to verify that no forbidden build-directory prefix remains. Because `Path.rglob("*.trace")` matches only filenames ending in `.trace`, any `.trace.nobuild` sidecar created after a failed `--no-build` check (`writeNoBuildFile` in `Lake/Build/Trace.lean`) is not matched by `*.trace`.

### 3. Read-Only Relocation, Offline Semantics, Concurrency, and the `v4.31.0` / `v4.34.1` Config-Ownership Delta

Detailed source analysis in [`support/lake-readonly-relocation-offline-concurrency/FINDINGS.md`](support/lake-readonly-relocation-offline-concurrency/FINDINGS.md) (with boundaries in [`support/lake-readonly-relocation-offline-concurrency/BOUNDARIES.md`](support/lake-readonly-relocation-offline-concurrency/BOUNDARIES.md), evidence in [`support/lake-readonly-relocation-offline-concurrency/EVIDENCE.md`](support/lake-readonly-relocation-offline-concurrency/EVIDENCE.md), and revalidation steps in [`support/lake-readonly-relocation-offline-concurrency/REVALIDATION.md`](support/lake-readonly-relocation-offline-concurrency/REVALIDATION.md)) establishes four orthogonal operational dimensions:

- **No process-wide build lock**: `Lake.Util.Lock` (`withLockFile` in `src/lake/Lake/Util/Lock.lean`) is used only when compiling configuration files (`lakefile.olean.lock`) and during reservoir/cache metadata operations. Concurrent `lake build` processes sharing a writable `.lake/build` directory have no global lock protecting target outputs or `.trace` files.
- **`--offline` vs. `LAKE_NO_CACHE` / `--no-cache`**: In Lake's CLI (`src/lake/Lake/CLI/Main.lean`), `--no-cache` and `LAKE_NO_CACHE=1` disable Lake's artifact cache (`enableArtifactCache := false` when `noCache` is set and `LAKE_ARTIFACT_CACHE` is unset), whereas `--offline` is not a general Lake firewall flag (`--offline` is rejected by `lake` CLI parsing, while Mathlib's `Cache/Main.lean` defines its own cache subcommands). True network isolation requires a pre-materialized manifest/package tree plus OS/sandbox network denial.
- **Executed read-only relocation probe on `v4.30.0-rc2`**:
  In the macOS arm64 probe retained under [`support/lake-generated-workspace-readonly-probe/SUPPORT.md`](support/lake-generated-workspace-readonly-probe/SUPPORT.md), [`support/lake-generated-workspace-readonly-probe/lake-probes/runs.json`](support/lake-generated-workspace-readonly-probe/lake-probes/runs.json), and [`support/lake-generated-workspace-readonly-probe/lake-probes/summary.json`](support/lake-generated-workspace-readonly-probe/lake-probes/summary.json) (scripts [`support/lake-generated-workspace-readonly-probe/lake-probes/probe.py`](support/lake-generated-workspace-readonly-probe/lake-probes/probe.py), [`support/lake-generated-workspace-readonly-probe/lake-probes/probe2.py`](support/lake-generated-workspace-readonly-probe/lake-probes/probe2.py), [`support/lake-generated-workspace-readonly-probe/lake-probes/probe3.py`](support/lake-generated-workspace-readonly-probe/lake-probes/probe3.py), and [`support/lake-generated-workspace-readonly-probe/lake-probes/probe4.py`](support/lake-generated-workspace-readonly-probe/lake-probes/probe4.py)):
  - Toolchain binaries: `lake` SHA-256 `9a89b2af1bddb7e6d5a8dbb2c715288bcb4f24b9129132640cee950734366bcb`, `lean` SHA-256 `b48bc5ab229bd8b320a224b87e20fc428dba6fa8a1c054bd4fa6def846e19997`.
  - Prebuilt producer (`probe_dep`): `Dep.olean` SHA-256 `cebebbbc892381bd3920a0b12ab5e4d65f1804574357994ccb20f95f87f98f9b`, relocated and locked read-only (`chmod -R a-w`, tree hashes `feff44a7359080f18d0a64ebe9190a1311de0d587d8754171ba2540916df4e65` and `46b046ceaf6a9423ec9d57e4e97ebd3234d0deb3a5964d4443222bd9b7894a4f`).
  - Consumer workspace (`probe_consumer`, requiring `probe_dep` from the parent-relative producer directory):
    - **Without pre-seeded `lake-manifest.json`** (`probe.py`): `lake --no-build --no-cache build`, `lake --no-cache --old build`, and `lake --no-build --no-cache setup-file Generated.lean` all exited `1` with `error: ... producer/.lake/config/probe_dep/lakefile.olean.lock: permission denied`.
    - **With pre-seeded relative `lake-manifest.json`** (`probe2.py`, manifest SHA-256 `4b5492c7d64718a5d310b0e588428b5de28293ebed2875792ec65b25b32f3897`, `path: "<parent-dir>/producer"`): `--no-build` dependency check (`ProbeDep`), `--old build` of `Generated` (`Generated.olean` SHA-256 `260bd52b339001cbd7fa23ad2a656976e007ddecc2f4c5596cb56ba031b4d0ec`), `setup-file Generated.lean`, and `lake env lean --json Generated.lean` all exited `0` (max wall time `3.306s`) with zero modifications to the read-only producer tree.
- **Version delta in `v4.31.0` and `v4.34.1` (workspace-hoisted configuration cache)**:
  - In `v4.30.0-rc2`, each package owned its own `.lake/config/<pkgName>/` directory (`pkgDir / defaultLakeDir / defaultConfigDir`), causing Lake to create `lakefile.olean.lock` inside the dependency's own `.lake/config/` whenever `importConfigFile` ran in build mode.
  - Starting in `v4.31.0` (`leanprover/lean4` commit `8a3fc2361ff5d3de7ca3a3c7ee75dd7dcab5f5ee`) and verified at `v4.34.1` (`5045d0056413266e57c625dcd7c365b10e377c52`), `LoadConfig.configDir` (`src/lake/Lake/Load/Config.lean:83`) is `wsDir / defaultLakeDir / defaultConfigDir / pkgIdx.toString`, and `importConfigFile` (`src/lake/Lake/Load/Lean/Elab.lean:180–185`) writes `lakefile.olean`, `lakefile.olean.trace`, and `lakefile.olean.lock` inside the root consumer workspace's `.lake/config/<pkgIdx>/` directory rather than inside the dependency package tree.

### 4. Package-Tree Pruning Boundaries and Native / Cross-Platform Artifacts

As documented in [`support/lake-package-tree-pruning/pruning-safety-contract.json`](support/lake-package-tree-pruning/pruning-safety-contract.json), [`support/lean-package-native-artifacts/source-map.json`](support/lean-package-native-artifacts/source-map.json), [`support/lean-lake-cross-platform-artifact-portability/portability-matrix.json`](support/lean-lake-cross-platform-artifact-portability/portability-matrix.json), and [`support/lean-lake-cross-platform-artifact-portability/source-map.json`](support/lean-lake-cross-platform-artifact-portability/source-map.json):

- **Anneal pruning contract (`anneal/prune-lake-cache.py`)**:
  - Deletes `PACKAGE_META_FILES = (".gitignore", ".gitattributes", "README.md", "LICENSE", "bors.toml", ".pre-commit-config.yaml", ".gitpod.yml")`, `PACKAGE_META_DIRS = (".github", ".vscode", ".devcontainer", ".docker", "docs", "tests", "test")`, and all `*.ltar` files across every package, then removes empty directories.
  - Because `PackageConfig.lean` defaults `readmeFile := "README.md"` and `licenseFiles := #["LICENSE"]`, deleting those files drops Reservoir/metadata equivalence while preserving elaboration imports.
  - For non-Mathlib packages, `prune_package` marks all `.lean` files outside `.lake` as reachable, but subsequently calls `remove_package_metadata`, which recursively deletes `test/` and `tests/`. Any target source file placed under `test/` or `tests/` is therefore deleted.
  - For unreachable Mathlib modules, `prune-lake-cache.py` scans only `.lake/build/lib/lean` and `.lake/build/ir` for `<Module>.` prefix matches. It does not scan `.lake/build/lib` or `.lake/build/bin`, nor does it compute mangled per-module shared library names (`Module.dynlibFile` in `Lake/Config/Module.lean`).
- **Native artifacts and cross-platform portability (`v4.30.0-rc2` and `v4.34.1`)**:
  - `Lake/Build/Facets.lean` and `Lake/Build/ModuleArtifacts.lean` separate module elaboration outputs (`leanArts`: `.olean`, `.olean.server`, `.olean.private`, `.ilean`, `.ir`, `.c`, `.bc`, plus `.ir.sig` in `v4.34.1`) from native facets (`c.o`, `c.o.export`, `c.o.noexport`, `bc.o`, `o`, `static`, `static.export`, `shared`).
  - Native object (`buildO`, `buildLeanO`), shared-library, and executable builders mix `platformTrace` (`System.Platform.target`, the LLVM target triple from `src/Init/System/Platform.lean`) into their traces.
  - Module elaboration uses tri-state `platformIndependent : Option Bool` (`Lake/Build/Module.lean:124`, `Lake/Config/LeanConfig.lean`): `none` propagates platform traces naturally from any native library/plugin dependencies (`Aeneas` and `Mathlib` both leave `platformIndependent` unset at `none`), `some false` forces `platformTrace`, and `some true` omits the native-library/plugin trace without verification ("configuration can lie").
  - In `AeneasVerif/aeneas@ac9f1bc5262a5e4ff1e24ca78617121382202727`, `backends/lean/lakefile.lean` sets `precompileModules := notCI` on `AeneasMeta`, emitting host-specific per-module shared libraries (`lib/lean/<mangled_stem>.{so,dylib,dll}`) whenever `CI` is unset.
- **Mathlib `lake exe cache` (`v4.30.0-rc2` vs. `v4.34.1`)**:
  - Comparing `leanprover-community/mathlib4@5450b53e5ddc75d46418fabb605edbf36bd0beb6` (`v4.30.0-rc2`) and `d13f23b723b8a846827a245b89c10fc7d3f11612` (`v4.34.1`): `Cache/Lean.lean` is byte-identical; `Cache/IO.lean` increments `rootHashGeneration` from `4` to `5` (line 150), adds optional `.ir.sig` and `.ir.sig.hash` paths to `mkBuildPaths` (line 344), and appends a per-process suffix to temporary `<hash>.ltar.part` files (line 69); `Cache/Main.lean` and `Cache/Requests.lean` add `--scope`, `--unsafe`, container selection, and a trust-ordered read URL chain (line 298).

### 5. Language-Server Preparation (`lake serve` vs. `lake setup-file`) Across `v4.30.0-rc2` and `v4.34.1`

As detailed in [`support/lake-server-preparation/FINDINGS.md`](support/lake-server-preparation/FINDINGS.md) (with boundaries in [`support/lake-server-preparation/BOUNDARIES.md`](support/lake-server-preparation/BOUNDARIES.md), evidence in [`support/lake-server-preparation/EVIDENCE.md`](support/lake-server-preparation/EVIDENCE.md), and revalidation in [`support/lake-server-preparation/REVALIDATION.md`](support/lake-server-preparation/REVALIDATION.md)):

- `lake serve` (`Lake/CLI/Actions.lean`) loads the workspace environment and root `moreGlobalServerArgs`, then spawns `lean --server`. It does not pre-build or pre-compute `ModuleSetup` for individual files.
- When the Lean file worker (`src/Lean/Server/FileWorker.lean`) opens or refreshes a document, it parses the in-memory import header and runs `lake setup-file <filePath> -` (passing `ModuleHeader` JSON on stdin, or `--no-build --no-cache` when automatic dependency building is disabled).
- `setupFile` (`Lake/CLI/Actions.lean`, `Lake/Build/Module.lean` `prepareServerModule`) builds or fetches the transitive imports declared in the header without building the edited target module itself, then prints `ModuleSetup` JSON to stdout:
  - Exit code `0`: success (`ModuleSetup` JSON written to stdout).
  - Exit code `2`: no Lake configuration found (worker falls back to standalone elaboration).
  - Exit code `3`: `--no-build` failed because an import or dependency artifact was missing or stale; the worker translates exit code `3` into `importsOutOfDate`.
- **Version delta in `v4.34.1`**: In `v4.29.0` and `v4.30.0-rc2`, `ModuleSetup.importArts` serialized each module's resolved `.olean` path list as a flat string array (`["/path/to/Mod.olean"]`). In `v4.34.1`, `lake setup-file` serializes `importArts` entries as a **nested array of string arrays** (`[["/path/to/Mod.olean"]]`).

## Boundaries

- **Pruned-tree execution**: The pruning analysis in `lake-package-tree-pruning` and `lean-package-native-artifacts` is source-derived against `google/zerocopy@41f5b37afe7060fd9fe08c00b200672cd76d77b9`; a full end-to-end execution of every Aeneas/Mathlib target after pruning was **not examined** in this package.
- **Cross-architecture `.olean` binary portability**: While Lake's `platformIndependent` controls invalidation traces, cross-architecture binary import of `.olean` files between x86-64 and AArch64 hosts was **not examined** empirically and remains **unknown** without a dedicated cross-host probe.
