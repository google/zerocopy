# Official Sail RV64D Lean integration: checked effects, arithmetic and full-state framing

## Summary

Lean checked the actual generated top-level RISC-V ADD executor's exact effect tree and universal full-state result: read x1, read x2, write x3 with their modulo 2^64 sum, then retire successfully. The only initial-state premises require x1/x2 to contain the quantified inputs. Every other register and all memory, tags, cycle count and output are framed; PC is preserved for this instruction-AST execution. Independent replay checked all four main theorems at trust level zero and reproduced the identical proof artifact. A subsequent independent replay also checked the 13-theorem control suite; accepted semantic refutations accompany rejection of four concrete false claims.

This success uses the full official configured model's actual import closure with two explicitly identified integration repairs: termination-ranking maintenance and three abstract external-hook declarations. It is not untouched upstream replay. The printed main and concrete-control axiom lists each contain 78 names, including unreachable hooks through the theorem type's whole executor reference; none contains sorryAx. No fetch/decode, ABI return, hardware, weak-memory or Rust-resource correspondence follows.

## Findings

### Actual generated execution has a universal arithmetic and frame theorem

The actual executor receives `instruction.RTYPE (Regidx 2, Regidx 1, Regidx 3, ADD)`, in rs2/rs1/rd/op order. `execute_add_effects` proves by rfl that the entire top-level computation equals precisely two register reads, one x3 write of their sum, and pure `Retire_Success ()`. It excludes hidden memory, choice, exception or ignored system-notification effects on this selected path before interpreting them. This matters because the general sequential interpreter ignores some system effects; final-state equality alone would not establish their absence. Basis: source + execution. [Exact proof source](Proof.lean), [independent theorem review](support/independent/INDEPENDENT-THEOREM-REVIEW.md).

`execute_add_full_state` quantifies all `a b : BitVec 64` and all actual `SequentialState RegisterType` states `s`. Its only premises are `s.regs.get? x1 = some a` and `s.regs.get? x2 = some b`; the conclusion is:

```text
interpretSailEffects (Functions.execute selected_ADD) |>.run s
  = .ok (Retire_Success ()) {s with regs := s.regs.insert x3 (a+b)}
```

The state uses the generated `Register` enumeration and dependent `RegisterType` mapping, stored in `Std.ExtDHashMap`. Prior x3 presence and unrelated register initialization are unnecessary. The actual register read errors when a source entry is absent, so the two premises delimit a meaningful domain. `BitVec 64` addition supplies modulo 2^64 arithmetic, without a carry result. Memory, tags, cycleCount and sailOutput are unchanged by equality of the entire returned state.

`execute_add_register_frame` projects unchanged lookup for every generated register `r ≠ x3`, including absent entries. `execute_add_pc_frame` specializes it to PC. The nextPC register is included in the general frame. This is AST execution: actual fetch/step assigns nextPC = PC + 4 outside execute, and tick_pc subsequently copies it to PC. Neither advancement nor fetched bytes are included here. The x1, x2 and x3 registers are selected ISA registers, not a Rust ABI argument/result assignment.

The accepted source SHA256 is `f62057489d30152c39dcfab87c5b7ecbb43dd2e6bbe14d0368c4cbc832b6f2d4`; Proof.olean is `a37ef2b0d8f2ed3613a85ae666e89771464e2453df0929f9f80fb44397faa3bf`. Initial acceptance took 1.064552 seconds, peak RSS 1,555,508 KiB. Independent `-t0` replay took 1.495498 seconds, peak RSS 1,552,348 KiB, and reproduced the identical artifact after independently validating the 143 imported olean identities. It did not rebuild those 143 sources. [Replay receipt](support/independent/independent-proof-native.json).

### Checked controls distinguish faults and changed instructions

Accepted Controls.lean contains 13 theorems: six general effect/full-state/missing-source lemmas plus seven concrete arithmetic/observation fixtures. It uses the same actual top-level executor and interpreter, importing the accepted Proof module. Its constructive witnesses establish:

- the maximum 64-bit word plus 1 writes 0 to x3;
- SUB on 1 and 2 writes the maximum 64-bit word, with a separate theorem that observed x3 differs from ADD's 3;
- ADD with destination x4 leaves initial x3 = 0 and writes 3 to x4;
- missing x1, or present x1 with missing x2, returns actual Unreachable and the unchanged state.

These are proved semantic observations, not an inference from an unsuccessful tactic. Ordinary decide is confined to finite numeral arithmetic/constructor distinctness; native_decide is not used. The suite checked with `-t0`, exit 0 in 2.107820 seconds, peak RSS 1,554,060 KiB. Source SHA256 is `7c9301d8c6080cd8cd1cf1a4ae356532b92de8378e416fd7ed48f35945d5635b`; Controls.olean is `b2fbb76b44f7eb0ad57ca724d959a62dc0ddd7594df0db0a4b26b129fe9aa0b7`. [Exact controls](Controls.lean), [accepted control receipt](support/runtime/controls-parent-1-native.json).

Independent Controls-v4 replay passed with `-t0` in 2.144861 seconds, peak RSS 1,555,444 KiB, reproducing the same Controls.olean hash. The accepted SemanticAudit3 then proved four negations: SUB on inputs 1 and 2 does not give ADD’s result of 3; ADD to x4 does not give x3 the result 3; the missing-x1 fixture does not return the specified success state; and the overflowing 64-bit sum is not the unbounded natural sum 18446744073709551616. Its observation helper only runs the actual executor/interpreter and projects x3; it defines no instruction semantics. [Independent controls review](support/independent/INDEPENDENT-CONTROLS-V4-REVIEW.md), [accepted semantic audit](support/independent/controls-v4-review/SemanticAudit3.lean).

Lean then rejected the four corresponding well-typed opposite claims in two deliberately failing files, FalsePair1 and FalsePair2, through numeric or success/error constructor distinctions. The semantic evidence is the prior accepted negations, not the failure of decide or rfl alone. These checks distinguish the selected concrete counterclaims; they are not a rejection test for every operand, destination, missing-state configuration or byte-level mutation. The earlier independent Controls-v3 rejection remains a different failed version.

### Kernel acceptance retains the declared semantic inputs

Each of the four main theorem axiom lists contains 78 names: 67 floating-point hooks, 8 other data/computation hooks, and `propext`, `Classical.choice` and `Quot.sound`. The independent SemanticAudit3 prints all 13 control-theorem lists plus its five helper/negation lists; all 18 contain exactly the same 78 names. The 8 other hooks are `cancel_reservation`, `event_callback`, `event_csr_write_callback`, `get_16_random_bits`, `load_reservation`, `match_reservation`, `plat_term_write` and `sys_enable_experimental_extensions`. No list contains sorryAx. These are individual collected theorem closures, not merely the global imported list. [Exact main lists](support/independent/independent-proof-axioms.json), [all 18 control/audit lists](support/independent/controls-v4-review/all-theorem-axioms.json).

Lean 4.29's CollectAxioms traverses the theorem's type and value, and whole referenced definitions, syntactically. Since each statement binds actual whole Functions.execute, unreachable branches contribute hooks even though the checked selected effect tree invokes none. The 78-name closure is not a minimal semantic dependence result; no dependency was removed to hide the executor's identity. The added hooks are arbitrary data/computation semantic inputs, not logical correctness axioms, but remain declared assumptions. Default Float-based FakeReal and all external-support choices remain part of the identified model; this scalar proof does not validate floating-point semantics.

This is useful to Anneal as a proof-producing ISA endpoint: proof search, rfl/simp and auxiliary scripting propose terms whose acceptance is checked by Lean, including an independent trust-zero replay. They do not need authority to assert ADD correctness. The selected Sail definition/configuration, generator rewrites and output, support interpretation, official compiler/kernel and imported artifacts still form the semantic/implementation boundary. Kernel acceptance does not verify Sail-to-Lean translation or hardware fidelity. A future relation to another executor must connect its complete state, effects and observations to this endpoint; shared arithmetic alone does not supply that relation.

## Boundaries

- **Established:** full 143-module integration import build; four main theorems with exact actual executor/effect/state binding; 13 control theorems; independent trust-zero main and control replays; four accepted concrete semantic negations and corresponding false-claim rejections; recorded nonempty axiom closures.
- **Not examined:** rejection of every possible instruction or state mutant, artifact tampering or byte-level mutations. The four concrete rejection checks do not establish those broader properties.
- **Not examined:** actual decoder for word 0x002081b3 or byte-fetch/step theorem, PC+4, ABI stack/return/carry, load/store permission/fault contracts, arbitrary instruction programs or a cross-ISA shared contract.
- **Known not to apply:** the sequential interpreter chooses 0 for finite nonempty choices, errors on absent registers/memory, rejects nonzero tags and ignores some architecture/cache/translation notifications. Selected ADD's exact effect tree avoids those cases; no general adequacy or weak-memory theorem is proved.
- **Not examined:** source/generator verification, hardware correspondence, Rust provenance/borrow/resource authority, Rust compiler/ABI refinement, or Kraken-to-Sail state/effect simulation. The repairs and data-hook assumptions must not disappear from such a later comparison.
