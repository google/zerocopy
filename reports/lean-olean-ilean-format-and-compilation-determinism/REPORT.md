# Lean 4 `.olean` and `.ilean` Formats, Compilation Determinism, Cross-Version Reproducibility, and Bundled `leantar` Packaging

## Summary

Across Lean `v4.29.0`, `v4.30.0-rc2`, and `v4.34.1`, Lean's compiled module artifacts (`.olean`, `.olean.server`, `.olean.private`, `.ir`, `.ir.sig`), editor reference indexes (`.ilean`), compilation determinism mechanisms, and release-archive helper binaries (`bin/leantar`) obey strict format, toolchain-identity, and materialization boundaries:

1. **`.olean` binary format, multipart module system, and `CHECK_OLEAN_VERSION` (`v4.30.0-rc2` and `v4.34.1`)**:
   - A `.olean` file is a compacted native Lean runtime object graph (`object_compactor` in `src/runtime/compact.cpp`) preceded by a fixed-layout `olean_header` (`80 + sizeof(size_t)` = 88 bytes on 64-bit hosts in `src/library/module.cpp`) containing a 5-byte `"olean"` marker, 1-byte version (`2`), 1-byte flags bitfield (`bit 0` = `LEAN_USE_GMP`), 33-byte `lean_version` string, 40-byte `githash`, and native `size_t` mmap base address derived deterministically from the module `Name`.
   - Under the module system (`src/Lean/Environment.lean`), `OLeanLevel` partitions module data into `exported` (`.olean`), `server` (`.olean.server`), and `private` (`.olean.private`), written together by `saveModuleDataParts` with shared compacted-region memory pointers; in `v4.34.1`, Lake also tracks `.ir.sig` alongside `.ir`.
   - A `.olean` payload does not store its own module `Name` or source SHA-256; `findOLean` (`src/Lean/Util/Path.lean`) resolves module names purely by `LEAN_PATH` directory layout.
   - `CHECK_OLEAN_VERSION` defaults to `OFF` in `src/CMakeLists.txt` (lines 114, 153–156) for local development builds, but official release CI (`.github/workflows/build-template.yml`) compiles with `-DCHECK_OLEAN_VERSION=ON`, enforcing exact `lean_version` and 40-byte `githash` verification on load.

2. **`.ilean` reference-index schema and language-server overlay (`v4.30.0-rc2` and `v4.34.1`)**:
   - Persisted `.ilean` files (`Lean.Server.Ilean` in `src/Lean/Server/References.lean` and `src/Lean/Data/Lsp/Internal.lean`) are compressed JSON objects with five fields: `version : Nat := 5`, `module : Name`, `directImports : Array Lsp.ImportInfo`, `references : Lsp.ModuleRefs`, and `decls : Lsp.Decls`.
   - The standalone frontend (`src/Lean/Elab/Frontend.lean`) emits `.ilean` after elaboration using `findModuleRefs ... (localVars := false)`, omitting local `FVarId` references, whereas open-file LSP workers (`src/Lean/Server/FileWorker.lean`) compute transient overlays with `localVars := true` via `$/lean/ileanInfoUpdate` and `$/lean/ileanInfoFinal`.
   - `Ilean.load` and `References.addIlean` decode JSON without checking `ilean.version == 5`. The watchdog (`src/Lean/Server/Watchdog.lean`) loads `.ilean` files asynchronously at startup (`startLoadingReferences`, synchronized via `$/lean/waitForILeans`) and uses them for cross-file references, rename, workspace symbols, call/module hierarchy, and `bendLocationLinks` definition-range correction, while proof goals (`$/lean/plainGoal`, `$/lean/plainTermGoal` in `src/Lean/Server/FileWorker/RequestHandling.lean`) require live worker `InfoTree` snapshots.

3. **Compilation determinism and executed 3-version reproducibility (`v4.29.0`, `v4.30.0-rc2`, `v4.34.1`)**:
   - Lean stabilizes asynchronous elaboration (`Elab.async = true` waiting on `waitForFinalCmdState?`), deferred realizations (`enableRealizationsForConst`, `Lean.Meta.realizeValue`, `realizeConst`, heartbeat save/restore), exported constant ordering (`mkModuleData` re-sorting filtered constants by `Name` so `.olean` is independent of `.olean.private`), non-GMP bignum struct padding (`object_compactor::insert_mpz` zeroing destination memory), LCNF reference-counting variable ordering (`ExplicitRC` `Context.idx`), and buffered stderr diagnostics (`stderrAsMessages`).
   - Across executed two-module batch builds on `v4.29.0`, `v4.30.0-rc2`, and `v4.34.1` ([`support/lean-compilation-reproducibility-429-430-434-batch-delta/results.json`](support/lean-compilation-reproducibility-429-430-434-batch-delta/results.json)), repeated clean builds within each version produced 16 byte-identical artifacts, and repeated local-cache reuse builds produced 6 byte-identical local files (`.ilean`, `.ilean.hash`, `.trace`) while omitting project-local `.olean` files. Because `lake env lean --json Probe.lean` requires local `.olean` files on `LEAN_PATH`, batch `lean` failed after cache reuse in all three versions until a no-cache build materialized all 16 local files.
   - Across versions, `.olean`, `.trace`, and `.c` hashes differ by toolchain while `.ilean` (`35041f9c03bbbf9318aebc5469258dc0868231ca32d240077f101131d0aad421`) remained identical. In `v4.30.0-rc2`, LSP `initialize` added `experimental.rpcProvider.rpcWireFormat: "v1"` relative to `v4.29.0`. In `v4.34.1`, `lake setup-file` changed `importArts["Probe.Base"]` from a flat 1-element string array to a nested array of string arrays.

4. **Linux AArch64 bundled `bin/leantar` anomaly (`v4.30.0-rc2`) and resolution (`v4.34.1`)**:
   - In `lean-4.30.0-rc2-linux_aarch64.tar.zst` (SHA-256 `b196f41da23960e842fc0fc04749d1639d44839feafc0414e53cb2db6b16790f`), the bundled `bin/leantar` (2,653,464 bytes, SHA-256 `89ef0c3bd2c40e727191bcd406ef3dac95e0b9000ac93cb7f8c681031ad486be`) is an **x86-64** ELF binary (`e_machine = 62`), requiring Anneal (`anneal/flake.nix`) to fetch standalone `leantar-v0.1.16-aarch64-unknown-linux-musl.tar.gz` (`e_machine = 183`).
   - Static recheck of `lean-4.34.1-linux_aarch64.tar.zst` (SHA-256 `fdb974c2cdb4627e090d5d4007b913e090d13c4868720fb5594e22808b3de9e37`) confirms that its bundled `bin/leantar` (2,563,160 bytes, SHA-256 `5a7aaf4a60170490640a4463d31f12515f8de00aa9b66a124b1716768fbd62bc`) is a native **AArch64** ELF binary (`e_machine = 183`), resolving the packaging anomaly.

## Findings

### 1. `.olean` Container Format, Multipart Module Graph, and Version Checking (`v4.30.0-rc2` and `v4.34.1`)

In `src/library/module.cpp` (lines 48–252 in `v4.30.0-rc2`, lines 48–255 in `v4.34.1`) and `src/Lean/Environment.lean` (lines 124–180, 1804–1910):

- **Header layout (`olean_header`)**:
  - Total size is `80 + sizeof(size_t)` bytes (88 bytes on 64-bit targets; `static_assert(sizeof(olean_header) == 80 + sizeof(size_t))`).
  - Fields: `marker[5]` = `"olean"`, `version` = `2` (`uint8_t`), `flags` (`uint8_t`, bit `0` = `b_use_gmp` set iff compiled with `LEAN_USE_GMP`), `lean_version[33]` (null-padded version string or `"<disabled>"` when `LEAN_CHECK_OLEAN_VERSION` is off), `githash[40]` (`LEAN_GITHASH`), and `base_addr` (`size_t`).
  - `base_addr` is computed deterministically from a 64-bit hash of the logical module `Name` shifted into a fixed virtual address window so distinct modules map into non-overlapping regions when `mmap` succeeds, falling back to `compacted_region` pointer relocation (`src/runtime/compact.cpp:387–505`) when `mmap` cannot map at `base_addr`.
- **`CHECK_OLEAN_VERSION` build-flag split**:
  - In `src/CMakeLists.txt` (lines 114, 153–156), `option(CHECK_OLEAN_VERSION "Only loadable with exact same Lean version" OFF)` is disabled by default for local builds, whereas `.github/workflows/build-template.yml` sets `-DCHECK_OLEAN_VERSION=ON` for official releases.
  - On load (`parse_olean_header`), Lean always checks `marker == "olean"`, `version == 2`, and the `b_use_gmp` bit, and when built with `LEAN_CHECK_OLEAN_VERSION` also requires `lean_version` and `githash` to match the running binary.
- **Multipart `OLeanLevel` and `ModuleData` (`src/Lean/Environment.lean`)**:
  - `ModuleData` contains `isModule : Bool`, `imports : Array Import`, `constNames : Array Name`, `constants : Array ConstantInfo`, `extraConstNames : Array Name`, and `entries : Array (Name × Array EnvExtensionEntry)`.
  - `OLeanLevel` defines three levels: `exported` (`.olean`), `server` (`.olean.server`), and `private` (`.olean.private`). When `saveModuleDataParts` serializes a multi-level module, part `i` is compacted in a `object_compactor` seeded with the regions of parts `0 .. i-1`, so `.olean.server` references objects inside `.olean`, and `.olean.private` references objects inside both `.olean` and `.olean.server`. Moving or mixing parts independently breaks internal pointers.
  - `lean_save_module_data_parts` writes each output via a sibling `.tmp` file (`<fname>.tmp`) and atomically renames it into place.
  - **Self-identity**: Neither `olean_header` nor `ModuleData` embeds the module's own `Name` or source file digest; `findOLean` (`src/Lean/Util/Path.lean:116–128`) maps a requested `Name` to `<searchPath>/<modPath>.olean`.
  - **`v4.34.1` delta**: `v4.34.1` preserves the 88-byte `olean_header` (version `2`), `ModuleData` fields, and `OLeanLevel` three-part structure, while adding `.ir.sig` (`Lean.IR` signature files) alongside `.ir` in Lake's `ModuleOutputArtifacts` (`src/lake/Lake/Build/ModuleArtifacts.lean`).

### 2. `.ilean` Schema, Asynchronous Watchdog Loading, and Live Worker Overlay (`v4.30.0-rc2` and `v4.34.1`)

In `src/Lean/Server/References.lean` (lines 205–228 in `v4.30.0-rc2`, lines 206–230 in `v4.34.1`), `src/Lean/Data/Lsp/Internal.lean` (lines 29–322), `src/Lean/Elab/Frontend.lean` (lines 193–211), `src/Lean/Server/FileWorker.lean` (lines 154–335), and `src/Lean/Server/Watchdog.lean` (lines 501–1692):

- **Top-level schema (`Lean.Server.Ilean`)**:
  - `version : Nat := 5` (format version field; **not** compared by `Ilean.load` or `References.addIlean` at load time in either `v4.30.0-rc2` or `v4.34.1`).
  - `module : Name` (string-encoded logical module name).
  - `directImports : Array Lsp.ImportInfo` (each serialized as a 4-element JSON array `[moduleName, isPrivate, isAll, isMeta]`).
  - `references : Lsp.ModuleRefs` (map keyed by compressed JSON `RefIdent` strings—`"c"` for global constants, `"f"` for local `FVarId`s—to `RefInfo` objects containing `definition` and `usages` 4- or 5-element arrays `[startLine, startChar, endLine, endChar, parentDecl?]`).
  - `decls : Lsp.Decls` (map from declaration name to an 8-integer array `[fullStartLine, fullStartChar, fullEndLine, fullEndChar, selStartLine, selStartChar, selEndLine, selEndChar]`).
- **Persisted vs. transient worker reference state**:
  - Persisted `.ilean` files are written by `Elab.Frontend` only after error-free elaboration using `findModuleRefs ... (localVars := false)` and `Json.compress (toJson ilean)`.
  - Open-file workers (`FileWorker.lean`) extract references from live `InfoTree` snapshots with `localVars := true`, sending incremental `$/lean/ileanInfoUpdate` and final `$/lean/ileanInfoFinal` notifications tagged with the LSP document `version`. The watchdog's `References` store prioritizes live worker entries over on-disk `.ilean` entries for open files (`allRefs`, `getModuleRefs?`, `bendLocationLinks`).
- **Startup loading vs. interactive proof goals**:
  - `startLoadingReferences` (`Watchdog.lean`) loads `.ilean` files from `LEAN_PATH` in a background task at server startup, swallowing individual load errors; deterministic synchronization requires `$/lean/waitForILeans`.
  - `.ilean` contains no metavariable contexts, tactic states, or `InfoTree` nodes. Interactive proof queries (`$/lean/plainGoal` and `$/lean/plainTermGoal` in `src/Lean/Server/FileWorker/RequestHandling.lean`, lines 143–249 in `v4.30.0-rc2` and lines 213, 244 in `v4.34.1`) always evaluate against the open worker's live `InfoTree` snapshots.

## Boundaries

- **Whole-language compilation determinism**: Local stabilization points in Lean's frontend, `.olean` serializer, and LCNF pass, together with the two-module reproducibility probe, do not establish global byte identity across arbitrary metaprograms, native `.o`/`.a`/`.so` compiler outputs, GMP bignum configurations, or parallel multithreaded schedules (**not examined** for arbitrary Mathlib modules).
- **LSP server probe on `v4.34.1`**: While `v4.29.0` and `v4.30.0-rc2` were compared under both batch CLI and live `lake serve` LSP sessions, the `v4.34.1` delta replay executed only the 60 sequential batch CLI commands (`lake serve` on `v4.34.1` was **not examined** in that replay due to the host >30% free-RAM admission gate).
- **Cross-version `.olean` reuse**: Loading `.olean` artifacts across distinct Lean commits is **unsupported** on release builds compiled with `-DCHECK_OLEAN_VERSION=ON` (`known not to apply` across `v4.29.0`, `v4.30.0-rc2`, and `v4.34.1`).
- **Foreign binary execution**: Neither the `v4.30.0-rc2` x86-64 `bin/leantar` nor the `v4.34.1` AArch64 `bin/leantar` was executed on the macOS arm64 inspection host; runtime behavior of bundled `leantar` on a live Linux AArch64 kernel was **not examined** in the static archive check.
