# Formal ISA Models for x86-64, i386, and AArch64: Coverage, Fidelity, and Lean 4 Integration

## Summary

Choosing trusted ISA models for a verified Rust compiler targeting the Tier 1 architectures (`x86_64`, `i686`/`i386`, and `aarch64`) requires measuring candidate models against three concrete baselines:
1. **`rustc 1.99.1` target feature surface (`compiler/rustc_target/src/target_features.rs`):** **80** x86/x86-64 features (56 stable, 20 unstable, 4 internal-only) and **94** AArch64 features (44 stable, 48 unstable, 2 internal-only).
2. **`rustc 1.99.1` actual `libcore` machine-code emission (`llvm-objdump -d` across all `.o` members):** **34,044** instructions across **199** distinct mnemonics on `x86_64-unknown-linux-gnu`; **47,521** instructions across **165** distinct mnemonics on `i686-unknown-linux-gnu`; and **32,203** instructions across **129** distinct mnemonics on `aarch64-unknown-linux-gnu`.
3. **LLVM 23.1.1 (`1b9c0d5ff9bbe7634aead059efe6b11a7eeba145`) TableGen instruction universe:** **11,867** `def`/`defm` records across 65 `.td` files (89,325 lines) in `llvm/lib/Target/X86` and **13,804** `def`/`defm` records across 56 `.td` files (113,058 lines) in `llvm/lib/Target/AArch64`.

Across all evaluated x86 and AArch64 specifications, no single existing Lean 4 repository covers the full Tier 1 surface out of the box, but the optimal architecture for each ISA is clear from measured coverage:
- **AArch64:** Arm's official Machine-Readable Architecture Specification (**AArchMRS / ASL** `v2025-03_rel`) and its Sail translation (`rems-project/sail-arm@7d0581642d0e3aaca367bbc5650aca7c53057543`, Armv9.4-A) provide **100% coverage** of all 94 Rust AArch64 target features, full EL0–EL3 system/privileged semantics, and integrated concurrency (`Isla` / `lean-sail` `ArchSem.Effect` monad). While the monolithic 182,786-line generated `SailArm.lean` exceeds practical Lean 4 per-file elaboration limits, combining **LNSym / Kraken / cslib-bignum's idiomatic per-instruction Lean 4 operational semantics** with **ASLp / Sail-Lean per-opcode sliced translations from AArchMRS** yields fast kernel reduction (~15–100 ms per proof obligation) and authoritative vendor coverage.
- **x86-64:** **K-X86-64** (`kframework/X86-64-semantics`, 3,155 opcode variants across Base, SSE–SSE4.2, AVX/AVX2, FMA, BMI1/BMI2, ADX, AES/PCLMULQDQ) has the broadest user-space SIMD coverage (covering **36 of 56** stable Rust x86 features, excluding AVX-512), whereas **ACL2 `x86isa`** (`acl2/acl2@9df88e946034e24212f3aedd8b71b02e4224783e`) and its mechanical Sail translation (`rems-project/sail-x86-from-acl2@0c6c023dccc7c20d8d9dbfc481f01d9bb49d62bf`) provide the only mechanized 64-bit + 32-bit compatibility/IA-32 + ring-0 paging/descriptor semantics (~450 instruction families). For Lean 4, pairing **Intel XED** (`Apache-2.0`) for machine-readable instruction decoding/encoding tables with a tiered semantics—extending `cslib-bignum` / `Kraken` / `sail-x86-from-acl2` for base + scalar/system instructions and importing K-X86-64 / SDM rules for SSE/AVX/AVX-512—avoids maintaining hand-written variable-length x86 decoders.
- **i386 (`i686`):** Only **ACL2 `x86isa`** (via 32-bit compatibility mode in `sail-x86-from-acl2`), **CompCert `x86/Asm.v`** (`Archi.ptr64 = false`), and **HOL4 L3 `x86`** model 32-bit x86 execution (`pushl`/`popl`, 32-bit effective addresses, and `x87` `fld`/`fstp` float returns required by the System V i386 ABI). K-X86-64, Strata, s2n-bignum, Kraken, and MM0 are strictly 64-bit (`x86_64`) only.

## Findings

### 1. Rust 1.99.1 Target Feature Universe vs. Actual `libcore` Instruction Footprint

Basis: source (`rust-lang/rust@58cf8f9c`, `compiler/rustc_target/src/target_features.rs`) + execution (`support/rust_1991_target_features_and_libcore_isa.json`)

A verified Rust compiler must distinguish between two ISA coverage tiers:
- **Baseline Codegen Footprint (required to verify `core`, `alloc`, `std`, and standard Rust crates without explicit SIMD intrinsics):** Measured by disassembling all `.o` objects in `rustc 1.99.1`'s prebuilt `libcore` archives using `llvm-objdump -d`.
- **Full Target-Feature Intrinsic Surface (required to verify `core::arch::{x86, x86_64, aarch64}` and `-Ctarget-feature=+...` crates):** Defined by `X86_FEATURES` and `AARCH64_FEATURES` in `compiler/rustc_target/src/target_features.rs`.

Key observations from the `libcore` disassembly (`support/rust_1991_target_features_and_libcore_isa.json`):
- **Compact baseline footprint:** Even across all of `libcore` (formatting, UTF-8 validation, sorting, floating-point parsing/printing, atomics, and slice iterators), `rustc 1.99.1` emits only **199** distinct mnemonics on `x86_64`, **165** on `i686`, and **129** on `aarch64`.
- **Baseline SIMD usage in `libcore`:** On `x86_64-unknown-linux-gnu`, `libcore` uses 128-bit SSE2 vector instructions (`movdqu`: 280, `movdqa`: 130, `pshufd`: 95, `pxor`: 93, `pcmpeqb`: 45, `pmovmskb`: 43, `paddb`/`psubb`/`pminub`) for slice/string operations and scalar SSE2 float instructions (`mulsd`, `addsd`, `divsd`, `ucomisd`, `xorps`). On `aarch64-unknown-linux-gnu`, `libcore` uses base A64 GP instructions plus NEON/AdvSIMD (`ldp`/`stp` on `q` registers, `cmeq`, `umaxv`, `shrn`, `tbl`, `eor`, `movi`) and LL/SC atomics (`ldaxr`/`stlxr`, `ldxr`/`stxr`, `dmb`).
- **32-bit `i686` stack-passing and `x87` requirements:** On `i686-unknown-linux-gnu`, `pushl` (5,344) and `popl` (1,990) account for 15.4% of all instructions because the System V i386 ABI passes arguments on the stack rather than in registers. Furthermore, `i686` `libcore` emits `x87` FPU instructions (`fldt`, `fstpt`, `fldl`, `fstpl`, `flds`, `fstps`, `fnstcw`, `fldcw`) because the System V i386 ABI returns `f32`/`f64` values in `st(0)`. Any ISA model used to verify `i686` must therefore model both 32-bit addressing/stack operations and the `x87` register stack.

### 4. Recommended ISA Model Selection for a Verified Rust Compiler in Lean 4

Basis: derived

To support all three Tier 1 architectures (`x86_64`, `i686`, `aarch64`) in Lean 4 without either (a) choking the Lean 4 kernel on a 180,000-line monolithic auto-generated file or (b) hand-writing thousands of error-prone SIMD/encoding rules:

1. **AArch64 Selection:**
   - **Authoritative Specification Root:** Arm **AArchMRS (`ASL v2025-03_rel`, BSD-3-Clause)** via **Sail-Arm (`rems-project/sail-arm@7d058164`, BSD-3-Clause)** and **ASLp partial evaluation**.
   - **Lean 4 Realization:** Instead of compiling all of `sail-arm` into a single `SailArm.lean` file, partition the `sail -lean` output by instruction class (Base GP, Atomics/LSE, NEON/FP, Crypto, SVE/SME, System/VMSA) using the `lean-sail` (`rems-project/lean-sail@1e5b216b`) `ArchSem` monad, and bridge it via proved equivalence lemmas (`StepSim`, following the `Verified-zkEVM/riscv-zkvm@6810fc14` pattern) to the fast flat `ArmState` WP evaluator from **Kraken / LNSym / cslib-bignum**.
2. **x86-64 Selection:**
   - **Decoding / Encoding Table Root:** **Intel XED (`intelxed/xed`, Apache-2.0)** machine-readable grammar tables (`all-dec-instructions.txt`, `all-enc-instructions.txt`), compiled into a total Lean 4 decoder/encoder covering legacy, VEX, EVEX (AVX-512), and REX2/APX prefixes.
   - **Operational Semantics Root:** A two-layer Lean 4 model combining:
     - **Base GP + System + 32/64-bit Mode:** **ACL2 `x86isa` / `sail-x86-from-acl2@0c6c023d` (BSD-3-Clause)** for architectural state, flag computations, 32/64-bit effective address calculation, and ring-0 paging, paired with **`cslib-bignum` / `Kraken` (Apache-2.0)** fast WP rules for the ~200 instructions emitted by `rustc` on standard crates.
     - **User-Space SIMD (SSE–AVX2/FMA/BMI/AES):** Mechanical translation of **K-X86-64 (`kframework/X86-64-semantics`, NCSA license)** bitvector rewrite rules (3,155 opcode variants) into per-extension Lean 4 modules, supplemented by Intel SDM / XED specifications for AVX-512.
3. **i386 (`i686`) Selection:**
   - Reuse the 32-bit compatibility/IA-32 mode of **`sail-x86-from-acl2@0c6c023d` / ACL2 `x86isa`** (which already parameterizes effective address size, stack pointer width `ESP` vs `RSP`, and `x87` 80-bit FPU stack registers by mode bits `CS.L = 0, CS.D = 1`), rather than maintaining a separate `i386` ISA formalization.

## Boundaries

- **Not examined:** Formal ISA models for Tier 2 Rust architectures (`riscv64gc`, `powerpc64`, `s390x`, `loongarch64`, `arm` 32-bit A32/T32, `wasm32`) are outside the scope of this Tier 1 (`x86_64`, `i386`, `aarch64`) comparison (RISC-V 64 models are covered in `sail-isa-models-lean-backend-and-rv64d-decoding-framing`).
- **Known not to apply:**
  - **Strata** (`10.1145/2908080.2908121`) cannot serve as a standalone ISA model for `rustc` verification because its synthesized formulas omit memory addressing modes, control-flow instructions, and IEEE-754 floating-point operations.
  - **CompCert's `x86/Asm.v` and `aarch64/Asm.v`** cannot be directly translated into a permissively licensed (`Apache-2.0 / MIT / BSD`) Lean 4 TCB without an commercial license from INRIA/AbsInt due to CompCert's dual INRIA Non-Commercial license on those files.
- **Unsupported in current `sail -lean` without partitioning:** Compiling the full `rems-project/sail-arm@7d0581642d0e3aaca367bbc5650aca7c53057543` (`arm-v9.4-a`) specification into a single monolithic `SailArm.lean` file produces 182,786 lines of Lean 4 that cannot be interactively elaborated within standard workstation memory ceilings without per-extension module splitting.
