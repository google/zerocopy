# R530 host-layout probe on May and September Rust nightlies

## Scope and outcome

The [published R530 source report](../rust-layout-rustc-nightly-2026-05-31/REPORT.md) (SHA-256 `a3eacb87198884ffa11be030ec07771f1884ab97cd56053dda4c1c2368b41488`) describes rustc's internal layout data and notes that it performed no layout execution. This supplement runs a [new, reconstructed fixture](fixture/layout.rs) on the local `aarch64-apple-darwin` host with the installed May 31 and September 30 nightly compilers. It is not a replay of preserved R530 fixture bytes: none were retained. The experiment records what public `std::mem` queries and rustc's unstable `-Zprint-type-sizes` text exposed for selected types.

For 12 printed size, alignment, offset, and dynamic-size lines, the executable output is **byte-identical** across the two versions. Among them, the default `repr(Rust)` `Reordered` struct is 16 bytes/alignment 8 with offsets `a=10`, `b=0`, `c=8`; the `repr(C)` control is 24 bytes/alignment 8 with declaration-order offsets `0,8,16`; `Option<&u8>` and `&u8` are each eight bytes; slice, string, and trait-object reference values are each 16 bytes on this host. The chosen unsized values report lengths/sizes of six bytes for a three-element `u16` slice, three for `str`, and four for the concrete trait-object referent. The [full output](raw/old/run.stdout) includes the union and data-carrying enum lines.

The compiler's `-Zprint-type-sizes` output is 98 lines in each version. The selected `Reordered`, `CControl`, `CUnion`, `Payload`, `Option<&u8>`, and `DynMetadata<dyn Trait>` type printouts are unchanged. The entire compiler printout has exactly **one differing line**: an internal unwind type is named `unwind::libunwind::_Unwind_Reason_Code` in May and `unwind::types::_Unwind_Reason_Code` in September; both lines print four bytes/alignment four. The two linked executables have different binary SHA-256 values, which does not imply a difference in the tested layout values. `-Zprint-type-sizes` reports compiler-selected layout text, not a stable language contract or the complete internal `LayoutData` object.

## Exact versions and method

The source report pins `rust-lang/rust@14210df0e27ccd7d9e6a05b8085cbd438e4bbc65`. The installed May 31 compiler instead reports commit `f8a08b688cbe60acc386ed1fbd1b7cbaaf5576b1`, `rustc 1.98.0-nightly`, executable SHA-256 `2ab7af1ea2ec5c69195fd8dfb0e1f91afdb7cc1e53127bba416616ce43a18dbc`. The September 30 compiler reports `5c543b0b8c73c7b72bc8284ced4fb22ead15734d`, `rustc 1.101.0-nightly`, executable SHA-256 `29f8ccc9aa7b0d8798eda854fa7f0e4ba3867c8c336b87d52dbb3b24b3f0878d`. Both are host `aarch64-apple-darwin`. This is a **toolchain-era comparison**, not execution of the source report's exact `14210df…` pin. [results.json](results.json) retains the full `rustc -Vv` strings, exact compiler argv, binary hashes, raw stream hashes, resource admission, and exits.

Each compiler ran `--crate-name layout_probe --edition 2024 -C opt-level=0 -Zprint-type-sizes -o <role>/layout-probe fixture/layout.rs`; each resulting executable ran once. All four admitted child processes exited 0. The first exploratory compile failed solely because the runner had not created its output directory, as its retained [stderr](preliminary/missing-output-directory/compile.stderr) says. The runner was corrected before the four reported cells; the preliminary failure is not counted as a compiler behavior result.

Before **each** compiler or executable child, [support/probe.py](support/probe.py) required >20% estimated reclaimable RAM (`vm_stat` free + inactive + speculative pages divided by physical RAM), >1 GiB free disk, and <100 MB owned package bytes. It capped child duration at 30 seconds and sampled RSS at 1 GiB. Minimum recorded admission was **24.2453%** RAM and **4,194,693,120 bytes** free disk; maximum owned bytes at admission were **968,401**, sampled child RSS **101,744 KiB**, and duration **0.583 s**. A sampled RSS of zero on a short child means it finished before a poll. All runs were serial, offline, and host-only; no dependency was downloaded or installed.

## Interpretation and limits

The result provides concrete evidence of unchanged selected host layout values for these two compiler binaries and this fixture. It does not establish that `repr(Rust)` field order or size is guaranteed across releases, targets, flags, or generic instantiations. It does not directly inspect `LayoutData` fields such as `largest_niche`, scalar validity ranges, backend representation, inhabitation, metadata typing inside rustc, or `FnAbi` pass modes. A two-target comparison requested in R530's Revalidation section remains unperformed because no matching non-host target standard library is installed. No `rustc_public`/rustc-private query executable for both versions was built; the later nightly does not have the local `rustc-dev` component. Those are explicit limits of this host-runtime supplement, not evidence that the internal source claims persisted unchanged.

The [raw compiler and executable outputs](raw/), [analysis.json](analysis.json), and [results.json](results.json) retain the evidence. `python3 -B support/check.py` verifies the exact fixture and recorded tool identities, all four command structures and output/binary hashes, gate arithmetic, selected layout values, and the one-line compiler-print delta offline and after relocation. `python3 -B support/probe.py` reruns the guarded local experiment against the installed binaries.
