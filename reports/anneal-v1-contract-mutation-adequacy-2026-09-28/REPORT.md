# Anneal V1 contract mutation and specification adequacy probe

## Summary

Retained Anneal V1 verified an impossible-precondition theorem whose postcondition is false on ordinary inputs, and it verified a function that always returns zero after the input/output equations were removed from its contract. These are logically valid proofs of the stated contracts, not evidence that the contracts adequately describe the intended `abs` behavior. With a satisfiable precondition, the false postcondition failed; when the original complete contract was attached to an identity function, Lean exposed the false obligations and verification failed. A successful `verify` exit therefore needs an independently reviewed precondition, postcondition, and attachment to the intended Rust item before it can support a behavioral claim.

This is executed evidence for #3725 recommendation R05, with additional negative-control evidence relevant to R03 and R10.

## Applicability

The experiment used the source-built retained Anneal V1 CLI at `google/zerocopy@bd0956be95c5f798f0c0484921b9b9d1fc6e9988` with Charon 0.1.210, Aeneas at `42c0e90dacf486f7d3ed5b6cde3a9a81f04915a4`, Lean 4.30.0-rc2, and the installed mathlib4 revision named in `REPORT.json`. The host was macOS aarch64; Cargo and rustc were the local 1.98.0 nightly toolchain. Each run used the same dependency-free Cargo binary package and one active Rust source file. This report is about proof statements generated by this V1 stack for these fixtures; it does not claim the same behavior for Anneal V2 or later toolchains.

The local toolchain view used the path-manifest adaptation described in `support/prepare-toolchain-mirror.py` and the earlier `anneal-v1-abs-end-to-end-fail-closed-controls-2026-09-28` report. That adaptation let the installed Aeneas package trees be reused without fetching or modifying their sources. It is a setup qualification for every result here.

## Findings

### Mutation outcomes

`support/observations.json` records the exact `verify` exit, input hash, generated specification hash, and output byte counts for each run. The retained Rust and generated Lean files are named in the table.

| Mutation | Exit | Decisive observation |
| --- | ---: | --- |
| Original `abs` contract and body (`baseline.rs`) | 0 | Generated `Post` contains nonnegativity and both positive/negative input equations. |
| Satisfiable original precondition; postcondition changed to `ret < 0` (`satisfiable_pre_false_post.rs`) | 1 | Lean rejects the false obligation; diagnostics include goals `0 < ↑x` and `↑ret < 0`. |
| `requires: False`; postcondition `ret < 0` (`false_precondition.rs`) | 0 | Generated `Pre` has field `h_anon : False`; both progress and postcondition branches close by eliminating that field. |
| Original body; negative-input equation and its proof removed (`omit_negative_equation.rs`) | 0 | Generated `Post` has `h0` and `h1`, but no `h2`. |
| Complete original contract attached to `identity(x) = x` (`wrong_attachment.rs`) | 1 | Aeneas emits `identity x := ok x`; Lean leaves false goals `x ≥ 0` and `↑x < 0 → ↑x = -↑x`. |
| Body changed to constant zero; only nonnegativity retained (`weak_relation_zero_body.rs`) | 0 | Aeneas emits `abs x := ok 0#i32`; the generated `Post` requires only `ret ≥ 0`. |

Basis: **execution** for exits, generated statements, Aeneas models, and diagnostics; **derived** for the interpretation of what these formulas permit. The false-precondition run does not prove `ret < 0` for any admissible input, because its `Pre x` includes `False` and therefore has no inhabitant. The original signed-minimum exclusion admits values such as `x = 0`; under that precondition the false-postcondition control failed. The constant-zero body satisfies nonnegativity but violates the deleted equation for `x = 1` and the negative-input equation for `x = -1`; both inputs satisfy the original precondition. This is a concrete specification adequacy gap, not a Lean kernel or solver defect.

### Attachment is represented in the generated theorem

The wrong-attachment specimen retains the baseline's precondition and all three postconditions, but places the annotation on `identity`. The generated `Pre`, `Post`, and theorem refer to `v1_abs_probe.identity`; the Aeneas `Funs.lean` model is `ok x`. After the proof script was adapted to the simpler model, the rejection was semantic: Lean could not prove nonnegativity for all admitted `x`, nor the negative-input equation. Thus this case confirms that V1's generated statement follows the annotated function in this fixture. It does not establish a general check that the annotated function is the human's intended one. If the contract is weakened enough, a different function can satisfy it, as the constant-zero case shows.

Basis: **execution** + **derived**. See `support/wrong_attachment.rs`, `support/wrong_attachment.generated.lean`, `support/wrong_attachment.Funs.lean`, and `support/wrong_attachment.stderr`.

## Boundaries

- This is a six-case mutation corpus around one scalar function. It is a discriminating example of precondition vacuity and weakened postconditions, not an estimate of how often they occur in real annotations.
- The positive exits establish that the configured V1 checker accepted the generated proof statements. The mutation runs did not separately query each theorem's Lean axiom dependencies or independently validate the Rust-to-LLBC-to-Lean semantic translation. The baseline theorem's separate axiom query is in the earlier V1 report.
- The `omit_negative_equation` case retains the original correct Rust body. Its positive exit establishes that the generated theorem omits the deleted clause; the constant-zero case demonstrates why such a missing relation matters.
- The wrong-attachment case was deliberately made semantically false under the full contract. It does not show that V1 detects a wrong attachment when the attached function happens to satisfy a weak contract.
- No human study, automated adequacy metric, or broad mutation search was performed. Whether a particular contract captures its author's intent requires an external specification or review.

## Evidence

On 2026-09-28, the CLI binary SHA-256 was `9f8283296b0150fbfe1043bbe3633879c900067915bb46aa293e55711564aee8`; the Charon and Aeneas binary hashes are in `REPORT.json`. Rustc was `1.98.0-nightly (f8a08b688 2026-05-30)`, and Lean reported commit `3dc1a088b6d2d8eafe25a7cd7ec7b58d731bd7cc`. The source fixture descends from `google/zerocopy@bd0956be95c5f798f0c0484921b9b9d1fc6e9988:anneal/v1/examples/abs.rs` and is preserved here with every mutation.

For each case, `src/main.rs` was replaced by the named `support/*.rs` file in the same package, then the source-built CLI ran `cargo-anneal verify --manifest-path Cargo.toml`. The environment set `ANNEAL_TOOLCHAIN_DIR` to the local path-manifest mirror, `CHARON_TOOLCHAIN_IS_IN_PATH=1`, and placed the matching nightly Rust, Lean, Charon, and Aeneas binaries on `PATH`. `support/Cargo.toml` and `support/Cargo.lock` preserve the package input. The generated `*.generated.lean` files preserve the actual proof statements; the two changed Aeneas functional models are preserved as `*.Funs.lean`. All stdout files were empty; stderr was retained after replacing the one local workspace prefix with `$WORKSPACE`. `support/observations.json` records the pre-redaction stderr byte counts and hashes of the preserved source and generated specifications. The path substitution changes the retained diagnostic byte hashes but not its goal text.

The failure controls are especially useful to inspect directly: `support/satisfiable_pre_false_post.stderr` and `support/wrong_attachment.stderr` contain Lean proof failures. The false-precondition run produced empty stdout and stderr; its generated Lean file records the elimination of `False`. Successful baseline and omission runs produced Lean tactic-linter warnings, while the constant-zero run produced only an unused-Rust-variable warning.

## Revalidation

Use the retained source-built V1 CLI and matching toolchain, or rebuild the CLI from the identified V1 revision. If the installed Lake manifest uses Git package entries that V1 rejects, make a disposable local-path view using `support/prepare-toolchain-mirror.py` and already installed package trees. In one clean Cargo package, replace `src/main.rs` with each preserved Rust specimen and run `cargo-anneal verify --manifest-path Cargo.toml`. Inspect the newly generated `Pre` and `Post` fields, the function named by the theorem, and the exit status. The shortest discriminating pair is `satisfiable_pre_false_post.rs` (expected failure) versus `false_precondition.rs` (expected success); the strongest adequacy counterexample is `weak_relation_zero_body.rs` (expected success with a body that violates the original input/output equations).
