# Lake Concurrent Shared-Tree Writers, Package-Local Interruption, and Cross-Version Read-Only Consumer Ownership

## Summary

Across Lean and Lake `v4.29.0`, `v4.30.0-rc2`, `v4.31.0`, and `v4.34.1` (paired with Aeneas `nightly-2026.06.03`), source analysis and six empirical execution suites establish the concurrency, interruption, and cross-version ownership boundaries for Lake package build trees:

1. **Conflicting concurrent writers in a shared writable package tree vs. isolated trees (`v4.30.0-rc2`)**: When two Lake processes concurrently compiled `Dep.lean` in a single shared writable package tree while the source changed from `depValue := 7` (read by Writer A) to `depValue := 9` (read by Writer B), killing newer Writer B allowed older Writer A to exit 0 and publish a stale `7` `.olean` (`17bae46ced2944349a85c534f3e6240dc96b89da2569fe358620932df0c8f89c`) at the `9` source path. Consequently, a surviving writer's `exit 0` in a shared mutable tree does not certify current source bytes, though a subsequent `lake --no-build build Dep` rejected the stale artifact (`exit 3`, writing `Dep.trace.nobuild`) and an ordinary retry repaired it to `9` (`d934a89791cbb4236eca9f88c4e3f5d7136c47c8f3aecc965f476df32f69b15c`). In matched isolated package trees, each survivor remained up to date (`--no-build` `exit 0`) for its own source generation.
2. **Package-local `.olean` write interruption and repair (`v4.30.0-rc2`)**: Imposing a child-inherited file-size limit (`RLIMIT_FSIZE=2,308`, half of the 4,616-byte baseline `Dep.olean`) during a package-local rebuild from `depValue := 7` to `9` caused Lean to exit with code `153` (`128 + 25`, `SIGXFSZ`) and Lake to exit 1. The old final `Dep.olean` was unlinked before a 2,308-byte partial temporary file (`Dep.olean.tmp.13182`, SHA-256 `7e1d8d579e75d02a1861874190a82afbe13ae8effab532d8128eabe1fee94995`) remained alongside the old `.trace` and `.olean.hash` sidecar. Both `lake --no-build build Dep` (`exit 3`) and direct Lean import (`exit 1`) rejected the incomplete state; an uncapped `lake build Dep` wrote the 4,520-byte value-9 `Dep.olean` (`fe893ce3c24d2c295ade06017eb859638f0e75aa29df7e9444f3026bfd7a7745`) while leaving the orphan `.tmp.13182` file untouched.
3. **Cross-version locking and read-only dependency ownership (`v4.30.0-rc2` vs. `v4.31.0` and `v4.34.1`)**: Across `v4.30.0-rc2`, `v4.31.0`, and `v4.34.1`, Lake's `src/lake/Lake/Build/Run.lean` and `src/lake/Lake/Load/Workspace.lean` acquire `.lake/build/lake.lock` around top-level `lake build` runs, whereas `lake setup-file` (`src/lake/Lake/CLI/Main.lean`) evaluates module setup without acquiring the top-level build lock. However, package configuration ownership changed after `v4.30.0-rc2`: against a prebuilt read-only path dependency, a fresh manifest-absent consumer in `v4.30.0-rc2` failed `lake build`, `lake setup-file`, and `lake serve` (`exit 1` / plain `lean --server` fallback) because Lake attempted to create `producer/.lake/config/probe_dep/lakefile.olean.lock` inside the read-only dependency. Under `v4.34.1`, the identical manifest-absent consumer succeeded across `lake build`, `lake setup-file`, and live `lake serve` (`didOpen` publishing diagnostic `7`) with zero writes to the read-only dependency, eliminating the `v4.30.0-rc2` pre-seeded manifest workaround for that layout. In addition, `v4.34.1` `setup-file` JSON wraps `importArts` entries in one extra array level compared to `v4.30.0-rc2` and exhibited ~50 MiB higher process-group RSS on a three-module canary (`1,096,880 KiB` vs. `1,046,032 KiB`, crossing a strict 1 GiB guard).

**Shared behavior vs. version deltas**:
- **Shared across `v4.30.0-rc2`, `v4.31.0`, and `v4.34.1`**: Top-level `lake build` acquires `.lake/build/lake.lock` (`src/lake/Lake/Build/Run.lean`, `src/lake/Lake/Load/Workspace.lean`), whereas `lake setup-file` (`src/lake/Lake/CLI/Main.lean`) loads the workspace and computes module setup without acquiring `.lake/build/lake.lock`. Pre-seeded relative consumer manifests work against read-only prebuilt path dependencies in both `v4.30.0-rc2` and `v4.34.1`.
- **Version deltas (`v4.29.0`/`v4.30.0-rc2` vs. `v4.31.0`/`v4.34.1`)**: In `v4.29.0` and `v4.30.0-rc2`, an unseeded consumer without `lake-manifest.json` attempts to lock and write `.lake/config/<dep>/lakefile.olean.lock` inside the dependency's directory, failing on read-only dependencies. Starting in `v4.31.0` and verified by execution on `v4.34.1`, fresh manifest-absent consumers build, run `setup-file`, and serve live LSP diagnostics against a read-only dependency without writing to the dependency directory. Furthermore, `v4.34.1` adds one outer array nesting level to `importArts.<Module>` in `lake setup-file` JSON output and exhibits a slightly higher RSS footprint (~1,097 MiB vs. ~1,046 MiB on a three-module build).

## Findings

### Conflicting Writers in a Shared Writable Package Tree vs. Isolated Trees (`v4.30.0-rc2`)

In `support/lake-shared-tree-conflicting-writers/probe.py` (with `LAKE_ARTIFACT_CACHE=false`, `LEAN_NUM_THREADS=1`, and a 4,400,000 KiB sampled summed-RSS guard; observed peak 3,643,280 KiB), two Lake processes entered real Lean `run_cmd` gates while building the same `Dep.lean` and `.lake` output tree. Writer A read `depValue := 7` and wrote `A.entered`; the harness then rewrote `Dep.lean` to `depValue := 9` before launching Writer B, waited for `B.entered`, killed one writer's process group, and released the survivor:

| Killed Writer | Surviving Build | Immediate `lake --no-build build Dep` | Fresh Direct Lean Before Retry | Ordinary Retry and Fresh Lean Afterward |
| --- | --- | --- | --- | --- |
| Writer A (`old 7`) | Writer B exited 0 | Exit 0 (up to date) | `9` accepted; `7` rejected | `9` accepted; `7` rejected |
| Writer B (`new 9`) | Writer A exited 0 | Exit 3 (out of date) | Old `7` accepted; current `9` rejected | `9` accepted; `7` rejected |

In `support/matched-lake-writer-isolation/probe.py` (admitted at 42% free memory, gate-period sampled summed process-tree RSS maxima 3,614,416 to 3,642,960 KiB under a 4,000,000 KiB guard), four matched two-writer cells directly contrasted one shared writable package/build tree against two isolated package/build trees (after priming configuration and removing `.lake/build`):

| Topology; Killed Writer | Survivor Exit and Published `Dep.olean` Value (SHA-256) | Immediate `--no-build build Dep` | Fresh Direct Lean Proof Controls |
| --- | --- | --- | --- |
| Shared; kill A (`old 7`) | Writer B exits 0; value `9` (`d934a89791cbb4236eca9f88c4e3f5d7136c47c8f3aecc965f476df32f69b15c`) | Exit 0 (up to date) | `9` succeeds; `7` fails |
| Isolated; kill A (`old 7`) | Writer B exits 0; value `9` (`d934a89791cbb4236eca9f88c4e3f5d7136c47c8f3aecc965f476df32f69b15c`) | Exit 0 (up to date) | `9` succeeds; `7` fails |
| Shared; kill B (`new 9`) | Writer A exits 0; value `7` (`17bae46ced2944349a85c534f3e6240dc96b89da2569fe358620932df0c8f89c`) | Exit 3 (out of date; writes `Dep.trace.nobuild`) | `7` succeeds; `9` fails |
| Isolated; kill B (`new 9`) | Writer A exits 0; value `7` (`17bae46ced2944349a85c534f3e6240dc96b89da2569fe358620932df0c8f89c`) | Exit 0 (up to date for A's unchanged `7` root) | `7` succeeds; `9` fails |

When Writer B (`new 9`) was killed in the shared tree, Writer A exited 0 and wrote the `7` `.olean` at the pathname whose source already contained `9`. Lake's subsequent `--no-build` check caught the mismatch (`exit 3`), demonstrating that while Lake's trace hash detects the stale artifact afterward, a writer process's `exit 0` in a shared mutable directory does not attest current source bytes. Basis: **execution** (`support/lake-shared-tree-conflicting-writers/results.json`, `support/lake-shared-tree-conflicting-writers/results-kill-B.json`, `support/matched-lake-writer-isolation/results.json`).

### Interrupted Package-Local `.olean` Write and Uncapped Repair (`v4.30.0-rc2`)

In `support/package-local-interrupted-olean/probe.py` (admitted at 30.95% and 30.98% reclaimable RAM, minimum runtime reclaimable RAM 29.90%, maximum summed group RSS 996,976 KiB under a 1.2 GiB cap, `LAKE_ARTIFACT_CACHE=false`), a valid package-local build of `depValue := 7` produced a 4,616-byte `Dep.olean`. Editing `Dep.lean` to `depValue := 9` and rebuilding under a child-inherited `RLIMIT_FSIZE=2,308` byte limit (verified separately by a Python child write of 3,332 bytes failing with `File too large` at 2,308 bytes) interrupted Lean's package-local `.olean` write:

| Sequence Point | Package-Local Output and Process Result | Fresh Consumer / Loader Verification |
| --- | --- | --- |
| Old valid (`depValue := 7`) | `Dep.olean`: 4,616 bytes (SHA-256 `cebebbbc892381bd3920a0b12ab5e4d65f1804574357994ccb20f95f87f98f9b`); old `Dep.trace` and 16-byte `Dep.olean.hash` retained. | Baseline `lake build Dep` exited 0. |
| Limited value-9 update (`RLIMIT_FSIZE=2,308`) | Lake exited 1 (`Lean exited with code 153`, `128 + 25` `SIGXFSZ`). Final `Dep.olean` was removed; `Dep.olean.tmp.13182` remained at 2,308 bytes (SHA-256 `7e1d8d579e75d02a1861874190a82afbe13ae8effab532d8128eabe1fee94995`); old `Dep.trace` and `Dep.olean.hash` kept their old hashes. | `lake --no-build build Dep` exited 3 (out of date); fresh direct Lean import exited 1 (missing `Dep` module). |
| Uncapped repair (`depValue := 9`) | `lake build Dep` exited 0 and wrote a 4,520-byte value-9 `Dep.olean` (SHA-256 `fe893ce3c24d2c295ade06017eb859638f0e75aa29df7e9444f3026bfd7a7745`); `Dep.trace` and `Dep.olean.hash` updated; orphan `Dep.olean.tmp.13182` remained byte-identical. | `lake --no-build build Dep` exited 0; fresh direct Lean `#eval depValue` exited 0 and returned `9`. |

Because Lean unlinked the old final `Dep.olean` and wrote into `Dep.olean.tmp.<PID>` before renaming on completion, interrupting the write left the final `.olean` absent rather than exposing a half-written file at `Dep.olean`. Basis: **execution** (`support/package-local-interrupted-olean/results.json`).

### Cross-Version Locking Architecture and Read-Only Consumer Ownership (`v4.29.0`–`v4.34.1`)

An initial local toolchain inventory on 2026-09-29 (`support/installed-lean-lake-inventory/inventory.json`) recorded the bundled Elan `v4.29.0` and `v4.30.0-rc2` toolchains, a matching `/nix/store` `v4.30.0-rc2` toolchain (`wf1mr6pak9n88v5bwm6y749d8k19r0mw-lean-toolchain-aarch64-darwin-4.30.0-rc2`), and the Aeneas `nightly-2026.06.03` `backends/lean/lean-toolchain` pin (`leanprover/lean4:v4.30.0-rc2`).

Source comparison across `v4.30.0-rc2` (`3dc1a088b6d2`), `v4.31.0` (`68218e876d2a`), and `v4.34.1` (`5045d0056413`) established two structural invariants:
1. **Top-level build lock vs. lockless `setup-file`**: In `src/lake/Lake/Build/Run.lean` and `src/lake/Lake/Load/Workspace.lean`, Lake acquires `.lake/build/lake.lock` around top-level `lake build` invocations, whereas `lake setup-file` (`src/lake/Lake/CLI/Main.lean`) loads the workspace and evaluates module setup without acquiring `.lake/build/lake.lock`. This asymmetry is unchanged across `v4.30.0-rc2`, `v4.31.0`, and `v4.34.1`.
2. **Dependency configuration lock elimination after `v4.30.0-rc2`**: Executing the same seven-cell read-only producer matrix on `v4.30.0-rc2` (`Lake 5.0.0-src+3dc1a08`) and `v4.34.1` (`Lake 5.0.0-src+5045d00`) under a 2 GiB process-group RSS cap (observed max ~1,021 MiB for batch and ~1,015 MiB for live servers, minimum `memory_pressure` free 43%, minimum free disk 17,601,011,712 bytes) in `support/lake-readonly-consumer-server-430rc2-to-4341/` demonstrated:

| Operation Against Read-Only Prebuilt Producer | Lake `v4.30.0-rc2` (`3dc1a088b6d2`) | Lake `v4.34.1` (`5045d0056413`) |
| --- | --- | --- |
| Fresh consumer, pre-seeded relative manifest: `--keep-toolchain --no-cache --old --no-build build Dep` | Exit 0 (up to date) | Exit 0 (up to date) |
| Same pre-seeded consumer: `--keep-toolchain --no-cache --old build Generated` | Exit 0 (evaluates `7`) | Exit 0 (evaluates `7`) |
| Same pre-seeded consumer: `--keep-toolchain --no-cache setup-file Generated.lean` and `env lean --json Generated.lean` | Exit 0 (resolves `Dep.olean`; JSON value `7`) | Exit 0 (resolves `Dep.olean` with one extra outer array level in `importArts.Dep`; JSON value `7`) |
| Independent manifest-absent `fresh-build-first`: `--keep-toolchain --no-cache --old build Generated` | Exit 1 (`producer/.lake/config/probe_dep/lakefile.olean.lock`: permission denied) | Exit 0 (evaluates `7`; creates manifest in consumer directory) |
| Independent manifest-absent `fresh-unseeded`: `--keep-toolchain --no-cache setup-file Generated.lean` | Exit 1 (same dependency config lock permission denied) | Exit 0 (resolves `Dep.olean`; creates manifest in consumer directory) |
| Pre-seeded live `lake --keep-toolchain --no-cache serve` (`initialize` and `didOpen`) | Published diagnostic `7` | Published diagnostic `7` |
| Independent manifest-absent live `lake serve` (`initialize` and `didOpen`) | Workspace configuration error and plain `lean --server` fallback; no `7` | Published diagnostic `7` |

In both `v4.30.0-rc2` (25 producer files) and `v4.34.1` (22 producer files), the read-only producer's complete path, SHA-256, mode, and `mtime` snapshot (`snap-*-before.json` vs. `snap-*-final.json`) was 100% unchanged across all batch and server operations. Basis: **source + execution** (`support/installed-lean-lake-inventory/inventory.json`, `support/lake-readonly-consumer-server-430rc2-to-4341/runs.jsonl`, `support/lake-readonly-consumer-server-430rc2-to-4341/identity.json`).

### Cross-Version `.olean` Invalidation Canary and Process-Group RSS Boundary (`v4.30.0-rc2` vs. `v4.34.1`)

In `support/lake-invalidation-canary-resource-stop/canary.py`, a three-module fixture (path dependency `Dep` and consumer modules `Core` and `Main` via `lake --no-cache -v build Core Main`) was run under a strict **1 GiB (`1,048,576 KiB`)** process-group RSS cap, `>20%` reclaimable RAM gate, and `>10 GiB` free disk gate:

| Toolchain Version | Admission Free RAM / Free Disk | Command Execution Result | Sampled Peak Process-Group RSS | Workspace File Growth and Outputs |
| --- | --- | --- | ---: | --- |
| `v4.30.0-rc2` (toolchain ~2.5 GiB) | 24.9760% / 19,377,070,080 B | Exit `0` in 1.423 s (7 Lake jobs) | `1,046,032 KiB` (2,544 KiB below 1 GiB cap) | `324 -> 248,671` bytes; produced `.olean`, `.ilean`, and `.trace` for `Dep`, `Core`, and `Main` |
| `v4.34.1` (toolchain ~2.7 GiB) | 24.2571% / 19,375,308,800 B | Exit `-9` after 3.838 s (killed by 1 GiB RSS guard) | `1,096,880 KiB` (exceeded 1 GiB cap by 48,304 KiB) | `324 -> 222,074` bytes; wrote package configuration outputs only (no module `.olean`, `.ilean`, or `.trace`) |

An excluded preliminary setup run on `v4.30.0-rc2` without `lean_lib Core` in `lakefile.lean` (`support/lake-invalidation-canary-resource-stop/preliminary/old-unregistered-core/`) exited 1 with `unknown module prefix 'Core'` at 749,872 KiB RSS before the fixture was corrected. The `v4.34.1` termination is a resource-cap enforcement observation (~50.8 MiB higher sampled RSS than `v4.30.0-rc2` on the same three-module build), not a compiler bug. Basis: **execution** (`support/lake-invalidation-canary-resource-stop/analysis.json`, `support/lake-invalidation-canary-resource-stop/raw/`).

## Boundaries

- **Surviving writer `exit 0` in shared writable directories (`known not to apply`)**: A writer process that read an older source revision before an overlapping edit can finish after the newer writer is killed and overwrite `.olean` and `.trace` outputs with stale bytes while exiting 0. Shared writable package build trees therefore cannot rely on process exit status alone for current-source verification.
- **Orphan temporary files after interrupted package-local builds (`known not to apply` for automatic cleanup)**: After `SIGXFSZ` interrupted Lean's write to `Dep.olean.tmp.13182`, a subsequent uncapped `lake build Dep` succeeded and wrote the new `Dep.olean` via a fresh PID-suffixed temporary file without deleting the orphaned `Dep.olean.tmp.13182`.
- **Full `v4.34.1` invalidation matrix under a 1 GiB RSS cap (`not examined`)**: Because `v4.34.1` exceeded the 1,048,576 KiB process-group RSS cap during the initial three-module canary (`1,096,880 KiB`), subsequent invalidation perturbations (CRLF normalization, `leanOptions`, `moreLeanArgs`, `weakLeanArgs`, and `--old` mode on `v4.34.1`) were **not examined** in that run and require a higher RSS budget (such as the 2 GiB cap used in `support/lake-readonly-consumer-server-430rc2-to-4341/`).
- **Full Mathlib/Aeneas archive migration to `v4.34.1` (`not examined`)**: While `v4.34.1` removed the read-only dependency config-lock failure on the two-package path-dependency fixture, Aeneas `nightly-2026.06.03` pins `v4.30.0-rc2`, and full Aeneas/Mathlib archive compatibility with `v4.34.1` was **not examined**.
