# Fuchsia Zircon Channel Handle Linearity, vDSO PC-Origin Syscall Enforcement, and Multi-Tenant Reactor Invariants

## Summary

Formally verifying userspace components and inter-process communication (IPC) protocols on Fuchsia's Zircon microkernel requires exact alignment with Zircon's Rust kernel syscall and handle-table semantics (`zircon/kernel/lib/syscalls/`, `zircon/kernel/object/`):

1. **`zx_channel_write` and `zx_channel_write_etc` consume non-duplicate payload handles across early validation and user-copy failures via `zr::defer`.** In `prepare_write` (`zircon/kernel/lib/syscalls/channel.rs:286-334`), a `zr::defer` guard invokes `remove_user_handles` in 64-handle chunks (`ZX_CHANNEL_MAX_MSG_HANDLES`) on *every* pre-transfer error—including invalid `options`, bad or unwritable destination `channel` handles, `OUT_OF_RANGE` `num_bytes > 65536` or `num_handles > 64`, and unreadable `bytes` buffers—stopping early only when `copy_slice_from_user` on the `handles` array itself faults. In `zx_channel_write_etc` (`zircon/kernel/object/user_handles.rs:266-290, 434-438, 470-473`), every entry with `operation != ZX_HANDLE_OP_DUPLICATE` (including invalid opcodes) removes its source handle, and disposition `result` fields are copied back to userspace **only** when `result.is_err()`.
2. **`zx_channel_read` and `zx_channel_read_etc` are atomic only on `BUFFER_TOO_SMALL`, not on output-pointer faults.** When a queued message exceeds `num_bytes` or `num_handles` without `ZX_CHANNEL_READ_MAY_DISCARD`, `ChannelDispatcher::read` (`zircon/kernel/object/channel_dispatcher.rs:401-405`) leaves the message queued. Once size checks pass (`line 406`), `pop_front()` dequeues `msg` *before* writing `actual_bytes`, `actual_handles`, `bytes`, and `handles` (`channel.rs:155-176, 228-236`); if any user write fails, `finish_get_handles` (`user_handles.rs:123`) is skipped and `MessagePacket::drop` destroys the message and closes all attached handles.
3. **vDSO PC-origin validation and `ZX_POL_BAD_HANDLE` turn double-closes and raw `svc` traps into fatal policy exceptions.** Normal-mode non-`@vdsocall` syscalls verify `valid_pc((pc as usize).wrapping_sub(vdso_code_address))` (`zircon/kernel/lib/syscalls/syscalls.rs:207-240`), signaling `ZX_EXCP_POLICY_CODE_BAD_SYSCALL` if entered outside the mapped vDSO return offset. `HandleTable::lookup_handle_locked_internal` (`zircon/kernel/object/handle_table.rs:326-346`) enforces `(value & 0b11) == 0b11`, per-process `random_value` XOR unscrambling, 12-bit arena generation matching, and `ZX_POL_BAD_HANDLE` on lookup failure (`ZX_HANDLE_INVALID = 0` is skipped only in `sys_handle_close` and `remove_handles`, not in `get_dispatcher*` or `put_handles_from_user`). Consequently, a caller that closes payload handles in its error branch after a failed `zx_channel_write` triggers a fatal `ZX_EXCP_POLICY_CODE_BAD_HANDLE` exception or closes a recycled slot.
4. **Compositional multi-component and single-process reactor models fail under three specification pitfalls unless `ObjId` ownership, handle tables, and port-slot quotas are partitioned.** Encoding two processes' kernel objects via `2 * id` / `2 * id + 1` and projecting/writing back via `id / 2` silently rebinds cross-channel transferred handles onto the receiver's private object `2 * id + 1`; flat `nextHandle + 1` cursors deadlock universal handle-ownership premises; and sharing an unpartitioned `MAX_SLOTS` port-reactor array breaks 2-run tenant non-interference under slot-exhaustion floods, whereas static per-tenant slot quotas preserve chronological trace equivalence (`support/ZirconHandleAndReactorInvariants.lean`, 0 axioms in `leanprover/lean4@v4.34.1`).

## Findings

### 1. Exact Error-Path Handle Consumption in `zx_channel_write` and `zx_channel_write_etc`

Basis: normative + source + derived

Normative vDSO documentation in `zircon/vdso/channel.fidl:380-382` states for `zx_channel_write`: *"All handles are discarded and no longer available to the caller, on success or failure."* Direct inspection of `zircon/kernel/lib/syscalls/channel.rs:286-367` and `zircon/kernel/object/user_handles.rs:246-475` establishes the exact operational ordering across failure modes:

| Failure Condition | Location (`fuchsia@273f473fa9ac`) | Return `Status` | Handle-Table Effect | User Memory Effect |
| :--- | :--- | :--- | :--- | :--- |
| `(options & !USE_IOVEC) != 0` | `channel.rs:297-305` | `INVALID_ARGS` | `zr::defer` removes readable `handles` in 64-entry chunks (`!= OP_DUPLICATE`) | None |
| Bad / wrong-type / unwritable `handle` | `channel.rs:308-309` | `BAD_HANDLE` / `WRONG_TYPE` / `ACCESS_DENIED` | `zr::defer` removes readable `handles` in 64-entry chunks (`!= OP_DUPLICATE`) | None |
| `num_bytes > 65536` or `num_handles > 64` | `message_packet.rs:306-310` | `OUT_OF_RANGE` | `zr::defer` loops over all `num_handles` in 64-entry chunks (`user_handles.rs:370-383, 421-445`) until end or user-copy fault | None |
| Unreadable `bytes` (or `iovec`) | `channel.rs:311-319` | `INVALID_ARGS` | `zr::defer` removes readable `handles` in 64-entry chunks (`!= OP_DUPLICATE`) | None |
| Unreadable `handles` at chunk $k$ | `user_handles.rs:311, 377, 425` | `INVALID_ARGS` | `put_handles_from_user` (`num_handles <= 64`) removes **0** handles (`owns_handles = false`); `zr::defer` (`num_handles > 64`) removes chunks $0..k-1$ and stops at chunk $k$ | None |
| Invalid `disp.operation` (`write_etc`) | `user_handles.rs:286-289, 434-438` | `INVALID_ARGS` (or `BAD_HANDLE` if `disp.handle` invalid) | **Removes and closes `disp.handle`** (`!= ZX_HANDLE_OP_DUPLICATE`), latches first error across all entries | Copies updated `result` array to user (`line 471`) |
| Missing `TRANSFER`, self-transfer (`h == chan`), wrong `type_`, escalated `rights` | `user_handles.rs:163-185, 319-334` | `ACCESS_DENIED` / `NOT_SUPPORTED` / `WRONG_TYPE` / `INVALID_ARGS` | All `OP_MOVE` & invalid-op source handles removed; temporary `OP_DUPLICATE` copies dropped by `MessagePacket::drop`; `OP_DUPLICATE` source handles remain open | Copies updated `result` array (`write_etc` only) |
| `write_etc` disposition copy-out fault when `result.is_err()` | `user_handles.rs:470-472` | `INVALID_ARGS` (overrides latched disposition error) | `msg` already has `owns_handles = true` (`line 336`); `MessagePacket::drop` closes all moved handles and frees temporary duplicates | Page-straddling prefix may be partially written |
| `channel.write` fails (`PEER_CLOSED`) | `channel.rs:366` | `PEER_CLOSED` | All `OP_MOVE` handles closed when `msg` drops; `write_etc` does **not** copy `dispositions` back (`result.is_ok()` at `line 470`) | None (`handles` may even reside in read-only memory on `ZX_OK`/`PEER_CLOSED`) |

Two verification consequences follow directly:

1. **Pre-checking `canRead bytesPtr` before consuming `handles` is unsound against Zircon.** A syscall specification that returns `(ZX_ERR_INVALID_ARGS, k)` unchanged when `bytes` is null or unreadable (`num_bytes > 0`) disagrees with `prepare_write`'s `zr::defer` whenever `num_handles > 0` and `handles` is readable.
2. **Linear capability transfer at the call boundary prevents `ZX_POL_BAD_HANDLE` double-close traps.** In an ownership type system or separation logic (`HandleOwn h obj rights`), `zx_channel_write` must consume `∗_{h ∈ hs} HandleOwn h _ _` in its **precondition** and return `emp` on *both* `ZX_OK` and every error status (provided `handles` is readable in `Memory`), statically forbidding caller error-branch `zx_handle_close(h)` calls.

### 2. Non-Atomic User Copy-Out Ordering in `zx_channel_read` and `zx_channel_read_etc`

Basis: source + derived

In `zircon/kernel/lib/syscalls/channel.rs:155-176, 200-236` and `zircon/kernel/object/channel_dispatcher.rs:401-419`:

1. **Pre-dequeue size check (`BUFFER_TOO_SMALL`):** If `*msg_size > max_size || *msg_handle_count > max_handle_count` and `(options & ZX_CHANNEL_READ_MAY_DISCARD) == 0`, `ChannelDispatcher::read` (`channel_dispatcher.rs:402-404`) returns `Err(Status::BUFFER_TOO_SMALL)` *without* popping `messages`. Subsequent faults in `actual_bytes.write` (`channel.rs:229`) or `actual_handles.write` (`line 232`) leave the message queued (though `*actual_bytes` remains modified in user memory if only `actual_handles.write` faults).
2. **Post-dequeue copy-out (`!too_small`):** Once the buffer sizes suffice, `messages.as_mut().pop_front()` (`channel_dispatcher.rs:406`) dequeues `msg` (`owns_handles = true`) and updates channel signals **before** any user-pointer write. User writes then execute in strict order:
   $$\texttt{actual\_bytes.write} \;\to\; \texttt{actual\_handles.write} \;\to\; \texttt{msg.copy\_data\_to(bytes)} \;\to\; \texttt{user\_out.copy\_slice\_to\_user(hvs)} \;\to\; \texttt{finish\_get\_handles}$$
   If any of the four user writes faults (`Err(Status::INVALID_ARGS)`), `finish_get_handles` (`user_handles.rs:123`) never runs, so zero handles enter `proc`'s handle table, and `MessagePacket::drop` (`message_packet.rs:416-437`) permanently destroys the dequeued message and closes its attached handles. Formal models that roll back `kernel := k` on output-pointer faults misstate both channel queue contents and peer `PEER_CLOSED` observations when output buffers may be unmapped or overlapping.

### 3. vDSO PC-Origin Validation, `VDsoMutator` Symbol Blocking, and `HandleTable` Scrambling

Basis: source + derived

Zircon enforces capability and syscall integrity across three coupled mechanisms:

1. **Per-syscall vDSO return-PC check (`syscalls.rs:115-119, 207-240`, `vdso.rs:257-266`):** Zither (`zircon/tools/zither/backends/kernel/templates/kernel_wrappers.rs.tmpl:54, 66-71, 137-143`) wraps every non-`@vdsocall` syscall in `do_syscall(ZX_SYS_<NAME>, pc, ValidSyscallPC::<name>, ...)`. On AArch64, `pc` is `elr_el1` (the instruction immediately following `svc #0`). `do_syscall` rejects any call where `pc.wrapping_sub(vdso_code_address)` does not match one of that specific syscall's compiled `VDSO_CODE_SYSRET_zx_<name>_VIA_<caller> - VDSO_CODE_START` offsets, invoking `sys_invalid_syscall` (`ZX_EXCP_POLICY_CODE_BAD_SYSCALL` + `Status::BAD_SYSCALL`). Two architectural exceptions exist:
   - In Restricted Mode (`zircon/kernel/arch/arm64/exceptions.S:840-841, 867`), EL0 `svc` when `PERCPU_IN_RESTRICTED_MODE != 0` branches directly to `syscall_from_restricted` (exiting restricted mode to normal mode) prior to `arm64_syscall_dispatcher`'s `wrapper_<syscall>` table.
   - `@vdsocall` functions (`zx_ticks_get`, `zx_clock_get_monotonic` fast paths) execute purely in usermode without `svc`.
2. **`VDsoMutator::block_symbol` 64-bit `ElfSym` layout quirk (`zircon/kernel/lib/userabi/vdso.rs:300-306, 352-374`):** When creating restricted/variant vDSOs, `VDsoMutator` overwrites blocked function bodies with `TRAP_FILL` (`0xd4200020`, `brk #1` on AArch64) and masks `.dynsym` entries via `sym.info &= 0xf` (`STB_LOCAL = 0`). Notably, `vdso.rs:302-306` defines `struct ElfSym { info: usize, value: usize, size: usize }` (`24` bytes on 64-bit), where `info: usize` overlays bytes `0..8` of `Elf64_Sym` (`st_name: u32`, `st_info: u8`, `st_other: u8`, `st_shndx: u16`). On little-endian 64-bit targets, `sym.info &= 0xf` zeroes `st_name[31:4]`, clears `st_info` (`byte 4`), *and* zeroes `st_shndx` (`bytes 6..8`, turning the symbol into `SHN_UNDEF`)! A standalone ELF64 `.dynsym` resolver must still check `(st_info >> 4) != STB_LOCAL` (`0`) as well as `st_shndx != SHN_UNDEF` so genuine local `.dynsym` symbols are never resolved as callable entrypoints.
3. **`HandleValue` bit invariants and `ZX_POL_BAD_HANDLE` scope (`zircon/kernel/object/handle_table.rs:35-55, 273-280, 326-375, 585-619`, `handle.rs:23, 53-55, 534-545`, `handle_ops.rs:26-28`):**
   - Live handles satisfy `(value & HANDLE_MUST_BE_ONE_MASK) == 0b11` (`HANDLE_RESERVED_BITS = 2`), XOR-masked by per-process `random_value` (which has its low 2 bits cleared) and carrying an arena index plus a **12-bit generation counter** (wrapping after 4,096 reuses of the same arena slot).
   - `ZX_HANDLE_INVALID` (`0`) is skipped *before* lookup only in `sys_handle_close(0)` (`handle_ops.rs:26-28`) and `HandleTable::remove_handles` (`handle_table.rs:610-612`). Passing `0` to `zx_channel_read`, `zx_object_wait_one`, or inside `zx_channel_write`'s `put_handles_from_user` (`user_handles.rs:238, 268, 278, 287`), or passing **any non-zero closed/forged handle** to `sys_handle_close` or `remove_handles` (`handle_table.rs:613`), passes `caller = Some(proc)` to `lookup_handle_locked_internal` and invokes `proc.enforce_basic_policy(ZX_POL_BAD_HANDLE)` (`process_dispatcher.rs:1838-1860`).

### 4. Multi-Process Quotient Hazards and Quota-Partitioned Reactor Non-Interference

Basis: execution + derived

When formalizing multi-component Fuchsia systems and single-threaded `zx_port_wait` + `zx_object_wait_async` event loops in constructive `Type 0` Lean 4 (`support/ZirconHandleAndReactorInvariants.lean`), four structural invariants govern soundness:

1. **Cross-channel handle transfer forbids lossy `ObjId` parity quotients.** Modeling two processes in a shared `KernelState` by mapping Process 1 local IDs to `2 * id` and Process 2 local IDs to `2 * id + 1` while projecting local views via `decodeSharedObj(sharedId) = sharedId / 2` breaks on cross-channel handle transfer: an in-flight handle to Process 1's object `2 * id` queued in Process 2's endpoint projects to `id` (`(2 * id) / 2 = id`) and is written back by Process 2's slice update as `2 * id + 1` (`even_odd_quotient_rebinds_transferred_handle`), forging a capability to Process 2's private object! Sound multi-process models keep `ObjId` globally unique (never quotiented on projection) and store per-process `HandleTable : ProcId → List HandleEntry` maps rather than a single flat handle list with `nextHandle + 1` cursors (which otherwise violate `∀ kv ∈ k1'.handles, own1 kv.1` as soon as `nextHandle` crosses a partition boundary, making universal transition safety vacuously true).
2. **Duplicated channel handles require reference-counted endpoint closure.** Asserting `peerClosed := true` on a peer channel when `zx_handle_close` closes `h` is unsound if `zx_handle_duplicate` (or `ZX_HANDLE_OP_DUPLICATE`) created another live handle to the same `ObjId` in any process or in-flight `rxQueue`; `peerClosed` asserts iff zero live handles and zero queued `MessagePacket` handles reference `ep.objId`.
3. **Intra-process multi-component packing requires capability branding and per-tenant slot quotas.** Co-locating multiple components inside one single-threaded Zircon process (`ZX_VM_COMPACT`) shares one kernel `HandleTable` and one port reactor. At the machine-code level where handles are bare `u32` integers, nothing prevents Component A from closing Component B's handles without whole-binary value-range proofs; at the Rust MIR level, private non-`Copy` `OwnedHandle` types with ghost ownership (`SepPCM`) isolate handle namespaces by construction. Furthermore, `shared_slot_pool_violates_noninterference` proves that a single shared `MAX_SLOTS` array allows Tenant A to exhaust all slots via `Directory.Open` and cause Tenant B's `Directory.Open` to fail; partitioning per-tenant quotas `(quotaA, quotaB)` (`\sum_i \text{quota}_i \le \text{MAX\_SLOTS}`) restores exact 2-run chronological trace non-interference (`partitioned_two_run_noninterference`) and per-wakeup worst-case step bounds (`wakeupSteps_dos_bound`).

## Boundaries

- **Restricted Mode & `@vdsocall` syscalls (`known not to apply`):** The `ValidSyscallPC` return-offset check in `do_syscall` does not apply to Restricted Mode EL0 `svc` transitions (`syscall_from_restricted` in `zircon/kernel/arch/arm64/exceptions.S:840-841`) or usermode-only `@vdsocall` functions.
- **Timing and microarchitectural side channels (`not examined`):** `partitioned_two_run_noninterference` proves logical state and sequence-ordered reply-stream non-interference; shared-thread queueing latency (bounded per wakeup by `wakeupSteps_dos_bound`) and CPU cache/branch-predictor state remain observable across co-located tenants unless separately mitigated.
- **`zx_channel_call` / `zx_channel_call_etc` two-phase retry (`not examined` in Lean mechanization):** Source inspection of `channel.rs:394-535` confirms `channel_call_noretry` uses the same `prepare_write` `zr::defer` cleanup and `channel_call_epilogue` drops `reply` on `BUFFER_TOO_SMALL` (`channel.fidl:763-764`, unlike `zx_channel_read`!), but `ZirconHandleAndReactorInvariants.lean` mechanizes only `zx_channel_write`/`write_etc` and asynchronous port dispatch.
