## R348 — compilation-subject identity

Both nightly `unit-build` outputs have six planned units and two roots. The same `probe-dep` Cargo target appears twice with distinct feature vectors `host` and `normal`; the app contributes library, binary, build-script compilation, and `run-custom-build` units. `unit-test` gives the app library both `build` and `test` modes, and combines `dev,normal` for the non-host dependency. `unit-release` changes the effective profile from `dev` to `release`. `unit-target --target aarch64-apple-darwin` gives ordinary app/dependency units a non-null platform while the build dependency and build-script compilation remain host units. This directly demonstrates the baseline's warning that package or target name alone cannot identify the tested planned units.

For **each** of the five nightly graph commands, the two JSON objects have equal roots, units, profiles, features, modes, platforms, and edges after removing one new serialized field: the newer nightly adds `profile.trim_paths: "none"` to every unit; the pinned nightly omits it. Thus the unit-graph JSON schema differs even in this default configuration. This is a statement about the exposed projection, not proof that `trim_paths` changes internal `Unit` equality or that all Cargo versions have an otherwise identical graph. Stable Cargo 1.98.1 rejected all five unstable graph requests, so no stable unit-graph subject tuple is claimed. Its successful builds provide only an execution cross-check.

## R349 — metadata and contextual features

Across all three versions, four `cargo metadata --format-version 1` variants produce the same structured JSON after removing the intentionally different `target_directory` and `build_directory` paths. For `probe-dep`, each resolve graph has **one** package node with the union `dev,host,normal,targeted`, including in the host and Windows `--filter-platform` cells of this fixture. `--features with-opt` activates the optional dependency edge and adds `probe-opt` to the active resolve graph. Metadata remains a package-level feature view here; the Windows-specific request's presence in the list should not be mistaken for an executed Windows unit.

In contrast, both nightlies' `unit-build` output contains separate `probe-dep` units with `host` and `normal` feature vectors; `unit-test` has `host` and `dev,normal`. Enabling `with-opt` adds one planned unit (six to seven). This concretely demonstrates the claim-specific representation gap for this reconstructed resolver-2 workspace: the single metadata feature list cannot encode its two simultaneous unit contexts. Stable's metadata agrees, but its stable-channel `-Z` rejection prevents the same unit-level observation there. The run does not exercise a Windows compilation or prove all target-filtering cases.

## R352 — planned graph and actual compiler processes

Both nightly `unit-build` graphs include the build-script compile unit and a distinct `run-custom-build` unit; neither JSON graph contains final compiler argv. In the real cold `-vv` build, **each** of the three versions logs six `Running` actions: five rustc invocations and one build-script execution. The app's downstream rustc command includes `--extern probe_dep=...` and the build-script-derived `PROBE_BUILD_TAG=host` environment value. An immediate unchanged second build logs no rustc action and reports both `probe-dep` and `probe-app` `Fresh`, although the same planned graph is obtainable. This separates plan membership from executed work for this fixture.

The newer nightly's **actual invocation transcript** differs from both earlier versions: its representative app rustc argv includes `-Z embed-metadata=no` and `--json=...unused-externs-silent`; observed `--out-dir`/`--extern` artifacts use paths under `debug/build/<package>/<hash>/out` rather than the pinned/stable `debug/deps` layout. The [raw cold-build logs](raw/) preserve exact commands and environment. These are version-specific observations of a combined Cargo/rustc toolchain; the fixture does not isolate which component caused each difference, test wrapper ordering, use a foreign target, or exhaust all late build-script outputs. The preceding stable source review already identified changed compiler argument/search-path code; this execution supplies a narrow concrete comparison, not an equivalence theorem.
