# Scheduler adequacy: generated execution domains and restricted quantifiers (Lean 4 toy model)

## Summary

This package is a kernel-checked Lean 4 model of the gap between a claim about **every interleaving** of a concurrent program and a claim about **every run of a generator**: a run function `gen : O → Prog α → List α` driven by a scheduler oracle `o : O`. Programs `Prog α` are finite straight-line programs built from atomic actions with sequential composition `p ; q` and binary parallel composition `p ∥ q`; the reference semantics `Interleavings p` lists all interleavings structurally. A generator `gen` is *complete* on `p` (`Complete gen p`) if every interleaving of `p` is `gen o p` for some oracle `o`, and *sound* on `p` (`Sound gen p`) if `gen o p` is an interleaving of `p` for every oracle `o`. Four concrete generators are studied: the per-step generator `runPerStep`, the shared-choice generator `runShared`, the deterministic scheduler `runRoundRobin`, and the countermodel `runIgnoringSeq`.

One sentence per result (statements, hypothesis ledgers and witnesses are under [Findings](#findings)):

1. **`per-step-generator-sound`.** For every program `p`, every run produced by the per-step generator `runPerStep` (a fresh oracle bit at every parallel node on the path to the next action) is an interleaving of `p`.
2. **`per-step-generator-complete`.** For every program `p`, every interleaving of `p` is the run of `runPerStep` for some oracle.
3. **`shared-choice-generator-sound`.** For every program `p`, every run produced by the shared-choice generator `runShared` (one oracle bit per scheduling step, reused at every parallel node on that step's root-to-action path) is an interleaving of `p`.
4. **`shared-choice-incomplete-nested-par`.** On the program `a ∥ (b ∥ c)` (distinct actions) `runShared` produces exactly the 4 distinct runs `a b c`, `a c b`, `c a b`, `c b a` while the program has 6 distinct interleavings, and on `a ∥ ((b ∥ c) ; d)` (distinct actions) it produces exactly 5 distinct runs while the program has 8 distinct interleavings; on both programs `runShared` is not complete.
5. **`shared-choice-complete-without-nested-par`.** For every program `p` in which no parallel composition occurs inside a component of another parallel composition (`NoNestedPar p`), `runShared` is complete on `p`.
6. **`shared-choice-complete-iff-no-nested-par`.** For every program `p` whose action labels are pairwise distinct, `runShared` is complete on `p` iff no parallel composition of `p` occurs inside a component of another parallel composition.
7. **`deterministic-scheduler-single-run`** (reference point). For every program `p`, the deterministic scheduler `runRoundRobin` produces the same run for every oracle, that run is an interleaving of `p`, and `runRoundRobin` is complete on `p` iff `p` has exactly one distinct interleaving.
8. **`universal-transfer-iff-complete`.** For every generator `gen` (with any oracle type) and program `p`: the implication "`P` holds on every run generated by `gen` ⇒ `P` holds on every interleaving of `p`" holds for every trace property `P` iff `gen` is complete on `p`.
9. **`existential-transfer-iff-sound`.** For every generator `gen` (with any oracle type) and program `p`: the implication "some run generated by `gen` satisfies `Bad` ⇒ some interleaving of `p` satisfies `Bad`" holds for every trace property `Bad` iff `gen` is sound on `p`.
10. **`representative-transfer`.** For every symmetric relation `I` on actions, generator `gen`, program `p` and trace property `P`: if `P` is invariant under the trace equivalence generated by `I`, and the trace class of every interleaving of `p` contains a run generated by `gen`, then `P` holding on every run generated by `gen` implies `P` holding on every interleaving of `p`.
11. **`invariant-transfer-iff-meets-every-class`.** For every symmetric relation `I`, generator `gen` and program `p`: every trace property invariant under the trace equivalence generated by `I` transfers from the runs generated by `gen` to all interleavings of `p` iff the trace class of every interleaving of `p` contains a run generated by `gen`.
12. **`sound-generator-meets-every-class-under-full-independence`.** For every relation `I` under which all distinct actions are related, every program `p`, and every generator `gen` with an inhabited oracle type: if `gen` is sound on `p`, then every interleaving of `p` is reachable by commuting adjacent `I`-related actions from some run generated by `gen`.
13. **`shared-choice-misses-class-when-b-conflicts-with-a-and-c`.** Under the relation `indepOnlyAC`, which is symmetric and irreflexive and relates only `a` and `c`, the sound generator `runShared` on `a ∥ (b ∥ c)` produces no run that is trace-equivalent to the interleaving `b a c`; hence `runShared` does not meet every trace class of `a ∥ (b ∥ c)`.
14. **`per-step-generator-oracle-bound`.** For every program `p`, the run of `runPerStep` on `p` is unchanged when the oracle is truncated to its first `schedPoints p` bits.
15. **`shared-choice-generator-oracle-bound`.** For every program `p`, the run of `runShared` on `p` is unchanged when the oracle is truncated to its first `schedPoints p` bits, and also when it is truncated to its first `size p - 1` bits.
16. **`bounded-adequacy-check-correct`.** For every action type `α` with decidable equality, every generator `gen` with list-of-bits oracles, program `p` and bound `n` such that the run of `gen` on `p` depends only on the first `n` oracle bits (`OracleBounded gen p n`), `checkComplete gen p n` returns `true` iff `gen` is complete on `p`, and `checkSound gen p n` returns `true` iff `gen` is sound on `p`.
17. **`claims-equivalent-iff-complete-and-sound`.** For every generator `gen` (with any oracle type) and program `p`: "`P` holds on every run generated by `gen`" is equivalent to "`P` holds on every interleaving of `p`" for every trace property `P` iff `gen` is both complete and sound on `p`; and "some run generated by `gen` satisfies `Bad`" is equivalent to "some interleaving of `p` satisfies `Bad`" for every trace property `Bad` iff `gen` is both complete and sound on `p`.

Design consequence (derived, not a theorem; see the modeling-bridge lines under Findings): a sentence of the form "for every schedule, `P`" about a program whose schedules are the runs of a generator `gen` may be read as "for every interleaving, `P`" as a rule valid for all properties `P` only together with completeness of `gen` on that program (result 8), and "some schedule exhibits `Bad`" may be read as "some interleaving exhibits `Bad`" for all `Bad` only together with soundness (result 9); otherwise the sentence should name its generator ("for every run of `runShared`").

What these results do **not** show is recorded first under [Boundaries](#boundaries), per result.

## Applicability

**Model fidelity: this is a toy model.** All definitions live in the Lean namespace `Toy.SchedAdequacy` of a self-contained Lake project (`lean/`, library `SchedAdequacy`, modules `Basic`, `Traces`, `Bounded`, `Lemmas`, `Examples`, `Results`). The definitions are meant to capture:

- **Concurrent programs.** `Prog α` with atomic actions (`act`), sequential composition (`seq`, written `;`) and binary parallel composition (`par`, written `∥`). Every program is finite, terminates, and performs at least one visible action: there is no `skip`, no silent step, no loop, no blocking or synchronization, no shared-memory model beyond optional state-transformer semantics used in examples, no weak memory, no fairness, and no infinite execution. Because `par` is binary, three or more peer threads must be written with nested `par`.
- **"Every interleaving".** `Interleavings p`: concatenation for `seq`, shuffle for `par`. This plays the role of the semantics a plain-language claim refers to.
- **Generated execution domains.** `Gen O α := O → Prog α → List α`, an oracle-indexed run function, models a scheduler-driven step semantics, a randomized or systematic schedule explorer, or an operational semantics parameterized by a scheduling oracle. `Oracle := List Bool` is the concrete oracle type of the four example generators; an exhausted oracle answers `false`. The general transfer and adequacy theorems (results 8–12 and 17) hold for an arbitrary oracle type `O`.
- **Partial-order reduction representatives.** `TraceEquiv I` (the closure of swapping adjacent `I`-related actions), `TraceInvariant I P` and `MeetsEveryClass I gen p`, for a fixed relation `I` on action labels. For symmetric `I` these are Mazurkiewicz trace equivalence, invariance under it, and "every trace class contains a generated run". State-dependent (conditional) independence, persistent sets, sleep sets, stuttering and temporal logic are not modeled.

**Known gaps.** Real schedulers and testing tools interleave at the granularity of memory operations, block on synchronization, run unbounded loops and need fairness assumptions; none of this is modeled. The shared-choice generator `runShared` is a deliberately simple choice-reuse pattern (one bit per step, reused at every `par` node on that step's root-to-action path, never at sibling subtrees); it is not a model of any particular tool. Every connection between a theorem and a real system is stated as a separate `Basis: derived (modeling bridge)` line in Findings and is not kernel-checked. Model–system relation: none proved. These are statements about the toy model; they neither establish nor refute the corresponding claims about real schedulers, schedule explorers, testing tools, model checkers or memory models.

**Toolchain.** Lean 4 `v4.34.1` (`leanprover/lean4`, tag commit `5045d0056413266e57c625dcd7c365b10e377c52`), core library only: no Mathlib, no Lake `[[require]]` dependencies, no imports outside the package.

**Subjects.** `REPORT.json` lists the Lean toolchain release that checks every proof, and the primary sources for the known results restated here (trace theory, partial-order reduction, series-parallel composition, bounded schedule exploration, one-way commutation). The papers are prior art for the T0 results and background for the T1 results; the package does not examine any implementation described in them.

The per-step generator (G1): one fresh oracle bit at every `par` node on the path to the next action; a `par` node whose component finishes is replaced by the other component.

```lean
-- lean/SchedAdequacy/Basic.lean:137-151
def stepPerNode {α : Type} : Prog α → Oracle → α × Option (Prog α) × Oracle
  | .act x, o => (x, none, o)
  | .seq p q, o =>
      match stepPerNode p o with
      | (x, none, o') => (x, some q, o')
      | (x, some p', o') => (x, some (.seq p' q), o')
  | .par p q, o =>
      if o.headD false then
        match stepPerNode q o.tail with
        | (x, none, o') => (x, some p, o')
        | (x, some q', o') => (x, some (.par p q'), o')
      else
        match stepPerNode p o.tail with
        | (x, none, o') => (x, some q, o')
        | (x, some p', o') => (x, some (.par p' q), o')
-- lean/SchedAdequacy/Basic.lean:155-160
def runPerStepAux {α : Type} : Nat → Oracle → Prog α → List α
  | 0, _, _ => []
  | n + 1, o, p =>
      match stepPerNode p o with
      | (x, none, _) => [x]
      | (x, some p', o') => x :: runPerStepAux n o' p'
-- lean/SchedAdequacy/Basic.lean:166
def runPerStep {α : Type} : Gen Oracle α := fun o p => runPerStepAux p.size o p
```

The shared-choice generator (G2): one bit per step that crosses a `par` node (`needsChoice`), reused at every `par` node on that step's root-to-action path.

```lean
-- lean/SchedAdequacy/Basic.lean:172-175
def needsChoice {α : Type} : Prog α → Bool
  | .act _ => false
  | .seq p _ => needsChoice p
  | .par _ _ => true
-- lean/SchedAdequacy/Basic.lean:183-197
def stepShared {α : Type} : Prog α → Bool → α × Option (Prog α)
  | .act x, _ => (x, none)
  | .seq p q, b =>
      match stepShared p b with
      | (x, none) => (x, some q)
      | (x, some p') => (x, some (.seq p' q))
  | .par p q, b =>
      if b then
        match stepShared q b with
        | (x, none) => (x, some p)
        | (x, some q') => (x, some (.par p q'))
      else
        match stepShared p b with
        | (x, none) => (x, some q)
        | (x, some p') => (x, some (.par p' q))
-- lean/SchedAdequacy/Basic.lean:201-207
def runSharedAux {α : Type} : Nat → Oracle → Prog α → List α
  | 0, _, _ => []
  | n + 1, o, p =>
      let bo : Bool × Oracle := if needsChoice p then (o.headD false, o.tail) else (false, o)
      match stepShared p bo.1 with
      | (x, none) => [x]
      | (x, some p') => x :: runSharedAux n bo.2 p'
-- lean/SchedAdequacy/Basic.lean:217
def runShared {α : Type} : Gen Oracle α := fun o p => runSharedAux p.size o p
```

The results follow, one card each, in the order of `results.json`. Every card informs one design question: a claim about a concurrent program that says "for every schedule" or "on every interleaving" usually quantifies over the runs produced by a generated semantics (a step function driven by a scheduler oracle); which certificate must accompany such a claim so that its plain-language reading is justified? Each card states its specific part of that question.

### 1. `per-step-generator-sound` — every per-step run is an interleaving

**Lean:** `perStep_sound` · **Kind:** theorem · **Tier:** T0 · **Depth:** substantive

**Plain claim.** For every program p, every run produced by the per-step generator runPerStep (a fresh oracle bit at every parallel node on the path to the next action) is an interleaving of p.

**Statement** (verbatim source; proofs elided):

```lean
-- lean/SchedAdequacy/Results.lean:23
theorem perStep_sound (p : Prog α) : Sound runPerStep p := …
```

Unfolded (explicit) rendering of `perStep_sound`, checked to be definitionally equal to its statement:

```lean
∀ (p : Prog α) (o : Oracle), runPerStepAux p.size o p ∈ Interleavings p
```

The generator quantified over is `runPerStep` alone (definition under [Core definitions](#core-definitions)); the oracle `o` ranges over all finite bit lists.

**Hypothesis ledger.**

No hypotheses beyond the universally quantified data (the binders `p`, `gen`, … range over all values of their types).

**Non-vacuity witness.** Hypothesis-free; on a ∥ (b ∥ c) the run of every oracle is an interleaving (case analysis on the oracle) and all six interleavings occur. Lean: `perStep_adequate_parA_parBC`.

Witness `perStep_adequate_parA_parBC` (verbatim source):

```lean

```

**Non-claims.** See [Boundaries](#boundaries), entry `per-step-generator-sound`.

**Prior art.**

- Agreement between a small-step interleaving semantics and a structural shuffle semantics of sequential and parallel composition is classical; no source was found that states it for this oracle-driven formulation.
- J. L. Gischer, "The equational theory of pomsets", Theoretical Computer Science 61(2-3), 1988, pp. 199-224, doi:10.1016/0304-3975(88)90124-7. Series-parallel pomsets built by sequential and parallel composition; a Prog denotes such a pomset, and its linearizations correspond to the traces that Interleavings computes (correspondence not formalized here). Background for the reference semantics; it does not treat oracle-driven step functions.
- J. A. Bergstra, J. W. Klop, "Process algebra for synchronous communication", Information and Control 60(1-3), 1984, pp. 109-137, doi:10.1016/S0019-9958(84)80025-X. Axiomatizes sequential composition and parallel merge (with left merge and communication); without communication the merge of action sequences interleaves them, which is the shuffle used by Interleavings. Background only.
- J. W. de Bakker, J. I. Zucker, "Processes and the denotational semantics of concurrency", Information and Control 54(1-2), 1982, pp. 70-120, doi:10.1016/S0019-9958(82)91250-5. Metric denotational semantics of processes including the interleaving merge operator; background for giving parallel composition a structural interleaving meaning.
- R. Gu, Z. Shao, H. Chen, X. Wu, J. Kim, V. Sjoeberg, D. Costanzo, "CertiKOS: An extensible architecture for building certified concurrent OS kernels", OSDI 2016, USENIX, pp. 653-669. Mechanized (Coq) verification of concurrent kernel code against machine models in which interleaving is resolved by an environment context or scheduling oracle that supplies the next thread or CPU to run; a large-scale instance of an oracle-indexed execution semantics like Gen here, without the shuffle-semantics adequacy statements of this package.
- A. Hobor, A. W. Appel, F. Zappa Nardelli, "Oracle semantics for concurrent separation logic", ESOP 2008, LNCS 4960, Springer, pp. 353-367, doi:10.1007/978-3-540-78739-6_27. An oracle-driven operational semantics for a concurrent language; its oracles abstract the behaviour of other threads, a different notion from the scheduler-choice oracles here, cited only as an instance of oracle-parameterized concurrency semantics.

**Design question.** Is the per-step generator a trustworthy domain for existential claims (every run it produces is a real interleaving)?

Basis: execution (Lean kernel check) — every quoted declaration is kernel-checked by `lake build` under Lean `v4.34.1`; axioms and hashes are listed under [Evidence](#evidence).

Basis: derived (modeling bridge) — a schedule explorer that draws a fresh scheduler decision at every point where two parallel components are both enabled behaves like `runPerStep` on straight-line programs, so a behaviour it exhibits is a real interleaving. Real explorers also handle blocking, shared memory and unbounded loops, which this model omits.

### 4. `shared-choice-incomplete-nested-par` — on `a ∥ (b ∥ c)` and on `a ∥ ((b ∥ c) ; d)` (distinct actions), `runShared` is not complete

### 10. `representative-transfer` — for symmetric `I`, `I`-invariant `P`, and `gen` with a run in the trace class of every interleaving of `p`: `P` on every run of `gen` ⇒ `P` on every interleaving of `p`

**Lean:** `representative_transfer` · **Kind:** theorem · **Tier:** T0 · **Depth:** shallow

**Plain claim.** For every symmetric relation I on actions, generator gen, program p and trace property P: if P is invariant under the trace equivalence generated by I, and the trace class of every interleaving of p contains a run generated by gen, then P holding on every run generated by gen implies P holding on every interleaving of p.

**Statement** (verbatim source; proofs elided):

```lean

theorem representative_transfer {O : Type} (I : α → α → Prop) (hSym : Symmetric I)
    (gen : Gen O α) (p : Prog α) (P : List α → Prop) (hP : TraceInvariant I P)
    (hrep : MeetsEveryClass I gen p) :
    (∀ o, P (gen o p)) → ∀ t ∈ Interleavings p, P t := …
```

Unfolded (explicit) rendering of `representative_transfer`, checked to be definitionally equal to its statement:

```lean
∀ {O : Type} (I : α → α → Prop), (∀ x y, I x y → I y x) →
  ∀ (gen : O → Prog α → List α) (p : Prog α) (P : List α → Prop),
    (∀ s t, TraceEquiv I s t → P s → P t) →
    (∀ t ∈ Interleavings p, ∃ o, TraceEquiv I (gen o p) t) →
    (∀ o, P (gen o p)) → ∀ t ∈ Interleavings p, P t
```

For symmetric `I`, `TraceEquiv I` is an equivalence relation (`traceEquiv_equivalence_of_symmetric`), `TraceInvariant I P` is two-sided invariance (`traceInvariant_iff_two_sided_of_symmetric`), and `MeetsEveryClass I gen p` says that the trace class of every interleaving contains a generated run (`meetsEveryClass_iff_of_symmetric`); these bridge lemmas, in `Traces.lean`, justify the words "invariant" and "trace class" in the plain claim.

**Design question.** When may "for every run of gen" and "for every interleaving" (and the existential forms) be used interchangeably?

Basis: execution (Lean kernel check) — every quoted declaration is kernel-checked by `lake build` under Lean `v4.34.1`; axioms and hashes are listed under [Evidence](#evidence).

Basis: derived (modeling bridge) — a plain-language claim "for every interleaving" that is established over the runs of a generated semantics is justified for every property only with a completeness certificate for that generator, and an existential claim only with a soundness certificate; without them the claim should name the generator ("for every run of `gen`"). This citation rule is a design consequence argued here, not a theorem.

## Boundaries

### Non-claims (per result)

**1. `per-step-generator-sound`**

- Says nothing about real schedulers, memory models (no weak memory), fairness, or infinite executions: programs are finite, terminating, straight-line, and actions are atomic labels.
- This statement is about the toy step function runPerStep; it neither establishes nor refutes soundness of any other oracle-driven semantics (no relation between runPerStep and any other semantics is proved).
- Does not say that different oracles produce different runs: on a ∥ (b ∥ c) the oracles [false, false, false] and [false, false, true] both produce a b c (perStep_runs_on_length3_oracles_parA_parBC).
- Adequacy is about which traces occur, not how often: under a uniformly random oracle of length 3 the interleavings of a ∥ (b ∥ c) are not equally likely: of the eight oracles of length 3 on a ∥ (b ∥ c), two each produce a b c and a c b and one each produces the other four interleavings (perStep_runs_on_length3_oracles_parA_parBC).

**2. `per-step-generator-complete`**

- The statement asserts that an oracle exists; it exposes no oracle-construction function (the proof constructs one by induction).
- Completeness is relative to the package's Interleavings (finite shuffles of finite traces); no fairness, no infinite executions, no weak memory.
- Does not bound the oracle length; see per-step-generator-oracle-bound for that.
- Adequacy is about which traces occur, not how often: under a uniformly random oracle of length 3 the interleavings of a ∥ (b ∥ c) are not equally likely: of the eight oracles of length 3 on a ∥ (b ∥ c), two each produce a b c and a c b and one each produces the other four interleavings (perStep_runs_on_length3_oracles_parA_parBC).

**3. `shared-choice-generator-sound`**

- Soundness says the shared-choice runs are possible interleavings; it does not say they are all of them (they are not: shared_incomplete_parA_parBC).
- A universal claim proved over runShared does not transfer to all interleavings on this basis (see universal-transfer-iff-complete).
- runShared reuses one bit at a parent par node and at the par nodes nested below it on the same step's path; a step enters only one component of each par node, so the bit is never given to two sibling subtrees. The package does not model evaluating sibling subtrees with one unsplit random seed.
- Unlike Interleavings, the set of runs of runShared depends on how par is parenthesized and ordered: a ∥ (b ∥ c) and (a ∥ c) ∥ b have the same interleavings, but b a c is a run of runShared only on the second (shared_depends_on_parenthesization).

**4. `shared-choice-incomplete-nested-par`**

- Is about these two programs; the general picture for distinct labels is shared-choice-complete-iff-no-nested-par.
- Counts are of distinct traces; the package's Interleavings list may contain duplicates for programs with repeated action labels (not here).
- Does not claim that the missing interleavings matter for every property: for properties invariant under a trace equivalence see representative-transfer, and every final-state postcondition of Act.effPair transfers from runShared on a ∥ (b ∥ c) despite incompleteness (postconditions_transfer_from_incomplete_shared).
- Because par is binary, a flat pool of three or more peer threads must be written with nested par, such as a ∥ (b ∥ c); NoNestedPar p therefore allows at most two concurrently running sequential threads in each parallel region, and such pools are outside its scope.

**5. `shared-choice-complete-without-nested-par`**

- NoNestedPar is sufficient, not necessary in general: with repeated action labels runShared can be complete on a nested program (shared_complete_iff_needs_nodup); necessity is proved only for distinct labels (shared-choice-complete-iff-no-nested-par).
- Because par is binary, a flat pool of three or more peer threads must be written with nested par, such as a ∥ (b ∥ c); NoNestedPar p therefore allows at most two concurrently running sequential threads in each parallel region, and such pools are outside its scope.

**6. `shared-choice-complete-iff-no-nested-par`**

- Says nothing about programs with repeated labels beyond the sufficient direction (shared-choice-complete-without-nested-par).
- The necessity direction uses that every program performs at least one visible action: Prog has no empty program (skip) and no silent steps. In an extension with a no-op thread, skip ∥ (b ∥ c) would have distinct visible labels and a nested par while runShared could still produce both b c and c b (not proved here; the package has no such constructor).
- Because par is binary, a flat pool of three or more peer threads must be written with nested par, such as a ∥ (b ∥ c); NoNestedPar p therefore allows at most two concurrently running sequential threads in each parallel region, and such pools are outside its scope.
- This statement concerns the toy generator runShared; it neither establishes nor refutes completeness characterizations for other ways of sharing or splitting scheduler choices (no relation between runShared and any other generator is proved).

**7. `deterministic-scheduler-single-run`**

- Reference point: records the degenerate case of a generator with a single run; its only non-definitional input is per-step soundness (perStep_sound).
- runRoundRobin alternates consumed oracle bits, not threads: on (a ∥ b) ∥ (c ∥ d) it produces b a d c, running the whole left pair before the right pair (runRoundRobin_nested_runs_left_first).
- Does not claim that the single run is a good representative for any property; for that see representative-transfer.

**8. `universal-transfer-iff-complete`**

- Complete gen p is the right-hand side of the equivalence, not a hypothesis; there are no hypotheses.
- The direction from transfer to completeness quantifies over all trace properties P. For a restricted class of properties completeness is not needed: every postcondition on the final state of Act.effPair transfers from the incomplete runShared on a ∥ (b ∥ c) (postconditions_transfer_from_incomplete_shared); see also representative-transfer.
- A particular property can transfer from an incomplete generator (postconditions_transfer_from_incomplete_shared, representative_transfer_nonvacuous); incompleteness only guarantees that some property fails to transfer.
- Countermodels for an incomplete generator: the racy final value of x (x ≠ 3 on every runShared run of a ∥ (b ∥ c), x = 3 on b a c; shared_final_value_claim_does_not_transfer) and the ordering claim "b is not first" (shared_ordering_claim_does_not_transfer).

**9. `existential-transfer-iff-sound`**

- Sound gen p is the right-hand side of the equivalence, not a hypothesis; there are no hypotheses.
- Soundness justifies reporting a found bug as real; it does not justify concluding absence of bugs from not finding one (that needs completeness: universal-transfer-iff-complete).
- The countermodel generator runIgnoringSeq on a ; b is complete but unsound and produces the forbidden order b a (ignoringSeq_false_positive); completeness does not rescue existential claims.

**10. `representative-transfer`**

- This is the finite-trace shape of the partial-order-reduction soundness argument; it does not formalize persistent sets, sleep sets, ample sets, stuttering, LTL, or any reduction algorithm.
- Invariance of a property must be established separately; the package proves it for occurrence counts (traceInvariant_count) and for final states of semantics in which related actions commute (finalState_eq_of_traceEquiv).
- Commuting effects make the final state invariant, not the intermediate states: with Act.effInc, a and b commute, yet "every prefix leaves the counter nonnegative" holds on a b and fails on b a (commuting_does_not_make_prefix_safety_invariant). Safety properties along prefixes need a separate invariance argument.
- I is a fixed relation on action labels; state-dependent (conditional) independence is not modeled.
- MeetsEveryClass I gen p does not require the representatives to be interleavings: under fullIndep the constant generator constBA meets every class of a ; b although none of its runs is an interleaving (meetsEveryClass_without_sound). The transfer is one-directional: a property true on all interleavings need not hold on such runs (complete_alone_does_not_give_equivalence).
- For an asymmetric relation the directed forms (representative_transfer_directed, invariant_transfer_iff_meets_every_class_directed) still hold, with TraceEquiv read as one-way rewriting from a generated run to an interleaving; they do not speak of classes, and the reverse reading fails (reversed_reading_fails_without_symmetry).
- Says nothing about infinite executions or fairness.

**11. `invariant-transfer-iff-meets-every-class`**

- Characterizes transfer for the whole class of I-invariant properties at once; a property that is not invariant may still transfer (noninvariant_property_may_transfer).
- The class of properties is fixed by I: relating more pairs of actions gives fewer invariant properties and a representative condition that is easier to meet (not proved here).
- MeetsEveryClass I gen p does not require the representatives to be interleavings: under fullIndep the constant generator constBA meets every class of a ; b although none of its runs is an interleaving (meetsEveryClass_without_sound). The transfer is one-directional: a property true on all interleavings need not hold on such runs (complete_alone_does_not_give_equivalence).
- For an asymmetric relation the directed forms (representative_transfer_directed, invariant_transfer_iff_meets_every_class_directed) still hold, with TraceEquiv read as one-way rewriting from a generated run to an interleaving; they do not speak of classes, and the reverse reading fails (reversed_reading_fails_without_symmetry).

**12. `sound-generator-meets-every-class-under-full-independence`**

- Under full independence the invariant properties are exactly the permutation-invariant ones (traceInvariant_iff_perm_invariant_of_full_independence), so representative-transfer then applies only to properties that depend on the multiset of actions alone; for order-sensitive properties this result gives nothing.
- Does not say that a sound generator meets every class under a relation that leaves some pair of distinct actions unrelated: for indepOnlyAC it fails (meets_every_class_needs_full_independence), while for indepExceptBC, which also leaves a pair unrelated, runShared still meets every class of a ∥ (b ∥ c) (shared_meets_every_class_when_only_b_c_conflict).
- Soundness is more than the proof needs: it uses one run that is a permutation of the program's actions; runIgnoringSeq on a ; b is unsound and still meets every class (meets_every_class_unsound_permuting).
- Symmetry of I is not assumed separately because it follows from hI (symmetric_of_full_independence).
- A corollary for the shared-choice generator is proved separately: under full independence runShared meets every class of every program (shared_meets_every_class_of_full_independence).

**13. `shared-choice-misses-class-when-b-conflicts-with-a-and-c`**

- A conflict between the two nested actions b and c alone does not make runShared miss a class: with only b–c dependent it meets every class (shared_meets_every_class_when_only_b_c_conflict).
- For this program, an exhaustive evaluation over the 8 symmetric irreflexive relations on {a, b, c} found that runShared meets every class for each of the 4 relations that relate at least two of the three pairs, and misses a class for each of the other 4 (bounded evidence, not proved here; probe support/BoundedEvidence.lean). Three of these cases are also kernel-checked theorems: indepOnlyAC misses a class (shared_misses_class_when_b_conflicts_with_a_and_c), while indepExceptBC (shared_meets_every_class_when_only_b_c_conflict) and fullIndep, which relates all three pairs (meetsEveryClass_pos), meet every class.
- Is about one program and one relation.
- Escape hatches: using runPerStep, which is complete (perStep_adequate_parA_parBC); checking only a property that is invariant under indepOnlyAC and already holds on b a c, such as an occurrence count (traceInvariant_count); or writing the same actions as (a ∥ c) ∥ b, for which b a c is a run of runShared (shared_depends_on_parenthesization). Whether that parenthesization misses another class instead is not proved here.

**14. `per-step-generator-oracle-bound`**

- schedPoints p is an upper bound on the bits read. It is attained on a ∥ (b ∥ c) (two bits do not suffice, perStep_not_oracleBounded_below_schedPoints) and on a ∥ (b ∥ (c ∥ d)) (five bits do not suffice, schedPoints_spine4). With repeated labels fewer bits can suffice: on a ∥ (a ∥ a), where schedPoints = 3, no bit is needed (perStep_oracleBounded_zero_parA_parAA). An exhaustive evaluation over all 275 program shapes with 1 to 5 actions and pairwise distinct action labels found that for none of the 252 of them that contain a parallel composition (schedPoints p > 0) does truncating the oracle to its first schedPoints p - 1 bits leave every run of runPerStep unchanged (bounded evidence, not proved here; probe support/BoundedEvidence.lean). For the other 23 shapes, which have no parallel composition, schedPoints p = 0 and, with truncating natural-number subtraction, schedPoints p - 1 = 0, so that bound holds by perStep_oracleBounded itself.
- schedPoints counts per-node choices, not steps: on a right-nested chain of k parallel actions it is k (k - 1) / 2 (a direct calculation from the definition, not proved here for general k; the instance k = 4, value 6, is schedPoints_spine4), and a bounded check enumerates 2^(schedPoints p + 1) - 1 oracles.

**15. `shared-choice-generator-oracle-bound`**

- Neither bound is claimed minimal: on a ∥ (b ∥ c) two bits suffice (oracleBounded_pos), which equals size - 1 there, while schedPoints = 3.
- On a ∥ (b ∥ (c ∥ d)) the linear bound size - 1 = 3 is well below schedPoints = 6 (schedPoints_spine4); the schedPoints form is kept because it is shared with runPerStep.

**16. `bounded-adequacy-check-correct`**

- The answers true for checkComplete and false for checkSound are correct without any bound (complete_of_checkComplete, not_sound_of_checkSound); only the other two answers can be wrong without the bound (check_needs_oracleBounded).
- Combined with per-step-generator-oracle-bound and shared-choice-generator-oracle-bound this decides completeness and soundness of runPerStep and runShared on any given program (executed on three programs in check_on_examples); it is not a general decision procedure for arbitrary generators.
- oraclesUpTo n enumerates all 2^(n+1) - 1 bit lists of length at most n; with n = schedPoints p this is exponential in schedPoints p, which grows quadratically along right-nested chains of parallel actions (not proved here for general chains; the 4-action instance is schedPoints_spine4). For runShared the bound size p - 1 (shared_oracleBounded_size_pred) can be used instead.

**17. `claims-equivalent-iff-complete-and-sound`**

- The equivalences are per program p; adequacy on one program says nothing about another.
- Complete gen p and Sound gen p are the right-hand side, not hypotheses, and neither alone suffices: runIgnoringSeq on a ; b is complete and both equivalences fail (complete_alone_does_not_give_equivalence); runShared on a ∥ (b ∥ c) is sound and both fail (sound_alone_does_not_give_equivalence).
- A one-directional use needs only one of the two: concluding a claim about all interleavings from all generated runs needs completeness (universal-transfer-iff-complete); reporting a found behaviour as real needs soundness (existential-transfer-iff-sound).
- For a restricted class of properties a universal claim can transfer without completeness: every final-state postcondition of Act.effPair (from (0, 0)) transfers from the incomplete runShared on a ∥ (b ∥ c) (postconditions_transfer_from_incomplete_shared). This is one proved instance, not a theorem about postconditions of every state semantics.
- Adequacy is about which traces occur, not how often: under a uniformly random oracle of length 3 the interleavings of a ∥ (b ∥ c) are not equally likely: of the eight oracles of length 3 on a ∥ (b ∥ c), two each produce a b c and a c b and one each produces the other four interleavings (perStep_runs_on_length3_oracles_parA_parBC).
- That a plain claim "for every interleaving" over a generated semantics should cite an adequacy theorem, or else name the generator, is a design consequence argued in prose (derived, modeling bridge), not a theorem.


### Attractive stronger conclusions that are not established

- That `runShared` is complete on every program without "three-way" parallelism: the proved condition is `NoNestedPar p` (sufficient for every program; also necessary when the action labels are pairwise distinct). With repeated labels `runShared` can be complete on a program with a nested `par` (`shared_complete_iff_needs_nodup`).
- That a sound generator is always a valid set of trace-class representatives: the package proves this under full independence (`meets_every_class_of_sound_of_full_independence`), and it fails for `runShared` on `a ∥ (b ∥ c)` under `indepOnlyAC` (`shared_misses_class_when_b_conflicts_with_a_and_c`).
- That `schedPoints p` (or `size p - 1` for `runShared`) is the least number of oracle bits that determines every run of `runPerStep` (or of `runShared`) on `p`: minimality is not claimed (`oracleBounded_pos`, `perStep_oracleBounded_zero_parA_parAA`). That `schedPoints p` bits are attained for `runPerStep` is proved on two programs, `a ∥ (b ∥ c)` and `a ∥ (b ∥ (c ∥ d))` (`perStep_not_oracleBounded_below_schedPoints`, `schedPoints_spine4`), and supported by the bounded evidence below.
- That `checkComplete`/`checkSound` decide adequacy of an arbitrary generator: they decide it for a generator with list-of-bits oracles on a program for which a bound `OracleBounded gen p n` has been proved; `runPerStep` and `runShared` have such bounds on every program.
- That adequacy says anything about frequencies: under a uniformly random oracle of length 3, `runPerStep` does not produce the six interleavings of `a ∥ (b ∥ c)` with equal frequency (`perStep_runs_on_length3_oracles_parA_parBC`).
- That any statement here holds for a real scheduler, testing tool, model checker or memory model: such statements are modeling bridges (`Basis: derived`), not theorems. The model–system relation is `none proved`: the theorems neither establish nor refute the corresponding claims about real systems.

### Disproved or dropped statements

Every result listed in `results.json` is proved as stated. The following stronger candidate statements are false; each is refuted by a kernel-checked theorem of the package (quoted in the cards or under [Auxiliary lemmas cited by name](#auxiliary-lemmas-cited-by-name)):

- *For every generator `gen` and program `p`: "`P` holds on every run of `gen`" is equivalent to "`P` holds on every interleaving of `p`" for every trace property `P` iff `gen` is complete on `p`.* False: `runIgnoringSeq` on `a ; b` is complete and both the universal and the existential equivalence fail (`complete_alone_does_not_give_equivalence`). The proved characterization requires completeness and soundness (`claims-equivalent-iff-complete-and-sound`).
- *`runShared` misses a trace class of `a ∥ (b ∥ c)` whenever the two nested actions `b` and `c` conflict.* False: under `indepExceptBC`, where `b`, `c` is the one unrelated pair of distinct actions, `runShared` meets every class of `a ∥ (b ∥ c)` (`shared_meets_every_class_when_only_b_c_conflict`). The proved impossibility has `b` in conflict with both `a` and `c` (`shared-choice-misses-class-when-b-conflicts-with-a-and-c`).
- *Every trace property that transfers from the runs of a generator meeting every `I`-class to all interleavings is `I`-invariant.* False: the property "the trace is not `b a d`" is not invariant under `fullIndep`, yet it holds on every run of `runShared` on `a ∥ (b ∥ c)` (which meets every `fullIndep` class, `meetsEveryClass_pos`) and on every interleaving (`noninvariant_property_may_transfer`). The proved characterization quantifies over the whole class of `I`-invariant properties (`invariant-transfer-iff-meets-every-class`).
- *`representative_transfer` holds without `Symmetric I` when the representative condition is read from each interleaving to a generated run (`∀ t ∈ Interleavings p, ∃ o, TraceEquiv I t (gen o p)`).* False: for the one-way relation `oneWayAB` and the sound constant generator `constBA` on `a ∥ b`, this reversed condition holds and the `oneWayAB`-invariant property "the trace is `b a`" holds on every generated run, yet it fails on an interleaving (`reversed_reading_fails_without_symmetry`). Without symmetry the directed reading, from a generated run to each interleaving, is proved (`representative_transfer_directed`).

Two candidate generalizations are recorded as bounded evidence, not as theorems (see [Bounded evidence](#bounded-evidence-by-evaluation-not-proved-here)): that `schedPoints p - 1` oracle bits do not determine every run of `runPerStep` on any program with pairwise distinct labels that contains a parallel composition (checked for up to 5 actions), and the classification of the 8 symmetric irreflexive relations on `{a, b, c}` according to whether `runShared` meets every class of `a ∥ (b ∥ c)`.

## Revalidation

Requirements: `elan` (so that `lake` uses the toolchain pinned in `lean/lean-toolchain`) and `python3`. Run all commands from the package directory (the directory containing `REPORT.md`).

**1. One-command check.**

```bash
python3 support/revalidate.py .
```

`support/revalidate.py` copies `lean/` to a temporary directory (the package is not modified) and checks: (1) `lake build` succeeds; (2) no Lean source contains `sorry`, `admit` or `native_decide`, or declares an `axiom`; (3) every declaration of the library depends only on `propext`, `Classical.choice` and `Quot.sound` (Lean's `collectAxioms`); (4) for every Lean name referenced by `results.json` and every name recorded in `audit/statements.json`, the statement hash and the closure hash (defined under [Evidence](#evidence): SHA-256 of the `repr` of the type, and of the sorted closure lines) equal the recorded values. It prints `REVALIDATED` and exits with status 0 iff all checks pass.

**2. Build and axioms by hand.**

```bash
cd lean
lake build
cat > /tmp/SchedAdequacyAxioms.lean <<'EOF'
import SchedAdequacy
#print axioms Toy.SchedAdequacy.perStep_sound
#print axioms Toy.SchedAdequacy.perStep_complete
#print axioms Toy.SchedAdequacy.shared_sound
#print axioms Toy.SchedAdequacy.shared_complete_iff_noNestedPar_of_nodup
#print axioms Toy.SchedAdequacy.universal_transfer_iff_complete
#print axioms Toy.SchedAdequacy.representative_transfer
#print axioms Toy.SchedAdequacy.meets_every_class_of_sound_of_full_independence
#print axioms Toy.SchedAdequacy.check_correct_of_oracleBounded
#print axioms Toy.SchedAdequacy.universal_claims_equiv_iff_complete_and_sound
EOF
lake env lean /tmp/SchedAdequacyAxioms.lean
```

Each line of output must list a subset of `propext`, `Classical.choice`, `Quot.sound` (or report no axioms), matching `audit/axioms.json`. Any other card-referenced name from the table under [Evidence](#evidence) can be added to the file.

**3. Bounded evidence.** From `lean/` after `lake build`: `lake env lean ../support/BoundedEvidence.lean`; the output must equal the three lines recorded under [Evidence](#evidence).

**What a passing run establishes.** That the kernel accepts every proof under the pinned toolchain with the standard axioms, and that the statements and their definition closures are byte-for-byte the ones recorded here. It does not re-establish the modeling bridges, the bibliographic descriptions, or anything about real systems.
