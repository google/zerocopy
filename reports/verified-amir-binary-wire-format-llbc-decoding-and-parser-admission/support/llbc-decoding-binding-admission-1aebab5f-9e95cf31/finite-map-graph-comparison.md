## What the existing OCaml structures actually provide

[`Collections.MakeMap`, lines 267–285][ocaml] includes OCaml `Map.Make(Ord)` and adds wrappers. `of_list` folds `add` from left to right; `keys`/`values` project the ordered `bindings`. `add_strict` asserts the key is absent; `add_strict_or_unchanged` permits an existing binding only if its payload is structurally equal. Ordinary `of_list` does not call either strict helper. Its duplicate policy follows ordinary replacement by `Map.add`, so later entries overwrite earlier ones; that conclusion uses the delegated Map API contract, rather than a verified theorem about Charon's wrapper. The exact linked OCaml standard-library release and a formal refinement of its balanced tree were not established.

`MakeSet`, lines 371–387, includes `Set.Make(Ord)` and supplies union/list/disjointness helpers. Identifier-specific maps and sets arise from the generative `IdGen` namespaces. `IdGen` still represents IDs internally as integers, while separate opaque host types prevent mixing identifier kinds. Map validity does not imply that a referenced declaration exists or that a key matches a record's internal ID.

`MakeInjMap`, lines 512–570, has a map plus a cached codomain set. Its `add k e` asserts that `e` is not in that set, then updates both structures. `remove` finds the mapped value and removes it from the codomain set. This is a concrete additional invariant, not an ordinary finite-map property. Its `add` does not itself require a fresh key: replacing an existing key by a fresh value can leave the old value in the cached set. Therefore proving `elems = range(map)` requires a caller discipline such as fresh-key insertion or an additional preservation argument; the class name alone supplies no witness. This is a source-derived caller obligation, not a reported failure on an executed input.

Aeneas's [`SCC.Make`, lines 172–250][scc] consumes an association list from vertex identifiers to sets of outgoing identifiers, assigns local integer vertex labels, and constructs an imperative OCamlgraph directed graph. It deliberately uses `Imperative.Digraph.Concrete` rather than a global-counter-backed vertex implementation to avoid cross-domain races. The return representation contains SCC membership lists and a map from SCC IDs to dependency sets. `MakeReorder`, lines 28–42, explicitly relies on ordered set elements when stabilizing component order. Thus replacing graph storage by an extensionally equal unordered adjacency structure does not by itself establish byte-for-byte output stability or the same scheduling order. Connectivity and ordering are different obligations. The SCC conversion also asserts disjointness and coverage of the returned components before and after reordering (lines 244–274); these are partial consistency checks, not a full strong-connectivity theorem.

## Lean options and their actual invariants

| Option at Lean 4.35 | Representation/interface fact | Proof and algorithm implications |
| --- | --- | --- |
| `Std.HashMap α β` | Wrapper over `DHashMap α (fun _ => β)`; separate chaining over an array of buckets; bundled internal WF | Lookup/update lemmas; semantic `Equiv`, rather than ordinary equality of different bucket histories. Documentation recommends linear use to avoid expensive copies. |
| `Std.DHashMap α β` | `β : α → Type`; raw structure plus `wf : inner.WF` | Values depend on their keys; lookup requires lawful equality to transport a stored value to the queried key's fiber. WF is table validity, not application-specific declaration typing. |
| `Std.ExtHashMap α β` | Constant-value wrapper over extensional dependent hash maps | Actual equality extensionality is available; arbitrary iteration order is deliberately unavailable because observations must respect the quotient. |
| `Std.TreeMap α β cmp` | Size-bounded self-balancing search tree; keys equal when `cmp k a = .eq` | Ordered/min/max/order-statistic queries; comparator laws control rewrite theorems. `Equiv` plus sorted enumeration supports deterministic order-sensitive consumers. |
| `Array (Option β)` | Dense natural-number slots, with `none` available as an explicit hole | Array extensionality and set/push laws are concrete and simple; validity additionally needs the size/index domain and distinction between absent slot and out-of-bounds. |

These are sourced facts from [`HashMap.Basic`, lines 42–66][hash-basic], [`DHashMap.Basic`, lines 45–73][dhash-basic], [`ExtHashMap.Basic`, lines 35–62][ext-basic], and [`TreeMap.Basic`, lines 34–69][tree-basic]. Hash correctness needs equivalence of `BEq` and hash compatibility (`EquivBEq`, `LawfulHashable`); lawful equality gives the stronger identification with Lean equality. Tree correctness depends on orientation/transitivity of the comparator. These assumptions are part of the actual APIs and laws, not optional performance hints.

## Lookup, update, and domain laws already present in source

Write `⟦m⟧ k = m[k]?` for the partial-function view of a constant-valued map. Under `LawfulBEq`, this is a view on actual keys; under only equivalence/hash laws it is a view on equivalence classes, and representative-key observations need additional care.

- **Hash update:** `HashMap.getElem?_insert` states `(m.insert k v)[a]? = if k == a then some v else m[a]?`; `getElem?_erase` changes exactly that equality class to `none`. `mem_insert` states `a ∈ insert m k v ↔ k == a ∨ a ∈ m`; `contains_eq_isSome_getElem?` connects domain membership to successful lookup. The assumptions are `EquivBEq α` and `LawfulHashable α`. These are actual theorem statements, not proposed laws. [`HashMap.Lemmas`, lines 118–124, 264–286, 312–322][hash-laws].
- **Dependent hash update:** `DHashMap.get?_insert`, under `LawfulBEq α`, returns `some (cast (congrArg β (eq_of_beq h)) v)` when the keys match; otherwise it keeps the old lookup. The cast is essential when values inhabit different key-indexed types. `mem_iff_isSome_get?` relates domain to dependent lookup, and `get?_erase` supplies deletion. [`DHashMap.Lemmas`, lines 271–305][dhash-laws].
- **Tree update:** `TreeMap.getElem?_insert`/`getElem?_erase` use `if cmp k a = .eq`, under `TransCmp cmp`; `contains_eq_isSome_getElem?` supplies the domain link. This is comparator equivalence, which must be related to identifier equality if used as an actual-ID store. [`TreeMap.Lemmas`, lines 233–243, 280–290][tree-laws].
- **Array update:** `Array.getElem?_set`, for `i < xs.size`, states `(xs.set i v)[j]? = if i = j then some v else xs[j]?`. `size_set` preserves the length; `size_push` increases it by one; `getElem_push_lt` and `getElem_push_eq` preserve old entries and give the new last entry. `getElem?_eq_none_iff` characterizes out-of-bounds access. [`Array.Basic`, lines 43–53][array-basic]; [`Array.Lemmas`, lines 126–132, 187–198, 901–925][array-laws]. For `Array (Option β)`, the lookup result is nested optionality: `none` outside the array versus `some none` for an in-range hole. A refinement must state whether and how it flattens these.

Consequently the abstract insertion law `⟦insert m k v⟧ = Function.update ⟦m⟧ k (some v)` is a straightforward **derived** corollary for lawful key equality, not a newly proved result here. Its application to OCaml identifiers still needs a relation between OCaml IDs and Lean keys, equality/comparison coherence, and validation of integer ranges. Bundled table WF alone does not discharge those cross-language conditions.

## Extensional refinement is implemented, with concrete costs to the interface

Regular `HashMap.Equiv` is an equivalence relation; its namespace includes lookup, domain, size, insert/erase, filtering, and mapping congruences. `Equiv.of_forall_getElem?_eq` derives map equivalence from pointwise optional lookup under `LawfulBEq`. `equiv_iff_toList_perm` relates it to permutation of enumeration, not equality of list order. Thus an efficient regular hash table already has a mathematical observation interface without pretending internal bucket representations are equal. [`HashMap.Lemmas`, lines 2880–2928 and 2993–3045][hash-equiv].

The extensional option takes a further actual step: [`ExtDHashMap.Basic`, lines 64–103][extd] stores `Quotient (DHashMap.isSetoid α β)`. Its `lift` requires that the observer respect `~m`; `sound` and `exact` relate regular-map equivalence to equality of quotient values. The wrapper's `ExtHashMap.ext_getElem?`, under `LawfulBEq`, states that pointwise lookup equality implies equality of maps. With only `EquivBEq`/`LawfulHashable`, `ext_getKey_getElem?` requires both representative-key equality and value lookup equality. This distinction prevents silently identifying arbitrary equivalent representatives when their concrete keys remain observable. [`ExtHashMap.Lemmas`, lines 2332–2352][ext-laws].

The price is explicit and useful: one cannot freely expose an order-dependent bucket fold as an observer of an extensional map. A fold over regular hash storage either needs a result invariant under enumeration permutation or a separately chosen canonical ordering. Extensional hashes are therefore attractive for map equalities; regular maps plus `Equiv` are more direct when an algorithm needs efficient enumeration and can prove its own permutation invariance. This is an interface comparison, not a recommendation to alter Aeneas.

Tree maps supply a different deterministic bridge. `TreeMap.Equiv.getElem?_eq` preserves lookup; `equiv_iff_toList_eq`, under `TransCmp`, relates equivalent maps to equal ordered enumerations. That stronger enumeration interface matters for current SCC reordering, which explicitly depends on ordered sets. It still does not establish that the Lean comparator uses the same ordering as OCaml's ID comparator. [`TreeMap.Lemmas`, lines 3950–3965 and 4363–4368][tree-equiv].

Array refinement is also concrete: `Array.ext` uses equal size and pointwise in-bounds equality; `ext_getElem?` uses optional lookup equality; `ext'` uses equality of `toList`. These laws give dense table refinement without a hash or comparator hypothesis. Runtime copy behavior remains a separate performance matter: the inspected `Array.markLinear` documentation describes making an array unique and copying when the reference is shared. A persistent mathematical view is compatible with in-place updates on uniquely owned runtime arrays, but this supplement did not audit the native runtime implementation. [`Array.Basic`, lines 50–85 and 217–219][array-basic]; [`Array.Lemmas`, lines 218–222][array-laws].

## Applying these interfaces to the graph that Aeneas actually uses

The current SCC input can be viewed as a finite domain `V` and a relation `E u v := v ∈ adjacency(u)`. This is a **derived specification**, grounded in the actual map/set adjacency representation, not an already-located formal specification of the OCamlgraph call.

For `HashMap Id (HashMap Id Unit)`, the stated domain/lookup laws and unit-map extensionality (`Equiv.of_forall_mem_unit_iff`) support preservation of `V` and `E` when adjacency tables are updated. For extensional hash maps the analogous `ext_mem_unit` proves equality of adjacency sets from membership equivalence. For tree maps/sets the comparator relation must agree with ID equality, but sorted traversal additionally supplies an order-preserving route to existing deterministic reordering. For dense `Array (Array Id)` adjacency, array extensionality proves slot-level correspondence; membership of inner arrays ignores duplicate edges, so an SCC proof must state whether duplicate edges are allowed and show they do not change reachability. These examples instantiate actual library laws, while the graph-level correspondence itself remains to be proved.

No collection law alone proves Tarjan/OCamlgraph correctness, SCC partition completeness, preservation of reachability, acyclicity of the condensation graph, or the ordering policy. The inspected Aeneas conversion creates a finite ID-to-integer map and inverse map, adds graph vertices/edges, computes SCCs, then reorders them. A refinement needs an injective ID/vertex correspondence, closed edge endpoints, partition/strong-connectivity properties, and dependencies preserving inter-component edges. It also needs a separate statement for deterministic ordering. Graph representations in mathlib were not examined: the concrete question here is a directed dependency graph with order-sensitive output, so an undirected simple-graph API would not settle it without additional work.

## Bounded conclusions and revalidation

Lean 4.35 supplies researched, concrete lookup/update/domain/extensionality interfaces for all five compared storage choices. Extensional hashes implement an actual quotient bridge; regular hashes expose equivalence and permutation-based enumeration; trees add ordered-enumeration equivalence; arrays give size/index extensionality. These substantially reduce the foundational facts that would otherwise need to be rediscovered. They do not establish a verified refinement of Charon/Aeneas's present OCaml structures, application invariants, or SCC implementation.

Revalidate by comparing the named Lean theorem statements and assumptions, the quotient/equivalence definitions, OCaml `MakeMap`/`MakeInjMap` wrappers, and SCC conversion/order code. A changed comparator/hash law, map-equivalence relation, traversal policy, or cached codomain invariant can change the applicable proof interface. No benchmark, native execution, or compilation was performed; source complexity/copying descriptions are documentation, not measured performance claims.
