# V1 annotation parsing and diagnostics: historical evidence

## Summary

Mainline V1 uses a line-oriented indentation grammar over Rust doc comments; separate branches explored verbatim Lean and a Chumsky parser without becoming the active path. The historical diagnostics path moved from custom `Diagnostics.lean` to direct `lean --json`.

## Applicability

Source, tests, docs, and local Git history for Anneal V1/Hermes. The verbatim Lean and whole-document parser claims are tied to their separate identified historical commits/branches, not current mainline V1.

## Findings


This is a historical V1 report, read at `bd0956be9` on `main` (27 September 2026). It does not define current Anneal design. [PRINCIPLES](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/PRINCIPLES.md) governs the user promise and [DESIGN](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/DESIGN.md) deliberately leaves the annotation language and result schema open. `anneal/v1/AGENTS.md` identifies V1 documentation as historical. This investigation used source, checked-in tests, documentation, and Git history; it did not run a build or tests. Scratch location: `$CHECKOUT_LOCAL_TOOLS/scratch/v1-annotations-diagnostics/`.

### What is checked in on main

V1 scans each Rust source file with `syn::parse_file`, visits its Rust AST, and processes documentation attributes on supported items. A Rust syntax error produces a spanned `AnnealError::Syn`; an annotated nested item is rejected because V1 cannot name it from the external Lean file ([`parse/mod.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/parse/mod.rs#L260), [`parse/mod.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/parse/mod.rs#L326)). This is one Rust AST **per scanned source file**, not one AST shared with Charon or Lean.

The active `attr.rs` extracts `///`, `//!`, block doc comments, and literal `#[doc = "..."]` through `syn` attributes, then tries to recover byte spans in the original source. An exact text match enables a line span; escaped text, macro expansion, or other mismatch falls back to the full attribute span. The code splits multiline doc attributes into lines and strips `\r` when present ([`attr.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/parse/attr.rs#L193), [`attr.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/parse/attr.rs#L240)). This is source-span recovery, not a Rust or Lean lexer.

A fence is recognized after trimming if it begins with at least three backticks. Its comma-separated info string must contain `anneal`; tokens before it are ignored, and the following mode is either default `spec`, explicit `spec`, or `unsafe(axiom)` for functions ([`attr.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/parse/attr.rs#L160), [`attr.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/parse/attr.rs#L363)). The parser collects doc lines until a trimmed line **starts with** the opening run of backticks. It rejects an unclosed block and more than one Anneal block on an item, but it does not validate a Markdown fence as a Markdown parser would ([`attr.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/parse/attr.rs#L328), [`attr.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/parse/attr.rs#L395)). For example, an indented inner three-backtick block can occur within an outer four-backtick annotation, while a fence-looking line at the beginning of Lean content could terminate the block. A `-- ``` ` Lean comment line is retained because it does not begin with backticks after trimming. The source tests cover nested fences and comments ([`attr.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/parse/attr.rs#L2022)).

After extracting the block, mainline V1 parses an Anneal-specific, line-oriented language. `context`, `requires`, `ensures`, `proof context`, `proof`, `isValid`, and `isSafe` have contextual checks; `requires` on a safe function and `isSafe` on a safe trait are rejected. The first keyword sets the baseline indentation; further keyword lines must be at precisely that indentation, and a continuation generally must be deeper ([`attr.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/parse/attr.rs#L874), [`attr.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/parse/attr.rs#L947), [`attr.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/parse/attr.rs#L1074)). Blank lines are retained in the active section. A top-of-block Lean comment before any keyword fails. The indentation metric is **byte length removed by `trim_start`**: tabs and spaces each count as one byte, while an em space counts as three. The tests demonstrate these cases, CRLF retention, keyword prefix protection, and indented `ensures:` being content of `requires` rather than a new clause ([`attr.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/parse/attr.rs#L1961), [`attr.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/parse/attr.rs#L2084), [`attr.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/parse/attr.rs#L2172), [`attr.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/parse/attr.rs#L2225)). V1 does not parse Lean expressions: after structural routing it passes their lines to generation. The V1 design prose describes this as treating Lean syntax as a black box ([`design.md`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/docs/design/design.md#L511)).

**Documentation limit:** the agent guide calls this a Python-style off-side rule and says a broken Lean expression line must be indented deeper than its preceding Lean line ([`04_specifications_and_syntax.md`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/docs/agent/04_specifications_and_syntax.md#L36)). The implementation compares a continuation to the **section baseline**, not to each previous Lean line. It therefore cannot guarantee the illustrated Lean expression nesting rule; Lean later judges that syntax. Similarly, stale comments inside `attr.rs` still describe the earlier grammar even on the verbatim rewrite branch (see below). Treat executable branches and tests as the source for historical behavior.

### Direct `lean --json` diagnostic path and its limits

Mainline V1 first builds Lean dependencies, then invokes `lake --keep-toolchain env lean --json` on each generated spec artifact ([`aeneas.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/aeneas.rs#L514), [`aeneas.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/aeneas.rs#L590)). It parses each stdout line as a `NativeLeanDiagnostic` with `fileName`, `data`, `severity`, `pos`, and optional `endPos`; recognized errors set `has_errors`, while warnings/information are rendered but do not fail verification. An unparseable line is logged and skipped. If Lean exits nonzero with no parsed diagnostics, V1 reports stderr and fails ([`aeneas.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/aeneas.rs#L612), [`aeneas.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/aeneas.rs#L642), [`aeneas.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/aeneas.rs#L886)). A successful process status with only unparseable stdout has no corresponding `has_errors` update in this code; that is a code-level diagnostic completeness gap to test, not evidence that Lean actually emits such output.

The generator records sidecar `SourceMapping` spans marked `Source`, `Synthetic`, or `Keyword` ([`generate.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/generate.rs#L13), [`generate.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/generate.rs#L30)). `resolve_mapping` finds overlaps, combines a multi-line span in one source file, and specially redirects a synthetic “declaration uses `sorry`” diagnostic toward a following mapped keyword when available ([`aeneas.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/aeneas.rs#L776)). The `DiagnosticMapper` renders a Rust source excerpt with `miette` when its path and byte range are usable, otherwise prints an external diagnostic fallback ([`diagnostics.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/diagnostics.rs#L227)). The checked-in `diagnostic_mapping` golden output shows mapped errors inside `proof context` and a direct `sorry` error ([`source`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/tests/fixtures/diagnostic_mapping/source/src/lib.rs), [`expected.stderr`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/tests/fixtures/diagnostic_mapping/expected.stderr)); it is narrower evidence than a guarantee that every generated Lean span maps correctly.

This arrangement is a **batch compiler diagnostic** interface. It does not provide a structured, versioned goal-state API or a complete parse tree for the user-authored Lean. Mapping can fall back to generated Lean paths when source spans do not overlap, and source extraction may have only an attribute-wide span. `resolve_byte_offset` walks generated text by Unicode scalar positions and clamps out-of-range lines to EOF ([`aeneas.rs`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/src/aeneas.rs#L900)); byte/column conventions and Unicode cases deserve explicit fixtures before making exact-position claims. The V1 parser itself also reports local `miette` errors for malformed Rust/doc blocks; the `broken_doc_block` snapshot demonstrates an opening-fence source span ([`expected.stderr`](https://github.com/google/zerocopy/blob/bd0956be95c5f798f0c0484921b9b9d1fc6e9988/anneal/v1/tests/fixtures/broken_doc_block/expected.stderr)).

### Setup and prompt recommendation

For any next annotation/proof-interface prototype, pin an explicit branch and syntax contract before prompting an agent: `main` V1 uses Anneal directives; `dc12610c8` demonstrates verbatim Lean but is separate. Ask for one typed annotation IR that preserves item identity, exact Rust doc-comment bytes/spans, raw Lean text, mode, and fence metadata. Keep a small adversarial corpus: `///` without space, `#[doc]` escapes, multiline block docs, blank lines, tabs/Unicode whitespace, comments before directives, nested/backtick-looking content, multiple and unclosed fences, malformed Rust, and a non-ASCII diagnostic location. Have the prototype emit both parse errors and Lean JSON results with source-map provenance; make malformed or missing diagnostic output visibly incomplete. Compare emitted Lean and mapped diagnostics against fixed inputs, then use an actual Lean session only for a separately scoped goal-state experiment. Do not infer a current design obligation to use either V1's line grammar, the WIP Chumsky parser, or verbatim Lean from these historical artifacts.
