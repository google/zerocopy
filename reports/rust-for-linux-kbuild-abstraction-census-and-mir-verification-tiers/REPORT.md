# Rust for Linux Kbuild Compilation Architecture, Kernel Abstraction Census, and MIR Verification Stratification

## Summary

Verifying unmodified Rust code inside the mainline Linux kernel (`torvalds/linux@b6a9fa34ce4187cb69d3c588a4bbffc31ce5db8f`, `Linux 7.4-rc4`, byte-identical to `Rust-for-Linux/linux` `rust-next`) with an in-process `rustc_driver` MIR extractor and a Lean 4 verification backend is **architecturally high-leverage because `unsafe` authority is heavily concentrated in reusable kernel crates, while Kbuild's compilation model diverges from Cargo across six concrete compiler-invocation and ABI seams**:

1. **90.1% `unsafe` Concentration in Core Kernel Crates vs. Safe Leaf Drivers:** Across all `568` `.rs` files in `torvalds/linux@b6a9fa34ce4187cb69d3c588a4bbffc31ce5db8f` (`210,514` total lines; `357` non-vendored `.rs` files containing `113,738` lines and `2,208` `unsafe` blocks), **`1,870` `unsafe` blocks (`84.7%`) reside in `rust/kernel/`** (`169` files, `62,930` lines) and **`119` (`5.4%`) reside in `rust/pin-init/`** (`17` files, `7,452` lines)—together accounting for **`1,989 / 2,208` (`90.1%`)** of non-vendored kernel `unsafe` blocks. By contrast, all `129` driver and subsystem `.rs` files outside `rust/` (`37,606` lines) contain only **`201` `unsafe` blocks (`9.1%`)**: production block, Ethernet PHY, and PWM drivers (`drivers/block/rnull`, `drivers/net/phy`, `drivers/pwm/pwm_th1520.rs`) contain **`0` `unsafe` blocks**, `drivers/gpu/drm` (`6,724` lines) contains **`9`**, the `19,223`-line NVIDIA GSP GPU driver `drivers/gpu/nova-core` (`86` files) contains **`37`** (`0.19` per `100` lines, alongside `113` `zerocopy` trait uses), and `drivers/android/binder` (`10,436` lines) contains **`152`**. Furthermore, `torvalds/linux` vendors `zerocopy` `0.8.62` directly in-tree at `rust/zerocopy/` (`125` files, `34,504` lines, `302` `unsafe` blocks), making `zerocopy` proofs immediately applicable to an in-tree Linux kernel crate.
2. **Non-Cargo Two-Graph Kbuild Compilation and Bitcode C-Helper Linking:** Linux invokes `$(RUSTC)` directly from Make (`rust/Makefile`, `scripts/Makefile.build`) with `RUSTC_BOOTSTRAP=1` across a sliding toolchain window (`rustc >= 1.85.0` minimum; `1.95.0` on `powerpc`, `1.96.0` on `s390`) and zero Cargo manifests. Kbuild builds two disjoint crate graphs: a host proc-macro graph (`proc_macro2`, `quote`, `syn`, `macros`, `zerocopy_derive`, `pin_init_internal`) targeting the host ABI, and a freestanding kernel rlib graph (`core` compiled from source, `compiler_builtins`, `ffi`, `build_error`, `zerocopy`, `pin_init`, `bindings`, `uapi`, `kernel`, and leaf drivers/modules) compiled with `--sysroot=/dev/null`, `@include/generated/rustc_cfg` response files, soft-float bare-metal targets (`scripts/target.json` on `x86_64`, `aarch64-unknown-none-softfloat` on `arm64`), `-Cpanic=abort`, `-Copt-level=2`/`s`, `-Zsanitizer=kcfi`, and `include!(concat!(env!("OBJTREE"), "..."))` `bindgen` outputs. Across `69` leaf `.c` files under `rust/helpers/`, `439` `rust_helper_*` C shims wrap `static inline` kernel headers and C macros; when `CONFIG_RUST_INLINE_HELPERS=y`, Kbuild emits LLVM bitcode and runs `llvm-link --internalize` against `rust/helpers/helpers.bc` after MIR lowering.
3. **Why `rust-project.json` Cannot Serve as a Sound Verification Authority:** `scripts/generate_rust_analyzer.py` enumerates crate roots only under `rust/`, `samples/`, and `drivers/` (omitting `lib/`, `mm/`, and future subsystem trees), injects placeholder environment values (`"RUST_MODFILE": "This is only for rust-analyzer"`), and drops target ABI, optimization, sanitizer, and `@rustc_cfg` flags. Authoritative MIR capture for Linux must therefore consume Kbuild's actual per-crate command state (`cmd_rustc_library` / `.o.cmd` or a Kbuild split-action rule) rather than `rust-project.json`.
4. **Live MIR Capture & End-to-End Verification Audit (`google/zerocopy@ccf9caacb6abc54b8b2cfd6db114f02cb87276e5`):** Probing `anneal-rustc-capture` and `cargo-anneal` across `18` targeted RfL compilation cases and `2` end-to-end Lean 4 `v4.34.1` (`ExecSeal` `linux_bwrap`, `axioms = ["propext"]`) verifications confirms that unmodified `torvalds/linux/rust/zerocopy/src/` (`0.8.62` with `--cfg zerocopy_unstable_linux --panic abort`) and `#![no_std]` `--panic=abort` Tier-0 scalar/offset/bitmask units (including diverging `unsafe extern "C" { fn rust_build_error() -> !; }` dead branches and `core::mem::offset_of!`) verify end-to-end today, while isolating nine deterministic fail-closed gates separating full `rust/kernel/` crates from admission.

## Findings

### 1. Kbuild `rustc` Invocation Architecture and Non-Cargo Crate Topology

#### 1.1 Toolchain Window, `RUSTC_BOOTSTRAP`, and `@rustc_cfg` Response Files

Basis: source

Linux does not pin a single nightly `rustc` commit. Instead, `scripts/min-tool-version.sh:33-44` defines a minimum supported stable floor—`rustc >= 1.85.0` by default (`1.95.0` on `CONFIG_PPC`, `1.96.0` on `CONFIG_S390`), `llvm >= 17.0.1` (`18.0.0` on `CONFIG_LOONGARCH`), and `bindgen >= 0.71.1`—while top-level `Makefile:648` exports `RUSTC_BOOTSTRAP=1` globally and `Makefile:486` passes `-Astable_features` so a single kernel revision builds across `rustc` `1.85` through `1.98+`.

Conditional compilation combines Kconfig symbols with compiler-version capability probes inside a generated response file `@$(objtree)/include/generated/rustc_cfg`, appended to every kernel Rust invocation at `scripts/Makefile.lib:175`. Inspecting `init/Kconfig:2022-2150` and `rust/kernel/lib.rs:14-49` shows two distinct mechanisms:

- **Compiler-version feature gates:** `Kconfig` probes `CONFIG_RUSTC_VERSION` and emits `--cfg CONFIG_RUSTC_HAS_COERCE_POINTEE` (`rustc >= 1.84`, toggling `#![feature(derive_coerce_pointee)]` vs. legacy `#![feature(coerce_unsized, dispatch_from_dyn, unsize)]` at `rust/kernel/lib.rs:32-45`) and `--cfg CONFIG_RUSTC_HAS_ERASED_TRAIT_BOUNDS`.
- **Per-crate unstable feature allowlists:** `rust/kernel/lib.rs:14-49` enables `#![feature( arbitrary_self_types, arbitrary_self_types_pointers, asm_const, asm_goto, cfg_sanitize, container_of, core_intrinsics, inline_const, lint_reasons, offset_of_nested, raw_ref_op, slice_range, type_alias_impl_trait, used_with_arg )]` (version-gated where stabilized), while `scripts/Makefile.build:347-360` restricts leaf driver crates via `-Zallow-features=arbitrary_self_types,asm_goto,generic_arg_infer,used_with_arg` and injects crate-level attributes `-Zcrate-attr=no_std` and `-Zcrate-attr='feature(arbitrary_self_types, ...)'` from the command line without requiring `#![no_std]` in every driver file.

#### 1.2 Disjoint Host Proc-Macro and Freestanding Kernel Crate Graphs

Basis: source

`rust/Makefile:9-98, 597-821` constructs two separate dependency DAGs with zero Cargo metadata:

1. **Host proc-macro shared libraries (`--out-dir $(objtree)/rust/host`, host target & sysroot, `-Copt-level=2`):**
   - `libproc_macro2.rlib` → `libquote.rlib` → `libsyn.rlib` (vendored under `rust/{proc-macro2,quote,syn}/` to keep kernel builds hermetic and offline).
   - `libmacros.so` (`rust/macros/lib.rs`, `edition=2021`): implements `#[module]`, `#[vtable]`, `Zeroable`, `fmt!`, `concat_idents!`, `paste!`, and `kunit_tests!`.
   - `libzerocopy_derive.so` (`rust/zerocopy-derive/`, vendored `0.8.62`, compiled with `--cfg zerocopy_unstable_linux`).
   - `libpin_init_internal.so` (`rust/pin-init/internal/`).
2. **Freestanding kernel target rlibs (`--sysroot=/dev/null`, `-Zunstable-options`, `-L $(objtree)/rust`):**
   - `libcore.rlib` (`rust/Makefile:78, 688-752`): compiled directly from `$(RUST_LIB_SRC)/core/src/lib.rs` (`edition=2024` when `CONFIG_RUSTC_VERSION >= 108700`, else `2021`) with `-Zforce-unstable-if-unmarked`, followed by `objcopy --redefine-sym` (`rust/Makefile:688-710`) redirecting compiler-emitted float/128-bit symbols to prevent unintended libcall linkage.
   - `libcompiler_builtins.rlib` (`rust/compiler_builtins.rs`): minimal `#![no_core]` shim preventing `rustc` from pulling upstream `compiler_builtins` soft-float routines.
   - Tier-A foundation rlibs: `libffi.rlib` (`rust/ffi.rs`), `libbuild_error.rlib` (`rust/build_error.rs`), `libzerocopy.rlib` (`rust/zerocopy/src/lib.rs`, vendored `0.8.62` compiled with `--cfg zerocopy_unstable_linux --extern zerocopy_derive`), and `libpin_init.rlib` (`rust/pin-init/src/lib.rs`, `--extern pin_init_internal --extern macros`).
   - Tier-B generated FFI rlibs: `libbindings.rlib` (`rust/bindings/lib.rs`) and `libuapi.rlib` (`rust/uapi/lib.rs`), each expanding `bindgen`-generated files via `include!(concat!(env!("OBJTREE"), "/rust/bindings/bindings_generated.rs"))` (`rust/bindings/lib.rs:53-69`, `rust/uapi/lib.rs:42`).
   - Tier-C `libkernel.rlib` (`rust/kernel/lib.rs`, `--extern ffi --extern build_error --extern pin_init --extern macros --extern bindings --extern uapi --extern zerocopy --extern zerocopy_derive`), which defines the kernel's `#[panic_handler]` (`rust/kernel/lib.rs:182`, invoking `bindings::BUG()`).
   - Tier-D built-in subsystems and loadable `.ko` modules (`scripts/Makefile.build:347-382`): compiled with `--extern pin_init --extern kernel --extern macros --extern build_error --extern ffi --extern zerocopy --extern zerocopy_derive` (`bindings` and `uapi` are intentionally omitted from driver `--extern` flags so drivers cannot bypass `kernel::*` abstractions without explicit `rust/Makefile` exemption).

Basis: source

Kernel target ABIs disable floating-point/SIMD registers and redzones while enabling kernel control-flow integrity and return-thunk mitigations:

| `x86_64` | `--target=$(objtree)/scripts/target.json` (`scripts/generate_rust_target.rs:197-240`) | `"rustc-abi": "softfloat"` (`>=1.98.0`) or `"x86-softfloat"` (`<1.98.0`), `"data-layout": "e-m:e-p270:32:32-p271:32:32-p272:64:64-i64:64-i128:128-f80:128-n8:16:32:64-S128"`, `-Ctarget-feature=-sse,-sse2,-sse3,-ssse3,-sse4.1,-sse4.2,-avx,-avx2`, `-Cno-redzone=y`, `-Ccode-model=kernel`, `-Zfunction-return=thunk-extern`, `-Zcf-protection=branch`, `-Cjump-tables=n`, `-Zpatchable-function-entry=16,16` (`arch/x86/Makefile:24-240`) |
| `arm64` | `--target=aarch64-unknown-none-softfloat` (`arch/arm64/Makefile:51`) | `-Zfixed-x18`, `-Zbranch-protection=bti,pac-ret`, `-Zuse-sync-unwind=n`, `-Zsanitizer=shadow-call-stack` (`arch/arm64/Makefile:51-122`) |
| `riscv64` | `--target=riscv64imac-unknown-none-elf` (or arch-configured JSON) | Soft-float integer ABI, `-Cno-redzone=y`, `-Zsanitizer=shadow-call-stack` (`arch/riscv/Makefile`) |

Global `KBUILD_RUSTFLAGS` (`Makefile:619-626, 939-951, 1082-1140`) sets `-Cpanic=abort`, `-Cembed-bitcode=n`, `-Clto=n`, `-Ccodegen-units=1`, `-Cforce-unwind-tables=n`, `-Copt-level=2` (or `-Copt-level=s` under `CONFIG_CC_OPTIMIZE_FOR_SIZE`; Kbuild never supports `-Copt-level=0` because `rust/kernel/build_assert.rs:12-71` relies on dead-branch elimination of `rust_build_error()` after const propagation and inlining), `-Cdebug-assertions=$(CONFIG_RUST_DEBUG_ASSERTIONS)`, `-Coverflow-checks=$(CONFIG_RUST_OVERFLOW_CHECKS)` (default `y`), and `-Zsanitizer=kcfi -Zsanitizer-cfi-normalize-integers` under `CONFIG_CFI_CLANG`.

Because `bindgen` cannot translate C `static inline` functions or function-like preprocessor macros (`spin_lock`, `rcu_read_lock`, `atomic_fetch_add_relaxed`, `readl`, `raw_copy_from_user`), `rust/helpers/helpers.c` `#include`s `69` leaf `.c` files defining **`439` `rust_helper_*` functions**. Under `-D__BINDGEN__`, `__rust_helper` expands to empty so `bindgen` emits extern declarations into `bindings_helpers_generated.rs`, where `sed` (`rust/Makefile:550-558`) rewrites `pub fn rust_helper_<name>` to `#[link_name = "rust_helper_<name>"] pub fn <name>`. Under `CONFIG_RUST_INLINE_HELPERS=y` (`lib/Kconfig.debug`, `rust/Makefile:659-669`, `scripts/Makefile.build:368-373`), `rustc` emits `--emit=llvm-bc` instead of `.o`, `clang` compiles `helpers.c` to `helpers.bc` (`__always_inline`), and `llvm-link --internalize` merges `helpers.bc` into each Rust compilation unit before `clang -c` codegen—meaning **at the MIR level every C helper remains an opaque `extern "C"` call boundary even when LTO-inlined into machine code**.

#### 1.4 Build-Graph Capture Integration: `rust-project.json` vs. Kbuild Command Authority

Basis: source + derived

Comparing three candidate non-Cargo capture integration surfaces against `scripts/generate_rust_analyzer.py:1-385`, `rust/Makefile`, and `anneal/docs/build-systems-and-receipts.md`:

- **`scripts/generate_rust_analyzer.py` (`make rust-analyzer` → `rust-project.json`) is insufficient for sound verification:** Line `345` scans only `samples/` and `drivers/` (missing `lib/find_bit_benchmark_rust.rs`, `mm/kasan/kasan_test_rust.rs`, and future `fs/` or `net/` crates), injects `"RUST_MODFILE": "This is only for rust-analyzer"`, and omits `--target`, `-Coverflow-checks`, `-Cdebug-assertions`, `-Zsanitizer=*`, and `@include/generated/rustc_cfg`. Using it for IDE discovery is benign, but using it as capture authority violates exact compiler-flag and source-hash fidelity.
- **Global `make RUSTC=anneal-rustc-capture` wrapper intercepts heterogeneous host+target actions:** A single kernel build invokes `$(RUSTC)` for version probing, `scripts/generate_rust_target` (a host binary), three host `proc-macro` `.so` crates, `#![no_core]` `libcore.rlib`, and freestanding `--sysroot=/dev/null` kernel rlibs. Live probe `P16` confirms that `anneal-rustc-capture`'s raw driver pass-through (`driver::run`) executes `@rustc_cfg`, `-Copt-level=2`, and `-Zallow-features` cleanly in `22.0 ms`, but whole-graph interception pollutes Kbuild's build critical path unless gated to target verification units.
- **Recommended Kbuild split-action / `.cmd` extraction contract:** Kbuild records the exact `cmd_rustc_library` / `cmd_rustc_objs` command line and dependency list for every target crate in `.<target>.cmd` alongside prebuilt upstream `.rmeta` artifacts (`libcore.rmeta`, `libbindings.rmeta`, `libkernel.rmeta`) in `$(objtree)/rust/`. A non-intrusive Kbuild verification generator (or `make rust-anneal-request` target) extracts the exact `@include/generated/rustc_cfg` tokens, `OBJTREE` path, `--extern <name>=$(objtree)/rust/lib<name>.rmeta` bindings, and `dep-info` source allowlist for any selected crate (`rust/kernel/` or a leaf driver) without modifying Kbuild's production `.o`/`.ko` rules.

Basis: source + derived

| Tier | Target Abstractions & Representative Files | Required Semantic & Capture Substrate | Kernel Leverage & Safety Properties |

## Boundaries

- **Live Kbuild C+Rust full-kernel build (`make LLVM=1 rustavailable` / `vmlinux`):** `not examined` via live full-kernel C compilation in this study; Kbuild command construction, `bindgen` invocation, `objcopy --redefine-sym`, and `llvm-link` helper internalization were established from authoritative `Makefile`, `rust/Makefile`, `scripts/Makefile.build`, and `arch/*/Makefile` source at `b6a9fa34ce4187cb69d3c588a4bbffc31ce5db8f`.
- **Cargo workspace discovery (`cargo metadata` / `Cargo.toml`):** `known not to apply` to upstream `torvalds/linux` kernel builds (`rust/Makefile` invokes `rustc` and `bindgen` directly without Cargo manifests).
- **Non-x86_64/arm64/riscv64 architecture runtime quirks (`powerpc`, `s390x`, `loongarch` inline assembly and big-endian `s390x` MMIO):** `not examined` beyond Kbuild `min-tool-version.sh` and `Makefile` target flags; `s390x` is notably big-endian whereas `x86_64`, `arm64`, `riscv64`, and `loongarch64` are little-endian.
- **Unmodified whole-crate capture of `rust/kernel/lib.rs` on `google/zerocopy@ccf9caacb6`:** Currently `unsupported` (`anneal-rustc-capture` rejects `--extern`, `--sysroot=/dev/null`, non-`x86_64-unknown-linux-gnu` targets, `LangItem::PanicImpl`, `extern "C"` ABIs, `patchable_function_entry`, `kcfi`/`shadow-call-stack` sanitizers, ADTs, raw pointers, and non-diverging calls).
- **Equivalence between LKMM (`tools/memory-model/linux-kernel.cat`) and C11/RC11 weak memory:** `known not to apply`; LKMM and RC11 are formally incomparable (LKMM relies on control/address dependencies, `smp_mb__after_atomic`, and RCU grace periods not present in RC11). Whether a compositional separation logic over LKMM covers all `rust/kernel/sync/` patterns without custom `herd7` side conditions remains `unknown` pending mechanization.
